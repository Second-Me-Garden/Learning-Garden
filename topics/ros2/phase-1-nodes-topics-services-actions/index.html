Phase 0 looked at a talker and listener someone else wrote; this phase writes your own. It starts with nodes and the graph, then what each of the three ways of communicating is for: a topic is an anonymous, many-to-many data stream, a service is one request and one reply, and an action is a long task that reports progress and can be cancelled midway — and an action is itself assembled from three services and two topics. Then it covers how a message type goes from a .msg file to generated C++ and Python code, how parameters are declared and validated, and finally writes the same node once in Python and once in C++ to compare the two client libraries.

核心概念

Core concepts

1. 节点与 graph

1. Nodes and the graph

节点是 graph 里一个有名字的参与者，负责一件边界清楚的事（读一个传感器、跑一个控制器）。在代码里它是一个对象：rclpy 里继承 rclpy.node.Node，rclcpp 里继承 rclcpp::Node。节点通过它创建的 publisher、subscription、service、client 和 action 与别人相连；这些连接和节点一起构成 ROS graph。节点不是进程：一个进程里可以有多个节点，Phase 4 的组合（composition）就是这样做的。

A node is a named participant in the graph that does one well-bounded job (read a sensor, run a controller). In code it is an object: in rclpy you subclass rclpy.node.Node, in rclcpp rclcpp::Node. A node connects to others through the publishers, subscriptions, services, clients and actions it creates; those connections together with the nodes form the ROS graph. A node is not a process: one process can hold several nodes, which is exactly what composition does in Phase 4.

名字的机制：节点有名字和命名空间，话题、服务名可以是绝对的（/chatter）、相对的（chatter，前面拼上节点的命名空间）或私有的（~/status，前面拼上节点的完整名字）。运行时可以不改代码地重映射：--ros-args -r chatter:=/robot1/chatter 改一个名字，-r __node:=my_talker 改节点名，-r __ns:=/robot1 改命名空间。正因为相对名字跟着命名空间走，同一个节点才能在一台机器上为两个机器人各起一份。

How names work: a node has a name and a namespace, and topic and service names can be absolute (/chatter), relative (chatter, prefixed with the node’s namespace) or private (~/status, prefixed with the node’s full name). At run time you can remap without changing code: --ros-args -r chatter:=/robot1/chatter changes one name, -r __node:=my_talker changes the node name, and -r __ns:=/robot1 changes the namespace. Because relative names follow the namespace, the same node can be started once per robot on one machine.

节点和 DDS 的对应关系：从 Foxy 起，一个进程（准确说是一个 rcl context）只创建一个 DDS participant，不论里面有几个节点；节点名本身通过一个隐藏话题（大致是 /ros_discovery_info）向别人通告，ros2 node list 就是读这个信息拼出来的。所以 Phase 0 里 ss 看到的端口数量跟进程数有关，跟节点数无关。细节以 rmw 实现为准。
How nodes map to DDS: since Foxy, one process (strictly, one rcl context) creates one DDS participant no matter how many nodes it holds; node names themselves are announced to others on a hidden topic (approximately /ros_discovery_info), and ros2 node list is assembled from that information. So the number of ports you saw with ss in Phase 0 depends on the number of processes, not of nodes. The details depend on the rmw implementation.

2. 话题：publisher 与 subscription

2. Topics: publishers and subscriptions

话题是一个有名字、有类型的数据通道。publisher 不知道谁在听，subscription 不知道谁在说；同一个话题可以有任意多个发布者和订阅者，名字和类型一致、QoS 兼容就连上。适合周期性的、丢一条也不要紧的数据：传感器读数、状态、/cmd_vel。

A topic is a named, typed data channel. A publisher does not know who is listening and a subscription does not know who is speaking; a topic can have any number of publishers and subscribers, and they connect when name and type match and the QoS is compatible. It suits periodic data where losing one message does not matter: sensor readings, state, /cmd_vel.

  • create_publisher(String, 'topic', 10) 里的 10 是 QoS 的历史深度（KEEP_LAST 10）：中间件最多为这个 writer 保留 10 条还没送达的消息，满了就丢最旧的。完整 QoS 在 Phase 3。
  • The 10 in create_publisher(String, 'topic', 10) is the QoS history depth (KEEP_LAST 10): the middleware keeps at most 10 not-yet-delivered messages for this writer and drops the oldest when full. Full QoS is in Phase 3.
  • publish() 把消息交给中间件后就返回，不等订阅者处理。订阅者的回调不是在消息到达时立刻被调用，而是在你的线程执行 spin 时由执行器（executor）从等待集合里取出来调用；不 spin，回调永远不会跑（Phase 2 细讲）。
  • publish() returns once it has handed the message to the middleware; it does not wait for subscribers. A subscriber’s callback is not called the moment a message arrives; the executor calls it when your thread is inside spin and picks the ready entity out of the wait set. Without spin, no callback ever runs (Phase 2 goes into detail).

回调拿到的是副本还是借来的内存：跨进程时，消息以 CDR 字节穿过 socket 或共享内存，接收端的 rmw 把字节反序列化进一个新分配的消息对象，再交给你的回调。所以你拿到的是自己的副本，可以留着、可以改，发布端之后再改它自己的对象也影响不到你。rclpy 还要多一步：把 C 结构体转换成 Python 对象，又是一次复制。rclcpp 的回调可以按 const T &、std::unique_ptr<T> 或 std::shared_ptr<const T> 等签名接收，签名决定了你能不能接管或修改这条消息。避免复制有两条路：同进程内的进程内通信（Phase 4，发布 unique_ptr 时把所有权直接移交给订阅者），以及 loaned message：发布者向中间件借一块内存（borrow_loaned_message()），原地填好再发布，订阅者拿到的是同一块内存的视图。后者只在 rmw 支持、类型是定长纯数据时可用，Phase 3 再讲，细节请查文档。

Does the callback receive a copy or borrowed memory? Across processes, the message crosses a socket or shared memory as CDR bytes, and the receiving rmw deserializes those bytes into a freshly allocated message object before handing it to your callback. So what you get is your own copy: you may keep it or modify it, and the publisher changing its own object afterwards cannot affect you. rclpy adds one more step, converting the C struct into a Python object, which is another copy. An rclcpp callback can accept the message as const T &, std::unique_ptr<T> or std::shared_ptr<const T>, among other signatures, and the signature decides whether you may take ownership of or modify it. There are two ways to avoid the copy: intra-process communication inside one process (Phase 4; publishing a unique_ptr hands ownership straight to the subscriber), and a loaned message: the publisher borrows memory from the middleware (borrow_loaned_message()), fills it in place and publishes it, and the subscriber gets a view of that same memory. The latter works only when the rmw supports it and the type is fixed-size plain data; Phase 3 covers it, and for the details check the docs.

3. 接口：.msg、.srv、.action 与 IDL

3. Interfaces: .msg, .srv, .action and IDL

ROS 2 的消息类型叫接口，写在三种文本文件里：

ROS 2 message types are called interfaces, written in three kinds of text file:

  • .msg：一组字段，每行「类型 名字」，例如 int64 num。
  • .msg: a list of fields, one “type name” per line, for example int64 num.
  • .srv：请求和响应两部分，用一行 --- 隔开。
  • .srv: a request part and a response part separated by a line of ---.
  • .action：目标、结果、反馈三部分，按这个顺序用两行 --- 隔开。
  • .action: goal, result and feedback parts, in that order, separated by two --- lines.

字段类型有 bool、int8 到 int64、uint8 到 uint64、float32、float64、string，别的消息类型（geometry_msgs/Point），以及数组：不定长 int32[]、定长 int32[3]、有上界 int32[<=5]。还可以写常量（int32 MAX=10）和默认值（int32 x 5）。

Field types include bool, int8 to int64, uint8 to uint64, float32, float64, string, other message types (geometry_msgs/Point), and arrays: unbounded int32[], fixed int32[3] and bounded int32[<=5]. You can also write constants (int32 MAX=10) and default values (int32 x 5).

从文件到代码：构建接口包时，rosidl 先把 .msg、.srv、.action 转成 OMG IDL（.idl）这一种中间表示，再由各个生成器从 IDL 生成 C 结构体、C++ 类、Python 类，以及每个中间件需要的 typesupport（告诉 rmw 怎么把这个类型序列化成 CDR）。生成器是插件：接口包在 package.xml 里只依赖 rosidl_default_generators（构建时）和 rosidl_default_runtime（运行时），并声明 <member_of_group>rosidl_interface_packages</member_of_group>，表示「我是接口包」，让构建工具把它排在用它的包前面。接口包必须是 ament_cmake 类型，哪怕只有 Python 节点用它。

From file to code: when an interface package is built, rosidl first converts the .msg, .srv and .action files into a single intermediate form, OMG IDL (.idl); generators then produce from the IDL the C structs, C++ classes, Python classes, and the typesupport each middleware needs (which tells the rmw how to serialize this type into CDR). The generators are plugins: in package.xml the interface package depends only on rosidl_default_generators (at build time) and rosidl_default_runtime (at run time), and declares <member_of_group>rosidl_interface_packages</member_of_group>, which says “I am an interface package” so that the build tools order it before the packages that use it. An interface package must be of type ament_cmake, even if only Python nodes use it.

完整类型名是 包名/msg/类型名，例如 std_msgs/msg/String；ros2 interface show 打印定义，ros2 interface list 列出所有已装的接口。官方建议尽量复用现有接口（std_msgs、geometry_msgs、sensor_msgs……），只有语义真的不同时才自定义；把接口放在单独的包里，节点包依赖它。

The full type name is package/msg/Type, for example std_msgs/msg/String; ros2 interface show prints a definition and ros2 interface list lists every installed interface. The official advice is to reuse existing interfaces (std_msgs, geometry_msgs, sensor_msgs…) where possible and define your own only when the meaning really differs; keep interfaces in a separate package that node packages depend on.

延伸阅读：Renard《ROS 2 From Scratch》讲自定义接口的章节；官方 Interfaces 与 Creating custom msg and srv files。

Further reading: the chapter on custom interfaces in Renard, ROS 2 From Scratch; the official Interfaces and Creating custom msg and srv files.

4. 服务：一问一答

4. Services: one request, one reply

服务是请求 / 响应：client 发一个请求，server 的回调算出响应并返回。适合短的、需要确认结果的操作：查询一个值、切换一个模式、触发一次标定。一个服务名应该只有一个 server（多个 server 同名时哪个回答是不确定的），client 可以有很多个。

A service is request / response: a client sends a request, and the server’s callback computes a response and returns it. It suits short operations whose outcome you need to confirm: query a value, switch a mode, trigger a calibration. A service name should have exactly one server (with several servers of the same name, which one answers is undefined); there can be many clients.

底下是什么：在基于 DDS 的 rmw 里，一个服务大致就是两个话题，一个承载请求、一个承载响应（Fast DDS 下名字大致是 rq/add_two_intsRequest 和 rr/add_two_intsReply）。每个请求带上 client 的身份和一个序列号，server 回复时原样带回，client 端据此把响应交给等待它的那个 future，其他 client 看到的响应会被丢掉。所以服务不是一条「连接」，只是两个话题加一套配对规则。

What lies underneath: in DDS-based rmw implementations a service is roughly two topics, one carrying requests and one carrying responses (under Fast DDS the names are approximately rq/add_two_intsRequest and rr/add_two_intsReply). Each request carries the client’s identity and a sequence number, which the server copies back into its reply; the client side uses them to hand the response to the future waiting for it, and responses meant for other clients are dropped. So a service is not a “connection”, just two topics plus a pairing rule.

client 的调用是异步的：rclpy 的 call_async() 和 rclcpp 的 async_send_request() 立即返回一个 future，响应要等执行器 spin 时才会被处理并填进去。在 main 里用 spin_until_future_complete 等它没问题；但如果在另一个回调里同步地等这个 future，而执行器是单线程的，处理响应的那个线程正是被你堵住的线程，于是永远等不到——这就是 Phase 2 要讲的死锁。
A client call is asynchronous: rclpy’s call_async() and rclcpp’s async_send_request() return a future at once, and the response is processed and filled in only when the executor spins. Waiting for it with spin_until_future_complete in main is fine; but if you wait for that future synchronously inside another callback on a single-threaded executor, the thread that would process the response is exactly the thread you are blocking, so the wait never ends — the deadlock Phase 2 covers.

5. 动作：可取消、有反馈的长任务

5. Actions: long tasks with feedback and cancel

「走到厨房」要几十秒，中途你想知道进度，也可能改主意。用服务做不到：一个请求只有一个响应，而且不能撤回。动作就是为此设计的：client 发一个目标（goal），server 接受后开始执行，期间不断发反馈（feedback），结束时给出结果（result）；任何时候 client 都可以请求取消（cancel）。Nav2 的 NavigateToPose 就是一个动作（Phase 6）。

“Go to the kitchen” takes tens of seconds; you want progress along the way, and you may change your mind. A service cannot do this: one request gets exactly one response and cannot be withdrawn. An action is designed for it: the client sends a goal, the server accepts it and starts executing, sends feedback repeatedly, and gives a result at the end; at any time the client may request a cancel. Nav2’s NavigateToPose is an action (Phase 6).

动作是用什么拼出来的：一个名为 /fibonacci 的动作在 graph 里是三个隐藏服务加两个隐藏话题，都挂在 /fibonacci/_action/ 下：

What an action is built from: an action named /fibonacci is, in the graph, three hidden services plus two hidden topics, all under /fibonacci/_action/:

  1. send_goal（服务）：请求里是 client 生成的 goal ID（一个 UUID）和目标本身；响应只说接受还是拒绝，加一个时间戳。server 的 goal 回调在这里做决定。
  2. send_goal (service): the request holds a goal ID generated by the client (a UUID) and the goal itself; the response only says accepted or rejected, plus a timestamp. The server’s goal callback makes the decision here.
  3. get_result（服务）：client 一拿到「已接受」就带着 goal ID 发出这个请求，server 先不回答，直到这个目标到达终态（SUCCEEDED、ABORTED 或 CANCELED）才把状态和结果一起回复。这是一种长轮询。
  4. get_result (service): as soon as the client sees “accepted” it sends this request with the goal ID; the server does not answer until the goal reaches a terminal state (SUCCEEDED, ABORTED or CANCELED), and then replies with the status and the result together. It is a form of long polling.
  5. cancel_goal（服务）：请求取消一个或多个目标；server 的 cancel 回调决定接受与否。接受只是把目标置为 CANCELING，真正停下来要靠执行代码自己检查并调用 canceled()。
  6. cancel_goal (service): asks to cancel one or more goals; the server’s cancel callback decides whether to accept. Accepting only moves the goal to CANCELING; actually stopping depends on the executing code checking for it and calling canceled().
  7. feedback（话题）：server 发布，带 goal ID；每个 client 只处理属于自己目标的那些。
  8. feedback (topic): published by the server, tagged with the goal ID; each client handles only the ones for its own goals.
  9. status（话题）：server 发布当前所有目标的状态列表（ACCEPTED、EXECUTING、CANCELING 和三种终态）。
  10. status (topic): the server publishes the status list of all its current goals (ACCEPTED, EXECUTING, CANCELING and the three terminal states).

所以动作没有自己的传输机制，ros2 action 和 rclcpp_action、rclpy.action 只是把这五个实体和目标状态机包装成一个对象。两种库的分工略有不同：rclpy.action.ActionServer 接受目标后替你调用 execute_callback；rclcpp_action 的 server 只调用 handle_goal、handle_cancel 和 handle_accepted，长时间的执行要你在 handle_accepted 里自己开线程或交给执行器，否则会堵住 spin（官方 C++ 教程就是开一个 std::thread）。

So an action has no transport of its own; ros2 action, rclcpp_action and rclpy.action merely wrap these five entities and the goal state machine into one object. The two libraries divide the work slightly differently: rclpy.action.ActionServer calls your execute_callback for you after accepting a goal; the rclcpp_action server calls only handle_goal, handle_cancel and handle_accepted, and the long-running execution is yours to start in handle_accepted on a thread of your own or through the executor, or it blocks spin (the official C++ tutorial starts a std::thread).

6. 参数：节点自己持有的配置

6. Parameters: configuration held by each node

ROS 2 没有全局参数服务器，参数属于各自的节点。机制分四步：

ROS 2 has no global parameter server; parameters belong to their own node. The mechanism has four parts:

  1. 声明：declare_parameter('my_parameter', 'world') 给出名字和默认值，默认值同时确定了类型。默认情况下未声明的参数不能被设置，类型声明后也不能改：给一个 string 参数设整数会被拒绝。
  2. Declare: declare_parameter('my_parameter', 'world') gives the name and a default value, and the default also fixes the type. By default, undeclared parameters cannot be set, and a declared type cannot change: setting an integer on a string parameter is rejected.
  3. 覆盖：启动时用 --ros-args -p name:=value 或 --ros-args --params-file file.yaml 给的值，会在声明那一刻替换默认值。YAML 顶层是节点名（/** 匹配所有节点），下一层固定是 ros__parameters。
  4. Override: values given at start-up with --ros-args -p name:=value or --ros-args --params-file file.yaml replace the default at the moment of declaration. The top level of the YAML is the node name (/** matches every node), and the next level is always ros__parameters.
  5. 远程读写：每个节点自动提供一组服务，~/list_parameters、~/get_parameters、~/set_parameters、~/describe_parameters 等。ros2 param list/get/set/dump 只是这些服务的客户端；你在 Phase 0 里看到 talker 有一串参数服务就是这个原因。
  6. Remote read and write: every node automatically offers a set of services, ~/list_parameters, ~/get_parameters, ~/set_parameters, ~/describe_parameters and others. ros2 param list/get/set/dump is just a client of these services; that is why the talker in Phase 0 had a row of parameter services.
  7. 校验与通知：一次设置请求到达后，节点先把待设的参数列表交给每个用 add_on_set_parameters_callback 注册的回调。只要有一个回调返回 SetParametersResult(successful=False, reason=…)，整次设置就被拒绝，值保持不变，reason 原样回到调用者（ros2 param set 会打印它）。全部通过后才真正写入，并在 /parameter_events 话题上发布一条变更事件，别的节点可以订阅它来跟进。
  8. Validation and notification: when a set request arrives, the node first hands the list of parameters to be set to every callback registered with add_on_set_parameters_callback. If any callback returns SetParametersResult(successful=False, reason=…), the whole set is rejected, the values stay unchanged, and the reason goes back to the caller unchanged (ros2 param set prints it). Only when all pass are the values written, and a change event is published on the /parameter_events topic, which other nodes may subscribe to in order to follow along.
on-set 回调只该校验，不该在里面改节点状态：它运行时设置还没生效，后面的回调还可能拒绝。要在值变了之后做事（例如按新频率重建定时器），较新的发行版另有「设置后」回调（rclcpp 大致叫 add_post_set_parameters_callback），或者订阅 /parameter_events；Jazzy 上的可用性请查文档。rclcpp 的 add_on_set_parameters_callback 返回一个句柄，句柄被销毁回调就注销了，所以要存成成员变量。
An on-set callback should only validate, not change node state: when it runs the set has not taken effect, and a later callback may still reject it. To act after a value has changed (for example rebuild a timer at the new rate), newer distributions also have a “post-set” callback (in rclcpp approximately add_post_set_parameters_callback), or you can subscribe to /parameter_events; check the docs for availability on Jazzy. rclcpp’s add_on_set_parameters_callback returns a handle and the callback is unregistered when the handle is destroyed, so store it as a member variable.

7. rclcpp 与 rclpy：同一套概念，两种写法

7. rclcpp and rclpy: one set of concepts, two ways to write it

两种库都建在 rcl 之上，所以概念一一对应，线上互通：Python 发布、C++ 订阅完全没问题（Lab A 会验证）。差别在语言和运行时：rclcpp 用模板在编译期确定消息类型（create_publisher<std_msgs::msg::String>），rclpy 把类型当参数传进去（create_publisher(String, …)）；rclcpp 的定时器用 std::chrono 时长，rclpy 用秒数；C++ 包用 ament_cmake，可执行文件靠 add_executable 和 install(TARGETS …) 安装，Python 包用 ament_python，可执行文件是 setup.py 里的 console_scripts 入口。性能上，rclpy 的每条消息都要在 C 和 Python 之间转换，Python 回调还受 GIL 限制，所以高频、低延迟、实时的节点通常用 C++，工具、编排和原型用 Python。

Both libraries sit on rcl, so the concepts correspond one to one and interoperate on the wire: publishing from Python and subscribing from C++ just works (Lab A checks it). The differences are in language and runtime: rclcpp fixes the message type at compile time with templates (create_publisher<std_msgs::msg::String>), rclpy passes the type as an argument (create_publisher(String, …)); rclcpp timers take std::chrono durations, rclpy takes seconds; C++ packages use ament_cmake and install executables with add_executable and install(TARGETS …), Python packages use ament_python and an executable is a console_scripts entry in setup.py. On performance, every rclpy message is converted between C and Python and Python callbacks are bound by the GIL, so high-rate, low-latency and real-time nodes are usually C++, while tools, orchestration and prototypes are Python.

延伸阅读：Renard《ROS 2 From Scratch》全书 Python 与 C++ 并列的写法；Joseph 与 Cacace《Mastering ROS 2 for Robotics Programming》讲用 C++ 和 Python 编写 ROS 2 程序的章节。

Further reading: Renard, ROS 2 From Scratch, which writes every example in Python and C++ side by side; the chapters on writing ROS 2 programs in C++ and Python in Joseph and Cacace, Mastering ROS 2 for Robotics Programming.

  4. 写 server。它在教程版本上加了 goal 回调（拒绝负数）和 cancel 回调。执行回调里有 sleep，为了让取消请求在执行期间也能被处理，这里用可重入回调组加多线程执行器；为什么必须这样，Phase 2 解释：Write the server. It adds to the tutorial version a goal callback (rejecting negative orders) and a cancel callback. The execute callback sleeps, so to let cancel requests be processed during execution it uses a reentrant callback group with a multithreaded executor; Phase 2 explains why this is necessary:
    import time

import rclpy
from rclpy.action import ActionServer, CancelResponse, GoalResponse
from rclpy.callback_groups import ReentrantCallbackGroup
from rclpy.executors import MultiThreadedExecutor
from rclpy.node import Node
from action_tutorials_interfaces.action import Fibonacci


class FibonacciActionServer(Node):
    def __init__(self):
        super().__init__('fibonacci_action_server')
        self._action_server = ActionServer(
            self, Fibonacci, 'fibonacci',
            execute_callback=self.execute_callback,
            goal_callback=self.goal_callback,
            cancel_callback=self.cancel_callback,
            callback_group=ReentrantCallbackGroup())

    def goal_callback(self, goal_request):
        # 在 send_goal 服务里决定接受还是拒绝
        return GoalResponse.REJECT if goal_request.order < 0 else GoalResponse.ACCEPT

    def cancel_callback(self, goal_handle):
        # 接受只让目标进入 CANCELING，停不停由 execute_callback 决定
        return CancelResponse.ACCEPT

    def execute_callback(self, goal_handle):
        feedback = Fibonacci.Feedback()
        feedback.partial_sequence = [0, 1]
        for i in range(1, goal_handle.request.order):
            if goal_handle.is_cancel_requested:
                goal_handle.canceled()
                return Fibonacci.Result(sequence=feedback.partial_sequence)
            feedback.partial_sequence.append(
                feedback.partial_sequence[i] + feedback.partial_sequence[i - 1])
            goal_handle.publish_feedback(feedback)      # feedback 话题
            time.sleep(1)
        goal_handle.succeed()
        return Fibonacci.Result(sequence=feedback.partial_sequence)


def main():
    rclpy.init()
    rclpy.spin(FibonacciActionServer(), executor=MultiThreadedExecutor())
    rclpy.shutdown()

class MinimalParam(Node):
    def __init__(self):

        self.declare_parameter('my_parameter', 'world')   # 默认值决定类型：string

            if p.name == 'rate_hz' and p.value <= 0.0:

    def timer_callback(self):
        name = self.get_parameter('my_parameter').get_parameter_value().string_value
        self.get_logger().info(f'Hello {name}!')

自测

Self-check

1. 一个 ROS 2 动作在 graph 里由什么组成？

1. What is a ROS 2 action made of in the graph?

动作没有自己的传输，rclpy.action 和 rclcpp_action 只是把挂在 _action/ 下的三个服务和两个话题包装起来。a 错在 DDS 里没有 action 实体；c 错在目标需要被确认接受，结果要可靠地配对，取消也是一个显式请求，这些都是服务。An action has no transport of its own; rclpy.action and rclcpp_action merely wrap the three services and two topics under _action/. a is wrong because DDS has no action entity; c is wrong because a goal must be explicitly accepted, the result must be reliably paired with its goal, and a cancel is an explicit request, all of which are services.

2. 节点注册了 on-set 回调，它对 rate_hz = -1.0 返回 successful=False。执行 ros2 param set … rate_hz -1.0 之后会怎样？

2. A node has registered an on-set callback that returns successful=False for rate_hz = -1.0. What happens after ros2 param set … rate_hz -1.0?

on-set 回调在写入之前运行，任何一个回调拒绝，整次设置都不生效，ros2 param set 会打印 reason。a 和 b 都假设值已经写入；实际上只有设置成功时才会在 /parameter_events 上发布变更事件。On-set callbacks run before the write; if any callback rejects, the whole set does not take effect, and ros2 param set prints the reason. a and b both assume the value was written; in fact a change event appears on /parameter_events only when a set succeeds.

3. 另一个进程里的 Python 订阅者把收到的每条消息存进一个列表。发布者发布后又修改并复用自己的消息对象。列表里已存的消息会变吗？

3. A Python subscriber in another process stores every received message in a list. The publisher, after publishing, modifies and reuses its own message object. Do the stored messages change?

跨进程时消息以序列化字节传递，接收端总是得到新分配的对象。b 混淆了传输和对象：共享内存传输搬运的仍是序列化后的字节，只有 loaned message 才让订阅者直接看发布者的内存，而且 rclpy 回调拿到的永远是转换后的 Python 对象。c 错在历史深度只决定保留几条，不改变复制语义。Across processes, messages travel as serialized bytes, and the receiver always gets a freshly allocated object. b confuses transport with objects: a shared-memory transport still moves serialized bytes, only a loaned message lets a subscriber see the publisher’s memory directly, and an rclpy callback always receives a converted Python object. c is wrong because the history depth only decides how many messages are kept, not the copy semantics.

4. 一个导航请求要 30 秒，需要显示进度，用户可能中途改主意。应该用哪种通信方式？

4. A navigation request takes 30 seconds, progress must be shown, and the user may change their mind midway. Which kind of communication fits?

这正是动作的设计目标，Nav2 的 NavigateToPose 就是动作。a 的服务没有中途反馈，请求也不能撤回，长时间的回调还会堵住执行器；c 用话题发目标没有接受确认，丢一条就不知道目标是否被收到，也没有取消和终态的定义。This is exactly what actions are designed for; Nav2’s NavigateToPose is an action. The service in a has no feedback midway and the request cannot be withdrawn, and a long callback also blocks the executor; c sends the goal on a topic with no acceptance, so a lost message leaves you unsure the goal arrived, and there is no definition of cancel or of a terminal state.
