核心概念

Core concepts

1. DDS 与 RTPS：participant、topic、DataWriter、DataReader

1. DDS and RTPS: participant, topic, DataWriter, DataReader

DDS（Data Distribution Service）是 OMG 的标准，规定了一套「以数据为中心的发布订阅」API 和语义；RTPS（Real-Time Publish-Subscribe，也叫 DDSI-RTPS）是另一份 OMG 标准，规定线上的报文格式。所以 Fast DDS 和 Cyclone DDS 是两家不同的 DDS 实现，但线上说的都是 RTPS。DDS 里有四个要认识的对象：

DDS (Data Distribution Service) is an OMG standard that defines an API and semantics for “data-centric publish-subscribe”; RTPS (Real-Time Publish-Subscribe, also called DDSI-RTPS) is a separate OMG standard that defines the packet format on the wire. So Fast DDS and Cyclone DDS are two different DDS implementations, but both speak RTPS on the wire. DDS has four objects to know:

  • DomainParticipant：加入一个 domain（即 ROS_DOMAIN_ID）的入口。它拥有发现协议的状态、一组 socket（Phase 0 里数过的那些端口）和几个后台线程。
  • DomainParticipant: the entry point for joining one domain (the ROS_DOMAIN_ID). It owns the discovery protocol state, a set of sockets (the ports you counted in Phase 0) and several background threads.
  • Topic：名字加类型。ROS 话题 /chatter 在 DDS 里叫 rt/chatter，类型名大致是 std_msgs::msg::dds_::String_；服务被拆成请求和应答两个 DDS 话题（前缀 rq/ 和 rr/）。用 Wireshark 抓包时你看到的是这些名字。
  • Topic: a name plus a type. The ROS topic /chatter is called rt/chatter in DDS, with a type name of approximately std_msgs::msg::dds_::String_; a service is split into two DDS topics, request and reply (prefixes rq/ and rr/). These are the names you see in a Wireshark capture.
  • DataWriter：ROS 的一个 publisher 在底下就是一个 DataWriter。它有自己的发送历史（QoS 里的 history 和 depth 就是这个缓冲区的大小），可靠模式下重传也从这里取。
  • DataWriter: a ROS publisher is a DataWriter underneath. It keeps its own send history (the QoS history and depth are the size of this buffer), and in reliable mode retransmissions are taken from it.
  • DataReader：ROS 的一个 subscription 就是一个 DataReader，有自己的接收队列。DDS 的接收线程把数据放进这个队列，再通知 rmw 唤醒你的执行器（Phase 2）。
  • DataReader: a ROS subscription is a DataReader with its own receive queue. The DDS receive thread puts data into this queue and then notifies rmw to wake your executor (Phase 2).

为什么一个进程只建一个 participant：participant 很重。每个 participant 要周期性地发自己的发现报文、要被网络上所有其他 participant 记住、要占两个单播端口和若干线程。早期的 ROS 2 每个节点一个 participant，一个组合了几十个节点的进程会在网络上冒出几十个 participant，发现流量和内存按平方增长。从 Foxy 起，rmw 改为每个上下文（通常就是每个进程）一个 participant，节点只是一个 ROS 层面的概念：哪个节点拥有哪些 writer 和 reader，由 rmw 另外发布在一个内部话题（ros_discovery_info）上，ros2 node list 读的就是它。

Why one participant per process: a participant is heavy. Each one sends its own discovery packets periodically, must be remembered by every other participant on the network, and takes two unicast ports and several threads. Early ROS 2 created one participant per node, so a process composing dozens of nodes would put dozens of participants on the network, and discovery traffic and memory grew quadratically. Since Foxy, rmw creates one participant per context (usually one per process), and a node is only a ROS-level concept: which node owns which writers and readers is published by rmw separately on an internal topic (ros_discovery_info), and that is what ros2 node list reads.

RTPS 把一条消息拆成几种子报文（submessage）：DATA（或大消息分片后的 DATA_FRAG）装数据，HEARTBEAT 是 writer 告诉 reader「我手里有第几号到第几号」，ACKNACK 是 reader 回答「我收到了哪些、缺哪些」，GAP 表示「这几号不会再有了」。概念 4 的可靠性就是这几种子报文的来回。
RTPS splits a message into several kinds of submessage: DATA (or DATA_FRAG for a fragmented large message) carries data; HEARTBEAT is the writer telling readers “I hold sequence numbers so-and-so to so-and-so”; ACKNACK is the reader answering “these I have, these are missing”; GAP says “these numbers will never come”. The reliability of concept 4 is exactly the exchange of these submessages.

2. rmw 层与三种中间件

2. The rmw layer and the three middlewares

Phase 0 讲过 rmw 是一套 C 接口、实现可替换。这里补上三件事：实现各是什么、序列化在哪里做、混用会怎样。Jazzy 上可用的三个实现（2026-10-31 按 Jazzy 文档核对）：

Phase 0 said rmw is a C interface with swappable implementations. Here are three more things: what each implementation is, where serialization happens, and what happens when you mix them. The three implementations available on Jazzy (checked against the Jazzy docs on 2026-10-31):

  • rmw_fastrtps_cpp：默认，基于 eProsima Fast DDS，装 ROS 2 时就有。同一台机器上的进程之间默认可以走共享内存传输，跨机器走 UDP。
  • rmw_fastrtps_cpp: the default, based on eProsima Fast DDS, installed with ROS 2. Between processes on the same host it can use a shared-memory transport by default; across hosts it uses UDP.
  • rmw_cyclonedds_cpp：基于 Eclipse Cyclone DDS，包名 ros-jazzy-rmw-cyclonedds-cpp，设 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp 使用。也是 RTPS。
  • rmw_cyclonedds_cpp: based on Eclipse Cyclone DDS, package ros-jazzy-rmw-cyclonedds-cpp, used by setting RMW_IMPLEMENTATION=rmw_cyclonedds_cpp. Also RTPS.
  • rmw_zenoh_cpp：基于 Eclipse Zenoh，包名 ros-jazzy-rmw-zenoh-cpp。它不是 DDS，线上说的是 Zenoh 协议；默认要先启动它的路由器 rmw_zenohd 才能发现彼此。它在 Jazzy 上的支持等级、默认传输和配置方式，请查官方文档。
  • rmw_zenoh_cpp: based on Eclipse Zenoh, package ros-jazzy-rmw-zenoh-cpp. It is not DDS and speaks the Zenoh protocol on the wire; by default its router rmw_zenohd must be running before nodes can find each other. For its support tier on Jazzy, its default transport and its configuration, check the official docs.

序列化在哪里：你的消息在内存里是一个 C++ 结构体或 Python 对象。每个消息包在构建时由 rosidl 生成若干份 typesupport 代码，rmw 实现用它把结构体编码成 CDR 字节（DDS 标准的编码格式），再交给中间件库；接收方反过来解码。所以序列化发生在 rmw 和中间件的交界处，在 rcl 之下、在 socket 之上。Python 节点在这里还多一次从 Python 对象到 C 结构的转换，这是 rclpy 处理大消息比 rclcpp 慢的原因之一。

Where serialization happens: in memory your message is a C++ struct or a Python object. When each message package is built, rosidl generates several pieces of typesupport code; the rmw implementation uses one of them to encode the struct into CDR bytes (the encoding defined by the DDS standard) and hands them to the middleware library, and the receiver decodes in reverse. So serialization happens at the boundary between rmw and the middleware, below rcl and above the socket. A Python node also pays an extra conversion from the Python object to the C struct here, which is one reason rclpy handles large messages more slowly than rclcpp.

混用会怎样：节点代码和 .msg 定义不变，换的是这个进程链接的库。但同一个系统里最好所有进程用同一个 rmw：Fast DDS 和 Cyclone DDS 都说 RTPS，跨厂商通信有时能通，但官方文档明确说不保证；Zenoh 和 DDS 之间根本不通。换 rmw 后还要重启 ros2 daemon，否则命令行还在用旧的那个。

What happens when you mix them: node code and .msg definitions stay the same; what changes is the library the process links. But in one system all processes should use the same rmw: Fast DDS and Cyclone DDS both speak RTPS, and cross-vendor communication sometimes works, but the official docs say plainly that it is not guaranteed; Zenoh and DDS do not talk to each other at all. After switching rmw, also restart ros2 daemon, or the command line keeps using the old one.

3. 发现：发现报文里装了什么，怎么改变发现方式

3. Discovery: what discovery packets carry, and how to change discovery

RTPS 的 simple discovery 分两步，两步装的东西不同：

RTPS simple discovery has two steps, and they carry different things:

  1. SPDP（participant 发现）：每个 participant 周期性地发一条「我在这里」，内容是 participant 的 GUID 前缀、协议版本和厂商 ID、它在哪些地址和端口上收发现报文和用户数据（locator）、租约时长（lease duration：这么久没听到我，就当我不在了）。默认发到多播组 239.255.0.1 的发现端口。这一步之后，双方知道对方存在、怎么联系对方，但还不知道对方有什么话题。
  2. SPDP (participant discovery): each participant periodically sends an “I am here”, containing its GUID prefix, the protocol version and vendor ID, the addresses and ports (locators) where it receives discovery and user data, and its lease duration (if you hear nothing from me for this long, treat me as gone). By default it goes to the discovery port of multicast group 239.255.0.1. After this step, each side knows the other exists and how to reach it, but not yet which topics it has.
  3. SEDP（endpoint 发现）：participant 之间用单播、而且是可靠的方式交换各自的每个 writer 和 reader：GUID、DDS 话题名（rt/chatter）、类型名，以及全部 QoS。匹配就在收到 SEDP 的那一刻、在本地判定：名字和类型一样、QoS 兼容（概念 5），就把对方加为匹配的端点，之后数据直接发过去。
  4. SEDP (endpoint discovery): participants exchange, over unicast and reliably, every writer and reader they have: GUID, DDS topic name (rt/chatter), type name and all QoS. Matching is decided locally the moment SEDP arrives: same name and type and compatible QoS (concept 5), and the other side is added as a matched endpoint, after which data is sent straight to it.

所以发现流量的大小大致与「participant 数 × 端点数」相关，每个 participant 都记着所有别人的所有端点。几个机器人、上百个话题的系统，光发现就能吃掉可观的带宽和内存，Wi-Fi 下多播还常常丢。ROS 2 给了几种改变发现方式的办法：

So the volume of discovery traffic grows roughly with “participants × endpoints”, and every participant remembers every endpoint of everyone else. In a system with several robots and hundreds of topics, discovery alone can use noticeable bandwidth and memory, and multicast over Wi-Fi is often lost. ROS 2 offers several ways to change how discovery works:

  • ROS_AUTOMATIC_DISCOVERY_RANGE（Jazzy）：SUBNET（默认，多播能到的都发现）、LOCALHOST（只在本机，实验容器用的就是它）、OFF（不自动发现）、SYSTEM_DEFAULT（不改中间件自己的设置）。旧名 ROS_LOCALHOST_ONLY 从 Iron 起弃用，见实验环境页概念 4。
  • ROS_AUTOMATIC_DISCOVERY_RANGE (Jazzy): SUBNET (the default: discover everything multicast reaches), LOCALHOST (this host only; the lab container uses it), OFF (no automatic discovery), SYSTEM_DEFAULT (leave the middleware’s own settings alone). The old name ROS_LOCALHOST_ONLY is deprecated since Iron; see concept 4 of the lab environment page.
  • ROS_STATIC_PEERS：用分号分隔的 IP 或主机名列表，直接单播给这些对端，不依赖多播。可以和上面的范围一起用，例如范围设 LOCALHOST，再把另一台机器人的地址写进静态对端。
  • ROS_STATIC_PEERS: a semicolon-separated list of IPs or hostnames that discovery unicasts to directly, without relying on multicast. It combines with the range above, for example range LOCALHOST plus the address of another robot as a static peer.
  • Fast DDS discovery server（只适用于 Fast DDS）：启动一个服务器 fastdds discovery -i 0，每个进程设 ROS_DISCOVERY_SERVER=127.0.0.1:11811（11811 是 Fast DDS discovery server 的默认端口，Jazzy 教程 2026-10-31 核对）。participant 只向服务器报到，服务器只把每个 participant 需要的端点转给它，不再人人记住人人。代价是多了一个要运维的进程；命令行工具要看到全图还需额外配置（super client，查官方教程）。
  • Fast DDS discovery server (Fast DDS only): start a server with fastdds discovery -i 0 and set ROS_DISCOVERY_SERVER=127.0.0.1:11811 in each process (11811 is the default discovery server port, checked against the Jazzy tutorial on 2026-10-31). Participants report only to the server, and the server forwards to each participant only the endpoints it needs, so not everyone remembers everyone. The cost is one more process to operate; for the command-line tools to see the whole graph you need extra setup (a super client; see the official tutorial).
以上两个环境变量只对 DDS 的 rmw 起作用：Jazzy 文档写明 rmw_zenoh 不支持 ROS_AUTOMATIC_DISCOVERY_RANGE 和 ROS_STATIC_PEERS，Zenoh 的发现范围要在它自己的配置里设。
The two environment variables above apply only to the DDS rmw implementations: the Jazzy docs state that rmw_zenoh does not support ROS_AUTOMATIC_DISCOVERY_RANGE or ROS_STATIC_PEERS; Zenoh’s discovery scope is set in its own configuration.
容器里 LOCALHOST 的「本机」是容器的网络命名空间。Lab B 会在一个 shell 里临时改成 SUBNET，好在 eth0 上看到多播；那个网段是 Docker Desktop 虚拟机里的桥接网络，一般不会直接到达你的局域网（推断，取决于 Docker Desktop 的网络实现）。
Inside the container, “this host” for LOCALHOST is the container’s network namespace. Lab B temporarily switches one shell to SUBNET to see multicast on eth0; that subnet is a bridge network inside the Docker Desktop VM and normally does not reach your LAN directly (inference; it depends on Docker Desktop’s networking).

4. QoS 策略：每一条在机制上是什么

4. QoS policies: what each one is, mechanically

QoS（Quality of Service）是附在每个 publisher 和 subscription 上的一组策略，经 SEDP 告诉对方。create_publisher(topic, 10) 里的 10 是「默认 profile，history depth 10」的简写。逐条看：

QoS (Quality of Service) is a set of policies attached to each publisher and subscription and announced to the other side through SEDP. The 10 in create_publisher(topic, 10) is shorthand for “the default profile with history depth 10”. Policy by policy:

  • Reliability：reliable 时，writer 把发出去的样本留在历史里，周期性发 HEARTBEAT；reader 用 ACKNACK 报告缺哪几号，writer 重传。best_effort 时，发一次就算，丢了就丢了，没有确认和重传。
  • Reliability: with reliable, the writer keeps sent samples in its history and sends HEARTBEATs periodically; the reader reports missing numbers with ACKNACK and the writer retransmits. With best_effort, each sample is sent once; if it is lost, it is lost, with no acknowledgement and no retransmission.
  • History 与 depth：keep_last 加 depth N 表示 writer 和 reader 各自最多留最新的 N 个样本，满了就丢最旧的；keep_all 表示尽量都留（受资源上限约束）。depth 同时决定了可靠模式下最多能补发多少，以及订阅者处理慢时会丢多少。
  • History and depth: keep_last with depth N means the writer and the reader each keep at most the newest N samples and drop the oldest when full; keep_all means keep everything as far as resource limits allow. Depth also sets how much can be resent in reliable mode, and how much is dropped when a subscriber is slow.
  • Durability：volatile 时，后加入的订阅者只能收到加入之后发的数据。transient_local 时，writer 把最后 depth 个样本留着，新的 reader 一匹配就补发给它——/tf_static、/robot_description、地图服务器发布的地图都这样，因为它们只发一次或很少发。
  • Durability: with volatile, a late-joining subscriber receives only data sent after it joined. With transient_local, the writer keeps the last depth samples and sends them to each new reader as soon as it matches — /tf_static, /robot_description and the map published by the map server work this way, because they are published once or rarely.
  • Deadline：约定的最大样本间隔。publisher 承诺「至少每 T 发一次」，subscription 要求「至少每 T 收到一次」；超时双方各自收到一个 deadline missed 事件。它不让数据变快，只是让你知道迟了。
  • Deadline: an agreed maximum interval between samples. The publisher promises “at least once every T”, the subscription requires “at least once every T”; when it is exceeded, each side receives a deadline-missed event. It does not make data faster; it only tells you it is late.
  • Lifespan：样本的保质期。超过这个时长还没交付的样本直接丢弃，不会再交给新加入的订阅者，避免 transient_local 补发一条早已过时的数据。
  • Lifespan: the shelf life of a sample. A sample not delivered within this time is discarded and never handed to a late joiner, so transient_local does not replay data that is long out of date.
  • Liveliness 与 lease duration：publisher 怎样证明自己还活着。automatic 由中间件代为声明（进程活着就算）；manual_by_topic 要应用自己发布或显式声明才算。超过 lease duration 没有声明，订阅者收到 liveliness changed 事件。
  • Liveliness and lease duration: how a publisher proves it is still alive. With automatic the middleware asserts it on your behalf (the process being alive is enough); with manual_by_topic the application must publish or assert explicitly. With no assertion within the lease duration, the subscriber receives a liveliness-changed event.

为什么传感器用 best effort：一台 10 Hz 的激光雷达，下一帧 100 ms 后就到。如果用 reliable，一帧在 Wi-Fi 上丢了，writer 要等 reader 的 ACKNACK 再重传，这期间新帧也在排队；重传到的是一帧已经过时的扫描，还挤占了新帧的带宽。对控制和避障来说，「最新的那一帧」比「每一帧都到」重要。所以 sensor-data profile 是 best effort、depth 5：丢就丢，留几帧缓冲就够。反过来，指令、地图、参数这类丢一条就出错的数据用 reliable。

Why sensors use best effort: a 10 Hz lidar delivers the next scan 100 ms later. With reliable, if one scan is lost over Wi-Fi, the writer must wait for the reader’s ACKNACK before resending, while new scans queue up behind it; what finally arrives is an outdated scan that also took bandwidth from the fresh ones. For control and obstacle avoidance, “the newest scan” matters more than “every scan arrives”. So the sensor-data profile is best effort with depth 5: if a sample is lost, it is lost, and a few samples of buffer are enough. Conversely, data where one lost message causes errors — commands, maps, parameters — uses reliable.

deadline、lifespan、liveliness 三项在各个 rmw 上的支持程度不同（例如是否支持某种 liveliness kind、事件是否都会触发），请查你用的 rmw 的文档；本页实验只用 reliability、durability 和 depth，这三项在三种 rmw 上都有。
Support for deadline, lifespan and liveliness differs between rmw implementations (for example which liveliness kinds are supported and whether every event fires); check the docs of the rmw you use. The labs on this page use only reliability, durability and depth, which all three rmw implementations have.

5. 兼容规则：提供 ≥ 请求，以及 ros2 topic info -v

5. Compatibility: offered ≥ requested, and ros2 topic info -v

DDS 把 QoS 看成一份合同：publisher 提供（offered），subscription 请求（requested）。只有提供的不比请求的差，两端才会匹配（DDS 叫 Request vs Offered，RxO）。会影响匹配的几项：

DDS treats QoS as a contract: the publisher offers and the subscription requests. The two endpoints match only when what is offered is no worse than what is requested (DDS calls this Request vs Offered, RxO). The policies that affect matching:

  • Reliability：reliable 发布者 + best effort 订阅者 → 匹配，按 best effort 交付（订阅者不发 ACKNACK）。best effort 发布者 + reliable 订阅者 → 不匹配，发布者给不了它要的保证。
  • Reliability: reliable publisher + best-effort subscription → match, delivered best effort (the subscriber sends no ACKNACK). Best-effort publisher + reliable subscription → no match; the publisher cannot give the guarantee it asks for.
  • Durability：transient_local 发布者 + volatile 订阅者 → 匹配，只收新数据。volatile 发布者 + transient_local 订阅者 → 不匹配，发布者根本没留历史。
  • Durability: transient_local publisher + volatile subscription → match, new data only. Volatile publisher + transient_local subscription → no match; the publisher keeps no history at all.
  • Deadline：发布者承诺的周期必须 ≤ 订阅者要求的周期。Liveliness：发布者的 kind 必须不弱于订阅者要求的，lease duration 必须 ≤ 订阅者要求的。
  • Deadline: the period the publisher promises must be ≤ the period the subscription requires. Liveliness: the publisher’s kind must be no weaker than requested, and its lease duration must be ≤ the requested one.
  • History、depth、lifespan 不影响匹配，它们只是各端自己的缓冲行为。
  • History, depth and lifespan do not affect matching; they only govern each endpoint’s own buffering.

不匹配时会发生什么：不报错、不断开，只是这对端点永远不连，数据一条也不过去。两端各自收到一个 incompatible QoS 事件，rclcpp 和 rclpy 默认把它打成一条警告日志，大意是「发现了一个 QoS 不兼容的发布者 / 订阅者，最后一个不兼容的策略是 RELIABILITY」（措辞以实际输出为准）。排查顺序：ros2 topic list 确认名字，ros2 topic info -v 列出每个端点的节点名、GID 和完整 QoS——不兼容的端点照样会列出来，因为 SEDP 已经交换过了，只是没匹配上。

What happens on a mismatch: no error and no disconnection; the pair simply never connects and not one message gets through. Each side receives an incompatible-QoS event, which rclcpp and rclpy log as a warning by default, roughly “a publisher / subscription with incompatible QoS was discovered; the last incompatible policy was RELIABILITY” (go by the actual wording). The order to investigate: confirm the name with ros2 topic list, then ros2 topic info -v, which lists every endpoint with its node name, GID and full QoS — incompatible endpoints are still listed, because SEDP has already exchanged them; they just did not match.

ros2 topic echo 和 ros2 bag record 在较新的发行版里默认会按已发现的发布者自动选一个能匹配的 QoS（官方叫 best available，Jazzy 上的具体行为以 --help 为准）。所以 Lab A 里每次都显式给出 --qos-reliability 和 --qos-durability，不靠默认值。
In recent distributions ros2 topic echo and ros2 bag record by default pick a QoS that matches the publishers already discovered (the docs call this best available; check --help for the exact behaviour on Jazzy). That is why Lab A always gives --qos-reliability and --qos-durability explicitly instead of relying on the defaults.

6. 大消息：共享内存传输与 loaned messages

6. Large messages: shared-memory transport and loaned messages

一帧 1080p 的 RGB 图像约 6 MB，一帧点云也常是几 MB。走 UDP 时，一条消息要被拆成几千个 DATA_FRAG，每片都要过一遍内核网络栈，丢一片整条作废（best effort）或要补发（reliable）；接收 socket 缓冲区不够大时丢得更多（缓冲区调优见 Phase 7）。同一台机器上有两条更短的路：

One 1080p RGB image is about 6 MB, and a point cloud is often several MB too. Over UDP, one message is split into thousands of DATA_FRAG pieces, each passing through the kernel network stack; losing one piece voids the whole message (best effort) or forces a resend (reliable), and a receive socket buffer that is too small loses even more (buffer tuning is in Phase 7). On one host there are two shorter paths:

  • 共享内存传输：Fast DDS 在同一台机器的进程之间默认可以用共享内存段（在 /dev/shm 下）代替 UDP 传用户数据。数据仍然被序列化、仍然从 writer 拷贝到共享段，但不经过网络栈，也不分片。这就是实验环境给容器配 shm_size: "4g" 的原因；Phase 0 Lab B 里你在 /dev/shm 看到的文件就是它。
  • Shared-memory transport: between processes on the same host, Fast DDS can by default use a shared-memory segment (under /dev/shm) instead of UDP for user data. The data is still serialized and still copied from the writer into the segment, but it skips the network stack and is not fragmented. That is why the lab environment gives the container shm_size: "4g"; the files you saw in /dev/shm in Phase 0 Lab B are this transport.
  • Loaned messages：rclcpp 的 borrow_loaned_message() 向中间件「借」一块它自己管理的内存，你直接把数据写在里面再发布，省掉从你的缓冲区到中间件缓冲区的那次拷贝；中间件支持时，配合共享内存可以做到接收方直接读同一块内存（零拷贝）。限制很多：通常只适用于定长（plain）的消息类型，publisher->can_loan_messages() 返回 false 时会退回普通路径。哪些 rmw、哪些类型、需要什么配置，请查文档。
  • Loaned messages: rclcpp’s borrow_loaned_message() “borrows” a block of memory managed by the middleware; you write the data directly into it and publish, saving the copy from your buffer into the middleware’s; where the middleware supports it, combined with shared memory the receiver can read the very same memory (zero copy). There are many limits: it usually applies only to fixed-size (plain) message types, and when publisher->can_loan_messages() returns false it falls back to the normal path. Which rmw, which types and what configuration are needed: check the docs.

还有第三条路完全绕开中间件：同一进程里的节点用进程内通信，直接传指针。那是 Phase 4 组合（composition）的内容。

A third path bypasses the middleware entirely: nodes in the same process use intra-process communication and pass pointers directly. That belongs to composition in Phase 4.

7. SROS2：keystore、enclave，以及它加密什么、不加密什么

7. SROS2: keystores, enclaves, and what it encrypts and what it does not

SROS2 是一套工具和约定，把 DDS-Security 规范里的插件（认证、访问控制、加密）用到 ROS 2 上。三个名词：

SROS2 is a set of tools and conventions that applies the plugins of the DDS-Security specification (authentication, access control, cryptography) to ROS 2. Three terms:

  • keystore：一个目录，里面有充当 CA 的密钥和证书，以及每个 enclave 的材料。ros2 security create_keystore demo_keystore 创建它。
  • keystore: a directory holding the keys and certificates that act as the CA, plus the material for each enclave. ros2 security create_keystore demo_keystore creates it.
  • enclave：一个安全身份，对应一个 participant，也就是一个进程（一个进程里的所有节点共用它）。ros2 security create_enclave demo_keystore /talker_listener/talker 为它生成私钥、由 CA 签发的身份证书、签过名的 governance（这个 domain 里哪些要保护、保护到什么程度）和 permissions（这个身份能发布和订阅哪些话题）。
  • enclave: one security identity, corresponding to one participant, that is, one process (all nodes in a process share it). ros2 security create_enclave demo_keystore /talker_listener/talker generates its private key, an identity certificate signed by the CA, a signed governance document (what in this domain is protected and how strongly) and a permissions document (which topics this identity may publish and subscribe to).
  • 环境变量：ROS_SECURITY_KEYSTORE 指向 keystore，ROS_SECURITY_ENABLE=true 打开，ROS_SECURITY_STRATEGY=Enforce 表示找不到合法的安全材料就拒绝启动（另一个取值 Permissive 会退回不加密运行）。进程用 --ros-args --enclave /talker_listener/talker 选身份，或用 ROS_SECURITY_ENCLAVE_OVERRIDE 强制指定。
  • Environment variables: ROS_SECURITY_KEYSTORE points at the keystore, ROS_SECURITY_ENABLE=true turns security on, and ROS_SECURITY_STRATEGY=Enforce means refuse to start without valid security material (the other value, Permissive, falls back to running unsecured). A process picks its identity with --ros-args --enclave /talker_listener/talker, or ROS_SECURITY_ENCLAVE_OVERRIDE forces one.

它保护什么：两个 participant 先用证书互相认证（双方都由同一个 CA 签发，才算自己人），再协商出会话密钥；之后按 governance 的设定，用户数据、SEDP 的端点信息等被加密或签名，没有证书的 participant 匹配不上任何受保护的端点；permissions 限制每个身份能碰的话题。效果是：局域网上的旁观者抓到的是密文，冒充的节点连不进来。

What it protects: two participants first authenticate each other with certificates (both must be signed by the same CA to be trusted), then agree on session keys; after that, as the governance document specifies, user data and SEDP endpoint information are encrypted or signed, and a participant without a certificate cannot match any protected endpoint; permissions limit which topics each identity may touch. The effect: an onlooker on the LAN captures ciphertext, and an impostor node cannot get in.

它不保护什么：

What it does not protect:

  • SPDP 的「我在这里」仍是明文，因为认证要先知道对方存在。旁观者仍能看到有几个 participant、它们的 IP 和端口；从报文的大小和频率还能推断出大致的通信模式。
  • The SPDP “I am here” stays in the clear, since authentication first needs to know the peer exists. An onlooker can still see how many participants there are and their IPs and ports, and can infer a rough traffic pattern from packet sizes and rates.
  • 私钥是 keystore 里的普通文件。能读这台机器文件系统的人就能拿到身份；SROS2 不管文件权限，也不管机器本身被攻破。
  • Private keys are ordinary files in the keystore. Anyone who can read the machine’s file system can take the identity; SROS2 does not manage file permissions or protect a compromised machine.
  • 持有合法证书的节点发什么内容，它不检查。它也不防拒绝服务：有人往发现端口灌流量，节点照样被拖慢。
  • It does not check what a node with a valid certificate sends. Nor does it prevent denial of service: someone flooding the discovery port still slows the nodes down.
  • 同一进程内的进程内通信不经过 DDS，不在它的范围内；Zenoh 有自己的一套安全机制，不是 DDS-Security（查 rmw_zenoh 文档）。
  • Intra-process communication inside one process does not go through DDS and is outside its scope; Zenoh has its own security mechanism, which is not DDS-Security (see the rmw_zenoh docs).
governance 里默认对哪些部分加密、哪些只签名，由 sros2 生成的模板决定，本页没有逐项核对；Lab B 用抓包直接看结果，以你看到的为准。
Which parts the default governance encrypts and which it only signs is decided by the template that sros2 generates, and this page has not checked it item by item; Lab B looks at the result directly with a packet capture, and what you see is what counts.

Lab A · Cause QoS incompatibilities, then switch the middleware

  1. 进入容器，开三个 shell（宿主机上三次 ./lab.sh shell），每个都先 source underlay。确认当前用的是默认 rmw：Enter the container and open three shells (./lab.sh shell three times on the host), sourcing the underlay in each. Confirm that the default rmw is in use:

ros2 doctor --report | grep -i middleware
  2. best effort 发布者 + reliable 订阅者：shell 1 发布，shell 2 用 reliable 订阅。应当收不到任何消息，并在 shell 2 看到一条 incompatible QoS 警告：Best-effort publisher + reliable subscription: publish in shell 1 and subscribe reliably in shell 2. You should receive nothing, and see an incompatible-QoS warning in shell 2:

ros2 topic pub -r 1 --qos-reliability reliable --qos-durability volatile /latched std_msgs/msg/String "{data: map v2}"

ros2 topic echo --qos-reliability reliable --qos-durability transient_local /latched

自测

Self-check

1. 一个激光雷达驱动用 reliable 发布 /scan，你的节点用 sensor-data profile（best effort）订阅。会怎样？

1. A lidar driver publishes /scan as reliable, and your node subscribes with the sensor-data profile (best effort). What happens?

规则是提供 ≥ 请求：reliable 的发布者能满足只要求 best effort 的订阅者，交付按订阅者要求的 best effort 进行。b 把「不同」当成了「不兼容」，只有反过来（best effort 发布者、reliable 订阅者）才不匹配。c 错在 QoS 不会被自动升级，订阅者请求的是什么就按什么交付。The rule is offered ≥ requested: a reliable publisher can serve a subscription that asks only for best effort, and delivery follows the best effort the subscription requested. b treats “different” as “incompatible”; only the reverse (best-effort publisher, reliable subscription) fails to match. c is wrong because QoS is never upgraded automatically; delivery follows what the subscription requested.

2. 地图服务器启动时发布一次 /map。RViz2 晚一分钟才打开，要让它立刻看到地图，需要什么？

2. The map server publishes /map once at start-up. RViz2 opens a minute later. What is needed for it to see the map at once?

只有订阅者也请求 transient_local，发布者才会把留存的样本补发给它。b 能匹配，但 volatile 订阅者只收加入之后的数据，而地图不会再发。a 错在 depth 只决定留多少，volatile 时根本不会补发给迟到的订阅者。The publisher sends stored samples to a subscription only when that subscription also requests transient_local. b matches, but a volatile subscription receives only data sent after it joined, and the map is not published again. a is wrong because depth only sets how much is kept; with volatile, nothing is replayed to a late joiner.

3. 话题名、类型都对，ros2 topic echo 却一条也收不到，日志里有一条 incompatible QoS 警告。下一步最有用的命令是？

3. Topic name and type are right, but ros2 topic echo receives nothing, and there is an incompatible-QoS warning in the log. What is the most useful next command?

警告说明发现已经成功、端点也交换过了，只是 QoS 不兼容；ros2 topic info -v 会列出两端的完整 QoS，直接看出是哪一项。a 只能说明节点在，看不到 QoS。c 换 domain 会让两端彼此看不见，问题只会更多。The warning means discovery succeeded and the endpoints were exchanged, but the QoS is incompatible; ros2 topic info -v lists the full QoS of both sides and shows the policy directly. a only shows the node exists, not its QoS. c, changing the domain, would make the two sides invisible to each other and add a problem.

4. talker 和 listener 都在 Enforce 模式下用 SROS2 运行。同一局域网上的旁观者抓包，仍然能得到什么？

4. Talker and listener both run under SROS2 in Enforce mode. What can an onlooker capturing on the same LAN still learn?

SPDP 的「我在这里」必须是明文，对方才能知道你存在并开始认证，所以 participant 的存在、地址和端口是可见的，流量模式也看得出来。b 忽略了这一点。c 错在 SROS2 按 governance 会加密用户数据，Lab B 里加密后 grep 找不到 Hello World。The SPDP “I am here” must be in the clear so that peers learn you exist and can start authentication, so participants, their addresses and ports are visible, and so is the traffic pattern. b ignores this. c is wrong because SROS2 encrypts user data as the governance document specifies; in Lab B, after encryption, grep no longer finds Hello World.
