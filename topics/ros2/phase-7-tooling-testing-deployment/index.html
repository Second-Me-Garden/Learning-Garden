核心概念

Core concepts

1. 看清系统：rqt、ros2 doctor 与日志

1. Seeing the system: rqt, ros2 doctor and logging

rqt 是一个 Qt 框架，各种图形工具是它的插件，单独启动时各自有命令名：rqt_graph 把节点和话题画成图，数据来自 DDS 发现信息，跟 ros2 node info 是同一个来源；rqt_console 订阅 /rosout，按级别和节点过滤日志；rqt_plot 订阅一个话题里的数值字段（例如 /odom/pose/pose/position/x）画曲线。它们都只是普通的 ROS 节点，所以在容器里要从 noVNC 桌面启动，而且会出现在 ros2 node list 里。

rqt is a Qt framework whose graphical tools are plugins, each with its own command name when started alone: rqt_graph draws nodes and topics as a graph, from DDS discovery information, the same source as ros2 node info; rqt_console subscribes to /rosout and filters log messages by level and node; rqt_plot subscribes to a numeric field inside a topic (for example /odom/pose/pose/position/x) and draws it as a curve. They are all ordinary ROS nodes, so in the container you start them from the noVNC desktop, and they show up in ros2 node list.

ros2 doctor --report 不看你的代码，看的是环境：发行版与版本、平台、网络接口、当前 rmw 实现、已安装包是否落后于发行版。装错源、混用发行版、网卡没有多播这类问题，在这里比在节点日志里更容易看出来。

ros2 doctor --report does not look at your code but at the environment: distribution and version, platform, network interfaces, the active rmw implementation, and whether installed packages lag behind the distribution. Problems such as a wrong apt source, mixed distributions or an interface without multicast are easier to see here than in node logs.

日志的三个去处：按官方 Logging 概念页，一条 get_logger().info(…) 默认同时写到三处：控制台的 stderr（设 RCUTILS_LOGGING_USE_STDOUT=1 改到 stdout）、磁盘上的日志文件（通常在 ~/.ros/log，可用 ROS_LOG_DIR 改）、以及 ROS 网络上的 /rosout 话题。级别在启动时调：--ros-args --log-level debug 改全部，--log-level talker:=DEBUG 只改一个 logger。控制台格式由 RCUTILS_CONSOLE_OUTPUT_FORMAT 决定，默认是 [{severity}] [{time}] [{name}]: {message}。日志走 stderr 这一点后面会用到：launch_testing 断言日志内容时，默认就去 stderr 里找。

Where a log line goes: per the official Logging concept page, one get_logger().info(…) by default goes to three places at once: the console on stderr (set RCUTILS_LOGGING_USE_STDOUT=1 to switch to stdout), log files on disk (typically under ~/.ros/log, configurable with ROS_LOG_DIR), and the /rosout topic on the ROS network. Levels are set at start-up: --ros-args --log-level debug for everything, --log-level talker:=DEBUG for one logger only. The console format comes from RCUTILS_CONSOLE_OUTPUT_FORMAT; the default is [{severity}] [{time}] [{name}]: {message}. The fact that logs go to stderr matters later: when launch_testing asserts on log text, it looks in stderr by default.

延伸阅读：Martín Rico《A Concise Introduction to Robot Programming with ROS2》讲开发工具与调试的部分；Quigley 等《Programming Robots with ROS》讲 rqt 与 rosbag 等工具的章节（ROS 1，工具的用途在 ROS 2 中不变）；官方 Logging and logger configuration。

Further reading: the parts of Martín Rico, A Concise Introduction to Robot Programming with ROS2, on development tools and debugging; the chapters of Quigley et al., Programming Robots with ROS, on tools such as rqt and rosbag (ROS 1; what the tools are for is unchanged in ROS 2); the official Logging and logger configuration.

2. 录制与回放：ros2 bag 与仿真时间

2. Record and replay: ros2 bag and simulation time

ros2 bag record 是一个订阅者：它订阅你点名的话题（-a 是全部），把收到的序列化字节原样写进存储文件，不反序列化，所以录任何类型都不需要它认识这个类型的代码。每条消息记下它被录下时的时间戳，消息里自己的 header.stamp 也原样留在字节里。-o name 指定目录名；目录里是 metadata.yaml（话题、类型、QoS、消息数、起止时间，ros2 bag info 读的就是它）和存储文件。存储插件有 mcap 和 sqlite3 两种，--storage 选择；rosbag2 jazzy 分支的 README 写明默认是 mcap（2026-10-31 查）。

ros2 bag record is a subscriber: it subscribes to the topics you name (-a for all) and writes the serialized bytes it receives straight into a storage file without deserializing them, so it can record any type without knowing that type’s code. Each message is stored with the time it was recorded, and the message’s own header.stamp stays inside the bytes unchanged. -o name names the directory; the directory holds metadata.yaml (topics, types, QoS, message counts, start and end time; this is what ros2 bag info reads) and the storage file. There are two storage plugins, mcap and sqlite3, chosen with --storage; the README of the rosbag2 jazzy branch states that the default is mcap (checked 2026-10-31).

ros2 bag play 是一个发布者：按录制时的间隔把消息重新发出去（-r 调倍速）。问题在于时间。回放时消息里的 header.stamp 还是录制那天的，而节点的 now() 默认读的是系统时钟，也就是今天。于是 tf2 用一个「几天前」的时间戳去查变换，会报外推错误；按消息年龄丢弃旧数据的代码会把每一条都判成过期；定时器按墙钟跑，和数据流的节奏对不上，倍速回放时更明显。

ros2 bag play is a publisher: it sends the messages again at their recorded spacing (-r changes the rate). The problem is time. During replay, the header.stamp inside each message is still from the recording day, while a node’s now() reads the system clock by default, which is today. So tf2 asked for a transform at a timestamp “days ago” reports an extrapolation error; code that drops data by message age judges every message stale; and timers run on the wall clock, out of step with the data, which is worse at a changed rate.

修法是两半，缺一不可。--clock 让播放器充当时间源：按固定频率在 /clock 上发布「当前回放到的录制时间」（不给数值时默认 40 Hz，以 ros2 bag play -h 为准；同时会排除 bag 里自带的 /clock，免得两个时间源打架）。use_sim_time:=true 是每个节点上的参数，按设计文章 Clock and Time，它让这个节点的 ROS time 改读 /clock 的最新值。只开 --clock，没人听；只开 use_sim_time，节点等不到 /clock，时间停在 0，按设计文章 0 表示「时间未初始化」，基于 ROS time 的定时器一次都不会触发。两半都开，now()、定时器、tf 查询就都在录制的时间线上，暂停播放，整个系统的时间也跟着停。

The fix has two halves, and both are needed. --clock makes the player a time source: it publishes “the recorded time playback has reached” on /clock at a fixed rate (40 Hz when no value is given; go by ros2 bag play -h; it also excludes any /clock stored in the bag so that two time sources do not fight). use_sim_time:=true is a parameter on each node; per the design article Clock and Time, it makes that node’s ROS time read the latest value from /clock. With only --clock, nobody listens; with only use_sim_time, the node never gets a /clock, so its time stays at 0, which the design article defines as “time not initialized”, and a timer on ROS time never fires. With both, now(), timers and tf lookups all live on the recorded timeline, and pausing playback pauses time for the whole system.

录制时也有对应的一面：如果被录的系统本身在仿真时间上（Gazebo 发布 /clock），给 ros2 bag record 加 --use-sim-time，消息就按仿真时间打戳。rosbag2 README 提醒：开了这个选项后，在收到第一条 /clock 之前录制器不写任何消息，否则时间会从 0 跳到 N，bag 基本没法回放。
Recording has a matching side: if the recorded system itself runs on simulation time (Gazebo publishes /clock), add --use-sim-time to ros2 bag record so messages are stamped with simulation time. The rosbag2 README warns that with this option the recorder writes nothing until the first /clock arrives; otherwise time would jump from 0 to N and the bag would be essentially unplayable.

3. 测试金字塔：单元测试与 launch_testing

3. The test pyramid: unit tests and launch_testing

单元测试检查一个函数或一个类在给定输入下对不对。C++ 用 gtest：在 CMakeLists.txt 的 if(BUILD_TESTING) 里写 ament_add_gtest(${PROJECT_NAME}_test test/test_x.cpp)，package.xml 加 <test_depend>ament_cmake_gtest</test_depend>。Python 用 pytest：ament_python 包把 test_*.py 放进包根目录的测试目录；CMake 包里的 Python 测试用 ament_add_pytest_test 登记。单元测试快、可以写很多，但它看不到进程、DDS、launch 文件，也看不到节点之间是否真的连上。

A unit test checks whether one function or class is correct for a given input. C++ uses gtest: inside if(BUILD_TESTING) in CMakeLists.txt write ament_add_gtest(${PROJECT_NAME}_test test/test_x.cpp), and add <test_depend>ament_cmake_gtest</test_depend> to package.xml. Python uses pytest: an ament_python package puts test_*.py files into the test directory at the package root; Python tests in a CMake package are registered with ament_add_pytest_test. Unit tests are fast and you can write many, but they cannot see processes, DDS or launch files, nor whether nodes really connect to each other.

launch_testing 补的正是这一层。测试文件里的 generate_test_description() 返回一个 LaunchDescription，和普通 launch 文件一样起真正的进程，再加一个 launch_testing.actions.ReadyToTest() 告诉框架「可以开始测了」。之后有两类测试：

launch_testing fills exactly that layer. In a test file, generate_test_description() returns a LaunchDescription that starts real processes, just as a normal launch file does, plus a launch_testing.actions.ReadyToTest() that tells the framework “you may start testing now”. After that there are two kinds of test:

  • 活动测试（普通的 unittest.TestCase）在被测进程运行期间执行。它们能做单元测试做不到的事：用 proc_output.assertWaitFor(…) 断言某个进程在超时之前打印了某行日志；自己建一个节点订阅被测节点的话题，断言消息真的跨进程、经过 DDS 发现到达了，频率和内容也对；验证 launch 文件里的重映射、参数文件和命名空间确实生效。
  • Active tests (ordinary unittest.TestCase classes) run while the processes under test are running. They can do what a unit test cannot: assert with proc_output.assertWaitFor(…) that a process printed a given log line before a timeout; create a node of their own that subscribes to the topics of the nodes under test and assert that messages really arrived across processes through DDS discovery, at the right rate and with the right content; and check that the remaps, parameter files and namespaces in a launch file actually took effect.
  • 关闭后测试（用 @launch_testing.post_shutdown_test() 装饰的类）在所有进程退出之后执行，能拿到每个进程的退出码和全部输出。最常见的一条是 launch_testing.asserts.assertExitCodes(proc_info)：节点被 launch 用 SIGINT 结束时是否干净退出（默认只接受 0）。崩溃、关闭时抛异常、析构顺序出错，都只在这一层暴露。
  • Post-shutdown tests (classes decorated with @launch_testing.post_shutdown_test()) run after every process has exited and can see each process’s exit code and full output. The most common one is launch_testing.asserts.assertExitCodes(proc_info): did each node exit cleanly when launch ended it with SIGINT (only 0 is accepted by default)? Crashes, exceptions during shutdown and wrong destruction order only show up at this layer.

集成测试互相隔离是个真问题：两个测试同时跑，各自起一个 talker，DDS 发现会把它们连在一起，测试就互相污染。官方集成测试教程的做法是在 CMake 里用 ament_cmake_ros 自带的 run_test_isolated.py 作为 runner 登记 add_launch_test，它给每个测试挑一个独占的 ROS_DOMAIN_ID。金字塔的顶层是系统测试：把真实录下的 bag 回放给整条链路，比较输出和上一次认可的参考结果，这是概念 2 和毕业项目的内容。

Isolating integration tests is a real problem: if two tests run at the same time, each starting a talker, DDS discovery connects them and the tests contaminate each other. The official integration-testing tutorial registers add_launch_test in CMake with run_test_isolated.py from ament_cmake_ros as the runner, which picks an exclusive ROS_DOMAIN_ID for each test. The top of the pyramid is the system test: replay a really recorded bag into the whole chain and compare the output with the last accepted reference; that is concept 2 and the capstone.

4. colcon test 跑了什么，结果去了哪里

4. What colcon test runs, and where the results go

colcon test 不自己执行测试，它按每个包的构建类型把活交出去，所以必须先 colcon build：

colcon test does not run tests itself; it hands the work to each package according to its build type, which is why you must colcon build first:

  • ament_cmake 包：colcon 在 build/<pkg> 里调用 CTest。ament_add_gtest、ament_add_pytest_test、add_launch_test 和 ament_lint_auto 在 CMake 配置时把每个测试登记成一个 CTest 条目；每个条目由 ament 的包装脚本运行，并写出一份 JUnit 风格的 XML，大致路径在 build/<pkg>/test_results/<pkg>/ 下，以实际目录为准。
  • ament_cmake packages: colcon invokes CTest in build/<pkg>. ament_add_gtest, ament_add_pytest_test, add_launch_test and ament_lint_auto registered each test as a CTest entry at configure time; each entry is run by an ament wrapper script that writes a JUnit-style XML file, at the approximate path build/<pkg>/test_results/<pkg>/; go by the real directory.
  • ament_python 包：colcon 直接调用 pytest，并传入 --junit-xml，结果写到 build/<pkg>/pytest.xml（colcon-core 的 pytest 任务源码里就是这个文件名）。ros2 pkg create 生成的 Python 包自带 test/test_copyright.py、test_flake8.py、test_pep257.py 三个风格检查，所以第一次 colcon test 就可能因为代码风格失败。
  • ament_python packages: colcon calls pytest directly with --junit-xml, writing the result to build/<pkg>/pytest.xml (that is the file name in the colcon-core pytest task source). A Python package generated by ros2 pkg create comes with three style checks, test/test_copyright.py, test_flake8.py and test_pep257.py, so your first colcon test may well fail on code style.

两件容易踩的事。第一，按 colcon 文档，测试失败不算 colcon test 的错误：测试挂了它照样以 0 退出，除非加 --return-code-on-test-failure。第二，colcon test-result 扫描 build/ 下所有结果文件做汇总，--verbose 打印每个失败用例；它的源码在有错误或失败时返回 1。所以 CI 脚本的惯用写法是 colcon test 之后再跑 colcon test-result --verbose，让后者的退出码决定成败。每个包的测试输出还会留在 log/latest_test/<pkg>/ 下（大致路径）。

Two things trip people up. First, per the colcon docs, failing tests are not errors for colcon test: it exits with 0 even when tests fail, unless you pass --return-code-on-test-failure. Second, colcon test-result scans every result file under build/ and summarizes them, and --verbose prints each failing case; its source returns 1 when there are errors or failures. So the usual CI pattern runs colcon test-result --verbose after colcon test and lets the former’s exit code decide. Each package’s test output also stays under log/latest_test/<pkg>/ (approximate path).

依赖从哪来：package.xml 里的 depend、test_depend 写的是 rosdep 键，不是 apt 包名。rosdep install --from-paths src --ignore-src -y 读出工作区里所有包的键，查 rosdep 数据库翻译成当前系统的 apt 包并安装，--ignore-src 跳过工作区里自己就有源码的包。依赖写全了，CI 和 Docker 构建才能在一台干净的机器上复现你的环境。

Where dependencies come from: depend and test_depend in package.xml hold rosdep keys, not apt package names. rosdep install --from-paths src --ignore-src -y collects the keys of every package in the workspace, translates them through the rosdep database into apt packages for the current system and installs them; --ignore-src skips packages whose source is already in the workspace. Only when dependencies are complete can CI and a Docker build reproduce your environment on a clean machine.

5. 持续集成：每次提交都在干净环境里重来一遍

5. Continuous integration: start from a clean environment on every commit

CI 的价值在于「干净」：你的容器里装过太多东西，一个漏写的依赖在本机永远发现不了。ros-tooling 提供两个 GitHub Action：setup-ros 在 runner 上配好 ROS 的 apt 源和构建工具；action-ros-ci 按 README 依次做 vcs import（可选）、把代码检出到工作区、rosdep install、colcon build、colcon test。下面的版本标签取自两个 README 的示例（2026-10-31 查，最新发布分别是 0.7.19 和 0.4.8），用之前请再核对：

The value of CI is that it is clean: your container has had too much installed into it, and a missing dependency will never show up on your own machine. ros-tooling provides two GitHub Actions: setup-ros configures the ROS apt source and build tools on the runner; per its README, action-ros-ci does vcs import (optional), checks the code out into a workspace, then runs rosdep install, colcon build and colcon test. 6. 部署：多阶段镜像

6. Deployment: multi-stage images

实验容器是开发环境：编译器、desktop、Gazebo、Nav2 全在里面。机器人上只需要运行你的包。多阶段构建在一个 Dockerfile 里写两个 FROM：第一阶段 FROM ros:jazzy-ros-base AS build，装依赖、拷源码、colcon build；第二阶段从一个更小的基础镜像重新开始，只用 COPY --from=build 拿走构建结果。最终镜像只包含最后一个阶段的层，第一阶段的编译器、源码、build/ 和 log/ 目录、apt 缓存都不会被带走。

The lab container is a development environment: compilers, desktop, Gazebo and Nav2 are all inside. The robot only needs your packages to run. A multi-stage build writes two FROM lines in one Dockerfile: the first stage, FROM ros:jazzy-ros-base AS build, installs dependencies, copies the source and runs colcon build; the second stage starts again from a smaller base image and takes only the build result with COPY --from=build. The final image contains only the layers of the last stage; the first stage’s compilers, source, build/ and log/ directories and apt caches are left behind.

What must be copied from the build stage: only install/. It is the overlay: each package’s executables, libraries, Python modules, share/<pkg>/package.xml, launch files and setup.bash. Three conditions decide whether the copy runs:

  1. 构建阶段不能用 --symlink-install。那个选项让 install/ 里放的是指回 src/ 和 build/ 的符号链接；只拷 install/，链接全部悬空。
  2. The build stage must not use --symlink-install. That option fills install/ with symbolic links back into src/ and build/; copy only install/ and every link dangles.
  3. 两个阶段同一发行版、同一 Ubuntu。C++ 可执行文件链接的是 /opt/ros/jazzy 里的库，Python 包装在 python3.12 的目录下；运行阶段换一个发行版或 Ubuntu 版本，就找不到这些库和路径。
  4. Both stages use the same distribution and the same Ubuntu. C++ executables link against libraries in /opt/ros/jazzy, and Python packages are installed under a python3.12 directory; a runtime stage on another distribution or Ubuntu release will not find those libraries and paths.
  5. 拷到同一个路径，运行依赖另装。colcon 生成的部分 setup 脚本里写着安装目录的绝对路径（推断，以生成的脚本为准），所以两边都用 /ws/install 最省事。你的包在运行时依赖、但 ros-core 里没有的 apt 包，要在运行阶段另外装，否则启动时报缺库。
  6. Copy to the same path, and install runtime dependencies separately. Some of the setup scripts colcon generates contain the absolute install path (inference; check the generated scripts), so using /ws/install in both stages is simplest. Any apt package your packages need at run time that ros-core lacks must be installed in the runtime stage, or start-up fails on a missing library.

7. 追踪：ros2_tracing 与 LTTng

7. Tracing: ros2_tracing and LTTng

日志告诉你「发生了什么」，追踪告诉你「什么时候、花了多久」。Phase 2 讲过：rclcpp、rcl 和 rmw 里编进了 tracepoint，例如 ros2:callback_start 和 ros2:callback_end；按 ros2_tracing 的 README，Iron 起 LTTng 是 ROS 2 的依赖，二进制安装开箱即可追踪，ros2 run tracetools status 应打印 Tracing enabled。

Logs tell you “what happened”; tracing tells you “when, and how long it took”. As Phase 2 explained, rclcpp, rcl and rmw are built with tracepoints such as ros2:callback_start and ros2:callback_end; per the ros2_tracing README, LTTng has been a ROS 2 dependency since Iron, a binary install can be traced out of the box, and ros2 run tracetools status should print Tracing enabled.

一个 tracepoint 花多少：没有追踪会话时，tracepoint 只是一次「这个事件开着吗」的判断，README 的说法是对执行几乎没有影响。会话开着时，LTTng-UST 在你的线程里把事件字段写进按 CPU 划分的共享内存环形缓冲区，然后立即返回；README 列出的特性是完全在用户态实现、可重入、不阻塞、快路径上没有系统调用、不复制追踪数据。把缓冲区搬到磁盘的是另一个 consumer 守护进程，不在你的线程上。README 引用的一篇综述给出 LTTng-UST 平均每个 tracepoint 约 158 ns 的延迟开销；具体数字随 CPU 和事件字段而变，在你的机器上要自己量（Lab B 第 8 步）。代价是真实存在的：每秒上万个回调就是每秒上万次写入，缓冲区写满时会丢事件。

What one tracepoint costs: with no tracing session, a tracepoint is just a check of “is this event enabled”, which the README describes as having virtually no impact on execution. With a session active, LTTng-UST writes the event fields into a per-CPU ring buffer in shared memory from your own thread and returns immediately; the README lists its properties as implemented entirely in user space, reentrant, non-blocking, no system calls in the fast path, and no copies of the trace data. Moving buffers to disk is done by a separate consumer daemon, not on your thread. A survey cited in the README gives LTTng-UST an average latency overhead of about 158 ns per tracepoint; the real number varies with the CPU and the event fields, so measure it on your machine (Lab B step 8). The cost is real: ten thousand callbacks a second means ten thousand writes a second, and events are lost when the buffers fill up.

它能看到什么：每个回调的开始和结束时间（于是有了耗时分布，而不是日志里的一个平均值）、回调属于哪个定时器或订阅、发布和对应回调之间隔了多久、执行器何时取到了哪个实体。要看线程何时被调度、何时在等锁，还得加内核事件（ros2 trace -k …），那需要另装 LTTng 内核模块，在容器里做不到。

What it reveals: the start and end time of every callback (so you get a distribution of durations rather than an average in a log line), which timer or subscription a callback belongs to, how long passes between a publish and the matching callback, and when the executor picked up which entity. To see when a thread was scheduled or waited on a lock you also need kernel events (ros2 trace -k …), which require the LTTng kernel modules installed separately and are not possible in the container.

README 里的硬规则：追踪必须在应用启动之前开始。节点初始化时会记录元数据（哪个回调地址属于哪个定时器、哪个节点），后面的事件要靠它解读；先启动节点再开追踪，得到的数据可能无法使用。所以 Lab B 先 ros2 trace start，再运行节点；launch 文件里的 Trace 动作（tracetools_launch）会自动保证这个顺序。追踪数据默认写到 ~/.ros/tracing/ 下。
A hard rule from the README: tracing must be started before the application is launched. Nodes record metadata during initialization (which callback address belongs to which timer and which node), and later events can only be interpreted with it; start the node first and the trace data may be unusable. That is why Lab B runs ros2 trace start before the node; the Trace action for launch files (tracetools_launch) guarantees this order automatically. Trace data goes under ~/.ros/tracing/ by default.

8. 系统边缘：micro-ROS 与 DDS 调优

8. At the edges: micro-ROS and DDS tuning

micro-ROS（只讲概念）把 ROS 2 的客户端 API 放到微控制器上。微控制器跑不动完整的 DDS，所以它用的是为资源受限设备设计的 XRCE-DDS 客户端，通过串口或 UDP 连到 Linux 一侧的 micro_ros_agent。按 micro-ROS-Agent 的 README，这个 agent 是一个包装了 Micro XRCE-DDS Agent 的 ROS 2 节点，代表微控制器上的节点和 DDS 网络打交道，让它们在 graph 里看起来和普通节点一样。电机驱动板、IMU 采集板常这样接入。

micro-ROS (concept only) puts the ROS 2 client API on microcontrollers. A microcontroller cannot run full DDS, so it uses an XRCE-DDS client designed for resource-constrained devices and connects over serial or UDP to a micro_ros_agent on the Linux side. Per the micro-ROS-Agent README, this agent is a ROS 2 node wrapping the Micro XRCE-DDS Agent; it deals with the DDS network on behalf of the nodes on the microcontroller, so they look like ordinary nodes in the graph. Motor driver boards and IMU boards are often connected this way.

DDS 调优：Phase 3 讲过，大消息走 UDP 时被拆成很多 IP 分片，丢一片整条作废。官方 DDS tuning 页列出的内核参数：net.ipv4.ipfrag_time（默认 30 s，残缺的分片在内存里留多久，调小能更快释放）、net.ipv4.ipfrag_high_thresh（分片重组可用的内存上限）、net.core.rmem_max（socket 接收缓冲区的上限；Cyclone DDS 想申请大缓冲区时，被这个上限截断）。这些是内核参数，属于 Docker Desktop 那台 VM 的内核，在实验容器里只能读不能改（推断，以实际报错为准）；在真机器人上用 sysctl -w 或 /etc/sysctl.d/ 设置。

DDS tuning: as Phase 3 explained, a large message sent over UDP is split into many IP fragments, and losing one voids the whole message. The kernel parameters listed on the official DDS tuning page are net.ipv4.ipfrag_time (default 30 s, how long incomplete fragments stay in memory; lowering it frees them sooner), net.ipv4.ipfrag_high_thresh (the memory limit for fragment reassembly) and net.core.rmem_max (the ceiling on socket receive buffers; when Cyclone DDS asks for a large buffer, this ceiling truncates it). These are kernel parameters belonging to the kernel of Docker Desktop’s VM, so in the lab container you can read them but not change them (inference; go by the actual error); on a real robot set them with sysctl -w or in /etc/sysctl.d/.

        self.publisher_.publish(msg)
        self.get_logger().info(f'Publishing: "{msg.data}"')

Self-check

1. CI 脚本里只有一行 colcon test。一个 pytest 用例明明失败了，流水线却是绿的。原因和修法是什么？

1. A CI script has a single line, colcon test. A pytest case clearly failed, yet the pipeline is green. What is the cause, and the fix?

colcon 文档明确说测试失败不被当作错误，colcon test-result 的源码在有错误或失败时返回 1。a 错在 colcon 对 ament_python 包直接调用 pytest，用例确实跑了才会失败；b 错在官方文档说测试前不必 source 工作区，而且用例失败本身说明它运行过、写了结果。The colcon docs state that failing tests are not considered errors, and the colcon test-result source returns 1 when there are errors or failures. a is wrong because colcon calls pytest directly for ament_python packages; the case only failed because it ran; b is wrong because the official docs say sourcing the workspace before testing is unnecessary, and a failing case shows it ran and wrote a result.

2. 你用 ros2 bag play run1（没有 --clock）把三天前录的 /scan 回放给一个节点，它对每条消息用 tf2 查 base_link 到 laser 在 header.stamp 时刻的变换。最可能发生什么？

2. You replay a /scan recorded three days ago with ros2 bag play run1 (no --clock) into a node that, for every message, asks tf2 for the base_link to laser transform at header.stamp. What most likely happens?

bag 保存的是序列化字节，header.stamp 原样回放；节点的时间默认是系统时钟，两者差了三天。b 错在播放器不反序列化、不改写消息内容；c 错在 use_sim_time 只是让节点去读 /clock，没有人发布 /clock 时它的时间停在 0（「未初始化」），定时器不触发，问题并没有解决。A bag stores serialized bytes and header.stamp is replayed unchanged; the node’s time is the system clock by default, three days apart. b is wrong because the player neither deserializes nor rewrites message content; c is wrong because use_sim_time only makes the node read /clock, and with nobody publishing /clock its time stays at 0 (“uninitialized”) and timers never fire, so nothing is fixed.

3. 多阶段 Dockerfile 的构建阶段运行 colcon build --symlink-install，运行阶段只 COPY --from=build /ws/install /ws/install。镜像构建成功，但 ros2 run py_pubsub talker 报找不到模块。为什么？

3. The build stage of a multi-stage Dockerfile runs colcon build --symlink-install, and the runtime stage only does COPY --from=build /ws/install /ws/install. The image builds, but ros2 run py_pubsub talker reports a missing module. Why?

符号链接被原样拷贝，目标却留在构建阶段里，最终镜像中不存在。去掉 --symlink-install，install/ 就是自包含的。a 错在按 REP 2001 ros_core 就包含 rclpy；c 错在 COPY --from 可以拷整个目录，本页的 Dockerfile 就是这么做的。The symbolic links are copied as they are, but their targets stay in the build stage and do not exist in the final image. Drop --symlink-install and install/ is self-contained. a is wrong because, per REP 2001, ros_core includes rclpy; c is wrong because COPY --from copies whole directories, as the Dockerfile on this page does.

4. 你先启动了一个长期运行的节点，半小时后才执行 ros2 trace start，停止后发现事件很多，却分不清哪个回调地址属于哪个定时器。最可能的原因是什么？

4. You started a long-running node first and ran ros2 trace start half an hour later. After stopping, there are many events, but you cannot tell which callback address belongs to which timer. What is the most likely cause?

ros2_tracing 的 README 要求追踪在应用启动之前开始，正是因为初始化阶段的元数据是解读后续事件的钥匙；launch 的 Trace 动作会自动保证顺序。a 错在丢事件发生在缓冲区写满时，不会专挑元数据；b 错在 ROS 2 的 tracepoint 全在用户态，callback_start 本身就带着回调地址，内核模块只影响内核事件。The ros2_tracing README requires tracing to start before the application precisely because initialization metadata is the key to interpreting later events; the Trace launch action guarantees the order automatically. a is wrong because events are lost when buffers fill up, not selectively metadata; b is wrong because the ROS 2 tracepoints are all in user space, callback_start itself carries the callback address, and kernel modules only matter for kernel events.

整门课的收尾是一个你能拿给别人看的包：scan_guard，一个 ament_python 节点，订阅 Phase 5 仿真机器人的 /scan（sensor_msgs/msg/LaserScan），在最近的有效距离小于参数 stop_distance 时在 /guard/stop 上发布 std_msgs/msg/Bool 的 true。逻辑很小，是故意的：功夫花在让它可测、可复现、可交付上。规格如下，每一条都对应本阶段的一个概念：

The course ends with a package you can show someone: scan_guard, an ament_python node that subscribes to /scan (sensor_msgs/msg/LaserScan) from the Phase 5 simulated robot and publishes true as a std_msgs/msg/Bool on /guard/stop when the nearest valid range drops below the parameter stop_distance. The logic is small on purpose: the effort goes into making it testable, reproducible and deliverable. The specification follows, each item matching a concept of this phase:

  1. 单元测试（概念 3）：把判断抽成纯函数 nearest_valid(ranges, range_min, range_max)，pytest 覆盖 inf、nan、小于 range_min、大于 range_max 和空数组。参数校验用 Phase 1 的 on-set 回调，拒绝非正的 stop_distance，也写一个测试。
  2. Unit tests (concept 3): factor the decision into a pure function nearest_valid(ranges, range_min, range_max), with pytest covering inf, nan, values below range_min or above range_max, and an empty array. Validate parameters with the on-set callback from Phase 1, rejecting a non-positive stop_distance, and test that too.
  3. 集成测试（概念 3、4）：一个 launch test 起 scan_guard，测试类自己发布一条最近距离 0.3 m 的假 LaserScan，断言 5 秒内在 /guard/stop 上收到 true；再发一条全部 3 m 的，断言收到 false。关闭后测试断言退出码为 0。用独占 domain 的 runner 登记。
  4. Integration test (concepts 3 and 4): a launch test starts scan_guard; the test class publishes a fake LaserScan whose nearest range is 0.3 m and asserts that true arrives on /guard/stop within 5 seconds, then one with every range at 3 m and asserts false. A post-shutdown test asserts exit code 0. Register it with the exclusive-domain runner.
  5. bag 回归（概念 2，动画 (b)）：在 Gazebo 里用 teleop_twist_keyboard 把机器人开向一面墙再开走，ros2 bag record --use-sim-time -o scan_run /scan 录下输入（前提是 /clock 已经从 Gazebo 桥接到 ROS 一侧，否则录制器一条也不写）。用 ros2 bag play scan_run --clock --topics /scan 回放给 use_sim_time:=true 的 scan_guard，录下 /guard/stop，人工确认一次后存成 golden。写一个 launch test，用 ExecuteProcess 起播放器，测试类订阅 /guard/stop，把每次状态切换的仿真时间和 golden 比较，容差 0.2 s。bag 放在 test/data/ 下，这样 colcon test 每次都会重跑这条回归。
  6. Bag regression (concept 2, diagram (b)): in Gazebo, drive the robot towards a wall and away again with teleop_twist_keyboard, recording the input with ros2 bag record --use-sim-time -o scan_run /scan (this assumes /clock is already bridged from Gazebo to the ROS side; otherwise the recorder writes nothing). Replay it with ros2 bag play scan_run --clock --topics /scan into scan_guard running with use_sim_time:=true, record /guard/stop, check it by hand once and keep it as golden. Write a launch test that starts the player with ExecuteProcess, subscribes to /guard/stop in the test class, and compares the simulation time of every state change with golden, within 0.2 s. Keep the bags under test/data/ so that colcon test reruns this regression every time.
  7. CI（概念 5）：一个 GitHub Actions 工作流，setup-ros 加 action-ros-ci，package-name: scan_guard。CI 里没有 Gazebo，回归测试只依赖 bag，正好能跑。
  8. CI (concept 5): a GitHub Actions workflow with setup-ros and action-ros-ci, package-name: scan_guard. CI has no Gazebo; the regression test needs only the bag, so it runs there.
  9. 部署镜像（概念 6）：Lab B 的多阶段 Dockerfile，运行阶段 ros:jazzy-ros-core，CMD 是 ros2 run scan_guard scan_guard，stop_distance 通过 --ros-args -p 在 docker run 时给出。确认 sensor_msgs 在运行阶段可用（它属于 common_interfaces）。
  10. Deployment image (concept 6): the multi-stage Dockerfile from Lab B, runtime stage ros:jazzy-ros-core, CMD set to ros2 run scan_guard scan_guard, with stop_distance given through --ros-args -p at docker run. Confirm that sensor_msgs is available in the runtime stage (it belongs to common_interfaces).
  11. 性能报告（概念 7）：回放 scan_run 时追踪 scan_guard，给出 /scan 回调的中位数、p99 和最大耗时，并说明它在 lidar 的扫描周期里占多少。scan_guard 是 Python 节点：rclpy 是否带 callback_start 一类 tracepoint，请先用 babeltrace 看实际事件；若没有，就把节点用 C++ 重写一个版本来测，或者在报告里写明这个限制。
  12. Performance report (concept 7): trace scan_guard while replaying scan_run, and report the median, p99 and maximum duration of the /scan callback and what share of the lidar scan period it takes. scan_guard is a Python node: check with babeltrace whether rclpy emits tracepoints like callback_start; if it does not, write a C++ version of the node to measure, or state the limitation in the report.

读 bag 的比较脚本可以照 rosbag2 jazzy 分支里 rosbag2_py 的测试写：rosbag2_py.SequentialReader()、open(StorageOptions(uri=…, storage_id='mcap'), ConverterOptions('cdr', 'cdr'))，循环 has_next() 和 read_next() 拿到话题、字节和时间戳，再用 rclpy.serialization.deserialize_message 和 rosidl_runtime_py.utilities.get_message 还原消息。交付物是一个仓库：包源码与 test/、test/data/ 下的两个 bag、CI 工作流、Dockerfile、一份 README，写清如何重录 golden 以及性能报告的数字。

The comparison script that reads bags can follow the rosbag2_py tests in the rosbag2 jazzy branch: rosbag2_py.SequentialReader(), open(StorageOptions(uri=…, storage_id='mcap'), ConverterOptions('cdr', 'cdr')), then loop over has_next() and read_next() to get topic, bytes and timestamp, and rebuild each message with rclpy.serialization.deserialize_message and rosidl_runtime_py.utilities.get_message. The deliverable is one repository: the package source with test/, the two bags under test/data/, the CI workflow, the Dockerfile, and a README that explains how to re-record golden and gives the numbers of the performance report.

What comes next

做完毕业项目，ROS 2 这条线就走完了：从一个节点，到一个能建图、导航、被测试、被打包的机器人栈。往下有两条路，都是这门课里已经碰到、但没有展开的东西：

With the capstone done, the ROS 2 track is complete: from one node to a robot stack that maps, navigates, is tested and is packaged. Two paths lead on, both about things this course touched without going deep:

  • Parallel Programming（专题规划中）：执行器的线程、回调组的互斥与可重入、回调之间共享的数据，本质上都是并发问题。那个专题会从线程、内存模型和数据并行讲起，回头再看 Phase 2 的 MultiThreadedExecutor 会清楚得多。
  • Parallel Programming (topic in planning): executor threads, mutually exclusive and reentrant callback groups, and data shared between callbacks are concurrency problems at heart. That topic starts from threads, memory models and data parallelism, and Phase 2’s MultiThreadedExecutor will look much clearer afterwards.
  • Kernel Engineering：这门课里每一处「容器里做不到」都指向它：PREEMPT_RT 和调度器（Phase 2）、UDP 与 socket 缓冲区（Phase 3 和本阶段的 rmem_max）、LTTng 的内核事件（本阶段）、以及 ros2_control 背后的设备驱动。一台能装自己内核的 Linux 机器，加上那个专题，就能把这些补上。
  • Kernel Engineering: every “not possible in the container” in this course points there: PREEMPT_RT and the scheduler (Phase 2), UDP and socket buffers (Phase 3 and rmem_max in this phase), LTTng kernel events (this phase), and the device drivers behind ros2_control. A Linux machine that can install its own kernel, plus that topic, fills those gaps.
