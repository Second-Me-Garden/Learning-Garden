Environment setup · before any lab

实验环境Lab environment Lab environment: arm64 container, browser desktop, VM fallbackarm64 container, browser desktop, VM fallback

ROS 2 的实验不会像内核实验那样把机器弄崩，但它会往系统里加一个 apt 源和几百个包，会在局域网上用 UDP 多播找同伴，而且 macOS 本身不是 Jazzy 的正式支持平台。所以本课程的实验全部跑在 Apple Silicon Mac 上的一个 Linux 客体里：首选一个 arm64 Docker 容器，里面装 ROS 2 Jazzy、Gazebo Harmonic 和一个从浏览器打开的轻量桌面；备选一台 UTM 里的 Ubuntu 24.04 虚拟机，或者一台带 GPU 的云主机。宿主 Mac 只负责编辑文件和开浏览器。

ROS 2 labs will not crash the machine the way kernel labs do, but ROS 2 adds an apt repository and hundreds of packages to the system, finds its peers by UDP multicast on the local network, and macOS itself is not an officially supported platform for Jazzy. So every lab in this course runs in a Linux guest on the Apple Silicon Mac: first choice is an arm64 Docker container holding ROS 2 Jazzy, Gazebo Harmonic and a lightweight desktop opened from the browser; the fallbacks are an Ubuntu 24.04 VM in UTM or a cloud machine with a GPU. The host Mac only edits files and opens a browser.

为什么要隔离

Why isolate

  • 安装面很大。一次 ros-jazzy-desktop 加 Gazebo、Nav2、ros2_control 会装进一个第三方 apt 源和几百个包，还会在 /opt/ros/jazzy 下放一整套环境脚本。放在容器里，删掉镜像就干净了；放在你每天用的系统里，就很难再说清哪些文件是谁装的。
  • The install surface is large. One ros-jazzy-desktop plus Gazebo, Nav2 and ros2_control brings in a third-party apt repository and hundreds of packages, and drops a whole set of environment scripts under /opt/ros/jazzy. In a container, deleting the image leaves nothing behind; on the system you use every day, it soon becomes hard to say which files came from where.
  • 发现流量是局域网多播。ROS 2 默认的 DDS 中间件用 UDP 多播做节点发现：同一网段里、ROS_DOMAIN_ID 相同的每一台 ROS 2 机器都会看到你的节点和话题，你也会收到它们的数据。在公司、学校或共享 Wi-Fi 上，这既会串数据，也会把你的话题暴露给别人。实验环境默认只在本机内发现（见概念 4）。
  • Discovery traffic is LAN multicast. ROS 2’s default DDS middleware discovers nodes by UDP multicast: every ROS 2 machine on the same subnet with the same ROS_DOMAIN_ID sees your nodes and topics, and you receive their data. On an office, campus or shared Wi-Fi network this mixes up data and exposes your topics to others. The lab environment discovers only within the machine by default (see concept 4).
  • macOS 不是 Jazzy 的正式平台。REP 2000 给 Jazzy 列的 Tier 1 平台是 Ubuntu 24.04（Noble）的 amd64 和 arm64，以及 Windows 10；macOS 只列为 Tier 3（amd64、源码编译），Apple Silicon 上的 macOS 不在表里。Linux 客体里的 Ubuntu 24.04 arm64 正好是 Tier 1。
  • macOS is not an official Jazzy platform. REP 2000 lists Jazzy’s Tier 1 platforms as Ubuntu 24.04 (Noble) on amd64 and arm64, plus Windows 10; macOS appears only as Tier 3 (amd64, built from source), and macOS on Apple Silicon is not in the table. Ubuntu 24.04 arm64 in a Linux guest is exactly a Tier 1 platform.
  • 可重来。镜像就是一份可重建的环境说明：./lab.sh build 在任何一台 Apple Silicon Mac 上得到同样的东西，./lab.sh snapshot 存一个可以回退的点。
  • Repeatable. The image is an environment description you can rebuild: ./lab.sh build gives the same result on any Apple Silicon Mac, and ./lab.sh snapshot saves a point you can go back to.
一条规则：宿主 Mac 不装 ROS 2、不加 ROS apt 源、不跑 ROS 节点。宿主上只做三件事：用编辑器改 share/ 下的文件、跑 ./lab.sh、在浏览器里开 http://localhost:6080/vnc.html。
One rule: the host Mac gets no ROS 2 install, no ROS apt repository and no ROS nodes. The host does three things only: edit files under share/, run ./lab.sh, and open http://localhost:6080/vnc.html in the browser.

2. 镜像：ros-base 之上装桌面

2. The image: a desktop on top of ros-base

建一个实验目录 ~/ros2-lab，下面四个文件都放在里面。Dockerfile 分三层：ROS 2 包、浏览器桌面、启动脚本。基础镜像已经配好了 ROS 的 apt 源，所以直接 apt-get install。

Create a lab directory ~/ros2-lab and put the four files below in it. The Dockerfile has three layers: ROS 2 packages, the browser desktop, and the start script. The base image already has the ROS apt repository configured, so it can apt-get install directly.

# Dockerfile: ROS 2 Jazzy lab for Apple Silicon (linux/arm64)
FROM ros:jazzy-ros-base
ENV DEBIAN_FRONTEND=noninteractive
# discover only within this container (Jazzy variable; see concept 4)
ENV ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST

# 1. ROS 2 packages (names checked in the Jazzy arm64 apt index, 2026-10-31)
RUN apt-get update && apt-get install -y --no-install-recommends \
      ros-jazzy-desktop \
      ros-jazzy-ros-gz \
      ros-jazzy-navigation2 ros-jazzy-nav2-bringup \
      ros-jazzy-slam-toolbox \
      ros-jazzy-ros2-control ros-jazzy-ros2-controllers ros-jazzy-gz-ros2-control \
      ros-jazzy-rqt ros-jazzy-rqt-common-plugins \
    && rm -rf /var/lib/apt/lists/*

# Optional, for the tracing lab (Phase 7): the ros2 trace command
# RUN apt-get update && apt-get install -y --no-install-recommends \
#       ros-jazzy-ros2trace ros-jazzy-tracetools-launch && rm -rf /var/lib/apt/lists/*

# 2. Browser desktop: XFCE + TigerVNC + noVNC, plus glxinfo
RUN apt-get update && apt-get install -y --no-install-recommends \
      xfce4 xfce4-terminal dbus-x11 \
      tigervnc-standalone-server novnc websockify \
      mesa-utils \
    && rm -rf /var/lib/apt/lists/*

# 3. Start script and shell setup
COPY start-desktop.sh /usr/local/bin/start-desktop.sh
RUN chmod +x /usr/local/bin/start-desktop.sh \
 && echo 'source /opt/ros/jazzy/setup.bash' >> /root/.bashrc \
 && mkdir -p /root/ws/src
WORKDIR /root/ws
EXPOSE 6080
CMD ["/usr/local/bin/start-desktop.sh"]

启动脚本先开一个虚拟 X 显示 :1（TigerVNC 的 Xtigervnc，VNC 端口 5901，只接受容器内的连接），在上面跑 XFCE，最后用 websockify 把 VNC 转成浏览器能连的 WebSocket，并在 6080 端口提供 noVNC 网页（Ubuntu 的 novnc 包把网页放在 /usr/share/novnc）。

The start script first opens a virtual X display :1 (TigerVNC’s Xtigervnc, VNC port 5901, accepting connections from inside the container only), runs XFCE on it, and finally uses websockify to turn VNC into a WebSocket the browser can reach, serving the noVNC web page on port 6080 (Ubuntu’s novnc package puts the page in /usr/share/novnc).

#!/bin/sh
# start-desktop.sh: X display :1 + XFCE + noVNC on port 6080
set -eu
Xtigervnc :1 -rfbport 5901 -geometry 1600x900 -depth 24 -localhost -SecurityTypes None &
sleep 2
DISPLAY=:1 dbus-launch startxfce4 >/tmp/xfce.log 2>&1 &
exec websockify --web /usr/share/novnc 6080 localhost:5901
VNC 没有设密码（-SecurityTypes None）。这只在两层限制同时成立时才安全：Xtigervnc 只听容器内的回环地址，compose.yaml 只把 6080 发布到 Mac 的 127.0.0.1。不要把端口改成 "6080:6080"，那样同一网络里的人都能打开你的桌面。
VNC has no password (-SecurityTypes None). This is safe only while two limits both hold: Xtigervnc listens only on the container’s loopback, and compose.yaml publishes 6080 only on the Mac’s 127.0.0.1. Do not change the port to "6080:6080"; anyone on the same network could then open your desktop.

4. 网络：发现、ROS_DOMAIN_ID 与 ROS_AUTOMATIC_DISCOVERY_RANGE

4. Networking: discovery, ROS_DOMAIN_ID and ROS_AUTOMATIC_DISCOVERY_RANGE

ROS 2 没有中心的 master。每个节点启动时，DDS 向网络发 UDP 多播的「我在这里」消息，收到的节点再直接建立连接。端口号由 ROS_DOMAIN_ID 算出：ID 不同，端口不同，两组节点就互相看不见。这就是为什么一个网络里的每个人或每台机器人应该用自己的 ID。

ROS 2 has no central master. When each node starts, DDS sends UDP multicast “I am here” messages to the network, and the nodes that receive them connect directly. Port numbers are computed from ROS_DOMAIN_ID: different IDs give different ports, so the two groups of nodes cannot see each other. That is why each person or robot on a network should use its own ID.

ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST 更进一步：节点只在本机内发现和通信，不往网卡发多播。在容器里，「本机」是容器的网络命名空间，所以同一容器里的多个 shell 照常互通（两个 ./lab.sh shell 进的是同一个容器），别的机器则完全看不到你。本页默认打开它，原因就是上面那条：发现流量是局域网多播，而你不知道同一网络里还有谁在跑 ROS 2。

ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST goes further: nodes discover and talk only within the machine, and send no multicast out of the network card. In the container, “the machine” is the container’s network namespace, so several shells in the same container talk as usual (two ./lab.sh shell sessions enter the same container), while other machines cannot see you at all. This page turns it on by default for the reason above: discovery traffic is LAN multicast, and you do not know who else on the network is running ROS 2.

ROS_AUTOMATIC_DISCOVERY_RANGE 是 Iron 引入、Jazzy 文档使用的变量，取值有 SUBNET（默认，发现多播能到达的所有节点）、LOCALHOST、OFF、SYSTEM_DEFAULT。旧教程里常见的 ROS_LOCALHOST_ONLY=1 是它的弃用旧名：从 Iron 起弃用，Jazzy 仍然照办，但每个节点启动时打印一行 ROS_LOCALHOST_ONLY is deprecated but still honored 警告，而且一旦设为 1，会压过 ROS_AUTOMATIC_DISCOVERY_RANGE 和 ROS_STATIC_PEERS。迁到 Lyrical 时旧名可能被移除（以 Lyrical 文档为准），所以本页不用它。
ROS_AUTOMATIC_DISCOVERY_RANGE was introduced in Iron and is the variable the Jazzy docs use; its values are SUBNET (the default: every node reachable by multicast), LOCALHOST, OFF and SYSTEM_DEFAULT. The ROS_LOCALHOST_ONLY=1 common in older tutorials is its deprecated old name: deprecated since Iron, still honoured on Jazzy, but it prints a ROS_LOCALHOST_ONLY is deprecated but still honored warning each time a node starts, and once set to 1 it overrides ROS_AUTOMATIC_DISCOVERY_RANGE and ROS_STATIC_PEERS. The old name may be removed by the time you move to Lyrical (check the Lyrical docs), so this page does not use it.

以后要让容器和一台真机器人或另一台电脑通信时（Phase 6 之后），才把它关掉，并且两边约定同一个 ROS_DOMAIN_ID。Docker Desktop 默认的 bridge 网络下，多播能不能走出那台 Linux VM 到达局域网，随 Docker Desktop 版本和网络设置变化（推断，以 Docker 文档为准）；跨机通信更稳的做法是 UTM 虚拟机的桥接网络或 ROS_STATIC_PEERS。

Only later, when the container must talk to a real robot or another computer (after Phase 6), do you turn it off, and then both sides agree on the same ROS_DOMAIN_ID. On Docker Desktop’s default bridge network, whether multicast can leave that Linux VM and reach the LAN varies with the Docker Desktop version and network settings (inference; the Docker docs are authoritative); for cross-machine traffic, a UTM VM on a bridged network or ROS_STATIC_PEERS is more dependable.

5. 内核交叉点：容器共享一个内核

5. Kernel crossover: containers share one kernel

做过 Kernel Engineering 专题的话，这一节是两门课的接口。容器不是虚拟机：它只是一组命名空间和 cgroup，所有容器共用 Docker Desktop 那台 Linux VM 的内核。对 ROS 2 来说这没问题，因为 ROS 2 全在用户态：节点是普通进程，执行器是线程，DDS 用的是普通的 UDP 套接字和共享内存。

If you have done the Kernel Engineering topic, this section is the interface between the two courses. A container is not a VM: it is just a set of namespaces and cgroups, and every container shares the kernel of Docker Desktop’s Linux VM. That is fine for ROS 2, because ROS 2 lives entirely in user space: nodes are ordinary processes, executors are threads, and DDS uses ordinary UDP sockets and shared memory.

  • SCHED_FIFO 需要权限。把一个线程设成实时 FIFO 调度要 CAP_SYS_NICE 能力，或者 RLIMIT_RTPRIO 允许的优先级。cap_add: [SYS_NICE] 和 ulimits: rtprio: 99 两样都给，Phase 2 的 chrt -f 80 和 rclcpp 里设线程优先级才会成功。
  • SCHED_FIFO needs privilege. Putting a thread under real-time FIFO scheduling needs the CAP_SYS_NICE capability, or a priority allowed by RLIMIT_RTPRIO. Give both, cap_add: [SYS_NICE] and ulimits: rtprio: 99, and the Phase 2 chrt -f 80 and setting thread priorities in rclcpp will succeed.
  • PREEMPT_RT 在这里做不到。实时补丁内核是内核本身的属性，要换的是 Docker Desktop 那台 VM 的内核，而它由 Docker Desktop 管理，你换不了。在容器里 apt install 一个 RT 内核包也没用：容器根本不引导内核。所以这里的实时实验只能演示「有优先级」和「没有优先级」的区别，测不出真正的实时延迟上限。要做 PREEMPT_RT，得用一台能装自己内核的 Linux 机器（UTM 虚拟机可以试，但虚拟化本身会带来延迟抖动，推断）。
  • PREEMPT_RT is not possible here. A real-time patched kernel is a property of the kernel itself; what would have to change is the kernel of Docker Desktop’s VM, which Docker Desktop manages and you cannot replace. Running apt install for an RT kernel package inside the container does nothing either: a container never boots a kernel. So the real-time labs here can only show the difference between “with priority” and “without priority”; they cannot measure a true real-time latency bound. For PREEMPT_RT you need a Linux machine that can install its own kernel (a UTM VM is worth a try, but virtualisation itself adds latency jitter; inference).
  • 不要用 --privileged 代替。它给的权限远多于 SYS_NICE，包括往那台共享 VM 的内核里装模块。只加需要的那一项能力。
  • Do not use --privileged instead. It grants far more than SYS_NICE, including loading modules into the shared VM’s kernel. Add only the one capability you need.

7. lab.sh 与快照

7. lab.sh and snapshots

把常用的五个动作收进一个脚本，以后每个 Phase 都只敲 ./lab.sh：

Collect the five common actions in one script, so every later Phase only needs ./lab.sh:

#!/bin/sh
# lab.sh: ROS 2 lab container.  Usage: ./lab.sh build|up|shell|down|snapshot [tag]
set -eu
cd "$(dirname "$0")"
mkdir -p share
case "${1:-}" in
  build)    docker compose build ;;
  up)       docker compose up -d
            echo "desktop: http://localhost:6080/vnc.html" ;;
  shell)    docker compose exec ros bash ;;
  down)     docker compose down ;;
  snapshot) tag="snap-${2:-$(date +%Y%m%d-%H%M)}"
            docker commit ros2-lab "ros2-lab:$tag"
            echo "saved ros2-lab:$tag (the ws volume is NOT included)" ;;
  *)        echo "usage: $0 build|up|shell|down|snapshot [tag]" >&2; exit 2 ;;
esac
  • snapshot 存的是什么：docker commit 把容器当前的文件系统（比如你后来 apt install 的包）存成一个新镜像标签，但不包括命名卷。你的代码在 ws 卷里，它本来就不随容器消失；要备份它，另外打包：docker run --rm -v ros2-lab_ws:/ws -v "$PWD/share:/out" ubuntu:24.04 tar czf /out/ws.tgz -C /ws .（卷名是项目名 ros2-lab 加 _ws，用 docker volume ls 确认）。
  • What snapshot saves: docker commit saves the container’s current filesystem (for example packages you apt install-ed later) as a new image tag, but does not include named volumes. Your code is in the ws volume, which does not disappear with the container anyway; to back it up, archive it separately: docker run --rm -v ros2-lab_ws:/ws -v "$PWD/share:/out" ubuntu:24.04 tar czf /out/ws.tgz -C /ws . (the volume name is the project name ros2-lab plus _ws; confirm with docker volume ls).
  • 回到某个快照：docker tag ros2-lab:snap-名字 ros2-lab:jazzy，再 ./lab.sh down 和 ./lab.sh up。想回到完全干净的状态，就 ./lab.sh build 重建。
  • Going back to a snapshot: docker tag ros2-lab:snap-name ros2-lab:jazzy, then ./lab.sh down and ./lab.sh up. To return to a completely clean state, rebuild with ./lab.sh build.
  • 资源预算（推断）：镜像装完大约数 GB 到十几 GB；在 Docker Desktop 的设置里给它的 VM 至少 8 GB 内存和 4 个 CPU，Gazebo 软件渲染很吃 CPU。不做实验时 ./lab.sh down 并退出 Docker Desktop。
  • Resource budget (inference): the finished image is roughly several GB to over ten GB; in Docker Desktop’s settings give its VM at least 8 GB of memory and 4 CPUs, since Gazebo’s software rendering is CPU-hungry. When not doing labs, run ./lab.sh down and quit Docker Desktop.

延伸阅读：《ROS 2 From Scratch》讲工作区和 colcon 构建的章节（~/ws 里以后放什么）。

Further reading: the chapters of ROS 2 From Scratch on workspaces and building with colcon (what goes into ~/ws later).

自测

Self-check

1. 为什么实验环境默认设 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST？

1. Why does the lab environment set ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST by default?

它把发现限制在本机（这里是容器的网络命名空间），别的机器看不到你。同一容器里的节点本来就互通，设不设都一样；它和渲染无关，渲染由 LIBGL_ALWAYS_SOFTWARE 和有没有 GPU 决定。It limits discovery to the machine (here, the container’s network namespace), so other machines cannot see you. Nodes in the same container talk either way; it has nothing to do with rendering, which depends on LIBGL_ALWAYS_SOFTWARE and whether there is a GPU.

2. 在 UTM 的 Ubuntu 虚拟机里，gz sim shapes.sdf 的窗口一打开就黑屏崩溃。最合适的做法是？

2. In the Ubuntu VM in UTM, the gz sim shapes.sdf window goes black and crashes as soon as it opens. What is the best move?

问题在 UTM 不完整的 OpenGL，图形界面才需要它；服务端无头运行不受影响。osrf/ros 的 desktop 镜像只列 amd64，而且换镜像不改变虚拟机的 OpenGL；域 ID 只管发现，和渲染无关。The problem is UTM’s partial OpenGL, which only the GUI needs; the headless server is unaffected. The osrf/ros desktop images list amd64 only, and changing images does not change the VM’s OpenGL; the domain ID governs discovery only and has nothing to do with rendering.

3. 容器里 chrt -f 80 … 报 Operation not permitted。按本页的设计，应该怎么做？

3. In the container, chrt -f 80 … reports Operation not permitted. Following this page’s design, what should you do?

SCHED_FIFO 需要 CAP_SYS_NICE 或 rtprio 上限，只给这一项能力就够。容器不引导内核，装 RT 内核包不起作用；--privileged 能用但给得太多，连往共享 VM 内核装模块都允许。SCHED_FIFO needs CAP_SYS_NICE or an rtprio limit, and that one capability is enough. A container never boots a kernel, so installing an RT kernel package has no effect; --privileged would work but grants far too much, even loading modules into the shared VM kernel.

4. 你跑了 ./lab.sh snapshot clean，后来在 ~/ws 里写了一个包，又 apt install 了几个工具。回到 snap-clean 镜像后，会发生什么？

4. You ran ./lab.sh snapshot clean, then wrote a package in ~/ws and apt install-ed a few tools. After going back to the snap-clean image, what happens?

docker commit 只存容器自己的文件系统，apt 装的工具在那里，回到旧镜像就没了。~/ws 是命名卷，不在快照里，也不随镜像切换改变。快照不只是标签：它是一个新的镜像层。docker commit saves only the container’s own filesystem, where the apt-installed tools live, so going back to the old image drops them. ~/ws is a named volume, not in the snapshot and unchanged by switching images. A snapshot is not only a tag: it is a new image layer.
