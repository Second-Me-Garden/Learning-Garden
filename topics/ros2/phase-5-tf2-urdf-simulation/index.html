1. 坐标系约定：REP 103 与 REP 105

1. Frame conventions: REP 103 and REP 105

两个人写的节点要能对上，先得对坐标轴达成一致。REP 103 规定：坐标系都是右手系；相对机器人本体，x 向前、y 向左、z 向上；单位用米、弧度、秒。所以一台机器人「向前开」就是沿自己的 +x，「左转」就是绕 +z 的正角速度，/cmd_vel 里的 linear.x 和 angular.z 正是这个意思。

Before nodes written by different people can fit together, they must agree on the axes. REP 103 says: all frames are right-handed; relative to the robot body, x forward, y left, z up; units are metres, radians and seconds. So “drive forward” means along the robot’s own +x, and “turn left” means a positive angular velocity about +z, which is exactly what linear.x and angular.z in /cmd_vel mean.

REP 105 规定移动机器人的几个标准坐标系，排成一条链 earth → map → odom → base_link（本课程用不到 earth）：

REP 105 defines the standard frames of a mobile robot as one chain, earth → map → odom → base_link (this course does not need earth):

  • base_link：固定在机器人底盘上，随机器人一起动。传感器的坐标系（如 lidar）挂在它下面。
  • base_link: rigidly attached to the robot base and moving with it. Sensor frames such as lidar hang below it.
  • odom：世界固定的坐标系，机器人在里面的位姿由里程计（轮子编码器、视觉里程计、IMU）积分出来。REP 105 要求它连续：位姿平滑变化、不跳变；代价是误差随时间累积、会漂移。所以它适合短时间的局部控制，不适合当长期参考。
  • odom: a world-fixed frame in which the robot’s pose is integrated from odometry (wheel encoders, visual odometry, an IMU). REP 105 requires it to be continuous: the pose evolves smoothly without jumps; the price is that error accumulates and it drifts. So it is good for short-term local control and poor as a long-term reference.
  • map：同样是世界固定的坐标系，机器人在里面的位姿由定位模块根据传感器观测反复重算，不漂移，但可以跳变：新观测到来时，位姿可能一下子挪一段。所以它适合当长期全局参考，不适合直接拿来做局部控制。
  • map: also world-fixed; the robot’s pose in it is recomputed again and again by a localization component from sensor observations, so it does not drift but can jump: when new observations arrive, the pose may move suddenly. So it is a good long-term global reference and a poor frame for local control.

谁发布哪一段：tf 是一棵树，每个坐标系只能有一个父坐标系。所以 REP 105 规定 map 是 odom 的父、odom 是 base_link 的父：里程计（本页是 Gazebo 的差速驱动插件，概念 7）发布 odom → base_link；定位模块（Phase 6 的 AMCL 或 SLAM）不直接发 map → base_link，而是算出 map → odom 这一段「修正量」来发。这样两边各管一段，互不覆盖；也正因为如此，跳变只发生在 map → odom 上，控制器在 odom 里看到的轨迹始终是平滑的。

Who publishes which link: tf is a tree, and each frame may have only one parent. So REP 105 makes map the parent of odom and odom the parent of base_link: odometry (on this page, Gazebo’s differential-drive plugin, concept 7) publishes odom → base_link; the localization component (AMCL or SLAM in Phase 6) does not publish map → base_link directly, but computes and publishes the correction map → odom. Each side owns one link and neither overwrites the other; and for the same reason, jumps happen only on map → odom, while the trajectory a controller sees in odom stays smooth.

2. tf2 树、广播者与监听者，以及查变换为什么要带时间

2. The tf2 tree, broadcasters and listeners, and why a lookup needs a time

tf2 不是一个中心服务器，而是两个普通话题加每个进程里的一份缓冲区：

tf2 is not a central server; it is two ordinary topics plus one buffer inside each process:

  • 动态变换走 /tf：会随时间变的边，比如 odom → base_link、轮子的转角。发布者用 tf2_ros::TransformBroadcaster（Python 是 tf2_ros.TransformBroadcaster），每条 TransformStamped 带一个时间戳、一个父坐标系 header.frame_id 和一个子坐标系 child_frame_id。
  • Dynamic transforms go on /tf: links that change over time, such as odom → base_link or a wheel’s angle. Publishers use tf2_ros::TransformBroadcaster (tf2_ros.TransformBroadcaster in Python), and every TransformStamped carries a timestamp, a parent frame header.frame_id and a child frame child_frame_id.
  • 静态变换走 /tf_static：永远不变的边，比如 base_link → lidar。发布者用 StaticTransformBroadcaster，只发一次；话题是 transient_local，晚加入的监听者也能拿到（Phase 3 概念 4）。命令行也能发：ros2 run tf2_ros static_transform_publisher --x 0.1 --frame-id base_link --child-frame-id lidar。
  • Static transforms go on /tf_static: links that never change, such as base_link → lidar. Publishers use StaticTransformBroadcaster and send once; the topic is transient_local, so late-joining listeners still receive it (Phase 3 concept 4). The command line can publish one too: ros2 run tf2_ros static_transform_publisher --x 0.1 --frame-id base_link --child-frame-id lidar.
  • 监听者：tf2_ros::Buffer 加 TransformListener。listener 订阅这两个话题，把收到的每条边按时间存进 Buffer；你的代码只和 Buffer 打交道，调用 lookupTransform(target, source, time)（Python 是 lookup_transform）。结果是 source 坐标系在 target 坐标系里的位姿，也就是「把 source 里的数据变到 target 里」用的那个变换。
  • Listeners: a tf2_ros::Buffer plus a TransformListener. The listener subscribes to both topics and stores every link it receives in the Buffer by time; your code deals only with the Buffer, calling lookupTransform(target, source, time) (lookup_transform in Python). The result is the pose of the source frame in the target frame, that is, the transform that takes data from source into target.

为什么要带时间：机器人在动。一帧激光扫描在 12.35 秒测得，等它到你的回调已经是 12.40 秒；这 50 ms 里底盘可能转了几度。要把这帧扫描放进 odom，用的必须是 12.35 秒那一刻 的 odom → base_link，而不是「现在」的。所以每条传感器消息都带 header.stamp，查变换时就用这个时间。用错时刻的后果是：机器人转弯时，墙在地图里被画成弯的或重影的。

Why a time is needed: the robot moves. A laser scan is measured at 12.35 s and reaches your callback at 12.40 s; in those 50 ms the base may have turned several degrees. To put the scan into odom you must use odom → base_link at 12.35 s, not “now”. That is why every sensor message carries header.stamp, and the lookup uses that time. Use the wrong instant and, while the robot turns, walls are drawn bent or doubled in the map.

缓冲区存了什么、插值的是什么：Buffer 为树上的每一条动态边保存一段按时间排序的样本，默认保留 10 秒（Jazzy 的 tf2 源码和教程，2026-10-31 核对）。查询时刻 t 时，tf2 先在树上找出从 source 到 target 的路径，再对路径上的每一条边分别取 t 时刻的值：t 正好落在两个样本之间，就在这两个样本之间插值——平移做线性插值，旋转做四元数球面插值（slerp）；静态边对任何时刻都返回同一个值。最后把各边首尾组合起来。注意 tf2 只内插不外推：

What the buffer stores and what it interpolates: for every dynamic link in the tree, the Buffer keeps a time-ordered series of samples, by default for 10 seconds (Jazzy tf2 source and tutorial, checked 2026-10-31). To look up time t, tf2 first finds the path from source to target in the tree, then takes the value at t on each link of the path separately: when t falls between two samples, it interpolates between those two — linear interpolation for translation, quaternion spherical interpolation (slerp) for rotation; a static link returns the same value for any time. Finally it composes the links end to end. Note that tf2 only interpolates and never extrapolates:

  • t 晚于某条边的最新样本：报 Lookup would require extrapolation into the future，并给出请求时刻和最新数据时刻。最常见的原因是你用了「现在」，而那条边的下一个样本还在路上。办法是给 lookup 加一个超时，让它等几十毫秒。
  • t later than a link’s newest sample: it raises Lookup would require extrapolation into the future, giving the requested time and the time of the latest data. The usual cause is asking for “now” while that link’s next sample is still in flight. The fix is to give the lookup a timeout so it waits a few tens of milliseconds.
  • t 早于缓冲区里最旧的样本（超过 10 秒前）：报 extrapolation into the past。
  • t earlier than the oldest sample in the buffer (more than 10 seconds ago): it raises extrapolation into the past.
  • t = 0（C++ 的 tf2::TimePointZero，Python 的 rclpy.time.Time()）不是「1970 年」，而是「最新可用」：tf2 取路径上所有边都有数据的最晚共同时刻。它方便调试，但对传感器数据不对，因为那不是测量的时刻。
  • t = 0 (tf2::TimePointZero in C++, rclpy.time.Time() in Python) does not mean 1970; it means “latest available”: tf2 takes the latest time at which every link on the path has data. It is handy for debugging but wrong for sensor data, because it is not the time of the measurement.
两个查错工具：ros2 run tf2_tools view_frames 听几秒 tf，生成一份 PDF 画出整棵树，每条边标着发布者和频率；ros2 run tf2_ros tf2_echo map base_link 持续打印 base_link 在 map 里的位姿（第一个参数是 target，第二个是 source，和 lookup 的顺序一样）。树断开时，view_frames 里会看到两棵互不相连的树。
Two debugging tools: ros2 run tf2_tools view_frames listens to tf for a few seconds and writes a PDF of the whole tree, with each link labelled by its publisher and rate; ros2 run tf2_ros tf2_echo map base_link keeps printing the pose of base_link in map (the first argument is the target and the second the source, in the same order as a lookup). When the tree is broken, view_frames shows two trees that do not connect.

3. 仿真时间：use_sim_time 与 /clock

3. Simulation time: use_sim_time and /clock

仿真器的时间和墙上的时间不是一回事。Gazebo 每一步物理推进固定的仿真时长，但每一步花多少真实时间取决于 CPU；在实验容器里用 llvmpipe 软件渲染激光雷达，仿真很可能比真实时间慢（Gazebo 界面上显示的 real time factor 小于 1），你也可以随时暂停它。传感器消息的时间戳、差速驱动发出的 tf，都用仿真时间打戳，是从仿真开始算起的几十、几百秒。

Simulator time is not wall-clock time. Each Gazebo physics step advances a fixed amount of simulated time, but how much real time a step takes depends on the CPU; with the lidar rendered by llvmpipe in the lab container, the simulation will likely run slower than real time (the real time factor shown in the Gazebo GUI is below 1), and you can pause it at any moment. Sensor message timestamps and the tf from the differential drive are all stamped in simulation time: tens or hundreds of seconds since the simulation started.

机制：仿真器把自己的时钟发布在 /clock 话题上（类型 rosgraph_msgs/msg/Clock，本页由桥从 Gazebo 转过来）。每个 ROS 节点都有一个内置参数 use_sim_time，默认 false；设为 true 后，这个节点的 ROS 时钟不再读系统时间，而是订阅 /clock，now() 返回收到的最新仿真时刻。按节点时钟走的定时器（create_timer）也跟着仿真时间走，仿真暂停它就停；create_wall_timer 则仍按真实时间。

Mechanism: the simulator publishes its clock on the /clock topic (type rosgraph_msgs/msg/Clock; on this page the bridge forwards it from Gazebo). Every ROS node has a built-in parameter use_sim_time, false by default; set to true, the node’s ROS clock stops reading system time, subscribes to /clock instead, and now() returns the latest simulated instant received. Timers that run on the node clock (create_timer) follow simulation time too and stop when the simulation pauses; create_wall_timer still runs on real time.

缺了它会坏在哪里：假设 RViz2 忘了设 use_sim_time。它的「现在」是 Unix 时间，约 17 亿秒；而缓冲区里 odom → base_link 的样本都打着「第 120 秒」这样的仿真时间戳。RViz2 按自己的「现在」去查变换，请求时刻比最新样本晚了十几亿秒，就是概念 2 里的 extrapolation into the future；激光扫描的显示会因为找不到对应时刻的变换而丢弃消息，机器人模型显示报错。反过来也一样：你的节点用墙上时间给自己发的消息打戳，别的节点在仿真时间里查不到它。所以规则很简单：仿真时，系统里每一个节点都设 use_sim_time:=true，包括 robot_state_publisher、RViz2 和你自己写的节点。

What breaks without it: suppose RViz2 forgot to set use_sim_time. Its “now” is Unix time, about 1.7 billion seconds, while the odom → base_link samples in the buffer carry simulated stamps such as “second 120”. RViz2 looks up transforms at its own “now”, a requested time over a billion seconds after the newest sample: that is the extrapolation into the future of concept 2; the laser scan display drops messages because it cannot find a transform for their time, and the robot model display shows errors. It works the other way too: a node that stamps its own messages with wall time cannot be looked up by other nodes running in simulation time. So the rule is simple: in simulation, set use_sim_time:=true on every node in the system, including robot_state_publisher, RViz2 and your own nodes.

设了 use_sim_time 但还没收到第一条 /clock 时，now() 大致返回 0（推断，具体行为查 rclcpp 和 rclpy 的文档）。所以启动顺序是：先起仿真器和 /clock 的桥，再起其他节点；否则早启动的节点会先用 0 时刻打几条戳。
With use_sim_time set but before the first /clock message arrives, now() returns roughly 0 (inference; check the rclcpp and rclpy docs for the exact behaviour). So the start-up order is: simulator and the /clock bridge first, then the other nodes; otherwise a node started early stamps a few messages at time 0.

4. URDF 与 xacro，robot_state_publisher，RViz2

4. URDF and xacro, robot_state_publisher, RViz2

URDF（Unified Robot Description Format）是一份 XML，根元素 <robot>，里面两种东西：

URDF (Unified Robot Description Format) is an XML file with root element <robot>, holding two kinds of things:

  • <link>：一个刚体。<visual> 是给人看的形状，<collision> 是物理引擎算碰撞用的形状（通常更简单），<inertial> 是质量和惯性张量。RViz2 只要 visual；仿真器三样都要，缺了 inertial 的 link 在 Gazebo 里不会按你想的那样动。
  • <link>: one rigid body. <visual> is the shape people see, <collision> the shape the physics engine uses for contacts (usually simpler), and <inertial> the mass and inertia tensor. RViz2 needs only the visual; a simulator needs all three, and a link without inertial does not move the way you expect in Gazebo.
  • <joint>：连接一个父 link 和一个子 link。<origin xyz rpy> 是关节零位时子 link 在父 link 里的位姿；type 决定能怎么动：fixed 不动（雷达支架），continuous 绕 <axis> 无限转（轮子），revolute 绕轴在上下限之间转（机械臂关节）。
  • <joint>: connects one parent link to one child link. <origin xyz rpy> is the child’s pose in the parent when the joint is at zero; type says how it moves: fixed does not move (a lidar mount), continuous spins without limit about its <axis> (a wheel), revolute turns about the axis between limits (an arm joint).

每个 link 一个坐标系、每个 joint 一条边，所以一份 URDF 天然就是一棵 tf 树。xacro 是 XML 的宏处理器：<xacro:property> 定义常量，<xacro:macro> 定义可带参数的片段（左右两个轮子写一次），${...} 里能做算术，<xacro:arg> 和 <xacro:if> 按命令行参数开关一段内容。xacro robot.urdf.xacro 把它展开成普通 URDF 打到标准输出。

One frame per link and one tree edge per joint, so a URDF is a tf tree by construction. xacro is a macro processor for XML: <xacro:property> defines constants, <xacro:macro> defines parameterised fragments (write the left and right wheel once), ${...} evaluates arithmetic, and <xacro:arg> with <xacro:if> switches a section on or off by a command-line argument. xacro robot.urdf.xacro expands it into a plain URDF on standard output.

What robot_state_publisher does: it reads the URDF string from the parameter robot_description (which must be set at start-up, or the node fails to start), and then:

  • 所有 fixed 关节在启动时往 /tf_static 发一次；
  • publishes every fixed joint once on /tf_static at start-up;
  • 可动关节（continuous、revolute）的变换取决于关节角，它订阅 /joint_states（sensor_msgs/msg/JointState），每收到新的关节角就算出对应变换发到 /tf（频率上限由 publish_frequency 参数决定，默认 20 Hz）；
  • for movable joints (continuous, revolute) the transform depends on the joint angle, so it subscribes to /joint_states (sensor_msgs/msg/JointState) and, for each new set of angles, computes the transforms and publishes them on /tf (capped by the publish_frequency parameter, 20 Hz by default);
  • 把 URDF 原文再发到 /robot_description 话题上（transient_local），RViz2 的 RobotModel 显示和 Gazebo 的生成工具都从这里读。
  • republishes the URDF text on the /robot_description topic (transient_local), which RViz2’s RobotModel display and Gazebo’s spawn tool read.

这就解释了一个常见现象：底盘和雷达显示正常，轮子却报「没有变换」。fixed 关节走的是 /tf_static，不需要任何人；轮子是 continuous 关节，没人发 /joint_states，robot_state_publisher 就算不出它们。真机上 /joint_states 来自电机驱动，仿真里来自 Gazebo（概念 7），只想在 RViz2 里看模型时，用 joint_state_publisher_gui 拖滑条手动给。

This explains a common sight: the base and lidar display fine, but the wheels report “no transform”. Fixed joints go through /tf_static and need nobody; the wheels are continuous joints, and with nobody publishing /joint_states, robot_state_publisher cannot compute them. On a real robot /joint_states comes from the motor drivers, in simulation from Gazebo (concept 7); when you only want to view the model in RViz2, joint_state_publisher_gui provides it by hand with sliders.

RViz2 是一个 tf2 监听者加一组显示插件。它有一个 Fixed Frame（全局参考坐标系），每个显示把自己的数据按消息时间戳变换到这个坐标系里画出来：RobotModel 画 URDF 的每个 link，TF 画每个坐标系的三色轴（红 x、绿 y、蓝 z），LaserScan 画 /scan 的点。某个显示变红报错时，几乎总是两件事之一：它要的坐标系在树里接不到 Fixed Frame，或者它请求的时刻缓冲区里没有。

RViz2 is a tf2 listener plus a set of display plugins. It has a Fixed Frame (the global reference frame), and each display transforms its data into that frame by the message timestamp and draws it: RobotModel draws each URDF link, TF draws each frame’s three coloured axes (red x, green y, blue z), and LaserScan draws the points of /scan. When a display turns red with an error, it is almost always one of two things: the frame it needs does not connect to the Fixed Frame in the tree, or the buffer has no data for the time it asked for.

5. Gazebo Harmonic：SDF 世界、系统插件、仿真传感器

5. Gazebo Harmonic: SDF worlds, system plugins, simulated sensors

Gazebo Harmonic 是 Jazzy 推荐配套的仿真器，实验镜像里的 ros-jazzy-ros-gz 通过 ROS 的 vendor 包把它装了进来。它读 SDF（Simulation Description Format）：<world> 里放灯光、地面、若干 <model> 和若干 <plugin>；model 里是 link、joint、sensor，和 URDF 很像，但多了世界、物理、插件这些 URDF 没有的东西（对照表）。gz sim world.sdf 启动服务器和图形界面，-r 表示一启动就开始跑，-s 表示只起服务器、不开界面。

Gazebo Harmonic is the simulator recommended for Jazzy; ros-jazzy-ros-gz in the lab image installs it through the ROS vendor packages. It reads SDF (Simulation Description Format): a <world> holds lights, a ground, several <model>s and several <plugin>s; a model holds links, joints and sensors much like URDF, plus world, physics and plugins, which URDF lacks (see the comparison table). gz sim world.sdf starts the server and the GUI; -r runs the simulation on start, and -s starts only the server, without the GUI.

系统插件：Gazebo 的服务器本身几乎什么都不做，物理、传感器、差速驱动都是一个个「system」，编成共享库、在 SDF 里用 <plugin filename="…" name="…"> 加载。2026-10-31 的 Harmonic 教程里用到的几个（名字查文档）：gz-sim-physics-system（物理）、gz-sim-user-commands-system（接收生成模型等命令）、gz-sim-scene-broadcaster-system（把场景发给界面）、gz-sim-sensors-system（渲染类传感器，带 <render_engine>ogre2</render_engine>）。一个容易踩的坑：Gazebo 自带的 empty.sdf 只加载了物理、用户命令、场景广播和接触这几个，没有 Sensors 系统，你挂上去的激光雷达不会出任何数据。所以 Lab B 自己写一个世界文件。

System plugins: the Gazebo server itself does almost nothing; physics, sensors and differential drive are each a “system”, built as a shared library and loaded in SDF with <plugin filename="…" name="…">. The ones used in the Harmonic tutorials as of 2026-10-31 (names: check the docs): gz-sim-physics-system (physics), gz-sim-user-commands-system (accepts commands such as spawning models), gz-sim-scene-broadcaster-system (sends the scene to the GUI), and gz-sim-sensors-system (rendering-based sensors, with <render_engine>ogre2</render_engine>). An easy trap: Gazebo’s bundled empty.sdf loads only physics, user commands, scene broadcaster and contact, with no Sensors system, so a lidar attached to your robot produces no data at all. That is why Lab B writes its own world file.

仿真传感器怎么出数据：激光雷达在 SDF 里是 <sensor type="gpu_lidar">，配上采样数、角度范围、量程和 <update_rate>。Sensors 系统按这个频率，用渲染引擎从雷达的位置朝每个角度「看」一次场景，读出最近表面的距离，填进一条 gz.msgs.LaserScan，发到 SDF 里 <topic> 指定的 Gazebo 话题上。相机（camera）同理，渲染出一幅图；IMU（imu，由 gz-sim-imu-system 处理）不需要渲染，直接从物理引擎读加速度和角速度。所以在软件渲染的容器里，雷达和相机会是最吃 CPU 的部分。

How a simulated sensor produces data: in SDF a lidar is a <sensor type="gpu_lidar"> with its sample count, angle range, range limits and <update_rate>. At that rate the Sensors system uses the rendering engine to “look” at the scene from the lidar’s position at each angle, reads the distance to the nearest surface, fills a gz.msgs.LaserScan and publishes it on the Gazebo topic named by the SDF <topic>. A camera (camera) works the same way and renders an image; an IMU (imu, handled by gz-sim-imu-system) needs no rendering and reads acceleration and angular velocity straight from the physics engine. So in the software-rendered container, lidar and cameras will be the most CPU-hungry part.

和 Kernel Engineering 的连接：仿真里的传感器插件，替代的是 Kernel Engineering Phase 5 里的设备驱动那一整条链。一台真的激光雷达接在 USB 串口或以太网上：数据到达时设备触发中断，内核驱动的上半部和下半部把字节搬进缓冲区（可能经过 DMA），再经字符设备（如 /dev/ttyUSB0）或 UDP socket 交给用户态的 ROS 驱动节点，由它解析成 LaserScan 发布（具体走哪条路取决于雷达型号，属推断）。在 Gazebo 里，这一切都换成了 Sensors 系统里的一次渲染查询：没有中断、没有 DMA、没有驱动代码。好处是可重复；代价是驱动层的问题——中断延迟、缓冲区溢出、串口丢字节、驱动 bug——仿真里一个也看不到。SDF 能给传感器加噪声模型（写法查文档），但那只模拟测量误差，不模拟驱动。
The connection to Kernel Engineering: a sensor plugin in simulation stands in for the whole device-driver chain of Kernel Engineering Phase 5. A real lidar sits on USB serial or Ethernet: when data arrives the device raises an interrupt, the kernel driver’s top and bottom halves move the bytes into a buffer (possibly via DMA), and a character device (such as /dev/ttyUSB0) or a UDP socket hands them to a user-space ROS driver node, which parses them into a LaserScan and publishes it (which path depends on the lidar model; inference). In Gazebo all of this becomes one rendering query inside the Sensors system: no interrupt, no DMA, no driver code. The gain is repeatability; the cost is that driver-level problems — interrupt latency, buffer overruns, bytes lost on a serial line, driver bugs — never show up in simulation. SDF can add a noise model to a sensor (syntax: check the docs), but that models measurement error, not the driver.

6. ros_gz_bridge：它转换什么，为什么两边类型必须对上

6. ros_gz_bridge: what it converts, and why the types must match on both sides

Gazebo 不说 DDS。它有自己的通信库 gz-transport 和自己的消息类型（gz.msgs.*，Protobuf 定义），话题空间和 ROS 完全分开：Gazebo 里有一个 /scan，ROS 里不会自动出现 /scan。ros_gz_bridge 的 parameter_bridge 是一个同时加入两边的进程：对你声明的每一个话题，它在一边订阅、把消息逐字段拷进另一边的类型、在另一边发布。命令行写法是「话题名 @ ROS 类型 方向符 Gazebo 类型」：

Gazebo does not speak DDS. It has its own communication library, gz-transport, its own message types (gz.msgs.*, defined in Protobuf), and a topic space completely separate from ROS: a /scan in Gazebo does not make a /scan appear in ROS. The parameter_bridge of ros_gz_bridge is one process that joins both sides: for each topic you declare, it subscribes on one side, copies the message field by field into the other side’s type, and publishes there. The command-line form is “topic name @ ROS type, direction sign, Gazebo type”:

ros2 run ros_gz_bridge parameter_bridge \
  /scan@sensor_msgs/msg/LaserScan[gz.msgs.LaserScan \
  /cmd_vel@geometry_msgs/msg/Twist]gz.msgs.Twist
# 方向符：@ 双向，[ 只从 Gazebo 到 ROS，] 只从 ROS 到 Gazebo（parameter_bridge 的帮助文字，jazzy 分支）

为什么类型必须两边都对：桥只认识一张固定的「ROS 类型 ↔ Gazebo 类型」对照表（README 里列着，例如 sensor_msgs/msg/LaserScan ↔ gz.msgs.LaserScan、tf2_msgs/msg/TFMessage ↔ gz.msgs.Pose_V），每一对都有一段手写的转换代码。你声明的那一对，决定了它在 ROS 一侧用什么类型建发布者或订阅者，在 Gazebo 一侧用什么类型。两侧又各自只和同类型的端点相连：ROS 里，一个类型不同的发布者在发现时就不会和桥的订阅者匹配（Phase 3 概念 3）；Gazebo 里，插件订阅的话题如果收到别的类型也不会处理。所以任何一侧对不上，结果都是「不报错、没数据」。最典型的是 teleop_twist_keyboard 设了 stamped:=true：它改发 TwistStamped，而桥声明的是 Twist，机器人纹丝不动。

Why the types must match on both sides: the bridge knows only one fixed table of “ROS type ↔ Gazebo type” pairs (listed in the README, for example sensor_msgs/msg/LaserScan ↔ gz.msgs.LaserScan and tf2_msgs/msg/TFMessage ↔ gz.msgs.Pose_V), each with a hand-written conversion. The pair you declare decides which type the bridge uses for its publisher or subscription on the ROS side and which type on the Gazebo side. Each side then connects only to endpoints of the same type: in ROS, a publisher of a different type never matches the bridge’s subscription at discovery (Phase 3 concept 3); in Gazebo, a plugin does not handle a message of another type on its topic. So a mismatch on either side ends the same way: no error, no data. The classic case is teleop_twist_keyboard with stamped:=true: it then publishes TwistStamped, the bridge declared Twist, and the robot does not move.

桥只转换内容，不改时间戳和坐标系名：Gazebo 消息头里的时间（仿真时间）和 frame_id 原样进入 ROS 消息（除非打开 override_timestamps_with_wall_time 之类的选项，查 README）。所以两件事要在 Gazebo 一侧就做对：/clock 要桥过来，让 ROS 节点能用 use_sim_time；传感器消息的 frame_id 要和 URDF 里的 link 名一致，否则 RViz2 在 tf 树里找不到它。Harmonic 的传感器可以用 <gz_frame_id> 指定这个名字（gz-sensors8 源码里读这个元素；写法查文档）。话题多了可以写成 YAML 配置文件，用 -p config_file:=… 加载，格式查 README。

The bridge converts content only; it does not change timestamps or frame names: the time in the Gazebo message header (simulation time) and its frame_id go into the ROS message unchanged (unless an option such as override_timestamps_with_wall_time is enabled; see the README). So two things must be right on the Gazebo side: /clock must be bridged so ROS nodes can use use_sim_time; and the frame_id of sensor messages must equal the link name in the URDF, or RViz2 cannot find it in the tf tree. Harmonic sensors can set this name with <gz_frame_id> (the gz-sensors8 source reads this element; syntax: check the docs). With many topics you can write a YAML configuration file and load it with -p config_file:=…; for the format, see the README.

生成模型：ros2 run ros_gz_sim create -topic robot_description -name bot 从 ROS 话题 /robot_description（就是 robot_state_publisher 发的那份 URDF）读出机器人描述，请 Gazebo 把它加进正在运行的世界。Gazebo 加载 URDF 时，由 libsdformat 在内部把它转成 SDF。也可以用 ros2 launch ros_gz_sim gz_sim.launch.py gz_args:="-r world.sdf" 从 ROS 的 launch 体系里启动 Gazebo 本身。

Spawning: ros2 run ros_gz_sim create -topic robot_description -name bot reads the robot description from the ROS topic /robot_description (the very URDF that robot_state_publisher publishes) and asks Gazebo to add it to the running world. When Gazebo loads a URDF, libsdformat converts it to SDF internally. You can also start Gazebo itself from the ROS launch system with ros2 launch ros_gz_sim gz_sim.launch.py gz_args:="-r world.sdf".

7. 差速驱动插件：odom → base_link 从哪里来

7. The differential-drive plugin: where odom → base_link comes from

两轮差速机器人靠左右轮的速度差转弯：给定线速度 v 和角速度 ω，左右轮的线速度分别是 v − ω·L/2 和 v + ω·L/2（L 是轮距），除以轮半径就是轮子的角速度。Gazebo 的 DiffDrive 系统（gz-sim-diff-drive-system，名字查文档）把这件事双向都做了：

A two-wheel differential-drive robot turns by the speed difference between its left and right wheels: given a linear velocity v and angular velocity ω, the wheels’ linear speeds are v − ω·L/2 and v + ω·L/2 (L is the wheel separation), and dividing by the wheel radius gives each wheel’s angular velocity. Gazebo’s DiffDrive system (gz-sim-diff-drive-system; name: check the docs) does this in both directions:

  • 输入：订阅一个 gz.msgs.Twist 话题（<topic>，不设时默认是 /model/<模型名>/cmd_vel），按上面的公式给 <left_joint> 和 <right_joint> 设速度，由物理引擎去转轮子。
  • Input: subscribes to a gz.msgs.Twist topic (<topic>, default /model/<model name>/cmd_vel) and sets the velocities of <left_joint> and <right_joint> by the formula above; the physics engine turns the wheels.
  • 输出：反过来从两个轮子实际转过的角度积分出底盘位姿，也就是轮式里程计，以 <odom_publish_frequency>（默认 50 Hz）发两样东西：一条 gz.msgs.Odometry 到 <odom_topic>（默认 /model/<模型名>/odometry），以及同一个位姿作为一条变换、以 gz.msgs.Pose_V 发到 <tf_topic>（默认 /model/<模型名>/tf）。桥把后者转成 tf2_msgs/msg/TFMessage 接到 ROS 的 /tf 上，它就是 tf 树里的 odom → base_link。
  • Output: in the other direction it integrates the base pose from how far the two wheels actually turned — wheel odometry — and at <odom_publish_frequency> (default 50 Hz) publishes two things: a gz.msgs.Odometry on <odom_topic> (default /model/<model name>/odometry), and the same pose as a transform, a gz.msgs.Pose_V, on <tf_topic> (default /model/<model name>/tf). The bridge turns the latter into a tf2_msgs/msg/TFMessage on ROS /tf, and that is the odom → base_link of the tf tree.

一处必须改的默认值：DiffDrive 发出的这条变换，父坐标系默认叫 <模型名>/odom，子坐标系默认叫 <模型名>/<link 名>（gz-sim8 的 DiffDrive.hh 注释，2026-10-31 核对）。如果不改，ROS 里会出现一条 bot/odom → bot/base_link，和 URDF 里的 base_link 是两棵不相连的树。所以 Lab B 用 <frame_id>odom</frame_id> 和 <child_frame_id>base_link</child_frame_id> 把它们改成 REP 105 的名字。轮子自己的转角则由另一个系统 JointStatePublisher（gz-sim-joint-state-publisher-system）发出，经桥变成 /joint_states，robot_state_publisher 再算出轮子的 tf——和 Lab A 里滑条做的事一样，只是来源换成了仿真器。

One default that must change: the transform DiffDrive publishes has a parent frame named <model name>/odom and a child frame named <model name>/<link name> by default (comments in gz-sim8 DiffDrive.hh, checked 2026-10-31). Left alone, ROS gets a bot/odom → bot/base_link link, a tree that does not connect to the URDF’s base_link. So Lab B renames them to the REP 105 names with <frame_id>odom</frame_id> and <child_frame_id>base_link</child_frame_id>. The wheels’ own angles come from another system, JointStatePublisher (gz-sim-joint-state-publisher-system), which the bridge turns into /joint_states, from which robot_state_publisher computes the wheel tf — the same job as the sliders in Lab A, with the simulator as the source.

Phase 6 会换一种做法：用 ros2_control 的 diff_drive_controller 代替这个 Gazebo 插件，odom → base_link 改由控制器在 ROS 一侧发布。两种做法不要同时开，否则 odom → base_link 有两个发布者，tf 会在两个值之间来回跳。
Phase 6 takes another route: ros2_control’s diff_drive_controller replaces this Gazebo plugin, and odom → base_link is published by the controller on the ROS side. Do not run both at once, or odom → base_link gets two publishers and tf jumps back and forth between their values.

    # tf_probe.py: look up the same transforms at different times, once per second
import rclpy
from rclpy.duration import Duration
from rclpy.node import Node
from rclpy.time import Time
from tf2_ros import TransformException
from tf2_ros.buffer import Buffer
from tf2_ros.transform_listener import TransformListener

TARGET, SOURCE = 'base_link', 'left_wheel'   # Lab B：改成 'odom', 'base_link'


class TfProbe(Node):
    def __init__(self):
        super().__init__('tf_probe')
        self.buffer = Buffer()                       # 默认缓存 10 秒
        # spin_thread=True：listener 在自己的线程里收 /tf，
        # 否则下面带超时的 lookup 会挡住同一个执行器，永远等不到新数据
        self.listener = TransformListener(self.buffer, self, spin_thread=True)
        self.timer = self.create_timer(1.0, self.tick)

    def show(self, label, target, source, when, timeout=Duration()):
        try:
            t = self.buffer.lookup_transform(target, source, when, timeout)
        except TransformException as ex:
            self.get_logger().warn(f'{label}: {ex}')
            return
        p, q, s = t.transform.translation, t.transform.rotation, t.header.stamp
        self.get_logger().info(
            f'{label}: {source} in {target} @ {s.sec}.{s.nanosec:09d} '
            f'xyz=({p.x:.3f}, {p.y:.3f}, {p.z:.3f}) '
            f'q=({q.x:.3f}, {q.y:.3f}, {q.z:.3f}, {q.w:.3f})')

    def tick(self):
        now = self.get_clock().now()
        self.show('static, latest', 'base_link', 'lidar', Time())
        self.show('dynamic, latest', TARGET, SOURCE, Time())
        self.show('dynamic, now', TARGET, SOURCE, now)
        self.show('dynamic, now + wait', TARGET, SOURCE, now, Duration(seconds=0.2))
        self.show('dynamic, 20 s ago', TARGET, SOURCE, now - Duration(seconds=20.0))


def main():
    rclpy.init()
    rclpy.spin(TfProbe())


if __name__ == '__main__':
    main()

1. 一帧激光扫描的时间戳是 12.35 秒。缓冲区里 odom → base_link 有 12.34 和 12.36 两个样本，base_link → lidar 是静态的。lookup_transform('odom', 'lidar', 12.35) 会怎样？

1. A laser scan is stamped 12.35 s. The buffer holds odom → base_link samples at 12.34 and 12.36, and base_link → lidar is static. What does lookup_transform('odom', 'lidar', 12.35) do?

tf2 对路径上每条动态边在请求时刻两侧的样本之间插值，静态边对任何时刻都有效，最后组合。a 错在 tf2 不是取最近样本，而是插值。c 错在静态边不看时间，只有动态边会因时刻超出范围而报 extrapolation。tf2 interpolates each dynamic link on the path between the samples either side of the requested time, treats static links as valid at any time, and composes the result. a is wrong because tf2 interpolates rather than taking the nearest sample. c is wrong because static links ignore time; only dynamic links raise extrapolation errors when the time is out of range.

2. Gazebo 和其他节点都用 use_sim_time:=true 运行，只有 RViz2 忘了设。最可能看到什么？

2. Gazebo and all other nodes run with use_sim_time:=true; only RViz2 forgot it. What are you most likely to see?

RViz2 本身是 tf2 监听者，用自己的时钟查变换；它的「现在」比缓冲区里最新的仿真样本晚了十几亿秒。a 错在 RViz2 不只是看，它要按时刻查 tf。b 混淆了两件事：use_sim_time 不影响 QoS 匹配，消息照样能收到，只是变换查不到。RViz2 is itself a tf2 listener and looks up transforms with its own clock; its “now” is over a billion seconds past the newest simulated sample in the buffer. a is wrong because RViz2 does more than view: it looks up tf at given times. b confuses two things: use_sim_time does not affect QoS matching; messages still arrive, only the transforms cannot be found.

3. 桥声明的是 /cmd_vel@geometry_msgs/msg/Twist]gz.msgs.Twist，而 teleop 以 stamped:=true 运行。机器人不动。原因是？

3. The bridge declares /cmd_vel@geometry_msgs/msg/Twist]gz.msgs.Twist, and teleop runs with stamped:=true. The robot does not move. Why?

桥只转换声明过的那一对类型，ROS 一侧的订阅者是 Twist，TwistStamped 的发布者与它不匹配，不报错也没数据。b 错在 ] 正是「从 ROS 到 Gazebo」，指令就该这个方向。c 错在桥不做类型之间的猜测转换；而且换回 stamped:=false 后机器人能动，说明轮距不是原因。The bridge converts only the declared type pair; its ROS-side subscription is Twist, and a TwistStamped publisher does not match it: no error, no data. b is wrong because ] is exactly “ROS to Gazebo”, the right direction for commands. c is wrong because the bridge does not guess conversions between types; and with stamped:=false the robot moves, so the wheel separation is not the cause.

4. 在 RViz2 里，底盘和雷达显示正常，两个轮子却报没有变换。最可能缺了什么？

4. In RViz2 the base and lidar display fine, but both wheels report no transform. What is most likely missing?

fixed 关节（雷达、万向球）走 /tf_static，不依赖任何人；continuous 关节的变换取决于关节角，要有人发 /joint_states：Lab A 里是滑条，Lab B 里是 Gazebo 的 JointStatePublisher。a 错在雷达也走 /tf_static 却显示正常。c 错在没有 robot_description 时 robot_state_publisher 根本起不来，底盘也不会显示。Fixed joints (lidar, caster) go through /tf_static and depend on nobody; continuous joints depend on the joint angle, so someone must publish /joint_states: the sliders in Lab A, Gazebo’s JointStatePublisher in Lab B. a is wrong because the lidar also uses /tf_static and displays fine. c is wrong because without robot_description, robot_state_publisher does not start at all and the base would not display either.
