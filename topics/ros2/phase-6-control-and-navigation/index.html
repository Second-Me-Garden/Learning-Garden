Phase 5 里，机器人靠 Gazebo 自带的差速插件动起来：/cmd_vel 进去，轮子转，odom 出来，中间发生了什么你看不见，也换不到真车上。这一阶段把这段路拆成两层。下层是 ros2_control：一个按固定周期运行的循环，每个周期从硬件读状态、让控制器算一次、再把命令写回硬件；同一个 diff_drive_controller 既能驱动 Gazebo 里的关节，也能驱动真正的电机，换的只是硬件插件。上层是 Nav2：一棵行为树把「去那里」拆成规划、跟随和脱困三类动作调用，规划器和控制器各看一张 costmap，AMCL 或 slam_toolbox 告诉它们机器人在地图的哪里。实验里你先给 Phase 5 的机器人换上 ros2_control，再用 slam_toolbox 建一张房间地图，最后让 Nav2 在这张图上自己开过去。

In Phase 5 the robot moved thanks to Gazebo’s own differential-drive plugin: /cmd_vel went in, the wheels turned, odom came out, and what happened in between was invisible and could not move to a real robot. This phase splits that path into two layers. The lower one is ros2_control: a loop that runs at a fixed period and, every period, reads state from the hardware, lets the controllers compute once, and writes commands back; the same diff_drive_controller drives joints in Gazebo or real motors, and only the hardware plugin changes. The upper one is Nav2: a behavior tree breaks “go there” into three kinds of action calls (plan, follow, recover), the planner and the controller each look at a costmap, and AMCL or slam_toolbox tells them where the robot is on the map. In the labs you first give the Phase 5 robot ros2_control, then build a map of a room with slam_toolbox, and finally let Nav2 drive across that map on its own.

核心概念

Core concepts

1. ros2_control 的结构：硬件、接口、控制器

1. The structure of ros2_control: hardware, interfaces, controllers

ros2_control 把「和硬件打交道」与「控制算法」切开，中间只隔着一层接口。四个角色：

ros2_control separates “talking to hardware” from “the control algorithm”, with only a layer of interfaces between them. Four roles:

  • 硬件组件（hardware component）：一个 pluginlib 插件，负责和一种具体硬件说话，实现 read() 和 write()。种类有 system（多关节，例如一台底盘的两个轮子）、actuator（单个执行器）和 sensor（只读）。仿真里是 gz_ros2_control/GazeboSimSystem，真车上是厂商或你自己写的电机驱动插件。用哪个插件、导出哪些接口，写在 URDF 的 <ros2_control> 块里。
  • Hardware component: a pluginlib plugin that talks to one kind of hardware and implements read() and write(). The kinds are system (several joints, such as the two wheels of a base), actuator (one actuator) and sensor (read-only). In simulation it is gz_ros2_control/GazeboSimSystem; on a real robot it is a motor-driver plugin from the vendor or from you. Which plugin to use and which interfaces it exports are written in the URDF’s <ros2_control> block.
  • state 与 command 接口：每个接口就是一个带名字的 double，名字是「关节名/接口类型」，例如 left_wheel_joint/position、left_wheel_joint/velocity。state 接口由硬件在 read() 里填写，任何控制器都可以读，可以共享；command 接口由控制器写、由硬件在 write() 里送出，同一时刻只能被一个控制器占用（claim）。这条独占规则让两个控制器不会同时给一个电机下命令。
  • State and command interfaces: each interface is one named double, named “joint name/interface type”, for example left_wheel_joint/position and left_wheel_joint/velocity. State interfaces are filled in by the hardware in read() and any controller may read them, shared; command interfaces are written by a controller and sent out by the hardware in write(), and only one controller may claim one at a time. This exclusivity rule means two controllers never command one motor at the same time.
  • 控制器：也是 pluginlib 插件，例如 diff_drive_controller/DiffDriveController。它声明自己要哪些 state 和 command 接口，每个周期的 update() 里读前者、写后者。控制器本身是 lifecycle 节点：加载后是 unconfigured，configure 后是 inactive，activate 时才去占用 command 接口（Phase 4 的状态机，原样复用）。
  • Controllers: also pluginlib plugins, such as diff_drive_controller/DiffDriveController. A controller declares which state and command interfaces it needs, and in every period’s update() reads the former and writes the latter. A controller is itself a lifecycle node: unconfigured after loading, inactive after configure, and it claims its command interfaces only on activate (the state machine of Phase 4, reused as is).
  • controller_manager：把以上三者串起来的节点。它的资源管理器（resource manager）加载硬件组件、登记全部接口；它按名字加载控制器，并在每个周期依次调用 read、各控制器的 update、write。对外它是一组服务（加载、配置、切换、卸载控制器），ros2 control … 命令和 spawner 都是这些服务的客户端。真车上它跑在 ros2_control_node 这个可执行文件里；仿真里它由 Gazebo 插件在 Gazebo 进程内创建（概念 3）。
  • controller_manager: the node that ties the three together. Its resource manager loads hardware components and registers all their interfaces; it loads controllers by name and, every period, calls read, each controller’s update, then write. To the outside it is a set of services (load, configure, switch and unload controllers), and the ros2 control … commands and spawner are clients of those services. On a real robot it runs in the ros2_control_node executable; in simulation a Gazebo plugin creates it inside the Gazebo process (concept 3).

2. 实时更新环：为什么固定频率、为什么一个线程、错过截止时间会怎样

2. The real-time update loop: why a fixed rate, why one thread, and what a missed deadline does

controller_manager 的参数 update_rate 决定周期 T = 1 / update_rate，Lab A 用 100 Hz，即 10 ms。每个周期严格按 read → update → write 的顺序跑一遍，然后睡到下一个周期边界。这样设计有三个原因：

The controller_manager parameter update_rate sets the period T = 1 / update_rate; Lab A uses 100 Hz, which is 10 ms. Every period runs strictly read → update → write, then sleeps until the next period boundary. The design has three reasons:

  1. 控制器是离散时间系统。PID 的积分项累加 e·dt，微分项算 (ek − ek−1) / dt；差速控制器用两次读数之间的轮转角度积分出位姿；速度和加速度限幅也按 dt 换算。控制器的增益是按某个采样周期调出来的，周期一抖，等效增益就跟着抖。ros2_control 会把实测的周期传进 update(time, period)，让控制器至少用对 dt，但「被控对象在这段时间里没人管」这件事无法靠算数补回来：反馈来得越晚，相位滞后越大，闭环越接近不稳定。
  2. Controllers are discrete-time systems. A PID’s integral term accumulates e·dt and its derivative term computes (ek − ek−1) / dt; a differential-drive controller integrates the pose from the wheel angle turned between two readings; velocity and acceleration limits are converted with dt too. A controller’s gains are tuned for some sampling period, and when the period jitters, the effective gain jitters with it. ros2_control passes the measured period into update(time, period) so that a controller at least uses the right dt, but arithmetic cannot make up for “nobody controlled the plant during that gap”: the later the feedback, the more phase lag, and the closer the closed loop comes to instability.
  3. 一份一致的快照。read 一次性把所有关节的状态拷进 state 接口，本周期所有控制器都基于同一时刻的数据计算，write 再一次性送出。接口只是普通内存里的 double，只有这一个线程碰它们，所以不需要加锁。一旦让第二个线程也来读写，就得加锁，而锁会带来优先级反转：高优先级的控制线程等一个被抢占的低优先级线程放锁。
  4. One consistent snapshot. read copies the state of every joint into the state interfaces in one go, every controller in the period computes from data of the same instant, and write sends everything out in one go. The interfaces are plain doubles in ordinary memory and only this one thread touches them, so no locks are needed. Let a second thread read or write them and you need a lock, and a lock brings priority inversion: the high-priority control thread waits for a preempted low-priority thread to release it.
  5. 热路径里不做不确定的事。话题订阅、服务、参数这些 ROS 通信都在执行器的其他线程里跑。新的 cmd_vel 由订阅回调放进一个实时安全的缓冲区（realtime_tools 提供的 realtime buffer 一类结构，具体类名随版本变化，请查文档），update() 只取最新的一份；发布 /odom 也用不阻塞的实时发布器，抢不到就跳过这一次。控制环里不分配内存、不打日志、不等锁，这正是 Phase 2 概念 7 的规则。
  6. Nothing unpredictable on the hot path. ROS communication (topic subscriptions, services, parameters) runs on other executor threads. A new cmd_vel is put by the subscription callback into a real-time-safe buffer (a realtime buffer of the kind realtime_tools provides; the exact class name changes between versions, check the docs), and update() only takes the latest one; publishing /odom also uses a non-blocking real-time publisher that skips a cycle if it cannot get its lock. The control loop does not allocate memory, log or wait on locks, which are exactly the rules of Phase 2 concept 7.

真车上的线程。按 controller_manager 的 Jazzy 文档和 ros2_control_node 的源码：主循环跑在一个专门的线程里，不管内核是不是 PREEMPT_RT，它都会尝试把自己设成 SCHED_FIFO 优先级 50（参数 thread_priority），失败时打印一条警告继续跑；lock_memory 在实时内核上默认为真，否则为假；cpu_affinity 可以把它钉在某个核上。实验容器的 compose 给了 CAP_SYS_NICE 和 rtprio 99，所以 FIFO 能设上，但没有放宽 memlock，也没有 PREEMPT_RT（见 Phase 2）。

The thread on a real robot. Per the Jazzy controller_manager docs and the ros2_control_node source: the main loop runs on a dedicated thread that, whether or not the kernel is PREEMPT_RT, tries to put itself into SCHED_FIFO at priority 50 (parameter thread_priority), and on failure logs a warning and carries on; lock_memory defaults to true on a real-time kernel and false otherwise; cpu_affinity can pin it to a core. The lab container’s compose file grants CAP_SYS_NICE and rtprio 99, so FIFO can be set, but it does not raise memlock and there is no PREEMPT_RT (see Phase 2).

错过截止时间会怎样。假设 100 Hz 的环里有一个周期因为缺页或被别的任务抢占做了 25 ms。按 2026-10-31 的 jazzy 分支源码，overruns.manage 默认为真时，下一个截止时间已经过去，循环打印 Overrun detected! 警告、跳过错过的周期，不会连跑几次去「补」；关掉它，循环会立刻连跑追赶。无论哪种，对轮子来说这 25 ms 里硬件一直执行上一条命令：如果这时本该刹车，以 4 rad/s 转的轮子会多转约 0.1 rad，对一台 5 cm 半径的小车是 5 mm，无伤大雅；对一个靠反馈保持平衡的机器人，或者一个在接触中用力控的机械臂，这就是一次没有反馈的 25 ms。很多电机驱动器还有自己的看门狗，超过一段时间收不到命令就断电停转，轮子会突然一顿（是否有、多长，取决于驱动器）。仿真时间下 overrun 处理被关闭，所以在 Gazebo 里你看不到这一切。

What a missed deadline does. Suppose one period of a 100 Hz loop takes 25 ms because of a page fault or preemption by another task. Per the jazzy branch source on 2026-10-31, with overruns.manage at its default of true, the next deadline has already passed, so the loop logs an Overrun detected! warning and skips the missed periods instead of running several in a row to “catch up”; with it turned off, the loop runs back to back at once to catch up. Either way, for the wheel the hardware keeps executing the previous command for those 25 ms: if it should have braked just then, a wheel turning at 4 rad/s turns about 0.1 rad too far, which is 5 mm for a small robot with 5 cm wheels and harmless; for a robot that keeps its balance through feedback, or an arm in contact under force control, it is 25 ms with no feedback at all. Many motor drivers also have their own watchdog that cuts power when no command arrives for a while, and the wheel stops with a jerk (whether there is one and how long it waits depends on the driver). Overrun handling is disabled under simulation time, so in Gazebo you see none of this.

和 Kernel Engineering 的连接。这个控制环是内核里中断驱动的驱动程序路径在用户态的孪生（Kernel Phase 5 · 设备驱动）。在那里，设备一来中断，上半部只做最少的事：读寄存器、确认中断、把数据交给下半部或线程化中断，慢的工作挪出热路径。这里，一个定时器把一个高优先级线程叫醒，它只做 read、update、write 这一小段有界的工作，ROS 通信交给执行器线程，中间靠无锁缓冲区交接。两边的规则相同：热路径有上界、不睡眠、不分配。区别在于谁来叫醒：中断由硬件触发，控制环由内核的定时器和调度器触发，所以它的抖动就是 Phase 2 讲的调度故事：定时器的精度、FIFO 任务被唤醒后等多久才上 CPU、内核里不可抢占的区段。
The connection to Kernel Engineering. This control loop is the user-space twin of the kernel’s interrupt-driven driver path (Kernel Phase 5 · Device Drivers). There, when a device raises an interrupt, the top half does the least it can: read a register, acknowledge the interrupt, hand the data to a bottom half or a threaded interrupt, and move the slow work off the hot path. Here, a timer wakes one high-priority thread that does only the short, bounded work of read, update and write, while ROS communication goes to executor threads, with a lock-free buffer as the hand-off. The rules on both sides are the same: a bounded hot path, no sleeping, no allocation. The difference is what does the waking: an interrupt is triggered by hardware, the control loop by the kernel’s timer and scheduler, so its jitter is the scheduling story of Phase 2: timer precision, how long a woken FIFO task waits for a CPU, and the non-preemptible sections inside the kernel.

3. diff_drive_controller、joint_trajectory_controller 与 gz_ros2_control

3. diff_drive_controller, joint_trajectory_controller and gz_ros2_control

  • diff_drive_controller：订阅 ~/cmd_vel，在 Jazzy 上类型是 geometry_msgs/msg/TwistStamped（控制器文档原文），只取线速度 x 分量 v 和角速度 z 分量 ω。用轮距 L（参数 wheel_separation）和轮半径 r（wheel_radius）做逆运动学：ω左 = (v − ω·L/2) / r，ω右 = (v + ω·L/2) / r，写进 left_wheel_names、right_wheel_names 列出的关节的 velocity command 接口。反过来用两轮的 position（或 velocity）state 积分出位姿，发布 ~/odom，enable_odom_tf 为真时还发布 odom → base_link 的 tf。cmd_vel_timeout（默认 0.5 s）内收不到新命令就停车。
  • diff_drive_controller: subscribes to ~/cmd_vel, whose type on Jazzy is geometry_msgs/msg/TwistStamped (as the controller docs say), and takes only the linear x component v and the angular z component ω. With the wheel separation L (parameter wheel_separation) and wheel radius r (wheel_radius) it does the inverse kinematics ωleft = (v − ω·L/2) / r and ωright = (v + ω·L/2) / r, and writes them to the velocity command interfaces of the joints listed in left_wheel_names and right_wheel_names. In the other direction it integrates the pose from the two wheels’ position (or velocity) state, publishes ~/odom, and, when enable_odom_tf is true, the odom → base_link tf. If no new command arrives within cmd_vel_timeout (default 0.5 s), it stops.
  • joint_state_broadcaster：不占用任何 command 接口，只读全部 state 接口，发布 /joint_states，robot_state_publisher 再据此算出轮子的 tf。Phase 5 里这件事由 Gazebo 的 JointStatePublisher 系统做，现在换成了控制器。
  • joint_state_broadcaster: claims no command interface, reads every state interface and publishes /joint_states, from which robot_state_publisher computes the wheels’ tf. In Phase 5 Gazebo’s JointStatePublisher system did this job; now a controller does.
  • joint_trajectory_controller：机械臂的标准控制器。它接受一条带时间戳的关节轨迹（话题或 FollowJointTrajectory 动作，MoveIt 2 就是用后者），每个周期在相邻轨迹点之间插值出当前时刻的期望位置、速度，再写进 position、velocity 或 effort command 接口。插值方式和容差参数请查文档。本课程的底盘用不到它，但它把「固定周期」说得最清楚：轨迹是连续时间的，控制器只在每个周期边界采样一次。
  • joint_trajectory_controller: the standard controller for arms. It accepts a time-stamped joint trajectory (by topic or through the FollowJointTrajectory action, which is what MoveIt 2 uses), interpolates the desired position and velocity at the current instant between neighbouring trajectory points every period, and writes them to position, velocity or effort command interfaces. Check the docs for the interpolation methods and tolerance parameters. This course’s base does not use it, but it shows “fixed period” most plainly: the trajectory is in continuous time, and the controller samples it once at each period boundary.
  • gz_ros2_control：一个 Gazebo 系统插件（gz_ros2_control::GazeboSimROS2ControlPlugin），在 Gazebo 进程里创建一个 controller_manager，并把 URDF <ros2_control> 块里列出的关节接成硬件组件 GazeboSimSystem。按它 jazzy 分支的源码，它没有单独的实时线程：Gazebo 每个仿真步的 PostUpdate 里，仿真时间每过一个控制周期就调用一次 read 和 update，PreUpdate 里调用 write；它还强制 use_sim_time:=true。于是控制环按仿真时间严格等周期，即使墙上时间里 Gazebo 卡了一下，仿真也只是变慢，控制器察觉不到。这让仿真结果可重复，也意味着仿真永远测不出概念 2 的那些实时问题。
  • gz_ros2_control: a Gazebo system plugin (gz_ros2_control::GazeboSimROS2ControlPlugin) that creates a controller_manager inside the Gazebo process and connects the joints listed in the URDF’s <ros2_control> block as the hardware component GazeboSimSystem. Per the source on its jazzy branch it has no separate real-time thread: in the PostUpdate of each Gazebo simulation step, every time a control period of simulation time has passed, it calls read and update, and in PreUpdate it calls write; it also forces use_sim_time:=true. So the control loop is exactly periodic in simulation time: even if Gazebo stalls in wall time, the simulation just runs slower and the controllers cannot tell. That makes simulation results repeatable, and it also means simulation can never reveal the real-time problems of concept 2.

This is what switching to ros2_control buys: Phase 5’s DiffDrive belongs to Gazebo and has to be replaced by different code on a real robot; now diff_drive_controller and its YAML parameters are identical in simulation and on the real robot, and only the <hardware><plugin> line changes. The price is one more layer to configure, and on Jazzy the type difference between TwistStamped and the unstamped Twist (you meet it in steps 6 and 7 of Lab A and step 6 of Lab B).

4. Nav2 的结构：服务器、插件与生命周期

4. The structure of Nav2: servers, plugins and lifecycle

Nav2 不是一个节点，而是一组各管一件事的服务器，彼此主要通过 ROS 2 动作（Phase 1）说话。每个服务器都是一个 lifecycle 节点，算法部分是可替换的 pluginlib 插件：

Nav2 is not one node but a set of servers that each do one job and talk to each other mainly through ROS 2 actions (Phase 1). Every server is a lifecycle node, and the algorithmic part of each is a replaceable pluginlib plugin:

  • bt_navigator：对外提供 navigate_to_pose（类型 nav2_msgs/action/NavigateToPose）和 navigate_through_poses 动作，收到目标后加载一棵行为树并执行它（概念 5）。它也订阅 /goal_pose，RViz2 的 2D Goal Pose 工具发到这里的位姿会被当成一个 NavigateToPose 目标。
  • bt_navigator: offers the navigate_to_pose action (type nav2_msgs/action/NavigateToPose) and navigate_through_poses, and on a goal loads and runs a behavior tree (concept 5). It also subscribes to /goal_pose, so a pose sent there by RViz2’s 2D Goal Pose tool is treated as a NavigateToPose goal.
  • planner_server：compute_path_to_pose 动作，在 global costmap 上算一条从当前位置到目标的路径。插件有 NavFn（2026-10-31 jazzy 分支默认参数里的选择）和 Smac 系列等。
  • planner_server: the compute_path_to_pose action, which computes a path from the current position to the goal on the global costmap. Plugins include NavFn (the choice in the default parameters on the jazzy branch on 2026-10-31) and the Smac family.
  • controller_server：follow_path 动作，以 controller_frequency（默认参数 20 Hz）在 local costmap 上算出每一步的速度命令，发布到 cmd_vel。插件有 DWB、MPPI、Regulated Pure Pursuit（RPP）；上述默认参数里是 MPPI，你装到的版本默认是哪个，请查文档和 nav2_params.yaml。
  • controller_server: the follow_path action, which at controller_frequency (20 Hz in the default parameters) computes each step’s velocity command on the local costmap and publishes it on cmd_vel. Plugins include DWB, MPPI and Regulated Pure Pursuit (RPP); those default parameters choose MPPI, and which one is the default in your installed release is for the docs and nav2_params.yaml to say.
  • smoother_server 让路径更平滑；behavior_server 提供 Spin、BackUp、DriveOnHeading、Wait 等脱困动作；map_server 从 YAML 加 PGM 文件发布 /map；amcl 做定位（概念 7）；velocity_smoother 和 collision_monitor 依次过滤速度命令。按 navigation_launch.py 的 jazzy 版本，controller_server 的输出被重映射为 cmd_vel_nav，平滑后成为 cmd_vel_smoothed，过了碰撞监视才是最终的 cmd_vel。
  • smoother_server smooths paths; behavior_server provides recovery actions such as Spin, BackUp, DriveOnHeading and Wait; map_server publishes /map from a YAML plus PGM file; amcl localises (concept 7); velocity_smoother and collision_monitor filter velocity commands in turn. Per the jazzy version of navigation_launch.py, controller_server’s output is remapped to cmd_vel_nav, becomes cmd_vel_smoothed after smoothing, and only after the collision monitor is it the final cmd_vel.
  • lifecycle_manager：参数 node_names 列出它管的服务器，autostart 为真时启动后自动先把全部服务器 configure，再全部 activate，这正是 Phase 4 概念 4 说的「两阶段启动」。它还和每个服务器建立 bond 心跳，一个服务器崩溃，管理者能察觉并把整个栈带下来（重启策略请查文档）。nav2_bringup 里定位和导航各有一个管理者。
  • lifecycle_manager: its node_names parameter lists the servers it manages, and with autostart true it first configures all of them after start-up and then activates all of them, which is exactly the “two-phase start-up” of Phase 4 concept 4. It also keeps a bond heartbeat with each server, so when a server crashes the manager notices and brings the whole stack down (check the docs for the restart policy). nav2_bringup has one manager for localisation and one for navigation.
Nav2 发布 Twist 还是 TwistStamped，由每个相关节点的参数 enable_stamped_cmd_vel 决定。按 nav2_util/twist_publisher.hpp 的 jazzy 源码，它在 Jazzy 上默认为假，即发布不带时间戳的 Twist；Nav2 的迁移指南说下一个发行版把默认改成了 TwistStamped。而 Jazzy 的 diff_drive_controller 只收 TwistStamped。两者直接相连时什么也不会动，也不报错（Phase 5 的测验 3 是同一个现象），所以 Lab B 要把相关节点的这个参数都设成真。

5. 行为树：从一个目标到规划、跟随与恢复

5. Behavior trees: from one goal to planning, following and recovery

行为树（behavior tree，Nav2 用 BehaviorTree.CPP 4.x）是一棵节点树，由 bt_navigator 以固定频率从根开始 tick。每个节点被 tick 后返回三种结果之一：SUCCESS、FAILURE，或者 RUNNING（还没做完，下次 tick 再问）。叶子是动作节点，内部组合规则在控制节点里：

A behavior tree (Nav2 uses BehaviorTree.CPP 4.x) is a tree of nodes that bt_navigator ticks from the root at a fixed rate. Each node, when ticked, returns one of three results: SUCCESS, FAILURE, or RUNNING (not done yet; ask again next tick). The leaves are action nodes, and the rules for combining them live in control nodes:

  • 动作节点包着动作客户端。ComputePathToPose 第一次被 tick 时向 planner_server 发一个动作目标并返回 RUNNING，之后每次 tick 查一下结果，规划完成时返回 SUCCESS，并把路径写进黑板（blackboard，树里共享的键值表）上的 {path}。FollowPath 从黑板读 {path}，调用 controller_server。Spin、BackUp、Wait 调用 behavior_server，ClearEntireCostmap 调用 costmap 的清除服务。行为树本身不做规划，也不算速度，它只决定什么时候调用谁。
  • Action nodes wrap action clients. When ComputePathToPose is ticked for the first time it sends an action goal to planner_server and returns RUNNING; each later tick checks for the result, and when planning finishes it returns SUCCESS and writes the path to {path} on the blackboard (a key-value table shared across the tree). FollowPath reads {path} from the blackboard and calls controller_server. Spin, BackUp and Wait call behavior_server, and ClearEntireCostmap calls a costmap’s clearing service. The behavior tree itself neither plans nor computes velocities; it only decides when to call whom.
  • 控制节点决定组合方式。Sequence 按顺序执行孩子，一个失败就整体失败；Fallback 依次尝试，一个成功就整体成功；PipelineSequence 在后面的孩子还在 RUNNING 时继续重新 tick 前面已经成功的孩子；RecoveryNode 有两个孩子，第一个失败时执行第二个（恢复动作），再重试第一个，最多 number_of_retries 次；RoundRobin 每次被 tick 时轮到下一个孩子；装饰节点 RateController 限制它的孩子被 tick 的频率。
  • Control nodes decide how to combine. Sequence runs its children in order and fails as soon as one fails; Fallback tries them in turn and succeeds as soon as one succeeds; PipelineSequence keeps re-ticking the earlier, already successful children while a later one is still RUNNING; RecoveryNode has two children, and when the first fails it runs the second (the recovery) and retries the first, up to number_of_retries times; RoundRobin moves to the next child each time it is ticked; and the decorator RateController limits how often its child is ticked.

默认树怎样运转（navigate_to_pose_w_replanning_and_recovery.xml，按 2026-10-31 的 jazzy 分支；你装到的版本细节可能不同，以 nav2_bt_navigator 包 share 目录下 behavior_trees/ 里的文件为准）：

How the default tree runs (navigate_to_pose_w_replanning_and_recovery.xml, per the jazzy branch on 2026-10-31; your installed release may differ in details, and the file under behavior_trees/ in the nav2_bt_navigator package’s share directory wins):

  1. 根是 RecoveryNode（number_of_retries="6"）。它的第一个孩子是一个 PipelineSequence，里面依次是：放在 RateController hz="1.0" 下的 ComputePathToPose，和 FollowPath。
  2. The root is a RecoveryNode (number_of_retries="6"). Its first child is a PipelineSequence holding, in order, ComputePathToPose under a RateController hz="1.0", and FollowPath.
  3. 第一次 tick：先规划，成功后开始跟随。之后 FollowPath 一直 RUNNING，PipelineSequence 每次 tick 都会回头再 tick 规划那一支，而 RateController 只让它每秒真正执行一次。于是机器人边走边以 1 Hz 重新规划，新路径写进黑板，正在运行的 FollowPath 换用它。
  4. On the first tick it plans, and once that succeeds it starts following. From then on FollowPath stays RUNNING, PipelineSequence goes back and re-ticks the planning branch on every tick, and RateController lets it actually run only once per second. So the robot replans at 1 Hz while driving, the new path goes onto the blackboard, and the running FollowPath switches to it.
  5. 两个动作各自先有一次局部恢复：规划失败就清空 global costmap 再试一次，跟随失败就清空 local costmap 再试一次（新版本还会先判断这个错误码值不值得恢复）。
  6. Each of the two actions first gets one local recovery: if planning fails, clear the global costmap and try once more; if following fails, clear the local costmap and try once more (newer versions first check whether the error code is worth recovering from).
  7. 局部恢复也失败，整个 PipelineSequence 失败，根上的 RecoveryNode 转去执行恢复分支：RoundRobin 依次轮到「清空两张 costmap」「原地转 1.57 rad」「等 5 秒」「以 0.15 m/s 后退 0.30 m」中的一个，然后从头重试导航。目标在恢复期间被更新时（GoalUpdated），立刻放弃恢复回去导航。
  8. If the local recovery fails too, the whole PipelineSequence fails and the root RecoveryNode runs the recovery branch: RoundRobin takes one of “clear both costmaps”, “spin 1.57 rad in place”, “wait 5 s” and “back up 0.30 m at 0.15 m/s”, in turn, and then navigation is retried from the top. If the goal is updated during recovery (GoalUpdated), recovery is abandoned at once and navigation resumes.
  9. 重试 6 次仍失败，根返回 FAILURE，bt_navigator 以 ABORTED 结束这个 NavigateToPose 目标。反馈里的 number_of_recoveries 就是数这些恢复的。
  10. If it still fails after 6 retries, the root returns FAILURE and bt_navigator ends the NavigateToPose goal as ABORTED. The number_of_recoveries in the feedback counts these recoveries.
为什么用行为树而不是一台状态机：「边走边每秒重规划」「失败先做便宜的恢复、再做昂贵的」「目标一更新就打断恢复」这些组合，用状态机写要为每种组合加状态和转换；在行为树里只是换一种控制节点或加一个装饰节点，而且整个策略是一份 XML，换策略不用重新编译。代价是行为不再写在一处的 C++ 里，排查时要对着 XML 和每个节点的返回值读。
Why a behavior tree rather than a state machine: combinations such as “replan every second while driving”, “try cheap recoveries before expensive ones” and “interrupt recovery as soon as the goal changes” would each need extra states and transitions in a state machine; in a behavior tree they are a different control node or one more decorator, and the whole strategy is one XML file, so changing strategy needs no recompiling. The price is that behaviour no longer lives in one place in C++, and debugging means reading the XML against each node’s return values.

6. costmap 与它的层：为什么要膨胀

6. Costmaps and their layers: why inflation exists

costmap 是一张二维栅格，默认参数里每格 0.05 m，每格存一个 0–255 的代价。几个特殊值写在 nav2_costmap_2d/cost_values.hpp：0 是自由空间，253 是「内切」（机器人中心到这里就必然碰撞），254 是致命障碍，255 是未知。costmap 由若干层（layer 插件）叠出来：每层维护自己的栅格，更新时每层先报告这次改动了哪个范围，再按列出的顺序把自己的值合进总图。

A costmap is a 2D grid, 0.05 m per cell in the default parameters, each cell holding a cost from 0 to 255. The special values are in nav2_costmap_2d/cost_values.hpp: 0 is free space, 253 is “inscribed” (with the robot’s centre here, a collision is certain), 254 is a lethal obstacle and 255 is unknown. A costmap is stacked from several layers (layer plugins): each layer keeps its own grid, and on each update every layer first reports which area it changed, then merges its values into the master grid in the order listed.

  • static 层：把 /map（map_server 或 slam_toolbox 发布的占据栅格）里被占据的格子标为致命，未知格子标为未知。它只反映建图那一刻的世界。
  • Static layer: marks the occupied cells of /map (the occupancy grid published by map_server or slam_toolbox) as lethal and unknown cells as unknown. It reflects the world only as it was when the map was built.
  • obstacle 层：订阅 /scan 这类传感器。每束激光的终点所在的格子标为障碍（marking），从传感器到终点之间穿过的格子清为自由（clearing，靠光线追踪）。于是地图上没有的箱子会出现，走开的人会消失。voxel 层是它的三维版本，按高度分层，适合深度相机；默认参数里 local costmap 用的是它。
  • Obstacle layer: subscribes to sensors such as /scan. The cell at each beam’s end point is marked as an obstacle (marking), and the cells the beam passed through between sensor and end point are cleared to free (clearing, by ray tracing). So a box that is not on the map appears, and a person who walks away disappears. The voxel layer is its 3D version, split by height, suited to depth cameras; the default parameters use it for the local costmap.
  • inflation 层：把每个致命格子向外「膨胀」，放在层列表的最后。
  • Inflation layer: “inflates” every lethal cell outwards, and comes last in the list of layers.

膨胀为什么必须存在。规划器和大部分控制器把机器人当成一个点（它的中心）在栅格上搜索，这样快得多。但机器人有半径。把每个障碍向外扩出机器人的内切半径，「点不进入这些格子」就等价于「整台机器人不碰障碍」：这是把机器人的形状搬进地图，即运动规划里的构型空间。只做到这一步，最优路径会贴着墙走，任何定位误差都会擦墙。所以膨胀在内切半径之外继续给一段递减的代价，让路径愿意离墙远一点。按 inflation_layer.hpp 的 jazzy 源码，距最近障碍 d 米处的代价是：

Why inflation has to exist. The planner and most controllers search the grid treating the robot as one point (its centre), which is much faster. But the robot has a radius. Expand every obstacle outwards by the robot’s inscribed radius, and “the point never enters these cells” becomes equivalent to “the whole robot never touches an obstacle”: the robot’s shape has been moved into the map, which is the configuration space of motion planning. Stopping there, the optimal path would hug the walls and any localisation error would scrape them. So beyond the inscribed radius inflation keeps adding a decreasing cost, so that paths are willing to keep some distance from walls. Per the jazzy source of inflation_layer.hpp, the cost at d metres from the nearest obstacle is:

  • d = 0：254（致命）；0 < d ≤ 内切半径：253（内切）；
  • d = 0: 254 (lethal); 0 < d ≤ inscribed radius: 253 (inscribed);
  • 再往外：252 × exp(−k × (d − 内切半径))，k 是 cost_scaling_factor（默认参数 3.0），直到 inflation_radius（默认参数 0.70 m）为止。k 越大，代价随距离下降得越快，路径越敢贴近障碍；inflation_radius 要大于机器人的外接半径，否则窄门前后的代价会突然断开。
  • further out: 252 × exp(−k × (d − inscribed radius)), where k is cost_scaling_factor (3.0 in the default parameters), up to inflation_radius (0.70 m in the default parameters). The larger k, the faster cost falls with distance and the closer paths dare to go to obstacles; inflation_radius should exceed the robot’s circumscribed radius, otherwise the cost in front of and behind a narrow door breaks off abruptly.

两张图、两个坐标系。global costmap 在 map 坐标系里，覆盖整张地图（默认参数：static、obstacle、inflation 三层，1 Hz 更新），给规划器用。local costmap 是一个跟着机器人滚动的小窗口（rolling_window: true），在 odom 坐标系里（默认参数：voxel、inflation，5 Hz），给控制器用。控制器放在 odom 里，是因为 odom 连续平滑；AMCL 每次修正 map → odom 时 map 坐标系里的位姿会跳一下，控制器不该被这种跳变扰动（REP 105 对 odom 的定义正是「连续但会漂移」）。

Two maps, two frames. The global costmap is in the map frame, covers the whole map (default parameters: static, obstacle and inflation layers, updated at 1 Hz) and serves the planner. The local costmap is a small window that rolls along with the robot (rolling_window: true), in the odom frame (default parameters: voxel and inflation, 5 Hz), and serves the controller. The controller works in odom because odom is continuous and smooth; each time AMCL corrects map → odom, the pose in the map frame jumps, and the controller should not be disturbed by such jumps (REP 105 defines odom as exactly “continuous but drifting”).

7. 定位与建图：AMCL 估计什么，slam_toolbox 估计什么

7. Localisation and mapping: what AMCL estimates, what slam_toolbox estimates

两者都发布 map → odom，都吃激光和里程计，但回答的问题不同：

Both publish map → odom and both consume laser scans and odometry, but they answer different questions:

  • AMCL（自适应蒙特卡洛定位）：地图已知、固定，只估计机器人此刻的位姿。它维护一群粒子，每个粒子是一个位姿假设。机器人一动，每个粒子按里程计的增量加上噪声移动（差速机器人用 nav2_amcl::DifferentialMotionModel）；一帧激光到来，按「如果我在这里，这帧激光和地图有多吻合」给每个粒子打分；再按分数重新抽样，吻合的留下、不吻合的淘汰。「自适应」指粒子数随不确定度增减。粒子群可以同时保持几个分开的假设，所以它能处理「两条一模一样的走廊」。它需要一个初始位姿（RViz2 的 2D Pose Estimate，或参数），算出 map → base_link 后减去 odom → base_link，发布 map → odom，让 tf 树保持 REP 105 的形状。
  • AMCL (Adaptive Monte Carlo Localisation): the map is known and fixed, and it estimates only the robot’s current pose. It keeps a set of particles, each a pose hypothesis. When the robot moves, every particle moves by the odometry increment plus noise (a differential robot uses nav2_amcl::DifferentialMotionModel); when a scan arrives, every particle is scored by “if I were here, how well would this scan match the map”; then particles are resampled by score, keeping those that match and dropping those that do not. “Adaptive” means the number of particles grows and shrinks with uncertainty. The cloud can hold several separate hypotheses at once, so it copes with “two identical corridors”. It needs an initial pose (RViz2’s 2D Pose Estimate, or a parameter), computes map → base_link, subtracts odom → base_link, and publishes map → odom so the tf tree keeps REP 105’s shape.
  • slam_toolbox：地图未知，同时估计地图和整条轨迹。它是基于图的 SLAM：每走过一段距离或转过一个角度（minimum_travel_distance、minimum_travel_heading），就把当前位姿连同这帧激光加成图里的一个节点；新节点和前面节点的扫描做匹配，得到一条相对位姿约束（边）。回到走过的地方时，扫描和很早以前的节点也匹配上，这就是回环（loop closure），加进一条长边；然后优化器（默认配置里是 Ceres）重新求解所有节点的位姿，让所有约束尽量同时满足，地图由全部扫描按优化后的位姿重新画出。所以它的地图会在回环那一刻「啪」地对齐，过去的位姿也被改写。它发布 /map 和 map → odom；配置里的 mode 还可以设成 localization，只在已有的图上定位（请查文档）。
  • slam_toolbox: the map is unknown, and it estimates the map and the whole trajectory together. It is graph-based SLAM: each time the robot has travelled some distance or turned some angle (minimum_travel_distance, minimum_travel_heading), the current pose together with its scan is added as a node in a graph; the new node’s scan is matched against earlier nodes, giving a relative pose constraint (an edge). When the robot comes back to a place it has been, the scan also matches a node from long ago: that is a loop closure, adding a long edge; then the optimiser (Ceres in the default configuration) re-solves every node’s pose so that all constraints hold as well as possible at once, and the map is redrawn from all scans at the optimised poses. So its map “snaps” into alignment at the moment of a loop closure, and past poses are rewritten. It publishes /map and map → odom; the mode in its configuration can also be set to localization, localising on an existing graph only (check the docs).
一个直接的后果：不要同时运行两者。两个节点都发布 map → odom，tf 树里同一条边有两个作者，查到的变换会在两份估计之间跳。Lab B 先用 slam_toolbox 建图、保存，停掉它，再让 map_server 加 AMCL 接手。
A direct consequence: never run both at once. Both nodes publish map → odom, so one edge of the tf tree has two authors and lookups jump between two estimates. Lab B first builds and saves a map with slam_toolbox, stops it, and only then lets map_server and AMCL take over.

    # nav_goal.py: send one NavigateToPose goal and follow its feedback
import math
import sys

import rclpy
from action_msgs.msg import GoalStatus
from nav2_msgs.action import NavigateToPose
from rclpy.action import ActionClient
from rclpy.node import Node
from rclpy.utilities import remove_ros_args


class NavGoal(Node):
    def __init__(self):
        super().__init__('nav_goal')
        self.client = ActionClient(self, NavigateToPose, 'navigate_to_pose')

    def run(self, x, y, yaw):
        goal = NavigateToPose.Goal()
        goal.pose.header.frame_id = 'map'
        goal.pose.header.stamp = self.get_clock().now().to_msg()
        goal.pose.pose.position.x = x
        goal.pose.pose.position.y = y
        goal.pose.pose.orientation.z = math.sin(yaw / 2.0)   # 绕 z 轴的四元数
        goal.pose.pose.orientation.w = math.cos(yaw / 2.0)

        self.get_logger().info('waiting for navigate_to_pose ...')
        self.client.wait_for_server()
        sent = self.client.send_goal_async(goal, feedback_callback=self.on_feedback)
        rclpy.spin_until_future_complete(self, sent)
        handle = sent.result()
        if not handle.accepted:
            self.get_logger().error('goal rejected')
            return
        done = handle.get_result_async()
        rclpy.spin_until_future_complete(self, done)
        res = done.result()
        ok = res.status == GoalStatus.STATUS_SUCCEEDED
        self.get_logger().info(f'status {res.status} ({"SUCCEEDED" if ok else "not succeeded"}): {res.result}')

    def on_feedback(self, msg):
        fb = msg.feedback
        self.get_logger().info(
            f'{fb.distance_remaining:.2f} m left, {fb.number_of_recoveries} recoveries',
            throttle_duration_sec=1.0)


def main():
    rclpy.init(args=sys.argv)
    x, y, yaw = (float(v) for v in remove_ros_args(sys.argv)[1:4])
    node = NavGoal()
    node.run(x, y, yaw)
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

自测

Self-check

1. 真车上 controller_manager 以 100 Hz 运行。某个周期因为一次缺页做了 25 ms。在 Jazzy 的默认设置下，接下来会发生什么？

1. On a real robot the controller_manager runs at 100 Hz. One period takes 25 ms because of a page fault. With Jazzy’s default settings, what happens next?

overruns.manage 默认为真时，循环发现下一个截止时间已过，就把截止时间向后推过错过的周期，并打印警告。a 错：连跑追赶只在关掉 overrun 处理时出现，而且补跑的几次也无法撤回那 25 ms 里没有反馈的事实。c 错：控制器被停用的条件是 update 返回错误，不是运行时间超时。With overruns.manage at its default of true, the loop sees that the next deadline has passed, moves the deadline past the missed periods, and logs a warning. a is wrong: back-to-back catch-up only happens with overrun handling turned off, and catch-up runs cannot undo the 25 ms without feedback anyway. c is wrong: a controller is deactivated when its update returns an error, not when a period runs long.

2. 把 inflation 层从 global costmap 里去掉，只留 static 和 obstacle 层，规划器把机器人当作一个点。最可能出现什么？

2. You remove the inflation layer from the global costmap, keeping only the static and obstacle layers, and the planner treats the robot as a point. What is most likely to happen?

膨胀把机器人的半径搬进地图（构型空间），并在外面加一段递减的代价让路径离墙。去掉它，一个点能过的缝在规划器看来都能过。a 错：膨胀不处理传感器噪声，标记和清除是 obstacle 层的事。b 错：自由格子多少对搜索时间有影响，但这不是主要后果，主要后果是路径不安全。Inflation moves the robot’s radius into the map (configuration space) and adds a decreasing cost beyond it to keep paths away from walls. Without it, any gap a point can pass looks passable to the planner. a is wrong: inflation does not deal with sensor noise; marking and clearing belong to the obstacle layer. b is wrong: the number of free cells does affect search time, but that is not the main consequence; the main one is unsafe paths.

3. 关于 AMCL 和 slam_toolbox，哪一句是对的？

3. Which statement about AMCL and slam_toolbox is right?

AMCL 是在已知地图上的粒子滤波定位，状态只有位姿；slam_toolbox 是基于图的 SLAM，状态是全部节点的位姿，地图从它们画出。b 错：AMCL 根本不建图。c 错：两者都发布 map → odom，同时运行时同一条 tf 边有两个作者，查到的变换会来回跳。AMCL is particle-filter localisation on a known map, and its state is only the pose; slam_toolbox is graph-based SLAM whose state is every node’s pose, with the map drawn from them. b is wrong: AMCL builds no map at all. c is wrong: both publish map → odom, so running both gives one tf edge two authors and lookups jump back and forth.

4. 机器人按默认行为树导航时，一个箱子突然挡住了路，FollowPath 失败。接下来最先发生的是什么？

4. While the robot navigates with the default behavior tree, a box suddenly blocks the way and FollowPath fails. What happens first?

默认树有两级恢复：每个动作外面一个只重试一次、先清对应 costmap 的 RecoveryNode，最外层一个最多重试 6 次、用 RoundRobin 轮流选恢复动作的 RecoveryNode。a 错：只有 6 次重试都失败才 ABORTED。c 错：控制器只算速度，什么时候脱困、怎样脱困由行为树决定，旋转由 behavior_server 执行。The default tree has two levels of recovery: around each action, a RecoveryNode that retries once after clearing the matching costmap; at the top, a RecoveryNode with up to 6 retries that picks recoveries in turn through RoundRobin. a is wrong: the goal is ABORTED only after all 6 retries fail. c is wrong: the controller only computes velocities; when and how to recover is the behavior tree’s decision, and spinning is executed by behavior_server.
