Phase 1 里你写的每个回调都「自己跑了起来」，这一阶段拆开是谁在跑它们：执行器（executor）在一个或几个 Linux 线程里循环，睡在 wait set 上，醒来后按固定规则一个个调用就绪的回调。弄清这个循环，就能解释三件常见的怪事：为什么在回调里同步调用服务会永远卡住，为什么一个慢回调会让 100 Hz 的定时器时快时慢，以及为什么换成多线程执行器有时仍然没用。最后把回调线程当成内核里的普通任务来看：用 chrt -f 80 把它放进 SCHED_FIFO，对比抖动，并说清在容器里这一招能修好什么、修不好什么。

Every callback you wrote in Phase 1 “just ran”; this phase opens up who runs them. An executor loops in one or several Linux threads, sleeps on a wait set, and on waking calls the ready callbacks one by one according to fixed rules. Once that loop is clear, three common puzzles explain themselves: why calling a service synchronously inside a callback hangs forever, why one slow callback makes a 100 Hz timer speed up and slow down, and why switching to a multithreaded executor sometimes still does not help. Finally the callback thread is treated as an ordinary kernel task: you put it into SCHED_FIFO with chrt -f 80, compare the jitter, and pin down what that fixes inside a container and what it cannot.

核心概念

Core concepts

1. spin、执行器循环与 wait set

1. spin, the executor loop and the wait set

节点自己不会调用任何回调。你创建的 subscription、timer、service、client 只是登记在节点上的实体（entity）；真正调用回调的是执行器。rclcpp::spin(node) 就是：建一个 rclcpp::executors::SingleThreadedExecutor，executor.add_node(node)，再在当前线程里 executor.spin()——一个直到关闭（例如 Ctrl+C）才返回的循环。每一轮做三件事：

A node never calls any callback by itself. The subscriptions, timers, services and clients you create are only entities registered on the node; what actually calls the callbacks is the executor. rclcpp::spin(node) means: create an rclcpp::executors::SingleThreadedExecutor, executor.add_node(node), then executor.spin() in the current thread — a loop that returns only at shutdown (for example on Ctrl+C). Each round does three things:

  1. 收集：把加入执行器的所有节点上、按 callback group 组织的实体放进一个 wait set。
  2. Collect: put the entities of every node added to the executor, organised by callback group, into a wait set.
  3. 等待：调用 rcl_wait()，它再调用 rmw 实现的 rmw_wait()。线程在这里睡眠，直到 wait set 里至少一项就绪或超时；超时设为最近一个定时器的到期时刻。
  4. Wait: call rcl_wait(), which calls the rmw implementation’s rmw_wait(). The thread sleeps here until at least one entry in the wait set is ready or the timeout passes; the timeout is set to the nearest timer expiry.
  5. 执行：醒来后，wait set 里没就绪的项被置空，执行器逐个取出就绪项：对 subscription 先 rcl_take 取出一条消息，对 timer 先 rcl_timer_call，然后调用你的回调。处理完回到第 1 步。
  6. Execute: on waking, the entries that are not ready are cleared from the wait set, and the executor takes the ready ones one by one: for a subscription it first takes one message with rcl_take, for a timer it first calls rcl_timer_call, and then it calls your callback. When done it goes back to step 1.

wait set 是什么：rcl 里的 rcl_wait_set_t，是几个指针数组——subscriptions、guard_conditions、timers、clients、services、events，每类一个。rmw_wait() 拿着它睡眠，返回时把没就绪的项改成空指针。官方文档的说法是「每个队列一个二值标志」：它只告诉执行器某个话题有没有消息，不告诉有几条、哪条先到。guard condition 是别的线程可以手动触发的标志，用来叫醒正在睡的执行器，例如添加节点或关闭时。

What a wait set is: in rcl it is an rcl_wait_set_t, a few arrays of pointers — subscriptions, guard_conditions, timers, clients, services and events, one per kind. rmw_wait() sleeps holding it, and on return sets the entries that are not ready to null. The official docs describe it as “one binary flag per queue”: it tells the executor only whether a topic has messages, not how many or which arrived first. A guard condition is a flag another thread can trigger by hand to wake an executor that is asleep, for example when a node is added or at shutdown.

由此得出三个后果，后面几节都会用到：

Three consequences follow, and the following sections use all of them:

  • 不是先来先服务。Jazzy 的 rclcpp（executor.cpp 的 get_next_ready_executable）在就绪集合里按类型扫描：timer、subscription、service、client、waitable。文档把整体效果描述为轮转（round-robin）而非 FIFO：回调来得及处理时近似 FIFO，处理不过来时消息堆在下层队列里，顺序就不再是到达顺序。
  • Not first come, first served. Jazzy’s rclcpp (get_next_ready_executable in executor.cpp) scans the ready set by kind: timers, subscriptions, services, clients, waitables. The docs describe the overall effect as round-robin, not FIFO: while callbacks keep up it is roughly FIFO, but when they fall behind, messages pile up in the lower-layer queues and the order is no longer arrival order.
  • 执行期间到的东西要等下一轮。正在执行回调时新到的消息，要等这一轮结束、下一次 rmw_wait 才被看见。
  • Arrivals during execution wait for the next round. A message that arrives while callbacks are running is only seen when this round ends and the next rmw_wait happens.
  • 一个线程一次只做一件事。单线程执行器里，一个跑了 30 ms 的回调会把其他所有回调都推迟 30 ms。
  • One thread does one thing at a time. In a single-threaded executor, a callback that runs for 30 ms delays every other callback by 30 ms.
和 Kernel Engineering 的连接：执行器线程睡在 rmw_wait 里时，在内核看来就是一个状态为 S 的 task，大致是在一个条件变量上做 futex 等待（Fast DDS 的 rmw 实现大致如此，以源码为准）。DDS 的接收线程从 recvmsg() 返回、把数据放进队列后通知这个条件变量，内核把执行器线程放回运行队列；它什么时候真正上 CPU，由 Kernel Phase 1 的调度器决定（概念 4，EEVDF），futex 本身见 Kernel Phase 3 的概念 8。
The connection to Kernel Engineering: while an executor thread sleeps in rmw_wait, the kernel sees a task in state S, approximately doing a futex wait on a condition variable (roughly how the Fast DDS rmw implementation does it; the source is authoritative). When a DDS receive thread returns from recvmsg() and puts the data in a queue, it notifies that condition variable and the kernel puts the executor thread back on a run queue; when it actually gets the CPU is decided by the scheduler from Kernel Phase 1 (concept 4, EEVDF), and the futex itself is concept 8 of Kernel Phase 3.

2. 执行器的种类

2. Kinds of executor

  • rclcpp::executors::SingleThreadedExecutor：只有一个线程，就是调用 spin() 的那个。所有回调串行，不需要考虑回调之间的并发；rclcpp::spin(node) 用的就是它。
  • rclcpp::executors::SingleThreadedExecutor: one thread only, the one that calls spin(). Every callback runs serially, so there is no concurrency between callbacks to think about; rclcpp::spin(node) uses this one.
  • rclcpp::executors::MultiThreadedExecutor：一个线程池。Jazzy 头文件写明线程数参数默认 0，表示「CPU 核数，至少 2」。线程轮流持有一把等待锁去 rmw_wait 并取出一个就绪项，放开锁之后再去执行它，所以多个回调可以同时跑——前提是 callback group 允许（概念 3）。
  • rclcpp::executors::MultiThreadedExecutor: a thread pool. The Jazzy header states that the thread-count parameter defaults to 0, meaning “the number of CPU cores, at least 2”. Threads take turns holding a wait lock to call rmw_wait and take one ready item, then release the lock before executing it, so several callbacks can run at once — provided the callback groups allow it (concept 3).
  • StaticSingleThreadedExecutor：按官方文档，它不在每一轮重新扫描节点结构，因此开销更小，只适合在初始化时就建好全部实体的节点。Jazzy 的头文件里它没有标为弃用，但它在后续发行版中的状态有变化——请查你所用发行版的文档。
  • StaticSingleThreadedExecutor: per the official docs, it does not rescan the node structure on every round, so its overhead is lower, and it suits only nodes that create all their entities at initialisation. Jazzy’s header does not mark it deprecated, but its status changes in later distributions — check the docs for your distribution.
  • Events executor：不再每轮把实体塞进 wait set 去轮询，而是让中间件在有事件时把事件推进一个队列，执行器按到达顺序处理；定时器由单独的机制管理。Jazzy 的 rclcpp 源码里有 rclcpp::experimental::executors::EventsExecutor（在 experimental 命名空间下）；它在各发行版、各客户端库（例如 rclpy）上的可用性和成熟度请查文档。
  • Events executor: instead of putting entities into a wait set and polling every round, the middleware pushes an event into a queue when something happens, and the executor handles events in arrival order; timers are managed by a separate mechanism. Jazzy’s rclcpp source contains rclcpp::experimental::executors::EventsExecutor (in the experimental namespace); for its availability and maturity on each distribution and client library (for example rclpy), check the docs.

rclpy 有对应的 rclpy.executors.SingleThreadedExecutor 和 MultiThreadedExecutor（Jazzy 源码里线程数默认取 os.cpu_count()）。但 Python 3.12 有 GIL：同一时刻只有一个线程在执行 Python 字节码。所以 rclpy 的多线程执行器带来的是并发（一个回调在等服务响应或做 I/O 时，别的回调能跑），而不是 CPU 上的并行。

rclpy has matching rclpy.executors.SingleThreadedExecutor and MultiThreadedExecutor (in the Jazzy source the thread count defaults to os.cpu_count()). But Python 3.12 has the GIL: only one thread executes Python bytecode at any moment. So what rclpy’s multithreaded executor gives you is concurrency (while one callback waits for a service response or does I/O, others can run), not parallelism on the CPU.

3. callback group：MutuallyExclusive 与 Reentrant

3. Callback groups: MutuallyExclusive and Reentrant

执行器线程有几个，决定的是最多能同时跑几个回调；callback group 决定的是允许哪些回调同时跑。规则只有四条：

The number of executor threads decides how many callbacks at most can run at once; callback groups decide which callbacks are allowed to run at once. There are only four rules:

  • MutuallyExclusive（rclcpp::CallbackGroupType::MutuallyExclusive）：同一组里任何时刻最多一个回调在跑。
  • MutuallyExclusive (rclcpp::CallbackGroupType::MutuallyExclusive): at most one callback of the group runs at any moment.
  • Reentrant（rclcpp::CallbackGroupType::Reentrant）：组内回调可以任意并行，官方文档特别说明同一个回调的不同实例也可以同时跑。
  • Reentrant (rclcpp::CallbackGroupType::Reentrant): callbacks of the group may run in parallel without restriction; the official docs point out that different instances of the same callback may also run at the same time.
  • 不同组之间总是可以并行。
  • Different groups may always run in parallel.
  • 默认组：创建实体时不指定 group，它就进节点的默认组，而默认组是 MutuallyExclusive。所以只把执行器换成多线程、不建新组，一个节点里的回调仍然一个接一个跑。
  • The default group: an entity created without a group goes into the node’s default group, and the default group is MutuallyExclusive. So switching only the executor to multithreaded, without creating new groups, still runs the callbacks of one node one after another.
// 在节点构造函数里：控制环一组，传感器输入一组
auto control = create_callback_group(rclcpp::CallbackGroupType::MutuallyExclusive);
auto io = create_callback_group(rclcpp::CallbackGroupType::Reentrant);

timer_ = create_wall_timer(10ms, [this]() {control_step();}, control);

rclcpp::SubscriptionOptions opts;
opts.callback_group = io;
sub_ = create_subscription<sensor_msgs::msg::LaserScan>(
  "scan", 10, [this](sensor_msgs::msg::LaserScan::ConstSharedPtr m) {on_scan(m);}, opts);

// main()：只有多线程执行器才会真的并行
rclcpp::executors::MultiThreadedExecutor executor;
executor.add_node(node);
executor.spin();
from rclpy.callback_groups import MutuallyExclusiveCallbackGroup, ReentrantCallbackGroup

Reentrant 只是「允许并行」，并不让你的代码变得线程安全。两个同时运行的 on_scan 要写同一个成员变量，仍然得自己加 std::mutex 或 threading.Lock——这就是 Kernel Phase 3 里的竞态，只是换到了用户态。在单线程执行器上，group 怎么设都不会产生并行。
Reentrant only “allows parallelism”; it does not make your code thread-safe. Two on_scan calls running at once that write the same member still need your own std::mutex or threading.Lock — the races of Kernel Phase 3, moved to user space. On a single-threaded executor, no group setting ever produces parallelism.

4. 定时器

4. Timers

create_wall_timer(period, callback, group) 用 steady 时钟，不受系统时间调整影响，也不跟随仿真时间；create_timer 用节点的时钟，use_sim_time 为真时跟着 /clock 走（Phase 5）。一个定时器在 rcl 里就是一个 rcl_timer_t，记着下一次到期时刻 next_call_time：

create_wall_timer(period, callback, group) uses the steady clock, which is unaffected by system time changes and does not follow simulated time; create_timer uses the node’s clock, which follows /clock when use_sim_time is true (Phase 5). In rcl a timer is an rcl_timer_t that remembers its next expiry, next_call_time:

  1. 执行器把「离最近一个 next_call_time 还有多久」当作 rmw_wait 的超时。
  2. The executor uses “time left until the nearest next_call_time” as the timeout for rmw_wait.
  3. 醒来后发现定时器到期，执行器调用 rcl_timer_call，再调用你的回调。所以回调只会晚于到期时刻开始，晚多少就是这一轮的延迟。
  4. On waking, the executor finds the timer has expired, calls rcl_timer_call, then your callback. So the callback can only start after the expiry, and how much later is this round’s latency.
  5. 下一次到期从计划时刻算起，加一个周期，而不是从回调实际开始的时刻算起，所以迟到不会累积。如果已经错过了不止一个周期，Jazzy 的 rcl/src/rcl/timer.c 会把到期时刻一次往后推若干个周期：错过的那几次直接跳过，不会连发补上。
  6. The next expiry is computed from the scheduled time plus one period, not from when the callback actually started, so lateness does not accumulate. If more than one period has been missed, Jazzy’s rcl/src/rcl/timer.c moves the expiry forward by as many periods as needed in one step: the missed calls are skipped, not fired back to back.

5. 在回调里调用服务为什么会死锁

5. Why calling a service inside a callback deadlocks

场景：一个定时器回调里调用服务，然后阻塞等待响应——rclpy 里是 client.call(req)，rclcpp 里是 async_send_request 之后对 future 调用 get() 或 wait()。在单线程执行器上它永远不返回。按执行器循环一步步看：

The scenario: a timer callback calls a service and then blocks waiting for the response — client.call(req) in rclpy, or async_send_request followed by get() or wait() on the future in rclcpp. On a single-threaded executor it never returns. Follow the executor loop step by step:

  1. 执行器唯一的线程在执行你的定时器回调。请求发出去了，服务端很快回了响应。
  2. The executor’s only thread is executing your timer callback. The request goes out, and the server answers quickly.
  3. 响应到了 DDS 的 reader 队列，对应的 client 实体在 wait set 里会变成就绪——但只有执行器线程再次 rmw_wait、取出这个 client、调用 take response 之后，future 才会被置为完成（rclpy 里是触发 call() 在等的那个事件）。
  4. The response reaches the DDS reader queue, and the matching client entity would become ready in the wait set — but the future is only completed after the executor thread does rmw_wait again, takes that client and takes its response (in rclpy, this is what sets the event call() is waiting on).
  5. 执行器唯一的线程正阻塞在你的回调里等这个 future。等的人和要完成它的人是同一个线程：谁也不动，这就是死锁。
  6. The executor’s only thread is blocked inside your callback waiting for that future. The one waiting and the one who would complete it are the same thread: neither moves, and that is the deadlock.

换成多线程执行器也不一定够：如果 client 和发起调用的定时器都在默认组（MutuallyExclusive）里，处理响应的那一步要等这个组空出来，而组被正在等响应的回调占着——还是死锁。在回调里调用 rclcpp::spin_until_future_complete(node, future) 也不行：节点已经属于一个执行器，rclcpp 会抛异常拒绝再把它加进另一个。

Switching to a multithreaded executor is not necessarily enough: if the client and the timer making the call are both in the default (MutuallyExclusive) group, the step that handles the response must wait for that group to be free, and the group is held by the callback that is waiting for the response — still a deadlock. Calling rclcpp::spin_until_future_complete(node, future) inside a callback does not work either: the node already belongs to an executor, and rclcpp throws rather than add it to another one.

  • 修法 1，不阻塞：rclcpp 用 async_send_request(req, callback)，在响应回调里继续处理；rclpy 用 call_async(req) 加 future.add_done_callback(...)。回调立刻返回，执行器线程空出来处理响应。
  • Fix 1, do not block: in rclcpp use async_send_request(req, callback) and continue in the response callback; in rclpy use call_async(req) plus future.add_done_callback(...). The callback returns at once, and the executor thread is free to handle the response.
  • 修法 2，分组 + 多线程：把 client 放进另一个 callback group，用 MultiThreadedExecutor。这时阻塞等待的是一个线程，处理响应的是另一个线程，而且它们不在同一组。最好用带超时的等待（例如 wait_for），服务端不在时不至于永远卡住。
  • Fix 2, separate group + multithreaded: put the client in another callback group and use MultiThreadedExecutor. Now one thread blocks waiting and another thread handles the response, and they are not in the same group. Prefer a wait with a timeout (for example wait_for), so that a missing server does not hang you forever.

6. 回调延迟与抖动：从哪里来、怎么量

6. Callback latency and jitter: where they come from and how to measure them

延迟是事件（定时器到期、消息到达）到回调开始的时间；抖动是这个延迟（或相邻两次回调的间隔）的变化量。对一个 100 Hz 定时器，理想间隔是 10 000 µs，抖动就是实际间隔偏离它多少。来源可以拆成四类：

Latency is the time from an event (a timer expiring, a message arriving) to the start of the callback; jitter is how much that latency (or the interval between consecutive callbacks) varies. For a 100 Hz timer the ideal interval is 10 000 µs, and jitter is how far the actual interval strays from it. The sources fall into four kinds:

  1. 定时器本身：rmw_wait 的超时最终是内核里一个高精度定时器加一次唤醒。普通调度策略的线程有 timer slack，默认 50 µs，内核可以把到期推迟最多这么多，好把几次唤醒合并；实时策略的线程不加 slack（见 prctl(PR_SET_TIMERSLACK) 的手册）。在虚拟机里，客体内核的时钟中断还要经过宿主的虚拟化层。
  2. The timer itself: the timeout of rmw_wait ends up as a high-resolution timer in the kernel plus a wake-up. Threads under the normal scheduling policies have timer slack, 50 µs by default, by which the kernel may delay an expiry so as to merge several wake-ups; threads under real-time policies get no slack (see the prctl(PR_SET_TIMERSLACK) man page). In a VM, the guest kernel’s timer interrupts also pass through the host’s virtualisation layer.
  3. 执行器队列：同一线程里排在前面的回调，或同一 MutuallyExclusive 组里正在跑的回调（概念 1、3）。这一项和内核无关，是你的程序结构决定的，往往也是最大的一项。
  4. The executor queue: callbacks ahead of yours in the same thread, or a callback already running in the same MutuallyExclusive group (concepts 1 and 3). This one has nothing to do with the kernel; your program’s structure decides it, and it is often the largest.
  5. 调度器：线程被唤醒只是变成可运行，还得等 CPU。在普通（fair）类里它和所有其他普通任务一起由 EEVDF 排队；CPU 都忙时，排队时间可能达到毫秒级。Docker Desktop 里还多一层：Linux VM 的每个 vCPU 本身是 macOS 上的一个线程，由 XNU 调度，macOS 把它停下时，Linux 里的一切都停了，而 Linux 看不到原因。
  6. The scheduler: being woken only makes a thread runnable; it still has to wait for a CPU. In the ordinary (fair) class it queues under EEVDF with every other ordinary task; when all CPUs are busy, that wait can reach milliseconds. Docker Desktop adds one more layer: each vCPU of the Linux VM is itself a thread on macOS, scheduled by XNU, and when macOS stops it, everything in Linux stops, for a reason Linux cannot see.
  7. 内存分配与缺页：new / malloc 可能要拿分配器的锁、调用 brk 或 mmap；第一次写一个新页会触发缺页异常。std::vector 扩容、std::string 拼接、每条消息一次 make_shared、日志宏格式化，都可能在热路径上分配。Python 里几乎每个操作都分配内存，还有 GIL 和垃圾回收。
  8. Memory allocation and page faults: new / malloc may take the allocator’s lock and call brk or mmap; the first write to a new page triggers a page fault. Growing a std::vector, concatenating a std::string, one make_shared per message, formatting in a logging macro — all of these can allocate on the hot path. In Python almost every operation allocates, and there are also the GIL and garbage collection.

对消息还要再加上中间件那段：序列化、DDS 线程、内核的 socket 或共享内存（Phase 3）。怎么量：

For messages, add the middleware part on top: serialization, the DDS threads, and the kernel’s sockets or shared memory (Phase 3). How to measure:

  • ros2 topic hz /tick：打印平均频率、min、max、std dev 和窗口大小（-w 改窗口）。注意 Jazzy 的源码里 min 和 max 只打印到毫秒（%.3f 秒），std dev 到 10 µs，而且它测的是 CLI 进程收到消息的间隔，本身就带着 Python 订阅端的抖动。
  • ros2 topic hz /tick: prints the average rate, min, max, std dev and window size (-w changes the window). Note that in the Jazzy source min and max are printed only to the millisecond (%.3f seconds) and std dev to 10 µs, and it measures the interval at which the CLI process receives messages, so it carries the jitter of a Python subscriber itself.
  • ros2 topic delay /tick：用「现在」减去消息的 header.stamp，所以消息类型必须带 header（Lab A 用 geometry_msgs/msg/PointStamped）。测的是发布到 CLI 收到的整段延迟。
  • ros2 topic delay /tick: subtracts the message’s header.stamp from “now”, so the message type must have a header (Lab A uses geometry_msgs/msg/PointStamped). It measures the whole delay from publishing to the CLI receiving it.
  • 节点自己记时间戳：在回调开头读 std::chrono::steady_clock，存进预先分配好的数组，攒够一批再算统计。这是唯一能看到微秒级、只属于回调本身的数字的办法，Lab A 就这么做。
  • Timestamps recorded by the node itself: read std::chrono::steady_clock at the start of the callback, store it in a preallocated array, and compute statistics once a batch is full. This is the only way to see microsecond-level numbers that belong to the callback alone, and Lab A does exactly this.
  • ros2_tracing（可选）：rclcpp、rcl、rmw 里编进了 tracepoint，例如 ros2:callback_start 和 ros2:callback_end，用 LTTng 的用户态追踪记下每个回调的开始和时长。按 ros2_tracing 的 README，Iron 起 LTTng 用户态追踪器是 ROS 2 的依赖；ros2 trace 命令要装可选包 ros-jazzy-ros2trace，launch 里用的 Trace 动作在 ros-jazzy-tracetools-launch。追踪内核要另装 LTTng 内核模块，在容器里做不到（容器不能给 Docker 的 VM 内核装模块）。完整的追踪实验在 Phase 7。
  • ros2_tracing (optional): rclcpp, rcl and rmw are built with tracepoints such as ros2:callback_start and ros2:callback_end, and LTTng userspace tracing records the start and duration of every callback. Per the ros2_tracing README, the LTTng userspace tracer has been a ROS 2 dependency since Iron; the ros2 trace command needs the optional package ros-jazzy-ros2trace, and the Trace action for launch files is in ros-jazzy-tracetools-launch. Tracing the kernel needs the LTTng kernel modules installed separately, which is not possible in the container (a container cannot load modules into Docker’s VM kernel). The full tracing lab is in Phase 7.

7. ROS 2 的实时基础：SCHED_FIFO、内存、PREEMPT_RT

7. Real-time basics for ROS 2: SCHED_FIFO, memory, PREEMPT_RT

实时的意思不是「快」，而是最坏情况有界：控制环每一次都要在截止时间之前跑完。ROS 2 本身不会让程序变成实时的；它的设计是允许你在实时线程里用 rclcpp，剩下的靠内核和你自己的写法。按上面的四个来源逐个处理：

Real-time does not mean “fast”; it means a bounded worst case: the control loop finishes before its deadline every single time. ROS 2 does not make a program real-time by itself; it is designed to allow rclcpp to be used from a real-time thread, and the rest depends on the kernel and on how you write code. Take the four sources above one at a time:

  • 调度：SCHED_FIFO。Linux 的调度类有先后：实时类（SCHED_FIFO、SCHED_RR）排在普通 fair 类（EEVDF）之上。一个 CPU 上只要有可运行的 FIFO 任务，任何普通任务都不会被选中。FIFO 任务之间按优先级 1–99 比较，高的先跑；同优先级的 FIFO 任务没有时间片，一直跑到它自己阻塞或让出（SCHED_RR 才加时间片）。chrt -f 80 命令 用 FIFO 80 启动一个程序，chrt -p PID 查看。需要 CAP_SYS_NICE 或足够的 RLIMIT_RTPRIO，实验容器两样都给了。
  • Scheduling: SCHED_FIFO. Linux scheduling classes are ordered: the real-time class (SCHED_FIFO, SCHED_RR) sits above the ordinary fair class (EEVDF). As long as a CPU has a runnable FIFO task, no ordinary task is picked there. FIFO tasks compare by priority 1–99, higher first; a FIFO task has no time slice against equal-priority peers and runs until it blocks or yields (SCHED_RR adds a slice). chrt -f 80 command starts a program at FIFO 80, and chrt -p PID shows it. This needs CAP_SYS_NICE or a sufficient RLIMIT_RTPRIO, and the lab container grants both.
  • 安全网：实时节流。内核文档 sched-rt-group 给出的默认值是 sched_rt_runtime_us = 950000、sched_rt_period_us = 1000000：实时任务每秒最多用 0.95 秒，留 5% 给普通任务。一个写错了、在 FIFO 下死循环的线程不会让机器完全卡死，但它会被周期性地停下，这本身又是抖动。具体机制随内核版本变化，以 /proc/sys/kernel/sched_rt_runtime_us 和你内核的文档为准。
  • The safety net: real-time throttling. The kernel document sched-rt-group gives the defaults sched_rt_runtime_us = 950000 and sched_rt_period_us = 1000000: real-time tasks may use at most 0.95 s of every second, leaving 5% for ordinary tasks. A buggy thread spinning under FIFO will not freeze the machine completely, but it is stopped periodically, which is jitter in its own right. The exact mechanism changes between kernel versions; go by /proc/sys/kernel/sched_rt_runtime_us and your kernel’s documentation.
  • 内存：mlockall 与不在热路径上分配。mlockall(MCL_CURRENT | MCL_FUTURE) 把进程现有和以后的页都锁在内存里，不会被换出；需要 CAP_IPC_LOCK 或足够大的 RLIMIT_MEMLOCK——实验容器的 compose 没有放宽 memlock，所以 Lab B 里它很可能失败，这本身就是一个观察点。热路径里预先分配（reserve）、重复使用同一个消息对象、不在控制环里打日志。
  • Memory: mlockall and no allocation on the hot path. mlockall(MCL_CURRENT | MCL_FUTURE) locks the process’s current and future pages in memory so they are never swapped out; it needs CAP_IPC_LOCK or a large enough RLIMIT_MEMLOCK — the lab compose file does not raise memlock, so it will most likely fail in Lab B, which is itself something to observe. On the hot path, preallocate (reserve), reuse one message object, and do not log inside the control loop.
  • 锁：优先级反转。实时线程去拿一把被普通线程持有的 mutex，而这个普通线程又被别的任务抢走了 CPU，实时线程就被间接拖住。办法是优先级继承的 mutex（pthread 的 PTHREAD_PRIO_INHERIT，内核里落到 PI futex 和 rt_mutex），机制见 Kernel Phase 3 概念 1 和 8。注意 DDS 的内部线程和你的执行器线程共享队列和锁，它们不一定是同一个优先级。
  • Locks: priority inversion. A real-time thread takes a mutex held by an ordinary thread, and that ordinary thread has lost the CPU to some other task, so the real-time thread is held up indirectly. The remedy is a priority-inheritance mutex (pthread’s PTHREAD_PRIO_INHERIT, which becomes PI futexes and rt_mutex in the kernel); the mechanism is in concepts 1 and 8 of Kernel Phase 3. Note that the DDS internal threads share queues and locks with your executor threads, and they are not necessarily at the same priority.
  • 内核：PREEMPT_RT。普通内核里有不少不可抢占的区段，实时线程被唤醒后也得等它们结束。PREEMPT_RT 把大部分 spinlock 换成可睡眠的 rt_mutex、把中断处理放进内核线程，让几乎所有内核代码都可被抢占；它在 Linux 6.12 进入主线，但仍需要一个用这个选项编译的内核，运行中的内核在 uname -v 里会显示 PREEMPT_RT。在实验容器里做不到：容器共用 Docker Desktop VM 的内核，见实验环境页概念 5。
  • The kernel: PREEMPT_RT. An ordinary kernel has many non-preemptible sections, and a woken real-time thread must wait for them to finish. PREEMPT_RT turns most spinlocks into sleeping rt_mutexes and moves interrupt handling into kernel threads, so almost all kernel code becomes preemptible; it entered mainline in Linux 6.12, but it still needs a kernel built with that option, and a running one shows PREEMPT_RT in uname -v. It is not possible in the lab container: a container shares the kernel of Docker Desktop’s VM, see concept 5 of the lab environment page.
chrt 在容器里能修什么、修不了什么。能修：同一个 Linux VM 里普通任务和你抢 CPU 造成的排队（第 3 类来源的 Linux 部分），以及 timer slack。修不了：执行器队列（第 2 类，那是你的代码结构）；内存分配与缺页（第 4 类）；Docker VM 内核里不可抢占的区段（没有 PREEMPT_RT）；macOS 暂停 VM 的 vCPU 线程（Linux 根本看不到，FIFO 99 也一样）；以及优先级更高的实时任务或中断。所以 Lab B 能演示「有优先级」和「没有优先级」的区别，但测不出一个可以写进规格的最坏延迟。
What chrt can and cannot fix in a container. It can fix the queueing caused by ordinary tasks competing for the CPU inside the same Linux VM (the Linux part of source 3), and the timer slack. It cannot fix the executor queue (source 2, which is your code’s structure); memory allocation and page faults (source 4); non-preemptible sections of the Docker VM kernel (there is no PREEMPT_RT); macOS pausing the VM’s vCPU thread (Linux cannot see it at all, even at FIFO 99); or higher-priority real-time tasks and interrupts. So Lab B can show the difference between “with priority” and “without priority”, but cannot measure a worst-case latency you could write into a specification.

    // jitter_node.cpp: a 100 Hz timer, an optional slow timer, four executor setups
#include <sys/mman.h>

#include <algorithm>
#include <chrono>
#include <cmath>
#include <cstdio>
#include <memory>
#include <string>
#include <vector>

#include "geometry_msgs/msg/point_stamped.hpp"
#include "rclcpp/rclcpp.hpp"

using namespace std::chrono_literals;
using Clock = std::chrono::steady_clock;

class JitterNode : public rclcpp::Node
{
public:
  JitterNode(bool with_slow, bool split_groups)
  : Node("jitter_node")
  {
    rclcpp::CallbackGroup::SharedPtr fast_group;  // nullptr: the default group
    rclcpp::CallbackGroup::SharedPtr slow_group;
    if (split_groups) {
      fast_group = create_callback_group(rclcpp::CallbackGroupType::MutuallyExclusive);
      slow_group = create_callback_group(rclcpp::CallbackGroupType::MutuallyExclusive);
    }
    pub_ = create_publisher<geometry_msgs::msg::PointStamped>("tick", 10);
    periods_us_.reserve(kWindow);  // 只分配一次，不在热路径上分配
    fast_ = create_wall_timer(10ms, [this]() {on_fast();}, fast_group);
    if (with_slow) {
      slow_ = create_wall_timer(200ms, [this]() {on_slow();}, slow_group);
    }
  }

private:
  static constexpr size_t kWindow = 1000;  // 1000 个间隔 = 10 s

  void on_fast()
  {
    const auto t = Clock::now();
    if (started_) {
      periods_us_.push_back(std::chrono::duration<double, std::micro>(t - last_).count());
    }
    last_ = t;
    started_ = true;

    msg_.header.stamp = now();  // 给 ros2 topic delay 用
    pub_->publish(msg_);        // 中间件内部仍可能分配内存

    if (periods_us_.size() == kWindow) {
      report();
      periods_us_.clear();      // 保留容量
    }
  }

  void on_slow()
  {
    const auto until = Clock::now() + 30ms;
    while (Clock::now() < until) {}  // 30 ms 的假工作
  }

  void report()
  {
    auto & v = periods_us_;
    const auto [lo, hi] = std::minmax_element(v.begin(), v.end());
    const double pmin = *lo;
    const double pmax = *hi;
    for (auto & p : v) {p = std::abs(p - 10000.0);}  // 与 10 ms 的偏差
    std::sort(v.begin(), v.end());
    RCLCPP_INFO(
      get_logger(), "period min %.0f us max %.0f us | dev p50 %.0f p99 %.0f max %.0f us",
      pmin, pmax, v[v.size() / 2], v[v.size() * 99 / 100], v.back());
  }

  rclcpp::Publisher<geometry_msgs::msg::PointStamped>::SharedPtr pub_;
  rclcpp::TimerBase::SharedPtr fast_;
  rclcpp::TimerBase::SharedPtr slow_;
  geometry_msgs::msg::PointStamped msg_;
  std::vector<double> periods_us_;
  Clock::time_point last_;
  bool started_ = false;
};

int main(int argc, char ** argv)
{
  const auto args = rclcpp::init_and_remove_ros_arguments(argc, argv);
  const std::string mode = args.size() > 1 ? args[1] : "alone";
  if (args.size() > 2 && args[2] == "lock") {
    if (mlockall(MCL_CURRENT | MCL_FUTURE) != 0) {

    }

import rclpy
from example_interfaces.srv import AddTwoInts
from rclpy.callback_groups import MutuallyExclusiveCallbackGroup
from rclpy.executors import ExternalShutdownException
from rclpy.executors import MultiThreadedExecutor, SingleThreadedExecutor
from rclpy.node import Node


class Caller(Node):

    def __init__(self, own_group):
        super().__init__('caller')
        group = MutuallyExclusiveCallbackGroup() if own_group else None  # None: default group
        self.cli = self.create_client(AddTwoInts, 'add_two_ints', callback_group=group)
        self.timer = self.create_timer(1.0, self.on_timer)  # default group

        res = self.cli.call(AddTwoInts.Request(a=2, b=3))  # 阻塞本线程，直到响应被处理

    executor.add_node(node)
    try:
        executor.spin()
    except (KeyboardInterrupt, ExternalShutdownException):
        pass

自测

Self-check

1. 一个用 rclcpp::spin(node) 运行的节点，在定时器回调里 async_send_request 之后对 future 调用 get()，服务端明明在线，回调却再也不返回。为什么？

1. A node run with rclcpp::spin(node) calls async_send_request in a timer callback and then get() on the future; the server is definitely up, yet the callback never returns. Why?

rclcpp::spin 用的是单线程执行器，响应虽然到了 reader 队列，但只有执行器线程取出 client 才能完成 future，而这个线程正在等 future。a 错：响应留在下层队列里，没有丢；c 错：服务响应和定时器周期无关，由服务端处理完立即发送。rclcpp::spin uses a single-threaded executor; the response does reach the reader queue, but only the executor thread taking the client can complete the future, and that thread is waiting on the future. a is wrong: the response stays in the lower-layer queue and is not dropped; c is wrong: service responses have nothing to do with timer periods and are sent as soon as the server finishes.

2. 节点里有定时器 A 和订阅 B，创建时都没指定 callback group，节点由 4 线程的 MultiThreadedExecutor 运行。A 正在执行时 B 的消息到了，还有线程空闲。会发生什么？

2. A node has a timer A and a subscription B, both created without a callback group, and is run by a 4-thread MultiThreadedExecutor. While A is running a message for B arrives, and threads are idle. What happens?

线程数只决定上限，callback group 决定是否允许并行；默认组是 MutuallyExclusive。a 忽略了组的规则（要并行，得把 B 放进另一个组）；b 错：消息留在 reader 队列里，等组空出来再处理。The thread count sets only the ceiling; callback groups decide whether parallelism is allowed, and the default group is MutuallyExclusive. a ignores the group rule (to run in parallel, B must go into another group); b is wrong: the message stays in the reader queue and is handled once the group is free.

3. 在实验容器里用 chrt -f 80 跑定时器节点后，下面哪个抖动来源仍然存在？

3. After running the timer node under chrt -f 80 in the lab container, which jitter source is still there?

vCPU 是 macOS 上由 XNU 调度的线程，它被停下时 Linux 里所有任务都停，Linux 的调度策略管不到。b 错：只要有可运行的 FIFO 任务，fair 类的任务就不会被选中；c 错：实时策略的线程不加 timer slack。A vCPU is a thread on macOS scheduled by XNU; when it is stopped every task in Linux stops, and no Linux scheduling policy reaches it. b is wrong: while a FIFO task is runnable, no fair-class task is picked; c is wrong: threads under real-time policies get no timer slack.

4. 一个 10 ms 的 wall timer，因为同一线程里另一个回调跑了 35 ms，错过了几次到期。按 Jazzy 的 rcl，接下来会怎样？

4. A 10 ms wall timer misses a few expiries because another callback in the same thread ran for 35 ms. Per Jazzy’s rcl, what happens next?

rcl_timer_call 把下一次到期设为计划时刻加一个周期，若仍已过去，就一次向后推足够多的周期。所以没有连发补偿（a 错），而且到期时刻始终落在原来的 10 ms 网格上，相位不变（c 错）。rcl_timer_call sets the next expiry to the scheduled time plus one period and, if that is still in the past, moves it forward by enough periods in one step. So there is no catch-up burst (a is wrong), and expiries stay on the original 10 ms grid, so the phase is unchanged (c is wrong).
