到目前为止，每个节点都是你在一个 shell 里手动 ros2 run 起来的。真正的机器人有几十个节点，需要一次拉起、各自带参数、放进各自的命名空间，并且要按顺序进入工作状态：先把驱动和地图都配置好，再一起开始发布。这一阶段讲四个工具：launch 文件在运行时是一个带事件处理器的进程树；参数文件、命名空间与重映射让同一个节点不改代码就能用在不同位置；managed（lifecycle）节点把「创建」「配置」「激活」拆成外部可以驱动的状态机；组合（composition）把几个节点装进同一个进程，让消息以指针的形式在进程内传递，跳过序列化和 DDS。

So far every node has been started by hand with ros2 run in its own shell. A real robot has dozens of nodes that must start together, each with its parameters and in its own namespace, and must come into service in order: configure the drivers and the map first, then start publishing all at once. This phase covers four tools: a launch file is, at run time, a process tree with event handlers; parameter files, namespaces and remapping let one node be reused in different places without code changes; managed (lifecycle) nodes split “create”, “configure” and “activate” into a state machine that something outside can drive; and composition puts several nodes into one process so that messages travel inside it as pointers, skipping serialization and DDS.

核心概念

Core concepts

1. launch 文件在运行时是什么

1. What a launch file is at run time

Python launch 文件不是「按顺序执行的启动脚本」，而是一个返回描述的函数。ros2 launch 加载这个文件，调用其中的 generate_launch_description()，拿到一个 LaunchDescription：一列动作（action），例如声明参数、启动节点、包含另一个 launch 文件、注册事件处理器。然后一个 launch 服务（launch.LaunchService）在一个 asyncio 事件循环里逐个「访问」这些动作：

A Python launch file is not “a start-up script that runs in order”; it is a function that returns a description. ros2 launch loads the file, calls its generate_launch_description(), and gets a LaunchDescription: a list of actions such as declaring an argument, starting a node, including another launch file, or registering an event handler. A launch service (launch.LaunchService) then “visits” those actions one by one in an asyncio event loop:

  • 替换在访问时求值。LaunchConfiguration('ns') 这类替换（substitution）在写文件时只是一个占位对象，launch 服务访问到用它的动作时才从当时的上下文里取值。所以你不能在 generate_launch_description() 里用 Python 的 if 去判断一个 launch 参数的值；要条件执行，用动作的 condition=IfCondition(...)，或者 OpaqueFunction 在运行时拿到上下文（后者请查文档）。
  • Substitutions are evaluated on visit. A substitution such as LaunchConfiguration('ns') is only a placeholder object when the file is written; the launch service takes its value from the context of that moment, when it visits the action using it. So you cannot use a Python if inside generate_launch_description() to test a launch argument’s value; for conditional actions use condition=IfCondition(...) on the action, or an OpaqueFunction that receives the context at run time (check the docs for the latter).
  • Node 动作就是启动一个进程。launch_ros.actions.Node 是 ExecuteProcess 的特化：它把包名和可执行文件名解析成 install/<pkg>/lib/<pkg>/<exe> 这类路径（大致路径），把 name、namespace、remappings、parameters 翻译成 --ros-args -r __node:=… -r __ns:=… -r a:=b --params-file … 追加到命令行，然后由 launch 服务派生一个子进程去执行它。节点不在 launch 进程里运行。
  • A Node action starts a process. launch_ros.actions.Node is a specialisation of ExecuteProcess: it resolves the package and executable name to a path like install/<pkg>/lib/<pkg>/<exe> (approximate path), translates name, namespace, remappings and parameters into --ros-args -r __node:=… -r __ns:=… -r a:=b --params-file … appended to the command line, and the launch service spawns a child process to run it. The node does not run inside the launch process.
  • 结果是一棵进程树。运行中的系统在内核看来是：一个 ros2 launch 的 Python 进程，下面挂着每个节点一个子进程。launch 进程一直活着，用 asyncio 等待子进程的输出和退出，把它们变成事件（ProcessStarted、ProcessIO、ProcessExited），再分发给注册过的事件处理器。
  • The result is a process tree. To the kernel, the running system is one Python process for ros2 launch with one child process per node under it. The launch process stays alive, waits with asyncio for the children’s output and exit, turns them into events (ProcessStarted, ProcessIO, ProcessExited), and dispatches them to the registered event handlers.
  • 关闭是信号的升级。你在 launch 的终端按 Ctrl+C，launch 收到 SIGINT，发出一个 Shutdown 事件，再给仍在运行的子进程发 SIGINT；5 秒后还不退就发 SIGTERM，再过 5 秒发 SIGKILL。这两个 5 秒是 sigterm_timeout 和 sigkill_timeout 的默认值。这就是 Kernel Phase 1 里父进程管理子进程的那一套。
  • Shutdown is an escalation of signals. When you press Ctrl+C in the launch terminal, launch receives SIGINT, emits a Shutdown event, and sends SIGINT to the children still running; a child still running after 5 s gets SIGTERM, and after another 5 s SIGKILL. These are the sigterm_timeout and sigkill_timeout defaults. This is the parent-manages-children pattern of Kernel Phase 1.
launch 文件还可以写成 XML 或 YAML，它们被解析成同一套动作，能力略少。本课程只用 Python 格式，因为事件处理器和组合容器在 Python 里写最直接。按 launch 的设计文章，launch 系统的职责是「启动、监视、关闭一组进程，并对它们的状态变化作出反应」，而不是一个通用构建或部署工具。
Launch files can also be written in XML or YAML, which are parsed into the same actions with slightly fewer capabilities. This course uses only the Python format, because event handlers and composable containers are most direct to write in Python. Per the launch design article, the job of the launch system is “to start, monitor and shut down a set of processes, and to react to changes in their state”, not to be a general build or deployment tool.

2. launch 参数、替换、包含与事件

2. Launch arguments, substitutions, includes and events

  • launch 参数：DeclareLaunchArgument('ns', default_value='robot1', description='…') 声明一个可以从命令行覆盖的值，LaunchConfiguration('ns') 读取它。命令行写法是 ros2 launch pkg file.launch.py ns:=robot2；ros2 launch pkg file.launch.py --show-args 列出文件声明的全部参数和默认值。launch 参数和节点参数是两回事：前者只活在 launch 进程里，后者属于每个节点。
  • Launch arguments: DeclareLaunchArgument('ns', default_value='robot1', description='…') declares a value that can be overridden from the command line, and LaunchConfiguration('ns') reads it. On the command line it is ros2 launch pkg file.launch.py ns:=robot2; ros2 launch pkg file.launch.py --show-args lists every argument the file declares, with defaults. Launch arguments and node parameters are different things: the former live only in the launch process, the latter belong to each node.
  • 常用替换：LaunchConfiguration（launch 参数）、PathJoinSubstitution（拼路径）、ThisLaunchFileDir（当前 launch 文件所在目录）、launch_ros.substitutions.FindPackageShare（一个包的 share 目录）。它们都可以出现在动作的参数里，直到访问时才变成字符串。
  • Common substitutions: LaunchConfiguration (a launch argument), PathJoinSubstitution (join a path), ThisLaunchFileDir (the directory of the current launch file), launch_ros.substitutions.FindPackageShare (a package’s share directory). All of them can appear in action arguments and become strings only on visit.
  • 包含：IncludeLaunchDescription(PythonLaunchDescriptionSource(path), launch_arguments={'ns': 'robot2'}.items()) 把另一个 launch 文件的动作接进来，并给它的 launch 参数传值。大系统就是这样分层的：一个总文件包含驱动、感知、导航各自的 launch 文件。
  • Includes: IncludeLaunchDescription(PythonLaunchDescriptionSource(path), launch_arguments={'ns': 'robot2'}.items()) splices in another launch file’s actions and passes values to its launch arguments. Large systems are layered this way: one top file includes the launch files of the drivers, perception and navigation.
  • 事件处理器：RegisterEventHandler(OnProcessExit(target_action=talker, on_exit=[…])) 在 talker 这个进程退出时执行一列动作，例如 LogInfo、启动另一个节点，或 EmitEvent(event=Shutdown(reason='…')) 关掉整个系统。OnProcessStart、OnProcessIO 和 OnShutdown 用法相同。简单场景还有快捷方式：Node(..., on_exit=Shutdown())，以及让进程退出后重启的 respawn=True。
  • Event handlers: RegisterEventHandler(OnProcessExit(target_action=talker, on_exit=[…])) runs a list of actions when the talker process exits, for example LogInfo, starting another node, or EmitEvent(event=Shutdown(reason='…')) to bring the whole system down. OnProcessStart, OnProcessIO and OnShutdown work the same way. Simple cases have shortcuts: Node(..., on_exit=Shutdown()), and respawn=True to restart a process after it exits.
注意 OnProcessStart 只说明进程已经 exec，不说明节点已经建好发布者、完成了配置。launch 只看得见进程，看不见节点内部的状态。「等 A 准备好再启动 B」用进程事件做不可靠，这正是概念 4 的 lifecycle 节点要解决的问题。
Note that OnProcessStart only says the process has exec’d, not that the node has created its publishers or finished configuring. Launch sees processes, not the state inside a node. “Start B once A is ready” cannot be done reliably with process events, which is exactly the problem the lifecycle nodes of concept 4 solve.

3. 命名空间、重映射与参数 YAML

3. Namespaces, remapping and parameter YAML

同一个 talker 要给两台机器人用，代码不该改，改的是名字。名字的解析规则（设计文章 Topic and Service name mapping）是：

To use the same talker for two robots, the code should not change; the names do. The resolution rules (design article Topic and Service name mapping) are:

  • 相对名 chatter 接在节点的命名空间后面：命名空间是 /robot1 时，它解析为 /robot1/chatter。绝对名 /chatter 不受命名空间影响。私有名 ~/status 接在节点的全名后面：/robot1/talker/status。
  • A relative name chatter is appended to the node’s namespace: with namespace /robot1 it resolves to /robot1/chatter. An absolute name /chatter ignores the namespace. A private name ~/status is appended to the node’s full name: /robot1/talker/status.
  • 重映射 -r chatter:=speech（launch 里是 remappings=[('chatter', 'speech')]）在解析之前替换名字：代码里写的 chatter 变成 speech，再接上命名空间，得到 /robot1/speech。__ns:= 和 __node:= 两条特殊规则改的是命名空间和节点名本身。规则前加节点名（talker:chatter:=speech）只对那个节点生效，适合一个进程里有多个节点时（概念 5）。
  • Remapping -r chatter:=speech (in launch, remappings=[('chatter', 'speech')]) replaces a name before resolution: the chatter in the code becomes speech, then the namespace is prepended, giving /robot1/speech. The two special rules __ns:= and __node:= change the namespace and the node name themselves. Prefixing a rule with a node name (talker:chatter:=speech) applies it to that node only, which matters when one process holds several nodes (concept 5).
  • 参数 YAML 按节点全名匹配。顶层键是节点的全名，下一层固定是 ros__parameters。/robot1/talker: 只匹配命名空间 /robot1 下名为 talker 的节点；/**: 匹配所有节点，适合 use_sim_time 这类全局设置。把命名空间从 robot1 改成 robot2 后，/robot1/talker: 那一段就悄悄不生效了：不报错，节点只是拿到默认值。Lab A 会故意制造这个现象。
  • Parameter YAML matches by full node name. The top-level key is the node’s full name, and the next level is always ros__parameters. /robot1/talker: matches only the node named talker in namespace /robot1; /**: matches every node, which suits global settings such as use_sim_time. After changing the namespace from robot1 to robot2, the /robot1/talker: section silently stops applying: no error, the node just gets its defaults. Lab A provokes this on purpose.
  • 多个来源的先后：launch 的 parameters=[file.yaml, {'k': v}] 按列表顺序变成多个 --params-file 和 -p，后面的覆盖前面的（请查文档确认你的发行版仍是这个顺序）。和 Phase 1 一样，这些只是覆盖值，在节点声明参数的那一刻才生效；节点没声明的参数默认会被忽略。
  • Order of several sources: launch’s parameters=[file.yaml, {'k': v}] becomes several --params-file and -p arguments in list order, and later ones override earlier ones (check the docs that your distribution keeps this order). As in Phase 1, these are only overrides, applied at the moment the node declares the parameter; parameters the node never declares are ignored by default.

4. managed（lifecycle）节点：状态机与它的保证

4. Managed (lifecycle) nodes: the state machine and its guarantees

普通节点在构造函数里就建好发布者并开始工作，外面的人只能看到「进程起来了」。rclcpp_lifecycle::LifecycleNode 把这一过程拆成一台标准状态机（设计文章 Managed nodes），由外部通过服务驱动：

An ordinary node creates its publishers in its constructor and starts working, and the outside world sees only “the process is up”. rclcpp_lifecycle::LifecycleNode splits that into a standard state machine (design article Managed nodes) that is driven from outside through services:

  • 四个主状态：Unconfigured（节点对象刚建好，什么资源都没有）、Inactive（已配置：读了参数、建了发布者和定时器，但不对外产生数据）、Active（正常工作）、Finalized（终态，只等对象被销毁）。
  • Four primary states: Unconfigured (the node object exists and holds no resources), Inactive (configured: parameters read, publishers and timers created, but no data goes out), Active (working normally) and Finalized (terminal; it only waits for the object to be destroyed).
  • 转换与回调：configure（Unconfigured → Inactive，调用 on_configure）、activate（Inactive → Active，on_activate）、deactivate（Active → Inactive，on_deactivate）、cleanup（Inactive → Unconfigured，on_cleanup）、shutdown（从三个非终态都可以 → Finalized，on_shutdown）。每个转换执行期间节点处在对应的过渡状态：Configuring、Activating、Deactivating、CleaningUp、ShuttingDown，以及出错时的 ErrorProcessing。
  • Transitions and callbacks: configure (Unconfigured → Inactive, calls on_configure), activate (Inactive → Active, on_activate), deactivate (Active → Inactive, on_deactivate), cleanup (Inactive → Unconfigured, on_cleanup) and shutdown (from any of the three non-terminal states → Finalized, on_shutdown). While a transition runs, the node is in the matching transition state: Configuring, Activating, Deactivating, CleaningUp, ShuttingDown, plus ErrorProcessing on errors.
  • 返回值决定落点：回调返回 CallbackReturn::SUCCESS，到达目标状态；返回 FAILURE，回到出发的主状态（例如配置失败仍是 Unconfigured，可以改参数再试）；返回 ERROR 或抛出异常，进入 ErrorProcessing 并调用 on_error：它返回 SUCCESS 则回到 Unconfigured，否则进入 Finalized。
  • The return value decides where it lands: if a callback returns CallbackReturn::SUCCESS the node reaches the goal state; with FAILURE it goes back to the primary state it started from (a failed configure stays Unconfigured, so you can fix a parameter and try again); with ERROR, or an exception, it enters ErrorProcessing and on_error is called: if that returns SUCCESS the node goes back to Unconfigured, otherwise to Finalized.
  • 外部接口：每个 lifecycle 节点自动提供 ~/change_state、~/get_state、~/get_available_states、~/get_available_transitions 等服务（类型在 lifecycle_msgs 包），并在 ~/transition_event 话题上发布每次转换。ros2 lifecycle nodes、list、get、set /node configure 就是这些服务的客户端。
  • External interface: every lifecycle node automatically offers services such as ~/change_state, ~/get_state, ~/get_available_states and ~/get_available_transitions (types in the lifecycle_msgs package), and publishes each transition on the ~/transition_event topic. ros2 lifecycle nodes, list, get and set /node configure are clients of these services.
  • LifecyclePublisher：create_publisher 在 lifecycle 节点上返回的是 rclcpp_lifecycle::LifecyclePublisher。它在 Inactive 时也存在、也能被订阅端发现，但 publish() 不会发出任何东西（并打印一条警告）；只有被激活后才真正发布。安全的写法是在 on_activate 里显式调用 pub_->on_activate()，在 on_deactivate 里调用 pub_->on_deactivate()。较新版本的基类 LifecycleNode::on_activate 可能会自动激活所管理的实体，请查文档。
  • LifecyclePublisher: on a lifecycle node, create_publisher returns an rclcpp_lifecycle::LifecyclePublisher. It exists while Inactive and subscribers can discover it, but publish() sends nothing (and logs a warning); it really publishes only once activated. The safe pattern is to call pub_->on_activate() explicitly in on_activate and pub_->on_deactivate() in on_deactivate. In newer versions the base class LifecycleNode::on_activate may activate the managed entities automatically; check the docs.

它向系统保证了什么。设想一个导航栈：地图服务、定位、规划器、控制器。拉起它的「管理者」（Nav2 的 lifecycle manager 就是一个，Phase 6）要的是：

What it guarantees to the system. Picture a navigation stack: a map server, localisation, a planner and a controller. The “manager” bringing it up (Nav2’s lifecycle manager is one, Phase 6) needs:

  1. 可观察的就绪：状态由节点自己通过 ~/get_state 报告，不靠猜「进程起来几秒了」。概念 2 的进程事件给不了这个。
  2. Observable readiness: the node itself reports its state through ~/get_state, with no guessing from “the process has been up for a few seconds”. The process events of concept 2 cannot give this.
  3. 两阶段启动：先把所有节点 configure（分配内存、打开设备、加载地图、建发布者），全部成功后再一起 activate。于是没有哪个节点会在它的上游还没准备好时就开始发布，也不会有订阅者先收到半个系统的数据。慢而且可能失败的事集中在 configure，激活本身应该又快又不失败。
  4. Two-phase start-up: first configure every node (allocate memory, open devices, load the map, create publishers), and only when all succeed activate them together. So no node starts publishing while its upstream is not ready, and no subscriber sees data from half a system. The slow, failure-prone work is gathered into configure, and activation itself should be quick and not fail.
  5. 可恢复的失败：配置失败是一个明确的返回值，节点停在 Unconfigured，管理者可以报错、改参数后重试，不必杀进程。deactivate 让一个节点暂停而不丢掉已配置的资源，例如在重新定位时暂停控制器。
  6. Recoverable failure: a failed configure is an explicit return value, the node stays Unconfigured, and the manager can report it, change parameters and retry without killing a process. deactivate pauses a node without dropping its configured resources, for example pausing the controller during relocalisation.
这些保证是约定，不是强制：状态机只保证回调按规则被调用、状态按规则转换。如果你在构造函数里就建定时器并发布，或者在 on_activate 里做耗时几秒的事，状态机不会拦你，但「Inactive 不产生数据」「激活很快」就不再成立。launch 里也可以用 launch_ros.actions.LifecycleNode 和状态转换事件自动驱动它（请查文档）；本页实验用 CLI 手动驱动，看得最清楚。
These guarantees are a convention, not enforcement: the state machine guarantees only that callbacks are called and states change by the rules. If you create a timer and publish from the constructor, or do several seconds of work in on_activate, the machine will not stop you, but “Inactive produces no data” and “activation is quick” stop being true. Launch can also drive it automatically with launch_ros.actions.LifecycleNode and state-transition events (check the docs); the lab on this page drives it by hand with the CLI, which shows it most clearly.

5. 组合：component 与组件容器

5. Composition: components and the component container

「一个节点一个进程」隔离好、调试简单，但每个进程都有自己的 DDS participant、自己的发现流量、自己的线程，进程之间的每条消息都要序列化、穿过内核、再反序列化。组合让你在部署时而不是写代码时决定进程边界：

“One node per process” isolates well and is easy to debug, but every process has its own DDS participant, its own discovery traffic and its own threads, and every message between processes is serialized, crosses the kernel and is deserialized. Composition lets you decide process boundaries at deployment time rather than when writing the code:

  • component：一个继承 rclcpp::Node、构造函数只接受 const rclcpp::NodeOptions & 的类，编译进一个共享库，在源文件末尾用 RCLCPP_COMPONENTS_REGISTER_NODE(ns::Class) 注册。CMake 里的 rclcpp_components_register_node(target PLUGIN "ns::Class" EXECUTABLE name) 把它登记进 ament 资源索引，并顺便生成一个同名的独立可执行文件，所以同一个类既能单独运行，也能被装进容器。
  • A component is a class deriving from rclcpp::Node whose constructor takes only const rclcpp::NodeOptions &, compiled into a shared library and registered at the end of its source file with RCLCPP_COMPONENTS_REGISTER_NODE(ns::Class). In CMake, rclcpp_components_register_node(target PLUGIN "ns::Class" EXECUTABLE name) records it in the ament resource index and also generates a standalone executable of that name, so the same class can run on its own or be loaded into a container.
  • 组件容器：ros2 run rclcpp_components component_container 启动一个进程，里面有一个名为 /ComponentManager 的节点和一个执行器。它提供 ~/_container/load_node、unload_node、list_nodes 服务（类型在 composition_interfaces）。ros2 component load /ComponentManager pkg ns::Class 调用 load_node：容器从资源索引找到库，用 dlopen 把它映射进自己的地址空间，通过 class_loader 构造这个类，再把新节点加进自己的执行器。ros2 component list 和 ros2 component unload 分别列出和卸载。
  • The component container: ros2 run rclcpp_components component_container starts a process holding one node named /ComponentManager and one executor. It offers the ~/_container/load_node, unload_node and list_nodes services (types in composition_interfaces). ros2 component load /ComponentManager pkg ns::Class calls load_node: the container finds the library in the resource index, maps it into its own address space with dlopen, constructs the class through class_loader, and adds the new node to its executor. ros2 component list and ros2 component unload list and unload.
  • 容器的变体：component_container 用单线程执行器；component_container_mt 用多线程执行器；component_container_isolated 给每个组件一个独立的执行器。三者的线程模型和参数请查文档。无论哪种，Phase 2 的规则都成立：同一个容器里的所有回调共享这些执行器线程，一个慢回调会拖住同线程的其他节点。
  • Container variants: component_container uses a single-threaded executor; component_container_mt uses a multithreaded executor; component_container_isolated gives each component its own executor. Check the docs for their thread models and options. Whichever you use, the rules of Phase 2 hold: every callback in a container shares those executor threads, and one slow callback holds up the other nodes on the same thread.
  • 在 launch 里组合：ComposableNodeContainer(name=…, namespace=…, package='rclcpp_components', executable='component_container', composable_node_descriptions=[ComposableNode(package=…, plugin='ns::Class', name=…, extra_arguments=[{'use_intra_process_comms': True}])])。每个 ComposableNode 也接受 parameters、remappings 和 namespace，与 Node 动作相同。
  • Composing in launch: ComposableNodeContainer(name=…, namespace=…, package='rclcpp_components', executable='component_container', composable_node_descriptions=[ComposableNode(package=…, plugin='ns::Class', name=…, extra_arguments=[{'use_intra_process_comms': True}])]). Each ComposableNode also takes parameters, remappings and namespace, as the Node action does.
和 Kernel Engineering 的连接：组合把三个进程变成一个进程里的三组线程，/proc/PID/maps 里能看到三个组件的 .so 都映射在同一个地址空间。代价是隔离：一个组件段错误，整个容器连同其他组件一起死掉；一个组件写坏了内存，别的组件也会受影响。这是进程隔离（Kernel Phase 1）和共享地址空间之间的老权衡。
The connection to Kernel Engineering: composition turns three processes into three sets of threads in one process, and /proc/PID/maps shows all three components’ .so files mapped into the same address space. The price is isolation: if one component segfaults, the whole container dies with every other component in it; if one corrupts memory, the others are affected too. It is the old trade-off between process isolation (Kernel Phase 1) and a shared address space.

6. 进程内通信：为什么能省掉序列化，什么时候仍要拷贝

6. Intra-process communication: why it skips serialization, and when it still copies

只把节点装进同一个进程，消息默认仍然走 rmw 和 DDS：发布者序列化成 CDR 字节，DDS 投递给同一 participant 里的 reader，订阅端再反序列化。DDS 实现可能在进程内走捷径，但序列化这一步省不掉，因为 DDS 只认识字节（Phase 3）。进程内通信（intra-process communication）是 rclcpp 在 DDS 之上加的一条旁路：

Merely loading nodes into one process does not change the default: messages still go through rmw and DDS. The publisher serializes to CDR bytes, DDS delivers them to a reader in the same participant, and the subscriber deserializes. A DDS implementation may take a shortcut inside the process, but serialization cannot be skipped, because DDS only knows bytes (Phase 3). Intra-process communication is a bypass that rclcpp adds above DDS:

  1. 两个节点都用 rclcpp::NodeOptions().use_intra_process_comms(true) 创建（容器里是 extra_arguments 或 ros2 component load … -e use_intra_process_comms:=true）。同一个 context 里有一个 intra-process manager，记录哪些发布者和订阅者在同一个进程、同一个话题上，并且都开了这个选项。
  2. Both nodes are created with rclcpp::NodeOptions().use_intra_process_comms(true) (in a container, via extra_arguments or ros2 component load … -e use_intra_process_comms:=true). One intra-process manager per context records which publishers and subscriptions are in the same process, on the same topic, with the option enabled.
  3. 发布时，rclcpp 把消息对象本身（一个 C++ 指针）交给 manager，manager 把它放进每个进程内订阅者自己的缓冲区，再触发一个 guard condition 叫醒执行器（Phase 2）。订阅回调拿到的是同一块内存。没有 CDR 编码，没有 socket，没有内核里的拷贝。
  4. On publish, rclcpp hands the message object itself (a C++ pointer) to the manager, which puts it into each intra-process subscription’s own buffer and triggers a guard condition to wake the executor (Phase 2). The subscription callback receives the same memory. No CDR encoding, no socket, no copy in the kernel.
  5. 如果这个话题在其他进程里也有订阅者，rclcpp 仍会照常经 DDS 发一份序列化的副本给它们；进程内旁路只服务本进程的订阅者。
  6. If the topic also has subscribers in other processes, rclcpp still sends them a serialized copy through DDS as usual; the intra-process bypass serves only subscribers in this process.

零拷贝的条件（以 Jazzy 的 rclcpp 文档和源码为准，作者没有逐条核对，请查文档）：用 publish(std::unique_ptr<Msg>) 交出所有权，并且只有一个订阅者、它的回调接收 std::unique_ptr，所有权直接移交，零拷贝；订阅者都接收 const 的 shared 指针时，大家共享同一份；既有要所有权的订阅者又有别的订阅者时，manager 必须为前者拷贝；用 publish(const Msg &) 发布时，rclcpp 先拷贝一份才能交出去。另外，进程内通信对 QoS 有限制（例如 history 必须是 keep last，durability 的支持情况请查文档），而且这是 rclcpp 的特性，rclpy 没有对应的旁路。

Conditions for zero copy (per Jazzy’s rclcpp docs and source; the author did not verify each case, so check the docs): publishing with publish(std::unique_ptr<Msg>) hands over ownership, and with exactly one subscriber whose callback takes a std::unique_ptr, ownership moves straight across with zero copies; when all subscribers take a const shared pointer, they share one copy; when a subscriber that wants ownership coexists with others, the manager must copy for it; and publishing with publish(const Msg &) makes rclcpp copy once before it can hand anything over. Intra-process communication also restricts QoS (history must be keep last, for example; check the docs for durability support), and it is an rclcpp feature: rclpy has no matching bypass.

为什么这能显著降低延迟：一张 1 MB 的图像走 DDS，要做一次序列化（遍历并拷贝 1 MB）、一次或多次穿过内核（UDP 回环要分片，共享内存传输也有拷贝和通知）、一次反序列化（再拷贝 1 MB 并分配内存），还要唤醒 DDS 的接收线程。进程内只传一个指针，代价与消息大小基本无关。消息越大，差别越大；对几个字节的消息，差别主要来自省掉的线程切换。Lab B 用 1 MB 消息量这个差别。
Why this cuts latency so much: a 1 MB image over DDS needs one serialization (walk and copy 1 MB), one or more trips through the kernel (UDP loopback fragments it, and shared-memory transport also copies and notifies), one deserialization (copy 1 MB again and allocate), and a wake-up of the DDS receive thread. Intra-process passes one pointer, at a cost that hardly depends on message size. The larger the message, the larger the gap; for a message of a few bytes the gap comes mostly from the thread switches saved. Lab B measures this gap with 1 MB messages.

    #include <chrono>
#include <memory>
#include <string>

#include "rclcpp/rclcpp.hpp"
#include "rclcpp_lifecycle/lifecycle_node.hpp"
#include "std_msgs/msg/string.hpp"

using CallbackReturn = rclcpp_lifecycle::node_interfaces::LifecycleNodeInterface::CallbackReturn;

class ManagedTalker : public rclcpp_lifecycle::LifecycleNode
{
public:
  ManagedTalker()
  : LifecycleNode("managed_talker")
  {
    declare_parameter("period_ms", 500);   // 构造函数里只声明，不建资源
  }

  CallbackReturn on_configure(const rclcpp_lifecycle::State &) override
  {
    const auto period_ms = get_parameter("period_ms").as_int();
    if (period_ms <= 0) {
      RCLCPP_ERROR(get_logger(), "period_ms must be positive, got %ld", period_ms);
      return CallbackReturn::FAILURE;      // 回到 Unconfigured
    }
    pub_ = create_publisher<std_msgs::msg::String>("chatter", 10);
    timer_ = create_wall_timer(std::chrono::milliseconds(period_ms), [this]() {tick();});
    RCLCPP_INFO(get_logger(), "configured: publisher and timer exist, nothing goes out yet");
    return CallbackReturn::SUCCESS;
  }

  CallbackReturn on_activate(const rclcpp_lifecycle::State &) override
  {
    pub_->on_activate();
    RCLCPP_INFO(get_logger(), "activated");
    return CallbackReturn::SUCCESS;
  }

  CallbackReturn on_deactivate(const rclcpp_lifecycle::State &) override
  {
    pub_->on_deactivate();
    RCLCPP_INFO(get_logger(), "deactivated");
    return CallbackReturn::SUCCESS;
  }

  CallbackReturn on_cleanup(const rclcpp_lifecycle::State &) override
  {
    timer_.reset();
    pub_.reset();
    count_ = 0;
    RCLCPP_INFO(get_logger(), "cleaned up");
    return CallbackReturn::SUCCESS;
  }

  CallbackReturn on_shutdown(const rclcpp_lifecycle::State & state) override
  {
    timer_.reset();
    pub_.reset();
    RCLCPP_INFO(get_logger(), "shut down from %s", state.label().c_str());
    return CallbackReturn::SUCCESS;
  }

private:
  void tick()
  {
    auto msg = std::make_unique<std_msgs::msg::String>();
    msg->data = "managed hello " + std::to_string(count_++);
    pub_->publish(std::move(msg));     // Inactive 时不发出，只打印警告
  }

  rclcpp_lifecycle::LifecyclePublisher<std_msgs::msg::String>::SharedPtr pub_;
  rclcpp::TimerBase::SharedPtr timer_;
  size_t count_ = 0;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<ManagedTalker>();
  rclcpp::spin(node->get_node_base_interface());   // lifecycle 节点用基础接口 spin
  rclcpp::shutdown();
  return 0;
}

    }
  }

自测

Self-check

1. 参数文件的键是 /robot1/blackboard:，launch 时用了 ns:=robot2。会发生什么？

1. The parameter file’s key is /robot1/blackboard:, and the system is launched with ns:=robot2. What happens?

YAML 顶层键按节点全名（命名空间 + 节点名）匹配，不匹配的段落被静默忽略。a 错：launch 不校验参数文件里的节点是否存在；c 错：匹配包括命名空间，要跨命名空间得用通配写法。Top-level YAML keys match the node’s full name (namespace + node name), and sections that do not match are silently ignored. a is wrong: launch does not check whether the nodes in a parameter file exist; c is wrong: matching includes the namespace, and crossing namespaces needs a wildcard form.

2. 一个 lifecycle 节点的 on_configure 因为参数不合法返回了 CallbackReturn::FAILURE。节点现在在哪个状态？

2. A lifecycle node’s on_configure returns CallbackReturn::FAILURE because a parameter is invalid. Which state is the node in now?

FAILURE 表示「这次转换没做成」，节点回到出发的主状态。b 错：进入 ErrorProcessing 的是 ERROR 或异常，不是 FAILURE；a 错：只有 shutdown 或 on_error 失败才会到 Finalized。FAILURE means “this transition did not happen”, and the node returns to the primary state it started from. b is wrong: ERROR or an exception leads to ErrorProcessing, not FAILURE; a is wrong: only shutdown or a failing on_error leads to Finalized.

3. 两个 component 被装进同一个 component_container，加载时没有设置 use_intra_process_comms。一张 1 MB 的图像从一个传到另一个，走的是哪条路？

3. Two components are loaded into the same component_container without setting use_intra_process_comms. Which path does a 1 MB image take from one to the other?

进程内旁路是 rclcpp 的可选特性，两端都要开启；不开时消息照常走 DDS，DDS 只认识字节，所以序列化省不掉。a 错：同一地址空间只是让旁路可能，不会自动启用；c 错：DDS 路径在同一进程里同样能用，Lab B 的模式 2 就是这样。The intra-process bypass is an optional rclcpp feature that both ends must enable; without it messages go through DDS as usual, and DDS only knows bytes, so serialization cannot be skipped. a is wrong: sharing an address space only makes the bypass possible; it is not turned on automatically; c is wrong: the DDS path works within one process too, which is mode 2 of Lab B.

4. 一个 launch 文件用 OnProcessStart 在地图服务进程启动后再启动规划器，可规划器有时一开始拿不到地图。最根本的原因是什么？

4. A launch file uses OnProcessStart to start the planner after the map server process starts, yet the planner sometimes gets no map at first. What is the root cause?

launch 看得见进程，看不见节点内部的状态，所以「进程起来了」不等于「准备好了」。b 错：事件处理器里的动作会执行，这正是 Lab A 里关机的机制；c 错：进程事件与节点用什么语言写无关，它们来自 launch 对子进程的监视。Launch sees processes, not the state inside a node, so “the process is up” does not mean “ready”. b is wrong: actions in event handlers do run, which is how Lab A shuts down; c is wrong: process events have nothing to do with the node’s language; they come from launch watching its child processes.
