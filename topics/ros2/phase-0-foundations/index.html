在写第一个节点之前，先看清 ROS 2 到底由什么组成：它不是操作系统，而是一层跑在 Linux 进程里的中间件，加上一套命令行工具和一个软件包生态。这一阶段从「一次 publish() 一路落到内核 UDP socket」的分层讲起，再讲 ROS 1 的 master 为什么被 DDS 发现机制取代、发行版和 LTS 怎么选、工作空间的 overlay / underlay 是怎么靠环境变量叠起来的，最后在容器里用 ss 和 ps -T 看中间件在操作系统层面到底做了什么。

Before writing a first node, get clear on what ROS 2 is actually made of: it is not an operating system but a middleware layer running inside Linux processes, plus a set of command-line tools and a package ecosystem. This phase starts with the layer stack, following one publish() all the way down to a kernel UDP socket; then it covers why the ROS 1 master was replaced by DDS discovery, how distributions and LTS releases are chosen, and how workspace overlays and underlays are stacked through environment variables; finally, inside the container, you use ss and ps -T to see what the middleware really does at the OS level.

核心概念

Core concepts

1. ROS 2 是什么：中间件 + 工具 + 生态，不是操作系统

1. What ROS 2 is: middleware + tools + ecosystem, not an operating system

名字里有 OS，但 ROS 2 不管理 CPU、内存和设备。一个运行中的 ROS 2 系统就是若干普通的 Linux 进程，每个进程里有一个或多个节点（node）；节点之间通过有名字、有类型的话题（topic）、服务（service）和动作（action）交换消息。这些节点和连接合起来叫 ROS graph。ROS 2 提供的是三样东西：

The name contains OS, but ROS 2 does not manage the CPU, memory or devices. A running ROS 2 system is a set of ordinary Linux processes, each holding one or more nodes; nodes exchange messages over named, typed topics, services and actions. The nodes and their connections together are called the ROS graph. What ROS 2 provides is three things:

  • 中间件：客户端库（rclcpp、rclpy）和它们下面的通信层，负责发现对方、序列化消息、按 QoS 投递。
  • Middleware: the client libraries (rclcpp, rclpy) and the communication layer beneath them, which find peers, serialize messages and deliver them according to QoS.
  • 工具：ros2 命令行、RViz2（3D 可视化）、rqt（GUI 插件）、ros2 bag（录制与回放）、ros2 launch。
  • Tools: the ros2 command line, RViz2 (3D visualisation), rqt (GUI plugins), ros2 bag (record and replay), ros2 launch.
  • 生态：成千上万个按统一约定打包的软件包（Nav2、ros2_control、slam_toolbox……），由构建农场编成 ros-jazzy-* 这样的 apt 包；约定本身写在 REP（ROS Enhancement Proposal）里。
  • Ecosystem: thousands of packages following shared conventions (Nav2, ros2_control, slam_toolbox…), built by the build farm into apt packages named like ros-jazzy-*; the conventions themselves are written down in REPs (ROS Enhancement Proposals).

真正让节点跑起来的还是内核：哪个回调线程下一个上 CPU 由 Linux 调度器决定，消息走的是内核的 UDP socket 或共享内存，电机和传感器靠内核驱动。所以这门课会一直把内核放在视野里。

What actually makes the nodes run is still the kernel: the Linux scheduler decides which callback thread gets the CPU next, messages travel through kernel UDP sockets or shared memory, and motors and sensors are reached through kernel drivers. That is why this course keeps the kernel in view throughout.

2. 从 ROS 1 到 ROS 2：去掉 master，换成 DDS

2. From ROS 1 to ROS 2: the master is gone, DDS takes its place

ROS 1 的机制：先启动 roscore，它运行 master（一个 XML-RPC 服务器，默认 http://localhost:11311，由 ROS_MASTER_URI 指定）、参数服务器和 rosout。每个节点启动时向 master 注册「我发布 /chatter」或「我订阅 /chatter」；master 把发布者的地址告诉订阅者，之后两个节点直接建 TCP 连接（TCPROS）传数据。master 只做名字查找，但它是单点：master 不在，新节点就找不到彼此；所有机器还必须指向同一个 master。

How ROS 1 works: you start roscore first, which runs the master (an XML-RPC server, by default http://localhost:11311, set by ROS_MASTER_URI), the parameter server and rosout. Each node registers with the master on start-up (“I publish /chatter” or “I subscribe to /chatter”); the master tells subscribers the publisher’s address, and the two nodes then open a direct TCP connection (TCPROS) for the data. The master only does name lookup, but it is a single point: without it new nodes cannot find each other, and every machine must point at the same master.

ROS 2 的机制：没有 master。每个 ROS 2 进程创建一个 DDS participant，按 RTPS 协议周期性地向多播地址发布「我在这里」（participant 发现，SPDP），然后彼此交换各自有哪些 writer 和 reader、什么类型、什么 QoS（endpoint 发现，SEDP）。话题名和类型对上、QoS 兼容，就直接点对点传数据。发现是分布式的，谁先启动都行，任何一个进程退出都不影响其他进程互相发现。

How ROS 2 works: there is no master. Each ROS 2 process creates one DDS participant, which, following the RTPS protocol, periodically announces “I am here” to a multicast address (participant discovery, SPDP); participants then exchange which writers and readers they have, with what types and what QoS (endpoint discovery, SEDP). When topic name and type match and the QoS is compatible, data flows directly peer to peer. Discovery is distributed: start order does not matter, and any process exiting does not stop the others from finding each other.

ros2 daemon 不是 master。它只是一个常驻后台的进程，替 ros2 命令行保持在 graph 里、缓存发现结果，好让 ros2 node list 立刻返回；节点之间的通信完全不经过它，把它停掉（ros2 daemon stop）节点照样互通。
ros2 daemon is not a master. It is just a long-running background process that stays in the graph on behalf of the ros2 command line and caches discovery results, so that ros2 node list returns immediately; communication between nodes never passes through it, and with it stopped (ros2 daemon stop) nodes still talk to each other.

换成 DDS 之后顺带得到的东西：

What came along with the switch to DDS:

  • QoS：可靠或尽力而为、历史深度、持久性等按每个话题设置（Phase 3）。ROS 1 只有 TCP 一种「可靠」语义。
  • QoS: reliable or best effort, history depth, durability and so on, set per topic (Phase 3). ROS 1 has only the single “reliable” semantics of TCP.
  • 安全：SROS2 建立在 DDS-Security 之上，提供认证、加密和访问控制（Phase 3）。ROS 1 没有内置安全。
  • Security: SROS2 builds on DDS-Security for authentication, encryption and access control (Phase 3). ROS 1 has no built-in security.
  • 实时意图：rclcpp 的设计允许在实时线程里使用（可控的内存分配、执行器），但 ROS 2 本身不让程序变成实时的，还要靠内核的 SCHED_FIFO、PREEMPT_RT 和你自己的写法（Phase 2）。
  • Real-time intent: rclcpp is designed so it can be used from real-time threads (controlled memory allocation, executors), but ROS 2 does not make a program real-time by itself; that still takes the kernel’s SCHED_FIFO, PREEMPT_RT and your own coding discipline (Phase 2).
  • Python 3 与现代 C++：rclpy 只支持 Python 3（24.04 上是 3.12），rclcpp 用 C++17。ROS 1 直到最后一个发行版 Noetic 才转到 Python 3。
  • Python 3 and modern C++: rclpy supports only Python 3 (3.12 on 24.04), and rclcpp uses C++17. ROS 1 moved to Python 3 only in its last distribution, Noetic.

ROS 1 的最后一个发行版 Noetic 已于 2025 年 5 月停止支持，新项目都应该用 ROS 2。

Noetic, the last ROS 1 distribution, reached end of life in May 2025; new projects should all use ROS 2.

3. 发行版与 LTS

3. Distributions and LTS

一个发行版是一组一起冻结、一起测试、一起发布的软件包版本，绑定到特定的操作系统版本（支持的平台和等级见 REP 2000）。同一发行版里只做兼容的修复，不会突然改 API；跨发行版则可能有破坏性变化。所以「装哪个发行版」决定了包名（ros-jazzy-*）、安装路径（/opt/ros/jazzy）和你能用的 Gazebo 版本。

A distribution is a set of package versions frozen, tested and released together, bound to a particular operating-system release (REP 2000 lists the supported platforms and tiers). Within one distribution only compatible fixes land and APIs do not suddenly change; across distributions there may be breaking changes. So “which distribution you install” determines the package names (ros-jazzy-*), the install path (/opt/ros/jazzy) and the Gazebo version you can use.

  • 节奏：每年 5 月发布一个，名字按字母顺序；近几个偶数年的是 LTS，支持 5 年；奇数年的非 LTS 大致支持 1.5 年。另有一直滚动更新的开发版 Rolling。
  • Cadence: one release each May, named in alphabetical order; the recent even-year releases are LTS with 5 years of support; the odd-year non-LTS releases are supported for roughly 1.5 years. There is also Rolling, a development distribution that is updated continuously.
  • 本课固定在 Jazzy Jalisco：LTS，2024-05-23 发布，2029 年 5 月停止支持，跑在 Ubuntu 24.04 arm64 上，推荐搭配 Gazebo Harmonic。
  • This course is pinned to Jazzy Jalisco: LTS, released 2024-05-23, end of life May 2029, running on Ubuntu 24.04 arm64, with Gazebo Harmonic as the recommended simulator.
  • 更新的 LTS 是 Lyrical Luth（2026-05-22 发布，2031 年 5 月停止支持，Ubuntu 26.04，搭配 Gazebo Jetty）；Kilted Kaiju（2025-05-23）不是 LTS，2026 年 12 月停止支持。以上于 2026-10-31 按官方 Releases 页核对。
  • The newest LTS is Lyrical Luth (released 2026-05-22, end of life May 2031, Ubuntu 26.04, paired with Gazebo Jetty); Kilted Kaiju (2025-05-23) is not LTS and ends in December 2026. All of this was checked against the official Releases page on 2026-10-31.

Jazzy is chosen because Gazebo Harmonic, Nav2 and the books cited on this page all target it, so the material is most complete. 4. 分层结构：一次 publish 从节点落到内核

4. The layer stack: one publish from the node down to the kernel

跟着 talker 的一次 publisher->publish(msg) 往下走：

Follow one publisher->publish(msg) in the talker downwards:

  1. 用户节点：你的代码，定时器回调里填好一条 std_msgs/msg/String 然后 publish。
  2. User node: your code; a timer callback fills in a std_msgs/msg/String and publishes it.
  3. rclcpp / rclpy：各语言的客户端库，提供 Node、publisher、执行器（executor）和回调这些符合语言习惯的对象。rclpy 通过一个 C 扩展模块调用下一层，所以 Python 和 C++ 节点在线上完全一样。
  4. rclcpp / rclpy: the per-language client libraries, offering idiomatic objects such as Node, publishers, executors and callbacks. rclpy calls the next layer through a C extension module, so Python and C++ nodes are identical on the wire.
  5. rcl（C）：各语言共用的那部分逻辑——名字和重映射、graph 查询、参数、时间、日志——这样每种语言不必各写一遍。它不直接碰中间件。
  6. rcl (C): the logic shared by every language — names and remapping, graph queries, parameters, time, logging — so each language does not have to rewrite it. It does not touch the middleware directly.
  7. rmw（ROS middleware interface，C API）：ROS 需要中间件做的最小功能集合（创建 publisher、发布、等待、查询 graph）。具体实现是一个可替换的库：Jazzy 默认 rmw_fastrtps_cpp，可选 rmw_cyclonedds_cpp、rmw_zenoh_cpp（Zenoh 在各发行版上的支持等级请查官方文档）。用环境变量 RMW_IMPLEMENTATION 选择，节点代码一行都不用改。
  8. rmw (the ROS middleware interface, a C API): the minimum set of things ROS needs from a middleware (create a publisher, publish, wait, query the graph). The implementation is a swappable library: on Jazzy the default is rmw_fastrtps_cpp, with rmw_cyclonedds_cpp and rmw_zenoh_cpp as alternatives (check the docs for Zenoh’s support tier on your distribution). You choose with the RMW_IMPLEMENTATION environment variable without changing a single line of node code.
  9. DDS 或 Zenoh：真正的通信库。rmw_fastrtps_cpp 用消息的 typesupport 代码把它序列化成 CDR 字节，交给 Fast DDS 的 DataWriter，按 RTPS 打包。
  10. DDS or Zenoh: the actual communication library. rmw_fastrtps_cpp uses the message’s typesupport code to serialize it into CDR bytes and hands them to a Fast DDS DataWriter, which wraps them in RTPS.
  11. 操作系统：RTPS 报文经 sendmsg() 写进 UDP socket（跨机器，或同机时的某些配置），或写进共享内存段（Fast DDS 同机时可用共享内存传输，大致在 /dev/shm 下）。
  12. Operating system: the RTPS packet goes into a UDP socket through sendmsg() (across machines, or on one machine in some configurations), or into a shared-memory segment (Fast DDS can use a shared-memory transport between processes on the same host; approximately under /dev/shm).

接收方向反过来：DDS 库自己开的接收线程阻塞在 recvmsg() 上；数据到达时内核唤醒它，它把数据放进 reader 的队列并通知 rmw；你的执行器线程原本睡在 rcl / rmw 的 wait set 上，被唤醒后才调用你的回调。所以一个只写了单线程代码的节点，进程里也会有好几个线程。

Receiving runs the other way: a receive thread started by the DDS library blocks in recvmsg(); when data arrives the kernel wakes it, it puts the data into the reader’s queue and notifies rmw; your executor thread, which was asleep on the rcl / rmw wait set, is woken and only then calls your callback. That is why a node whose code is single-threaded still has several threads in its process.

和 Kernel Engineering 的连接：这些线程每一个都是一个 task_struct，阻塞时进入睡眠，被唤醒后由 EEVDF 决定何时上 CPU——机制见 Kernel Phase 1 的概念 2（线程模型）和概念 4（调度）；回调延迟里有一部分就是这段「唤醒到真正运行」的调度延迟，Phase 2 会量它。DDS 内部队列用锁保护、线程之间用 futex 等待和唤醒，共享内存传输也要靠同步原语，这些在 Kernel Phase 3 讲（那里覆盖锁、futex 和 UNIX domain socket；UDP socket 的内核路径课程没有单独展开）。
The connection to Kernel Engineering: each of these threads is a task_struct that sleeps while blocked and, once woken, runs when EEVDF decides — the mechanism is in concepts 2 (the thread model) and 4 (scheduling) of Kernel Phase 1; part of callback latency is exactly this wake-up-to-running scheduling delay, which Phase 2 measures. Inside DDS the queues are protected by locks, threads wait and wake through futexes, and the shared-memory transport also depends on synchronisation primitives; these are covered in Kernel Phase 3 (which covers locks, futexes and UNIX domain sockets; the kernel path of UDP sockets is not covered separately in that course).

5. 工作空间、overlay 与 underlay、colcon、ament、package.xml

5. Workspaces, overlays and underlays, colcon, ament, package.xml

一个包（package）就是一个带 package.xml 的目录。package.xml（format 3，REP 149）写名字、版本、许可证、依赖，以及 <export><build_type>：ament_cmake（C++，CMake 加 ament 的宏）或 ament_python（Python，setuptools）。ament 是这两种构建类型和它们的约定；colcon 是在它们之上的元构建工具：

A package is a directory with a package.xml. package.xml (format 3, REP 149) records the name, version, licence, dependencies, and <export><build_type>: ament_cmake (C++, CMake plus ament macros) or ament_python (Python, setuptools). ament is these build types and their conventions; colcon is the meta build tool on top of them:

  1. 在 src/ 下找出所有包，读每个 package.xml 的依赖，排成拓扑顺序（被依赖的先构建，互不依赖的并行）。
  2. It finds every package under src/, reads the dependencies in each package.xml, and sorts them topologically (dependencies are built first, independent packages in parallel).
  3. 对每个包调用它自己的构建系统，中间产物放在 build/<pkg>，日志放在 log/。
  4. It invokes each package’s own build system, with intermediate output in build/<pkg> and logs in log/.
  5. 把每个包安装到自己的前缀 install/<pkg>，并生成 install/setup.bash 和 install/local_setup.bash。--symlink-install 用符号链接代替复制，改 Python 文件和 launch 文件不用重新构建。
  6. It installs each package into its own prefix install/<pkg> and generates install/setup.bash and install/local_setup.bash. --symlink-install uses symbolic links instead of copies, so editing Python and launch files needs no rebuild.

overlay 与 underlay 全靠环境变量。source /opt/ros/jazzy/setup.bash 把这个前缀加进 AMENT_PREFIX_PATH、PATH、PYTHONPATH 等（大致还有 LD_LIBRARY_PATH）；这就是 underlay。source ~/ws/install/setup.bash 先重新 source 构建时所在的 underlay，再把工作空间里每个包的前缀加到前面；这就是 overlay。local_setup.bash 只加工作空间自己，不碰 underlay。

Overlays and underlays are entirely environment variables. source /opt/ros/jazzy/setup.bash adds that prefix to AMENT_PREFIX_PATH, PATH, PYTHONPATH and so on (approximately also LD_LIBRARY_PATH); that is the underlay. source ~/ws/install/setup.bash first re-sources the underlay that was active at build time, then adds every package prefix of the workspace in front of it; that is the overlay. local_setup.bash adds only the workspace itself and leaves the underlay alone.

ros2 pkg list 和 ros2 run 怎么找到包？靠 ament 资源索引：每个装好的包在 share/ament_index/resource_index/packages/ 下放一个以包名命名的空文件。工具按 AMENT_PREFIX_PATH 的顺序逐个前缀去看这个目录，先找到的算数——所以 overlay 里的同名包会遮住 underlay 里的。没有数据库，只有文件和路径顺序。

How do ros2 pkg list and ros2 run find packages? Through the ament resource index: each installed package places an empty file named after itself in share/ament_index/resource_index/packages/. The tools look in that directory under each prefix in AMENT_PREFIX_PATH order, and the first hit wins — so a package of the same name in the overlay shadows the one in the underlay. There is no database, only files and path order.

官方教程的规则：在一个没有 source 过这个 overlay 的终端里构建，在另开的新终端里 source overlay。在同一个终端里一边 source overlay 一边构建，可能把 overlay 自己当成 underlay，造成难查的问题。
The rule from the official tutorial: build in a terminal that has not sourced this overlay, and source the overlay in a new, separate terminal. Building in a terminal where the overlay is sourced can make the overlay act as its own underlay and cause hard-to-trace problems.

Further reading: the chapter on packages and workspaces in Renard, ROS 2 From Scratch; the chapters introducing ROS 2 and workspaces in Martín Rico, A Concise Introduction to Robot Programming with ROS2; the official Creating a workspace.

6. ros2 命令行与 ROS_DOMAIN_ID

6. The ros2 CLI and ROS_DOMAIN_ID

ros2 是一个 Python 程序，子命令（node、topic、service、param、pkg、run、doctor……）都是插件。查询 graph 的命令要么问 ros2 daemon，要么自己临时加入 graph 当一个 participant 等发现结果（多数 list 类命令有 --no-daemon 选项，以 --help 为准）。它们看到的只是发现协议告诉它们的东西：刚启动的节点要过一小会儿才出现，退出的节点也可能晚一点才消失。

ros2 is a Python program whose subcommands (node, topic, service, param, pkg, run, doctor…) are all plugins. Commands that query the graph either ask ros2 daemon or briefly join the graph as a participant themselves and wait for discovery results (most list commands accept --no-daemon; check --help). They only see what the discovery protocol tells them: a node that just started takes a moment to appear, and one that exited may linger a little.

ROS_DOMAIN_ID（默认 0）就是 DDS 的 domain 编号。不同 domain 的 participant 用不同的 UDP 端口，所以根本看不到彼此。端口按 RTPS port formula（DDS-RTPS 规范的默认端口公式，常数 PB = 7400、DG = 250、PG = 2，偏移 d0 = 0、d1 = 10、d2 = 1、d3 = 11）计算，d 是 domain ID，p 是这台机器上该 domain 的第几个 participant（从 0 开始）：

ROS_DOMAIN_ID (default 0) is the DDS domain number. Participants in different domains use different UDP ports, so they simply cannot see each other. Ports follow the RTPS port formula (the default port mapping in the DDS-RTPS specification, with constants PB = 7400, DG = 250, PG = 2 and offsets d0 = 0, d1 = 10, d2 = 1, d3 = 11), where d is the domain ID and p is the index of the participant in that domain on this machine (from 0):

  • 发现多播端口 = 7400 + 250 × d；用户数据多播端口 = 7400 + 250 × d + 1。
  • Discovery multicast port = 7400 + 250 × d; user-data multicast port = 7400 + 250 × d + 1.
  • 发现单播端口 = 7400 + 250 × d + 10 + 2 × p；用户数据单播端口 = 7400 + 250 × d + 11 + 2 × p。
  • Discovery unicast port = 7400 + 250 × d + 10 + 2 × p; user-data unicast port = 7400 + 250 × d + 11 + 2 × p.
  • 例：domain 0 的第一个进程用 7400、7401 和 7410、7411；domain 1 用 7650、7651，第一个进程的单播是 7660、7661（与 Jazzy 文档的例子一致）。
  • Example: the first process in domain 0 uses 7400 and 7401 plus 7410 and 7411; domain 1 uses 7650 and 7651, with 7660 and 7661 as the first process’s unicast ports (matching the example in the Jazzy docs).

后果都能从公式推出来：端口是 16 位，所以 domain ID 最大 232；Linux 的临时端口范围默认是 32768–60999，官方建议在 Linux 上取 0–101，避开它；每个进程一个 participant、各占两个单播端口，一台机器上同一 domain 超过大约 120 个 ROS 2 进程，就会溢出到下一个 domain 的端口。来源：Jazzy 文档 The ROS_DOMAIN_ID（2026-10-31 核对）。实际打开哪些端口还取决于 rmw 和配置，例如 Fast DDS 同机通信可能走共享内存，Lab B 以实际输出为准。

The consequences all follow from the formula: ports are 16-bit, so the largest domain ID is 232; the default Linux ephemeral port range is 32768–60999, and the docs recommend 0–101 on Linux to stay clear of it; each process is one participant taking two unicast ports, so more than about 120 ROS 2 processes in one domain on one machine spill into the next domain’s ports. Source: the Jazzy docs page The ROS_DOMAIN_ID (checked 2026-10-31). Which ports are actually opened also depends on the rmw and its configuration — for example Fast DDS may use shared memory on one host — so in Lab B the real output wins.

domain 只是隔离，不是安全：同一局域网、同一 domain ID 的任何机器都能看到并订阅你的话题。要防的是别人而不是误撞，就要用 SROS2（Phase 3）；只想限制在本机，Jazzy 有 ROS_AUTOMATIC_DISCOVERY_RANGE（Phase 3）。
A domain is isolation, not security: any machine on the same LAN with the same domain ID can see and subscribe to your topics. To guard against other people rather than accidents you need SROS2 (Phase 3); to stay on the local host only, Jazzy has ROS_AUTOMATIC_DISCOVERY_RANGE (Phase 3).

动手实验

Hands-on labs

Lab A · 第一个 graph 与第一个工作空间

Lab A · A first graph and a first workspace

  1. 在宿主机上按实验环境页启动容器并进入 shell，然后确认发行版。如果提示 ros2: command not found，说明这个 shell 还没 source underlay：On the host, start the container and open a shell as described on the lab environment page, then confirm the distribution. If you get ros2: command not found, this shell has not sourced the underlay yet:
    ./lab.sh up                        # 宿主机：启动容器
./lab.sh shell                     # 宿主机：进入容器
source /opt/ros/jazzy/setup.bash   # 容器里
printenv ROS_DISTRO                # 应输出 jazzy
printenv RMW_IMPLEMENTATION        # 没设置时为空，表示用默认的 rmw_fastrtps_cpp
  2. 终端 1 运行 talker；在宿主机另开一个终端，再 ./lab.sh shell 进同一个容器，运行 listener。listener 应该打印 I heard: [Hello World: N]：In terminal 1 run the talker; open another terminal on the host, run ./lab.sh shell again to enter the same container, and run the listener. The listener should print I heard: [Hello World: N]:
    # 终端 1
ros2 run demo_nodes_cpp talker
# 终端 2
source /opt/ros/jazzy/setup.bash
ros2 run demo_nodes_cpp listener
  3. 在第三个终端里检查 graph。注意 /talker 除了 /chatter 还发布了 /rosout（日志）和 /parameter_events，并提供一组参数服务——这些是每个 rclcpp 节点自带的：Inspect the graph from a third terminal. Notice that besides /chatter, /talker also publishes /rosout (logging) and /parameter_events, and offers a set of parameter services — every rclcpp node comes with these:
    ros2 node list
ros2 node info /talker
ros2 topic list
ros2 topic info /chatter     # 发布者数量和订阅者数量
ros2 topic echo /chatter     # Ctrl+C 停止
ros2 daemon status           # CLI 用的缓存进程，不是 master
  4. 运行 ros2 doctor，在报告里找出平台、rmw 中间件名和网络接口那几段。报告的分段名称以实际输出为准：Run ros2 doctor and find the sections for the platform, the rmw middleware name and the network interfaces. Go by the section names in the actual output:
    ros2 doctor --report | less
  5. 建一个工作空间和一个空的 Python 包并构建。ros2 pkg create 会生成 package.xml、setup.py、setup.cfg、resource/my_pkg（资源索引的标记文件）和同名 Python 包目录：Create a workspace and an empty Python package, then build it. ros2 pkg create generates package.xml, setup.py, setup.cfg, resource/my_pkg (the marker file for the resource index) and a Python package directory of the same name:
    mkdir -p ~/ws/src
cd ~/ws/src
ros2 pkg create --build-type ament_python my_pkg
cd ~/ws
colcon build --symlink-install
ls                                 # build  install  log  src
  6. 按官方规则另开一个新终端进入容器，source underlay 再 source overlay，看包是从哪个前缀找到的、AMENT_PREFIX_PATH 的顺序是什么：Following the official rule, open a new terminal into the container, source the underlay and then the overlay, and see which prefix the package is found in and what order AMENT_PREFIX_PATH has:
    source /opt/ros/jazzy/setup.bash
source ~/ws/install/setup.bash
ros2 pkg list | grep my_pkg
ros2 pkg prefix my_pkg                       # 应指向 ~/ws/install/my_pkg
printenv AMENT_PREFIX_PATH | tr ':' '\n'     # overlay 在前，/opt/ros/jazzy 在后
ls ~/ws/install/my_pkg/share/ament_index/resource_index/packages/

Lab B · 中间件在操作系统层面做了什么（与内核课程的交叉）

Lab B · What the middleware does at the OS level (crossover with the kernel course)

  1. 装上需要的工具（镜像里可能已有其中一部分；容器里默认是 root）：Install the tools you need (the image may already have some of them; the container runs as root by default):
    apt-get update
apt-get install -y iproute2 procps tcpdump
  2. 后台启动 talker，看它打开的 UDP socket。按 RTPS port formula，domain 0 的第一个 participant 应该出现 7400 附近的发现端口和 7410、7411 附近的单播端口；Fast DDS 实际打开哪些以输出为准：Start the talker in the background and look at the UDP sockets it opens. By the RTPS port formula, the first participant in domain 0 should show the discovery port around 7400 and unicast ports around 7410 and 7411; go by the output for which ports Fast DDS actually opens:
    ros2 run demo_nodes_cpp talker > /dev/null &
sleep 2
ss -ulpn | grep talker
  3. 看多播组成员关系。DDS 用 setsockopt(IP_ADD_MEMBERSHIP) 加入默认的发现多播组 239.255.0.1，内核为这个接口记下组成员：Look at multicast group membership. DDS joins the default discovery multicast group 239.255.0.1 with setsockopt(IP_ADD_MEMBERSHIP), and the kernel records the membership for the interface:
    ip maddr show | grep -B2 239.255.0.1
cat /proc/net/igmp
  4. 数一数 talker 进程里的线程。你没写多线程代码，但 DDS 的接收线程、事件线程和 rclcpp 自己的线程都在这里（数量随 rmw 和版本不同，大致几个到十几个）。wchan 显示每个线程睡在哪个内核函数里，在容器里可能被限制而只显示 0：Count the threads in the talker process. You wrote no multithreaded code, yet the DDS receive threads, event threads and rclcpp’s own threads are all here (the number varies with the rmw and version, roughly a few to a dozen or so). wchan shows which kernel function each thread sleeps in; inside a container it may be restricted and show only 0:
    PID=$(pgrep -x talker)
ps -T -p "$PID" -o spid,comm,stat,pri,ni
grep Threads /proc/$PID/status
for t in /proc/$PID/task/*; do echo "$(cat $t/comm) $(cat $t/wchan)"; done
    对照 Kernel Phase 1：每一行是一个 task_struct，共享同一个 mm，状态 S 表示正在睡眠等待（多半在 recvmsg 或 futex 上）。Compare with Kernel Phase 1: each line is a task_struct sharing the same mm, and state S means it is asleep waiting (most likely in recvmsg or on a futex).
  5. 再启动一个 listener，看第二个 participant 是不是用了 p = 1 的单播端口（7412、7413 附近）；再看 /dev/shm 里有没有 Fast DDS 的共享内存文件（文件名大致带 fastrtps 前缀）：Start a listener as well, and check whether the second participant uses the unicast ports for p = 1 (around 7412 and 7413); then look in /dev/shm for Fast DDS shared-memory files (the names approximately start with fastrtps):
    ros2 run demo_nodes_cpp listener > /dev/null &
sleep 2
ss -ulpn | grep -E 'talker|listener'
ls -l /dev/shm
  6. 换 domain：停掉两个进程，在 domain 7 启动 talker，先算端口再验证：7400 + 250 × 7 = 9150，单播 9160、9161。domain 0 的 listener 收不到，domain 7 的 listener 能收到：Change the domain: stop both processes, start the talker in domain 7, and compute the ports before you check them: 7400 + 250 × 7 = 9150, with unicast 9160 and 9161. A listener in domain 0 hears nothing; a listener in domain 7 does:
    kill %1 %2
ROS_DOMAIN_ID=7 ros2 run demo_nodes_cpp talker > /dev/null &
sleep 2
ss -ulpn | grep talker                          # 期望 9150、9160、9161 附近
ros2 run demo_nodes_cpp listener                # domain 0：没有输出，Ctrl+C
ROS_DOMAIN_ID=7 ros2 run demo_nodes_cpp listener  # domain 7：I heard ...
  7. 可选：抓几个发现报文，看到的就是第 6 层的 RTPS 流量：Optional: capture a few discovery packets; this is the layer 6 RTPS traffic:
    tcpdump -ni any udp port 9150 -c 5
交付物：Lab A 里 printenv AMENT_PREFIX_PATH | tr ':' '\n' 的输出 + Lab B 里 domain 0 和 domain 7 的 ss -ulpn 输出（标出哪个端口是公式里的哪一项）+ talker 的线程数，以及你用自己的话写的「一次 publish 经过哪几层、在哪一层第一次碰到内核」（10 行以内）。
Deliverables: the output of printenv AMENT_PREFIX_PATH | tr ':' '\n' from Lab A + the ss -ulpn output for domain 0 and domain 7 from Lab B (mark which port is which term of the formula) + the talker’s thread count, and your own explanation of “which layers one publish passes through and at which layer it first touches the kernel” (10 lines or fewer).

自测

Self-check

1. 在 ROS 2 里，listener 是怎么找到 talker 的？

1. In ROS 2, how does the listener find the talker?

ROS 2 没有 master，发现是分布式的（SPDP 再 SEDP）。a 是 ROS 1 的机制。ros2 daemon 只替命令行缓存发现结果，节点通信从不经过它，停掉它节点照样互通。ROS 2 has no master; discovery is distributed (SPDP, then SEDP). a is how ROS 1 works. ros2 daemon only caches discovery results for the CLI; node traffic never passes through it, and nodes still talk with it stopped.

2. ROS_DOMAIN_ID=3 时，按 RTPS port formula，participant 发现用的多播端口是多少？

2. With ROS_DOMAIN_ID=3, what is the multicast port used for participant discovery under the RTPS port formula?

发现多播端口 = 7400 + 250 × d = 7400 + 750 = 8150。b 把 domain 当成了直接加在 7400 上的偏移；c 错在 domain 正是通过端口隔离的，多播地址默认都是 239.255.0.1。Discovery multicast port = 7400 + 250 × d = 7400 + 750 = 8150. b treats the domain as an offset added straight to 7400; c is wrong because domains are separated precisely by port, while the multicast address is 239.255.0.1 by default for all of them.

3. 你在 ~/ws 里构建好了 my_pkg，打开一个新终端只 source 了 /opt/ros/jazzy/setup.bash，ros2 run my_pkg … 报找不到包。原因是？

3. You built my_pkg in ~/ws, opened a new terminal and sourced only /opt/ros/jazzy/setup.bash, and ros2 run my_pkg … says the package is not found. Why?

overlay 完全靠环境变量起作用：每个新 shell 都要 source 一次。构建产物还在 install/ 里，不用重编（a 错）；也不该往 underlay 里塞东西（c 错），overlay 的意义就是不碰它。An overlay works entirely through environment variables: every new shell must source it once. The build output is still in install/, so no rebuild is needed (a is wrong); nor should you put things into the underlay (c is wrong) — the point of an overlay is to leave it alone.

4. 哪一层让你能用 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp 把 Fast DDS 换成 Cyclone DDS，而不改节点代码？

4. Which layer lets you replace Fast DDS with Cyclone DDS through RMW_IMPLEMENTATION=rmw_cyclonedds_cpp without changing node code?

rmw 是中间件抽象层：上面的 rcl 只调用 rmw API，具体是 rmw_fastrtps_cpp 还是 rmw_cyclonedds_cpp 由环境变量选。rclcpp 是语言绑定，rcl 是各语言共用的逻辑，两者都不直接接触中间件。rmw is the middleware abstraction: rcl above it calls only the rmw API, and whether that is rmw_fastrtps_cpp or rmw_cyclonedds_cpp is chosen by the environment variable. rclcpp is a language binding and rcl is logic shared across languages; neither touches the middleware directly.
