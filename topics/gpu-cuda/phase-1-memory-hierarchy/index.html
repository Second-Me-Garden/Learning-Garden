A GPU is rarely short of arithmetic; it is short of data. This lesson starts from every kind of memory a thread can use: registers, local, shared, global, constant and texture, with L1 and L2 in between. Then come the two rules that decide bandwidth: how the 32 accesses of a warp combine into 32-byte sectors, and how the 32 banks of shared memory conflict. Shared memory then tiles a matrix multiply and cuts global accesses by the tile width; last come unified and pinned memory between host and device. 核心概念

Core concepts

1. 内存空间：谁能看见、活多久、在哪里

1. Memory spaces: who sees them, how long they live, where they sit

CUDA 的内存空间按两件事区分：作用域（哪些线程能访问）和位置（在 SM 片上还是在片外的显存里）。位置决定速度，作用域决定你能拿它做什么。下面的规格数字来自 CUDA Programming Guide 的 compute capability 附录（v13.4.2，2026-10-31 读取），按本专题的目标 sm_75（T4）给出：

CUDA tells its memory spaces apart by two things: scope (which threads can reach it) and location (on the SM chip or off chip in device memory). Location decides speed; scope decides what you can do with it. The figures below come from the compute-capability appendix of the CUDA Programming Guide (v13.4.2, read 2026-10-31), given for this topic’s target sm_75 (the T4):

  • 寄存器（registers）：每个线程私有，在片上，最快。每个 SM 有 64 K 个 32 位寄存器，每个线程最多 255 个。用得越多，一个 SM 上同时驻留的线程越少（Phase 2 的占用率）。
  • Registers: private to each thread, on chip, the fastest. An SM has 64 K 32-bit registers, and a thread can use at most 255. The more each thread uses, the fewer threads fit on an SM at once (occupancy, Phase 2).
  • local memory：也是每个线程私有，但「local」说的是作用域，不是位置。它在片外的 device memory 里，延迟和带宽与 global 一样。编译器在三种情况下用它：下标不是常量的数组、放不进寄存器的大结构、寄存器不够时的溢出（spilling）。每个线程最多 512 KB。
  • Local memory: also private to each thread, but "local" names its scope, not its place. It lives off chip in device memory, with the same latency and bandwidth as global. The compiler uses it in three cases: arrays indexed by non-constant subscripts, large structures that do not fit in registers, and spills when registers run out. Up to 512 KB per thread.
  • shared memory：一个 block 内的线程共享，在片上，生命周期就是这个 block。它和 L1 是同一块物理存储：sm_75 的统一数据缓存共 96 KB，其中 shared 可配成 32 KB 或 64 KB，每个 SM 和每个 block 最多 64 KB。一个 block 要用超过 48 KB，必须用动态 shared memory 并调用 cudaFuncSetAttribute 显式开启。
  • Shared memory: shared by the threads of one block, on chip, living as long as the block. It is the same physical storage as L1: on sm_75 the unified data cache is 96 KB, of which shared memory can be set to 32 KB or 64 KB, at most 64 KB per SM and per block. A block that needs more than 48 KB must use dynamic shared memory and opt in explicitly with cudaFuncSetAttribute.
  • global memory：所有线程和主机都能访问，在片外的显存里，生命周期由主机的分配决定（cudaMalloc 到 cudaFree）。容量最大、最慢，带宽全靠合并访问（概念 2）。
  • Global memory: reachable by every thread and by the host, off chip in device memory, living from the host’s allocation to its release (cudaMalloc to cudaFree). The largest and the slowest; its bandwidth depends entirely on coalescing (concept 2).
  • constant memory：整个 grid 可读、kernel 只读，用 __constant__ 声明，主机用 cudaMemcpyToSymbol 写入。共 64 KB，每个 SM 的常量缓存工作集 8 KB。一个 warp 的线程读同一个地址时最合适，比如滤波系数。
  • Constant memory: readable by the whole grid and read-only to kernels, declared with __constant__ and written by the host with cudaMemcpyToSymbol. 64 KB in all, with an 8 KB constant-cache working set per SM. It suits the case where the threads of a warp read the same address, such as filter coefficients.
  • texture 和 surface：老代码里常见，因为在早期 GPU 上有性能好处。指南现在的说法是：在所有仍受支持的 GPU 上，普通的 load/store 就能做到，texture 对非纹理数据不再有性能优势。它留给图像采样这类真正的纹理用途。
  • Texture and surface: common in old code, because they paid off on early GPUs. The guide now says that on every supported GPU ordinary loads and stores do the same job, and texture memory no longer gives any performance benefit for non-texture data. It remains for real texture work such as image sampling.
  • L1 和 L2：L1 在每个 SM 上，和 shared 共用物理空间，kernel 不用 shared 时整块都给 L1；L2 在芯片上、所有 SM 共享，大小用 cudaGetDeviceProperties 的 l2CacheSize 查。从 compute capability 6.0 起 global 的读默认经过 L1，但传输单位仍是 32 字节。
  • L1 and L2: L1 sits on each SM and shares its physical space with shared memory, taking all of it when a kernel uses no shared memory; L2 is on the chip and shared by all SMs, its size given by l2CacheSize from cudaGetDeviceProperties. From compute capability 6.0 on, global loads are cached in L1 by default, but the unit of transfer is still 32 bytes.

2. 合并访问：32 次读怎样变成 4 次传输

2. Coalescing: how 32 loads become 4 transactions

指南的原话是：global memory 通过 32 字节的内存传输访问；一个线程要读一个字时，它所在的 warp 会把 32 个线程的请求合并成满足它们所需的最少次数的传输。所以一个线程读 4 字节，实际搬的至少是 32 字节，剩下的 28 字节能不能派上用场，取决于同一个 warp 里别的线程要不要它们。

In the guide’s words, global memory is accessed through 32-byte memory transactions; when a thread asks for a word, its warp combines the requests of all 32 threads into the fewest transactions that serve them. So a thread reading 4 bytes moves at least 32, and whether the other 28 are of any use depends on whether other threads of the same warp want them.

  • 相邻线程读相邻的 float：32 × 4 = 128 字节，对齐时正好 4 个 32 字节 sector，4 次传输，利用率 100%。这就是「一个 warp 一条 128 字节」的来历：128 字节不是一次传输，是 4 个 sector 合起来。
  • Neighbouring threads read neighbouring floats: 32 × 4 = 128 bytes, exactly 4 aligned 32-byte sectors, 4 transactions, 100% use. That is where "one 128-byte line per warp" comes from: 128 bytes is not one transaction but four sectors together.
  • 错开一个 float（没对齐）：128 字节跨过 5 个 sector，5 次传输。Best Practices Guide 的例子里实际带宽只降到约 9/10，因为相邻 warp 会用到彼此多取的缓存内容。
  • Shifted by one float (misaligned): the 128 bytes straddle 5 sectors, 5 transactions. In the Best Practices Guide example the bandwidth only falls to about 9/10, because neighbouring warps reuse what the others over-fetched from the cache.
  • 步长为 s 个 float：步长 2 时 32 个地址分布在 256 字节里，要 8 个 sector，用到 50%；步长到 8（32 字节）时每个线程独占一个 sector，32 次传输共 1024 字节，用到 12.5%。再增大步长，sector 数不再增加（每个线程最多一个），按 sector 规则算的利用率也不再下降（推断：更大的步长还会碰到更多的 DRAM 行和 TLB 项，指南没有给这部分的数字）。
  • A stride of s floats: at stride 2 the 32 addresses spread over 256 bytes and need 8 sectors, 50% used; by stride 8 (32 bytes) every thread has a sector of its own, 32 transactions moving 1024 bytes, 12.5% used. Larger strides add no more sectors (at most one per thread), so by the sector rule the use stops falling (inference: larger strides also touch more DRAM rows and TLB entries, for which the guide gives no figures).

二维数据最容易踩这个坑：按行存储的矩阵，线程沿行走是合并的，沿列走就是步长 n 的跨步访问。Lab B 在这台 M5 上量到了同样的形状：64 MB 拷贝从步长 1 到步长 2 带宽掉到约五分之一，之后每加倍再减半，到步长 16 后不再下降。Apple 没有公开它的传输粒度；拐点落在 8 和 16 个 float 之间，说明粒度在 32 到 64 字节之间（推断）。

Two-dimensional data is where this bites: in a row-major matrix, threads walking along a row are coalesced and threads walking down a column make a stride-n access. Lab B measured the same shape on this M5: for a 64 MB copy the bandwidth fell to about a fifth from stride 1 to stride 2, halved again with each doubling, and stopped falling from stride 16. Apple does not document its transfer granularity; the knee between 8 and 16 floats suggests a granule between 32 and 64 bytes (inference).

3. bank 冲突：shared memory 的 32 条车道

3. Bank conflicts: the 32 lanes of shared memory

shared memory 被分成 32 个 bank，连续的 32 位字依次落在连续的 bank 上，每个 bank 每个时钟周期提供 32 位。所以字节地址 addr 所在的 bank 是 (addr / 4) % 32。一个 warp 的 32 个线程如果各自落在不同的 bank，一个周期全部取完；如果有几个线程访问同一个 bank 的不同地址，这些访问被串行化，带宽按串行的次数下降，这就是 bank 冲突。例外是多个线程读同一个地址：那是广播（broadcast），不算冲突。

Shared memory is divided into 32 banks: successive 32-bit words fall in successive banks, and each bank delivers 32 bits per clock cycle. So byte address addr lives in bank (addr / 4) % 32. If the 32 threads of a warp land in 32 different banks, one cycle serves them all; if several threads hit different addresses in the same bank, those accesses are serialized and bandwidth drops by the number of serial requests. That is a bank conflict. The exception is several threads reading the same address: that is a broadcast, not a conflict.

  • 步长 1 个字：32 个线程落在 32 个 bank，无冲突。步长 2：线程 0 和 16 都在 bank 0，两路冲突。步长 3：3 和 32 互质，32 个线程仍落在 32 个不同的 bank，无冲突。规律：步长为奇数时无冲突，步长含因子 2k 时是 2k 路冲突（最多 32 路）。
  • Stride of 1 word: 32 threads in 32 banks, no conflict. Stride 2: threads 0 and 16 both land in bank 0, a two-way conflict. Stride 3: 3 and 32 are coprime, so the 32 threads still fall in 32 different banks, no conflict. The rule: odd strides are conflict-free, and a stride with a factor of 2k gives a 2k-way conflict (at most 32-way).
  • 最典型的 32 路冲突：__shared__ float t[32][32]，线程 tx 读 t[tx][0]。相邻线程相隔 32 个字，全部落在 bank 0。补一列，声明成 t[32][33]，步长变成 33，对 32 取模等于 1，冲突就消失了。Best Practices Guide 的矩阵转置例子用的正是这一招。
  • The classic 32-way conflict: __shared__ float t[32][32] with thread tx reading t[tx][0]. Neighbouring threads are 32 words apart and all land in bank 0. Add one padding column, t[32][33], and the stride becomes 33, which is 1 modulo 32, so the conflict is gone. The matrix-transpose example in the Best Practices Guide uses exactly this trick.
  • 本课的分块矩阵乘没有冲突（TILE = 16，一个 warp 覆盖两行 ty）：读 As[ty][k] 时同一行的 16 个线程读同一个地址，是广播，两行落在相隔 16 的两个 bank；读 Bs[k][tx] 时 16 个 tx 落在 16 个相邻的 bank，两行读同样的地址，又是广播。
  • The tiled matrix multiply of this lesson is conflict-free (TILE = 16, so one warp covers two rows of ty): reading As[ty][k], the 16 threads of a row read one address, a broadcast, and the two rows fall in two banks 16 apart; reading Bs[k][tx], the 16 values of tx fall in 16 neighbouring banks and the two rows read the same addresses, a broadcast again.

4. 分块矩阵乘与 __syncthreads()

4. Tiled matrix multiply and __syncthreads()

朴素的矩阵乘让每个线程算 C 的一个元素：读 A 的一行 n 个数和 B 的一列 n 个数。整个矩阵一共 2n3 次 global 读，而 A 和 B 合起来只有 2n2 个不同的数，每个数被读了 n 次。分块（tiling）的想法是让一个 block 把 A 和 B 各一块 TILE × TILE 的数据搬进 shared memory，块里的每个数在 shared 里被这个 block 的 TILE 个线程复用。每个 block 沿 k 方向走 n / TILE 步，每步搬两块，于是每个数从 global 读的次数从 n 降到 n / TILE，global 访问少了 TILE 倍。TILE = 16 时少 16 倍；代价是每个 block 2 × 16 × 16 × 4 = 2048 字节的 shared memory。

The naive matrix multiply has each thread compute one element of C, reading a row of n values of A and a column of n values of B. The whole product makes 2n3 global reads, while A and B together hold only 2n2 distinct values, so each one is read n times. Tiling has one block copy a TILE × TILE tile of A and one of B into shared memory, where TILE threads of the block reuse each value. Each block walks along k in n / TILE steps, two tiles per step, so each value is read from global memory n / TILE times instead of n: global accesses drop by the tile width. With TILE = 16 that is 16 times fewer; the price is 2 × 16 × 16 × 4 = 2048 bytes of shared memory per block.

循环里的两个 __syncthreads() 各管一件事。指南的定义是：它让 block 里所有没退出的线程都到达同一个调用点后才继续，并且提供内存顺序，这次调用 happens-before 任何参与线程从等待中放行（Parallel Programming 专题的 Phase 3 讲过 happens-before）。于是：

The two __syncthreads() calls in the loop each guard one thing. The guide defines it as waiting until every non-exited thread of the block reaches the same call, and as providing memory ordering: the call happens-before any participating thread is released from the wait (Phase 3 of Parallel Programming covered happens-before). So:

  • 第一个防「写后读」：所有线程写完 As、Bs 之前，谁也不许开始读。没有它，快的线程会读到还没装进来的旧数据。
  • The first guards read-after-write: nobody starts reading until every thread has written its part of As and Bs. Without it, a fast thread reads stale data that has not arrived yet.
  • 第二个防「读后写」：所有线程用完当前这两块之前，谁也不许进入下一轮去覆盖它们。没有它，快的线程会把下一块写进别人还在读的位置。
  • The second guards write-after-read: nobody moves on to overwrite the tiles until every thread is done with the current pair. Without it, a fast thread writes the next tile over values others are still reading.
  • 它是 block 级的屏障，管不到别的 block，也不能放在只有部分线程会走到的分支里。本课的 kernel 要求 n 是 TILE 的倍数，所以没有线程提前返回。
  • It is a block-level barrier: it says nothing about other blocks, and it must not sit in a branch that only some threads reach. The kernels of this lesson require n to be a multiple of TILE, so no thread returns early.

Metal 里一模一样：threadgroup float As[16][16] 声明 threadgroup memory，threadgroup_barrier(mem_flags::mem_threadgroup) 是 __syncthreads() 的对应物。M5 上实测分块版只比朴素版快约 2 倍，不是 16 倍：global 访问次数确实少了 16 倍，但朴素版的很多重复读本来就被 GPU 缓存接住了，没有真的走到 DRAM（推断；要证实得看缓存命中计数，Phase 4 的内容）。

Metal is the same: threadgroup float As[16][16] declares threadgroup memory, and threadgroup_barrier(mem_flags::mem_threadgroup) is the counterpart of __syncthreads(). On the M5 the tiled version measured only about 2 times faster than the naive one, not 16: global accesses really did drop 16-fold, but the GPU caches already caught many of the naive kernel’s repeated reads before they reached DRAM (inference; proving it takes cache-hit counters, the subject of Phase 4).

5. 统一内存、缺页与 pinned 主机内存

5. Unified memory, page faults and pinned host memory

pinned 内存。malloc、new、mmap 拿到的主机内存是可分页的（pageable）：操作系统可以把它换出到磁盘，也可以搬到别的物理页。cudaMallocHost 分配的是页锁定（page-locked，也叫 pinned）内存。指南写明：异步拷贝必须用 pinned 内存，同步拷贝用它也更快。原因在 DMA：GPU 的拷贝引擎按物理地址直接读主机内存，这要求那些页在拷贝期间不动也不被换出。可分页内存没有这个保证，驱动只好先把数据复制到自己的一块 pinned 中转缓冲区，再从那里 DMA，多了一次主机内的复制。Runtime API 参考的「API synchronization behavior」一页（2026-10-12 版）写明：可分页缓冲区先被复制到用于 DMA 传输的中转内存（staging memory），再传到显存。copy.cu 量的就是这两者的差别。

Pinned memory. Host memory from malloc, new or mmap is pageable: the operating system may swap it to disk or move it to other physical pages. cudaMallocHost allocates page-locked, or pinned, memory. The guide states that asynchronous copies require pinned memory and that synchronous copies are faster with it. The reason is DMA: the copy engine of the GPU reads host memory by physical address, which needs those pages to stay put and stay resident for the whole copy. Pageable memory gives no such promise, so the driver first copies the data into a pinned staging buffer of its own and DMAs from there, one extra copy inside the host. The Runtime API reference page “API synchronization behavior” (2026-10-12 version) says so: “the pageable buffer has been copied to the staging memory for DMA transfer to device memory”. copy.cu measures the difference.

统一内存。cudaMallocManaged 给出一个 CPU 和 GPU 都能用同一个指针访问的分配。在 CPU 和 GPU 各有一套页表的系统上（指南称为 software-coherent，插 PCIe 的独立显卡就是这种），一致性靠缺页维持。一个处理器访问一个物理上在另一边的页时发生缺页，指南列出这时要做的三件事：

Unified memory. cudaMallocManaged returns an allocation that the CPU and the GPU reach through the same pointer. On systems where the CPU and GPU each keep their own page table (the guide calls them software-coherent; a discrete PCIe card is one), coherence is kept by page faults. When one processor touches a page that physically lives on the other side, a fault occurs, and the guide lists three things that then happen:

  1. 让当前拥有这一页的处理器不能再访问它：删掉或改写它那边的页表项。
  2. The processor that currently owns the page loses access to it: its page table entry is deleted or updated.
  3. 让发起访问的处理器能访问它：新建或更新这边的页表项。
  4. The processor asking for it gains access: a page table entry on its side is created or updated.
  5. 把这一页背后的物理页迁移过来。这一步很贵，工作量和页大小成正比。
  6. The physical page behind the virtual page is migrated over. This step is expensive, and its cost grows with the page size.

这和 Kernel Engineering Phase 2 的缺页路径是同一件事，只是「另一边」是 GPU 的显存，迁移走的是 PCIe。所以 CPU 初始化一大块统一内存后第一次在 GPU 上跑 kernel，时间里会混进一连串缺页和迁移；用 cudaMemPrefetchAsync 预先把数据搬过去可以避开它（Phase 6 量这件事）。你的 GPU 支持哪种统一内存，用 cudaDeviceGetAttribute 查 cudaDevAttrConcurrentManagedAccess 和 cudaDevAttrPageableMemoryAccess。

This is the same thing as the page-fault path of Kernel Engineering Phase 2, except that the other side is GPU memory and the migration crosses PCIe. So the first kernel run after the CPU initialises a large unified allocation has a train of faults and migrations mixed into its time; prefetching with cudaMemPrefetchAsync avoids it (Phase 6 measures this). Which form of unified memory your GPU supports is answered by cudaDeviceGetAttribute with cudaDevAttrConcurrentManagedAccess and cudaDevAttrPageableMemoryAccess.

Apple 的统一内存在物理上就是一块：CPU 和 GPU 共用同一组 DRAM。Lab B 用 makeBuffer(length:) 默认的共享存储模式（MTLStorageModeShared），CPU 写进去的数据 GPU 直接读，没有迁移，也没有拷贝。这也是 Lab B 里没有 cudaMemcpy 那一步的原因。

Apple’s unified memory is physically one pool: the CPU and the GPU share the same DRAM. #define TILE 16

// 朴素：每个线程算 C 的一个元素，A 的一行和 B 的一列全部从 global memory 读
__global__ void mm_naive(const float* A, const float* B, float* C, int n) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= n || col >= n) return;
    float acc = 0.0f;
    for (int k = 0; k < n; ++k) acc += A[row * n + k] * B[k * n + col];
    C[row * n + col] = acc;
}

// 分块：block 把 A 和 B 的 TILE x TILE 块搬进 shared memory，每个值在块内被用 TILE 次
// 要求 n 是 TILE 的倍数（main 里检查）
__global__ void mm_tiled(const float* A, const float* B, float* C, int n) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];
    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty, col = blockIdx.x * TILE + tx;
    float acc = 0.0f;
    for (int k0 = 0; k0 < n; k0 += TILE) {
        As[ty][tx] = A[row * n + k0 + tx];      // 相邻 tx 读相邻地址：合并
        Bs[ty][tx] = B[(k0 + ty) * n + col];
        __syncthreads();                        // 块装满之前谁也不许读
        for (int k = 0; k < TILE; ++k) acc += As[ty][k] * Bs[k][tx];
        __syncthreads();                        // 块用完之前谁也不许覆盖
    }
    C[row * n + col] = acc;
}

float median_ms(bool tiled, const float* A, const float* B, float* C, int n) {
    dim3 block(TILE, TILE), grid(n / TILE, n / TILE);
    cudaEvent_t t0, t1;
    CHECK(cudaEventCreate(&t0)); CHECK(cudaEventCreate(&t1));
    std::vector<float> ms;
    for (int r = 0; r < 13; ++r) {              // 前 2 次是预热

        if (tiled) mm_tiled<<<grid, block>>>(A, B, C, n);   // 按名字启动每个 kernel
        else       mm_naive<<<grid, block>>>(A, B, C, n);

        CHECK(cudaEventSynchronize(t1));

        if (r >= 2) ms.push_back(m);
    }
    CHECK(cudaEventDestroy(t0)); CHECK(cudaEventDestroy(t1));
    std::sort(ms.begin(), ms.end());
    return ms[ms.size() / 2];
}

func gpuMs(_ encode: (MTLComputeCommandEncoder) -> Void) -> Double {
    let cb = q.makeCommandBuffer()!
    let enc = cb.makeComputeCommandEncoder()!
    encode(enc)
    enc.endEncoding(); cb.commit(); cb.waitUntilCompleted()
    if let e = cb.error { print("command buffer error: \(e)"); exit(1) }
    return (cb.gpuEndTime - cb.gpuStartTime) * 1000
}

    for _ in 0..<2 { _ = gpuMs(encode) }
    let t = (0..<reps).map { _ in gpuMs(encode) }.sorted()
    return t[reps / 2]
}

Self-check

1. 一个 warp 里线程 i 读 a[2 * i]（float，起点对齐）。这次访问要几个 32 字节的 sector？

1. In a warp, thread i reads a[2 * i] (floats, aligned start). How many 32-byte sectors does the access need?

传输单位是 32 字节，warp 只取它需要的 sector。步长 2 时 32 个地址横跨 256 字节，也就是 8 个 sector，每个 sector 的 8 个 float 只用到 4 个，正好一半。128 字节一条说的是相邻访问时 4 个 sector 合起来的大小，不是固定的取数单位；每个线程独占一个 sector 要到步长 8（32 字节）才发生。The unit is 32 bytes, and the warp fetches only the sectors it needs. At stride 2 the 32 addresses span 256 bytes, which is 8 sectors, and each sector supplies 4 of its 8 floats, exactly half. The 128-byte line is just the size of the 4 sectors that adjacent access touches, not a fixed fetch unit; one sector per thread only happens at stride 8 (32 bytes).

2. __shared__ float t[32][32]，线程 tx（0 到 31）读 t[tx][0]。会发生什么？

2. With __shared__ float t[32][32], thread tx (0 to 31) reads t[tx][0]. What happens?

冲突看的是 bank，不是地址是否不同：(32 × tx) % 32 恒为 0，32 个不同地址挤在同一个 bank，要串行 32 次。广播只在多个线程读同一个地址时发生，第 0 列的 32 个元素是 32 个不同的地址。补一列后步长 33，对 32 取模为 1，每个线程一个 bank。Conflicts are about banks, not about whether addresses differ: (32 × tx) % 32 is always 0, so 32 different addresses crowd into one bank and take 32 serial accesses. A broadcast needs several threads reading the same address, and the 32 elements of column 0 are 32 different addresses. With the padding column the stride is 33, which is 1 modulo 32: one bank per thread.

3. 分块矩阵乘的循环末尾还有第二个 __syncthreads()。去掉它会怎样？

3. The loop of the tiled matrix multiply ends with a second __syncthreads(). What goes wrong without it?

第二个屏障防的是「读后写」：同一块 shared memory 下一轮就要被覆盖。__syncthreads() 只管一个 block 内部，从来不负责跨 block 的可见性，C 的写入也不需要它。硬件并不在每次读之后自动加屏障，正因为如此才要自己写。The second barrier guards write-after-read: the same shared memory is overwritten in the next round. __syncthreads() works only inside one block and never provides visibility across blocks, nor do the writes to C need it. The hardware adds no barrier after each read by itself, which is exactly why you write one.

4. 在插 PCIe 的独立显卡上，CPU 初始化了一块 cudaMallocManaged 内存，然后 GPU 第一次访问其中一页。发生了什么？

4. On a discrete PCIe card, the CPU initialises a cudaMallocManaged allocation, and then the GPU touches one of its pages for the first time. What happens?

在 CPU 和 GPU 各有页表的系统上，统一内存靠缺页维持一致：撤销旧主人的页表项、给新访问者建页表项、迁移物理页，代价和页大小成正比。直接穿过 PCIe 访问主机内存的是另一种机制（mapped pinned memory，零拷贝），不是统一内存的默认行为。分配时也不会整块复制；要提前搬，得自己调用 cudaMemPrefetchAsync。On systems where the CPU and GPU each keep a page table, unified memory keeps coherence with page faults: the old owner’s entry is revoked, an entry is created for the new accessor, and the physical page migrates, at a cost that grows with page size. Reading host memory directly across PCIe is a different mechanism (mapped pinned memory, zero copy), not the default behaviour of unified memory. Nor is the allocation copied when it is made; to move it early you call cudaMemPrefetchAsync yourself.
