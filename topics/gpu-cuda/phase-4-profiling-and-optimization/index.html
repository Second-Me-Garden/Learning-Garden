核心概念

Core concepts

一个 kernel 能跑、结果也对，但它为什么不更快？它可能在等内存带宽，可能把运算单元用满了，也可能两样都没用满、只是在空等。改错了方向就白改：给一个已经计算受限的 kernel 加分块，或者优化一个只占总时间 10% 的 kernel，都省不下多少。需要的是先量出时间花在哪，再对一个 kernel 回答两个问题：它顶着哪一条上限、离那条线还有多远，以及它的 warp 在等什么。

A kernel runs and gives the right answer, but why is it not faster? It may be waiting on memory bandwidth, it may have filled the arithmetic units, or it may be using neither and simply waiting. Changing the wrong thing is wasted work: tiling a kernel that is already compute-bound, or optimising one that is 10% of the total time, saves little. What is needed is to measure first where the time goes, and then answer two questions about one kernel: which ceiling it is up against and how far below it it sits, and what its warps are waiting for.

概念 1 的 nsys 回答时间花在哪，概念 3 的 roofline 回答顶着哪条线，概念 5 的停顿原因回答 warp 在等什么。

nsys in concept 1 answers where the time goes, the roofline of concept 3 answers which line the kernel is against, and the stall reasons of concept 5 answer what its warps wait for.

1. 先看全局，再看一个 kernel：Nsight Systems 与 Nsight Compute

1. The whole program first, then one kernel: Nsight Systems and Nsight Compute

两个工具回答两个层次的问题。Nsight Systems（nsys，本页读的是在线用户指南 v2026.5，比 13.4 Update 2 自带的 2026.3.2 新）画整个程序的时间线：CPU 线程上的 CUDA API 调用、GPU 上的 kernel 和内存拷贝、它们之间的空隙。它回答「时间花在哪」：是 cudaMemcpy 占了大头，是很多小 kernel 每个都在付启动开销，还是一个 kernel 本身就慢。Nsight Compute（ncu，本页读的是 v2026.3.1 的 Profiling Guide 和 CLI 文档）一次只看一个 kernel 的一次启动，把它重放（replay）多遍，每遍收一部分硬件计数器，回答「这个 kernel 为什么慢」。顺序总是先 nsys 后 ncu：如果 kernel 只占总时间的 10%，把它优化到零也只省 10%。

The two tools answer questions at two levels. Nsight Systems (nsys; this page read the online user guide v2026.5, newer than the 2026.3.2 bundled with 13.4 Update 2) draws the whole program on a timeline: CUDA API calls on the CPU threads, kernels and memory copies on the GPU, and the gaps between them. It answers where the time goes: whether cudaMemcpy takes the bulk, whether many small kernels each pay the launch cost, or whether one kernel is simply slow. Nsight Compute (ncu; this page read the v2026.3.1 Profiling Guide and CLI documentation) looks at one launch of one kernel at a time, replays it several times and collects part of the hardware counters on each pass, and answers why this kernel is slow. The order is always nsys first, then ncu: if the kernel is 10% of the total time, optimising it to zero saves only 10%.

  • nsys 的入口：nsys profile --stats=true ./app 录一份 .nsys-rep 报告，并在终端打印默认的一组统计表，其中有 cuda_api_sum（每种 API 调用的总时间）、cuda_gpu_kern_sum（每个 kernel 的总时间和次数）和 cuda_gpu_mem_time_sum（拷贝的时间）；用户指南说它和先 nsys profile 再 nsys stats report1.nsys-rep 给出的信息非常接近。
  • Starting with nsys: nsys profile --stats=true ./app records a .nsys-rep report and prints the default set of summary tables, among them cuda_api_sum (total time per API call), cuda_gpu_kern_sum (total time and count per kernel) and cuda_gpu_mem_time_sum (time in copies); the user guide says this presents very similar information to running nsys profile and then nsys stats report1.nsys-rep.
  • ncu 的入口：不加选项时收集 basic 这组 section；--set full 收全部；--section <名字> 只收指定的 section；-k（--kernel-name）按名字或 regex: 过滤 kernel，-c 限定收集几次启动，-s 先跳过几次；-o 把报告存成文件。编译时加 -lineinfo，报告才能把计数器对应到源代码行。
  • Starting with ncu: with no options it collects the basic set of sections; --set full collects all of them; --section <name> collects only the named ones; -k (--kernel-name) filters kernels by name or by regex:, -c limits how many launches are collected, -s skips some first; -o saves the report to a file. Build with -lineinfo so the report can map counters to source lines.
  • 为什么两个工具的时长不一样：Profiling Guide 列了几条原因。ncu 默认锁定 SM 时钟（CLI 文档写明 --clock-control 的默认值是 boost），nsys 不锁；ncu 默认在每遍重放之间清空所有 GPU 缓存，nsys 只跑一遍、不清缓存；ncu 把 kernel 启动串行化，nsys 不串行。所以 ncu 的 gpu__time_duration 适合比较同一个 kernel 的两个版本，不适合直接当作程序里的真实时间；要和 nsys 对照，文档建议先用 nvidia-smi 在外部锁频，再给 ncu 加 --clock-control none。
  • Why the two tools disagree on duration: the Profiling Guide lists several reasons. ncu locks the SM clocks by default (the CLI documentation gives boost as the default of --clock-control), while nsys does not; ncu flushes all GPU caches between replay passes by default, while nsys runs once and flushes nothing; ncu serialises kernel launches, nsys does not. So ncu’s gpu__time_duration is good for comparing two versions of one kernel, not for reading off the time inside the real program; to compare with nsys, the guide recommends locking clocks externally with nvidia-smi and passing --clock-control none to ncu.

2. Reading an ncu report: top down

Profiling Guide 的 section 表给每个 section 一个标识符（命令行里用）和一个显示名（报告里看到的）。按下面的顺序读，每一步都在缩小范围：

The section table of the Profiling Guide gives each section an identifier (used on the command line) and a display name (seen in the report). Read them in this order; each step narrows the search:

  1. SpeedOfLight（GPU Speed Of Light Throughput）：计算和访存两侧各自达到理论最大值的百分比，比如 sm__throughput.avg.pct_of_peak_sustained_elapsed。哪一侧高，瓶颈就在哪一侧；两侧都低，说明 kernel 既没喂饱计算单元也没用满带宽，多半是延迟受限（概念 4）。
  2. SpeedOfLight (GPU Speed Of Light Throughput): the percentage of the theoretical maximum reached on the compute side and on the memory side, such as sm__throughput.avg.pct_of_peak_sustained_elapsed. Whichever side is high is where the bottleneck is; if both are low, the kernel neither feeds the compute units nor fills the bandwidth, and is most likely latency-bound (concept 4).
  3. Occupancy 和 LaunchStats：理论 occupancy 与实际达到的 occupancy，以及是哪一项在限制理论值（launch__occupancy_limit_registers、launch__occupancy_limit_shared_mem、launch__occupancy_limit_blocks、launch__occupancy_limit_warps）。指南说，理论和实际相差很大，通常意味着负载很不均衡。这就是 Phase 2 对照表的实测版。
  4. Occupancy and LaunchStats: theoretical against achieved occupancy, and which item limits the theoretical value (launch__occupancy_limit_registers, launch__occupancy_limit_shared_mem, launch__occupancy_limit_blocks, launch__occupancy_limit_warps). The guide says a large gap between theoretical and achieved usually indicates a highly imbalanced workload. This is the measured version of Phase 2’s comparison table.
  5. SchedulerStats：每个调度器手里的 warp 池：理论上限、活动的（Active）、可以发射的（Eligible），以及没有任何 warp 可发射、发射槽被跳过的周期。指南的原话：跳过的发射槽多，说明延迟没藏住。这就是 Phase 2 动画 (a) 里那个空转的周期 7。
  6. SchedulerStats: each scheduler’s pool of warps: the theoretical bound, the active ones, the eligible ones that can issue, and the cycles in which no warp was eligible and the issue slot was skipped. In the guide’s words, many skipped issue slots indicate poor latency hiding. This is the idle cycle 7 of Phase 2’s diagram (a).
  7. WarpStateStats 和 SourceCounters：warp 在各种状态里花的周期（每条已发射指令平均几个周期），以及按源代码行采样到的停顿原因。概念 5 逐个讲。指南提醒：只有调度器不能每周期都发射时，才值得看停顿原因。
  8. WarpStateStats and SourceCounters: the cycles warps spend in each state (on average, per issued instruction), and stall reasons sampled per source line. Concept 5 goes through them. The guide warns: only look at stall reasons if the schedulers fail to issue every cycle.
  9. MemoryWorkloadAnalysis 和 ComputeWorkloadAnalysis：前者细看 L1、L2、DRAM 和 shared memory 各自的流量和命中率（含 bank 冲突），后者看每条运算流水线的利用率。上面几步指到哪一侧，就打开哪一个。
  10. MemoryWorkloadAnalysis and ComputeWorkloadAnalysis: the first looks closely at the traffic and hit rates of L1, L2, DRAM and shared memory (bank conflicts included), the second at the utilisation of each arithmetic pipeline. Open whichever side the steps above pointed to.

3. GPU 上的 roofline

3. The roofline on the GPU

roofline 和 Parallel Programming Phase 7 里 CPU 上的那张图是同一个模型（Williams、Waterman、Patterson，2009）：横轴是 arithmetic intensity（每搬一个字节做几次浮点运算，FLOP/byte），纵轴是 FLOP/s，两条线围出上限。左边斜线是内存带宽：intensity 乘带宽；右边平线是峰值算力；两线交点叫 ridge point。点落在 ridge 左边是访存受限，右边是计算受限，点到线的距离就是还能提升的空间（Profiling Guide，「Roofline Charts」）。换到 GPU 上，数字变了，道理不变。T4 的数来自 NVIDIA 的 T4 产品页（2026-10-31 读取）：

The roofline is the same model as the CPU chart in Parallel Programming Phase 7 (Williams, Waterman and Patterson, 2009): the horizontal axis is arithmetic intensity (floating-point operations per byte moved, FLOP/byte), the vertical axis is FLOP/s, and two lines bound what is possible. The slope on the left is memory bandwidth, intensity times bandwidth; the flat line on the right is peak compute; where they meet is the ridge point. A point left of the ridge is memory-bound, right of it compute-bound, and the distance from a point to its line is the room left for improvement (Profiling Guide, “Roofline Charts”). On a GPU the numbers change and the reasoning does not. The T4’s figures come from NVIDIA’s T4 product page (read 2026-10-31):

  • 三个峰值：FP32 8.1 TFLOP/s，FP16/FP32 混合精度（Tensor Core）65 TFLOP/s，GDDR6 带宽「320+ GB/s」。这些是厂商标称的峰值，不是实测；实测带宽一般会低一些，Lab A 用 ncu 量你那台卡。
  • Three peaks: 8.1 TFLOP/s FP32, 65 TFLOP/s mixed FP16/FP32 precision (tensor cores), and “320+ GB/s” of GDDR6 bandwidth. These are the vendor’s rated peaks, not measurements; measured bandwidth is usually somewhat lower, and Lab A measures your card with ncu.
  • ridge 在哪（从上面的数算出）：FP32 是 8100 / 320 ≈ 25 FLOP/byte，FP16 Tensor Core 是 65000 / 320 ≈ 203 FLOP/byte。也就是说，一个 FP32 kernel 每从 DRAM 读一个 float（4 字节）要做大约 100 次运算才能摸到算力上限；Tensor Core 把平线抬高了 8 倍，ridge 也右移了 8 倍，对数据复用的要求更高。
  • Where the ridge is (computed from the figures above): 8100 / 320 ≈ 25 FLOP/byte for FP32, and 65000 / 320 ≈ 203 FLOP/byte for FP16 tensor cores. So an FP32 kernel has to do about 100 operations for every float (4 bytes) it reads from DRAM to reach the compute ceiling; tensor cores raise the flat line 8 times and move the ridge 8 times further right, which demands even more reuse of data.
  • 三个矩阵乘的「代码上的」intensity（推算，按 kernel 里写的 global 读次数算）：朴素版每次 FMA（2 次运算）读 2 个 float（8 字节），0.25 FLOP/byte；Phase 1 的 TILE = 16 分块版每步搬 2 × 16 × 16 个 float（2048 字节）做 2 × 163 = 8192 次运算，4 FLOP/byte；Lab A 的 mm_reg 用 64 × 64 的块、每步搬 2 × 64 × 16 个 float（8192 字节）做 2 × 64 × 64 × 16 = 131072 次运算，16 FLOP/byte。在 T4 上，对应的上限分别是 80 GFLOP/s、1.28 TFLOP/s 和 5.1 TFLOP/s。
  • The intensity of the three matrix multiplies, as written (derived by counting the global loads in each kernel): the naive kernel reads 2 floats (8 bytes) per FMA (2 operations), 0.25 FLOP/byte; Phase 1’s TILE = 16 version moves 2 × 16 × 16 floats (2048 bytes) per step for 2 × 163 = 8192 operations, 4 FLOP/byte; Lab A’s mm_reg uses 64 × 64 blocks and moves 2 × 64 × 16 floats (8192 bytes) per step for 2 × 64 × 64 × 16 = 131,072 operations, 16 FLOP/byte. On a T4 the matching ceilings are 80 GFLOP/s, 1.28 TFLOP/s and 5.1 TFLOP/s.

  1. 工作量：C 有 1024 × 1024 个元素，每个做 1024 次 FMA，每次 FMA 算 2 次运算，一共约 21.5 亿次浮点运算。三个 kernel 的工作量一样，不同的只是每搬一个字节做几次运算。
  2. 朴素版：0.25 × 320 = 80 GFLOP/s，在 ridge（约 25）左边，上限由斜线给出，最快 26.8 ms（图解 (a) 第 3 步）。
  3. 分块版：intensity 涨 16 倍到 4，上限 1.28 TFLOP/s，最快 1.68 ms，时间下限也正好缩短 16 倍（第 4 步）。它仍在斜线上，所以再优化也还是在跟带宽较劲。
  4. mm_reg：16 × 320 = 5.12 TFLOP/s，仍低于 8.1 的平线，最快 0.42 ms（第 5 步）。intensity 要到约 25 FLOP/byte 才会被平线挡住，那时下限是 0.27 ms；在那之前，提高 intensity 每一步都直接换成时间。
  5. Lab A 量出真实时间后，把实测 GFLOP/s 除以对应的上限，就得到离线还有多远。实测可能超过这里的上限，因为缓存挡掉了重复读（下一段，以及 Lab B 在 M5 上看到的情形）。
  1. The work: C has 1024 × 1024 elements, each takes 1024 FMAs, and each FMA counts as 2 operations, about 2.15 billion floating-point operations in all. The three kernels do the same work; they differ only in operations per byte moved.
  2. Naive: 0.25 × 320 = 80 GFLOP/s, left of the ridge at about 25, so the slope sets the ceiling and the fastest possible run is 26.8 ms (step 3 of diagram (a)).
  3. Tiled: intensity rises 16 times to 4, the ceiling to 1.28 TFLOP/s, and the floor to 1.68 ms, exactly 16 times shorter (step 4). It is still on the slope, so any further work on it is still a fight with bandwidth.
  4. mm_reg: 16 × 320 = 5.12 TFLOP/s, still under the flat line at 8.1, for a floor of 0.42 ms (step 5). Only at about 25 FLOP/byte does the flat line take over, with a floor of 0.27 ms; until then every gain in intensity turns straight into time.
  5. Once Lab A has measured real times, divide each measured GFLOP/s by its ceiling to see how far below the line it sits. A measurement may beat the ceiling here, because caches absorb repeated loads (the next paragraph, and what Lab B saw on the M5).

代码上的 intensity 不等于 DRAM 上的：上面的算法假设每次 global 读都到了 DRAM。实际上 L1 和 L2 会挡掉很多重复读，真实的 DRAM 字节更少，真实 intensity 更高。Lab B 在 M5 上正好看到这一点：朴素版按「每次读都到内存」和 Phase 1 量到的约 134 GB/s 拷贝带宽算，上限只有约 34 GFLOP/s，实测却是 372 GFLOP/s，高出约 11 倍，所以大部分读一定被缓存挡住了（推断）。这就是为什么 ncu 的 roofline 用的是实测的 DRAM 字节，而且有分层的 roofline（SpeedOfLight_HierarchicalSingleRooflineChart 等），把 L1、L2、DRAM 三条带宽线画在一起；指南说，点贴着 DRAM 线时，缓存效率往往就是限制。

Intensity as written is not intensity at DRAM: the arithmetic above assumes every global load reaches DRAM. In practice L1 and L2 absorb many repeated loads, so the real DRAM bytes are fewer and the real intensity is higher. Lab B sees exactly this on the M5: counting every load as a memory access and using the copy bandwidth of about 134 GB/s measured in Phase 1, the naive kernel’s ceiling would be only about 34 GFLOP/s, yet it measured 372 GFLOP/s, about 11 times higher, so most of its loads must be caught by caches (an inference). This is why ncu’s roofline uses measured DRAM bytes, and why there are hierarchical rooflines (SpeedOfLight_HierarchicalSingleRooflineChart and others) that draw the L1, L2 and DRAM bandwidth lines together; the guide says that when a point sits at the DRAM line, cache efficiency is often what limits it.

4. 访存受限、计算受限和延迟受限

4. Memory-bound, compute-bound and latency-bound

roofline 只画了两种受限，ncu 的读法里实际有三种，改法各不相同：

The roofline draws two kinds of bound; reading ncu you meet three, each with its own fix:

  • 访存受限（memory-bound）：SpeedOfLight 里访存一侧接近峰值，点贴着斜线。办法只有两条：少搬字节（分块复用、合并访问、更小的数据类型），或者每个字节多做运算（提高 intensity，点沿斜线往右上走）。
  • Memory-bound: the memory side of SpeedOfLight is near its peak and the point sits on the slope. There are only two ways out: move fewer bytes (reuse through tiling, coalescing, smaller data types), or do more operations per byte (raise the intensity, so the point climbs the slope to the right).
  • 计算受限（compute-bound）：计算一侧接近峰值，点贴着平线，常见的停顿是 Math Pipe Throttle。换更快的运算：FP16 和 Tensor Core（概念 6）、更合适的指令组合；或者少算。
  • Compute-bound: the compute side is near its peak, the point sits under the flat line, and the common stall is Math Pipe Throttle. Use faster arithmetic: FP16 and tensor cores (concept 6), a better instruction mix; or compute less.
  • 延迟受限（latency-bound）：两侧都远离峰值，点在两条线下面很远，SchedulerStats 里跳过的发射槽很多。warp 在等，却没有足够的活动 warp 或独立指令把等待盖住。Profiling Guide 对 Long Scoreboard 的说明讲得很清楚：它占主导时，kernel 是访存延迟受限，不一定是带宽受限；带宽没用满时，优先选藏延迟的改法：ILP、循环展开、流水化，或提高 occupancy（Phase 2）。
  • Latency-bound: both sides are far from their peaks, the point is far below both lines, and SchedulerStats shows many skipped issue slots. Warps are waiting, and there are not enough active warps or independent instructions to cover the wait. The Profiling Guide’s note on Long Scoreboard puts it plainly: when it dominates, the kernel is memory-latency-bound, which is not necessarily bandwidth-bound; when bandwidth is not saturated, prefer latency-hiding changes such as ILP, unrolling or pipelining, or raise occupancy (Phase 2).

5. warp 停顿原因

5. Warp stall reasons

ncu 周期性地采样每个调度器里 warp 的状态，把样本记到 warp 正在等待的那条指令上。Profiling Guide 的「Warp Stall Reasons」一节列出每种原因的指标名（smsp__pcsamp_warps_issue_stalled_*）和改法。它同时给了三条读法：selected 和 not_selected 是调度状态，不是真正的停顿；目标是提高发射槽的利用率，不是把每个计数器压到零；样本记在等待数据的那条指令（消费者）上，不是产生数据的那条，要回到源代码和 SASS 里找根因。最常见的几种：

ncu periodically samples the state of the warps in each scheduler and charges each sample to the instruction the warp is waiting at. The “Warp Stall Reasons” part of the Profiling Guide lists each reason with its metric name (smsp__pcsamp_warps_issue_stalled_*) and what to change. It also gives three reading rules: selected and not_selected are scheduler states, not true stalls; the target is issue-slot utilisation, not driving every counter to zero; and samples are charged to the instruction waiting on the data (the consumer), not the one producing it, so look in the source and the SASS for the root cause. The most common ones:

  • Long Scoreboard（..._long_scoreboard）：在等一次 L1TEX 操作（local、global、surface、texture）的结果。朴素矩阵乘的典型停顿：每次 FMA 都在等两个 global 读。改法：合并访问、提高缓存命中、把常用数据放进 shared memory（Phase 1 的分块），或者用 ILP 盖住等待。
  • Long Scoreboard (..._long_scoreboard): waiting on the result of an L1TEX operation (local, global, surface, texture). The typical stall of the naive matrix multiply: every FMA waits on two global loads. Fixes: coalescing, better cache hit rates, moving frequently used data into shared memory (Phase 1’s tiling), or ILP to cover the wait.
  • Barrier（..._barrier）：在 __syncthreads() 等同一个 block 里别的 warp。指南说，屏障本身很便宜，样本多半积在先到的 warp 上，在等落后的那几个；block 有 512 个或更多线程时，可以考虑拆小。
  • Barrier (..._barrier): waiting at __syncthreads() for the other warps of the block. The guide says barriers themselves are cheap when warps arrive together; most samples pile up on the fast warps waiting for stragglers, and blocks of 512 threads or more are worth splitting.
  • MIO Throttle 与 Short Scoreboard（..._mio_throttle、..._short_scoreboard）：MIO 指令队列满了，或在等一次 MIO 操作（主要是 shared memory，也包括特殊数学函数和动态分支）的结果。分块矩阵乘每次 FMA 要从 shared memory 读两个数，很容易落到这里（推断，Lab A 验证）。改法：更宽、更少的 shared 读，或者在寄存器里复用，让每个 shared 读喂好几次 FMA，这就是 mm_reg 的做法；Short Scoreboard 高时先查 bank 冲突。
  • MIO Throttle and Short Scoreboard (..._mio_throttle, ..._short_scoreboard): the MIO instruction queue is full, or a warp is waiting on the result of an MIO operation (mostly shared memory, also special math functions and dynamic branches). The tiled matrix multiply reads two values from shared memory per FMA and can easily land here (an inference; Lab A checks it). Fixes: fewer, wider shared loads, or reuse in registers so that each shared load feeds several FMAs, which is what mm_reg does; when Short Scoreboard is high, check bank conflicts first.
  • Math Pipe Throttle（..._math_pipe_throttle）：所有活动 warp 的下一条指令都要用同一条已经满载的运算流水线。指南说它占主导时，kernel 通常是计算流水线受限。
  • Math Pipe Throttle (..._math_pipe_throttle): the next instruction of every active warp needs the same oversubscribed arithmetic pipeline. The guide says that when it dominates, the kernel is usually compute-pipeline-bound.
  • 其他：LG Throttle（global 和 local 访存指令太密，常见于寄存器溢出）、Wait（固定延迟的依赖，比如相互依赖的 FFMA 之间 4 个周期，通常只在已经很优化的 kernel 里排第一）、No Instructions（指令缓存缺失，或 grid 不足一波的很短的 kernel）。
  • Others: LG Throttle (global and local memory instructions too dense, common with register spills), Wait (a fixed-latency dependency, such as the 4 cycles between dependent FFMAs, usually on top only in already well-optimised kernels), No Instructions (instruction-cache misses, or very short kernels with less than one full wave).

6. Tensor Core 与 wmma

6. Tensor cores and wmma

Tensor Core 是 SM 里专做小矩阵乘加 D = A × B + C 的单元。Turing Tuning Guide：每个 Turing SM 有 8 个 Tensor Core；它们支持半精度矩阵乘，A 和 B 是 FP16，C 和 D 可以是 FP16 或 FP32，FP32 累加时 FP16 的乘积先算成全精度再用 FP32 加；Turing 还新增了整数矩阵乘，输入可以是 8 位、4 位或 1 位整数，用 32 位整数累加。所以 T4 的 Tensor Core 能吃的浮点输入只有 FP16，另有 INT8 和 INT4，以及只能通过实验性的 wmma::experimental 预览 API 使用的 1 位整数（INT1）。BF16 和 TF32 从 Ampere（sm_80）起才有：Ampere Tuning Guide 写明第三代 Tensor Core 新增 BF16 和 TF32，FP64 则通过 DMMA；编程指南的 Tensor Core 表只在 compute capability 8.0（A100）和后来的一些数据中心型号上标了 FP64，8.6 和 8.9 都没有，所以 L4 没有 FP64 Tensor Core。Ada（sm_89，比如 L4）的第四代 Tensor Core 带上了 Hopper 的 FP8 Transformer Engine。

A tensor core is a unit in the SM that does nothing but small matrix multiply-accumulates D = A × B + C. The Turing Tuning Guide: each Turing SM has 8 tensor cores; they support half-precision matrix multiplication with A and B in FP16 and C and D in FP16 or FP32, and when accumulating in FP32 the FP16 product is formed at full precision and then added in FP32; Turing also adds integer matrix multiplication, with 8-bit, 4-bit or 1-bit integer inputs and 32-bit integer accumulation. So the only floating-point input the T4’s tensor cores take is FP16, alongside INT8 and INT4, plus 1-bit (INT1) through the experimental wmma::experimental preview API. BF16 and TF32 arrive with Ampere (sm_80): the Ampere Tuning Guide says its third-generation tensor cores add BF16 and TF32, and FP64 through DMMA; the programming guide’s tensor-core table marks FP64 only on compute capability 8.0 (A100) and some later data-centre parts, not on 8.6 or 8.9, so an L4 has no FP64 tensor cores. Ada’s fourth-generation tensor cores (sm_89, such as the L4) bring Hopper’s FP8 Transformer Engine.

在 CUDA C++ 里用它最直接的方式是 warp 级矩阵函数（编程指南，「Warp Matrix Functions」，#include <mma.h>，命名空间 nvcuda::wmma）：

The most direct way to use them from CUDA C++ is the warp matrix functions (programming guide, “Warp Matrix Functions”, #include <mma.h>, namespace nvcuda::wmma):

  • fragment：wmma::fragment<Use, m, n, k, T, Layout>，Use 是 matrix_a、matrix_b 或 accumulator。一个 fragment 是分散在整个 warp 32 个线程寄存器里的一块矩阵，元素怎样分布没有规定，以后的架构可能会变。FP16 的形状有 16 × 16 × 16、32 × 8 × 16 和 8 × 32 × 16。
  • fragment: wmma::fragment<Use, m, n, k, T, Layout>, where Use is matrix_a, matrix_b or accumulator. A fragment is a piece of a matrix spread across the registers of all 32 threads of a warp; how the elements are distributed is unspecified and may change in future architectures. The FP16 shapes are 16 × 16 × 16, 32 × 8 × 16 and 8 × 32 × 16.
  • 四个函数：fill_fragment 置初值，load_matrix_sync 从内存读进 fragment，mma_sync 做一次 D = A × B + C，store_matrix_sync 写回内存。带 _sync 的三个都要求整个 warp 的线程都调用、参数一致；条件分支里调用时，条件必须在整个 warp 里一致，否则「很可能挂起」。指针要 256 位对齐，ldm 对 __half 要是 8 的倍数、对 float 要是 4 的倍数（都是 16 字节的倍数）。
  • Four functions: fill_fragment sets initial values, load_matrix_sync reads from memory into a fragment, mma_sync performs one D = A × B + C, and store_matrix_sync writes back to memory. The three _sync functions must be called by every thread of the warp with the same arguments; inside a conditional, the condition must evaluate identically across the warp, or execution is “likely to hang”. Pointers must be 256-bit aligned, and ldm must be a multiple of 8 for __half and of 4 for float (16 bytes in both cases).
  • Ampere 起的类型：__nv_bfloat16 的 fragment 必须配 float 累加器；TF32 要先用 __float_to_tf32 把输入转换好，只支持 16 × 16 × 8；double fragment 也要 compute capability 8.0 或更高（指南的 WMMA 一节写的是 8.0 及以上；它自己的表只在上面那几种型号上标了 FP64）。这些在 T4 上都用不了。
  • Types from Ampere on: __nv_bfloat16 fragments must pair with a float accumulator; TF32 needs the inputs converted first with __float_to_tf32 and supports only 16 × 16 × 8; double fragments also need compute capability 8.0 or higher (the guide’s WMMA section says 8.0 and higher; its own table limits FP64 to the parts above). None of these is available on a T4.

Lab A 的 mm_wmma 是最简单的写法：每个 warp 负责 C 的一块 16 × 16，沿 k 方向每次读一对 16 × 16 的 FP16 块、做一次 mma_sync，fragment 直接从 global 读，不经过 shared memory。它不快：每个 warp 自己从 global 读 A 和 B，没有 block 内的复用（推断）；它的用处是让你在 ncu 里看到 Tensor Core 流水线被用起来，并和 cuBLAS 的 FP16 版本比一比。动画 (b) 画出这条路径。

Lab A’s mm_wmma is the simplest form: each warp owns one 16 × 16 tile of C, reads one pair of 16 × 16 FP16 tiles per step along k and performs one mma_sync, loading fragments straight from global memory without shared memory. It is not fast: each warp reads its own A and B from global memory with no reuse inside the block (an inference); its purpose is to let you see the tensor pipeline in use in ncu and compare it with cuBLAS’s FP16 path. 7. cuBLAS 是上限

7. cuBLAS as the ceiling

自己写的矩阵乘快不快，要有一把尺子。cuBLAS 是 NVIDIA 针对每一代架构调好的 BLAS 库，它的 GEMM 时间就是「在这张卡上这个尺寸大致能做到多快」的参考。几个要点（cuBLAS 文档，2026-10-31 读取）：

To know whether your own matrix multiply is fast, you need a ruler. cuBLAS is NVIDIA’s BLAS library, tuned for each architecture, and its GEMM time is the reference for roughly how fast this size can go on this card. The key points (cuBLAS documentation, read 2026-10-31):

  • 列主序：cuBLAS 沿用 Fortran 的列主序。行主序的 C = A × B 在列主序里看就是 CT = BT × AT，所以把 B 当第一个矩阵、A 当第二个传进去，不用转置任何数据：cublasSgemm(h, CUBLAS_OP_N, CUBLAS_OP_N, n, n, n, &one, B, n, A, n, &zero, C, n)。
  • Column-major: cuBLAS keeps Fortran’s column-major storage. A row-major C = A × B, seen as column-major, is CT = BT × AT, so pass B as the first matrix and A as the second and no data needs transposing: cublasSgemm(h, CUBLAS_OP_N, CUBLAS_OP_N, n, n, n, &one, B, n, A, n, &zero, C, n).
  • FP16 走 Tensor Core：cublasGemmEx 可以分别指定输入、输出和计算类型；输入 CUDA_R_16F、输出 CUDA_R_32F、计算类型 CUBLAS_COMPUTE_32F 是文档表里支持的组合。文档说，从 cuBLAS 11.0.0 起，库会在它判断最快的地方自动使用 Tensor Core，除非选了 pedantic 模式。
  • FP16 on tensor cores: cublasGemmEx takes separate input, output and compute types; CUDA_R_16F inputs, a CUDA_R_32F output and CUBLAS_COMPUTE_32F are a supported combination in the documentation’s table. The documentation says that from cuBLAS 11.0.0 on, the library uses tensor cores automatically wherever it judges them fastest, unless a pedantic mode is chosen.
  • FP32 的 Sgemm 在 T4 上不会走 Tensor Core（推断）：默认数学模式 CUBLAS_DEFAULT_MATH 的定义是计算精度至少和请求的一样多的尾数位和指数位；T4 的 Tensor Core 没有 TF32，只有 FP16，尾数位不够，所以 FP32 的 GEMM 只能用 FP32 核。在 Ampere 以后的卡上，CUBLAS_TF32_TENSOR_OP_MATH 才能让单精度例程用 TF32 Tensor Core。
  • FP32 Sgemm does not use tensor cores on a T4 (an inference): the default math mode CUBLAS_DEFAULT_MATH is defined as using compute precisions with at least as many mantissa and exponent bits as requested; the T4’s tensor cores have no TF32, only FP16, which has too few mantissa bits, so an FP32 GEMM has to run on the FP32 cores. Only on Ampere and later can CUBLAS_TF32_TENSOR_OP_MATH let single-precision routines use TF32 tensor cores.
  • 编译：链接动态库用 -lcublas。cuBLAS 的 kernel 名字没有文档保证，ncu 里要先用 nsys 的 cuda_gpu_kern_sum 看清它这次实际启动了哪个 kernel，再用 -k regex: 过滤。
  • Building: link the dynamic library with -lcublas. cuBLAS kernel names carry no documented guarantee, so before filtering with -k regex: in ncu, read off from nsys’s cuda_gpu_kern_sum which kernel it actually launched this time.

Lab B measured it on the M5 at 5.2 times as fast as Phase 1’s tiled kernel: a gap this wide usually separates a tuned library from classroom tiling (register tiling, double buffering, vectorised loads, block sizes chosen for the architecture). Common misconceptions

  • 误解：ncu 报的时长就是这个 kernel 在程序里的真实时间。→ 实际：ncu 默认锁定时钟、在重放之间清空缓存并串行化启动，它的时长适合比较同一个 kernel 的两个版本。
  • 误解：Long Scoreboard 占主导，说明 kernel 是带宽受限。→ 实际：Profiling Guide 写明那是访存延迟受限，不一定是带宽受限；带宽没用满时先选藏延迟的改法。
  • 误解：要把每一种停顿计数器都压到零。→ 实际：selected 和 not_selected 根本不是停顿，目标是发射槽的利用率。
  • Myth: the duration ncu reports is the kernel’s real time inside the program. → Fact: by default ncu locks clocks, flushes caches between replays and serialises launches, so its duration is for comparing two versions of one kernel.
  • Myth: a dominant Long Scoreboard means the kernel is bandwidth-bound. → Fact: the Profiling Guide says it means memory-latency-bound, not necessarily bandwidth-bound; when bandwidth is not saturated, try latency hiding first.
  • Myth: every stall counter should be driven to zero. → Fact: selected and not_selected are not stalls at all, and the target is issue-slot utilisation.

#define TILE 16

// Phase 1, unchanged: one thread per element of C, every operand read from global memory
__global__ void mm_naive(const float* A, const float* B, float* C, int n) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= n || col >= n) return;
    float acc = 0.0f;
    for (int k = 0; k < n; ++k) acc += A[row * n + k] * B[k * n + col];
    C[row * n + col] = acc;
}

// Phase 1, unchanged: TILE x TILE tiles of A and B staged in shared memory
__global__ void mm_tiled(const float* A, const float* B, float* C, int n) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];
    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty, col = blockIdx.x * TILE + tx;
    float acc = 0.0f;
    for (int k0 = 0; k0 < n; k0 += TILE) {
        As[ty][tx] = A[row * n + k0 + tx];
        Bs[ty][tx] = B[(k0 + ty) * n + col];
        __syncthreads();
        for (int k = 0; k < TILE; ++k) acc += As[ty][k] * Bs[k][tx];
        __syncthreads();
    }
    C[row * n + col] = acc;
}

// the fix: a 64 x 64 block tile, each of 256 threads keeps a 4 x 4 block of C in registers,
// so every value read from shared memory feeds 4 FMAs instead of 1
__global__ void mm_reg(const float* A, const float* B, float* C, int n) {
    __shared__ float As[64][TILE];
    __shared__ float Bs[TILE][64];
    int tx = threadIdx.x, ty = threadIdx.y;            // 16 x 16 threads
    int r0 = blockIdx.y * 64, c0 = blockIdx.x * 64;
    float acc[4][4] = {};
    for (int k0 = 0; k0 < n; k0 += TILE) {
        for (int i = 0; i < 4; ++i) As[ty + 16 * i][tx] = A[(r0 + ty + 16 * i) * n + k0 + tx];
        for (int j = 0; j < 4; ++j) Bs[ty][tx + 16 * j] = B[(k0 + ty) * n + c0 + tx + 16 * j];
        __syncthreads();
        for (int k = 0; k < TILE; ++k) {
            float a[4], b[4];
            for (int i = 0; i < 4; ++i) a[i] = As[ty + 16 * i][k];
            for (int j = 0; j < 4; ++j) b[j] = Bs[k][tx + 16 * j];
            for (int i = 0; i < 4; ++i)
                for (int j = 0; j < 4; ++j) acc[i][j] += a[i] * b[j];
        }
        __syncthreads();
    }
    for (int i = 0; i < 4; ++i)
        for (int j = 0; j < 4; ++j) C[(r0 + ty + 16 * i) * n + c0 + tx + 16 * j] = acc[i][j];
}

// tensor cores through WMMA: each warp owns one 16 x 16 tile of C; FP16 inputs, FP32 accumulator.
// 4 warps per block; fragments load straight from global memory (no shared-memory staging)
__global__ void mm_wmma(const half* A, const half* B, float* C, int n) {
    int warp = threadIdx.x / 32;
    int tr = blockIdx.y * 16, tc = (blockIdx.x * 4 + warp) * 16;
    wmma::fragment<wmma::matrix_a, 16, 16, 16, half, wmma::row_major> a;
    wmma::fragment<wmma::matrix_b, 16, 16, 16, half, wmma::row_major> b;
    wmma::fragment<wmma::accumulator, 16, 16, 16, float> c;
    wmma::fill_fragment(c, 0.0f);
    for (int k0 = 0; k0 < n; k0 += 16) {
        wmma::load_matrix_sync(a, A + tr * n + k0, n);
        wmma::load_matrix_sync(b, B + k0 * n + tc, n);
        wmma::mma_sync(c, a, b, c);
    }
    wmma::store_matrix_sync(C + tr * n + tc, c, n, wmma::mem_row_major);
}

__global__ void to_half(const float* in, half* out, int count) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < count) out[i] = __float2half(in[i]);
}

// median of 11 timed runs after 2 warm-ups; launch() enqueues one run
template <class F> float median_ms(F launch) {
    cudaEvent_t t0, t1;
    CHECK(cudaEventCreate(&t0)); CHECK(cudaEventCreate(&t1));
    std::vector<float> ms;
    for (int r = 0; r < 13; ++r) {
        CHECK(cudaEventRecord(t0));
        launch();
        CHECK(cudaGetLastError());
        CHECK(cudaEventRecord(t1));
        CHECK(cudaEventSynchronize(t1));
        float m = 0; CHECK(cudaEventElapsedTime(&m, t0, t1));
        if (r >= 2) ms.push_back(m);
    }
    CHECK(cudaEventDestroy(t0)); CHECK(cudaEventDestroy(t1));
    std::sort(ms.begin(), ms.end());
    return ms[ms.size() / 2];
}

int main() {
    cublasHandle_t h;
    CHECK_BLAS(cublasCreate(&h));
    for (int n : {1024, 2048}) {
        if (n % 64 != 0) { std::fprintf(stderr, "n must be a multiple of 64\n"); return 1; }
        size_t cnt = size_t(n) * n, bytes = cnt * sizeof(float);
        std::vector<float> hA(cnt), hB(cnt), hC(cnt);
        // small integers: exact in float and in half, and every sum of products is exact in FP32
        for (size_t i = 0; i < cnt; ++i) { hA[i] = float(i % 7) - 3; hB[i] = float(i % 5) - 2; }
        float *A, *B, *C; half *Ah, *Bh;
        CHECK(cudaMalloc(&A, bytes)); CHECK(cudaMalloc(&B, bytes)); CHECK(cudaMalloc(&C, bytes));
        CHECK(cudaMalloc(&Ah, cnt * sizeof(half))); CHECK(cudaMalloc(&Bh, cnt * sizeof(half)));
        CHECK(cudaMemcpy(A, hA.data(), bytes, cudaMemcpyHostToDevice));
        CHECK(cudaMemcpy(B, hB.data(), bytes, cudaMemcpyHostToDevice));
        to_half<<<(cnt + 255) / 256, 256>>>(A, Ah, int(cnt));
        to_half<<<(cnt + 255) / 256, 256>>>(B, Bh, int(cnt));
        CHECK(cudaGetLastError());

        // CPU reference for rows 0, n/2 and n-1: enough to catch a wrong kernel
        const int rows[3] = {0, n / 2, n - 1};
        std::vector<float> ref(3 * size_t(n), 0.0f);
        for (int r = 0; r < 3; ++r)
            for (int k = 0; k < n; ++k)
                for (int j = 0; j < n; ++j) ref[size_t(r) * n + j] += hA[size_t(rows[r]) * n + k] * hB[size_t(k) * n + j];
        auto mismatches = [&]() {
            CHECK(cudaMemcpy(hC.data(), C, bytes, cudaMemcpyDeviceToHost));
            int bad = 0;
            for (int r = 0; r < 3; ++r)
                for (int j = 0; j < n; ++j) bad += hC[size_t(rows[r]) * n + j] != ref[size_t(r) * n + j];
            CHECK(cudaMemset(C, 0, bytes));
            return bad;
        };
        const float one = 1.0f, zero = 0.0f;
        dim3 b16(TILE, TILE), g16(n / TILE, n / TILE), g64(n / 64, n / 64), gw(n / 64, n / 16);
        struct Run { const char* name; float ms; int bad; };
        std::vector<Run> runs;
        auto run = [&](const char* name, auto launch) { float ms = median_ms(launch); runs.push_back({name, ms, mismatches()}); };
        run("mm_naive", [&] { mm_naive<<<g16, b16>>>(A, B, C, n); });
        run("mm_tiled", [&] { mm_tiled<<<g16, b16>>>(A, B, C, n); });
        run("mm_reg",   [&] { mm_reg<<<g64, b16>>>(A, B, C, n); });
        run("mm_wmma",  [&] { mm_wmma<<<gw, 128>>>(Ah, Bh, C, n); });
        // cuBLAS is column-major: computing C^T = B^T A^T gives the row-major C = A B
        run("cublasSgemm", [&] { CHECK_BLAS(cublasSgemm(h, CUBLAS_OP_N, CUBLAS_OP_N, n, n, n, &one, B, n, A, n, &zero, C, n)); });
        run("cublasGemmEx_fp16", [&] { CHECK_BLAS(cublasGemmEx(h, CUBLAS_OP_N, CUBLAS_OP_N, n, n, n, &one, Bh, CUDA_R_16F, n,
                                                              Ah, CUDA_R_16F, n, &zero, C, CUDA_R_32F, n,
                                                              CUBLAS_COMPUTE_32F, CUBLAS_GEMM_DEFAULT)); });
        double gflop = 2.0 * n * n * double(n) / 1e9;
        for (const Run& r : runs)
            std::printf("n=%4d %-18s %9.3f ms %8.1f GFLOP/s  mismatches %d\n", n, r.name, r.ms, gflop / (r.ms / 1e3), r.bad);
        CHECK(cudaFree(A)); CHECK(cudaFree(B)); CHECK(cudaFree(C)); CHECK(cudaFree(Ah)); CHECK(cudaFree(Bh));
    }
    CHECK_BLAS(cublasDestroy(h));
    return 0;
}

Events are recorded in the GPU’s stream and measure time between two points on the GPU, which rules out c. Clock locking, cache flushing and serialisation are the sources of difference the guide lists.

4. 你在 T4 上有一个 FP32 的大矩阵乘，想让它用上 Tensor Core。哪种做法可行？

4. You have a large FP32 matrix multiply on a T4 and want it to use the tensor cores. Which approach works?

TF32 Tensor Core 从 Ampere（sm_80）才有，T4 没有，a 不行。wmma 里 float 输入只能以 TF32 精度用，同样要 compute capability 8.0 以上，c 也不行。T4 的 Tensor Core 浮点输入只有 FP16；FP16 输入、FP32 累加是 cublasGemmEx 支持的组合。代价是输入只剩 FP16 的精度和范围。TF32 tensor cores arrive with Ampere (sm_80) and the T4 has none, so a fails. In wmma, float inputs can only be used at TF32 precision, which also needs compute capability 8.0 or higher, so c fails too. The only floating-point input of the T4’s tensor cores is FP16; FP16 inputs with FP32 accumulation is a combination cublasGemmEx supports. The price is that the inputs keep only FP16’s precision and range.
