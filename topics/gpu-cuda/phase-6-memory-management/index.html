核心概念

Core concepts

同一个 kernel、同一份数据，换一种分配方式，第一次启动可能慢得多，第二次又和 cudaMalloc 一样快；一个每步都分配、释放临时 buffer 的循环，会把多个流的并发掐断；一次越界写在框架里可能什么都不报。原因都不在 kernel 里，而在内存住在哪、什么时候搬、由谁分配和归还。那么：一页内存是怎样从 CPU 跑到 GPU 的，怎样提前告诉驱动它该去哪，怎样分配才不让所有流同步，出了错又怎样找到是哪一行？

The same kernel on the same data, with a different allocation, can be far slower on its first launch and then as fast as cudaMalloc on the second; a loop that allocates and frees a temporary buffer every step cuts off the concurrency of several streams; an out-of-bounds write inside a framework may report nothing at all. None of the causes is in the kernel; they lie in where memory lives, when it moves, and who allocates and returns it. So how does a page get from the CPU to the GPU, how do you tell the driver in advance where it should go, how do you allocate without making every stream synchronize, and when something breaks, how do you find the line?

1. 统一内存的几种形态，和第一次访问时的迁移

1. The forms of unified memory, and migration on first touch

CUDA 编程指南（「Understanding Memory」和「Unified Memory」两节，2026-10-31 读取）把统一内存分成四种形态，用三个设备属性区分：cudaDevAttrConcurrentManagedAccess 为 1 表示完整支持，为 0 表示有限支持（Windows、WSL 和部分 Tegra）；完整支持时，cudaDevAttrPageableMemoryAccess 为 1 表示所有系统内存（连 malloc 的都算）都是统一内存，为 0 表示只有显式分配的 managed 内存才是；所有系统内存都统一时，cudaDevAttrPageableMemoryAccessUsesHostPageTables 说明一致性靠硬件（1，比如 Grace Hopper 的 ATS）还是软件（0，Linux 的 HMM）。指南写明 HMM 需要 Linux 内核 6.1.24+、6.2.11+ 或 6.3+，compute capability 7.5 以上，以及 535 以上的驱动并使用开源内核模块。Colab 的 T4 是插在 PCIe 上的独立卡，属于 CPU 和 GPU 各有一套页表的「软件一致」系统；它具体落在哪一种形态，要看那台虚拟机的内核和驱动，Lab A 的第一行输出会告诉你（推断：本页没有在 Colab 上查过）。

The CUDA Programming Guide (the “Understanding Memory” and “Unified Memory” sections, read 2026-10-31) divides unified memory into four forms, told apart by three device attributes: cudaDevAttrConcurrentManagedAccess is 1 for full support and 0 for limited support (Windows, WSL and some Tegra devices); with full support, cudaDevAttrPageableMemoryAccess is 1 when all system memory, even memory from malloc, is unified memory, and 0 when only explicitly allocated managed memory is; when all system memory is unified, cudaDevAttrPageableMemoryAccessUsesHostPageTables says whether coherence comes from hardware (1, such as the ATS of Grace Hopper) or from software (0, Linux HMM). The guide states that HMM needs Linux kernel 6.1.24+, 6.2.11+ or 6.3+, compute capability 7.5 or higher, and a 535+ driver with the open kernel modules. The Colab T4 is a discrete card on PCIe, a “software-coherent” system in which the CPU and the GPU keep separate page tables; which form it falls into depends on the kernel and driver of that virtual machine, and the first output line of Lab A tells you (an inference: this page did not check it on Colab).

在完整支持的系统上，cudaMallocManaged 只给出一段 CPU 和 GPU 共用的虚拟地址。指南的分配器对照表写明，它的物理页按 first touch / hint 放置：谁先访问一页，那一页就落在谁的内存里，除非用 advice 另行指定；落在 CPU 上的页用系统页大小（多数系统 4 KiB 或 64 KiB），驻留在 GPU 上的页是 2 MB（指南注明 GPU 端的页大小以后可能改变）。默认机制是「缺页再迁移」（fault-and-migrate）：GPU 访问一页物理上在主机的内存时缺页，驱动让主机那边的页表项失效、把数据搬过 PCIe、在 GPU 页表里建新项（Phase 1 的三步），然后线程才能继续。指南还提醒，GPU 上的 TLB 缺失比 CPU 上贵得多。这就是为什么「CPU 初始化、GPU 第一次跑」的那次 kernel 会慢得多：它的时间里装着成千上万次缺页处理。动画 (a) 一步一步画出这个过程。

On a system with full support, cudaMallocManaged hands out a range of virtual addresses shared by CPU and GPU. The allocator table of the guide says its physical pages are placed by first touch / hint: whichever processor touches a page first gets that page in its memory, unless advice says otherwise; pages on the CPU use the system page size (4 KiB or 64 KiB on most systems), and pages resident on the GPU are 2 MB (the guide notes that GPU-side page sizes may change in future). The default mechanism is fault-and-migrate: when the GPU touches a page that physically lives on the host, it faults, the driver invalidates the host page-table entry, moves the data across PCIe and creates an entry in the GPU page table (Phase 1’s three steps), and only then can the thread continue. The guide also warns that TLB misses are much more expensive on the GPU than on the CPU. This is why the first kernel after a CPU initialisation is so much slower: its time contains thousands of fault services. Diagram (a) draws the process step by step.

2. 预取和建议：替驱动做决定

2. Prefetch and advice: deciding for the driver

缺页迁移是驱动在不知道你要做什么的情况下的兜底。你知道得更多时，有两种办法告诉它（CUDA Runtime API 参考的「Memory Management」一节，CUDA 13.4，2026-10-31 读取）：

Fault-and-migrate is the driver’s fallback when it does not know what you intend. When you know more, there are two ways to tell it (the “Memory Management” part of the CUDA Runtime API reference, CUDA 13.4, read 2026-10-31):

  • 预取：cudaMemPrefetchAsync(const void* devPtr, size_t count, cudaMemLocation location, unsigned int flags, cudaStream_t stream = 0)。目标是一个 cudaMemLocation：type = cudaMemLocationTypeDevice 加 id 为设备号，或 cudaMemLocationTypeHost（此时 id 被忽略）；flags 文档写明「留作将来使用，现在必须为 0」。它是按流排序的操作：在流里前面的工作完成后才开始迁移，在后面的工作开始前完成。范围会按 CPU 页大小对齐；还没有物理页的部分直接在目标上分配。预取到 GPU 要求设备的 concurrentManagedAccess 不为 0。较早的教程和代码里传的是一个整数设备号；本页读的 13.4 参考里只有 cudaMemLocation 这一种写法，旧代码要改（旧写法来自记忆，推断）。
  • Prefetch: cudaMemPrefetchAsync(const void* devPtr, size_t count, cudaMemLocation location, unsigned int flags, cudaStream_t stream = 0). The destination is a cudaMemLocation: type = cudaMemLocationTypeDevice with id set to the device ordinal, or cudaMemLocationTypeHost (whose id is ignored); for flags the reference says “flags for future use, must be zero now”. It is a stream-ordered operation: migration starts only after earlier work in the stream has finished and completes before later work starts. The range is aligned to the CPU page size, and parts with no physical memory yet are populated directly on the destination. Prefetching to a GPU requires a non-zero concurrentManagedAccess on that device. Older tutorials and code pass an integer device number; the 13.4 reference read for this page shows only the cudaMemLocation form, so old code needs changing (the older form is from memory, an inference).
  • 建议：cudaMemAdvise(const void* devPtr, size_t count, cudaMemoryAdvise advice, cudaMemLocation location)。cudaMemoryAdvise 有六个值，三对「设置 / 撤销」： cudaMemAdviseSetReadMostly / cudaMemAdviseUnsetReadMostly：数据主要被读、偶尔被写；任何处理器读它都会在自己的内存里建一份只读副本，有人写时除写的那份以外全部失效；location 被忽略。 cudaMemAdviseSetPreferredLocation / cudaMemAdviseUnsetPreferredLocation：数据的首选位置；页在首选位置、访问方又能直接建映射时，就不迁移，否则照常迁移；它不阻止 cudaMemPrefetchAsync。文档特别提醒：首选位置设为显存而页在主机和设备之间来回颠簸时，驱动原本会把它固定在主机，设了首选位置就会一直颠簸下去。 cudaMemAdviseSetAccessedBy / cudaMemAdviseUnsetAccessedBy：这个处理器会访问这段数据；它不迁移数据，而是让数据始终映射在那个处理器的页表里，避免缺页；数据因为别的原因迁移时映射跟着更新。
  • Advice: cudaMemAdvise(const void* devPtr, size_t count, cudaMemoryAdvise advice, cudaMemLocation location). cudaMemoryAdvise has six values, three set-and-unset pairs: cudaMemAdviseSetReadMostly / cudaMemAdviseUnsetReadMostly: the data is mostly read and only occasionally written; any processor that reads it gets a read-only copy in its own memory, and a write invalidates every copy except the writer’s; location is ignored. cudaMemAdviseSetPreferredLocation / cudaMemAdviseUnsetPreferredLocation: where the data should preferably live; when a page is in its preferred location and the accessing processor can map it directly, no migration happens, otherwise it migrates as usual; it does not prevent cudaMemPrefetchAsync. The reference warns specifically: when a page thrashes between host and device, the driver would normally pin it to host memory, but with the preferred location set to the device it keeps thrashing indefinitely. cudaMemAdviseSetAccessedBy / cudaMemAdviseUnsetAccessedBy: this processor will access the data; it does not migrate anything, but keeps the data mapped in that processor’s page tables so that accesses do not fault; if the data migrates for some other reason, the mapping follows it.

两者常常一起用：一个只读的大表设 ReadMostly，让每张卡各有一份；一块「多数时候在主机、偶尔被 GPU 看一眼」的数据设首选位置为主机、再对 GPU 设 AccessedBy，GPU 就经 PCIe 直接读它，不搬；一块马上要被 kernel 整块用到的数据，就在同一个流里先预取过去。Lab A 把「不预取」「预取」「主机 + AccessedBy」三种做法放在同一个 kernel 上比较。

The two often go together: a large read-only table gets ReadMostly, so each GPU holds its own copy; data that mostly lives on the host and is only glanced at by the GPU gets the host as its preferred location plus AccessedBy for the GPU, so the GPU reads it across PCIe without moving it; data a kernel is about to use in full is prefetched first, in the same stream. Lab A compares no prefetch, prefetch, and host plus AccessedBy on the same kernel.

3. pinned 内存、DMA 和零拷贝

3. Pinned memory, DMA and zero-copy

pinned（页锁定）主机内存的道理在驱动那一层：GPU 的拷贝引擎用 DMA 按物理地址读写主机内存，那些物理页在传输期间不能被换出或挪动（Kernel Engineering Phase 5 的概念 4 讲 DMA 和 IOMMU）。cudaHostAlloc 的说明给出两个后果：设备能直接访问这块内存，所以拷贝带宽比可分页内存高得多；但分配太多会减少系统可用于分页的内存、拖慢整个系统，所以应当省着用，主要用作主机和设备之间的中转区。它的几个标志彼此独立：cudaHostAllocPortable（所有 CUDA 上下文都把它当 pinned），cudaHostAllocMapped（映射进 CUDA 地址空间），cudaHostAllocWriteCombined（写合并：CPU 写、设备读时传得快，但多数 CPU 读它很慢）。

The reason for pinned (page-locked) host memory lies in the driver: the copy engine of the GPU reads and writes host memory by physical address through DMA, and those physical pages must not be swapped out or moved during the transfer (concept 4 of Kernel Engineering Phase 5 covers DMA and the IOMMU). The description of cudaHostAlloc gives two consequences: the device can access this memory directly, so copies reach much higher bandwidth than from pageable memory; but allocating too much reduces the memory the system has for paging and degrades the whole system, so use it sparingly, mainly as a staging area between host and device. Its flags are independent of each other: cudaHostAllocPortable (pinned for every CUDA context), cudaHostAllocMapped (mapped into the CUDA address space) and cudaHostAllocWriteCombined (write-combined: fast to transfer when the CPU writes and the device reads, but slow for most CPUs to read).

零拷贝就是 mapped memory：编程指南写明「mapped memory 在以前的文档里也叫 zero-copy memory」。没有 HMM 或 ATS 时，把主机分配映射进 GPU 的地址空间，kernel 就能用指针直接读写主机内存，不需要先拷贝。用 cudaHostAlloc(..., cudaHostAllocMapped) 分配后，cudaHostGetDevicePointer 给出设备端指针；在统一虚拟地址（UVA）下，cudaMallocHost 和 cudaHostAlloc 的内存会自动映射，以前需要的 cudaSetDeviceFlags(cudaDeviceMapHost) 已经不需要了。代价同样写在指南里：mapped memory 一直留在 CPU 内存里，GPU 的每次访问都要走 PCIe 或 NVLink C2C，延迟高得多、带宽低得多；它不保证所有访问类型（比如原子操作）在所有系统上都支持；指南的原话是，它不应被当作统一内存或显式内存管理的高性能替代品，来承担 kernel 的主要内存需求。合适的用处是：只读一次的数据、很小的标志位或结果、CPU 写 GPU 读的流式数据。和统一内存比：统一内存多数时候会把页迁到访问它的处理器那边，迁过去以后就能用满显存带宽；mapped memory 永远不搬。

Zero-copy is mapped memory: the programming guide says “mapped memory has also been referred to as zero-copy memory in previous documents”. Without HMM or ATS, a host allocation mapped into the GPU’s address space lets a kernel read and write host memory through a pointer, with no copy first. After cudaHostAlloc(..., cudaHostAllocMapped), cudaHostGetDevicePointer returns the device-side pointer; under unified virtual addressing (UVA), memory from cudaMallocHost and cudaHostAlloc is mapped automatically, and the old cudaSetDeviceFlags(cudaDeviceMapHost) is no longer needed. The price is in the guide too: mapped memory stays in CPU memory, so every GPU access crosses PCIe or NVLink C2C with much higher latency and much lower bandwidth; it does not guarantee that every kind of access, atomics for example, is supported on every system; and in the guide’s words it should not be considered a performant alternative to unified memory or explicit memory management for the majority of a kernel’s memory needs. It suits data read once, small flags or results, and streams the CPU writes and the GPU reads. Compared with unified memory: unified memory usually migrates pages to the processor that touches them, after which the kernel gets full device bandwidth; mapped memory never moves.

4. 流序分配器与内存池

4. The stream-ordered allocator and memory pools

编程指南「Stream-Ordered Memory Allocator」一节开头一句话说清了问题：用 cudaMalloc 和 cudaFree 管理内存会让 GPU 在所有正在执行的流之间同步。一个每步都分配、释放临时 buffer 的循环，因此会把 Phase 5 辛苦叠起来的并发一次次掐断。流序分配器（CUDA 11.2 起）把分配和释放变成流里的操作：

The “Stream-Ordered Memory Allocator” section of the programming guide states the problem in its first sentence: managing memory with cudaMalloc and cudaFree causes the GPU to synchronize across all executing CUDA streams. A loop that allocates and frees a temporary buffer on every step therefore keeps cutting off the concurrency that Phase 5 worked to build. The stream-ordered allocator (since CUDA 11.2) makes allocation and freeing operations on a stream:

  • cudaMallocAsync(void** devPtr, size_t size, cudaStream_t hStream) 和 cudaFreeAsync(void* devPtr, cudaStream_t hStream)：分配在流执行到那里时才「生效」，释放在流执行到那里时把内存还回池里。文档的规则：释放之后的任何访问都是未定义行为；别的流要用这块内存，必须用事件把顺序接上（分配流里记事件、使用流 cudaStreamWaitEvent，用完再记事件、释放流等它）。cudaMalloc 的内存可以用 cudaFreeAsync 释放，反过来也行。设备是否支持，用 cudaDevAttrMemoryPoolsSupported 查。
  • cudaMallocAsync(void** devPtr, size_t size, cudaStream_t hStream) and cudaFreeAsync(void* devPtr, cudaStream_t hStream): the allocation takes effect when the stream reaches it, and the free returns the memory to the pool when the stream reaches it. The documented rules: any access after the free is undefined behavior; for another stream to use the memory, events must connect the order (record an event in the allocating stream, cudaStreamWaitEvent in the using stream, record again when done, and have the freeing stream wait on it). Memory from cudaMalloc may be freed with cudaFreeAsync, and the other way round. Whether a device supports the allocator is queried with cudaDevAttrMemoryPoolsSupported.
  • 内存池：每个设备有一个默认池（cudaDeviceGetDefaultMemPool，指南称为隐式池；它的分配是不可迁移的显存，不支持进程间共享），cudaMallocAsync 从设备的当前池里分配（cudaDeviceSetMemPool / cudaDeviceGetMemPool）。cudaMemPoolCreate 建显式池（可以要求进程间共享、最大池大小、特定 NUMA 节点等），cudaMallocFromPoolAsync 从指定的池分配；还有 cudaMemPoolSetAttribute、cudaMemPoolGetAttribute、cudaMemPoolSetAccess、cudaMemPoolTrimTo、cudaMemPoolDestroy。CUDA 13.4 另有按位置取池的 cudaMemGetDefaultMemPool、cudaMemGetMemPool 和 cudaMemSetMemPool（以上名字都在 13.4 的 Runtime API 参考里核对过）。
  • Memory pools: every device has a default pool (cudaDeviceGetDefaultMemPool; the guide calls it the implicit pool; its allocations are non-migratable device memory, and it does not support IPC), and cudaMallocAsync allocates from the device’s current pool (cudaDeviceSetMemPool / cudaDeviceGetMemPool). cudaMemPoolCreate creates an explicit pool (which can ask for IPC, a maximum pool size, a particular NUMA node and so on), and cudaMallocFromPoolAsync allocates from a named pool; there are also cudaMemPoolSetAttribute, cudaMemPoolGetAttribute, cudaMemPoolSetAccess, cudaMemPoolTrimTo and cudaMemPoolDestroy. CUDA 13.4 also has cudaMemGetDefaultMemPool, cudaMemGetMemPool and cudaMemSetMemPool, which take a location (every name here was checked in the 13.4 Runtime API reference).
  • release threshold：cudaMemPoolAttrReleaseThreshold 是池在尝试把内存还给操作系统之前最多留住的字节数，默认 0：池持有的内存超过阈值时，下一次流、事件或上下文同步就会尝试归还。所以默认设置下，每次同步后池都会缩回去，下一轮又要向系统要。指南的做法是把阈值设成 UINT64_MAX，需要时再用 cudaMemPoolTrimTo(pool, minBytesToKeep) 手动缩。cudaMemPoolAttrReservedMemCurrent、...UsedMemCurrent 和两个 High 值用来看池实际占了多少。
  • The release threshold: cudaMemPoolAttrReleaseThreshold is the number of bytes a pool holds on to before trying to release memory back to the OS, and it defaults to 0: when the pool holds more than the threshold, the next stream, event or context synchronize tries to release the excess. With the default, then, the pool shrinks after every synchronization and has to ask the OS again on the next round. The guide’s remedy is to set the threshold to UINT64_MAX and shrink by hand with cudaMemPoolTrimTo(pool, minBytesToKeep) when needed. cudaMemPoolAttrReservedMemCurrent, ...UsedMemCurrent and the two High values show how much the pool actually holds.
  • 复用策略（三个属性，默认都打开）：cudaMemPoolReuseFollowEventDependencies：分配流对那次释放有流序依赖（比如经过事件）时，可以复用另一个流释放的内存；cudaMemPoolReuseAllowOpportunistic：没有依赖、但那次释放已经执行完时也可以复用；cudaMemPoolReuseAllowInternalDependencies：允许分配器自己插入流依赖来复用。指南提醒，后两种会带来运行之间不一样的分配模式，或以意想不到的方式把工作串行化，需要确定性时可以关掉。动画 (b) 画出一个池在两个流之间怎样分块。
  • Reuse policies (three attributes, all on by default): cudaMemPoolReuseFollowEventDependencies lets an allocation reuse memory freed in another stream when the allocating stream has a stream-order dependency on that free (through an event, for example); cudaMemPoolReuseAllowOpportunistic allows reuse with no dependency once the free has already completed; cudaMemPoolReuseAllowInternalDependencies lets the allocator insert stream dependencies of its own in order to reuse. The guide warns that the last two introduce run-to-run variance in allocation patterns or can serialise work in unexpected ways, so turn them off when you need determinism. 5. 框架里的缓存分配器：以 PyTorch 为例

5. Caching allocators in frameworks: PyTorch as the example

深度学习框架每一步都会创建和丢弃大量张量，如果每次都调 cudaMalloc / cudaFree，同步的代价会压过计算。PyTorch 的做法是在用户态自己缓存一层，和内存池是同一个想法。下面的要点来自 PyTorch 2.15 文档的「CUDA semantics」笔记（2026-10-31 读取），只讲轮廓：

A deep-learning framework creates and drops huge numbers of tensors every step; calling cudaMalloc / cudaFree each time would let synchronization outweigh the compute. PyTorch caches a layer of its own in user space, the same idea as a memory pool. The points below come from the “CUDA semantics” notes of the PyTorch 2.15 documentation (read 2026-10-31), in outline only:

  • 缓存：PyTorch 用缓存分配器加速分配，释放不需要设备同步。代价是分配器留着的空闲内存在 nvidia-smi 里看起来仍被占用。torch.cuda.memory_allocated() 是张量实际占用的，memory_reserved() 是分配器管着的总量；empty_cache() 把未用的缓存还给别的程序，但不会让 PyTorch 自己多出可用内存。
  • Caching: PyTorch uses a caching allocator to speed up allocation, and freeing needs no device synchronization. The price is that the allocator’s idle memory still looks used in nvidia-smi. torch.cuda.memory_allocated() is what tensors actually occupy, and memory_reserved() is everything the allocator manages; empty_cache() returns unused cached memory for other programs, but does not give PyTorch itself more usable memory.
  • 按流记账：Tensor.record_stream 的说明写明，缓存分配器只知道张量是在哪个流上分配的；张量在别的流上用过时，分配器可能过早复用它的内存。record_stream 告诉分配器还有哪些流用过它。这和概念 4 里「跨流复用要事件依赖」是同一个问题。
  • Booked per stream: the description of Tensor.record_stream says the caching allocator is aware only of the stream where a tensor was allocated; if the tensor is used on another stream, the allocator may reuse its memory too early. record_stream tells the allocator which other streams have used it. This is the same problem as concept 4’s need for an event dependency when reusing across streams.
  • 配置：环境变量 PYTORCH_ALLOC_CONF（PYTORCH_CUDA_ALLOC_CONF 是保留给向后兼容的别名），格式 <option>:<value>,...。backend 可选 native（默认，PyTorch 自己的实现）或 cudaMallocAsync（CUDA 的流序分配器，要 CUDA 11.4 或更新）；native 把内存分成小块和大块管理，large_segment_size_mb 默认 20 MB，max_split_size_mb 不让分配器切分超过这个大小的块，用来对付碎片导致的内存不足；expandable_segments（实验性）让分配可以扩展，适合批大小不断变化的情况。
  • Configuration: the environment variable PYTORCH_ALLOC_CONF (PYTORCH_CUDA_ALLOC_CONF is an alias kept for backward compatibility), in the form <option>:<value>,.... backend is native (the default, PyTorch’s own implementation) or cudaMallocAsync (CUDA’s stream-ordered allocator, which needs CUDA 11.4 or newer); native manages small and large blocks, large_segment_size_mb defaults to 20 MB, and max_split_size_mb stops the allocator from splitting blocks larger than that size, a remedy for out-of-memory errors caused by fragmentation; expandable_segments (experimental) makes allocations expandable, for batch sizes that keep changing.
  • 和检查工具打架：文档写明缓存分配器会干扰内存检查工具，调试内存错误时设 PYTORCH_NO_CUDA_MEMORY_CACHING=1 关掉缓存。原因（推断）：越界访问落进分配器缓存着的、仍然有效的大块里，检查工具看不出它越界。GPU 上的错误要尽早报到出错的那一行，可以设 CUDA_LAUNCH_BLOCKING=1 让每次启动同步。
  • Fighting the checkers: the documentation says a caching allocator interferes with memory-checking tools, and to set PYTORCH_NO_CUDA_MEMORY_CACHING=1 to disable caching when debugging memory errors. The reason (an inference): an out-of-bounds access lands inside a large block the allocator is caching, which is still valid memory, so the checker cannot see it is out of bounds. To have a GPU error reported at the line that caused it, set CUDA_LAUNCH_BLOCKING=1 so every launch is synchronous.

6. 设备端断言与 compute-sanitizer

6. Device-side asserts and compute-sanitizer

设备端 assert（编程指南，「C++ Language Extensions」的 Assertion 一节）：表达式为 0 时停止 kernel。在调试器里运行会触发断点；否则每个断言失败的线程在主机下一次 cudaDeviceSynchronize、cudaStreamSynchronize 或 cudaEventSynchronize 之后向 stderr 打印一行 <文件>:<行>:<函数>: block: [x,y,z], thread: [x,y,z] Assertion `<表达式>` failed.。之后 CUDA 上下文就坏了，后续所有 CUDA 调用都返回 cudaErrorAssert，只能重启进程。断言会影响性能，发布版用 -DNDEBUG 关掉，所以表达式里不能有副作用。

The device-side assert (programming guide, the Assertion part of “C++ Language Extensions”): it stops the kernel when the expression is 0. Under a debugger it triggers a breakpoint; otherwise every thread whose assertion failed prints a line <file>:<line>:<function>: block: [x,y,z], thread: [x,y,z] Assertion `<expression>` failed. to stderr after the host next calls cudaDeviceSynchronize, cudaStreamSynchronize or cudaEventSynchronize. After that the CUDA context is corrupted and every later CUDA call fails with cudaErrorAssert; only a new process recovers. Asserts cost performance, so release builds turn them off with -DNDEBUG, which is why the expression must have no side effects.

compute-sanitizer（本页读的是 Compute Sanitizer v2026.3.0 的文档）是 CUDA 工具包自带的功能正确性检查套件，四个工具用 --tool 选：

compute-sanitizer (this page read the documentation of Compute Sanitizer v2026.3.0) is the functional-correctness suite that ships with the CUDA toolkit; its four tools are chosen with --tool:

  • memcheck（默认工具）：精确定位并归因越界和未对齐的内存访问，也报告 GPU 遇到的硬件异常、malloc/free 错误和 CUDA API 错误。泄漏检查要显式打开：--leak-check full。--padding 在每个分配后面加一段填充区，让紧挨着的两个 buffer 之间的越界也能被发现。
  • memcheck (the default tool): precisely detects and attributes out-of-bounds and misaligned memory accesses, and also reports hardware exceptions the GPU hits, malloc/free errors and CUDA API errors. Leak checking must be enabled explicitly: --leak-check full. --padding adds a padding area after each allocation, so overflows between two back-to-back buffers are caught too.
  • racecheck：报告 shared memory 上的数据访问冒险（hazard）：写后写（WAW）、写后读（RAW）、读后写（WAR）。报告有两种模式，--racecheck-report 取 analysis（默认，把许多冒险归纳成「哪一行的写和哪一行的读之间有竞争」）、hazard（逐字节的详细报告）或 all。修法：线程之间用 __syncthreads()，同一个 warp 内用 __syncwarp()。文档提醒 racecheck 不做任何内存访问错误检查，应先用 memcheck 确认程序没有内存错误。
  • racecheck: reports data-access hazards on shared memory: write-after-write (WAW), read-after-write (RAW) and write-after-read (WAR). Reports come in two modes: --racecheck-report takes analysis (the default, which condenses many hazards into “a race between the write on this line and the read on that line”), hazard (detailed, byte-accurate reports) or all. The fixes: __syncthreads() between threads, __syncwarp() within a warp. The documentation warns that racecheck performs no memory-access error checking, so run memcheck first to make sure the program is free of memory errors.
  • initcheck：报告 GPU 读了未初始化的 global memory（文档的例子是 cudaMemset 的大小按元素而不是按字节传，四分之三的内存没被初始化）；--initcheck-address-space shared 或 all 把 shared memory 也纳入；--track-unused-memory 报告分配了却从没写过的内存。
  • initcheck: reports GPU reads of uninitialized global memory (the documentation’s example passes the size to cudaMemset in elements instead of bytes, leaving three quarters of the memory uninitialized); --initcheck-address-space shared or all includes shared memory as well; --track-unused-memory reports memory that was allocated but never written.
  • synccheck：报告同步原语的非法用法（文档的例子是只有一部分线程到达的 __syncthreads() 屏障）。本课不展开。
  • synccheck: reports invalid uses of synchronization primitives (the documentation’s example is a __syncthreads() barrier reached by only some of the threads in a block). This lesson does not go further into it.

编译时加 -lineinfo，报告就能指到源代码行而不影响优化级别；-G 生成完整调试信息但会关掉优化。文档还提到 memcheck 专用的编译期插桩 -fdevice-sanitize=memcheck，它更快，但不附带调试信息，仍要和 -lineinfo 或 -G 一起用。

Build with -lineinfo and reports point to source lines without changing the optimisation level; -G generates full debug information but turns off optimisation. The documentation also describes compile-time instrumentation for memcheck, -fdevice-sanitize=memcheck, which is faster but implies no debug information, so it still needs -lineinfo or -G alongside.

7. cuda-gdb

7. cuda-gdb

cuda-gdb（文档 v13.4）是在 GDB 上加了 CUDA 命令的调试器，目标平台是 Linux 和 QNX；它的 macOS 主机客户端已经被移除，所以和 CUDA 一样只能在云端机器上用。要点：

cuda-gdb (documentation v13.4) is GDB with CUDA commands added, for Linux and QNX targets; its macOS host client has been removed, so, like CUDA itself, it runs only on the cloud machines. The essentials:

  • 编译：nvcc -g -G foo.cu -o foo。-G 会强制 -O0（只保留很少的死代码消除和寄存器溢出优化），程序变大变慢，有些只在优化后出现的 bug 会因此消失。
  • Build: nvcc -g -G foo.cu -o foo. -G forces -O0 (keeping only very limited dead-code elimination and register-spilling optimisations), so the program gets bigger and slower, and some bugs that appear only when optimised may vanish.
  • 焦点：GPU 上有成千上万个线程，cuda-gdb 一次「站」在一个上。info cuda kernels、info cuda blocks、info cuda threads 列出它们；cuda kernel 0、cuda thread (15) 或 cuda device 0 sm 1 warp 2 lane 3 切换焦点，没给出的坐标沿用当前值；切过去以后 print threadIdx、backtrace 照常用。
  • Focus: a GPU runs thousands of threads, and cuda-gdb stands on one at a time. info cuda kernels, info cuda blocks and info cuda threads list them; cuda kernel 0, cuda thread (15) or cuda device 0 sm 1 warp 2 lane 3 switch the focus, with any coordinates left out taken from the current focus; after the switch, print threadIdx and backtrace work as usual.
  • 断点：break foo.cu:23 if threadIdx.x == 1 && i < 5 是条件断点，条件里可以用 threadIdx、blockIdx，不能调函数；它每次都会被求值，所以会拖慢运行。set cuda break_on_launch application 在每个 kernel 的第一条指令停下。
  • Breakpoints: break foo.cu:23 if threadIdx.x == 1 && i < 5 is a conditional breakpoint whose condition may use threadIdx and blockIdx but no function calls; it is evaluated on every hit, so it slows the run down. set cuda break_on_launch application stops at the first instruction of every kernel.
  • 自动查错：set cuda api_failures stop 让任何返回致命错误的 CUDA API 调用停下（默认 ignore 只打印警告）；set cuda launch_blocking on 让启动同步，错误就停在出错的那次启动上。GPU 异常有编号，比如 CUDA_EXCEPTION_14「Warp Illegal Address」：一个线程访问了非法的 global、local 或 shared 地址，调试器会停在那条指令上。
  • Automatic error checks: set cuda api_failures stop stops at any CUDA API call that returns a fatal error (the default, ignore, only prints a warning); set cuda launch_blocking on makes launches synchronous, so an error stops at the launch that caused it. GPU exceptions are numbered, such as CUDA_EXCEPTION_14, “Warp Illegal Address”: a thread accessed an illegal global, local or shared address, and the debugger stops at that instruction.

  • cudaMallocManaged 只给虚拟地址，物理页落在第一个访问它的处理器那边，GPU 上驻留的页是 2 MB。
  • 默认的缺页再迁移是驱动的兜底，第一次启动的时间里装着全部缺页处理；在同一个流里先 cudaMemPrefetchAsync 就能整块提前搬好。
  • cudaMemAdvise 的 ReadMostly、PreferredLocation 和 AccessedBy 告诉驱动数据该复制、该住哪、该映射给谁。
  • pinned 内存让拷贝引擎直接 DMA，mapped（零拷贝）内存永远不搬，GPU 的每次访问都要过 PCIe 或 NVLink C2C。
  • cudaMalloc 和 cudaFree 会在所有流之间同步，cudaMallocAsync 把分配变成流里的操作，release threshold 默认 0，要调高池才不会每次同步都缩回去。
  • 查内存错误按顺序来：assert 暴露、compute-sanitizer 先 memcheck 再 racecheck 定位、cuda-gdb 停到那个线程上看。
  • cudaMallocManaged hands out only virtual addresses; physical pages land with the first processor to touch them, and pages resident on the GPU are 2 MB.
  • The default fault-and-migrate is the driver’s fallback, and the first launch’s time contains all of the fault servicing; a cudaMemPrefetchAsync earlier in the same stream moves everything in bulk beforehand.
  • ReadMostly, PreferredLocation and AccessedBy in cudaMemAdvise tell the driver whether data should be copied, where it should live and whom it should be mapped for.
  • Pinned memory lets the copy engines DMA directly; mapped (zero-copy) memory never moves, and every GPU access to it crosses PCIe or NVLink C2C.
  • cudaMalloc and cudaFree synchronize across all streams; cudaMallocAsync makes allocation a stream operation, and its release threshold defaults to 0, so raise it or the pool shrinks at every synchronization.
  • Hunt memory errors in order: assert exposes them, compute-sanitizer locates them with memcheck before racecheck, and cuda-gdb stops on that thread to look.

常见误解

Common misconceptions

  • 误解：统一内存就是零拷贝，数据不用搬。→ 实际：在 T4 这样的独立卡上，统一内存会把页迁到访问它的处理器那边，搬过去以后才用满显存带宽；永远不搬的是 mapped 内存。
  • 误解：nvidia-smi 显示显存快满了，说明张量占了这么多。→ 实际：PyTorch 的缓存分配器留着空闲块，memory_allocated() 才是张量实际占用，memory_reserved() 是分配器管着的总量。
  • 误解：racecheck 没报错，程序的内存访问就是对的。→ 实际：racecheck 只查 shared memory 上的冒险，不做内存访问错误检查，文档要求先用 memcheck。
  • Myth: unified memory is zero-copy, so nothing moves. → Fact: on a discrete card such as the T4, unified memory migrates pages to whichever processor touches them, and only then gets full device bandwidth; mapped memory is the kind that never moves.
  • Myth: when nvidia-smi shows device memory nearly full, tensors are using that much. → Fact: PyTorch’s caching allocator keeps idle blocks; memory_allocated() is what tensors occupy and memory_reserved() is all the allocator holds.
  • Myth: if racecheck reports nothing, the memory accesses are correct. → Fact: racecheck checks only shared-memory hazards and does no memory-access error checking; the documentation says to run memcheck first.

    %%writefile um_prefetch.cu
// 未运行 · not run; assembled from the CUDA documentation on 2026-10-31
// um_prefetch.cu: the same kernel on explicit, managed (with and without prefetch, with advice) and mapped memory
// build: nvcc -arch=sm_75 -O3 um_prefetch.cu -o um_prefetch
#include <cstdio>
#include <cstdlib>
#include <vector>
#include <cuda_runtime.h>

#define CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) { \
    std::fprintf(stderr, "%s:%d %s\n", __FILE__, __LINE__, cudaGetErrorString(e_)); std::exit(1); } } while (0)

// one read and one write per element: the time is all data movement
__global__ void scale(const float* x, float* y, size_t n) {
    size_t i = blockIdx.x * size_t(blockDim.x) + threadIdx.x;
    if (i < n) y[i] = 2.0f * x[i] + 1.0f;
}

const size_t N = size_t(1) << 26;                 // 64 Mi floats: 256 MB per array
const size_t BYTES = N * sizeof(float);
const int THREADS = 256;
const unsigned BLOCKS = unsigned((N + THREADS - 1) / THREADS);

// GPU time between two events around whatever enqueue() puts on stream s
template <class F> float ms_on(cudaStream_t s, F enqueue) {
    cudaEvent_t a, b;
    CHECK(cudaEventCreate(&a)); CHECK(cudaEventCreate(&b));
    CHECK(cudaEventRecord(a, s));
    enqueue();
    CHECK(cudaGetLastError());
    CHECK(cudaEventRecord(b, s)); CHECK(cudaEventSynchronize(b));
    float ms = 0; CHECK(cudaEventElapsedTime(&ms, a, b));
    CHECK(cudaEventDestroy(a)); CHECK(cudaEventDestroy(b));
    return ms;
}
// the CPU writes x first, so the CPU touches every page first
void fill(float* x) { for (size_t i = 0; i < N; ++i) x[i] = float(i % 1024); }
size_t mismatches(const float* y) {
    size_t bad = 0;
    for (size_t i = 0; i < N; ++i) bad += y[i] != 2.0f * float(i % 1024) + 1.0f;
    return bad;
}
void report(const char* name, float before, float k1, float k2, size_t bad) {
    std::printf("%-30s before %8.3f ms  kernel 1st %8.3f ms  2nd %8.3f ms  mismatches %zu\n", name, before, k1, k2, bad);
}

int main() {
    const int dev = 0;
    CHECK(cudaSetDevice(dev));
    int cma = 0, pma = 0;
    CHECK(cudaDeviceGetAttribute(&cma, cudaDevAttrConcurrentManagedAccess, dev));
    CHECK(cudaDeviceGetAttribute(&pma, cudaDevAttrPageableMemoryAccess, dev));
    std::printf("concurrentManagedAccess=%d pageableMemoryAccess=%d\n", cma, pma);
    if (!cma) { std::fprintf(stderr, "limited unified memory here: prefetch to the GPU is not supported\n"); return 1; }

    cudaStream_t s;
    CHECK(cudaStreamCreate(&s));
    cudaMemLocation gpu = {}; gpu.type = cudaMemLocationTypeDevice; gpu.id = dev;
    cudaMemLocation host = {}; host.type = cudaMemLocationTypeHost; host.id = 0;   // id is ignored for the host
    auto launch = [&](const float* x, float* y) { return ms_on(s, [&] { scale<<<BLOCKS, THREADS, 0, s>>>(x, y, N); }); };
    scale<<<1, 1, 0, s>>>(nullptr, nullptr, 0);   // create the context and load the module before any timing
    CHECK(cudaStreamSynchronize(s));

    {   // 1. explicit: cudaMalloc plus cudaMemcpy, the baseline; "before" is the copy in
        std::vector<float> hx(N), hy(N);
        fill(hx.data());
        float *x, *y;
        CHECK(cudaMalloc(&x, BYTES)); CHECK(cudaMalloc(&y, BYTES));
        float before = ms_on(s, [&] { CHECK(cudaMemcpyAsync(x, hx.data(), BYTES, cudaMemcpyHostToDevice, s)); });
        float k1 = launch(x, y), k2 = launch(x, y);
        CHECK(cudaMemcpy(hy.data(), y, BYTES, cudaMemcpyDeviceToHost));
        report("explicit cudaMalloc", before, k1, k2, mismatches(hy.data()));
        CHECK(cudaFree(x)); CHECK(cudaFree(y));
    }
    {   // 2. managed, no prefetch: the first launch faults the pages of x over from the host, one fault at a time
        float *x, *y;
        CHECK(cudaMallocManaged(&x, BYTES)); CHECK(cudaMallocManaged(&y, BYTES));
        fill(x);
        float k1 = launch(x, y), k2 = launch(x, y);
        report("managed, no prefetch", 0.0f, k1, k2, mismatches(y));   // the CPU read faults y back to the host
        CHECK(cudaFree(x)); CHECK(cudaFree(y));
    }
    {   // 3. managed with prefetch: move x and y to the GPU in bulk, in stream order, before the kernel
        float *x, *y;
        CHECK(cudaMallocManaged(&x, BYTES)); CHECK(cudaMallocManaged(&y, BYTES));
        fill(x);
        float before = ms_on(s, [&] {
            CHECK(cudaMemPrefetchAsync(x, BYTES, gpu, 0, s));            // flags must be 0
            CHECK(cudaMemPrefetchAsync(y, BYTES, gpu, 0, s));
        });
        float k1 = launch(x, y), k2 = launch(x, y);
        CHECK(cudaMemPrefetchAsync(y, BYTES, host, 0, s));              // bring the result back before the CPU reads it
        CHECK(cudaStreamSynchronize(s));
        report("managed + prefetch", before, k1, k2, mismatches(y));
        CHECK(cudaFree(x)); CHECK(cudaFree(y));
    }
    {   // 4. managed with advice: keep the data on the host and let the GPU map it instead of migrating
        float *x, *y;
        CHECK(cudaMallocManaged(&x, BYTES)); CHECK(cudaMallocManaged(&y, BYTES));
        for (float* p : {x, y}) {
            CHECK(cudaMemAdvise(p, BYTES, cudaMemAdviseSetPreferredLocation, host));
            CHECK(cudaMemAdvise(p, BYTES, cudaMemAdviseSetAccessedBy, gpu));
        }
        fill(x);
        float k1 = launch(x, y), k2 = launch(x, y);
        report("managed, host + accessed-by", 0.0f, k1, k2, mismatches(y));
        CHECK(cudaFree(x)); CHECK(cudaFree(y));
    }
    {   // 5. zero-copy: mapped pinned host memory; every GPU access crosses PCIe
        float *hx, *hy, *x, *y;
        CHECK(cudaHostAlloc(&hx, BYTES, cudaHostAllocMapped)); CHECK(cudaHostAlloc(&hy, BYTES, cudaHostAllocMapped));
        CHECK(cudaHostGetDevicePointer(&x, hx, 0)); CHECK(cudaHostGetDevicePointer(&y, hy, 0));
        fill(hx);
        float k1 = launch(x, y), k2 = launch(x, y);
        report("mapped (zero-copy)", 0.0f, k1, k2, mismatches(hy));
        CHECK(cudaFreeHost(hx)); CHECK(cudaFreeHost(hy));
    }
    CHECK(cudaStreamDestroy(s));
    return 0;
}

    %%writefile race.cu
// 未运行 · not run; assembled from the CUDA and Compute Sanitizer documentation on 2026-10-31
// race.cu: a block sum that forgets one __syncthreads(), for compute-sanitizer --tool racecheck
// build: nvcc -arch=sm_75 -lineinfo race.cu -o race        fixed: add -DFIXED
#include <cstdio>
#include <cstdlib>
#include <cuda_runtime.h>

#define CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) { \
    std::fprintf(stderr, "%s:%d %s\n", __FILE__, __LINE__, cudaGetErrorString(e_)); std::exit(1); } } while (0)
#define THREADS 256

__global__ void block_sum(const int* in, int* out) {
    __shared__ int s[THREADS];
    s[threadIdx.x] = in[blockIdx.x * THREADS + threadIdx.x];   // every thread writes its own slot
#ifdef FIXED
    __syncthreads();                                           // the missing barrier
#endif
    if (threadIdx.x == 0) {                                    // thread 0 reads all 256 slots
        int sum = 0;
        for (int i = 0; i < THREADS; ++i) sum += s[i];
        out[blockIdx.x] = sum;
    }
}

int main() {
    const int blocks = 64, n = blocks * THREADS;
    int *in, *out;
    CHECK(cudaMallocManaged(&in, n * sizeof(int))); CHECK(cudaMallocManaged(&out, blocks * sizeof(int)));
    for (int i = 0; i < n; ++i) in[i] = 1;                     // every block should sum to 256
    block_sum<<<blocks, THREADS>>>(in, out);
    CHECK(cudaGetLastError());
    CHECK(cudaDeviceSynchronize());
    int wrong = 0;
    for (int b = 0; b < blocks; ++b) wrong += out[b] != THREADS;
    std::printf("blocks with a wrong sum: %d of %d\n", wrong, blocks);
    CHECK(cudaFree(in)); CHECK(cudaFree(out));
    return 0;
}

    encode(cb); cb.commit(); cb.waitUntilCompleted()

func blit(_ from: MTLBuffer, _ to: MTLBuffer, _ bytes: Int) -> (MTLCommandBuffer) -> Void {
    return { cb in
        guard let b = cb.makeBlitCommandEncoder() else { fail("blit encoder") }
        b.copy(from: from, sourceOffset: 0, to: to, destinationOffset: 0, size: bytes)
        b.endEncoding()
    }
}

1. On a T4, an array from cudaMallocManaged is initialised by the CPU and then handed to a kernel. The program has already warmed up its context, yet the first launch is still much slower than the second. What is the most reasonable explanation and fix?

时钟爬升会让最早的短 kernel 慢一些，但第二次立刻变快、而且差距很大，指向的是只发生一次的事情：缺页迁移，a 不对。c 描述的是 mapped（零拷贝）内存：那样的话两次启动都慢，不会第二次变快。managed 内存按 first touch 放置、缺页时迁移，预取把这笔代价整块挪到 kernel 之前。A clock ramp slows the earliest short kernels a little, but a large gap that vanishes on the second launch points to something that happens once: fault-driven migration, so a is wrong. c describes mapped (zero-copy) memory, where both launches would be slow and the second would not speed up. 3. A multi-stream program allocates and frees a temporary buffer with cudaMalloc / cudaFree on every step, and the Nsight Systems timeline keeps showing gaps between the streams. What is the most direct fix?

编程指南写明 cudaMalloc 和 cudaFree 会让 GPU 在所有流之间同步，这正是空隙的来源；流序分配器把分配变成流里的操作，池在阈值以内留住内存。b 改的是数据住在哪，不是分配这一步，还会带来缺页迁移。c 让 kernel 的每次访问都走 PCIe，比空隙更糟，pinned 内存分配本身也不便宜。The programming guide says cudaMalloc and cudaFree make the GPU synchronize across all streams, which is where the gaps come from; the stream-ordered allocator turns allocation into a stream operation, and the pool keeps memory up to its threshold. b changes where the data lives, not the allocation step, and adds fault-driven migration. c sends every kernel access across PCIe, which is worse than the gaps, and allocating pinned memory is not cheap either.

4. Lab A 的 race.cu 少了一个 __syncthreads()，你连跑十次结果都对。下面哪一句是对的？

4. Lab A’s race.cu is missing a __syncthreads(), and ten runs in a row all give the right result. Which statement is correct?
