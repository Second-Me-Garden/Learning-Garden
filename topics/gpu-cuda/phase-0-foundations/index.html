1. 为什么用 GPU：吞吐而不是延迟

1. Why GPUs: throughput, not latency

CPU 核把大部分晶体管花在让一个线程跑快上：大缓存、分支预测、乱序执行，目标是缩短每条指令的等待，这叫面向延迟（latency-oriented）的设计。GPU 把晶体管花在大量简单的运算单元上，每个运算单元分到的控制逻辑很少。单看一个 GPU 线程，它比 CPU 线程慢得多；但同一时刻有成千上万个线程在跑，总的完成量（吞吐，throughput）高得多。前提是工作能拆成大量互不依赖的小份，向量加法正是这样：每个元素一份。

A CPU core spends most of its transistors on making one thread fast: large caches, branch prediction, out-of-order execution, all aimed at shortening the wait on each instruction. This is called latency-oriented design. A GPU spends its transistors on a great many simple arithmetic units, each with very little control logic of its own. A single GPU thread is much slower than a CPU thread, but tens of thousands of them run at the same time, so the total amount finished (throughput) is far higher. The precondition is that the work splits into many small independent pieces; a vector add is exactly that, one piece per element.

延迟怎样被藏起来：一次全局内存读要等几百个时钟周期（大致数量级，Phase 1 再讲）。CPU 靠缓存和乱序执行去减少这种等待；GPU 换了个办法：让每个 SM 同时驻留很多个 warp。每个线程的寄存器在 block 的整个生命期内都放在 SM 的大寄存器堆里，所以从一个 warp 换到另一个 warp 不需要保存和恢复任何东西，调度器每个周期只是挑一个「下一条指令的操作数已经就绪」的 warp 发射。一个 warp 在等内存，别的 warp 照样发射，运算单元就不闲着。对比一下：操作系统的线程切换要把寄存器存回内存再换进来（Kernel Engineering Phase 1），GPU 的 warp 切换在硬件里、几乎不花时间。

How latency gets hidden: a global-memory read waits hundreds of clock cycles (an approximate order of magnitude; Phase 1 covers it). A CPU reduces that wait with caches and out-of-order execution; a GPU takes another route and keeps many warps resident on each SM at once. Every thread’s registers stay in the SM’s large register file for the whole life of its block, so switching from one warp to another saves and restores nothing: each cycle the scheduler just picks a warp whose next instruction has its operands ready and issues it. While one warp waits on memory, other warps keep issuing, and the arithmetic units stay busy. Compare an operating-system thread switch, which writes registers back to memory and loads others (Kernel Engineering Phase 1); a GPU warp switch happens in hardware and costs almost nothing.

需要多少线程：Little 定律说，要维持带宽 B，在途的数据量必须等于 B × 延迟 L。拿 T4 来算：NVIDIA 给出的显存带宽是 320 GB/s 以上；假设一次读的延迟约 500 ns（这是示意值，不是测量值），在途数据就得有约 160 KB，也就是同时有约四万个 float 正在被读。一个 CPU 核同时只能挂起少量缓存未命中，GPU 能做到，是因为它有几万个线程，每个线程手里挂着一次读。所以对 GPU 来说「够并行」意味着至少几万个线程；Lab A 里 n = 1024 时，大部分 GPU 是闲着的。

How many threads it takes: Little’s law says that to sustain a bandwidth B, the data in flight must equal B × the latency L. Take the T4: NVIDIA gives its memory bandwidth as 320+ GB/s; assume a read latency of about 500 ns (an illustrative value, not a measurement), and about 160 KB must be in flight, that is, about forty thousand floats being read at once. A CPU core can keep only a small number of cache misses outstanding; a GPU gets there because it has tens of thousands of threads, each holding one read in flight. So for a GPU, “parallel enough” means at least tens of thousands of threads; at n = 1024 in Lab A, most of the GPU sits idle.

2. SIMT 与 warp

2. SIMT and the warp

SIMD（Parallel Programming Phase 6）：一条指令作用于一个固定宽度的向量寄存器，比如 NEON 的 128 位，一次 4 个 float。向量宽度写在代码里，由你或编译器写出向量指令，自己处理尾部和掩码。

SIMD (Parallel Programming Phase 6): one instruction acts on a fixed-width vector register, such as NEON’s 128 bits, 4 floats at a time. The vector width is written into the code: you or the compiler write the vector instructions and handle the tail and the masks yourselves.

SIMT（Single Instruction, Multiple Threads）：你只写一个标量线程的代码。硬件把一个 block 里编号连续的 32 个线程编成一个 warp，一条指令同时为这 32 个线程发射（CUDA C++ Programming Guide，「Warps and SIMT」一节）。每个线程有自己的寄存器，可以各自走分支；一个 warp 里的线程走了不同的路径时，warp 会把两条路径都执行一遍，每次屏蔽掉不走这条路的线程，这叫 divergence（分支发散，Phase 2）。从 Volta 开始有 Independent Thread Scheduling，warp 可以在分支之外保持分开（Best Practices Guide），但 warp 内所有线程走同一条路时最快。

SIMT (Single Instruction, Multiple Threads): you write the code of one scalar thread. The hardware groups 32 consecutively numbered threads of a block into a warp and issues one instruction for all 32 at once (CUDA C++ Programming Guide, section “Warps and SIMT”). Each thread has its own registers and may take its own branch; when the threads of one warp take different paths, the warp executes both paths in turn, masking off the threads that did not take each one. This is divergence (Phase 2). Since Volta, Independent Thread Scheduling lets a warp stay diverged beyond the conditional block (Best Practices Guide), but a warp is fastest when all its threads follow the same path.

为什么是 32：编程指南把 warp 定为 32 个线程，代码里可以读 warpSize，指南当前表格里的每一个 compute capability（7.5 到 12.x）warp 大小都是 32。这是一个设计取舍（以下是常见的解释，属推断）：一次取指、译码和调度决定服务 32 条通道，控制逻辑被摊到很多运算单元上；更宽的 warp 能摊得更薄，但线程一发散，浪费的通道也更多。还有一个巧合会在 Phase 1 用到：32 个线程各读一个 4 字节的 float，正好是连续的 128 字节。Apple GPU 的对应概念叫 SIMD-group，这台 M5 打印的 threadExecutionWidth 也是 32（Lab B）。实际后果是：block 的线程数应当是 32 的倍数，否则最后一个 warp 有空位。

Why 32: the programming guide sets the warp at 32 threads, code can read warpSize, and every compute capability in the guide’s current table (7.5 to 12.x) has a warp size of 32. It is a design trade-off (what follows is the common explanation, an inference): one instruction fetch, decode and scheduling decision serves 32 lanes, so the control logic is spread over many arithmetic units; a wider warp would spread it thinner, but would waste more lanes whenever threads diverge. One coincidence will matter in Phase 1: 32 threads each reading a 4-byte float read exactly 128 contiguous bytes. Apple’s GPU calls the same idea a SIMD-group, and this M5 prints a threadExecutionWidth of 32 as well (Lab B). The practical consequence: a block’s thread count should be a multiple of 32, or its last warp has empty lanes.

3. 编程模型：host、device、kernel、grid、block、thread

3. The programming model: host, device, kernel, grid, block, thread

host 指 CPU 和它的内存，device 指 GPU 和它的内存。用 __global__ 声明的函数是 kernel：在 host 上调用，在 device 上执行，写法是 kernel<<<gridDim, blockDim>>>(参数)。每个线程都执行整个函数体，区别只在内置变量：threadIdx（线程在 block 里的编号）、blockIdx（block 在 grid 里的编号）、blockDim（每个 block 的线程数）、gridDim（block 的个数），各自有 x、y、z 三维，本阶段只用 x。

The host is the CPU and its memory; the device is the GPU and its memory. A function declared __global__ is a kernel: called on the host, executed on the device, written as kernel<<<gridDim, blockDim>>>(args). Every thread runs the whole function body; the only difference between them is in the built-in variables: threadIdx (the thread’s number within its block), blockIdx (the block’s number within the grid), blockDim (threads per block) and gridDim (the number of blocks), each with x, y and z dimensions. This phase uses only x.

  • 选 blockDim：当前 GPU 上一个 block 最多 1024 个线程；一个 block 的全部线程驻留在同一个 SM 上、共享这个 SM 的资源，资源够的话一个 SM 可以同时放几个 block（编程指南）。block 内的线程可以用 shared memory 交换数据、用 __syncthreads() 同步（Phase 1）。取 32 的倍数；Best Practices Guide 建议从每 block 128 到 256 个线程开始试。本页用 256。
  • Choosing blockDim: on current GPUs a block holds at most 1024 threads; all threads of a block reside on the same SM and share its resources, and if resources allow, an SM holds several blocks at once (programming guide). Threads in a block can exchange data through shared memory and synchronise with __syncthreads() (Phase 1). Use a multiple of 32; the Best Practices Guide suggests 128 to 256 threads per block as a starting range. This page uses 256.
  • 选 gridDim，以及向上取整的写法：要让每个元素都有一个线程，block 数是 n / blockDim 向上取整。整数除法默认向下取整，所以写成 (n + block - 1) / block：加上 block − 1 再除，凡是有余数就多出一个 block。n = 2000、block = 256 时，(2000 + 255) / 256 = 8，共 2048 个线程，比 n 多 48 个，所以内核里必须有 if (i < n)，否则最后一个 block 的后 48 个线程会写到数组外面。
  • Choosing gridDim, and the ceiling-division idiom: to give every element a thread, the block count is n / blockDim rounded up. Integer division rounds down, so write (n + block - 1) / block: adding block − 1 before dividing yields one more block whenever there is a remainder. With n = 2000 and block = 256, (2000 + 255) / 256 = 8, which is 2048 threads, 48 more than n, so the kernel must contain if (i < n); otherwise the last 48 threads of the last block write past the end of the arrays.
  • block 彼此独立：block 以什么顺序、在哪个 SM 上运行都没有保证，block 之间也不能互相等待。正因为这样，同一个程序可以不改一行就在 SM 少的 GPU 和 SM 多的 GPU 上跑：多出来的 block 排队，等前面的 block 结束再上（动画 (a)）。
  • Blocks are independent: nothing guarantees the order in which blocks run or which SM each lands on, and blocks may not wait on each other. That is exactly why the same program runs unchanged on a GPU with few SMs and one with many: the extra blocks queue and start when earlier blocks finish (diagram (a)).
  • 启动是异步的：kernel 启动相对 host 线程是异步的（编程指南），<<< >>> 一返回，CPU 就接着往下走，GPU 可能还没开始。这决定了下面怎样检查错误、怎样计时。
  • Launches are asynchronous: a kernel launch is asynchronous with respect to the host thread (programming guide); as soon as <<< >>> returns, the CPU moves on, and the GPU may not have started yet. This decides how errors are checked and how time is measured below.

4. 内存空间一览，以及 host 与 device 之间的传输

4. Memory spaces at a glance, and transfers between host and device

  • 寄存器：每个线程私有，最快。shared memory：每个 block 一份，在 SM 片上，block 内共享。全局内存（global memory）：device 的 DRAM，所有线程可见，跨多次 kernel 启动一直存在，由 cudaMalloc 分配。常量内存：只读、有缓存。local memory：名义上线程私有，实际在 DRAM 里，寄存器不够时溢出到这里。每一种在 Phase 1 细讲。
  • Registers: private to each thread, the fastest. Shared memory: one per block, on the SM chip, shared within the block. Global memory: the device’s DRAM, visible to all threads, persisting across kernel launches, allocated with cudaMalloc. Constant memory: read-only and cached. Local memory: private to a thread in name, but physically in DRAM, where registers spill when they run out. Phase 1 covers each in detail.
  • 两块分开的内存：独立显卡上，host 的 DRAM 和 device 的 DRAM 是两块东西，中间隔着 PCIe。T4 是 16 GB GDDR6、PCIe Gen3 x16（NVIDIA T4 产品页）。cudaMalloc 返回的是 device 指针，host 代码不能解引用它；数据要用 cudaMemcpy(dst, src, bytes, kind) 搬过去、搬回来。
  • Two separate memories: on a discrete card, host DRAM and device DRAM are two different things with PCIe between them. The T4 has 16 GB of GDDR6 on PCIe Gen3 x16 (NVIDIA’s T4 product page). cudaMalloc returns a device pointer that host code must not dereference; data is moved there and back with cudaMemcpy(dst, src, bytes, kind).
  • cudaMemcpy 底下：真正搬数据的是 GPU 上的 DMA 引擎，驱动负责给它准备好物理地址（Kernel Engineering Phase 5 讲的 MMIO 与 DMA）。普通的 malloc/new 内存是可换页（pageable）的，操作系统可能把它换出或挪动；编程指南说 page-locked（固定）host 内存是异步拷贝的必要条件，也能加快同步拷贝。常见的解释是驱动先把可换页内存拷进一块固定的中转缓冲区再做 DMA（大致，NVIDIA 的驱动实现没有公开）。固定内存在 Phase 5 和 Phase 6 用到。
  • Under cudaMemcpy: the bytes are moved by DMA engines on the GPU, and the driver prepares the physical addresses for them (the MMIO and DMA of Kernel Engineering Phase 5). Ordinary malloc/new memory is pageable: the operating system may swap it out or move it. The programming guide says page-locked (pinned) host memory is required for asynchronous copies and also speeds up synchronous ones. The common explanation is that the driver first copies pageable memory into a pinned staging buffer and then runs the DMA (approximate; NVIDIA’s driver implementation is not public). Pinned memory returns in Phases 5 and 6.

为什么传输压过了小问题，也压过了向量加法：向量加法每个元素读 8 字节、写 4 字节，只做一次加法。在 device 上，这 12 字节以几百 GB/s 的速度流过；跨 PCIe Gen3 x16，理论上每个方向大致 16 GB/s。所以把 a、b 搬进去、把 c 搬回来，至少是内核本身时间的约 20 倍，而且不论 n 多大都是这个比例（这是从两个带宽推出的估计，Lab A 会量出你那台 T4 上的真实比例）。问题很小时还有固定开销：每次 cudaMemcpy、每次启动都要花几微秒（大致），和字节数无关，这时内核真正的计算几乎看不见。结论：把数据一次搬上去，在 device 上连着做很多个内核；或者让每个字节承担多得多的运算（矩阵乘，Phase 1 和 Phase 4）。在 Apple 的统一内存上，CPU 和 GPU 读同一块 DRAM，没有这次拷贝，但每次提交 command buffer 仍有固定开销，Lab B 量的就是它。

Why transfers outweigh small problems, and the vector add too: a vector add reads 8 bytes and writes 4 bytes per element and does a single add. On the device those 12 bytes stream past at hundreds of GB/s; across PCIe Gen3 x16 the theoretical rate is roughly 16 GB/s in each direction. So moving a and b in and c back out takes at least about 20 times as long as the kernel itself, at the same ratio whatever n is (an estimate derived from the two bandwidths; Lab A measures the real ratio on your T4). On small problems there are fixed costs as well: each cudaMemcpy and each launch costs a few microseconds (approximate) regardless of the byte count, and the kernel’s real work all but disappears. The conclusion: move the data over once and run many kernels on it while it stays on the device, or give every byte far more arithmetic (matrix multiply, Phases 1 and 4). On Apple’s unified memory the CPU and GPU read the same DRAM, so this copy does not exist, but every command-buffer submission still has a fixed cost, and that is what Lab B measures.

5. The toolchain, error checking and timing

  • nvcc: compiles a .cu file, handling the device code (compiled to the GPU’s PTX and SASS, Phase 7) separately from the host code (handed to the host C++ compiler). -arch=sm_75 targets Turing, which is the T4. The CUDA 13 release notes state that support for Maxwell, Pascal and Volta (the architectures before Turing) has been removed, so sm_75 is the oldest target the current toolchain builds for, and every lab in this topic starts from it. This topic is written for CUDA 13.x (13.4 Update 2 current on 2026-10-31; a 13.5.0 image reached Docker Hub on 2026-11-05); any 13.x will do.
  • nvidia-smi：看 GPU 型号、驱动版本、驱动支持的最高 CUDA 版本、显存占用、利用率和占用 GPU 的进程。Colab 上每次新开会话先跑一次，确认真的拿到了 T4。
  • nvidia-smi: shows the GPU model, the driver version, the highest CUDA version the driver supports, memory in use, utilisation and the processes on the GPU. On Colab, run it at the start of every new session to confirm you really got a T4.
  • 错误检查：运行时 API 函数返回 cudaError_t，但 <<< >>> 启动什么也不返回（编程指南）。运行时为每个 host 线程保存一个错误状态，cudaGetLastError 返回它并把它清回 cudaSuccess。所以有三件事：每个 API 调用都包进检查宏；启动之后立刻调 cudaGetLastError，抓住配置错误（比如每 block 2048 个线程，超过 1024 的上限）；内核执行中的错误（比如越界访问）只有到下一次同步调用才会报告，所以要在 cudaEventSynchronize 或 cudaDeviceSynchronize 的返回值上再检查一次。
  • Error checking: runtime API functions return a cudaError_t, but a <<< >>> launch returns nothing (programming guide). The runtime keeps an error state per host thread, and cudaGetLastError returns it and resets it to cudaSuccess. So there are three habits: wrap every API call in a check macro; call cudaGetLastError right after a launch to catch configuration errors (such as 2048 threads per block, over the limit of 1024); and since errors during execution (such as an out-of-bounds access) are reported only at the next synchronising call, check the return value of cudaEventSynchronize or cudaDeviceSynchronize as well.
  • 用事件计时：启动是异步的，在启动前后读 CPU 时钟，量到的只是启动本身。cudaEventRecord 往流里插一个时间戳，GPU 执行到那里时记下时间；cudaEventSynchronize 等它完成；cudaEventElapsedTime 给出两个事件之间的毫秒数，分辨率约 0.5 微秒（Runtime API 文档）。和 Parallel Programming 一样：先预热一次（第一次启动还要付一次性的开销，比如加载模块），再取多次运行的中位数。
  • Timing with events: since a launch is asynchronous, reading a CPU clock before and after it measures only the launch itself. cudaEventRecord puts a timestamp into the stream, recorded when the GPU reaches it; cudaEventSynchronize waits for it; cudaEventElapsedTime gives the milliseconds between two events, with a resolution of around 0.5 microseconds (Runtime API documentation). As in Parallel Programming: warm up once first (the first launch also pays one-time costs such as loading the module), then take the median of repeated runs.
  • Metal 的对应物：MTLCommandBuffer 完成后，gpuStartTime 和 gpuEndTime 给出 GPU 开始和结束执行这个 command buffer 的时刻，单位是秒；两者之差就是 GPU 时间。错误不靠全局状态，而是看 status 和 error。离线的 Metal 编译器 xcrun metal 不在 Command Line Tools 里（本机 xcrun -f metal 报 unable to find utility），所以 Lab B 用 makeLibrary(source:) 在运行时编译着色器源码。
  • The Metal counterpart: once an MTLCommandBuffer completes, gpuStartTime and gpuEndTime give the moments the GPU started and finished executing it, in seconds; their difference is the GPU time. Errors are not a global state: you look at status and error. The offline Metal compiler xcrun metal is not part of the Command Line Tools (on this Mac xcrun -f metal reports unable to find utility), so Lab B compiles the shader source at run time with makeLibrary(source:).

  • GPU 用单个线程的速度换总吞吐，靠在常驻 SM 的 warp 之间零代价切换来藏住内存延迟，所以要几万个线程才吃得满。
  • 硬件把一个 block 里编号连续的 32 个线程编成一个 warp，一条指令同时为它们发射；warp 内走不同分支时两条路径依次执行。
  • 每个线程用 i = blockIdx.x * blockDim.x + threadIdx.x 找到自己的元素，block 数用 (n + block - 1) / block 向上取整，再用 if (i < n) 挡住多余的线程。
  • block 之间没有执行顺序的保证，也不能互相等待，所以同一个程序不改就能在 SM 多少不同的 GPU 上跑。
  • 启动是异步的：启动后立刻调 cudaGetLastError 抓配置错误，执行中的错误要在下一次同步调用的返回值里看，计时用事件而不是 CPU 时钟。
  • 独立显卡上向量加法的 PCIe 拷贝比内核本身长得多，所以要把数据留在 device 上连着跑多个内核。
  • A GPU trades single-thread speed for total throughput and hides memory latency by switching for free among warps resident on the SM, so it takes tens of thousands of threads to keep it busy.
  • The hardware groups 32 consecutively numbered threads of a block into a warp and issues each instruction for all of them at once; when they take different branches the two paths run one after the other.
  • Each thread finds its element with i = blockIdx.x * blockDim.x + threadIdx.x, the block count is rounded up with (n + block - 1) / block, and if (i < n) stops the spare threads.
  • Blocks have no guaranteed order and may not wait on each other, which is why one program runs unchanged on GPUs with few or many SMs.
  • Launches are asynchronous: call cudaGetLastError right after a launch for configuration errors, read execution errors from the next synchronising call, and time with events rather than a CPU clock.
  • On a discrete card the PCIe copies of a vector add take far longer than the kernel, so keep data on the device and run several kernels on it.

常见误解

Common misconceptions

  • 误解：GPU 快，是因为它的每个线程都比 CPU 线程快。→ 实际：单个 GPU 线程慢得多，快的是同时在跑的几万个线程的总完成量。
  • 误解：<<< >>> 返回后 cudaGetLastError 是 cudaSuccess，内核就跑对了。→ 实际：它只抓到配置错误，越界访问这类执行中的错误要到下一次同步调用才报告。
  • 误解：在启动前后读 CPU 时钟就量到了内核时间。→ 实际：启动是异步的，这样只量到启动本身，要用 cudaEventRecord 和 cudaEventElapsedTime。
  • Myth: a GPU is fast because each of its threads is faster than a CPU thread. → Fact: a single GPU thread is much slower; what is fast is the combined output of tens of thousands running at once.
  • Myth: if cudaGetLastError returns cudaSuccess after <<< >>>, the kernel ran correctly. → Fact: it catches only configuration errors; errors during execution, such as an out-of-bounds access, are reported at the next synchronising call.
  • Myth: reading a CPU clock before and after a launch measures the kernel. → Fact: the launch is asynchronous, so that measures only the launch; use cudaEventRecord and cudaEventElapsedTime.

// 未运行 · not run; assembled from the CUDA documentation on 2026-10-31
// vec_add.cu: vector add with a check macro, cudaEvent timing and a size sweep
#include <algorithm>
#include <cstdio>
#include <cstdlib>
#include <vector>
#include <cuda_runtime.h>

#define CUDA_CHECK(call)                                                    \
  do {                                                                      \
    cudaError_t err_ = (call);                                              \
    if (err_ != cudaSuccess) {                                              \
      std::fprintf(stderr, "%s:%d: %s failed: %s\n", __FILE__, __LINE__,    \
                   #call, cudaGetErrorString(err_));                        \
      std::exit(1);                                                         \
    }                                                                       \
  } while (0)

__global__ void vec_add(const float* a, const float* b, float* c, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;    // this thread's element
  if (i < n) c[i] = a[i] + b[i];                    // the last block may reach past n
}

int main() {
  cudaDeviceProp p;
  CUDA_CHECK(cudaGetDeviceProperties(&p, 0));
  std::printf("device=%s sm_%d%d SMs=%d warpSize=%d maxThreadsPerBlock=%d\n",
              p.name, p.major, p.minor, p.multiProcessorCount, p.warpSize, p.maxThreadsPerBlock);

  const int block = 256;                            // threads per block, a multiple of 32
  const int reps = 21;                              // timed kernel runs per size, after one warm-up
  cudaEvent_t e0, e1;
  CUDA_CHECK(cudaEventCreate(&e0));
  CUDA_CHECK(cudaEventCreate(&e1));

  for (int lg : {10, 14, 18, 20, 22, 24, 26}) {
    const int n = 1 << lg;
    const size_t bytes = size_t(n) * sizeof(float);
    std::vector<float> a(n), b(n, 2.0f), c(n, -1.0f);
    for (int i = 0; i < n; ++i) a[i] = float(i % 1000);

    float *da, *db, *dc;
    CUDA_CHECK(cudaMalloc(&da, bytes));
    CUDA_CHECK(cudaMalloc(&db, bytes));
    CUDA_CHECK(cudaMalloc(&dc, bytes));

    float h2d = 0, d2h = 0;
    CUDA_CHECK(cudaEventRecord(e0));
    CUDA_CHECK(cudaMemcpy(da, a.data(), bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(db, b.data(), bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaEventRecord(e1));
    CUDA_CHECK(cudaEventSynchronize(e1));
    CUDA_CHECK(cudaEventElapsedTime(&h2d, e0, e1));

    const int grid = (n + block - 1) / block;       // ceil division: enough blocks to cover n
    std::vector<float> ms;
    for (int r = 0; r <= reps; ++r) {               // r == 0 is the warm-up
      CUDA_CHECK(cudaEventRecord(e0));
      vec_add<<<grid, block>>>(da, db, dc, n);
      CUDA_CHECK(cudaGetLastError());               // launch errors, such as a bad configuration
      CUDA_CHECK(cudaEventRecord(e1));
      CUDA_CHECK(cudaEventSynchronize(e1));         // errors during execution surface here
      float t = 0;
      CUDA_CHECK(cudaEventElapsedTime(&t, e0, e1));
      if (r > 0) ms.push_back(t);
    }
    std::sort(ms.begin(), ms.end());
    const float k = ms[ms.size() / 2];

    CUDA_CHECK(cudaEventRecord(e0));
    CUDA_CHECK(cudaMemcpy(c.data(), dc, bytes, cudaMemcpyDeviceToHost));
    CUDA_CHECK(cudaEventRecord(e1));
    CUDA_CHECK(cudaEventSynchronize(e1));
    CUDA_CHECK(cudaEventElapsedTime(&d2h, e0, e1));

    int bad = 0;
    for (int i = 0; i < n; ++i) bad += (c[i] != a[i] + b[i]);
    std::printf("n=2^%-2d %10d  h2d_ms=%8.4f  kernel_ms=%8.4f  d2h_ms=%8.4f  kernel_GB/s=%6.1f  bad=%d\n",
                lg, n, h2d, k, d2h, 3.0 * bytes / (k * 1e6), bad);
    CUDA_CHECK(cudaFree(da));
    CUDA_CHECK(cudaFree(db));
    CUDA_CHECK(cudaFree(dc));
  }
  CUDA_CHECK(cudaEventDestroy(e0));
  CUDA_CHECK(cudaEventDestroy(e1));
}

// build: swiftc -O vadd_sweep.swift -o vadd_sweep    run: ./vadd_sweep
import Foundation
import Metal

let source = """
#include <metal_stdlib>
using namespace metal;
kernel void vadd(device const float* a [[buffer(0)]],
                 device const float* b [[buffer(1)]],
                 device float*       c [[buffer(2)]],
                 constant uint&      n [[buffer(3)]],
                 uint i [[thread_position_in_grid]]) {
    if (i < n) c[i] = a[i] + b[i];          // same bounds check as the CUDA kernel
}
"""

func fail(_ msg: String) -> Never { print("error: \(msg)"); exit(1) }

guard let dev = MTLCreateSystemDefaultDevice() else { fail("no Metal device") }
let lib: MTLLibrary
do { lib = try dev.makeLibrary(source: source, options: nil) } catch { fail("compile: \(error)") }
guard let fn = lib.makeFunction(name: "vadd") else { fail("no function vadd") }
let pso: MTLComputePipelineState
do { pso = try dev.makeComputePipelineState(function: fn) } catch { fail("pipeline: \(error)") }
guard let queue = dev.makeCommandQueue() else { fail("no command queue") }

let tg = 256                                 // threads per threadgroup, like blockDim.x = 256
let reps = 21                                // timed runs per size, after one warm-up
print("device=\(dev.name) threadExecutionWidth=\(pso.threadExecutionWidth) " +
      "maxTotalThreadsPerThreadgroup=\(pso.maxTotalThreadsPerThreadgroup) hasUnifiedMemory=\(dev.hasUnifiedMemory)")

func median(_ x: [Double]) -> Double { let s = x.sorted(); return s[s.count / 2] }

for lg in [10, 14, 18, 20, 22, 24, 26] {
    let n = 1 << lg
    let bytes = n * MemoryLayout<Float>.stride
    guard let a = dev.makeBuffer(length: bytes, options: .storageModeShared),
          let b = dev.makeBuffer(length: bytes, options: .storageModeShared),
          let c = dev.makeBuffer(length: bytes, options: .storageModeShared) else { fail("buffer of \(bytes) bytes") }
    let pa = a.contents().bindMemory(to: Float.self, capacity: n)
    let pb = b.contents().bindMemory(to: Float.self, capacity: n)
    let pc = c.contents().bindMemory(to: Float.self, capacity: n)
    for i in 0..<n { pa[i] = Float(i % 1000); pb[i] = 2; pc[i] = -1 }   // shared storage: no copy to the GPU

    var gpu: [Double] = [], wall: [Double] = []
    for r in 0...reps {                                                  // r == 0 is the warm-up
        guard let cb = queue.makeCommandBuffer(), let enc = cb.makeComputeCommandEncoder() else { fail("encoder") }
        enc.setComputePipelineState(pso)
        enc.setBuffer(a, offset: 0, index: 0)
        enc.setBuffer(b, offset: 0, index: 1)
        enc.setBuffer(c, offset: 0, index: 2)
        var n32 = UInt32(n)
        enc.setBytes(&n32, length: MemoryLayout<UInt32>.stride, index: 3)
        let groups = (n + tg - 1) / tg                                   // ceil division, as in CUDA
        enc.dispatchThreadgroups(MTLSize(width: groups, height: 1, depth: 1),
                                 threadsPerThreadgroup: MTLSize(width: tg, height: 1, depth: 1))
        enc.endEncoding()
        let t0 = DispatchTime.now().uptimeNanoseconds
        cb.commit()
        cb.waitUntilCompleted()
        let t1 = DispatchTime.now().uptimeNanoseconds
        if cb.status != .completed { fail("command buffer: \(String(describing: cb.error))") }
        if r > 0 {
            gpu.append((cb.gpuEndTime - cb.gpuStartTime) * 1e3)          // seconds to ms
            wall.append(Double(t1 - t0) / 1e6)
        }
    }
    var bad = 0
    for i in 0..<n where pc[i] != pa[i] + pb[i] { bad += 1 }
    let g = median(gpu), w = median(wall)
    print(String(format: "n=2^%-2d %10d  gpu_ms=%8.4f  wall_ms=%8.4f  GB/s=%6.1f  bad=%d",
                 lg, n, g, w, Double(3 * bytes) / (g * 1e6), bad))
}

1. n = 1000，每个 block 256 个线程。启动几个 block？内核里为什么要有 if (i < n)？

1. n = 1000 with 256 threads per block. How many blocks are launched, and why does the kernel need if (i < n)?

整数除法 1000 / 256 = 3，只覆盖 768 个元素，后 232 个没人算，所以要向上取整得 4。4 × 256 = 1024，多出的 24 个线程的 i 落在 1000 到 1023，没有检查就越界写。GPU 不会替你丢弃越界的写：地址恰好可写时什么也不报，这正是 Lab A 第 5 步看到的情况。Integer division gives 1000 / 256 = 3, which covers only 768 elements and leaves the last 232 uncomputed, so round up to 4. 4 × 256 = 1024, and the 24 extra threads get i from 1000 to 1023, writing out of bounds without the check. The GPU does not discard such writes for you: when the address happens to be writable nothing is reported, which is what step 5 of Lab A shows.

2. 为什么 GPU 要同时驻留几万个线程才能把显存带宽用满？

2. Why does a GPU need tens of thousands of resident threads to use its full memory bandwidth?

向量加法几乎不做运算，算力不是瓶颈，所以 b 说的不是带宽的原因。warp 是 32 个线程，1024 是一个 block 的上限，c 把两者混了。答案是 Little 定律：T4 上 320 GB/s 乘以几百纳秒的延迟，需要几万个 float 同时在途。A vector add does almost no arithmetic, so compute is not the bottleneck, and b does not explain bandwidth. A warp is 32 threads and 1024 is the per-block limit, so c mixes the two up. The answer is Little’s law: 320 GB/s on a T4 times a latency of hundreds of nanoseconds needs tens of thousands of floats in flight.

3. 在 T4 上，n = 226 时 h2d_ms + d2h_ms 比 kernel_ms 大得多。最合理的解释是？

3. On a T4 at n = 226, h2d_ms + d2h_ms is far larger than kernel_ms. What is the most reasonable explanation?

上下文只在第一次调用 CUDA 时建立一次，而且程序在计时前已调用过 cudaGetDeviceProperties 和 cudaMalloc，所以不是 a。grid 有 26 万多个 block，会铺满所有 SM，所以不是 b。拷贝和内核搬同样的字节，拷贝走 PCIe（Gen3 x16 大致 16 GB/s 每方向），内核走显存（320 GB/s 以上），比值约 20 倍，与 n 无关。The context is created once, at the first CUDA call, and the program has already called cudaGetDeviceProperties and cudaMalloc before timing, so it is not a. The grid has over 260,000 blocks and fills every SM, so it is not b. The copies and the kernel move the same bytes, but the copies go over PCIe (roughly 16 GB/s each way on Gen3 x16) while the kernel uses device memory (320+ GB/s), a ratio of about 20 whatever n is.

4. 你用 vec_add<<<grid, 2048>>>(…) 启动内核。这个错误在哪里能被发现？

4. You launch a kernel with vec_add<<<grid, 2048>>>(…). Where can this error be caught?

<<< >>> 启动不返回 cudaError_t，所以没有 a 可查。每 block 2048 个线程超过 1024 的上限，这是配置错误，启动时就被记进错误状态，cudaGetLastError 立刻能读到。异步性影响的是执行中的错误，比如越界访问，那种才要等到同步时报告，所以 c 混淆了两类错误。A <<< >>> launch returns no cudaError_t, so a has nothing to check. 2048 threads per block exceeds the limit of 1024; it is a configuration error, recorded in the error state at launch, and cudaGetLastError reads it at once. Asynchrony matters for errors during execution, such as an out-of-bounds access, which wait until a synchronising call, so c confuses the two kinds of error.
