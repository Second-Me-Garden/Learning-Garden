核心概念

Core concepts

SM 按顺序发射指令，不做分支预测也不做推测执行，而一次全局内存读要等几百个周期。如果一个 warp 调度器手里只有一个 warp，它发出一条读之后就只能干等几百个周期，算力再多也用不上。另一方面，一个 warp 的 32 个线程共用一条指令，要是它们想走不同的路，就只能一条一条地走。

An SM issues instructions in order, with no branch prediction and no speculation, while a global-memory read waits hundreds of cycles. If a warp scheduler had only one warp, it would issue a load and then sit idle for hundreds of cycles, however much compute the SM has. On top of that, the 32 threads of a warp share one instruction, so if they want different paths they can only take them one at a time.

硬件和程序员要保证：每个周期总有一个 warp 能发射，一个 warp 里的线程尽量走同一条路。概念 2 和 3 的 warp 切换与 occupancy 回答前一件，概念 4 的分支发散回答后一件。

Hardware and programmer have to make sure that some warp can issue in every cycle and that the threads of a warp keep to one path where they can. Concepts 2 and 3, warp switching and occupancy, answer the first; concept 4, branch divergence, answers the second.

1. SM 与 warp 调度器

1. The SM and its warp schedulers

SM（streaming multiprocessor）是 GPU 上执行线程的单元。编程指南这样描述它：SM 拿到一个或几个 block 后，把它们切成 warp，每个 warp 交给一个 warp 调度器；SM 按顺序发射指令，不做分支预测，也不做推测执行（CUDA Programming Guide，「Hardware Implementation」一节）。CPU 核靠乱序执行在一个线程内部找活干；SM 不这么做，它的办法是在很多个 warp 之间找活干。

The SM (streaming multiprocessor) is the unit of a GPU that executes threads. The programming guide describes it like this: when an SM is given one or more blocks, it partitions them into warps and each warp is scheduled by a warp scheduler; the SM issues instructions in order, with no branch prediction and no speculative execution (CUDA Programming Guide, section “Hardware Implementation”). A CPU core finds work inside one thread through out-of-order execution; an SM does not, and instead finds work across many warps.

  • Turing（sm_75，T4）：每个 SM 有 4 个 warp 调度器，每个调度器管一组固定的 warp，向自己专属的一组运算单元发射；调度器每个周期都能发射一条独立的指令。每个 SM 有 64 个 FP32 核、64 个 INT32 核和 8 个 Tensor Core（Turing Tuning Guide）。
  • Turing (sm_75, T4): each SM has 4 warp schedulers; each handles a static set of warps and issues to its own dedicated set of arithmetic units, and each can issue an independent instruction every cycle. Each SM has 64 FP32 cores, 64 INT32 cores and 8 Tensor Cores (Turing Tuning Guide).
  • 每个 SM 能驻留多少：编程指南的 compute capability 表给出，sm_75 每 SM 最多 32 个 warp（1024 个线程）、16 个 block；sm_89（Ada，比如 L4）是 48 个 warp（1536 个线程）、24 个 block；sm_80（A100）是 64 个 warp、32 个 block。三者每个 SM 都是 64 K 个 32 位寄存器，每线程最多 255 个，每个 block 最多 64 K 个；每 SM 的 shared memory 最多 64 KB（sm_75）、100 KB（sm_89）、164 KB（sm_80）。表里的 K 和 KB 都按 1024 算。
  • How much an SM can hold: the compute-capability table of the programming guide gives, for sm_75, at most 32 warps (1024 threads) and 16 blocks per SM; for sm_89 (Ada, such as the L4), 48 warps (1536 threads) and 24 blocks; for sm_80 (A100), 64 warps and 32 blocks. All three have 64 K 32-bit registers per SM, at most 255 per thread and at most 64 K per block; shared memory per SM is at most 64 KB (sm_75), 100 KB (sm_89) and 164 KB (sm_80). K and KB in the table both mean 1024.
  • 调度器的个数：本页读过的 CUDA 文档只对 Turing 写明了「4 个」；Ada Tuning Guide 和新版编程指南都没有写。更新的架构请以 NVIDIA 的架构白皮书为准，本页不替它们给数。
  • The scheduler count: of the CUDA documents read for this page, only the Turing one states “4”; neither the Ada Tuning Guide nor the current programming guide states it. For newer architectures, rely on NVIDIA’s architecture whitepapers; this page gives no number for them.

2. 用切换 warp 藏起延迟

2. Hiding latency by switching warps

SM 上每个 warp 的执行上下文（程序计数器、寄存器等）在 warp 的整个生命期内都留在片上，所以「在 warp 之间切换没有代价」；每个发射周期，warp 调度器挑一个下一条指令已经可以执行的 warp，把这条指令发给它的活动线程（编程指南，「Hardware Multithreading」）。一个 warp 卡住的原因有很多：在等全局内存的数据、在等上一条指令的结果、在等 __syncthreads() 屏障。只要还有别的 warp 能发射，这个周期就没浪费；动画 (a) 画的就是这件事。

The execution context of each warp on an SM (program counters, registers and so on) stays on chip for the warp’s whole lifetime, so “switching between warps incurs no cost”; at each issue cycle a warp scheduler picks a warp whose next instruction is ready to run and issues it to that warp’s active threads (programming guide, “Hardware Multithreading”). A warp stalls for many reasons: waiting for data from global memory, waiting for the result of its previous instruction, waiting at a __syncthreads() barrier. As long as some other warp can issue, the cycle is not wasted; diagram (a) draws exactly this.

  • 算术延迟要几个 warp：Turing Tuning Guide 给了一个具体的数：相互依赖的 FMA 之间的发射延迟是 4 个周期，所以每个 SM 只要 16 个 warp（4 个调度器 × 4 个周期）就能藏住算术延迟；如果每个 warp 自己有 4 路互不依赖的指令（指令级并行，ILP），4 个 warp 就够。
  • How many warps arithmetic latency takes: the Turing Tuning Guide gives a concrete figure: the dependent issue latency of core FMA operations is 4 cycles, so 16 warps per SM (4 schedulers × 4 cycles) hide arithmetic latency, and if each warp has 4 independent instructions of its own (instruction-level parallelism, ILP), 4 warps are enough.
  • 内存延迟要多得多：一次全局内存读要等几百个周期（大致数量级，Phase 1），用同样的道理，要藏住它需要每个调度器手里有更多个 warp，或者每个线程同时挂起好几次读。这就是 Phase 0 的 Little 定律落到一个 SM 上的样子：驻留的 warp 越多，在途的读就越多。
  • Memory latency takes far more: a global-memory read waits hundreds of cycles (an approximate order of magnitude; Phase 1), so by the same reasoning hiding it needs many more warps per scheduler, or several reads in flight per thread. This is Phase 0’s Little’s law brought down to one SM: the more warps are resident, the more reads are in flight.
  • 两条路：多驻留几个 warp（提高 occupancy，概念 3），或者让每个线程自己多做几件互不依赖的事（ILP，比如每个线程处理 4 个元素）。Best Practices Guide 明确说，ILP 高的内核有时在低 occupancy 下也能完全藏住延迟。
  • Two routes: keep more warps resident (raise occupancy, concept 3), or give each thread several independent things to do (ILP, such as four elements per thread). The Best Practices Guide states plainly that a kernel with a high degree of ILP can, in some cases, fully cover latency at low occupancy.

3. Occupancy 与它的限制因素

3. Occupancy and what limits it

occupancy 是一个 SM 上活动的 warp 数和它最多能驻留的 warp 数之比。编程指南说，一个 SM 上能同时驻留多少个 block 和 warp，取决于内核用了多少寄存器和 shared memory、SM 有多少，以及每 SM 的 block 数和 warp 数上限；如果连一个 block 的资源都不够，内核启动失败。四个限制同时起作用，occupancy 由最紧的那个决定。下面用 T4（sm_75：32 个 warp、16 个 block、64 K 个寄存器、64 KB shared memory）的数字逐个算，算法是从上面的文档数字推出来的，不是测量值：

Occupancy is the ratio of active warps on an SM to the most warps it can hold. The programming guide says that how many blocks and warps can reside on an SM at once depends on the registers and shared memory the kernel uses, how much the SM has, and the per-SM limits on blocks and warps; if there is not enough for even one block, the kernel fails to launch. The four limits act together, and the tightest one sets the occupancy. Below, each is worked through with the T4’s numbers (sm_75: 32 warps, 16 blocks, 64 K registers, 64 KB shared memory); the arithmetic is derived from the documented figures above, not measured:

  • 寄存器：寄存器按 warp 分配，每个 warp 向上取整到 256 个寄存器的倍数（Best Practices Guide，「Calculating Occupancy」），而且一个 block 的寄存器一次分完。每线程 64 个寄存器时，一个 warp 用 64 × 32 = 2048 个，65536 / 2048 = 32 个 warp，T4 正好满（100%）；每线程 128 个时只剩 16 个 warp（50%）。同一个 64 寄存器的内核放到 sm_89 上，寄存器同样只够 32 个 warp，但那里上限是 48，所以只有 67%。
  • Registers: registers are allocated per warp, rounded up to a multiple of 256 registers per warp (Best Practices Guide, “Calculating Occupancy”), and a block’s registers are allocated all at once. At 64 registers per thread a warp uses 64 × 32 = 2048, and 65536 / 2048 = 32 warps, exactly full on a T4 (100%); at 128 per thread only 16 warps fit (50%). The same 64-register kernel on sm_89 also fits only 32 warps by registers, but the limit there is 48, so it reaches only 67%.
  • shared memory：shared memory 按 block 分。每个 block 用 48 KB 时，64 KB 的 SM 只放得下 1 个 block；block 是 256 个线程，也就是 8 个 warp，occupancy 只有 25%。静态声明的 shared memory 每 block 最多 48 KB，超过要用动态 shared memory 并显式开启（编程指南）。
  • Shared memory: shared memory is allocated per block. At 48 KB per block, a 64 KB SM holds only 1 block; with 256 threads, that is 8 warps, so occupancy is 25%. Statically declared shared memory is limited to 48 KB per block; going beyond needs dynamic shared memory and an explicit opt-in (programming guide).
  • block 太小：每 SM 最多 16 个 block。block 只有 32 个线程（1 个 warp）时，16 个 block 只有 16 个 warp，50%；block 至少 64 个线程，T4 上这一项才不卡。
  • Blocks that are too small: an SM holds at most 16 blocks. With 32 threads (1 warp) per block, 16 blocks are only 16 warps, 50%; from 64 threads per block up, this limit stops binding on a T4.
  • block 太大：资源按整个 block 分，block 越大，「装不下一个整 block」时浪费的越多。极端情况：每线程 96 个寄存器、每 block 1024 个线程，需要 98304 个寄存器，超过每 block 64 K 的上限，内核根本启动不了，cudaGetLastError 报资源不足。Best Practices Guide 建议总是写上 __launch_bounds__(maxThreadsPerBlock)，让编译器按你会用的最大 block 来控制寄存器。
  • Blocks that are too large: resources are handed out per whole block, so the larger the block, the more is wasted when the remainder cannot hold one more whole block. At the extreme, 96 registers per thread and 1024 threads per block need 98,304 registers, above the 64 K per-block limit, and the kernel does not launch at all; cudaGetLastError reports too many resources. The Best Practices Guide recommends always writing __launch_bounds__(maxThreadsPerBlock) so the compiler budgets registers for the largest block you will launch.

Occupancy is not the goal in itself: the Best Practices Guide states that raising occupancy from 66 percent to 100 percent generally does not give a similar speed-up. Squeezing registers with -maxrregcount=N (per file) or __launch_bounds__ (per kernel) raises occupancy, but the variables that no longer fit spill to local memory, which lives in DRAM. Whether to squeeze is a measurement question (Lab A step 5; Phase 4 looks at it properly with the profiler).

4. warp 内的分支发散

4. Branch divergence inside a warp

一个 warp 一次执行一条公共指令，所以 32 个线程走同一条路径时效率最高。编程指南：如果 warp 里的线程因为依赖数据的条件分支而走了不同的路，warp 会把每条被走到的路径都执行一遍，同时屏蔽不在这条路径上的线程；发散只发生在一个 warp 之内，不同的 warp 各走各的，互不影响。所以代价看的是「一个 warp 里有没有两种走法」，不是「整个 grid 里有没有两种走法」。动画 (b) 一步步画出来。

A warp executes one common instruction at a time, so it is most efficient when all 32 threads follow the same path. The programming guide: if threads of a warp diverge through a data-dependent conditional branch, the warp executes each branch path taken, disabling the threads that are not on that path; divergence occurs only within a warp, and different warps execute independently. So the cost depends on whether one warp contains both choices, not on whether the whole grid does. Diagram (b) draws it step by step.

  • 按 warp 对齐写条件：block 切成 warp 的方式是确定的（线程编号连续，第一个 warp 从线程 0 开始），所以条件只依赖 threadIdx.x / warpSize 时，没有一个 warp 会发散（Best Practices Guide，「Branching and Divergence」）。if (threadIdx.x % 2) 让每个 warp 都发散；if ((threadIdx.x / 32) % 2) 一个也不发散，而两者都让一半线程走 A、一半走 B。
  • Write conditions aligned to warps: the way a block is cut into warps is deterministic (consecutive thread IDs, the first warp starting at thread 0), so when a condition depends only on threadIdx.x / warpSize, no warp diverges (Best Practices Guide, “Branching and Divergence”). if (threadIdx.x % 2) makes every warp diverge; if ((threadIdx.x / 32) % 2) makes none diverge, yet both send half the threads down A and half down B.
  • 短分支常常不算数：分支体只有几条指令时，编译器可能用谓词执行（predication）代替真正的跳转：所有指令都发射，只有谓词为真的线程写结果。这时没有 warp 会发散，损失很小。Lab 里的两条路径都是 2000 次的循环，故意让编译器无法这样做。
  • Short branches often do not count: when a branch body is only a few instructions, the compiler may use predication instead of a real jump: every instruction is issued, and only threads with a true predicate write results. Then no warp diverges and the loss is small. Both paths in the labs are 2000-iteration loops, deliberately too long for that.
  • 循环次数不同也是发散：for (k = 0; k < len[i]; ++k) 里各线程的 len 不同，warp 要跑到最长的那个线程做完为止，其余线程陪着空转。不规则数据（稀疏矩阵、图）里的主要损失常在这里。
  • Different trip counts are divergence too: in for (k = 0; k < len[i]; ++k) with a different len per thread, the warp keeps going until its longest thread finishes, and the others idle along. In irregular data (sparse matrices, graphs) this is often where most of the loss is.

5. 独立线程调度（Volta 起）与 __syncwarp

5. Independent thread scheduling (Volta on) and __syncwarp

compute capability 7.0 之前，一个 warp 的 32 个线程共用一个程序计数器，外加一个标记哪些线程活动的掩码。从 7.0（Volta）起，GPU 为每个线程保存执行状态，包括程序计数器和调用栈，可以按线程粒度让出执行；一个调度优化器决定把同一个 warp 里哪些活动线程编成一个 SIMT 单元，线程可以在小于 warp 的粒度上发散和重新汇合（编程指南，「Independent Thread Scheduling」）。T4 是 7.5，所以本主题的所有 GPU 都是这种行为；CUDA 13 已经移除了 Turing（7.5）之前所有架构的支持。

Before compute capability 7.0, the 32 threads of a warp shared one program counter plus a mask of which threads were active. From 7.0 (Volta) on, the GPU keeps execution state per thread, including a program counter and call stack, and can yield execution at per-thread granularity; a schedule optimizer decides how to group active threads of the same warp into SIMT units, and threads can diverge and reconverge at sub-warp granularity (programming guide, “Independent Thread Scheduling”). The T4 is 7.5, so every GPU in this topic behaves this way; CUDA 13 has removed support for every architecture before Turing (7.5).

  • 它带来了什么：同一个 warp 里的线程现在可以互相等待（比如一个线程等另一个线程放开一把锁），不会像以前那样因为共用程序计数器而死锁。
  • What it brought: threads of one warp can now wait on each other (for example, one thread waiting for another to release a lock) without the deadlock a shared program counter used to cause.
  • 它打破了什么：老代码常假设「一个 warp 的线程每条指令都齐步走」，于是不加同步就通过 shared memory 在 warp 内交换数据（不加同步的 warp 内归约就是典型）。编程指南说这种假设现在不成立，这类代码必须用 __syncwarp() 显式同步。__syncwarp(mask) 让 mask 里的线程在这里会合，并保证它们之间的内存顺序；不写参数时 mask 是全部 32 个线程（C++ Language Extensions）。
  • What it broke: old code often assumed that the threads of a warp move in lockstep at every instruction, and exchanged data within a warp through shared memory without synchronising (the synchronisation-free intra-warp reduction is the classic case). The programming guide says that assumption no longer holds, and such code must synchronise explicitly with __syncwarp(). __syncwarp(mask) makes the threads named in mask meet there and orders memory among them; with no argument, mask is all 32 threads (C++ Language Extensions).

下面是一个 warp 通过 shared memory 求 32 个整数的和：每一轮先读、再写，读和写之间、写和下一轮读之间各放一个 __syncwarp()。去掉它们，在 Volta 以后的 GPU 上可能读到另一个线程还没写完的值。Phase 3 会用 warp shuffle（__shfl_down_sync）把它写得更快，那一族函数的名字里带着 _sync 和一个 mask 参数，原因相同。

Below, one warp sums 32 integers through shared memory: each round reads, then writes, with a __syncwarp() between the read and the write and between the write and the next read. Remove them, and on GPUs from Volta on a thread may read a value another thread has not finished writing. Phase 3 writes this faster with warp shuffles (__shfl_down_sync); that family of functions carries _sync in its name and a mask argument for the same reason.

// warp_sum.cu: one warp sums 32 ints through shared memory; launch with 32 threads per block
__global__ void warp_sum(const int* in, int* out) {
  __shared__ int s[32];
  unsigned t = threadIdx.x;
  s[t] = in[blockIdx.x * 32 + t];
  __syncwarp();                               // every write of s is visible before anyone reads
  for (int off = 16; off > 0; off /= 2) {
    int v = (t < off) ? s[t + off] : 0;       // read phase
    __syncwarp();                             // all reads finish before any write
    if (t < off) s[t] += v;                   // write phase
    __syncwarp();                             // all writes finish before the next read
  }
  if (t == 0) out[blockIdx.x] = s[0];
}

6. block 怎样分到各个 SM，以及一次启动底下发生了什么

6. How blocks reach the SMs, and what happens under a launch

block 调度：一个 grid 可以有几百万个 block，GPU 却只有几十到几百个 SM。一个 block 的所有线程由同一个 SM 执行，多数情况下在那个 SM 上一直跑到结束；block 之间没有调度上的保证，可以按任何顺序执行，所以一个 block 不能依赖另一个 block 的结果（编程指南，「Programming Model」）。每个 SM 按概念 3 的限制同时放 k 个 block，整块 GPU 一次能跑 SM 数 × k 个，这叫一波（wave）；剩下的 block 等前面的结束再上。这引出一个实用的推论（推断，Phase 4 用剖析器验证）：T4 有 40 个 SM（NVIDIA 给出 2560 个 CUDA 核，Turing 每个 SM 64 个 FP32 核），若每个 SM 放 4 个 block，一波是 160 个；一个 161 个 block 的 grid 要跑两波，第二波只有 1 个 block 在干活，这叫尾部效应（tail effect）。block 数远大于一波时，这点浪费就被摊薄了。

Block scheduling: a grid may have millions of blocks, while the GPU has only tens or hundreds of SMs. All threads of a block are executed by one SM and, in most cases, run to completion on it; there is no scheduling guarantee between blocks, which may run in any order, so a block must not depend on another block’s results (programming guide, “Programming Model”). Each SM holds k blocks at once under the limits of concept 3, so the whole GPU runs SMs × k blocks at a time, which is called a wave; the remaining blocks start as earlier ones finish. A practical consequence follows (an inference; Phase 4 checks it with the profiler): a T4 has 40 SMs (NVIDIA gives 2,560 CUDA cores, and a Turing SM has 64 FP32 cores), so at 4 blocks per SM one wave is 160 blocks, and a grid of 161 blocks runs two waves, the second with a single block at work. This is the tail effect. When the block count is far larger than one wave, that waste is spread thin.

The launch path: kernel<<<grid, block>>>(args) is rewritten by nvcc into a call to the CUDA runtime, whose public entry point is cudaLaunchKernel, which in turn hands off to the user-mode CUDA driver (an inference: the glue code nvcc generates is not documented). NVIDIA publishes the hardware side of the interface in open-gpu-doc, from which a rough path can be drawn; the CUDA user-mode driver is closed source, so which step is done by whom below is inference:

  1. 启动描述符：Turing 的计算类（TURING_COMPUTE_A）用一个叫 QMD 的结构描述一次启动。它的头文件里有 grid 宽度（CTA_RASTER_WIDTH）、block 维度（CTA_THREAD_DIMENSION0）、每线程寄存器数（REGISTER_COUNT）、shared memory 大小（SHARED_MEMORY_SIZE）和常量缓冲区地址等字段。寄存器数和 shared memory 就写在启动描述符里，这正是硬件按它们决定一个 SM 放几个 block 的原因（推断）。内核参数大致放在其中一个常量缓冲区里（大致）。
  2. The launch descriptor: Turing’s compute class (TURING_COMPUTE_A) describes a launch with a structure called the QMD. Its header has fields for the grid width (CTA_RASTER_WIDTH), the block dimensions (CTA_THREAD_DIMENSION0), registers per thread (REGISTER_COUNT), the shared-memory size (SHARED_MEMORY_SIZE), constant-buffer addresses and more. The register count and shared memory are written into the launch descriptor itself, which is why the hardware can use them to decide how many blocks fit on an SM (an inference). Kernel arguments go, approximately, into one of those constant buffers.
  3. 命令进入通道：驱动把指向 QMD 的命令写进一个 pushbuffer（内存里的命令流），再在通道的 GPFIFO 环里加一项指向这段 pushbuffer。TURING_CHANNEL_GPFIFO_A 类的头文件记录了 GPFIFO 项和 pushbuffer 方法的格式。
  4. Commands enter a channel: the driver writes commands that point at the QMD into a pushbuffer (a command stream in memory), then adds an entry to the channel’s GPFIFO ring pointing at that stretch of pushbuffer. The header of the TURING_CHANNEL_GPFIFO_A class records the format of GPFIFO entries and pushbuffer methods.
  5. 敲门铃：驱动往一个 MMIO 寄存器写一下，告诉 GPU 这个通道有新工作；Turing 的 usermode 手册把 NOTIFY_CHANNEL_PENDING 称为通道的门铃寄存器（doorbell），并说 USERMODE 是一段「可映射的、供用户态驱动使用的」寄存器。所以一次启动通常不需要系统调用（推断：闭源的 CUDA 驱动是否每次都这样做，没有文档）。这就是 Kernel Engineering Phase 5 讲的「环形队列 + 门铃寄存器」。
  6. Ringing the doorbell: the driver makes one MMIO write to tell the GPU the channel has new work; Turing’s usermode manual calls NOTIFY_CHANNEL_PENDING the channel doorbell register and describes USERMODE as “a mappable range of registers for use by usermode drivers”. So a launch usually needs no system call (an inference: whether the closed CUDA driver always does it this way is not documented). This is the “ring plus doorbell register” of Kernel Engineering Phase 5.
  7. GPU 取命令、分 block：GPU 的命令前端用 DMA 从内存读 GPFIFO 和 pushbuffer，计算引擎读 QMD，再把 block 一个个分给有空余资源的 SM（大致；分配器的细节没有公开）。内核本身的代码早在模块加载时就已经放进了 device 内存。
  8. The GPU fetches commands and hands out blocks: the GPU’s command front end reads the GPFIFO and the pushbuffer from memory by DMA, the compute engine reads the QMD, and then hands blocks one by one to SMs with free resources (approximate; the distributor’s details are not public). The kernel’s own code was placed in device memory long before, when the module was loaded.

这条路径解释了 Phase 0 量到的「每次启动几微秒的固定开销」大致从哪来，也解释了 Phase 5 的 CUDA graph 为什么能省时间：把一串启动预先录好，一次提交。

This path roughly explains where the fixed cost of a few microseconds per launch seen in Phase 0 comes from, and why Phase 5’s CUDA graphs save time: a series of launches is recorded in advance and submitted at once.

  • An SM issues in order without speculation, and it hides latency by switching among resident warps, a switch that costs nothing.
  • Occupancy is active warps over the maximum, set by the tightest of registers, shared memory, the per-SM block limit and the warp limit.
  • Resources go to whole blocks: on a T4, a 256-thread block at 64 registers per thread fits 4 blocks (100%), and at 72 only 3 (75%).
  • Occupancy is not the goal in itself: a kernel with high ILP can hide latency at low occupancy, and squeezing registers may spill to local memory in DRAM.
  • Divergence happens only within a warp, and the two paths run one after the other; a condition aligned to threadIdx.x / 32 does not diverge.
  • Since Volta each thread has its own program counter, so data exchanged within a warp through shared memory needs __syncwarp().

常见误解

Common misconceptions

  • 误解：occupancy 越高越快，100% 才是对的。→ 实际：Best Practices Guide 写明，从 66% 提到 100% 一般不会带来同样比例的提速；该不该提要量。
  • 误解：grid 里只要有线程走了不同的分支，就会发散。→ 实际：发散只看一个 warp 内部；if ((threadIdx.x / 32) % 2) 同样让一半线程走 A，却没有一个 warp 发散，Lab B 在 M5 上量到 1.00 到 1.01 倍。
  • 误解：一个 warp 的线程总是齐步走，所以 warp 内不用同步。→ 实际：从 compute capability 7.0 起线程可以在小于 warp 的粒度上发散和汇合，编程指南要求这类代码用 __syncwarp()。
  • Myth: higher occupancy is always faster, and 100% is the right target. → Fact: the Best Practices Guide states that going from 66% to 100% generally does not give a similar speed-up; whether to raise it is a measurement question.
  • Myth: if any threads in the grid take different branches, the kernel diverges. → Fact: divergence is decided inside one warp; if ((threadIdx.x / 32) % 2) also sends half the threads down A, yet no warp diverges, and Lab B measured 1.00 to 1.01 times on the M5.
  • Myth: the threads of a warp always move in lockstep, so a warp needs no synchronisation. → Fact: from compute capability 7.0 on, threads can diverge and reconverge below warp granularity, and the programming guide requires such code to use __syncwarp().

// R values stay live across the loop, so the register count grows with R
template <int R>
__global__ void pressure(const float* a, float* c, int n, int iters) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i >= n) return;
  float v[R];
#pragma unroll
  for (int k = 0; k < R; ++k) v[k] = a[i] * float(k + 1);
  for (int t = 0; t < iters; ++t) {
#pragma unroll
    for (int k = 0; k < R; ++k) v[k] = fmaf(v[k], v[(k + 1) % R], 0.5f);
  }
  float s = 0.0f;
#pragma unroll
  for (int k = 0; k < R; ++k) s += v[k];
  c[i] = s;
}

// uses dynamic shared memory, sized at launch, to show the shared-memory limiter
__global__ void staged(const float* a, float* c, int n) {
  extern __shared__ float tile[];
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  tile[threadIdx.x] = (i < n) ? a[i] : 0.0f;
  __syncthreads();
  if (i < n) c[i] = tile[blockDim.x - 1 - threadIdx.x];
}

// two paths of equal cost; mode 0: all lanes take A; mode 1: alternate warps take A or B;
// mode 2: alternate lanes take A or B, so every warp diverges
__global__ void branchy(const float* a, float* c, int n, int iters, int mode) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i >= n) return;
  float x = a[i];
  bool takeA = (mode == 0) ? true : (mode == 1) ? (((i / 32) & 1) == 0) : ((i & 1) == 0);
  if (takeA) {
    for (int t = 0; t < iters; ++t) x = fmaf(x, 1.0001f, 0.3f);
  } else {
    for (int t = 0; t < iters; ++t) x = fmaf(x, 0.9999f, -0.7f);
  }
  c[i] = x;
}

template <class K>
void report(const char* name, K kernel, const cudaDeviceProp& p, size_t smem) {
  cudaFuncAttributes fa;
  CUDA_CHECK(cudaFuncGetAttributes(&fa, kernel));
  std::printf("%-12s regs=%3d local_bytes=%zu smem_dyn=%6zu |", name, fa.numRegs, fa.localSizeBytes, smem);
  const int maxWarps = p.maxThreadsPerMultiProcessor / p.warpSize;
  for (int block : {32, 64, 128, 256, 512, 1024}) {
    int blocks = 0;
    CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocks, kernel, block, smem));
    const int warps = blocks * ((block + p.warpSize - 1) / p.warpSize);
    std::printf("  b%-4d %2d blk %3d%%", block, blocks, 100 * warps / maxWarps);
  }
  std::printf("\n");
}

3. 一段为 Pascal 写的 warp 内归约，通过 shared memory 交换数据，没有任何同步，靠「一个 warp 齐步走」保证正确。在 T4 上它会怎样？

3. An intra-warp reduction written for Pascal exchanges data through shared memory with no synchronisation at all, relying on the warp moving in lockstep. What happens on a T4?

warp 的大小没变，但独立线程调度让每个线程有自己的程序计数器，同一个 warp 的线程可以不在同一条指令上，所以 a 的理由不成立。编译器不会检查这种数据竞争，代码照样编译，这正是它危险的地方，所以 c 不对。编程指南要求这类代码用 __syncwarp() 显式同步，概念 5 的例子就是这样写的。The warp size did not change, but independent thread scheduling gives each thread its own program counter, so threads of one warp need not be on the same instruction, and a’s reasoning fails. The compiler does not check for this data race and the code compiles as before, which is exactly what makes it dangerous, so c is wrong. The programming guide requires such code to synchronise explicitly with __syncwarp(), as the example in concept 5 does.

4. ptxas 报告一个内核每线程用 96 个寄存器。你在 T4 上用 <<<grid, 1024>>> 启动它。会发生什么？

4. ptxas reports that a kernel uses 96 registers per thread. You launch it on a T4 with <<<grid, 1024>>>. What happens?

一个 block 要么整块放上一个 SM，要么放不上，不存在「不到一个 block」，所以 b 不对。寄存器数是编译时由 ptxas 定下、写进启动描述符的，驱动在启动时不会重新分配寄存器，所以 c 不对。编程指南说，资源连一个 block 都不够时内核启动失败。A block either fits on an SM whole or not at all; there is no “less than one block”, so b is wrong. The register count is fixed at build time by ptxas and written into the launch descriptor, and the driver does not reallocate registers at launch, so c is wrong. The programming guide says that if there are not enough resources for even one block, the kernel fails to launch.
