1. 运行时 API 与驱动 API

1. The runtime API and the driver API

前六课用的 cudaMalloc、cudaMemcpy、<<< >>> 都属于 CUDA 运行时 API（库 cudart，随工具链发布）。编程指南（「CUDA Runtime API and CUDA Driver API」一节，2026-09-10 版）说，运行时建立在更底层的 驱动 API 之上；驱动 API 由驱动安装时放到系统里的动态库实现（Linux 上是 libcuda.so），入口都以 cu 开头。两者能做的事基本一样，区别在于谁替你管理什么：

The cudaMalloc, cudaMemcpy and <<< >>> of the first six phases all belong to the CUDA runtime API (the cudart library, shipped with the toolkit). The programming guide (“CUDA Runtime API and CUDA Driver API”, edition of 2026-09-10) says the runtime is built on a lower-level driver API, implemented in a dynamic library that the driver installation puts on the system (libcuda.so on Linux), with every entry point prefixed cu. The two can do essentially the same things; what differs is who manages what for you:

  • 上下文：驱动 API 要先 cuInit(0)，再取得一个上下文（context）并设为当前。指南把上下文比作 CPU 上的进程：一切资源都装在里面，各自有独立的地址空间。运行时在第一次调用时隐式建好每个设备的 primary context；驱动 API 可以用 cuDevicePrimaryCtxRetain 拿到同一个，两套 API 因此能混用。
  • Contexts: the driver API needs cuInit(0) first, then a context made current. The guide compares a context to a process on the CPU: every resource lives inside it, each with its own address space. The runtime implicitly creates each device’s primary context on first use; the driver API can obtain the same one with cuDevicePrimaryCtxRetain, which is why the two APIs can be mixed.
  • 模块与启动：运行时把你的 kernel 编进可执行文件，<<< >>> 在背后找到它。驱动 API 要你显式加载模块（cuModuleLoad 读 PTX 或 cubin 文件），按名字取函数（cuModuleGetFunction），再用 cuLaunchKernel 传参数指针数组启动。指南写明：想在未来架构上运行的程序必须加载 PTX，因为二进制码绑定某一代架构，而 PTX 由驱动在加载时编译。
  • Modules and launches: the runtime compiles your kernels into the executable and <<< >>> finds them behind the scenes. The driver API makes you load a module explicitly (cuModuleLoad reads a PTX or cubin file), fetch the function by name (cuModuleGetFunction), and launch it with cuLaunchKernel and an array of argument pointers. The guide states that an application meant to run on future architectures must load PTX, because binary code is tied to one architecture while PTX is compiled by the driver at load time.
  • 什么时候用驱动 API：指南说大多数程序只用运行时就能达到全部性能；但新接口有时先出现在驱动 API，有些高级接口（例如虚拟内存管理）只在驱动 API 里有。在线编译（NVRTC 生成 PTX，再由 cuModuleLoadData 加载）、语言运行时和 JIT 编译器（Triton 就是一例，推断）也常走这一层。
  • When to use the driver API: the guide says most applications reach full performance with the runtime alone; but new interfaces sometimes appear in the driver API first, and some advanced ones (such as virtual memory management) exist only there. Runtime compilation (NVRTC producing PTX, then cuModuleLoadData loading it), language runtimes and JIT compilers (Triton is one; an inference) also tend to work at this level.
  • 两个版本号：cudaRuntimeGetVersion 返回编译时用的工具链版本（13.4 表示为 13040）；cudaDriverGetVersion 返回驱动支持的最高 CUDA 版本。nvidia-smi 右上角的「CUDA Version」是后者。Lab A 的程序两个都打印，概念 5 解释两者不同时会怎样。
  • Two version numbers: cudaRuntimeGetVersion returns the toolkit version the program was built with (13.4 reads as 13040); cudaDriverGetVersion returns the highest CUDA version the driver supports. The “CUDA Version” in the top-right corner of nvidia-smi is the latter. Lab A’s program prints both, and concept 5 explains what happens when they differ.

2. PTX 与 SASS

2. PTX and SASS

nvcc 的设备端编译分两个阶段（nvcc 文档「GPU Compilation」一章，2026-10-12 版）：

nvcc compiles device code in two stages (the “GPU Compilation” chapter of the nvcc documentation, edition of 2026-10-12):

  1. 阶段 1：源代码到 PTX。PTX（Parallel Thread Execution）是一种虚拟 GPU 的汇编语言，总是以文本形式存在。文档说这个虚拟 GPU「完全由它提供的能力来定义」，名字是 compute_75、compute_89 这样的虚拟架构。PTX ISA 文档（9.4 版，随 CUDA 13.4 和 r615 驱动发布）列出它的目标之一：提供一个跨越多代 GPU 的稳定 ISA。PTX 文件开头的 .version 是 PTX ISA 的版本，.target 是它假定的架构。
  2. Stage 1: source to PTX. PTX (Parallel Thread Execution) is the assembly language of a virtual GPU and always exists as text. The documentation says this virtual GPU is “defined entirely by the set of capabilities” it provides, with names such as compute_75 and compute_89 for the virtual architectures. The PTX ISA document (version 9.4, released with CUDA 13.4 and the r615 driver) lists among its goals a stable ISA that spans multiple GPU generations. The .version line at the top of a PTX file is the PTX ISA version, and .target is the architecture it assumes.
  3. 阶段 2：PTX 到 SASS。ptxas 把 PTX 编成某一代真实硬件（sm_75、sm_89）的机器码，叫 SASS；装着 SASS 的 ELF 文件叫 cubin。SASS 的指令和编码每一代主版本都不一样，所以 nvcc 文档说，跨主计算能力的二进制兼容没有保证：为 9.0 编的程序不能在 10.0 上跑，反过来也不行。
  4. Stage 2: PTX to SASS. ptxas compiles PTX into machine code for one real hardware generation (sm_75, sm_89), called SASS; the ELF file holding SASS is a cubin. SASS instructions and encodings differ with every major version, so the nvcc documentation says binary compatibility is not guaranteed across major compute capabilities: code built for 9.0 does not run on 10.0, nor the reverse.

一个规则决定一次编译是否合法：真实架构必须实现了那个虚拟架构。nvcc 文档的建议是虚拟架构尽量低（能跑的 GPU 越多）、真实架构尽量高（代码越好）。看产物用 CUDA Binary Utilities：cuobjdump -ptx 取出 PTX 文本，cuobjdump -sass 反汇编 SASS，cuobjdump -lelf 和 -lptx 列出可执行文件里嵌了哪些 cubin 和 PTX；nvdisasm 只收 cubin，但输出选项更多。Lab A 第 3 步在作品项目的可执行文件上跑这几条命令。

One rule decides whether a compilation is valid: the real architecture must implement the virtual one. The nvcc documentation advises choosing the virtual architecture as low as possible (so more GPUs can run it) and the real architecture as high as possible (so the code is better). To look at the output, use the CUDA Binary Utilities: cuobjdump -ptx extracts the PTX text, cuobjdump -sass disassembles the SASS, and cuobjdump -lelf and -lptx list which cubins and PTX an executable embeds; nvdisasm accepts only cubins but offers richer output. Step 3 of Lab A runs these commands on the capstone executable.

3. JIT 与 fatbin

3. JIT and fatbins

两阶段本身并不让程序在未来的 GPU 上跑起来。nvcc 文档说，靠的是另外两个机制：

The two stages on their own do not make a program run on future GPUs. The nvcc documentation names the two mechanisms that do:

  • JIT（即时编译）：可执行文件里带 PTX 时，驱动在加载时把它编成当前 GPU 的 SASS。编程指南（「PTX Compatibility」）说，compute_80 的 PTX 可以在运行时 JIT 到 sm_120 这样更新的架构，但只能往相同或更高的计算能力编。代价是启动变慢；驱动会把结果存进 compute cache（Linux 默认 ~/.nv/ComputeCache，大小由 CUDA_CACHE_MAXSIZE 控制，服务器上默认 1 GiB），驱动升级后缓存自动作废，于是程序能用上新驱动里更好的 JIT 编译器。
  • JIT (just-in-time compilation): when the executable carries PTX, the driver compiles it at load time into SASS for the GPU at hand. The programming guide (“PTX Compatibility”) says PTX for compute_80 can be JIT-compiled at run time to a newer architecture such as sm_120, but only to an equal or higher compute capability. The price is a slower start; the driver stores the result in the compute cache (on Linux by default ~/.nv/ComputeCache, sized by CUDA_CACHE_MAXSIZE, 1 GiB by default on servers), and the cache is invalidated automatically when the driver is upgraded, so the program picks up the improved JIT compiler of the new driver.
  • fatbin：同一份设备代码的多个译本装在一个容器里，嵌进主机可执行文件。可以有几个 cubin（每代硬件一个）加一份或几份 PTX。指南的说法：程序运行时，驱动从 fatbin 里为当前 GPU 挑最合适的那一个；有完全匹配的 cubin 就直接用，没有才拿 PTX 去 JIT。
  • Fatbins: several translations of the same device code in one container embedded in the host executable, typically a few cubins (one per hardware generation) plus one or more PTX versions. In the guide’s words, when the program runs the driver picks the best one in the fatbin for the GPU at hand; a matching cubin is used directly, and PTX is JIT-compiled only when there is none.
  • 同一主版本内的二进制兼容：指南写明，在同一个主计算能力内，次版本相同或更高的 GPU 能加载 cubin：为 8.6 编的 cubin 能在 8.6 和 8.9 上跑，不能在 8.0 上跑。所以 sm_75 的 cubin 在 T4（7.5）上直接跑，在 L4（8.9）上不能用，L4 只能靠 PTX。计算能力 10.0 起，同族内的兼容改由驱动在加载时「重新定稿」cubin（off-target finalization），比 PTX JIT 便宜；9.x 及更早的 cubin 不参与。
  • Binary compatibility within a major version: the guide states that within one major compute capability, a GPU whose minor version is equal or higher can load a cubin: a cubin built for 8.6 runs on 8.6 and 8.9 but not on 8.0. So an sm_75 cubin runs directly on a T4 (7.5) but is useless on an L4 (8.9), which must rely on PTX. From compute capability 10.0, compatibility within a family is handled by the driver re-finalising the cubin at load time (off-target finalization), which is cheaper than PTX JIT; cubins for 9.x and earlier are not eligible.
  • 两个用来验证的环境变量（编程指南「CUDA Environment Variables」）：CUDA_FORCE_PTX_JIT=1 让驱动忽略所有 cubin、一律 JIT 嵌入的 PTX，用来确认 PTX 真的在、JIT 真的能用；CUDA_DISABLE_PTX_JIT=1 反过来禁止 JIT，没有兼容 cubin 的 kernel 会加载失败，用来确认每个 kernel 都有对口的 cubin。Lab A 第 4 步两个都用。
  • Two environment variables for checking (programming guide, “CUDA Environment Variables”): CUDA_FORCE_PTX_JIT=1 makes the driver ignore every cubin and JIT the embedded PTX, which confirms that the PTX is there and that JIT works; CUDA_DISABLE_PTX_JIT=1 does the opposite and forbids JIT, so a kernel without a compatible cubin fails to load, which confirms every kernel has a matching cubin. Step 4 of Lab A uses both.

Metal 这边的对应物：本专题的每个 Metal 程序都用 makeLibrary(source:) 在运行时从源码编译 kernel，相当于 NVRTC 加 JIT 一步做完（类比，推断）；Apple 的离线编译器 xcrun metal 不在 Command Line Tools 里，所以这里没有对应 fatbin 的离线产物可看。

On the Metal side the counterpart is that every Metal program in this topic compiles its kernels from source at run time with makeLibrary(source:), roughly NVRTC and JIT in one step (an analogy, an inference); Apple’s offline compiler, xcrun metal, is not part of the Command Line Tools, so there is no offline fatbin-like artefact to inspect here.

4. -arch、--gpu-code 与 -gencode

4. -arch, --gpu-code and -gencode

三种写法其实是同一件事：告诉 nvcc 阶段 1 用哪个虚拟架构、阶段 2 为哪些真实架构生成 SASS、要不要把 PTX 也放进 fatbin。下面每条都摘自或按 nvcc 文档（「--gpu-architecture」「--generate-code」「NVCC Examples」）的规则展开：

The three spellings say the same thing: which virtual architecture stage 1 uses, which real architectures stage 2 generates SASS for, and whether PTX also goes into the fatbin. Each line below is quoted from, or expanded by the rules of, the nvcc documentation (“--gpu-architecture”, “--generate-code”, “NVCC Examples”):

  • -arch=sm_75：简写。只给真实架构、不给 --gpu-code 时，nvcc 用最接近的虚拟架构，并把它和真实架构都放进去，等价于 --gpu-architecture=compute_75 --gpu-code=sm_75,compute_75：一个 sm_75 cubin 加一份 compute_75 PTX。本专题每个实验都这样编，所以它们在 L4 上也能跑（靠 JIT）。
  • -arch=sm_75: the shorthand. Given only a real architecture and no --gpu-code, nvcc uses the closest virtual architecture and embeds both, which is equivalent to --gpu-architecture=compute_75 --gpu-code=sm_75,compute_75: one sm_75 cubin plus compute_75 PTX. Every lab in this topic builds this way, which is why they also run on an L4 (through JIT).
  • 不加任何选项：文档写明，CUDA 13.4 的 nvcc x.cu 等价于 --gpu-architecture=compute_75 --gpu-code=sm_75,compute_75，因为 Turing 是这个版本支持的最老架构。
  • No options at all: the documentation states that in CUDA 13.4 nvcc x.cu is equivalent to --gpu-architecture=compute_75 --gpu-code=sm_75,compute_75, since Turing is the oldest architecture this release supports.
  • --gpu-architecture=compute_75 --gpu-code=compute_75：只放 PTX，不放 SASS，把阶段 2 完全推迟到加载时。能跑的 GPU 最多，每台机器第一次启动都要 JIT。
  • --gpu-architecture=compute_75 --gpu-code=compute_75: PTX only, no SASS, deferring stage 2 entirely to load time. It runs on the most GPUs, and every machine pays for JIT on first launch.
  • -gencode（即 --generate-code）：前两种写法整次编译只能有一个虚拟架构；-gencode arch=…,code=… 可以重复，每次给一对。--gpu-architecture=X --gpu-code=Y,… 等价于 --generate-code=arch=X,code=Y,…；code 可以写成列表 code=[sm_80,sm_86]；code 是虚拟架构时放的是 PTX。用了不同虚拟架构，设备代码要靠 __CUDA_ARCH__ 做条件编译。
  • -gencode (that is, --generate-code): the first two forms allow one virtual architecture per compilation; -gencode arch=…,code=… can be repeated, one pair each time. --gpu-architecture=X --gpu-code=Y,… is equivalent to --generate-code=arch=X,code=Y,…; code may be a list, code=[sm_80,sm_86]; when code is a virtual architecture, PTX is embedded. With several virtual architectures, device code uses __CUDA_ARCH__ for conditional compilation.

5. 兼容性与 NGC 容器

5. Compatibility and the NGC container

概念 3 讲的是代码和 GPU 的兼容；这里讲工具链和 驱动 的兼容。CUDA Compatibility 文档（2026-09-09 版）把它分成三种，判断标准是驱动（libcuda.so）比编程序时的运行时新还是旧：

Concept 3 was about compatibility between code and the GPU; this one is about the toolkit and the driver. The CUDA Compatibility guide (edition of 2026-09-09) splits it three ways, by whether the driver (libcuda.so) is newer or older than the runtime the program was built with:

  • 向后兼容（驱动更新）：新驱动跑旧工具链编的程序，没有附加条件。这是最常见、最省事的升级方式。
  • Backward compatibility (newer driver): a newer driver runs programs built with an older toolkit, with no conditions. This is the commonest and simplest way to upgrade.
  • 小版本兼容（驱动更旧，主版本相同）：从 CUDA 11 起，同一主版本内的程序能在不低于最低版本的驱动上跑，CUDA 13.x 要求驱动 ≥ 580。文档列了三条限制：一些同时依赖新工具链和新驱动的功能会返回 cudaErrorCallRequiresNewerDriver；把设备代码编成 PTX 的程序在旧驱动上不能工作；必须给 nvcc 指定目标架构（-arch=sm_xx），让 fatbin 里有 SASS。原因可以从 PTX ISA 的发布历史看出来：CUDA 13.0 配 r580 驱动和 PTX ISA 9.0，CUDA 13.4 配 r615 和 PTX ISA 9.4；r580 里的 JIT 编译器不认识 9.4 的 PTX（推断，对应的错误是 cudaErrorUnsupportedPtxVersion：「PTX 由比 CUDA 驱动和 PTX JIT 编译器更新的编译器生成」）。
  • Minor-version compatibility (older driver, same major): from CUDA 11 on, a program from one major release runs on any driver at or above a minimum, which for CUDA 13.x is ≥ 580. The guide lists three caveats: some features that span both toolkit and driver return cudaErrorCallRequiresNewerDriver; applications that compile device code to PTX will not work on older drivers; and the target architecture must be given to nvcc (-arch=sm_xx) so the fatbin carries SASS. The PTX release history shows why: CUDA 13.0 came with the r580 driver and PTX ISA 9.0, CUDA 13.4 with r615 and PTX ISA 9.4, and the JIT compiler inside r580 does not know PTX 9.4 (an inference; the matching error is cudaErrorUnsupportedPtxVersion, “the PTX was generated by a compiler newer than what is supported by the CUDA driver and PTX JIT compiler”).
  • 向前兼容（驱动更旧，主版本也更旧）：装一个 cuda-compat-<主>-<次> 包，例如 cuda-compat-13-4，它带的是 615 驱动的用户态库（libcuda.so、PTX JIT 编译器等），装在 /usr/local/cuda-13.4/compat/，要自己用 LD_LIBRARY_PATH 指过去。文档说它只适用于 NVIDIA 数据中心 GPU、部分 NGC Server Ready 的 RTX 卡和 Jetson；它定义在内核驱动和 CUDA 驱动之间，所以没有小版本兼容的 PTX 限制。
  • Forward compatibility (older driver, older major too): install a cuda-compat-<major>-<minor> package, such as cuda-compat-13-4, which carries the user-mode libraries of the 615 driver (libcuda.so, the PTX JIT compiler and others) under /usr/local/cuda-13.4/compat/; you point LD_LIBRARY_PATH at it yourself. The guide says it applies only to NVIDIA data-center GPUs, selected NGC Server Ready RTX cards and Jetson boards; it is defined between the kernel driver and the CUDA driver, so the PTX restriction of minor-version compatibility does not apply.

文档还提到一个 2026 年的变化：从 CUDA 13.4 起，Linux 驱动不再和工具链打包发布，要单独获取。

The guide also notes a 2026 change: from CUDA 13.4 on, the NVIDIA Linux driver is no longer bundled with the toolkit and must be obtained separately.

6. 可移植性：HIP、SYCL、Kokkos 与 Apple 上的 Metal

6. Portability: HIP, SYCL, Kokkos, and Metal on Apple

CUDA 只跑在 NVIDIA GPU 上。想让同一份算法跑到别家硬件，有四条常见的路，抽象程度从低到高（概述，各自的细节以官方文档为准）：

CUDA runs only on NVIDIA GPUs. There are four common roads to running the same algorithm on other hardware, from the least abstract to the most (an outline; the details of each are in its official documentation):

  • HIP（AMD ROCm）：HIP 文档（7.16.0 版）的定义是「面向 AMD GPU 的 C++ 运行时 API 和 kernel 语言」。它的 API 和 CUDA 一一对照（hipMalloc、hipMemcpy、同样的 <<< >>>），HIPIFY 工具（基于 clang 的 hipify-clang 和基于 Perl 的 hipify-perl）把 CUDA 调用改写成 HIP 调用，hipBLAS、hipFFT 等库对应 cuBLAS、cuFFT。文档同时说明 HIP 不是 CUDA 的直接替代品，移植要预期手工修改和重新调优。warp 宽度就是一处要改的地方：本专题的 kernel 处处假定 32（0xffffffff 掩码、threadIdx.x % 32），而 AMD 部分 GPU 的 wavefront 是 64（推断，按 AMD 架构文档的一般说法，本页未逐型号核对）。
  • HIP (AMD ROCm): the HIP documentation (version 7.16.0) defines it as “a C++ runtime API and kernel language for AMD GPUs”. Its API mirrors CUDA one for one (hipMalloc, hipMemcpy, the same <<< >>>), the HIPIFY tools (the clang-based hipify-clang and the Perl-based hipify-perl) rewrite CUDA calls as HIP calls, and libraries such as hipBLAS and hipFFT stand in for cuBLAS and cuFFT. The documentation also says HIP is not a drop-in replacement for CUDA, and that porting should expect manual changes and retuning. Warp width is one such change: this topic’s kernels assume 32 everywhere (the 0xffffffff mask, threadIdx.x % 32), while some AMD GPUs use 64-wide wavefronts (an inference from AMD’s architecture documentation in general; this page did not check model by model).
  • SYCL（Khronos 标准）：单源（single-source）的标准 C++ 异构编程模型，当前规范是 SYCL 2020（Khronos 页面 2026-10-31 读取时为第 11 次修订）。kernel 写成 lambda，通过队列提交；实现有 Intel oneAPI 的 DPC++、独立的 AdaptiveCpp 等，Khronos 页面说这些实现除 OpenCL 外还接了多种加速器后端。某个实现能否在 NVIDIA GPU 上跑、怎样跑，要看那个实现的文档（本页没有核对）。
  • SYCL (a Khronos standard): a single-source, standard-C++ model for heterogeneous programming; the current specification is SYCL 2020 (at revision 11 when the Khronos page was read on 2026-10-31). Kernels are written as lambdas and submitted through queues; implementations include Intel oneAPI’s DPC++ and the independent AdaptiveCpp, and the Khronos page says these add several accelerator back ends besides OpenCL. Whether and how a given implementation runs on NVIDIA GPUs is in that implementation’s documentation (not checked here).
  • Kokkos：一个 C++ 性能可移植库。Kokkos Core 文档说它提供并行执行和数据管理两类抽象（parallel_for 等并行模式，View 多维数组），后端可以是 CUDA、HIP、SYCL、HPX、OpenMP 和 C++ 线程。你写一次，换后端重新编译；数据布局由 View 按后端决定。代价是离硬件更远：warp shuffle、shared memory 这类细节要通过它的层次并行接口间接表达，或者干脆放弃。
  • Kokkos: a C++ performance-portability library. The Kokkos Core documentation says it provides abstractions for both parallel execution and data management (parallel patterns such as parallel_for, and View multidimensional arrays), with CUDA, HIP, SYCL, HPX, OpenMP and C++ threads as back ends. You write once and rebuild for another back end; View chooses the data layout per back end. The price is distance from the hardware: details such as warp shuffles and shared memory have to be expressed indirectly through its hierarchical-parallelism interface, or given up.
  • Apple 上的 Metal：没有可移植层，是另一套原生 API，本专题每一课的 Lab B 都在做这件事。术语对照：kernel 函数 ↔ kernel 函数，grid/block/thread ↔ grid/threadgroup/thread，warp ↔ SIMD-group（这台 M5 上 threadExecutionWidth 打印出 32），shared memory ↔ threadgroup memory，__syncthreads ↔ threadgroup_barrier，__shfl_xor_sync 的归约 ↔ simd_max、simd_sum，stream ↔ 命令队列和命令缓冲区，cuBLAS 和 cuDNN 的角色 ↔ Metal Performance Shaders。移植作品项目时，算法和字节模型原样不变，变的只是这些名字和启动方式：Lab B 就是证明。
  • Metal on Apple: no portability layer, just another native API, which is what every Lab B in this topic has done. The term map: kernel function ↔ kernel function, grid/block/thread ↔ grid/threadgroup/thread, warp ↔ SIMD-group (threadExecutionWidth prints 32 on this M5), shared memory ↔ threadgroup memory, __syncthreads ↔ threadgroup_barrier, reductions with __shfl_xor_sync ↔ simd_max and simd_sum, stream ↔ command queue and command buffer, and the role of cuBLAS and cuDNN ↔ Metal Performance Shaders. Porting the capstone leaves the algorithm and the byte model unchanged; only these names and the launch code change, as Lab B shows.

8. 作品项目的算法：融合与在线 softmax

8. The capstone’s algorithm: fusion and online softmax

对矩阵 X 的每一行，softmax 是 yj = exp(xj − m) / d，其中 m 是这一行的最大值（减去它防止 exp 溢出，结果不变），d = Σ exp(xj − m)。直接照公式写，是三遍：求 m、求 d、写 y。本页的两个版本：

For each row of a matrix X, softmax is yj = exp(xj − m) / d, where m is the row’s maximum (subtracted so exp cannot overflow; the result is unchanged) and d = Σ exp(xj − m). Written straight from the formula it takes three passes: find m, find d, write y. This page’s two versions:

  • 未融合（四个 kernel）：row_max 写出 m；exp_sub 把 e = exp(x − m) 整个写回全局内存；row_sum 读 e 得到 d；divide 读 e 写 y。这是把 softmax 拆成几个现成算子时的样子。字节模型：读 x、x、e、e，写 e、y，共 6MN 个 float。
  • Unfused (four kernels): row_max writes m; exp_sub writes the whole of e = exp(x − m) back to global memory; row_sum reads e to get d; divide reads e and writes y. This is what softmax looks like when composed from ready-made operators. Byte model: read x, x, e, e and write e, y, 6MN floats in all.
  • 融合（一个 kernel，每行一个 block）：用 Milakov 和 Gimelshein（2018）的在线归一化，第一遍每个线程同时维护自己看到的最大值 m 和和 d；遇到更大的值 v 时，先把旧的和按 exp(m − m′) 缩放到新的最大值 m′ = max(m, v)，再加上 exp(v − m′)。然后整个 block 用 warp shuffle 和 shared memory 先归约 m，再把每个线程的 d 缩放到全局最大值后求和（Phase 3 的模式）。第二遍再读一次 x，写出 y。字节模型：读 x 两遍、写 y 一遍，共 3MN 个 float；如果一行小到第二遍能从缓存里读，就只有 2MN 次内存访问。
  • Fused (one kernel, one block per row): using Milakov and Gimelshein’s online normalizer (2018), each thread keeps both the maximum m and the sum d of what it has seen in a single first pass; when a larger value v arrives, it first rescales the old sum to the new maximum m′ = max(m, v) by exp(m − m′), then adds exp(v − m′). The block then reduces m with warp shuffles and shared memory, rescales every thread’s d to the global maximum and sums them (Phase 3’s pattern). A second pass reads x again and writes y. Byte model: read x twice, write y once, 3MN floats; if a row is small enough for the second pass to read from cache, only 2MN memory accesses remain.

两者都远在 roofline 的访存受限一侧（每个元素只有几次运算），所以时间由搬的字节决定，预测是融合版快 2 到 3 倍。Lab B 在 M5 上量到：4096 列时快 2.8 倍，32768 列时快 2.1 倍，正好落在这两端；动画 (b) 和 Lab B 第 4 步解释为什么。layer norm（每行求均值和方差，再归一化）是同一个形状：同样两次行内归约，同样可以融合，Welford 算法扮演在线 softmax 的角色（推断：本页没有实现 layer norm）。

Both sit far on the memory-bound side of the roofline (a few operations per element), so time is set by bytes moved, and the prediction is that the fused version is 2 to 3 times as fast.     // 未运行 · not run; assembled from the CUDA documentation on 2026-10-31
// softmax_kernels.cuh: the capstone kernels, shared by softmax_capstone.cu and softmax_op.cu
#pragma once
#include <cuda_runtime.h>
#include <cmath>

constexpr int TB = 256;                                  // threads per block: 8 warps

__device__ float warp_max(float v) { for (int o = 16; o > 0; o >>= 1) v = fmaxf(v, __shfl_xor_sync(0xffffffffu, v, o)); return v; }
__device__ float warp_sum(float v) { for (int o = 16; o > 0; o >>= 1) v += __shfl_xor_sync(0xffffffffu, v, o); return v; }

// block-wide max or sum; every thread gets the result
template <bool IsMax> __device__ float block_reduce(float v) {
    __shared__ float scratch[32];
    int lane = threadIdx.x % 32, w = threadIdx.x / 32;
    v = IsMax ? warp_max(v) : warp_sum(v);
    if (lane == 0) scratch[w] = v;
    __syncthreads();
    if (w == 0) {
        float x = lane < blockDim.x / 32 ? scratch[lane] : (IsMax ? -INFINITY : 0.0f);
        x = IsMax ? warp_max(x) : warp_sum(x);
        if (lane == 0) scratch[0] = x;
    }
    __syncthreads();
    float r = scratch[0];
    __syncthreads();                                     // scratch may be reused right after
    return r;
}

// ---- unfused: four kernels ----
__global__ void row_max(const float* x, float* m, int n) {
    float v = -INFINITY;
    for (int j = threadIdx.x; j < n; j += blockDim.x) v = fmaxf(v, x[size_t(blockIdx.x) * n + j]);
    v = block_reduce<true>(v);
    if (threadIdx.x == 0) m[blockIdx.x] = v;
}
__global__ void exp_sub(const float* x, const float* m, float* e, int n, size_t count) {
    size_t i = size_t(blockIdx.x) * blockDim.x + threadIdx.x;
    if (i < count) e[i] = expf(x[i] - m[i / n]);
}
__global__ void row_sum(const float* e, float* s, int n) {
    float v = 0.0f;
    for (int j = threadIdx.x; j < n; j += blockDim.x) v += e[size_t(blockIdx.x) * n + j];
    v = block_reduce<false>(v);
    if (threadIdx.x == 0) s[blockIdx.x] = v;
}
__global__ void divide(const float* e, const float* s, float* y, int n, size_t count) {
    size_t i = size_t(blockIdx.x) * blockDim.x + threadIdx.x;
    if (i < count) y[i] = e[i] / s[i / n];
}

// ---- fused: one block per row; pass 1 keeps a running (max, sum) per thread, pass 2 writes ----
// extern "C" keeps the name unmangled, so the driver API can find it by name in the PTX
extern "C" __global__ void softmax_fused(const float* x, float* y, int n) {
    const float* xr = x + size_t(blockIdx.x) * n;
    float m = -INFINITY, d = 0.0f;
    for (int j = threadIdx.x; j < n; j += blockDim.x) {
        float v = xr[j], m2 = fmaxf(m, v);
        d = d * expf(m - m2) + expf(v - m2);             // rescale the old sum when the max grows
        m = m2;
    }
    float gm = block_reduce<true>(m);
    float gd = block_reduce<false>(d * expf(m - gm));
    float inv = 1.0f / gd;
    for (int j = threadIdx.x; j < n; j += blockDim.x) y[size_t(blockIdx.x) * n + j] = expf(xr[j] - gm) * inv;
}

// softmax_capstone.cu: row-wise softmax over an M x N float matrix, unfused (four kernels, intermediates in global
// memory) and fused (one block per row, online max and sum, warp shuffles), timed with events against a CPU reference
// build: nvcc -arch=sm_75 -O3 -lineinfo softmax_capstone.cu -o softmax_capstone
#include <algorithm>
#include <cmath>
#include <cstdio>
#include <cstdlib>
#include <vector>
#include <cuda_runtime.h>

#define CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) { \
    std::fprintf(stderr, "%s:%d %s\n", __FILE__, __LINE__, cudaGetErrorString(e_)); std::exit(1); } } while (0)
#include "softmax_kernels.cuh"

int main() {
    int rt = 0, drv = 0;
    CHECK(cudaRuntimeGetVersion(&rt)); CHECK(cudaDriverGetVersion(&drv));
    cudaDeviceProp p; CHECK(cudaGetDeviceProperties(&p, 0));
    std::printf("device=%s cc=%d.%d runtime=%d driver=%d\n", p.name, p.major, p.minor, rt, drv);
    const int warm = 3, reps = 21;
    const int shapes[3][2] = {{4096, 1024}, {4096, 4096}, {1024, 32768}};
    for (const auto& sh : shapes) {
        int M = sh[0], N = sh[1];
        size_t cnt = size_t(M) * N, bytes = cnt * sizeof(float);
        std::vector<float> hx(cnt), hy(cnt);
        for (size_t i = 0; i < cnt; ++i) hx[i] = float((i * 37) % 1000) / 100 - 5;   // values in [-5, 5)
        float *x, *y, *e, *m, *s;
        CHECK(cudaMalloc(&x, bytes)); CHECK(cudaMalloc(&y, bytes)); CHECK(cudaMalloc(&e, bytes));
        CHECK(cudaMalloc(&m, M * sizeof(float))); CHECK(cudaMalloc(&s, M * sizeof(float)));
        CHECK(cudaMemcpy(x, hx.data(), bytes, cudaMemcpyHostToDevice));
        // CPU reference in double for rows 0, M/2 and M-1
        const int rows[3] = {0, M / 2, M - 1};
        std::vector<double> ref(3 * size_t(N));
        for (int k = 0; k < 3; ++k) {
            const float* r = &hx[size_t(rows[k]) * N];
            double mx = -INFINITY, sum = 0;
            for (int j = 0; j < N; ++j) mx = std::max(mx, double(r[j]));
            for (int j = 0; j < N; ++j) sum += std::exp(double(r[j]) - mx);
            for (int j = 0; j < N; ++j) ref[size_t(k) * N + j] = std::exp(double(r[j]) - mx) / sum;
        }
        auto max_err = [&]() {
            CHECK(cudaMemcpy(hy.data(), y, bytes, cudaMemcpyDeviceToHost));
            double err = 0;
            for (int k = 0; k < 3; ++k)
                for (int j = 0; j < N; ++j) err = std::max(err, std::fabs(hy[size_t(rows[k]) * N + j] - ref[size_t(k) * N + j]));
            CHECK(cudaMemset(y, 0, bytes));
            return err;
        };
        unsigned eb = unsigned((cnt + TB - 1) / TB);
        auto unfused = [&] {
            row_max<<<M, TB>>>(x, m, N);
            exp_sub<<<eb, TB>>>(x, m, e, N, cnt);
            row_sum<<<M, TB>>>(e, s, N);
            divide<<<eb, TB>>>(e, s, y, N, cnt);
        };
        auto fused = [&] { softmax_fused<<<M, TB>>>(x, y, N); };
        // byte model per run: unfused reads x, x, e, e and writes e, y (6 MN floats); fused reads x twice, writes y (3 MN)
        struct Run { const char* name; double gb; };
        const Run runs[2] = {{"unfused", 6.0 * cnt * 4 / 1e9}, {"fused", 3.0 * cnt * 4 / 1e9}};
        for (const Run& r : runs) {
            cudaEvent_t t0, t1;
            CHECK(cudaEventCreate(&t0)); CHECK(cudaEventCreate(&t1));
            std::vector<float> ms;
            for (int it = 0; it < warm + reps; ++it) {
                CHECK(cudaEventRecord(t0));
                if (r.name[0] == 'u') unfused(); else fused();
                CHECK(cudaGetLastError());
                CHECK(cudaEventRecord(t1));
                CHECK(cudaEventSynchronize(t1));
                float t = 0; CHECK(cudaEventElapsedTime(&t, t0, t1));
                if (it >= warm) ms.push_back(t);
            }
            std::sort(ms.begin(), ms.end());
            float med = ms[ms.size() / 2];
            std::printf("M=%5d N=%5d %-7s median_ms=%8.3f min=%8.3f max=%8.3f modelGB/s=%6.1f maxErr=%.2e\n",
                        M, N, r.name, med, ms.front(), ms.back(), r.gb / (med / 1e3), max_err());
            CHECK(cudaEventDestroy(t0)); CHECK(cudaEventDestroy(t1));
        }
        CHECK(cudaFree(x)); CHECK(cudaFree(y)); CHECK(cudaFree(e)); CHECK(cudaFree(m)); CHECK(cudaFree(s));
    }
    return 0;
}

// reduce one value per thread to one value per threadgroup (max or sum), result in every thread
inline float tg_reduce(float v, bool isMax, threadgroup float* scratch, uint lane, uint sg, uint nsg) {

自测

Self-check

1. 一个程序只用 nvcc -arch=sm_89 编译，拿到 T4（cc 7.5）上运行。会怎样？

1. A program built only with nvcc -arch=sm_89 is run on a T4 (cc 7.5). What happens?

PTX 只能 JIT 到相同或更高的计算能力，compute_89 编不到 7.5，a 不对。cubin 只能在同一主版本内、次版本相同或更高的 GPU 上运行，8.9 的 SASS 既不同主版本、也不是更低的目标，b 不对。fatbin 里没有能用的东西，对应 cudaErrorNoKernelImageForDevice。PTX can be JIT-compiled only to an equal or higher compute capability, so compute_89 cannot become 7.5 code, which rules out a. A cubin runs only within the same major version on a GPU of equal or higher minor version, and 8.9 SASS is a different major version and a higher target, which rules out b. Nothing in the fatbin is usable, which is cudaErrorNoKernelImageForDevice.

2. 一台机器的驱动是 r580（CUDA 13.0），你用 CUDA 13.4 的容器编译程序。按 CUDA Compatibility 文档，哪种构建最可能在这台机器上正常运行？

2. A machine has the r580 driver (CUDA 13.0), and you build in a CUDA 13.4 container. According to the CUDA Compatibility guide, which build is most likely to run there?

同一主版本内的小版本兼容允许 13.x 的程序在 ≥ 580 的驱动上运行，所以 c 不对；但文档列出的限制之一是把设备代码编成 PTX 的程序在旧驱动上不能工作，因为旧驱动的 JIT 不认识新的 PTX ISA，所以 b 不对；文档要求给 nvcc 指定目标架构，就是为了让 fatbin 里有 SASS。Minor-version compatibility lets a 13.x program run on any driver ≥ 580, which rules out c; but one of the caveats the guide lists is that programs compiling device code to PTX do not work on older drivers, since the old JIT does not know the newer PTX ISA, which rules out b; the guide requires a target architecture for nvcc precisely so that the fatbin carries SASS.

3. 在线 softmax 里，一个线程已经看过的元素的最大值是 m、和是 d（按 m 缩放过），现在读到一个更大的值 v。它应当怎样更新？

3. In the online softmax, a thread has seen elements with maximum m and sum d (scaled to m), and now reads a larger value v. How should it update?

d 里的每一项都是 exp(x − m)，换到新最大值 v 后应是 exp(x − v) = exp(x − m) · exp(m − v)，所以整个旧和乘 exp(m − v)，再加上新元素自己的 exp(v − v) = 1。a 没有缩放旧和，还按旧最大值加了新项，既错又可能溢出；c 丢掉了已经读过的元素。Each term in d is exp(x − m); under the new maximum v it should be exp(x − v) = exp(x − m) · exp(m − v), so the whole old sum is multiplied by exp(m − v), and the new element adds its own exp(v − v) = 1. Option a does not rescale the old sum and adds the new term against the old maximum, which is wrong and can overflow; c throws away the elements already read.

4. 你用 TORCH_LIBRARY 注册了一个 CUDA 算子，在 eager 模式下工作正常，但 torch.compile 追踪它时失败。最可能缺了什么？

4. You registered a CUDA operator with TORCH_LIBRARY; it works in eager mode, but torch.compile fails to trace it. What is most likely missing?

PyTorch 教程说，要支持 torch.compile，算子需要一个 FakeTensor kernel，它只根据输入的元数据算出输出的形状、步长、类型和设备，追踪时不碰真实数据。+PTX 决定 fatbin 里有没有 PTX，与追踪无关，b 不对；在当前流以外的流上启动会破坏 PyTorch 的执行顺序，是错误做法，c 不对。The PyTorch tutorial says that to support torch.compile an operator needs a FakeTensor kernel, which works out the output’s shape, strides, type and device from the inputs’ metadata, so tracing never touches real data. +PTX decides whether the fatbin carries PTX and has nothing to do with tracing, which rules out b; launching on a stream other than the current one breaks PyTorch’s ordering and is wrong, which rules out c.
