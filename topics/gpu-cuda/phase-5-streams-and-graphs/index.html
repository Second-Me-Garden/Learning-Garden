核心概念

Core concepts

1. 流与事件

1. Streams and events

CUDA Programming Guide 2.5 节（13.4 版，2026-10-31 读取）把流定义为一个按顺序执行的任务队列：同一个流里的拷贝和 kernel 一个接一个完成，不同流里的工作之间没有顺序，可以并发。kernel 启动和 cudaMemcpyAsync 对主机都是异步的：调用把任务放进队列就返回，主机线程接着往下走。

Section 2.5 of the CUDA Programming Guide (version 13.4, read 2026-10-31) defines a stream as a queue of tasks executed in order: copies and kernels in one stream complete one after another, while work in different streams has no order between it and may run concurrently. Kernel launches and cudaMemcpyAsync are asynchronous to the host: the call puts the task in the queue and returns, and the host thread carries on.

  • 建流。cudaStreamCreate(&s) 建的是阻塞流；cudaStreamCreateWithFlags(&s, cudaStreamNonBlocking) 建的是非阻塞流。kernel 用第四个启动参数选流：k<<<grid, block, 0, s>>>(…)。
  • Creating streams. cudaStreamCreate(&s) creates a blocking stream; cudaStreamCreateWithFlags(&s, cudaStreamNonBlocking) creates a non-blocking one. A kernel picks its stream with the fourth launch parameter: k<<<grid, block, 0, s>>>(…).
  • 默认流。不指定流的工作进入旧式默认流（legacy default stream，也叫 NULL 流或 0 号流）。指南 2.5.6 写明：它和所有阻塞流互相同步，和非阻塞流不同步。编译选项 --default-stream per-thread 让每个主机线程有自己的默认流，不再有这种全局同步。所以一个忘了指定流的 cudaMemcpy 会悄悄地把所有阻塞流串起来。
  • The default stream. Work with no stream goes to the legacy default stream, also called the NULL stream or stream 0. Section 2.5.6 of the guide states that it synchronizes with every blocking stream and not with non-blocking ones. The compiler option --default-stream per-thread gives each host thread its own default stream without that global synchronization. So one cudaMemcpy that forgot its stream quietly serializes every blocking stream.
  • 事件。cudaEventRecord(e, s) 在流 s 里放一个标记，前面的工作完成时它才算发生。cudaStreamWaitEvent(s2, e) 让流 s2 之后的工作等这个标记，等待发生在 GPU 一侧，主机不阻塞；这就是两个流之间的一条依赖边。cudaEventSynchronize(e) 才让主机等。cudaEventElapsedTime(&ms, a, b) 给出两个事件之间的毫秒数；只用来表达依赖的事件可以用 cudaEventDisableTiming 建，省掉计时。
  • Events. cudaEventRecord(e, s) puts a marker into stream s that counts as having happened once the work before it is done. cudaStreamWaitEvent(s2, e) makes later work in stream s2 wait for that marker; the waiting happens on the GPU side and the host does not block, so this is a dependence edge between two streams. Only cudaEventSynchronize(e) makes the host wait. cudaEventElapsedTime(&ms, a, b) gives the milliseconds between two events; an event used only for a dependence can be created with cudaEventDisableTiming to skip the timing.

Metal 一侧（SDK 头文件 MTLCommandQueue.h、MTLCommandBuffer.h、MTLEvent.h，2026-10-31 读取）：命令队列（MTLCommandQueue）在头文件里写作「一个串行的命令缓冲区队列」；命令缓冲区里放一个或多个编码器（计算、blit），对应 CUDA 一个流里的一段工作。跨队列的依赖用 MTLSharedEvent：encodeSignalEvent(_:value:) 在一个命令缓冲区里发出一个值，encodeWaitForEvent(_:value:) 让另一个命令缓冲区等这个值，两者都只能在没有打开的编码器时调用。它对应 cudaEventRecord 加 cudaStreamWaitEvent，只是事件带一个单调递增的 64 位计数，而不是「发生过一次」。计时用命令缓冲区的 gpuStartTime 和 gpuEndTime。

On the Metal side (the SDK headers MTLCommandQueue.h, MTLCommandBuffer.h and MTLEvent.h, read 2026-10-31), a command queue (MTLCommandQueue) is described in its header as a serial queue of command buffers; a command buffer holds one or more encoders (compute, blit), the counterpart of a run of work in one CUDA stream. A dependence across queues uses an MTLSharedEvent: encodeSignalEvent(_:value:) signals a value from one command buffer and encodeWaitForEvent(_:value:) makes another command buffer wait for it; both may be called only when no encoder is open. It plays the part of cudaEventRecord plus cudaStreamWaitEvent, except that the event carries a 64-bit counter that only goes up rather than a single happened-once state. Timing uses the command buffer’s gpuStartTime and gpuEndTime.

2. 拷贝和计算的重叠，以及为什么要页锁定内存

2. Overlapping copies with kernels, and why pinned memory is required

一块独立的 GPU 有专门的拷贝引擎，通过 PCIe 做 DMA，和 SM 上的 kernel 是两套硬件。它们能同时忙，前提是工作分在不同的流里，而且互不依赖。设备属性 asyncEngineCount（运行时 API 的说明是 Number of asynchronous engines）告诉你有几个：有 2 个时，拷入和拷出也能同时进行；concurrentKernels 说明不同流的 kernel 能否同时跑。Lab A 会打印这两个值。

A discrete GPU has dedicated copy engines that do DMA over PCIe, separate hardware from the kernels on the SMs. They can be busy at the same time, provided the work sits in different streams and does not depend on itself. The device property asyncEngineCount (described in the runtime API as Number of asynchronous engines) tells how many there are: with 2, a copy in and a copy out can also run at once; concurrentKernels says whether kernels from different streams can run together. Lab A prints both.

切块流水。把 n 个元素切成 c 块，第 k 块的拷入、kernel、拷出都放进流 k。设整份数据的拷入、计算、拷出各要时间 T，串行一共 3T；切块以后每段只要 T / c，三段像流水线一样错开，总时间约为 (c + 2) · T / c。c = 4 时是 1.5T，正好是串行的一半；c 越大越接近 T，但每块越小，固定开销占比越大。这个公式假设两个方向的拷贝能同时进行（两个拷贝引擎）、三段时间相等；实际的瓶颈是三段里最慢的那一段。图解 (a) 画的就是 c = 4 的情形。

Chunked pipelining. Split n elements into c chunks and put chunk k’s copy in, kernel and copy out into stream k. If the copy in, the compute and the copy out of the whole data each take time T, serial work takes 3T; in chunks each stage takes only T / c, the three stages stagger like a pipeline, and the total is about (c + 2) · T / c. At c = 4 that is 1.5T, exactly half of serial; a larger c approaches T, but the smaller each chunk, the more the fixed overhead weighs. The formula assumes the two copy directions run at once (two copy engines) and the three stages take equal time; in practice the bottleneck is the slowest of the three. Diagram (a) draws the case c = 4.

为什么必须页锁定。指南 2.5.2.3 的原话是：要让涉及 CPU 内存的拷贝异步进行，主机缓冲区必须是 pinned 且 page-locked 的；用普通内存时 cudaMemcpyAsync() 仍然正确，但会退回同步行为，不和其他工作重叠。原因在 DMA（推断，按 Kernel Engineering 专题的分页和 DMA 两课推出，指南没有展开）：拷贝引擎按物理地址读写内存，而普通的 malloc 内存是可分页的，操作系统随时可以把一页换出或挪走，DMA 进行到一半时物理页不能变。所以驱动对可分页内存只能先把数据拷进自己的一块页锁定暂存区，再从那里 DMA（这一步 Runtime API 参考的「API synchronization behavior」一页，2026-10-12 版，有明文：可分页缓冲区先被复制到用于 DMA 传输的中转内存），这一步要 CPU 参与，没法和别的工作并行。cudaMallocHost 直接给你页锁定的内存；运行时 API 的说明还提醒：它的带宽比可分页内存高得多，但分配太多会减少系统可用于分页的内存、拖慢整个系统，所以只该用来做和 GPU 交换数据的暂存区。

Why pinned memory is required. Section 2.5.2.3 of the guide says that for memory copies involving CPU memory to be carried out asynchronously, the host buffers must be pinned and page-locked; with ordinary memory cudaMemcpyAsync() still works correctly but reverts to synchronous behaviour and does not overlap other work. The reason lies in DMA (inference, drawn from the paging and DMA lessons of the Kernel Engineering topic; the guide does not spell it out): the copy engine reads and writes memory by physical address, while ordinary malloc memory is pageable, so the operating system may page it out or move it at any moment, and the physical page must not change in the middle of a DMA. For pageable memory the driver therefore has to copy the data into a page-locked staging area of its own first and DMA from there (this step is stated in the Runtime API reference page “API synchronization behavior”, 2026-10-12 version: “the pageable buffer has been copied to the staging memory for DMA transfer to device memory”), a step that needs the CPU and cannot run alongside other work. cudaMallocHost gives you page-locked memory directly; the runtime API notes that it has much higher bandwidth than pageable memory, but that allocating too much of it reduces the memory the system has for paging and slows the whole system, so it is best kept for staging areas that exchange data with the GPU.

Apple 的统一内存没有这个问题，也没有这份收益。CPU 和 GPU 读写同一块物理内存（MTLStorageModeShared），不需要 PCIe 拷贝，也就没有可以藏起来的拷贝时间。Lab B 量到：在 M5 上，一次 256 MB 的 blit 拷贝和一个小 kernel 放在两个队列上，并没有重叠，总跨度反而比两者单独时间之和略长。可能的原因是 blit 在这里用的是同一组 GPU 核心和同一条内存通路，而不是独立的 DMA 引擎（推断，Apple 没有公开 blit 的实现）。
Apple’s unified memory has neither this problem nor this gain. CPU and GPU read and write the same physical memory (MTLStorageModeShared), so there is no PCIe copy and no copy time to hide. Lab B measured that on the M5 a 256 MB blit copy and a small kernel on two queues did not overlap; their combined span was slightly longer than the sum of their separate times. A likely reason is that the blit here uses the same GPU cores and the same memory path rather than a separate DMA engine (inference; Apple does not document how blits are implemented).

3. CUDA graph：捕获、实例化、重放

3. CUDA graphs: capture, instantiate, replay

指南 4.2 节先讲了 graph 要解决的问题：每把一个 kernel 放进流，主机上的驱动都要做一串准备工作才能让它在 GPU 上跑，这是每个 kernel 都要付的开销；kernel 本身很短时，这笔开销会占端到端时间的很大一部分。把一个要跑很多次的工作流做成 graph，这些开销就只在实例化时为整个图付一次，之后每次启动整个图的开销都很小。（这里的驱动工作就是 Kernel Engineering Phase 5 讲的 MMIO 和命令提交。）

Section 4.2 of the guide starts with the problem graphs solve: each time a kernel goes into a stream, the driver on the host performs a sequence of operations to set it up and launch it on the GPU, an overhead paid for every kernel; for a kernel with a short execution time this overhead can be a large fraction of the end-to-end time. Make a workflow that runs many times into a graph, and those costs are paid once for the whole graph at instantiation, after which each launch of the graph costs very little. (The driver work here is the MMIO and command submission of Kernel Engineering Phase 5.)

  1. 定义。最方便的办法是流捕获：cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal) 和 cudaStreamEndCapture(s, &graph) 之间放进流 s 的工作不会执行，而是被记录成一张图（cudaGraph_t）的节点，流里的先后成为边。现成的代码和库调用只要接受一个流参数，就能原样被捕获。也可以用 cudaGraphAddNode 一个节点一个节点地建。
  2. Definition. The easiest way is stream capture: work put into stream s between cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal) and cudaStreamEndCapture(s, &graph) is not executed but recorded as the nodes of a graph (cudaGraph_t), and the order within the stream becomes its edges. Existing code and library calls are captured as they are, as long as they take a stream argument. A graph can also be built node by node with cudaGraphAddNode.
  3. 实例化。cudaGraphInstantiate(&exec, graph, 0) 给图拍一个快照、校验它，并完成大部分准备工作，得到可执行的 cudaGraphExec_t。这一步本身不便宜，只该做一次。
  4. Instantiation. cudaGraphInstantiate(&exec, graph, 0) takes a snapshot of the graph, validates it and does most of the setup, giving an executable cudaGraphExec_t. This step is not cheap in itself and should happen once.
  5. 执行。cudaGraphLaunch(exec, s) 把整张图作为一个单位放进流 s，想重放多少次就调用多少次。
  6. Execution. cudaGraphLaunch(exec, s) puts the whole graph into stream s as one unit; call it as many times as you want replays.

几条规则，都来自指南 4.2.2.1.2：捕获期间同步或查询正在被捕获的流是非法的，对包含它的设备或上下文做 cudaDeviceSynchronize 之类的调用也一样，因为被捕获的工作并没有真的排队；旧式默认流不能被捕获，所以 Lab A 用非阻塞流；跨流的依赖照样能捕获，只要用 cudaEventRecord 和 cudaStreamWaitEvent 表达，被等的事件在同一次捕获里记录，两个流就被捕获进同一张图，这正是把一个多流流水线整个录下来的办法。cudaStreamIsCapturing 可以查询一个流是否在捕获中。

A few rules, all from section 4.2.2.1.2 of the guide: during capture it is invalid to synchronize or query the stream being captured, or a device or context that contains it (with cudaDeviceSynchronize and the like), because the captured work is not actually queued; the legacy default stream cannot be captured, which is why Lab A uses a non-blocking stream; cross-stream dependencies are captured too, as long as they are expressed with cudaEventRecord and cudaStreamWaitEvent and the awaited event was recorded in the same capture, in which case both streams are captured into one graph, which is exactly how a whole multi-stream pipeline is recorded. cudaStreamIsCapturing tells whether a stream is being captured.

图里冻结了什么。实例化以后，每个 kernel 的启动配置和参数（包括指针）都固定了，重放用的是同样的值。数据可以变（指针指向的内容），形状和指针不能随便变。要改参数，可以用 cudaGraphExecUpdate 拿一张拓扑完全相同的新图去更新，或者单独更新某个节点，都比重新实例化便宜；拓扑变了就只能重新捕获和实例化（指南 4.2.3）。graph 从 CUDA 10 开始提供，T4 上可用。

What the graph freezes. After instantiation, each kernel’s launch configuration and arguments, pointers included, are fixed, and every replay uses the same values. The data may change (what the pointers point to); the shapes and the pointers may not change freely. To change arguments, cudaGraphExecUpdate updates from a new graph of identical topology, or individual nodes can be updated, both cheaper than instantiating again; a change of topology needs a new capture and instantiation (section 4.2.3 of the guide). Graphs have been available since CUDA 10 and work on the T4.

谁最受益。graph 省的是主机和驱动一侧的启动开销，不让任何一个 kernel 本身跑得更快。它在「很多很短的 kernel、每一步结构都一样」时收益最大。大语言模型推理的解码阶段正是这样：每生成一个 token 都要把整个模型走一遍，几十上百个 kernel，每个都很小，结构每一步都一样。计划中的 LLM Inference Kernels 专题就建立在这一点上，在解码路径上用 CUDA graph（推断：推理引擎通常为若干固定的批大小各捕获一张图，因为图里的形状是冻结的；本页没有核对具体项目的写法）。Metal 里最接近的东西是间接命令缓冲区（MTLIndirectCommandBuffer，计算命令类型 MTLIndirectCommandTypeConcurrentDispatch，用 executeCommandsInBuffer(_:withRange:) 执行）：命令编码一次、反复执行，只是它不是从现有代码捕获出来的，对应关系是近似的。

Who gains most. A graph saves launch overhead on the host and driver side; it makes no single kernel run faster. It pays most with many very short kernels whose structure is the same every step. The decode phase of large-language-model inference is exactly that: every generated token walks the whole model, tens or hundreds of kernels, each small, with the same structure every step. The planned LLM Inference Kernels topic builds on this, using CUDA graphs on the decode path (inference: inference engines commonly capture one graph for each of several fixed batch sizes, because a graph’s shapes are frozen; this page has not checked any particular project’s code). The closest thing in Metal is an indirect command buffer (MTLIndirectCommandBuffer, with the compute command type MTLIndirectCommandTypeConcurrentDispatch, executed with executeCommandsInBuffer(_:withRange:)): commands are encoded once and executed many times, though they are not captured from existing code, so the match is approximate.

4. 多 GPU：peer access 与 NCCL（概要）

4. Multiple GPUs: peer access and NCCL, in outline

一台机器上有几块 GPU 时，每块有自己的显存。指南 3.4 节讲了两件基本的事：

When one machine has several GPUs, each has its own memory. Section 3.4 of the guide covers two basic things:

  • Peer access。cudaDeviceCanAccessPeer(&ok, dev, peer) 先问两块卡之间能不能直接访问；能的话在 dev 上调用 cudaDeviceEnablePeerAccess(peer, 0)，之后 dev 上的 kernel 可以直接解引用另一块卡的指针。两块卡在统一虚拟地址空间里，同一个指针值在两边都有效。大块搬运用 cudaMemcpyPeerAsync(dst, dstDev, src, srcDev, bytes, s)。指南写明：没有 NVSwitch 的系统上，每块卡全系统最多 8 条 peer 连接。
  • Peer access. cudaDeviceCanAccessPeer(&ok, dev, peer) first asks whether two cards can reach each other directly; if so, calling cudaDeviceEnablePeerAccess(peer, 0) on dev lets kernels on dev dereference pointers into the other card. The two cards share the unified virtual address space, so one pointer value is valid on both. Bulk transfers use cudaMemcpyPeerAsync(dst, dstDev, src, srcDev, bytes, s). The guide states that on systems without NVSwitch each device supports at most eight peer connections system-wide.
  • NCCL。多卡训练和推理要的通常不是点对点拷贝，而是集合通信：all-reduce（每块卡的数组按元素相加，结果留在每块卡上）、all-gather、reduce-scatter、broadcast。NCCL 是 NVIDIA 的集合通信库，按机器的拓扑（NVLink、PCIe、网络）选路。它的调用形如 ncclAllReduce(sendbuff, recvbuff, count, datatype, op, comm, stream)（NCCL 2.32.3 文档，2026-10-31 读取）：最后一个参数是一个 CUDA 流，集合操作和 kernel 一样排进流里，所以本课的流、事件和重叠规则全都适用，通信可以和计算重叠。
  • NCCL. Multi-GPU training and inference usually need not point-to-point copies but collectives: all-reduce (the arrays on all cards summed element by element, the result left on every card), all-gather, reduce-scatter, broadcast. NCCL is NVIDIA’s collective communication library, which routes by the machine’s topology (NVLink, PCIe, network). Its calls look like ncclAllReduce(sendbuff, recvbuff, count, datatype, op, comm, stream) (NCCL 2.32.3 documentation, read 2026-10-31): the last argument is a CUDA stream, and a collective is queued into the stream like a kernel, so this lesson’s rules for streams, events and overlap all apply and communication can overlap computation.

5. MPS：多个进程共用一块 GPU

5. MPS: several processes sharing one GPU

流只在一个 CUDA 上下文（大致是一个进程）里并发。MPS 文档（2026-10-31 读取）写明：同一个上下文的工作队列由并发调度器调度，可以同时跑；不同上下文的工作由分时调度器调度，不能同时跑，每个进程轮流拿到整块 GPU 的一个时间片。几个各自只用一小部分 GPU 的进程（比如 MPI 的多个 rank）因此会让 GPU 大半空着。MPS（Multi-Process Service）用一个控制守护进程 nvidia-cuda-mps-control 和一个服务进程 nvidia-cuda-mps-server 让多个进程的工作像来自同一个上下文那样并发执行；从 Volta 起，客户端进程直接向硬件提交工作，服务进程只协调剩下的共享资源。环境变量 CUDA_MPS_ACTIVE_THREAD_PERCENTAGE 可以限制每个客户端能用的线程比例。它在 Linux 服务器上用，Colab 上没有，Metal 也没有对应物。延伸阅读：参考书目里没有一本书讲 MPS；这一段以 NVIDIA 的 Multi-Process Service 文档为准（见资料）。

Streams run concurrently only within one CUDA context, roughly one process. The MPS documentation (read 2026-10-31) states that work queues of one context are scheduled by a concurrent scheduler and can run at the same time, while work from different contexts is scheduled by a time-sliced scheduler and cannot: each process gets a time slice of the whole GPU in turn. Several processes that each use a small part of the GPU (the ranks of an MPI job, say) therefore leave most of it idle. MPS, the Multi-Process Service, uses a control daemon, nvidia-cuda-mps-control, and a server process, nvidia-cuda-mps-server, to let work from several processes run concurrently as if it came from one context; since Volta, client processes submit work to the hardware directly and the server mediates only the remaining shared resources. The environment variable CUDA_MPS_ACTIVE_THREAD_PERCENTAGE limits the share of threads each client may use. It is used on Linux servers; Colab does not offer it and Metal has no counterpart. Further reading: no book in the bibliography covers MPS; this paragraph rests on NVIDIA’s Multi-Process Service documentation (see Resources).

// 未运行 · not run; assembled from the CUDA documentation on 2026-10-31
// streams.cu: 把 64 MB 的「拷入、计算、拷出」切成 4 块放到 4 个流上，和单流、可分页内存比较
#include <algorithm>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <vector>
#include <cuda_runtime.h>

#define CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) { \
    std::fprintf(stderr, "%s:%d %s\n", __FILE__, __LINE__, cudaGetErrorString(e_)); std::exit(1); } } while (0)
#define N (1 << 24)          // 2^24 个 float，64 MB
#define ITERS 64             // 每个元素的乘加次数：调到 kernel 时间和单向拷贝时间差不多

__global__ void work(const float* in, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) { float x = in[i]; for (int k = 0; k < ITERS; ++k) x = x * 0.999f + 0.001f; out[i] = x; }
}

// 一次完整的拷入、计算、拷出，切成 nstreams 块，第 k 块全部放在流 s[k] 上；返回 5 次的中位数毫秒
float pipeline(const float* h_in, float* h_out, float* d_in, float* d_out, int nstreams, cudaStream_t* s) {
    cudaEvent_t t0, t1;
    CHECK(cudaEventCreate(&t0)); CHECK(cudaEventCreate(&t1));
    int chunk = N / nstreams; size_t bytes = size_t(chunk) * sizeof(float);
    std::vector<float> ms;
    for (int r = 0; r < 6; ++r) {                                 // 第 0 次是预热
        CHECK(cudaEventRecord(t0, 0));                            // 记在旧式默认流上：它和所有阻塞流互相同步
        for (int k = 0; k < nstreams; ++k) {
            int off = k * chunk;
            CHECK(cudaMemcpyAsync(d_in + off, h_in + off, bytes, cudaMemcpyHostToDevice, s[k]));
            work<<<(chunk + 255) / 256, 256, 0, s[k]>>>(d_in + off, d_out + off, chunk);
            CHECK(cudaGetLastError());
            CHECK(cudaMemcpyAsync(h_out + off, d_out + off, bytes, cudaMemcpyDeviceToHost, s[k]));
        }
        CHECK(cudaEventRecord(t1, 0));                            // 等前面所有流的工作都完成
        CHECK(cudaEventSynchronize(t1));
        float m = 0; CHECK(cudaEventElapsedTime(&m, t0, t1));
        if (r > 0) ms.push_back(m);
    }
    CHECK(cudaEventDestroy(t0)); CHECK(cudaEventDestroy(t1));
    std::sort(ms.begin(), ms.end());
    return ms[ms.size() / 2];
}

int main() {
    cudaDeviceProp p; CHECK(cudaGetDeviceProperties(&p, 0));
    std::printf("%s  asyncEngineCount=%d  concurrentKernels=%d\n", p.name, p.asyncEngineCount, p.concurrentKernels);
    size_t bytes = size_t(N) * sizeof(float);
    float *pin_in, *pin_out, *d_in, *d_out;
    CHECK(cudaMallocHost(&pin_in, bytes)); CHECK(cudaMallocHost(&pin_out, bytes));   // 页锁定（pinned）主机内存
    float* pg_in = (float*)std::malloc(bytes); float* pg_out = (float*)std::malloc(bytes);   // 普通的可分页内存

    for (int i = 0; i < N; ++i) pin_in[i] = pg_in[i] = float(i % 1000);
    cudaStream_t s[4];
    for (int k = 0; k < 4; ++k) CHECK(cudaStreamCreate(&s[k]));

    std::printf("pageable, 1 stream   %8.3f ms\n", pipeline(pg_in, pg_out, d_in, d_out, 1, s));
    std::printf("pageable, 4 streams  %8.3f ms\n", pipeline(pg_in, pg_out, d_in, d_out, 4, s));
    std::printf("pinned,   1 stream   %8.3f ms\n", pipeline(pin_in, pin_out, d_in, d_out, 1, s));
    std::vector<float> one(pin_out, pin_out + N);                 // 留下单流的结果，和四流的逐位比较
    std::printf("pinned,   4 streams  %8.3f ms\n", pipeline(pin_in, pin_out, d_in, d_out, 4, s));

// 未运行 · not run; assembled from the CUDA documentation on 2026-10-31
// graph.cu: 每一步 20 个很短的 kernel，跑 1000 步；逐个启动与捕获成 CUDA graph 后重放比较
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <cstdlib>
#include <vector>
#include <cuda_runtime.h>

#define CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) { \
    std::fprintf(stderr, "%s:%d %s\n", __FILE__, __LINE__, cudaGetErrorString(e_)); std::exit(1); } } while (0)
#define N 4096        // 很小的数组：每个 kernel 只有 16 个 block，运行时间远小于启动开销
#define K 20          // 每一步的 kernel 数，类似一次解码步里的一串小算子
#define STEPS 1000
#define REPS 5

__global__ void add1(float* x) { int i = blockIdx.x * blockDim.x + threadIdx.x; if (i < N) x[i] += 1.0f; }

void step(float* x, cudaStream_t s) {
    for (int k = 0; k < K; ++k) add1<<<N / 256, 256, 0, s>>>(x);
}

// 在流 s 上计时 STEPS 步，REPS 次取中位数
template <class F> float time_steps(F f, cudaStream_t s) {
    cudaEvent_t t0, t1;
    CHECK(cudaEventCreate(&t0)); CHECK(cudaEventCreate(&t1));
    std::vector<float> ms;
    for (int r = 0; r < REPS; ++r) {
        CHECK(cudaEventRecord(t0, s));
        for (int i = 0; i < STEPS; ++i) f();
        CHECK(cudaEventRecord(t1, s));
        CHECK(cudaEventSynchronize(t1));
        float m = 0; CHECK(cudaEventElapsedTime(&m, t0, t1));
        ms.push_back(m);
    }
    CHECK(cudaEventDestroy(t0)); CHECK(cudaEventDestroy(t1));
    std::sort(ms.begin(), ms.end());
    return ms[ms.size() / 2];
}

int main() {
    float* x; CHECK(cudaMalloc(&x, N * sizeof(float))); CHECK(cudaMemset(x, 0, N * sizeof(float)));
    cudaStream_t s; CHECK(cudaStreamCreateWithFlags(&s, cudaStreamNonBlocking));   // 捕获不能在旧式默认流上做

    step(x, s); CHECK(cudaGetLastError()); CHECK(cudaStreamSynchronize(s));        // 预热：加载模块
    float plain = time_steps([&] { step(x, s); }, s);
    CHECK(cudaGetLastError());

    // 捕获：这些启动只被记录成图里的节点，不执行
    auto h0 = std::chrono::steady_clock::now();
    cudaGraph_t g; cudaGraphExec_t ge;
    CHECK(cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal));
    step(x, s);
    CHECK(cudaStreamEndCapture(s, &g));
    CHECK(cudaGraphInstantiate(&ge, g, 0));                       // 实例化：校验并一次做完大部分准备工作
    double setup = std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - h0).count();

    CHECK(cudaGraphLaunch(ge, s)); CHECK(cudaStreamSynchronize(s));   // 预热：第一次重放
    float graph = time_steps([&] { CHECK(cudaGraphLaunch(ge, s)); }, s);

    std::vector<float> h(N);
    CHECK(cudaMemcpy(h.data(), x, N * sizeof(float), cudaMemcpyDeviceToHost));
    float want = float(K + REPS * STEPS * K + K + REPS * STEPS * K);   // 每个元素被加 1 的总次数，小于 2^24，浮点精确
    int bad = 0; for (int i = 0; i < N; ++i) bad += h[i] != want;
    std::printf("plain launches  %8.3f ms per %d steps  %6.2f us per kernel\n", plain, STEPS, plain * 1000 / (STEPS * K));
    std::printf("graph replay    %8.3f ms per %d steps  %6.2f us per kernel\n", graph, STEPS, graph * 1000 / (STEPS * K));
    std::printf("capture + instantiate %.3f ms (host clock, once)   mismatches %d\n", setup, bad);

    CHECK(cudaGraphExecDestroy(ge)); CHECK(cudaGraphDestroy(g));
    CHECK(cudaStreamDestroy(s)); CHECK(cudaFree(x));
    return 0;
}

#include <metal_stdlib>

// 计算密集的小 kernel：每个线程做 iters 次乘加，写回一个数，几乎不读内存
kernel void spin(device float* out [[buffer(0)]], constant uint& iters [[buffer(1)]],
                 uint i [[thread_position_in_grid]]) {
    float x = float(i);
    for (uint k = 0; k < iters; ++k) x = fma(x, 1.000001f, 0.5f);
    out[i] = x;
}
// 几乎什么都不做的 kernel，用来量每次提交的固定开销
kernel void tiny(device uint* out [[buffer(0)]], uint i [[thread_position_in_grid]]) { out[i] += 1; }

func encodeSpin(_ cb: MTLCommandBuffer, _ out: MTLBuffer, threads: Int) {
    let e = cb.makeComputeCommandEncoder()!
    e.setComputePipelineState(spin); e.setBuffer(out, offset: 0, index: 0)

    e.dispatchThreads(MTLSize(width: threads, height: 1, depth: 1), threadsPerThreadgroup: MTLSize(width: 256, height: 1, depth: 1))
    e.endEncoding()
}

1. 主机缓冲区用 malloc 分配，把拷入、计算、拷出分到四个流上，每个拷贝都用 cudaMemcpyAsync。会怎样？

1. The host buffers come from malloc, and the copy in, compute and copy out are split over four streams, each copy using cudaMemcpyAsync. What happens?

指南写明，主机内存不是页锁定的时候 cudaMemcpyAsync() 仍能正确工作，只是退回同步行为，不和其他工作重叠，所以它不报错。驱动要先把可分页的数据拷进自己的暂存区，这一步要 CPU 参与，重叠也就没了；问题不只是带宽低。The guide states that with host memory that is not page-locked cudaMemcpyAsync() still works correctly but reverts to synchronous behaviour and does not overlap other work, so there is no error. The driver must first copy the pageable data into its own staging area, a step that needs the CPU, and the overlap goes with it; the problem is more than lower bandwidth.

2. 把一步里的 20 个短 kernel 捕获成一张 CUDA graph 再重放，省掉的主要是什么？

2. Capturing the 20 short kernels of one step into a CUDA graph and replaying it saves mainly what?

指南 4.2 说明 graph 把每个 kernel 都要付的启动开销挪到实例化时一次付清。graph 不改 kernel 本身，20 个节点仍是 20 个 kernel，每个跑得一样快。实例化恰恰是贵的那一步，只该做一次；每步都重新实例化就把省下来的又花掉了。Section 4.2 of the guide explains that a graph moves the launch overhead every kernel pays into a single payment at instantiation. A graph does not change the kernels: 20 nodes are still 20 kernels, each as fast as before. Instantiation is precisely the expensive step and should happen once; redoing it every step spends the savings again.

3. 流 s2 里的 kernel 要等流 s1 里的 kernel 写完结果，但主机线程不能停下来等。怎么写？

3. A kernel in stream s2 must wait until a kernel in stream s1 has written its results, but the host thread must not stop and wait. How do you write it?

cudaStreamWaitEvent 在 GPU 一侧等，主机不阻塞，这正是一条流间依赖。cudaStreamSynchronize 也能保证先后，但它让主机等到 s1 跑完，违反了题目的要求。不同流之间没有顺序，这正是流存在的意义，所以不加依赖的话两个 kernel 可能同时跑。cudaStreamWaitEvent waits on the GPU side without blocking the host, which is exactly a dependence between streams. cudaStreamSynchronize also guarantees the order, but it makes the host wait until s1 finishes, which the question rules out. Different streams have no order between them, which is the point of streams, so without a dependence the two kernels may run at the same time.

4. Lab B 里，两个各有 220 个线程的 kernel 放在两个命令队列上，跨度正好是单独一个的两倍。为什么？

4. In Lab B, two kernels of 220 threads each on two command queues span exactly twice the time of one alone. Why?

同一个程序里 1024 线程的小 kernel 在两个队列上完全重叠了，跨度和单独一个差不多，所以不同队列并不总是串行。这一组里 A 和 B 写的是两个不同的缓冲区（outA 和 outB），没有冒险可跟踪。两个大 kernel 各自的时间窗口确实重叠，sum 大于跨度，但它们在争同一批核心，总时间不会少。In the same program the 1024-thread small kernels overlapped completely on two queues, spanning about the time of one alone, so different queues are not always serial. In this group A and B write two different buffers (outA and outB), so there is no hazard to track. The windows of the two large kernels do overlap, which is why sum exceeds the span, but they compete for the same cores and the total time does not shrink.
