为什么这样分层

Why these tiers

  • 这台 Mac 跑不了 CUDA。CUDA 只能跑在 NVIDIA GPU 上，而 Apple 芯片的 Mac 里是 Apple 自己的 GPU。NVIDIA 在 CUDA 10.2 的发布说明里写明，10.2 是最后一个支持 macOS 的版本。所以每个 CUDA 实验都要去云端找一块 NVIDIA GPU。
  • This Mac cannot run CUDA. CUDA runs only on NVIDIA GPUs, and an Apple-silicon Mac has Apple’s own GPU. NVIDIA’s CUDA 10.2 release notes state that 10.2 is the last release to support macOS. So every CUDA lab has to find an NVIDIA GPU in the cloud.
  • 前四课用免费层就够。Phase 0–3 只需要 nvcc、计时和结果检查，Colab 的 notebook 里用 ! 就能跑命令，T4（sm_75）支持本专题用到的所有基础特性。不花钱，代价是排队和断线。
  • The free tier is enough for the first four lessons. Phases 0–3 need only nvcc, timing and result checks; a Colab notebook runs commands with !, and the T4 (sm_75) supports every basic feature this topic uses. It costs nothing; the price is queues and dropped sessions.
  • 剖析要一台自己说了算的机器。从 Phase 4 起要用 Nsight Compute（ncu）和 Nsight Systems（nsys）。ncu 要读 GPU 的性能计数器，NVIDIA 的说明是：要么用管理员权限运行，要么在容器里时由主机放开权限或用 --cap-add=SYS_ADMIN 启动容器。在一台你有 root 的租用机器上，这些都由你决定。
  • Profiling needs a machine you control. From Phase 4 on you use Nsight Compute (ncu) and Nsight Systems (nsys). ncu reads the GPU’s performance counters, and NVIDIA’s instructions say it must run with administrative privileges, or, inside a container, the host must allow it or the container must start with --cap-add=SYS_ADMIN. On a rented machine where you are root, all of this is your call.
  • 每个想法都在本机再跑一遍。Metal 的 grid、threadgroup、SIMD-group 和 CUDA 的 grid、block、warp 一一对应。Mac 上的 Metal 孪生实验不花钱、不排队，而且是真跑出来的数字，用它检验你对 CUDA 那一侧的理解。
  • Every idea runs a second time here. Metal’s grid, threadgroup and SIMD-group map one to one onto CUDA’s grid, block and warp. The Metal twin on the Mac costs nothing, never queues, and gives numbers that were really measured; use it to test what you understood on the CUDA side.
租用 GPU 是花钱的决定，不是实验步骤。本页的云端部分只描述路径；开账户、选服务商、付费之前先定预算（概念 5 给出一个估算），并且只在决定之后才执行那些命令。
Renting a GPU is a decision to spend money, not a lab step. The cloud part of this page only describes the path; set a budget before you open an account, choose a provider or pay (concept 5 gives one estimate), and run those commands only after that decision.

Core concepts

1. 三层环境，各管哪几课

1. Three tiers and the lessons each one serves

每一课有两个实验。Lab A 是 CUDA，在云端跑；Lab B 是同一个想法的 Metal 版本，在这台 Mac 上跑。云端分两层，分界线在 Phase 4，也就是开始用剖析器的地方：

Every lesson has two labs. Lab A is CUDA and runs in the cloud; Lab B is the Metal version of the same idea and runs on this Mac. The cloud has two tiers, and the line between them is Phase 4, where the profilers start:

  • 第一层 · Colab 免费 T4：Phase 0–3 的 Lab A。浏览器里的 notebook，工具链预装。
  • Tier 1 · Colab free T4: Lab A of Phases 0–3. A notebook in the browser with the toolchain preinstalled.
  • 第二层 · 租用的 GPU 机器：Phase 4–7 的 Lab A。SSH 登录，在 NVIDIA 的 CUDA 容器里跑 ncu、nsys、compute-sanitizer。
  • Tier 2 · a rented GPU machine: Lab A of Phases 4–7. Log in over SSH and run ncu, nsys and compute-sanitizer in NVIDIA’s CUDA container.
  • 第三层 · 这台 Mac：每一课的 Lab B。Swift 程序加运行时编译的 Metal Shading Language（MSL）kernel，不需要 Xcode。
  • Tier 3 · this Mac: Lab B of every lesson. A Swift program plus a Metal Shading Language (MSL) kernel compiled at run time, with no Xcode needed.

所有 CUDA 实验都以 sm_75（Turing，T4 的架构）为目标，这样免费的 T4 和租来的更新的卡都能跑。用到更新硬件才有的特性时，那一课会单独说明。CUDA 13 已经去掉了 Turing 之前的架构（Maxwell、Pascal、Volta），所以 sm_75 也是 13.x 还支持的最老目标。

Every CUDA lab targets sm_75 (Turing, the T4’s architecture), so both the free T4 and a newer rented card can run it. When a lesson uses a feature that needs newer hardware, it says so. CUDA 13 removed the architectures before Turing (Maxwell, Pascal, Volta), so sm_75 is also the oldest target 13.x still supports.

2. 第一层：Colab 免费 T4

2. Tier 1: the free Colab T4

打开 colab.research.google.com，新建 notebook，在菜单 Runtime → Change runtime type 里选 T4 GPU（菜单名以 Colab 当前界面为准）。然后在单元格里先看清楚自己拿到了什么：

Open colab.research.google.com, create a notebook, and choose T4 GPU under Runtime → Change runtime type (the menu names are whatever the current Colab interface shows). Then check in a cell what you were given:

# 未运行 · not run; assembled from the Colab and CUDA documentation on 2026-10-31
!nvidia-smi       # GPU 型号（应为 Tesla T4）、驱动版本、显存 16 GB 左右
!nvcc --version   # Colab 预装的 CUDA 版本；任何 13.x 都可以，本专题用不到更新的东西

Colab 的单元格默认是 Python。! 开头的一行交给 shell 执行；%%writefile 放在单元格第一行，把整个单元格写成一个文件。CUDA 实验就是这两步：一个单元格写源文件，下一个单元格编译并运行。Lab A 用的就是这个流程。

Colab cells are Python by default. A line starting with ! goes to the shell; %%writefile on the first line of a cell writes the whole cell to a file. A CUDA lab is just those two steps: one cell writes the source file, the next one builds and runs it. Lab A uses exactly this flow.

免费层的限制，来自 Colab 的 FAQ（2026-10-31 读取）：资源不保证，用量上限会浮动；免费版对 GPU 这类昂贵资源限制很严；虚拟机空闲一段时间会被删除，并且有最长寿命。实际意义是：/content 里的文件会随虚拟机一起消失。每次实验结束前把源文件存进 Google Drive：

The limits of the free tier, from the Colab FAQ (read 2026-10-31): resources are not guaranteed and usage limits fluctuate; the free version heavily restricts expensive resources such as GPUs; virtual machines are deleted when idle for a while and have a maximum lifetime. In practice the files in /content vanish with the VM. Save your source files to Google Drive before every session ends:

# 未运行 · not run; assembled from the Colab documentation on 2026-10-31
from google.colab import drive
drive.mount('/content/drive')
!mkdir -p /content/drive/MyDrive/gpu-lab && cp add.cu /content/drive/MyDrive/gpu-lab/

Notebooks are saved to Drive and often shared, so anything in a cell or its output may be seen by others. Never put a credential in a notebook: no API tokens, cloud account keys or SSH private keys. The Colab labs of this topic need no credentials at all.

3. 第二层：租用的 GPU 机器

3. Tier 2: a rented GPU machine

本专题固定用 CUDA 13.4 Update 2（发布说明 2026-10-31 读取），租用机器上的容器标签是 nvidia/cuda:13.4.3-devel-ubuntu24.04。下面的版本事实都是 2026-10-31 从 NVIDIA 的发布说明和 Docker Hub 读到的：

This topic pins CUDA 13.4 Update 2 (release notes read 2026-10-31), and the container tag on the rented machine is nvidia/cuda:13.4.3-devel-ubuntu24.04. The version facts below were read from NVIDIA’s release notes and Docker Hub on 2026-10-31:

  • 13.4 Update 2 的组件：nvcc 13.4.92，Nsight Compute 2026.3.1.2，Nsight Systems 2026.3.2.476。
  • Components of 13.4 Update 2: nvcc 13.4.92, Nsight Compute 2026.3.1.2, Nsight Systems 2026.3.2.476.
  • 驱动分支：CUDA 13.4 对应 R615，13.3 对应 R610，13.2 对应 R595。次版本兼容（minor version compatibility）：任何 13.x 的程序在 580 或更新的驱动上都能跑，只有 13.4 的新特性要 R615 或更新。所以租来的机器上 nvidia-smi 显示的驱动只要不低于 580 就行。从 Linux 上的 13.4 起，驱动不再和 Toolkit 打包，要单独安装。
  • Driver branches: CUDA 13.4 goes with R615, 13.3 with R610, 13.2 with R595. Under minor version compatibility any 13.x application runs on a driver of 580 or newer; only the new 13.4 features need R615 or later. So the driver that nvidia-smi shows on the rented machine only needs to be 580 or newer. From 13.4 on Linux, the driver is no longer bundled with the toolkit and is installed separately.
  • CUDA 13 去掉了 Turing 之前的架构，sm_75 是还支持的最老目标。本专题的实验用不到比 13.x 更新的东西，所以 Colab 上预装的任何 13.x 都可以；单元格里的 !nvcc --version 会打印它的版本。
  • CUDA 13 removed the architectures before Turing, so sm_75 is the oldest supported target. The labs need nothing newer than 13.x, so any 13.x toolkit preinstalled on Colab is fine; the !nvcc --version cell prints which one it is.
  • Docker Hub 上的 13.4.3-devel-ubuntu24.04 推送于 2026-10-17，镜像里设的是 CUDA_VERSION=13.4.3，比上面读到的发布说明（Update 2）多一个更新；以容器里 nvcc --version 的输出为准。它的构建层装了 cuda-command-line-tools-13-4 和 cuda-nsight-compute-13-4，所以 ncu 在镜像里；nsys 只在镜像里找得到时才被链接进 PATH，要自己确认。
  • On Docker Hub, 13.4.3-devel-ubuntu24.04 was pushed on 2026-10-17, and the image sets CUDA_VERSION=13.4.3, one update past the release notes read above (Update 2); what nvcc --version prints inside the container is authoritative. Its build layers install cuda-command-line-tools-13-4 and cuda-nsight-compute-13-4, so ncu is in the image; nsys is linked onto the PATH only if a copy is found in the image, so check it yourself.

登录用密钥，不用密码。在 Mac 上生成一把只给这台 GPU 机器用的密钥，只把公钥交给服务商：

Log in with a key, not a password. On the Mac, generate a key used only for the GPU machine, and give the provider only the public half:

# 未运行 · not run; assembled from the OpenSSH and provider documentation on 2026-10-31
ssh-keygen -t ed25519 -f ~/.ssh/gpu_lab -C gpu-lab   # 设一个口令（passphrase）
cat ~/.ssh/gpu_lab.pub                              # 只把 .pub 粘进服务商控制台
ssh -i ~/.ssh/gpu_lab ubuntu@<IP>                   # 用户名因服务商而异，常见 ubuntu 或 root
rsync -av -e "ssh -i ~/.ssh/gpu_lab" ~/gpu-lab/ ubuntu@<IP>:gpu-lab/   # 把实验文件传上去

登录后先看 GPU 和驱动，再进 NVIDIA 的 CUDA 容器。--gpus all 要求主机装了 NVIDIA Container Toolkit；很多 GPU 机器的镜像自带，没有就按它的安装指南装。--cap-add=SYS_ADMIN 是给 ncu 读性能计数器用的，来自 NVIDIA 的 ERR_NVGPUCTRPERM 说明页：

After logging in, check the GPU and the driver first, then enter NVIDIA’s CUDA container. --gpus all needs the NVIDIA Container Toolkit on the host; many GPU machine images include it, and if not, install it from its guide. --cap-add=SYS_ADMIN lets ncu read the performance counters, as NVIDIA’s ERR_NVGPUCTRPERM page describes:

# 未运行 · not run; assembled from the CUDA, Container Toolkit and Nsight documentation on 2026-10-31
nvidia-smi                       # GPU 型号、驱动版本（要 ≥ 580）、右上角的 CUDA Version
docker run --rm -it --gpus all --cap-add=SYS_ADMIN \
  -v "$HOME/gpu-lab":/work -w /work \
  nvidia/cuda:13.4.3-devel-ubuntu24.04 bash
# 以下在容器里
nvcc --version                   # 应为 release 13.4
ncu --version                    # Nsight Compute
nsys --version                   # Nsight Systems；如果找不到，按 Nsight Systems 文档安装（check）
nvcc -arch=sm_75 add.cu -o add && ncu ./add   # 打印出剖析报告就说明计数器可用

两种机器要分清。整台虚拟机（比如 GCP 的 G2 实例）上你是 root，可以按上面跑 Docker、放开计数器。容器式租用（RunPod 的 pod 这类，你拿到的本身就是一个容器）通常不能再在里面跑 Docker，就直接选 nvidia/cuda 的 devel 镜像当 pod 的镜像；计数器权限由主机决定，你在里面改不了（推断，未在任何服务商上验证）。所以付费跑满几个小时之前，先用一个很小的 kernel 跑一次 ncu：如果报 ERR_NVGPUCTRPERM，换一台整机。

Tell the two kinds of machine apart. On a full virtual machine (a GCP G2 instance, for example) you are root and can run Docker and allow the counters as above. A container-style rental (a RunPod pod and the like, where what you get is itself a container) usually cannot run Docker inside; choose the nvidia/cuda devel image as the pod image instead. The counter permission is then decided by the host and you cannot change it from inside (inference, not verified on any provider). So before you pay for hours, run ncu once on a tiny kernel: if it reports ERR_NVGPUCTRPERM, switch to a full machine.

用完就停机。关掉 SSH 窗口不会停机，在容器里 exit 也只是退出容器，机器还在计费。在服务商控制台或命令行里停止（stop）或销毁（terminate），再到账单页确认它确实停了。有的服务商只有销毁才停止计费，停机后磁盘通常仍按存储收费。GCP 的例子：

Stop the machine when you are done. Closing the SSH window does not stop it, and exit in the container only leaves the container; the machine is still billing. Stop or terminate it from the provider console or command line, then confirm on the billing page that it really stopped. On some providers only terminating ends the billing, and a stopped machine usually still pays for its disk. A GCP example:

4. 第三层：这台 Mac 上的 Metal

4. Tier 3: Metal on this Mac

实验机只装了 Command Line Tools，没有完整的 Xcode。Swift 编译器在，离线的 Metal 编译器不在（2026-10-31 实验机输出）：

The lab machine has only the Command Line Tools, not the full Xcode. The Swift compiler is there; the offline Metal compiler is not (lab Mac output, 2026-10-31):

$ sw_vers -productVersion
27.2
$ xcode-select -p
/Library/Developer/CommandLineTools
$ swiftc --version
swift-driver version: 1.168.6 Apple Swift version 6.4.2 (swiftlang-6.4.2.1.9 clang-2100.4.1.1)
Target: arm64-apple-macosx27.2.0
$ xcrun -sdk macosx metal --version
xcrun: error: unable to find utility "metal", not a developer tool or in PATH
$ echo $?
72

所以本专题每一页都用运行时编译：MSL 源码作为字符串放在 Swift 程序里，程序运行时调用 MTLDevice.makeLibrary(source:options:) 编译成库，再从库里取出 kernel 函数，建成计算管线状态（compute pipeline state）后派发。好处是不需要 Xcode，也不需要 .metallib 文件；代价是每次运行都要编译一次 kernel，所以计时只看 GPU 自己报的执行时间（gpuStartTime 到 gpuEndTime），不看整个进程的运行时间。

So every page of this topic uses runtime compilation: the MSL source sits as a string inside the Swift program, which calls MTLDevice.makeLibrary(source:options:) at run time to compile it into a library, takes the kernel function from the library, builds a compute pipeline state and dispatches it. The gain is no Xcode and no .metallib file; the cost is one kernel compilation per run, so timing looks only at the execution time the GPU reports itself (gpuStartTime to gpuEndTime), never at the whole process run time.

硬件这一侧（system_profiler SPDisplaysDataType，2026-10-31）：Apple M5，GPU 10 核，Metal Support 显示 Metal 4。Lab B 的程序会再读出两个以后每课都要用的数：SIMD-group 宽度（threadExecutionWidth，对应 CUDA 的 warp）和每个 threadgroup 的线程上限（maxTotalThreadsPerThreadgroup，对应 CUDA 的每 block 线程上限）。

On the hardware side (system_profiler SPDisplaysDataType, 2026-10-31): Apple M5, a 10-core GPU, and Metal Support shows Metal 4. The Lab B program reads two more numbers that every later lesson uses: the SIMD-group width (threadExecutionWidth, the counterpart of the CUDA warp) and the per-threadgroup thread limit (maxTotalThreadsPerThreadgroup, the counterpart of CUDA’s per-block thread limit).

延伸阅读：PMPP 第 4 章 Compute architecture and scheduling（warp 和 SIMD 硬件，读完再看 Metal 的 SIMD-group 就是同一件事）。

Further reading: chapter 4 of PMPP, Compute architecture and scheduling (warps and SIMD hardware; after it, Metal’s SIMD-group reads as the same thing).

It does the same thing as the Metal program of Lab B: a[i] = i, b[i] = 2, compute c = a + b, and print the device parameters, c[12345] and the GPU time. Every CUDA call is wrapped in CHECK, and after the kernel launch cudaGetLastError picks up launch errors:
    %%writefile add.cu
// add.cu: 向量加法，结构和 Lab B 的 Metal 版一一对应
#include <cstdio>
#include <cuda_runtime.h>

#define CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) { \
    std::fprintf(stderr, "%s:%d %s\n", __FILE__, __LINE__, cudaGetErrorString(e_)); return 1; } } while (0)

__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // 这个线程负责的下标
    if (i < n) c[i] = a[i] + b[i];                   // 最后一个 block 可能越过 n
}

int main() {
    const int n = 1 << 20;
    const size_t bytes = n * sizeof(float);
    cudaDeviceProp p;
    CHECK(cudaGetDeviceProperties(&p, 0));

    float *ha = new float[n], *hb = new float[n], *hc = new float[n];
    for (int i = 0; i < n; ++i) { ha[i] = float(i); hb[i] = 2.0f; }

    float *da, *db, *dc;
    CHECK(cudaMalloc(&da, bytes)); CHECK(cudaMalloc(&db, bytes)); CHECK(cudaMalloc(&dc, bytes));
    CHECK(cudaMemcpy(da, ha, bytes, cudaMemcpyHostToDevice));
    CHECK(cudaMemcpy(db, hb, bytes, cudaMemcpyHostToDevice));

    cudaEvent_t t0, t1;
    CHECK(cudaEventCreate(&t0)); CHECK(cudaEventCreate(&t1));
    const int threads = 256, blocks = (n + threads - 1) / threads;
    CHECK(cudaEventRecord(t0));
    add<<<blocks, threads>>>(da, db, dc, n);
    CHECK(cudaGetLastError());                       // 启动参数错误在这里报
    CHECK(cudaEventRecord(t1));
    CHECK(cudaEventSynchronize(t1));                 // 等 kernel 跑完
    float ms = 0;
    CHECK(cudaEventElapsedTime(&ms, t0, t1));
    CHECK(cudaMemcpy(hc, dc, bytes, cudaMemcpyDeviceToHost));

    std::printf("device=%s sm_%d%d warpSize=%d maxThreadsPerBlock=%d c[12345]=%.1f gpuTime_ms=%.3f\n",
                p.name, p.major, p.minor, p.warpSize, p.maxThreadsPerBlock, hc[12345], ms);
    cudaEventDestroy(t0); cudaEventDestroy(t1);
    cudaFree(da); cudaFree(db); cudaFree(dc);
    delete[] ha; delete[] hb; delete[] hc;
    return 0;
}
  3. 第三个单元格编译并运行：The third cell builds and runs it:
    !nvcc -arch=sm_75 add.cu -o add && ./add
    通过的标准：c[12345]=12347.0（12345 + 2）。按 T4 的文档参数，设备那几项应当是 sm_75、warpSize=32、maxThreadsPerBlock=1024；设备名以你的输出为准。GPU 时间每次不同，一次运行不算测量，Phase 0 会做规模扫描和重复。The pass criterion: c[12345]=12347.0 (12345 + 2). From the T4’s documented parameters the device fields should read sm_75, warpSize=32 and maxThreadsPerBlock=1024; the device name is whatever your output shows. The GPU time differs every run, and one run is not a measurement; Phase 0 does the size sweep and the repetitions.
  4. 故意弄错一次：把 threads 改成 2048（超过每 block 1024 的上限），再编译运行。CHECK(cudaGetLastError()) 应当报一个启动配置错误并以 1 退出，而不是悄悄打印一个错的 c[12345]。这就是每次启动后都要查错误的原因。Break it once on purpose: change threads to 2048 (above the 1024 per-block limit), then build and run again. CHECK(cudaGetLastError()) should report a launch configuration error and exit with 1, instead of quietly printing a wrong c[12345]. That is why every launch is followed by an error check.

Lab B · 在这台 Mac 上跑 Metal 向量加法

Lab B · Run the Metal vector add on this Mac

  1. 确认工具链（对照概念 4 的输出）：Confirm the toolchain (compare with the output in concept 4):
    mkdir -p ~/gpu-lab && cd ~/gpu-lab
xcode-select -p
swiftc --version
xcrun -sdk macosx metal --version   # 预期失败：Command Line Tools 里没有它
  2. 写出程序。MSL kernel 放在三引号字符串里，makeLibrary(source:options:) 在运行时编译它；dispatchThreads 派发 220 个线程，每个 threadgroup 的大小取 threadExecutionWidth：Write the program. The MSL kernel sits in a triple-quoted string and makeLibrary(source:options:) compiles it at run time; dispatchThreads dispatches 220 threads, with a threadgroup size of threadExecutionWidth:
    // metal_add.swift: Metal 向量加法，kernel 在运行时从源码编译（不需要 xcrun metal）
import Metal

let src = """
#include <metal_stdlib>
using namespace metal;
kernel void add(device const float* a [[buffer(0)]],
                device const float* b [[buffer(1)]],
                device float*       c [[buffer(2)]],
                uint i [[thread_position_in_grid]]) {
    c[i] = a[i] + b[i];
}
"""

guard let dev = MTLCreateSystemDefaultDevice() else { print("no device"); exit(1) }
let lib = try dev.makeLibrary(source: src, options: nil)  // 运行时编译 MSL
let fn  = lib.makeFunction(name: "add")!
let pso = try dev.makeComputePipelineState(function: fn)

let n = 1 << 20
// 默认是共享存储：CPU 和 GPU 读写同一块内存
let a = dev.makeBuffer(length: n * 4)!
let b = dev.makeBuffer(length: n * 4)!
let c = dev.makeBuffer(length: n * 4)!
let pa = a.contents().bindMemory(to: Float.self, capacity: n)
let pb = b.contents().bindMemory(to: Float.self, capacity: n)
for i in 0..<n { pa[i] = Float(i); pb[i] = 2 }

let q = dev.makeCommandQueue()!
let cb = q.makeCommandBuffer()!
let enc = cb.makeComputeCommandEncoder()!
enc.setComputePipelineState(pso)
enc.setBuffer(a, offset: 0, index: 0)
enc.setBuffer(b, offset: 0, index: 1)
enc.setBuffer(c, offset: 0, index: 2)
let w = pso.threadExecutionWidth               // SIMD-group 宽度，对应 CUDA 的 warp
let maxT = pso.maxTotalThreadsPerThreadgroup   // 对应 CUDA 每 block 的线程上限
enc.dispatchThreads(MTLSize(width: n, height: 1, depth: 1),
                    threadsPerThreadgroup: MTLSize(width: w, height: 1, depth: 1))
enc.endEncoding()
cb.commit()
cb.waitUntilCompleted()

let pc = c.contents().bindMemory(to: Float.self, capacity: n)
print("device=\(dev.name) simdWidth=\(w) maxThreadsPerThreadgroup=\(maxT) "
    + "c[12345]=\(pc[12345]) gpuTime_ms=\((cb.gpuEndTime - cb.gpuStartTime) * 1000)")
  3. 编译并运行三次：Build it and run it three times:
    $ swiftc -O metal_add.swift -o metal_add
$ for i in 1 2 3; do ./metal_add; done
device=Apple M5 simdWidth=32 maxThreadsPerThreadgroup=1024 c[12345]=12347.0 gpuTime_ms=0.3859999997075647
device=Apple M5 simdWidth=32 maxThreadsPerThreadgroup=1024 c[12345]=12347.0 gpuTime_ms=0.3241666709072888
device=Apple M5 simdWidth=32 maxThreadsPerThreadgroup=1024 c[12345]=12347.0 gpuTime_ms=0.10974999167956412
# 2026-10-31 实验机输出（Apple M5，macOS 27.2，Swift 6.4.2）
    读法：SIMD-group 宽 32，和 CUDA 的 warp 一样宽；每个 threadgroup 最多 1024 个线程，和 CUDA 每 block 的上限相同；c[12345] 是 12347，结果对。xcrun swiftc -O 得到的是同一个编译器（xcrun --find swiftc 指向 /Library/Developer/CommandLineTools/usr/bin/swiftc），设备参数和 c[12345] 相同。How to read it: the SIMD-group is 32 wide, the same width as a CUDA warp; a threadgroup holds at most 1024 threads, the same as CUDA’s per-block limit; c[12345] is 12347, so the result is right. xcrun swiftc -O is the same compiler (xcrun --find swiftc points to /Library/Developer/CommandLineTools/usr/bin/swiftc) and prints the same device fields and c[12345].
  4. 看 GPU 时间的波动。同一天在实验机上把这个程序一共跑了 11 次（10 次 swiftc 编的、1 次 xcrun swiftc 编的），GPU 时间在 0.110 ms 到 0.519 ms 之间，差了将近 5 倍。每次运行是一个新进程，只派发一次，GPU 可能还没升到高频（推断）。按 0.110 ms 算，读两个数组、写一个数组共 12 MB（3 × 220 × 4 字节），约合 115 GB/s；按 0.519 ms 算只有约 24 GB/s。所以一次派发的时间不是测量结果：Phase 0 的 Lab B 会预热、重复、取中位数。Look at the spread of the GPU time. Eleven runs of this program on the lab Mac that day (10 built with swiftc, 1 with xcrun swiftc) gave GPU times from 0.110 ms to 0.519 ms, almost a factor of 5. Each run is a new process with a single dispatch, and the GPU may not have clocked up yet (inference). At 0.110 ms, reading two arrays and writing one, 12 MB in all (3 × 220 × 4 bytes), comes to about 115 GB/s; at 0.519 ms, only about 24 GB/s. So the time of one dispatch is not a measurement: Lab B of Phase 0 warms up, repeats and takes the median.

自测

Self-check

1. 为什么从 Phase 4 起要换到租用的机器？

1. Why do the labs move to a rented machine from Phase 4 on?

T4 有计数器，Turing 也在 Nsight Compute 的支持范围里；问题在于谁有权读它们。CUDA 13 去掉的是 Turing 之前的架构，sm_75 仍然支持，正因为如此本专题才以它为目标。The T4 has counters and Turing is within Nsight Compute’s support; the question is who may read them. CUDA 13 removed the architectures before Turing, and sm_75 is still supported, which is exactly why this topic targets it.

2. 在这台 Mac 上 xcrun -sdk macosx metal --version 报 unable to find utility "metal"。Lab B 的 kernel 是怎么编译的？

2. On this Mac, xcrun -sdk macosx metal --version reports unable to find utility "metal". How is the Lab B kernel compiled?

CUDA 10.2 之后就没有 macOS 版了，nvcc 也编不出 Metal kernel。下载来的二进制库来路不明，而且不需要：Metal 框架自己就能在运行时编译源码，这正是 Command Line Tools 下可走的路。There has been no macOS CUDA since 10.2, and nvcc cannot produce a Metal kernel anyway. A downloaded binary library is of unknown origin and not needed: the Metal framework can compile source at run time itself, which is exactly the route that works with the Command Line Tools.

3. 租来的机器应该怎么设置登录？

3. How should logins to the rented machine be set up?

一台公网上的 root 主机几分钟内就会被扫描，密码再强也会被反复尝试；密钥登录让这种尝试没有意义。私钥一旦写进 notebook，就随 Drive 和分享链接一起流出去了，凭据只能留在 Mac 上。A root host on the internet gets scanned within minutes, and even a strong password is tried over and over; key logins make those attempts pointless. A private key written into a notebook travels with Drive and every share link, so credentials stay on the Mac.

4. 一次 Phase 5 的实验做完了。下面哪一步才真正停止计费？

4. A Phase 5 lab session is finished. Which step actually stops the billing?

exit 只是退出容器，关终端只是断开连接，主机照样在跑。空闲回收是 Colab 免费层的行为，租来的机器不会替你关机。即使停了机，有的服务商仍按磁盘收费，所以还要看账单。exit only leaves the container and closing the terminal only drops the connection; the host keeps running. Idle reclaiming is how the free Colab tier behaves, and a rented machine does not shut down for you. Even after a stop some providers still charge for the disk, so check the bill as well.
