Memory 虚拟内存、ARM64 页表、缺页路径、分配器（buddy/slab ↔ Mach VM/zalloc）Virtual memory, ARM64 page tables, the page-fault path, allocators (buddy/slab ↔ Mach VM/zalloc)

进程看到的每一个地址都是「假的」：CPU 的 MMU 按页表把虚拟地址翻译成物理地址，翻不出来就触发异常交给内核补救。这一阶段把这条链从硬件走到软件：ARM64 页表长什么样、一次 ldr 碰到没映射的页时内核做了什么、内核自己又从哪里拿内存——Linux 和 XNU 并排对照。

Every address a process sees is “fake”: the CPU’s MMU translates virtual addresses into physical ones through page tables, and when a translation fails it raises an exception and hands the problem to the kernel to fix. This phase follows that chain from hardware to software: what ARM64 page tables look like, what the kernel does when one ldr hits an unmapped page, and where the kernel itself gets memory from — Linux and XNU side by side.

核心概念

Core concepts

1. 虚拟内存与地址空间：ARM64 的两半

1. Virtual memory and address spaces: the two halves of ARM64

ARM64 把 64 位虚拟地址空间切成两半，各用一个页表基址寄存器：低半（高位全 0）走 TTBR0_EL1，给用户态；高半（高位全 1）走 TTBR1_EL1，给内核。中间的「非规范」地址直接触发 translation fault。启用 Top Byte Ignore（TBI）时最高 8 位不参与翻译，选择哪个 TTBR 看 bit 55。好处：切换进程只需换 TTBR0_EL1，内核那一半所有进程共享、不用动。有效位数由 TCR_EL1 的 T0SZ/T1SZ 决定。

ARM64 splits the 64-bit virtual address space into two halves, each with its own page-table base register: the low half (top bits all 0) goes through TTBR0_EL1, for user mode; the high half (top bits all 1) goes through TTBR1_EL1, for the kernel. “Non-canonical” addresses in between raise a translation fault directly. With Top Byte Ignore (TBI) enabled, the top 8 bits take no part in translation and bit 55 selects the TTBR. The benefit: switching processes only requires a new TTBR0_EL1; the kernel half is shared by every process and stays untouched. The number of significant bits is set by T0SZ/T1SZ in TCR_EL1.

以 Linux arm64 经典配置 48-bit VA + 4 KB 页为例：页内偏移 12 位；每张页表 4 KB / 8 B = 512 项 = 9 位索引；48 − 12 = 36 = 4 × 9，所以是 4 级表 L0–L3：

Take the classic Linux arm64 configuration, 48-bit VA + 4 KB pages: the page offset is 12 bits; each page table is 4 KB / 8 B = 512 entries = a 9-bit index; 48 − 12 = 36 = 4 × 9, so there are 4 levels of tables, L0–L3:

VA:  [63:48] 全0→TTBR0 / 全1→TTBR1 | [47:39] L0 | [38:30] L1 | [29:21] L2 | [20:12] L3 | [11:0] offset
Linux 用户空间 0x0000_0000_0000_0000 – 0x0000_ffff_ffff_ffff（256 TB），内核从 0xffff_0000_0000_0000 起
VA:  [63:48] all 0→TTBR0 / all 1→TTBR1 | [47:39] L0 | [38:30] L1 | [29:21] L2 | [20:12] L3 | [11:0] offset
Linux user space 0x0000_0000_0000_0000 – 0x0000_ffff_ffff_ffff (256 TB); the kernel starts at 0xffff_0000_0000_0000

Apple Silicon 用 16 KB 页：XNU 在 M 系列上的默认页大小是 16 KB（pagesize 输出 16384；Intel Mac 是 4 KB）。16 KB 粒度下偏移 14 位，每张表 16 KB / 8 B = 2048 项 = 11 位索引；14 + 3 × 11 = 47，所以 47-bit VA 只要 3 级表（L1–L3），少走一级、TLB 每项覆盖面是 4 KB 页的 4 倍。Linux arm64 也能编成 16 KB 或 64 KB 页（CONFIG_ARM64_16K_PAGES / CONFIG_ARM64_64K_PAGES），Asahi Linux 在 Apple Silicon 上就用 16 KB——但发行版通用内核默认仍是 4 KB。

Apple Silicon uses 16 KB pages: XNU’s default page size on M-series chips is 16 KB (pagesize prints 16384; Intel Macs use 4 KB). With a 16 KB granule the offset is 14 bits and each table is 16 KB / 8 B = 2048 entries = an 11-bit index; 14 + 3 × 11 = 47, so a 47-bit VA needs only 3 levels of tables (L1–L3): one level fewer to walk, and each TLB entry covers 4 times as much as with 4 KB pages. Linux arm64 can also be built with 16 KB or 64 KB pages (CONFIG_ARM64_16K_PAGES / CONFIG_ARM64_64K_PAGES), and Asahi Linux uses 16 KB on Apple Silicon — but the generic kernels of distributions still default to 4 KB.

TLB 与 ASID：每次访存都走 4 级表太慢，MMU 把翻译结果缓存在 TLB。用户映射在描述符里置 nG（non-global），TLB 项会带上当前 ASID（8 或 16 位，放在 TTBR0 还是 TTBR1 的高位由 TCR_EL1.A1 决定；Linux arm64 放在 TTBR1_EL1）；不同进程的同一 VA 因 ASID 不同可以同时留在 TLB 里，切进程不必全刷。内核映射是 global 的，所有 ASID 共用。

TLB and ASID: walking 4 levels of tables on every memory access would be too slow, so the MMU caches translations in the TLB. User mappings set nG (non-global) in the descriptor, so their TLB entries carry the current ASID (8 or 16 bits; whether it sits in the high bits of TTBR0 or TTBR1 is decided by TCR_EL1.A1; Linux arm64 puts it in TTBR1_EL1); the same VA in different processes can stay in the TLB at the same time because the ASIDs differ, so a process switch does not need a full flush. Kernel mappings are global and shared by all ASIDs.

寄存器名这里统一写 _EL1。Phase 0 提过 XNU 在 M 系列上运行于 EL2 + VHE；VHE 下软件写 _EL1 名字的寄存器会被重定向到对应的 EL2 寄存器，概念不变。
Register names are written as _EL1 throughout. As Phase 0 mentioned, XNU on M-series chips runs at EL2 + VHE; under VHE, software accesses to _EL1-named registers are redirected to the corresponding EL2 registers, and the concepts are unchanged.

2. 页表遍历、TLB 与描述符

2. Page-table walks, the TLB and descriptors

TLB miss 时，硬件 table walker 从 TTBR 给出的 L0 表基址开始，每级用 VA 的一段索引取出 8 字节描述符，看最低两位：

On a TLB miss, the hardware table walker starts from the L0 table base given by the TTBR, uses one slice of the VA as the index at each level to fetch an 8-byte descriptor, and looks at its lowest two bits:

  • bit0 = 0：invalid → translation fault（缺页的最常见原因）。
  • bit0 = 0: invalid → translation fault (the most common cause of a page fault).
  • L0–L2 上 0b11 = table 描述符：指向下一级表。
  • 0b11 at L0–L2 = a table descriptor: points to the next-level table.
  • L1/L2 上 0b01 = block 描述符：直接映射一大块（4 KB 粒度下 L1 = 1 GB、L2 = 2 MB，就是「大页」/ THP 的硬件基础）。
  • 0b01 at L1/L2 = a block descriptor: maps a large block directly (with a 4 KB granule, L1 = 1 GB and L2 = 2 MB; this is the hardware basis of “huge pages” / THP).
  • L3 上 0b11 = page 描述符：给出 4 KB 页的输出地址（OA）。
  • 0b11 at L3 = a page descriptor: gives the output address (OA) of a 4 KB page.

block/page 描述符里的属性位决定「能不能访问、怎么缓存」：AttrIndx[4:2] 是一个下标，指向 MAIR_EL1 里 8 组内存类型之一（Normal Write-Back、Device-nGnRE……，页表里不直接写缓存属性）；AP[7:6] 管只读/可写与 EL0 是否可访问；SH[9:8] 共享域；AF[10] access flag，为 0 时第一次访问触发 access flag fault（内核借此统计「最近用过」，有 FEAT_HAFDBS 的 CPU 可由硬件自动置位）；nG[11]；高位的 PXN[53]/UXN[54] 分别禁止 EL1 / EL0 在此执行。

The attribute bits in block/page descriptors decide “can it be accessed, and how is it cached”: AttrIndx[4:2] is an index pointing to one of the 8 memory types in MAIR_EL1 (Normal Write-Back, Device-nGnRE…; the page table does not hold cache attributes directly); AP[7:6] controls read-only/writable and whether EL0 may access it; SH[9:8] is the shareability domain; AF[10] is the access flag — when it is 0, the first access raises an access flag fault (the kernel uses this to track “recently used”; on CPUs with FEAT_HAFDBS the hardware can set it automatically); nG[11]; and the high bits PXN[53]/UXN[54] forbid execution here at EL1 / EL0 respectively.

改页表后 TLB 里的旧项不会自己消失：内核要发 TLBI（如按 VA+ASID 的 tlbi vae1is）再 dsb ish、isb。Linux 封装为 flush_tlb_page()/flush_tlb_range()（arch/arm64/include/asm/tlbflush.h）；XNU 在 pmap 层内部处理。Arm 还要求修改有效映射时遵守 break-before-make（先置无效、刷 TLB、再写新值）。延伸阅读：《Computer Systems: A Programmer's Perspective》第 9 章「虚拟内存」；《Operating Systems: Three Easy Pieces》第 18–20 章（分页、TLB、多级页表）。

After a page-table change, stale TLB entries do not disappear on their own: the kernel has to issue a TLBI (for example tlbi vae1is, by VA+ASID), then dsb ish and isb. Linux wraps this as flush_tlb_page()/flush_tlb_range() (arch/arm64/include/asm/tlbflush.h); XNU handles it inside the pmap layer. Arm also requires break-before-make when changing a valid mapping (invalidate first, flush the TLB, then write the new value). Further reading: Computer Systems: A Programmer's Perspective, Chapter 9, “Virtual Memory”; Operating Systems: Three Easy Pieces, Chapters 18–20 (paging, TLBs, multi-level page tables).

3. 缺页路径：从 data abort 到重新执行

3. The page-fault path: from data abort to re-execution

翻译失败或权限不符时，CPU 产生同步异常 data abort（取指失败则是 instruction abort）：ESR_EL1.EC = 0x24 表示来自更低 EL（用户态），0x25 表示同一 EL（内核自己访问出错，例如 copy_from_user 碰到未映射的用户页）。ISS 里的 DFSC 区分 translation / access flag / permission fault 以及出错的表级，WnR 位说明是读还是写；出错的虚拟地址在 FAR_EL1。ELR_EL1 指向出错的那条指令本身——修好映射后 eret，同一条指令重新执行，用户程序完全无感。

When translation fails or the permissions do not match, the CPU raises a synchronous exception, a data abort (an instruction abort if an instruction fetch failed): ESR_EL1.EC = 0x24 means it came from a lower EL (user mode), 0x25 the same EL (the kernel’s own access faulted, for example copy_from_user hitting an unmapped user page). DFSC in the ISS distinguishes translation / access flag / permission faults and the table level that faulted, and the WnR bit says whether it was a read or a write; the faulting virtual address is in FAR_EL1. ELR_EL1 points at the faulting instruction itself — once the mapping is fixed, eret re-executes the same instruction, and the user program notices nothing.

Linux：el0t_64_sync → el0t_64_sync_handler 按 EC 分发到 el0_da（arch/arm64/kernel/entry-common.c）→ do_mem_abort(far, esr, regs) 按 DFSC 查 fault_info[] 表，translation fault 走 do_translation_fault，permission fault 直接进 do_page_fault（都在 arch/arm64/mm/fault.c）。do_page_fault 在当前进程的 mm_struct 里找覆盖该地址的 VMA（vm_area_struct，自 6.1 起存放在 mm->mm_mt maple tree 中；新内核先尝试 per-VMA 锁 lock_vma_under_rcu，失败再拿 mmap_lock），检查 VMA 权限，然后调通用的 handle_mm_fault（mm/memory.c）。后者逐级分配缺失的页表，最后在 handle_pte_fault 分情况：

Linux: el0t_64_sync → el0t_64_sync_handler dispatches on EC to el0_da (arch/arm64/kernel/entry-common.c) → do_mem_abort(far, esr, regs) looks up the fault_info[] table by DFSC; translation faults go to do_translation_fault, permission faults straight to do_page_fault (both in arch/arm64/mm/fault.c). do_page_fault looks up the VMA covering the address in the current process’s mm_struct (a vm_area_struct, stored in the mm->mm_mt maple tree since 6.1; newer kernels first try the per-VMA lock lock_vma_under_rcu and take mmap_lock only if that fails), checks the VMA’s permissions, and then calls the generic handle_mm_fault (mm/memory.c). That function allocates any missing page tables level by level, and finally handle_pte_fault splits into cases:

  • 匿名页首次访问（堆、栈、MAP_ANONYMOUS）：do_anonymous_page——读访问可映射共享的零页，写访问才真正分一页清零。这就是 demand paging。
  • First access to an anonymous page (heap, stack, MAP_ANONYMOUS): do_anonymous_page — a read can map the shared zero page; only a write actually allocates a zeroed page. This is demand paging.
  • 文件映射：do_fault → 读 page cache，没有就发起 I/O（major fault）；私有映射被写时走 do_cow_fault。
  • File mapping: do_fault → read from the page cache, starting I/O if the page is not there (a major fault); a write to a private mapping goes through do_cow_fault.
  • COW：fork 后父子共享物理页、PTE 都置只读；任一方写 → permission fault → do_wp_page 复制一页（若该页只剩自己一个使用者则直接改回可写）。
  • COW: after fork, parent and child share physical pages and all PTEs are set read-only; a write by either side → permission fault → do_wp_page copies one page (if the page has only this one user left, it is simply made writable again).

找不到 VMA 或权限不符 → 用户态收到 SIGSEGV；内核态则查异常修复表（fixup_exception），查不到就 oops。

No VMA found, or the permissions do not match → user mode gets SIGSEGV; in kernel mode the exception fixup table is consulted (fixup_exception), and if there is no entry the result is an oops.

XNU：fleh_synchronous → sleh_synchronous（osfmk/arm64/sleh.c）按 EC（ESR_EC_DABORT_EL0）调 handle_abort，用户态再进 handle_user_abort → vm_fault（osfmk/vm/vm_fault.c）。Mach VM 的模型和 Linux 同构但命名不同：任务的地址空间是 vm_map，由一串 vm_map_entry（对应 VMA）组成，每个 entry 指向一个 vm_object（「一段可被映射的内存」，背后挂 pager：vnode pager 读文件，匿名内存由 compressor / swap 承担），object 里是 vm_page。vm_fault 的大致路径：在 map 中查到 entry 和 object → vm_fault_page 在 object（及其 shadow 链）中找页，没有就向 pager 要或给零页 → vm_fault_enter → pmap_enter 写入硬件页表。COW 用 shadow object 实现：写一个 copy-on-write 的 entry 时，在原 object 前面叠一个新的 shadow object（vm_object_shadow），被写的页复制进 shadow，未写的页继续从下层 object 读。延伸阅读：《Understanding the Linux Kernel》第 9 章「进程地址空间」（含缺页异常处理程序）；《Understanding the Linux Virtual Memory Manager》第 4 章「进程地址空间」。

XNU: fleh_synchronous → sleh_synchronous (osfmk/arm64/sleh.c) calls handle_abort based on EC (ESR_EC_DABORT_EL0), and for user mode it continues into handle_user_abort → vm_fault (osfmk/vm/vm_fault.c). The Mach VM model is isomorphic to Linux’s but uses different names: a task’s address space is a vm_map, made of a chain of vm_map_entrys (corresponding to VMAs); each entry points to a vm_object (“a piece of mappable memory”, backed by a pager: the vnode pager reads files, and anonymous memory is handled by the compressor / swap), and the object holds vm_pages. The approximate path of vm_fault: find the entry and object in the map → vm_fault_page looks for the page in the object (and its shadow chain), asking the pager or supplying a zero page if it is not there → vm_fault_enter → pmap_enter writes the hardware page table. COW is implemented with shadow objects: when a copy-on-write entry is written, a new shadow object is stacked in front of the original object (vm_object_shadow); written pages are copied into the shadow, and unwritten pages are still read from the object below. Further reading: Understanding the Linux Kernel, Chapter 9, “Process Address Space” (including the page fault exception handler); Understanding the Linux Virtual Memory Manager, Chapter 4, “Process Address Space”.

4. 物理内存与内核分配器

4. Physical memory and kernel allocators

Linux：每页物理内存有一个 struct page（新代码越来越多用 struct folio 表示「一组连续页」）。物理内存按 node → zone（arm64 上有 ZONE_DMA/ZONE_DMA32/ZONE_NORMAL/ZONE_MOVABLE，没有 HIGHMEM）组织，每个 zone 用 buddy allocator 管理：按 2order 页分块挂在 free list 上，alloc_pages(gfp, order) 不够就拆大块、释放时与「伙伴」合并（/proc/buddyinfo 就是每个 order 的空闲块数）。小对象走 SLUB（6.8 起唯一的 slab 实现）：kmem_cache_create 建同类对象缓存，kmalloc 是按大小分档的通用缓存。需要虚拟连续、物理可以不连续的大块用 vmalloc。内核通过 linear map（phys_to_virt/virt_to_phys）直接访问全部物理内存。

Linux: every page of physical memory has a struct page (newer code increasingly uses struct folio for “a group of contiguous pages”). Physical memory is organised as node → zone (on arm64 there are ZONE_DMA/ZONE_DMA32/ZONE_NORMAL/ZONE_MOVABLE, and no HIGHMEM), and each zone is managed by the buddy allocator: blocks of 2order pages hang on free lists; when alloc_pages(gfp, order) finds none of the right size it splits a larger block, and on free it merges with its “buddy” (/proc/buddyinfo shows the number of free blocks of each order). Small objects go through SLUB (the only slab implementation since 6.8): kmem_cache_create builds a cache of same-type objects, and kmalloc is the general-purpose set of caches by size class. Large chunks that must be virtually contiguous but may be physically non-contiguous use vmalloc. The kernel accesses all of physical memory directly through the linear map (phys_to_virt/virt_to_phys).

XNU：架构相关的页表操作全部收在 pmap 层（pmap_enter、pmap_remove、pmap_protect……，arm 实现在 osfmk/arm/pmap/，旧版本是 osfmk/arm/pmap.c），机器无关的 Mach VM 只调这组接口——比 Linux 用通用的 pgd/pud/pmd/pte 抽象更彻底地隔离了硬件。物理页由 vm_page 描述，空闲页放在 free queue 上（vm_page_grab 取页）。内核小对象走 zone allocator：zalloc/zfree 按 zone（固定大小对象池）分配；kalloc 系列在其上按大小分档。iOS 15 / macOS 12 起引入 kalloc_type：按类型签名把不同类型的对象隔离到不同 zone（数据型走 kalloc_data），使 use-after-free 难以把一个类型的对象「换成」另一个类型——这是安全加固，不是性能优化。大块内核内存用 kmem_alloc（osfmk/vm/vm_kern.c）。

XNU: all architecture-specific page-table operations are confined to the pmap layer (pmap_enter, pmap_remove, pmap_protect…; the arm implementation is in osfmk/arm/pmap/, or osfmk/arm/pmap.c in older versions), and the machine-independent Mach VM calls only this interface — a more thorough isolation from the hardware than Linux’s generic pgd/pud/pmd/pte abstraction. Physical pages are described by vm_page, and free pages sit on a free queue (vm_page_grab takes a page). Small kernel objects go through the zone allocator: zalloc/zfree allocate by zone (a pool of fixed-size objects); the kalloc family builds size classes on top of it. iOS 15 / macOS 12 introduced kalloc_type: it uses type signatures to isolate objects of different types into different zones (data-only types go to kalloc_data), which makes it hard for a use-after-free to “swap” an object of one type for one of another type — this is security hardening, not a performance optimisation. Large blocks of kernel memory use kmem_alloc (osfmk/vm/vm_kern.c).

Apple Silicon 上页表并不由普通内核代码直接写：PPL（较新设备上是 SPTM）把页表修改关进一个更高权限的小环境里，pmap 调用会跨过这道边界。这是 Phase 7 的主题，这里只需知道「pmap_enter 背后还有一层保护」。
On Apple Silicon, page tables are not written directly by ordinary kernel code: PPL (SPTM on newer devices) locks page-table modification inside a small, more privileged environment, and pmap calls cross that boundary. This is the subject of Phase 7; here you only need to know that “there is one more layer of protection behind pmap_enter”.

延伸阅读：《Understanding the Linux Virtual Memory Manager》第 6 章「物理页分配」与第 8 章「Slab 分配器」；《Linux Kernel Development》第 12 章「内存管理」。

Further reading: Understanding the Linux Virtual Memory Manager, Chapter 6, “Physical Page Allocation”, and Chapter 8, “Slab Allocator”; Linux Kernel Development, Chapter 12, “Memory Management”.

5. 用户态视角：mmap、malloc 与 RSS

5. The user-space view: mmap, malloc and RSS

用户程序拿内存只有两类系统调用：brk（移动堆顶）和 mmap（映射一段匿名或文件内存）。glibc malloc 小块从堆（brk）和 arena 切，大块（默认阈值 128 KB 起，可动态调整）直接 mmap。macOS 上 BSD 层的 mmap 最终落到 Mach 的 mach_vm_map；也可以直接调 Mach 接口 mach_vm_allocate/mach_vm_map（旧名 vm_allocate/vm_map）；libmalloc 主要基于这些 VM 区域，而不是 brk。

User programs have only two kinds of system calls for getting memory: brk (move the top of the heap) and mmap (map a range of anonymous or file-backed memory). glibc malloc carves small blocks out of the heap (brk) and arenas, and uses mmap directly for large blocks (the threshold starts at 128 KB by default and is adjusted dynamically). On macOS, the BSD-layer mmap ends up in Mach’s mach_vm_map; you can also call the Mach interfaces mach_vm_allocate/mach_vm_map directly (old names vm_allocate/vm_map); libmalloc is built mainly on these VM regions rather than on brk.

两个数字要分清：VSZ（虚拟大小）= 映射了多少地址；RSS（驻留集）= 其中当前真有物理页的部分。mmap 只改 VSZ，缺页才让 RSS 增长。macOS 上 Apple 更推荐看 footprint（phys_footprint：脏页 + 被压缩的页等，算「这个进程真正占的内存」），工具是 vmmap 和 footprint。

Keep two numbers apart: VSZ (virtual size) = how many addresses are mapped; RSS (resident set size) = the part of that which currently has real physical pages. mmap changes only VSZ; only page faults make RSS grow. On macOS, Apple recommends looking at the footprint instead (phys_footprint: dirty pages + compressed pages and so on, counted as “the memory this process really occupies”); the tools are vmmap and footprint.

准备 · 一个让 demand paging 现形的小程序

Setup · A small program that makes demand paging visible

把下面存为 touch64.c。它 mmap 64 MB 匿名内存，然后分 4 段、每 4 KB 写一个字节，每段之后打印 RSS 和这一段触发的 minor fault 数。同一份源码在 Linux（读 /proc/self/status 的 VmRSS）和 macOS（Mach task_info）上都能编。

Save the following as touch64.c. It mmaps 64 MB of anonymous memory, then writes one byte every 4 KB in 4 segments, and after each segment prints the RSS and the number of minor faults that segment triggered. The same source builds on Linux (reading VmRSS from /proc/self/status) and on macOS (Mach task_info).

#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/resource.h>
#ifdef __APPLE__
#include <mach/mach.h>
#endif

static long rss_kb(void) {
#ifdef __APPLE__
  struct mach_task_basic_info info;
  mach_msg_type_number_t n = MACH_TASK_BASIC_INFO_COUNT;
  if (task_info(mach_task_self(), MACH_TASK_BASIC_INFO, (task_info_t)&info, &n) != KERN_SUCCESS) return -1;
  return (long)(info.resident_size / 1024);
#else
  FILE *f = fopen("/proc/self/status", "r");
  char line[256];
  long kb = -1;
  if (!f) return -1;
  while (fgets(line, sizeof line, f))
    if (sscanf(line, "VmRSS: %ld kB", &kb) == 1) break;
  fclose(f);
  return kb;
#endif
}

static long minflt(void) {
  struct rusage ru;
  getrusage(RUSAGE_SELF, &ru);
  return ru.ru_minflt;
}

int main(void) {
  const size_t len = 64UL * 1024 * 1024, step = 4096;
  printf("pid=%d pagesize=%ld\n", (int)getpid(), sysconf(_SC_PAGESIZE));
  char *p = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANON, -1, 0);
  if (p == MAP_FAILED) { perror("mmap"); return 1; }
  printf("after mmap:     RSS=%6ld kB\n", rss_kb());
  fflush(stdout);
  sleep(5);
  for (size_t q = 1; q <= 4; q++) {
    long f0 = minflt();
    for (size_t off = (q - 1) * len / 4; off < q * len / 4; off += step) p[off] = 1;
    printf("touched %2zu MB:  RSS=%6ld kB  +faults=%ld\n", q * 16, rss_kb(), minflt() - f0);
    fflush(stdout);
    sleep(5);
  }
  munmap(p, len);
  return 0;
}

自测

Self-check

1. Apple Silicon Mac 上 macOS 的默认页大小是多少？

1. What is the default macOS page size on an Apple Silicon Mac?

XNU 在 Apple Silicon 上用 16 KB 页（pagesize 输出 16384）；Intel Mac 和大多数 Linux arm64 发行版内核是 4 KB。16 KB 粒度下 47-bit VA 只需三级页表。XNU uses 16 KB pages on Apple Silicon (pagesize prints 16384); Intel Macs and most Linux arm64 distribution kernels use 4 KB. With a 16 KB granule, a 47-bit VA needs only three levels of page tables.

2. 一个高位全 1 的地址（如 0xffff_8000_1234_5000）由哪个寄存器提供页表基址？

2. For an address whose top bits are all 1 (such as 0xffff_8000_1234_5000), which register provides the page-table base?

高半（高位全 1）是内核地址，走 TTBR1_EL1；低半是用户地址，走 TTBR0_EL1，切换进程时只换 TTBR0。VBAR_EL1 是异常向量表基址，与翻译无关。The high half (top bits all 1) holds kernel addresses and goes through TTBR1_EL1; the low half holds user addresses and goes through TTBR0_EL1, and only TTBR0 is changed on a process switch. VBAR_EL1 is the exception vector table base and has nothing to do with translation.

3. fork 之后，copy-on-write 的物理页复制在什么时候真正发生？

3. After fork, when does the copy-on-write copy of a physical page actually happen?

fork 只复制页表并把共享页都设为只读；读不会触发复制。第一次写触发 permission fault，Linux 在 do_wp_page、XNU 通过 shadow object 才复制那一页。fork copies only the page tables and marks the shared pages read-only; a read does not trigger a copy. The first write triggers a permission fault, and only then does Linux (in do_wp_page) or XNU (through a shadow object) copy that page.

4. 48-bit VA、4 KB 页、4 级页表下，L2 表的索引取自 VA 的哪几位？

4. With a 48-bit VA, 4 KB pages and 4-level page tables, which VA bits form the L2 table index?

偏移 [11:0] 12 位，往上每级 9 位：L3 = [20:12]，L2 = [29:21]，L1 = [38:30]，L0 = [47:39]。L2 若是 block 描述符就直接映射 2 MB（221）。The offset [11:0] is 12 bits, and each level above takes 9 bits: L3 = [20:12], L2 = [29:21], L1 = [38:30], L0 = [47:39]. If the L2 entry is a block descriptor, it maps 2 MB (221) directly.
