核心概念

Core concepts

1. 高效读内核源码

1. Reading kernel source efficiently

内核源码太大，不能「从头读」。有效的读法是从入口追数据结构：先找到用户态能触发的入口（系统调用表、ioctl、fault handler），沿调用链往下，每遇到一个结构体就去看它在哪里分配、谁持有引用、谁加锁。工具只是让「跳到定义 / 列出调用者」这两个动作足够快。

Kernel source is too big to read “from the beginning”. The effective way is to follow data structures from an entry point: first find an entry user space can trigger (the system call table, an ioctl, a fault handler), go down the call chain, and for every structure you meet, look at where it is allocated, who holds references to it and who locks it. Tools only make the two actions “jump to definition / list callers” fast enough.

Linux：顶层 Makefile 自带 make tags、make cscope、make gtags 目标（交叉构建时记得带同样的 ARCH=arm64，否则只索引 x86 的 arch 代码）。更准的是 clangd：构建一次后 make LLVM=1 ARCH=arm64 compile_commands.json（底层是 scripts/clang-tools/gen_compile_commands.py，读构建产生的 .cmd 文件），编辑器里的 clangd 就能按真实的 .config 解析宏和 #ifdef。不想本地建索引时用在线交叉索引 Elixir（elixir.bootlin.com），可以按版本切换。Linux 有完整 git 历史：git log -S 符号名 找引入/删除某符号的提交，git blame + 提交信息往往直接告诉你「为什么这样写」，提交信息里的 Link: 还会指向邮件列表上的讨论。

Linux: the top-level Makefile has built-in make tags, make cscope and make gtags targets (when cross-building, remember to pass the same ARCH=arm64, otherwise only the x86 arch code is indexed). clangd is more accurate: after one build, run make LLVM=1 ARCH=arm64 compile_commands.json (underneath it is scripts/clang-tools/gen_compile_commands.py, which reads the .cmd files the build produces), and clangd in your editor can then resolve macros and #ifdefs according to the real .config. When you do not want to build an index locally, use the online cross-referencer Elixir (elixir.bootlin.com), which lets you switch between versions. Linux has its full git history: git log -S <symbol> finds the commits that introduced or removed a symbol, git blame + the commit message often tell you directly “why it is written this way”, and the Link: in a commit message points to the discussion on the mailing list.

XNU：仓库 README 同样给了 make tags / make TAGS / make cscope。XNU 构建不直接产出 compile_commands.json，要 clangd 可以用通用工具 Bear 包一层 make（bear -- make …，大致做法，前提是你能构建成功，见 Phase 8）。没有索引时，XNU 的代码风格本身帮你：函数定义把返回类型单独放一行，所以 grep -rn "^vm_fault(" osfmk/ 能直接定位定义。区别在历史：apple-oss-distributions/xnu 只按 macOS 版本发布快照（tag 形如 xnu-12377.121.6），没有逐提交的信息——想知道「为什么」，只能对比相邻 tag 的 diff 再结合 doc/ 目录下的设计说明。

XNU: the repository README likewise provides make tags / make TAGS / make cscope. The XNU build does not produce compile_commands.json directly; for clangd you can wrap make with the general-purpose tool Bear (bear -- make …, approximate approach, assuming you can build successfully — see Phase 8). Without an index, XNU’s coding style itself helps: function definitions put the return type on a line of its own, so grep -rn "^vm_fault(" osfmk/ finds a definition directly. The difference is history: apple-oss-distributions/xnu publishes only snapshots per macOS release (tags such as xnu-12377.121.6), with no per-commit information — to find out “why”, all you can do is compare the diff between adjacent tags and combine it with the design notes in the doc/ directory.

读两个内核时的通用顺序：系统调用表（Linux include/uapi/asm-generic/unistd.h，XNU bsd/kern/syscalls.master）→ 入口处理（Phase 0 的异常向量）→ 子系统主函数 → 数据结构的生命周期（分配、引用计数、释放）。
A general order for reading either kernel: the system call table (Linux include/uapi/asm-generic/unistd.h, XNU bsd/kern/syscalls.master) → entry handling (the exception vectors from Phase 0) → the subsystem’s main functions → the lifecycle of the data structures (allocation, reference counting, freeing).

2. 打印式调试：printk ↔ os_log

2. Print debugging: printk ↔ os_log

Linux：printk 写进内核的环形缓冲区，再按级别决定是否同步打到控制台。级别 0–7 从 KERN_EMERG 到 KERN_DEBUG，日常用 pr_err/pr_info/pr_debug，驱动用带设备名的 dev_err 等。/proc/sys/kernel/printk 的第一个数是控制台级别（低于它的数值才上控制台），启动参数 loglevel=、ignore_loglevel 控制同一件事；用户态用 dmesg（-w 跟随，-l err 过滤）读缓冲区。

Linux: printk writes into the kernel’s ring buffer, and the level decides whether the message is also printed to the console. Levels 0–7 run from KERN_EMERG to KERN_DEBUG; day to day you use pr_err/pr_info/pr_debug, and drivers use dev_err and friends, which include the device name. The first number in /proc/sys/kernel/printk is the console level (only values below it reach the console), and the boot parameters loglevel= and ignore_loglevel control the same thing; in user space, dmesg reads the buffer (-w to follow, -l err to filter).

dynamic debug（CONFIG_DYNAMIC_DEBUG）让每个 pr_debug 调用点都能在运行时单独开关：写 <debugfs>/dynamic_debug/control（无 debugfs 时是 /proc/dynamic_debug/control），例如 echo 'file fault.c +p'。高频路径里 printk 本身太慢、还会改变时序，可用 trace_printk 写进 ftrace 缓冲区。

dynamic debug (CONFIG_DYNAMIC_DEBUG) lets every pr_debug call site be switched on and off individually at run time: write to <debugfs>/dynamic_debug/control (/proc/dynamic_debug/control without debugfs), for example echo 'file fault.c +p'. On hot paths printk itself is too slow and also changes the timing; use trace_printk to write into the ftrace buffer instead.

XNU 有三条打印路径：printf（内核版，进内核消息缓冲区，sudo dmesg 可读）；kprintf（pexpert/arm/pe_kprintf.c，走串口/调试通道，需要相应 boot-arg 才输出）；以及 os_log 系列（libkern/os/log.h：os_log、os_log_info、os_log_debug、os_log_error），通过 firehose 缓冲区交给用户态 logd，进入统一日志系统。IOKit 驱动常用 IOLog。读取用 log show / log stream 加谓词，如 --predicate 'process == "kernel"'。统一日志默认把动态字符串参数显示为 <private>，格式串里写 %{public}s 才会明文记录——这是隐私设计，不是 bug。

XNU has three print paths: printf (the kernel version, which goes into the kernel message buffer and is readable with sudo dmesg); kprintf (pexpert/arm/pe_kprintf.c, which goes out over the serial/debug channel and prints only with the corresponding boot-arg); and the os_log family (libkern/os/log.h: os_log, os_log_info, os_log_debug, os_log_error), which hands messages through the firehose buffer to the user-space logd and into the unified logging system. IOKit drivers commonly use IOLog. Read the logs with log show / log stream plus a predicate, such as --predicate 'process == "kernel"'. By default unified logging shows dynamic string arguments as <private>; they are recorded in clear text only if the format string says %{public}s — this is a privacy design, not a bug.

zsh（macOS 默认 shell）有一个同名的内建命令 log，直接敲 log show 会报 too many arguments。本页一律写 /usr/bin/log。
zsh (the default macOS shell) has a builtin command of the same name, log, so typing log show directly fails with too many arguments. This page always writes /usr/bin/log.

延伸阅读：《Linux Kernel Development》第 18 章「调试」；《Linux Device Drivers》第 4 章「调试技术」。

Further reading: Linux Kernel Development, Chapter 18, “Debugging”; Linux Device Drivers, Chapter 4, “Debugging Techniques”.

3. 追踪与性能分析

3. Tracing and performance analysis

ftrace 是 Linux 内建的追踪框架，界面就是 tracefs（/sys/kernel/tracing）里的文件：current_tracer 选 function（记录每个被调用的函数）或 function_graph（记录进入/返回，画出带耗时的调用树）；set_ftrace_filter / set_graph_function 限定范围；events/ 下是静态 tracepoint；结果在 trace / trace_pipe。原理：编译时每个函数开头留一个可修补的位置，DYNAMIC_FTRACE 平时把它保持为 NOP，打开追踪时才改写成跳转，所以关掉时几乎零开销。trace-cmd 是它的命令行前端。

ftrace is the tracing framework built into Linux, and its interface is the files in tracefs (/sys/kernel/tracing): current_tracer selects function (records every function called) or function_graph (records entry/return and draws a call tree with timings); set_ftrace_filter / set_graph_function narrow the scope; static tracepoints live under events/; results are in trace / trace_pipe. How it works: at compile time a patchable slot is left at the start of every function; DYNAMIC_FTRACE normally keeps it as a NOP and rewrites it into a jump only when tracing is switched on, so when it is off the overhead is almost zero. trace-cmd is its command-line front end.

perf 回答「时间花在哪」：perf stat 读硬件/软件计数器，perf record -g 按频率采样调用栈，perf report / 火焰图汇总。eBPF 则是可编程追踪：把经过内核 verifier 校验的小程序挂到 kprobe、tracepoint、perf 事件上，在内核里就地聚合，bpftrace 提供 awk 风格的一行脚本。

perf answers “where does the time go”: perf stat reads hardware/software counters, perf record -g samples call stacks at a given frequency, and perf report / flame graphs summarise them. eBPF, by contrast, is programmable tracing: small programs checked by the kernel verifier are attached to kprobes, tracepoints and perf events and aggregate data in place inside the kernel; bpftrace provides awk-style one-liners.

macOS：dtrace 是 eBPF 的前辈，D 脚本挂在 provider 上（syscall、fbt 函数边界、proc、profile……）；但在 SIP 打开时它会提示 system integrity protection is on, some features will not be available，内核函数级的 fbt 等能力受限。Apple 自己的主力是 kdebug + kperf：内核里遍布 KDBG 事件点（类似 tracepoint，bsd/kern/kdebug.c），osfmk/kperf/ 负责按定时器或事件采样调用栈和计数器。命令行入口是 ktrace（ktrace trace 看事件流，ktrace artrace 录一份可用 Instruments 打开的系统级 trace，--kperf= 指定采样器，如 kstack、ustack），图形入口是 Instruments（命令行 xctrace，需要完整 Xcode）。轻量的现场快照用 sample（单进程）和 spindump（全系统，含内核栈）。延伸阅读：《Systems Performance》2nd ed. 的 perf、Ftrace、BPF 相关章节；《BPF Performance Tools》按子系统组织的工具章节。

macOS: dtrace is eBPF’s predecessor, with D scripts attached to providers (syscall, fbt function boundaries, proc, profile…); but with SIP on it warns system integrity protection is on, some features will not be available, and capabilities such as kernel function-level fbt are restricted. Apple’s own workhorse is kdebug + kperf: KDBG event points are spread throughout the kernel (similar to tracepoints, bsd/kern/kdebug.c), and osfmk/kperf/ samples call stacks and counters on timers or events. The command-line entry point is ktrace (ktrace trace shows the event stream, ktrace artrace records a system-wide trace that Instruments can open, and --kperf= selects samplers such as kstack and ustack); the graphical entry point is Instruments (command line xctrace, which needs the full Xcode). For lightweight on-the-spot snapshots use sample (a single process) and spindump (system-wide, including kernel stacks). Further reading: the chapters on perf, Ftrace and BPF in Systems Performance, 2nd ed.; the tool chapters of BPF Performance Tools, organised by subsystem.

4. 交互式调试器

4. Interactive debuggers

QEMU gdbstub：-s 是 -gdb tcp::1234 的简写，-S 让虚拟 CPU 在第一条指令前停住。gdb 用 GDB Remote Serial Protocol（RSP）通过 TCP 读写寄存器和内存、设断点——被调试的是整台虚拟机，内核毫不知情，所以从第一条指令起就能调。要点：内核要带完整调试信息（arm64 defconfig 默认开了 CONFIG_DEBUG_INFO_REDUCED，要关掉）、开 CONFIG_GDB_SCRIPTS 并 make scripts_gdb，命令行加 nokaslr（否则符号地址对不上；内核文档对直接 -kernel 启动的建议是干脆关掉 CONFIG_RANDOMIZE_BASE）。断在 start_kernel 这种 MMU 打开前后的地方用 hbreak（硬件断点），软件断点要往内存里写 brk，地址未映射时写不进去。vmlinux-gdb.py 提供 lx-symbols、lx-dmesg、lx-ps 等辅助命令。

QEMU gdbstub: -s is shorthand for -gdb tcp::1234, and -S holds the virtual CPU before its first instruction. gdb uses the GDB Remote Serial Protocol (RSP) over TCP to read and write registers and memory and to set breakpoints — what is being debugged is the whole virtual machine, and the kernel knows nothing about it, so you can debug from the very first instruction. Key points: the kernel needs full debug info (arm64 defconfig enables CONFIG_DEBUG_INFO_REDUCED by default, so turn it off), enable CONFIG_GDB_SCRIPTS and run make scripts_gdb, and add nokaslr to the command line (otherwise the symbol addresses do not match; for direct -kernel boots the kernel documentation recommends simply turning off CONFIG_RANDOMIZE_BASE). To stop in places around MMU enable such as start_kernel, use hbreak (a hardware breakpoint): a software breakpoint has to write brk into memory, which fails when the address is not mapped. vmlinux-gdb.py provides helper commands such as lx-symbols, lx-dmesg and lx-ps.

kgdb 是内核自带的调试桩（CONFIG_KGDB），用于真机：通过串口（kgdboc=ttyAMA0,115200，加 kgdbwait 则启动时等待）与 host 上的 gdb 通信，运行中用 echo g > /proc/sysrq-trigger 进入。代价是调试器本身依赖内核状态，内核坏得太厉害时就进不去。

kgdb is the debug stub built into the kernel (CONFIG_KGDB), used on real hardware: it talks to gdb on the host over a serial port (kgdboc=ttyAMA0,115200; add kgdbwait to wait at boot), and at run time you enter it with echo g > /proc/sysrq-trigger. The cost is that the debugger itself depends on kernel state, so when the kernel is too badly broken you cannot get in.

XNU 两机调试：被调试的「target Mac」跑 KDK 里的 development 内核，通过 boot-arg debug= 打开调试标志（位定义在 osfmk/kern/debug.h：如 DB_NMI 0x4、DB_ARP 0x40、DB_KERN_DUMP_ON_PANIC 0x400）。当它 panic 或收到 NMI 时停下等待调试器；「host Mac」上的 lldb 用 kdp-remote <ip> 通过 KDP（Kernel Debugging Protocol，UDP 41139，osfmk/kdp/kdp_protocol.h 里的 KDP_CONNECT、KDP_READREGS、KDP_READMEM64、KDP_BREAKPOINT64_SET……）连上。KDK 的 dSYM 里带着 tools/lldbmacros/ 那套 Python 宏，提供 showalltasks、showallstacks、paniclog、showbootargs 等命令。Apple Silicon 上改 boot-args、引导非默认内核都要先在 recoveryOS 里降低安全级别（Reduced Security）；具体步骤随 macOS 版本变化，以 KDK 自带的说明为准。没有第二台 Mac 时，可以对 macOS 虚拟机（XNU 的 VMAPPLE 机型配置）练习，大致路径。

XNU two-machine debugging: the “target Mac” being debugged runs the development kernel from the KDK, with debug flags turned on through the boot-arg debug= (the bits are defined in osfmk/kern/debug.h, such as DB_NMI 0x4, DB_ARP 0x40, DB_KERN_DUMP_ON_PANIC 0x400). When it panics or receives an NMI it stops and waits for a debugger; lldb on the “host Mac” connects with kdp-remote <ip> over KDP (Kernel Debugging Protocol, UDP 41139; KDP_CONNECT, KDP_READREGS, KDP_READMEM64, KDP_BREAKPOINT64_SET… in osfmk/kdp/kdp_protocol.h). The KDK’s dSYM carries the Python macros from tools/lldbmacros/, which provide commands such as showalltasks, showallstacks, paniclog and showbootargs. On Apple Silicon, changing boot-args or booting a non-default kernel first requires lowering the security level in recoveryOS (Reduced Security); the exact steps change with the macOS version, so follow the instructions that ship with the KDK. Without a second Mac you can practise against a macOS virtual machine (XNU’s VMAPPLE machine configuration) — approximate path.

两种模式要分清：QEMU gdbstub 和 KDP 都是停机调试（stop-mode），连上后整台机器冻结；ftrace、perf、dtrace、ktrace 是不停机观察。生产问题几乎都只能用后者 + 崩溃转储。
Keep the two modes apart: the QEMU gdbstub and KDP are both stop-mode debugging — once connected, the whole machine is frozen; ftrace, perf, dtrace and ktrace are observation without stopping. Production problems can almost always be handled only with the latter + crash dumps.

5. 崩溃分析

5. Crash analysis

Linux oops：内核态访问出错且查不到异常修复表时，arm64 打印 Unable to handle kernel NULL pointer dereference at virtual address …（或 paging request），随后 Internal error: Oops、寄存器（pc、lr、sp、x0–x29）、Call trace:（每帧形如 func+0x24/0x80，即函数内偏移/函数长度）、Tainted: 标志（加载过专有模块、之前已有 warning 等）。oops 默认只杀掉当前任务，panic_on_oops=1 才升级为 Kernel panic - not syncing；arm64 panic 时还打印 Kernel Offset: 0x… from 0x…（KASLR 偏移）。scripts/faddr2line vmlinux func+0x24/0x80 和 scripts/decode_stacktrace.sh vmlinux < oops.txt 把「符号+偏移」翻译成源码行——因为是相对函数的偏移，KASLR 不影响它。

Linux oops: when a kernel-mode access faults and no exception fixup entry is found, arm64 prints Unable to handle kernel NULL pointer dereference at virtual address … (or paging request), followed by Internal error: Oops, the registers (pc, lr, sp, x0–x29), the Call trace: (each frame looks like func+0x24/0x80, i.e. offset within the function / function length) and the Tainted: flags (a proprietary module was loaded, there was an earlier warning, and so on). By default an oops kills only the current task; only panic_on_oops=1 escalates it to Kernel panic - not syncing; on a panic arm64 also prints Kernel Offset: 0x… from 0x… (the KASLR offset). scripts/faddr2line vmlinux func+0x24/0x80 and scripts/decode_stacktrace.sh vmlinux < oops.txt translate “symbol + offset” into source lines — because the offset is relative to the function, KASLR does not affect it.

kdump：启动参数 crashkernel= 预留一块内存，用 kexec -p 预先装入一个「捕获内核」；panic 时直接跳进它（不经固件），原内核的内存以 /proc/vmcore（ELF core 格式）呈现，makedumpfile 过滤压缩后保存。分析用 crash vmlinux vmcore：bt、log、ps、kmem、struct——相当于对已死的内核跑一个调试器。

kdump: the boot parameter crashkernel= reserves a block of memory, and kexec -p preloads a “capture kernel” into it; on panic the system jumps straight into it (without going through the firmware), the original kernel’s memory is presented as /proc/vmcore (ELF core format), and makedumpfile filters, compresses and saves it. Analyse it with crash vmlinux vmcore: bt, log, ps, kmem, struct — the equivalent of running a debugger on a dead kernel.

macOS panic：XNU 在 osfmk/kern/debug.c 里生成 panic log：第一行 panic(cpu N caller 0x…): + panic 字符串（如 arm64 内核数据访问异常的 Kernel data abort.）；之后有 Kernel version、Kernel slide、Kernel text base、出事的任务（Panicked task）和以 lr: 0x… fp: 0x… 逐帧列出的回溯（osfmk/arm/model_dep.c）。日志先存在保留区域，重启后写成 /Library/Logs/DiagnosticReports/ 下的 .panic 文件（Console 的 Crash Reports 也能看到）。回溯里是滑动后的运行地址：减去 Kernel slide 才能对上 KDK 里未滑动的符号；或者让工具替你做（atos -l、lldb 的 target modules load --slide）。

macOS panic: XNU generates the panic log in osfmk/kern/debug.c: the first line is panic(cpu N caller 0x…): + the panic string (such as Kernel data abort. for an arm64 kernel data-access exception); then come Kernel version, Kernel slide, Kernel text base, the task where it happened (Panicked task) and the backtrace listed frame by frame as lr: 0x… fp: 0x… (osfmk/arm/model_dep.c). The log is first kept in a reserved region and written after reboot as a .panic file under /Library/Logs/DiagnosticReports/ (also visible under Crash Reports in Console). The backtrace holds slid run-time addresses: subtract Kernel slide to match the unslid symbols in the KDK, or let a tool do it for you (atos -l, lldb’s target modules load --slide).

kernel core：设置 DB_KERN_DUMP_ON_PANIC（0x400）和 _panicd_ip= 后，panic 的机器会把整个内核 core 通过网络发给另一台运行 kdumpd（/usr/libexec/kdumpd，UDP 1069，默认存到 /var/tmp/PanicDumps）的 Mac；之后 lldb -c core 配上 KDK 符号和 lldbmacros 分析（大致路径，网络与本地 core 的支持随硬件和版本变化）。延伸阅读：《Linux Kernel Debugging》的 Oops 解读与内核 panic 相关章节。

kernel core: with DB_KERN_DUMP_ON_PANIC (0x400) and _panicd_ip= set, the panicking machine sends the whole kernel core over the network to another Mac running kdumpd (/usr/libexec/kdumpd, UDP 1069, saved to /var/tmp/PanicDumps by default); then analyse it with lldb -c core plus the KDK symbols and lldbmacros (approximate path; support for network and local cores varies with hardware and version). Further reading: the chapters on interpreting Oopses and on kernel panics in Linux Kernel Debugging.

6. 二分定位

6. Bisecting

「v6.11 好的，v6.12 坏了」——两者之间有一万多个提交。git bisect 是二分查找：每步检出中点、你判断好坏，约 log2(N) 步收敛（1 万个提交约 14 步）。内核里每一步都要重新编译和启动，所以自动化才是关键：git bisect run ./test.sh，脚本返回 0 = good，1–127（125 除外）= bad，125 = skip（这个提交编不过或测不了）。QEMU + initramfs 的好处在这里体现：一个「编译 → 启动 → 跑复现 → 根据串口输出判好坏」的脚本几分钟一轮。

“v6.11 is good, v6.12 is bad” — there are more than ten thousand commits in between. git bisect is a binary search: at each step it checks out the midpoint and you judge good or bad, converging in about log2(N) steps (about 14 steps for 10,000 commits). In the kernel every step means rebuilding and rebooting, so automation is the key: git bisect run ./test.sh, where the script returns 0 = good, 1–127 (except 125) = bad, and 125 = skip (this commit does not build or cannot be tested). This is where QEMU + initramfs pays off: a “build → boot → run the reproducer → judge good or bad from the serial output” script takes a few minutes per round.

两个常见坑：bisect 过程中 .config 会随 Kconfig 变化，用 make olddefconfig 保持一致；问题偶发时，测试脚本要重复多次才敢判 good，否则会二分到错误的提交。XNU 外部只有按发布的快照，无法逐提交二分；你能做的是先在 macOS 版本之间缩小到「哪一次发布引入」，再对那两个 tag 做 git diff xnu-A xnu-B -- osfmk/vm/ 一类的定向比对（推断：Apple 内部有完整历史，可以真正二分）。

Two common pitfalls: during a bisect the .config changes along with Kconfig, so keep it consistent with make olddefconfig; and when the problem is intermittent, the test script must repeat many times before it dares to call a commit good, otherwise the bisect lands on the wrong commit. Outside Apple, XNU has only per-release snapshots, so per-commit bisection is impossible; what you can do is first narrow it down across macOS versions to “which release introduced it”, then do a targeted comparison of those two tags along the lines of git diff xnu-A xnu-B -- osfmk/vm/ (inference: Apple has the full history internally and can truly bisect).

7. 写最小复现

7. Writing a minimal reproducer

一个好的复现程序：单文件、无依赖、确定性、几秒内触发，在 QEMU 里用带 KASAN 的内核跑（KASAN 在越界/释放后使用的第一时间报告，而不是等到很久以后的随机崩溃）。缩小的方法是反复删：删一个系统调用、一个线程、一个参数，看还能不能触发；多线程竞态用 sched_setaffinity 绑核、循环放大窗口。

A good reproducer is a single file, dependency-free, deterministic, and triggers within a few seconds; run it in QEMU on a kernel with KASAN (KASAN reports an out-of-bounds access or use-after-free the moment it happens, instead of leaving you with a random crash much later). To shrink it, keep deleting: remove a system call, a thread, an argument, and see whether it still triggers; for multithreaded races, pin threads to cores with sched_setaffinity and widen the window with loops.

syzkaller 的 C 复现程序是很好的范本：它直接 syscall(__NR_xxx, …) 绕过 libc，把参数放在固定地址（常见 mmap(0x20000000, …) 映射出的区域），用很多小线程和循环重复竞态；syzbot 的 dashboard（syzkaller.appspot.com）上每个 bug 都附带复现程序、内核配置和 KASAN 报告，可以拿来练习「读报告 → 本地复现 → 定位」。syzkaller 也有 Darwin 目标（仓库 docs/darwin/），XNU 侧对应的是 KASAN 内核配置（XNU 的 SUPPORTED_KERNEL_CONFIGS 里有 KASAN）。

syzkaller’s C reproducers are a very good model: they call syscall(__NR_xxx, …) directly to bypass libc, put arguments at fixed addresses (commonly a region mapped with mmap(0x20000000, …)), and repeat races with many small threads and loops; on the syzbot dashboard (syzkaller.appspot.com) every bug comes with a reproducer, the kernel config and the KASAN report, which you can use to practise “read the report → reproduce locally → locate the bug”. syzkaller also has a Darwin target (docs/darwin/ in the repository), and the XNU-side counterpart is the KASAN kernel configuration (KASAN is in XNU’s SUPPORTED_KERNEL_CONFIGS).

自测

Self-check

1. 在 1000 个提交中用 git bisect 定位一个回归，大约需要测试多少次？

1. Using git bisect to locate a regression among 1000 commits, roughly how many tests do you need?

bisect 是二分查找，次数约为 log2(1000) ≈ 10。测不了的提交让脚本返回 125（skip），会多花几步但不影响正确性。bisect is a binary search, so the count is about log2(1000) ≈ 10. For a commit that cannot be tested, have the script return 125 (skip); it costs a few extra steps but does not affect correctness.

2. QEMU 启动参数 -s -S 的作用是？

2. What do the QEMU options -s -S do?

-s 是 -gdb tcp::1234 的简写；-S 让 CPU 在启动时停住，直到调试器发出 continue。调试桩在 QEMU 里，所以从内核第一条指令起就能调。-s is shorthand for -gdb tcp::1234; -S holds the CPU at startup until the debugger issues continue. The debug stub lives in QEMU, so you can debug from the kernel’s very first instruction.

3. macOS panic 报告回溯里的 lr 地址，为什么不能直接拿去 KDK 的内核符号里查？

3. Why can the lr addresses in the backtrace of a macOS panic report not be looked up directly in the KDK’s kernel symbols?

XNU 启动时整体随机滑动内核；panic log 同时记下 Kernel slide 和 Kernel text base 就是为了事后符号化。还要保证 KDK 与 build 号完全一致。Linux oops 的 Call trace 写的是函数加偏移，所以不受 KASLR 影响。At boot XNU slides the whole kernel by a random amount; the panic log records both Kernel slide and Kernel text base precisely so that it can be symbolicated afterwards. The KDK must also match the build number exactly. A Linux oops’s Call trace is written as function plus offset, so it is unaffected by KASLR.

4. 在 SIP 打开的 Mac 上运行 sudo dtrace …，最可能出现什么情况？

dtrace 仍在系统里，但 SIP 限制了它能看到的东西。Apple 自己更常用 kdebug/kperf（ktrace、Instruments），这些在 SIP 打开时可以正常使用。dtrace is still in the system, but SIP limits what it can see. Apple itself more often uses kdebug/kperf (ktrace, Instruments), which work normally with SIP on.
