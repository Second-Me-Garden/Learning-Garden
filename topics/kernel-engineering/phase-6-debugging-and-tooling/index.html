Debugging & Tooling 调试与工具：ftrace/perf/kgdb/crash ↔ lldb+KDP/dtrace/panic log；读内核源码的方法

内核工程师的大部分时间不是在写新代码，而是在读代码、追踪问题和分析崩溃。Apple 的内核面试通常包含调试环节，团队日常也离不开 panic log 分析和两机调试；这一阶段把 Linux 与 macOS 两边的工具箱配齐。

目标

读完并做完实验后，你应该能：
  • 用 cscope 或 clangd 在 Linux 与 XNU 源码树中快速跳转定义和调用者。
  • 用 ftrace 和 perf 追踪一个内核函数的调用与热点，并说出 macOS 上对应的 dtrace / Instruments 做法。
  • 用 QEMU gdbstub 单步调试 Linux 内核，并说明 lldb + KDP 两机调试 XNU 的基本流程。
  • 读懂一份 panic 日志的关键字段，并用 git bisect 与最小复现缩小问题范围。

前置

  • Phase 0（在 QEMU 中编译并启动 Linux、ARM64 寄存器）。
  • Phase 1–5（调试需要知道被调试的子系统在做什么；可与 Phase 3–5 交叉进行）。

核心概念

1. 高效读内核源码

本节讲 cscope/ctags、clangd + compile_commands.json（Linux 用 scripts/clang-tools/gen_compile_commands.py 生成）以及在线交叉索引的用法。

2. 打印式调试：printk ↔ os_log

本节讲日志级别、dmesg、dynamic debug，以及 XNU 内核日志如何进入统一日志系统（log show）。

3. 追踪与性能分析

本节对比 Linux 的 ftrace、perf、eBPF 与 macOS 的 dtrace、kperf/ktrace、Instruments。

4. 交互式调试器

本节讲 QEMU gdbstub（-s -S）与 kgdb，以及 macOS 上用 lldb 通过 KDP 连接目标机的两机调试。

5. 崩溃分析

本节讲 Linux oops/panic 信息、kdump + crash 工具，以及 macOS panic 日志的结构与 kernel core dump。

6. 二分定位

本节讲用 git bisect（含 git bisect run 自动化）在内核版本之间定位引入回归的提交。

7. 写最小复现

本节讲如何把一个偶发问题缩成可在 QEMU 中稳定重现的小程序或模块，以及 syzkaller 生成的复现程序长什么样。

动手实验

  • Linux（QEMU）：用 -s -S 启动 QEMU，gdb vmlinux 后 target remote :1234，在 start_kernel 下断点。
  • Linux（QEMU）：在 /sys/kernel/tracing 下启用 function_graph tracer，追踪一次 openat 的调用树。
  • macOS：在 Console 或 /Library/Logs/DiagnosticReports/ 中找一份历史 panic 报告，标出 panic 字符串、回溯与内核版本。
  • 任意：在内核树上用 git bisect 走一遍（可用人为制造的回归练习）。

自测

1. 在 1000 个提交中用 git bisect 定位一个回归，大约需要测试多少次？

bisect 是二分查找，次数约为 log2(1000) ≈ 10。

2. QEMU 启动参数 -s -S 的作用是？

-s 是 -gdb tcp::1234 的简写；-S 让 CPU 在启动时停住，直到调试器发出 continue。
