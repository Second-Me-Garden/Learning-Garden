Learning Garden Kernel Engineering Phase 6

Phase 6 / 9 · 约 1–2 周

Debugging & Tooling 调试与工具：ftrace/perf/kgdb/crash ↔ lldb+KDP/dtrace/panic log；读内核源码的方法

内核工程师的大部分时间不是在写新代码，而是在读代码、追踪问题和分析崩溃。Apple 的内核面试通常包含调试环节，团队日常也离不开 panic log 分析和两机调试；这一阶段把 Linux 与 macOS 两边的工具箱配齐。

目标

读完并做完实验后，你应该能：
  • 用 cscope 或 clangd 在 Linux 与 XNU 源码树中快速跳转定义和调用者。
  • 用 ftrace 和 perf 追踪一个内核函数的调用与热点，并说出 macOS 上对应的 dtrace / Instruments 做法。
  • 用 QEMU gdbstub 单步调试 Linux 内核，并说明 lldb + KDP 两机调试 XNU 的基本流程。
  • 读懂一份 panic 日志的关键字段，并用 git bisect 与最小复现缩小问题范围。

前置

  • Phase 0：在 QEMU 中编译并启动 Linux（本阶段直接复用 Lab A 的 Image 和 busybox initramfs）、ARM64 寄存器与异常。
  • Phase 1–5：调试需要知道被调试的子系统在做什么；本阶段可与 Phase 3–5 交叉进行。Phase 2 的缺页路径是读 oops 的最好练习素材。
  • macOS 一侧：能用 sudo；装了 Xcode（不只是 Command Line Tools）才有 xctrace 和 Instruments。

核心概念

1. 高效读内核源码

内核源码太大，不能「从头读」。有效的读法是从入口追数据结构：先找到用户态能触发的入口（系统调用表、ioctl、fault handler），沿调用链往下，每遇到一个结构体就去看它在哪里分配、谁持有引用、谁加锁。工具只是让「跳到定义 / 列出调用者」这两个动作足够快。

Linux：顶层 Makefile 自带 make tags、make cscope、make gtags 目标（交叉构建时记得带同样的 ARCH=arm64，否则只索引 x86 的 arch 代码）。更准的是 clangd：构建一次后 make LLVM=1 ARCH=arm64 compile_commands.json（底层是 scripts/clang-tools/gen_compile_commands.py，读构建产生的 .cmd 文件），编辑器里的 clangd 就能按真实的 .config 解析宏和 #ifdef。不想本地建索引时用在线交叉索引 Elixir（elixir.bootlin.com），可以按版本切换。Linux 有完整 git 历史：git log -S 符号名 找引入/删除某符号的提交，git blame + 提交信息往往直接告诉你「为什么这样写」，提交信息里的 Link: 还会指向邮件列表上的讨论。

XNU：仓库 README 同样给了 make tags / make TAGS / make cscope。XNU 构建不直接产出 compile_commands.json，要 clangd 可以用通用工具 Bear 包一层 make（bear -- make …，大致做法，前提是你能构建成功，见 Phase 8）。没有索引时，XNU 的代码风格本身帮你：函数定义把返回类型单独放一行，所以 grep -rn "^vm_fault(" osfmk/ 能直接定位定义。区别在历史：apple-oss-distributions/xnu 只按 macOS 版本发布快照（tag 形如 xnu-12377.121.6），没有逐提交的信息——想知道「为什么」，只能对比相邻 tag 的 diff 再结合 doc/ 目录下的设计说明。

读两个内核时的通用顺序：系统调用表（Linux include/uapi/asm-generic/unistd.h，XNU bsd/kern/syscalls.master）→ 入口处理（Phase 0 的异常向量）→ 子系统主函数 → 数据结构的生命周期（分配、引用计数、释放）。

2. 打印式调试：printk ↔ os_log

Linux：printk 写进内核的环形缓冲区，再按级别决定是否同步打到控制台。级别 0–7 从 KERN_EMERG 到 KERN_DEBUG，日常用 pr_err/pr_info/pr_debug，驱动用带设备名的 dev_err 等。/proc/sys/kernel/printk 的第一个数是控制台级别（低于它的数值才上控制台），启动参数 loglevel=、ignore_loglevel 控制同一件事；用户态用 dmesg（-w 跟随，-l err 过滤）读缓冲区。

dynamic debug（CONFIG_DYNAMIC_DEBUG）让每个 pr_debug 调用点都能在运行时单独开关：写 <debugfs>/dynamic_debug/control（无 debugfs 时是 /proc/dynamic_debug/control），例如 echo 'file fault.c +p'。高频路径里 printk 本身太慢、还会改变时序，可用 trace_printk 写进 ftrace 缓冲区。

XNU 有三条打印路径：printf（内核版，进内核消息缓冲区，sudo dmesg 可读）；kprintf（pexpert/arm/pe_kprintf.c，走串口/调试通道，需要相应 boot-arg 才输出）；以及 os_log 系列（libkern/os/log.h：os_log、os_log_info、os_log_debug、os_log_error），通过 firehose 缓冲区交给用户态 logd，进入统一日志系统。IOKit 驱动常用 IOLog。读取用 log show / log stream 加谓词，如 --predicate 'process == "kernel"'。统一日志默认把动态字符串参数显示为 <private>，格式串里写 %{public}s 才会明文记录——这是隐私设计，不是 bug。

zsh（macOS 默认 shell）有一个同名的内建命令 log，直接敲 log show 会报 too many arguments。本页一律写 /usr/bin/log。

3. 追踪与性能分析

ftrace 是 Linux 内建的追踪框架，界面就是 tracefs（/sys/kernel/tracing）里的文件：current_tracer 选 function（记录每个被调用的函数）或 function_graph（记录进入/返回，画出带耗时的调用树）；set_ftrace_filter / set_graph_function 限定范围；events/ 下是静态 tracepoint；结果在 trace / trace_pipe。原理：编译时每个函数开头留一个可修补的位置，DYNAMIC_FTRACE 平时把它保持为 NOP，打开追踪时才改写成跳转，所以关掉时几乎零开销。trace-cmd 是它的命令行前端。

perf 回答「时间花在哪」：perf stat 读硬件/软件计数器，perf record -g 按频率采样调用栈，perf report / 火焰图汇总。eBPF 则是可编程追踪：把经过内核 verifier 校验的小程序挂到 kprobe、tracepoint、perf 事件上，在内核里就地聚合，bpftrace 提供 awk 风格的一行脚本。

macOS：dtrace 是 eBPF 的前辈，D 脚本挂在 provider 上（syscall、fbt 函数边界、proc、profile……）；但在 SIP 打开时它会提示 system integrity protection is on, some features will not be available，内核函数级的 fbt 等能力受限。Apple 自己的主力是 kdebug + kperf：内核里遍布 KDBG 事件点（类似 tracepoint，bsd/kern/kdebug.c），osfmk/kperf/ 负责按定时器或事件采样调用栈和计数器。命令行入口是 ktrace（ktrace trace 看事件流，ktrace artrace 录一份可用 Instruments 打开的系统级 trace，--kperf= 指定采样器，如 kstack、ustack），图形入口是 Instruments（命令行 xctrace，需要完整 Xcode）。轻量的现场快照用 sample（单进程）和 spindump（全系统，含内核栈）。

4. 交互式调试器

QEMU gdbstub：-s 是 -gdb tcp::1234 的简写，-S 让虚拟 CPU 在第一条指令前停住。gdb 用 GDB Remote Serial Protocol（RSP）通过 TCP 读写寄存器和内存、设断点——被调试的是整台虚拟机，内核毫不知情，所以从第一条指令起就能调。要点：内核要带完整调试信息（arm64 defconfig 默认开了 CONFIG_DEBUG_INFO_REDUCED，要关掉）、开 CONFIG_GDB_SCRIPTS 并 make scripts_gdb，命令行加 nokaslr（否则符号地址对不上；内核文档对直接 -kernel 启动的建议是干脆关掉 CONFIG_RANDOMIZE_BASE）。断在 start_kernel 这种 MMU 打开前后的地方用 hbreak（硬件断点），软件断点要往内存里写 brk，地址未映射时写不进去。vmlinux-gdb.py 提供 lx-symbols、lx-dmesg、lx-ps 等辅助命令。

kgdb 是内核自带的调试桩（CONFIG_KGDB），用于真机：通过串口（kgdboc=ttyAMA0,115200，加 kgdbwait 则启动时等待）与 host 上的 gdb 通信，运行中用 echo g > /proc/sysrq-trigger 进入。代价是调试器本身依赖内核状态，内核坏得太厉害时就进不去。

XNU 两机调试：被调试的「target Mac」跑 KDK 里的 development 内核，通过 boot-arg debug= 打开调试标志（位定义在 osfmk/kern/debug.h：如 DB_NMI 0x4、DB_ARP 0x40、DB_KERN_DUMP_ON_PANIC 0x400）。当它 panic 或收到 NMI 时停下等待调试器；「host Mac」上的 lldb 用 kdp-remote <ip> 通过 KDP（Kernel Debugging Protocol，UDP 41139，osfmk/kdp/kdp_protocol.h 里的 KDP_CONNECT、KDP_READREGS、KDP_READMEM64、KDP_BREAKPOINT64_SET……）连上。KDK 的 dSYM 里带着 tools/lldbmacros/ 那套 Python 宏，提供 showalltasks、showallstacks、paniclog、showbootargs 等命令。Apple Silicon 上改 boot-args、引导非默认内核都要先在 recoveryOS 里降低安全级别（Reduced Security）；具体步骤随 macOS 版本变化，以 KDK 自带的说明为准。没有第二台 Mac 时，可以对 macOS 虚拟机（XNU 的 VMAPPLE 机型配置）练习，大致路径。

两种模式要分清：QEMU gdbstub 和 KDP 都是停机调试（stop-mode），连上后整台机器冻结；ftrace、perf、dtrace、ktrace 是不停机观察。生产问题几乎都只能用后者 + 崩溃转储。

5. 崩溃分析

Linux oops：内核态访问出错且查不到异常修复表时，arm64 打印 Unable to handle kernel NULL pointer dereference at virtual address …（或 paging request），随后 Internal error: Oops、寄存器（pc、lr、sp、x0–x29）、Call trace:（每帧形如 func+0x24/0x80，即函数内偏移/函数长度）、Tainted: 标志（加载过专有模块、之前已有 warning 等）。oops 默认只杀掉当前任务，panic_on_oops=1 才升级为 Kernel panic - not syncing；arm64 panic 时还打印 Kernel Offset: 0x… from 0x…（KASLR 偏移）。scripts/faddr2line vmlinux func+0x24/0x80 和 scripts/decode_stacktrace.sh vmlinux < oops.txt 把「符号+偏移」翻译成源码行——因为是相对函数的偏移，KASLR 不影响它。

kdump：启动参数 crashkernel= 预留一块内存，用 kexec -p 预先装入一个「捕获内核」；panic 时直接跳进它（不经固件），原内核的内存以 /proc/vmcore（ELF core 格式）呈现，makedumpfile 过滤压缩后保存。分析用 crash vmlinux vmcore：bt、log、ps、kmem、struct——相当于对已死的内核跑一个调试器。

macOS panic：XNU 在 osfmk/kern/debug.c 里生成 panic log：第一行 panic(cpu N caller 0x…): + panic 字符串（如 arm64 内核数据访问异常的 Kernel data abort.）；之后有 Kernel version、Kernel slide、Kernel text base、出事的任务（Panicked task）和以 lr: 0x… fp: 0x… 逐帧列出的回溯（osfmk/arm/model_dep.c）。日志先存在保留区域，重启后写成 /Library/Logs/DiagnosticReports/ 下的 .panic 文件（Console 的 Crash Reports 也能看到）。回溯里是滑动后的运行地址：减去 Kernel slide 才能对上 KDK 里未滑动的符号；或者让工具替你做（atos -l、lldb 的 target modules load --slide）。

kernel core：设置 DB_KERN_DUMP_ON_PANIC（0x400）和 _panicd_ip= 后，panic 的机器会把整个内核 core 通过网络发给另一台运行 kdumpd（/usr/libexec/kdumpd，UDP 1069，默认存到 /var/tmp/PanicDumps）的 Mac；之后 lldb -c core 配上 KDK 符号和 lldbmacros 分析（大致路径，网络与本地 core 的支持随硬件和版本变化）。

6. 二分定位

「v6.11 好的，v6.12 坏了」——两者之间有一万多个提交。git bisect 是二分查找：每步检出中点、你判断好坏，约 log2(N) 步收敛（1 万个提交约 14 步）。内核里每一步都要重新编译和启动，所以自动化才是关键：git bisect run ./test.sh，脚本返回 0 = good，1–127（125 除外）= bad，125 = skip（这个提交编不过或测不了）。QEMU + initramfs 的好处在这里体现：一个「编译 → 启动 → 跑复现 → 根据串口输出判好坏」的脚本几分钟一轮。

两个常见坑：bisect 过程中 .config 会随 Kconfig 变化，用 make olddefconfig 保持一致；问题偶发时，测试脚本要重复多次才敢判 good，否则会二分到错误的提交。XNU 外部只有按发布的快照，无法逐提交二分；你能做的是先在 macOS 版本之间缩小到「哪一次发布引入」，再对那两个 tag 做 git diff xnu-A xnu-B -- osfmk/vm/ 一类的定向比对（推断：Apple 内部有完整历史，可以真正二分）。

7. 写最小复现

一个好的复现程序：单文件、无依赖、确定性、几秒内触发，在 QEMU 里用带 KASAN 的内核跑（KASAN 在越界/释放后使用的第一时间报告，而不是等到很久以后的随机崩溃）。缩小的方法是反复删：删一个系统调用、一个线程、一个参数，看还能不能触发；多线程竞态用 sched_setaffinity 绑核、循环放大窗口。

syzkaller 的 C 复现程序是很好的范本：它直接 syscall(__NR_xxx, …) 绕过 libc，把参数放在固定地址（常见 mmap(0x20000000, …) 映射出的区域），用很多小线程和循环重复竞态；syzbot 的 dashboard（syzkaller.appspot.com）上每个 bug 都附带复现程序、内核配置和 KASAN 报告，可以拿来练习「读报告 → 本地复现 → 定位」。syzkaller 也有 Darwin 目标（仓库 docs/darwin/），XNU 侧对应的是 KASAN 内核配置（XNU 的 SUPPORTED_KERNEL_CONFIGS 里有 KASAN）。

动手实验

Lab A · QEMU Linux：ftrace、gdb、读一次 oops

  1. 把 Phase 0 的内核重新配置成「可调试」版本（arm64 defconfig 默认关着 ftrace、开着 DEBUG_INFO_REDUCED）：
    cd linux
./scripts/config -d DEBUG_INFO_REDUCED -e GDB_SCRIPTS \
  -e FTRACE -e FUNCTION_TRACER -e FUNCTION_GRAPH_TRACER -e DYNAMIC_FTRACE \
  -e DYNAMIC_DEBUG
make LLVM=1 ARCH=arm64 olddefconfig
grep -E "DEBUG_INFO_REDUCED|GDB_SCRIPTS|FUNCTION_GRAPH_TRACER|DYNAMIC_DEBUG=" .config
make LLVM=1 ARCH=arm64 -j"$(sysctl -n hw.ncpu)" Image scripts_gdb
make LLVM=1 ARCH=arm64 compile_commands.json     # 顺便给 clangd 用
    grep 那一行要看到 GDB_SCRIPTS=y、FUNCTION_GRAPH_TRACER=y，且 DEBUG_INFO_REDUCED 是 is not set；若某项被 olddefconfig 抹掉，说明有依赖没满足，用 make LLVM=1 ARCH=arm64 menuconfig 搜索该选项看依赖。
  2. 用 Phase 2 的 initramfs（busybox 链接里有 grep head sleep）正常启动，然后在 guest 里用 ftrace 画出一次 openat 的调用树：
    mount -t tracefs nodev /sys/kernel/tracing
cd /sys/kernel/tracing
cat available_tracers                        # 应含 function function_graph nop
grep openat available_filter_functions       # arm64 的系统调用入口通常是 __arm64_sys_openat
echo __arm64_sys_openat > set_graph_function
echo function_graph > current_tracer
echo 1 > tracing_on; cat /proc/version > /dev/null; echo 0 > tracing_on
head -80 trace                               # 带缩进和耗时的调用树：getname → do_filp_open → path_openat …
echo nop > current_tracer; echo > set_graph_function
    如果 grep 给出的名字不同，就用它给的那个；不要照抄。把调用树和 Phase 4 的 VFS 路径对照着读。
  3. dynamic debug 与 oops：
    mount -t debugfs none /sys/kernel/debug
grep -c . /sys/kernel/debug/dynamic_debug/control    # 可单独开关的 pr_debug 调用点数量
echo c > /proc/sysrq-trigger                          # 故意让内核崩溃（只在 QEMU 里做！）
    串口上会出现 Kernel panic - not syncing: sysrq triggered crash（现代内核里 sysrq_handle_crash 直接调 panic，不是空指针解引用，所以没有 Oops 和寄存器 dump）：在 Call trace: 里越过 show_stack/dump_backtrace/panic 几帧，找到 sysrq_handle_crash+0x…/0x… 那一帧，以及 Kernel Offset（因为 defconfig 开了 CONFIG_RANDOMIZE_BASE，arm64 的 panic notifier 会打印）。回到 macOS，把那一帧喂给 ./scripts/faddr2line vmlinux sysrq_handle_crash+0x../0x..，应该指向 drivers/tty/sysrq.c 里的 sysrq_handle_crash。
  4. gdb 单步内核。终端 1（注意 -s -S 和 nokaslr）：
    qemu-system-aarch64 -M virt -cpu cortex-a72 -m 1G -nographic -s -S \
  -kernel arch/arm64/boot/Image -initrd initramfs/initramfs.cpio.gz \
  -append "console=ttyAMA0 rdinit=/init nokaslr"
    终端 2：Homebrew 的 gdb 不支持 Apple Silicon 主机，在 arm64 Linux 容器里跑原生 gdb，经 host.docker.internal 连回宿主机的 1234 端口：
    docker run --platform linux/arm64 -it --rm -v "$PWD:/linux" -w /linux debian:bookworm bash -c \
  'apt-get update -qq && apt-get install -y -qq gdb python3 >/dev/null && \
   gdb -iex "add-auto-load-safe-path /linux" vmlinux'
(gdb) target remote host.docker.internal:1234
(gdb) hbreak start_kernel
(gdb) continue
(gdb) bt
(gdb) info registers pc sp
(gdb) next                    # 单步几行 start_kernel
(gdb) continue                # 等 shell 起来后按 Ctrl-C 停住
(gdb) lx-dmesg
(gdb) lx-ps
    常见问题：lx-* 不存在 → vmlinux-gdb.py 没被自动加载（检查 make scripts_gdb 和 safe-path）；断点不命中 → 忘了 nokaslr；源码路径显示为宿主机路径 → set substitute-path /你的/宿主机/linux /linux。不想用容器也可以用宿主机的 lldb：lldb vmlinux → gdb-remote 1234 → breakpoint set -H -n start_kernel（没有 lx-* 辅助命令）。
  5. perf 需要完整的用户态，busybox initramfs 里没有。在任意 arm64 Linux 虚拟机或真机（Debian：sudo apt install linux-perf；Ubuntu：linux-tools-$(uname -r)）上：
    perf stat -e task-clock,context-switches,page-faults -- ls -R /usr > /dev/null
sudo perf record -g -a -- sleep 5
sudo perf report --stdio | head -60
sudo bpftrace -e 'kprobe:do_filp_open { @[comm] = count(); }'   # Ctrl-C 后打印每个进程的 open 次数
    虚拟机若没有暴露 PMU，perf stat 会把 cycles 等硬件事件标成 <not supported>，这时改用软件事件 -e cpu-clock。

Lab B · macOS：统一日志、ktrace/kperf、dtrace 与 panic 报告

  1. 启动参数与版本——之后找 KDK 要用 build 号：
    sysctl kern.bootargs              # 正常机器上通常为空
nvram boot-args 2>&1               # 未设置时会报 data was not found
sysctl kern.version kern.osversion # osversion 就是 build 号，如 26B123
csrutil status
  2. 统一日志里的内核消息（注意用全路径，避开 zsh 的内建 log）：
    /usr/bin/log show --last 10m --predicate 'process == "kernel"' --style compact | tail -30
/usr/bin/log show --last 10m --predicate 'process == "kernel" AND eventMessage CONTAINS "Sandbox"' --style compact | tail -5
/usr/bin/log stream --predicate 'process == "kernel"' --style compact     # Ctrl-C 结束
sudo dmesg | tail -20
    第二条会看到 Sandbox 内核扩展记录的 deny(1) …——这是 MACF 策略在内核里拒绝操作留下的痕迹，Phase 7 会讲。
  3. ktrace / kperf：录 5 秒系统级 trace，按 1 ms 采内核栈和用户栈：
    sudo ktrace artrace -t 5s --kperf=kstack,ustack@1ms -o /tmp/sys.atrc
open /tmp/sys.atrc                  # 用 Instruments 打开（需要 Xcode）
sudo ktrace machine                 # 机器信息
man ktrace                          # FILTER / SAMPLING DESCRIPTIONS 两节说明了语法
    只装了 Command Line Tools 时，xcrun xctrace 会报「requires Xcode」；装了 Xcode 后可以 xcrun xctrace record --template 'Time Profiler' --time-limit 5s --launch -- /bin/ls -R /usr。更轻量的替代：sample <pid> 3、sudo spindump <pid> 3。
  4. dtrace 与 SIP：
    sudo dtrace -n 'syscall::open*:entry { @[execname] = count(); }'   # 跑几秒后 Ctrl-C
    SIP 打开时第一行会是 dtrace: system integrity protection is on, some features will not be available：对受保护进程和内核 fbt 的追踪受限，你自己编译的程序通常还能追。完全放开需要在 recoveryOS 里改 SIP 配置——这会降低整机安全性，只在专门的测试机上做，本实验不需要。
  5. panic 报告：
    ls -lt /Library/Logs/DiagnosticReports/ | grep -i panic | head
    有的话打开最新一份，标出 panic(cpu … caller …) 后的字符串、Kernel version、Kernel slide、Kernel text base、Panicked task 和 lr: 回溯；没有的话在 Console → Crash Reports 里找，或者用网上公开的 panic log 练习。若已装了匹配 build 号的 KDK（/Library/Developer/KDKs/），试着符号化前几帧：
    KDK=$(ls -d /Library/Developer/KDKs/*.kdk | tail -1)
ls "$KDK/System/Library/Kernels/"        # 找到与你的 SoC 对应的 kernel.release.tXXXX 及其 .dSYM
atos -o "$KDK/System/Library/Kernels/kernel.release.tXXXX.dSYM" -arch arm64e \
     -l <Kernel text base> <lr1> <lr2> <lr3>
    结果对不上时，用 lldb 显式给 slide：lldb kernel.release.tXXXX → target modules load --file kernel.release.tXXXX --slide <Kernel slide> → image lookup -a <lr>。kernelcache 的布局随版本变化，-l 填哪个基址以实际能对上的为准。
交付物：Lab A 的 function_graph 调用树前 30 行 + faddr2line 的输出；Lab B 的一段内核 Sandbox 日志 + 一份 panic 报告的字段标注（或 KDK 符号化结果）。再写 5 行：gdbstub 与 KDP 各自「谁在被调试、谁提供调试桩、连接前目标必须处于什么状态」。

自测

1. 在 1000 个提交中用 git bisect 定位一个回归，大约需要测试多少次？

bisect 是二分查找，次数约为 log2(1000) ≈ 10。测不了的提交让脚本返回 125（skip），会多花几步但不影响正确性。

2. QEMU 启动参数 -s -S 的作用是？

-s 是 -gdb tcp::1234 的简写；-S 让 CPU 在启动时停住，直到调试器发出 continue。调试桩在 QEMU 里，所以从内核第一条指令起就能调。

3. macOS panic 报告回溯里的 lr 地址，为什么不能直接拿去 KDK 的内核符号里查？

XNU 启动时整体随机滑动内核；panic log 同时记下 Kernel slide 和 Kernel text base 就是为了事后符号化。还要保证 KDK 与 build 号完全一致。Linux oops 的 Call trace 写的是函数加偏移，所以不受 KASLR 影响。

4. 在 SIP 打开的 Mac 上运行 sudo dtrace …，最可能出现什么情况？

dtrace 仍在系统里，但 SIP 限制了它能看到的东西。Apple 自己更常用 kdebug/kperf（ktrace、Instruments），这些在 SIP 打开时可以正常使用。
