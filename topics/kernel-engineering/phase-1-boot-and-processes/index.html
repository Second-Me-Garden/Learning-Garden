核心概念

Core concepts

1. Boot chain：从 bootloader 到 PID 1

1. Boot chain: from the bootloader to PID 1

Linux arm64（规范见 Documentation/arch/arm64/booting.rst）：

Linux arm64 (specified in Documentation/arch/arm64/booting.rst):

  1. 固件 / bootloader（QEMU 里是 QEMU 自己；真机上是 U-Boot、UEFI 等）把内核 Image 放进内存，x0 = 设备树（DTB）物理地址，MMU 关闭，CPU 处于 EL2 或 EL1。
  2. The firmware / bootloader (QEMU itself under QEMU; U-Boot, UEFI and so on on real hardware) places the kernel Image in memory, with x0 = the physical address of the device tree (DTB), the MMU off, and the CPU at EL2 or EL1.
  3. Image 开头是 64 字节的 header：第一条指令是跳转到真正入口的分支，后面有 text_offset、image_size、flags，偏移 0x38 处是魔数 "ARM\x64"。
  4. Image starts with a 64-byte header: the first instruction is a branch to the real entry point, followed by text_offset, image_size and flags; at offset 0x38 is the magic number "ARM\x64".
  5. primary_entry（arch/arm64/kernel/head.S）：保存启动参数、处理 EL2（初始化或降到 EL1）、建立最初的页表。
  6. primary_entry (arch/arm64/kernel/head.S): saves the boot arguments, handles EL2 (initialises it or drops to EL1), and builds the initial page tables.
  7. __primary_switch：调用 __enable_mmu 写 TTBR0/1_EL1 和 SCTLR_EL1 打开 MMU，之后跳到运行在内核虚拟地址上的 __primary_switched：设好 VBAR_EL1（Phase 0 的向量表）、init 任务的栈，再 bl start_kernel。
  8. __primary_switch: calls __enable_mmu, which writes TTBR0/1_EL1 and SCTLR_EL1 to turn the MMU on, then jumps to __primary_switched, which runs at kernel virtual addresses: it sets VBAR_EL1 (the vector table from Phase 0) and the init task’s stack, then does bl start_kernel.
  9. start_kernel()（init/main.c）：一长串 *_init()——内存、中断、定时器、调度器（sched_init）……最后调 rest_init()。
  10. start_kernel() (init/main.c): a long series of *_init() calls — memory, interrupts, timers, the scheduler (sched_init)… and finally rest_init().
  11. rest_init() 创建两个内核线程：kernel_init（拿到 PID 1）和 kthreadd（PID 2，以后所有内核线程的父亲）；启动它的那个 init task 自己退化成 CPU 0 的 idle 线程（PID 0，swapper/0）。
  12. rest_init() creates two kernel threads: kernel_init (which gets PID 1) and kthreadd (PID 2, the parent of every later kernel thread); the init task that started it degrades into CPU 0’s idle thread (PID 0, swapper/0).
  13. kernel_init 跑完 initcall（驱动、文件系统……），然后 run_init_process() exec 用户态的 /init、/sbin/init 等——PID 1 从内核线程变成用户进程（systemd / busybox init）。
  14. kernel_init runs the initcalls (drivers, filesystems…), then run_init_process() execs the user-space /init, /sbin/init and so on — PID 1 turns from a kernel thread into a user process (systemd / busybox init).

XNU on Apple Silicon（大致路径；ROM 和 iBoot 不开源，细节来自 Apple 平台安全白皮书和 Asahi 逆向）：

XNU on Apple Silicon (approximate path; the ROM and iBoot are not open source, and the details come from Apple’s Platform Security Guide and Asahi reverse engineering):

  1. Boot ROM → iBoot（分阶段，逐级验签）→ 加载签名过的 kernelcache（XNU + 预链接的 kext 打成一个镜像）和 Apple 设备树，经 boot_args 结构把参数交给内核。
  2. Boot ROM → iBoot (in stages, each verifying the signature of the next) → loads the signed kernelcache (XNU + prelinked kexts packed into one image) and the Apple device tree, and hands parameters to the kernel through the boot_args structure.
  3. osfmk/arm64/start.s：汇编入口（主 CPU 走 start_first_cpu），设置异常向量、早期页表、开 MMU，然后跳 C。
  4. osfmk/arm64/start.s: the assembly entry (the boot CPU takes start_first_cpu) sets up the exception vectors and early page tables, turns the MMU on, then jumps to C.
  5. arm_init()（osfmk/arm/arm_init.c）：平台早期初始化（pexpert、pmap、时钟），然后 machine_startup()。
  6. arm_init() (osfmk/arm/arm_init.c): early platform initialisation (pexpert, pmap, clocks), then machine_startup().
  7. kernel_bootstrap()（osfmk/kern/startup.c）：初始化 Mach——VM、IPC、task/thread、调度器，创建 kernel_task，然后切到第一个真正的内核线程。
  8. kernel_bootstrap() (osfmk/kern/startup.c): initialises Mach — VM, IPC, task/thread, the scheduler — creates kernel_task, then switches to the first real kernel thread.
  9. kernel_bootstrap_thread()：启动其余 CPU、IOKit（PE_init_iokit）、BSD 层 bsd_init()（bsd/kern/bsd_init.c）。
  10. kernel_bootstrap_thread(): starts the remaining CPUs, IOKit (PE_init_iokit) and the BSD layer, bsd_init() (bsd/kern/bsd_init.c).
  11. bsd_init 建立 kernproc（PID 0，对应 kernel_task），再通过 bsd_utaskbootstrap() → load_init_program() exec /sbin/launchd——PID 1。
  12. bsd_init sets up kernproc (PID 0, corresponding to kernel_task), then through bsd_utaskbootstrap() → load_init_program() execs /sbin/launchd — PID 1.
同一个形状：汇编入口开 MMU → 一个大的 C 初始化函数 → 第一个内核线程 → exec 用户态 PID 1。区别在于 XNU 的 C 初始化分两层（先 Mach 的 kernel_bootstrap，后 BSD 的 bsd_init），中间还要把 IOKit 拉起来。
The same shape: the assembly entry turns the MMU on → one big C initialisation function → the first kernel thread → exec of user-space PID 1. The difference is that XNU’s C initialisation has two layers (Mach’s kernel_bootstrap first, then BSD’s bsd_init), and IOKit has to be brought up in between.

2. 进程与线程模型

2. The process and thread model

Linux 只有一种可调度实体：struct task_struct（include/linux/sched.h）。「进程」和「线程」的区别只在于创建时 clone 的 flags 共享了什么：

Linux has only one schedulable entity: struct task_struct (include/linux/sched.h). The difference between a “process” and a “thread” is only what the clone flags shared at creation:

  • fork() ≈ clone 不带共享 flag：新 task 拿到一份写时复制（COW）的 mm_struct、复制的 fd 表。
  • fork() ≈ clone without sharing flags: the new task gets a copy-on-write (COW) mm_struct and a copied fd table.
  • pthread_create() ≈ clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | …)：新 task 和调用者共享 mm（同一套页表）、fd 表、信号处理；CLONE_THREAD 让它进同一个线程组。
  • pthread_create() ≈ clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | …): the new task shares mm (the same page tables), the fd table and signal handlers with the caller; CLONE_THREAD puts it in the same thread group.
  • 用户态的「PID」其实是线程组 ID（tgid）；每个线程自己的 ID 是 TID（gettid()）。全部路径汇到 kernel_clone()（kernel/fork.c）。
  • The user-space “PID” is really the thread group ID (tgid); each thread’s own ID is its TID (gettid()). All paths converge on kernel_clone() (kernel/fork.c).
  • execve()（fs/exec.c）丢掉旧 mm、装入新程序，task 本身（PID）不变。
  • execve() (fs/exec.c) drops the old mm and loads the new program; the task itself (its PID) is unchanged.

XNU 是两套抽象叠在一起：

XNU is two sets of abstractions stacked together:

  • Mach task（osfmk/kern/task.h）= 资源容器：地址空间（vm_map）+ port 命名空间（ipc_space），本身不执行。
  • Mach task (osfmk/kern/task.h) = a resource container: an address space (vm_map) + a port namespace (ipc_space); it does not execute by itself.
  • Mach thread（osfmk/kern/thread.h）= 执行与调度单位：寄存器状态、内核栈、优先级。task ⊃ 多个 thread。
  • Mach thread (osfmk/kern/thread.h) = the unit of execution and scheduling: register state, kernel stack, priority. A task ⊃ several threads.
  • BSD proc（bsd/sys/proc_internal.h）承载 PID、凭证、fd 表、信号；每个用户进程的 proc 与一个 task 一一对应，每个 thread 另有一个 BSD 侧的 uthread。
  • The BSD proc (bsd/sys/proc_internal.h) carries the PID, credentials, fd table and signals; each user process’s proc corresponds one-to-one to a task, and each thread also has a BSD-side uthread.
  • fork() 存在（bsd/kern/kern_fork.c），但 Apple 推荐 posix_spawn()（bsd/kern/kern_exec.c）：直接创建新 task 并装入程序，不复制父进程地址空间；而且多线程进程 fork 后子进程只剩调用线程，在 exec 之前只能调 async-signal-safe 函数，很多系统框架不是 fork-safe 的。
  • fork() exists (bsd/kern/kern_fork.c), but Apple recommends posix_spawn() (bsd/kern/kern_exec.c): it creates the new task and loads the program directly, without copying the parent’s address space; also, after a multithreaded process forks, the child has only the calling thread and may call only async-signal-safe functions before exec, and many system frameworks are not fork-safe.

3. 上下文切换

3. Context switch

切换总发生在内核态，并且对被切走的线程来说只是「调用了一个函数，很久以后它返回了」。因为是函数调用，按 AAPCS64 只需保存 callee-saved 寄存器（x19–x28、fp=x29、lr=x30、sp）；用户态的全部寄存器早在异常入口就存进了内核栈上的 pt_regs / saved state（Phase 0）。

A switch always happens in kernel mode, and to the thread being switched out it is just “I called a function, and much later it returned”. Because it is a function call, AAPCS64 only requires saving the callee-saved registers (x19–x28, fp=x29, lr=x30, sp); all user-mode registers were already saved into pt_regs / saved state on the kernel stack at exception entry (Phase 0).

  • Linux arm64：__schedule() → context_switch()（kernel/sched/core.c）：先 switch_mm_irqs_off() 切地址空间（不同 mm 时写 TTBR0_EL1 换用户页表；ASID 放在哪个 TTBR 由 TCR_EL1.A1 决定，Linux arm64 放在 TTBR1_EL1 高位，靠它避免整表 TLB flush；内核线程借用前一个 mm），再 switch_to() → __switch_to()（arch/arm64/kernel/process.c，切 FP/SIMD、TLS 等）→ cpu_switch_to(prev, next)（arch/arm64/kernel/entry.S）：把 x19–x28、fp、sp、lr 存进 prev->thread.cpu_context，从 next 的 cpu_context 载入，msr sp_el0 更新 current，ret。
  • Linux arm64: __schedule() → context_switch() (kernel/sched/core.c): first switch_mm_irqs_off() switches the address space (for a different mm it writes TTBR0_EL1 to swap the user page tables; which TTBR holds the ASID is decided by TCR_EL1.A1 — Linux arm64 puts it in the high bits of TTBR1_EL1, and this is what avoids a full TLB flush; kernel threads borrow the previous mm), then switch_to() → __switch_to() (arch/arm64/kernel/process.c, switches FP/SIMD, TLS and so on) → cpu_switch_to(prev, next) (arch/arm64/kernel/entry.S): stores x19–x28, fp, sp, lr into prev->thread.cpu_context, loads them from next’s cpu_context, updates current with msr sp_el0, and does ret.
  • XNU arm64：thread_block() → thread_select() 选出下一个 → thread_invoke()（osfmk/kern/sched_prim.c）→ machine_switch_context()（osfmk/arm64/pcb.c，大致路径：此处同时切 pmap，即 TTBR0/ASID）→ Switch_context（osfmk/arm64/cswitch.s）：存旧线程 callee-saved 寄存器、载入新线程的，更新当前线程指针（大致路径：arm64 上 current_thread() 读的是 TPIDR_EL1）。XNU 还支持 continuation：线程阻塞时可以交出内核栈，醒来后从指定函数重新开始，而不是「返回」。
  • XNU arm64: thread_block() → thread_select() picks the next thread → thread_invoke() (osfmk/kern/sched_prim.c) → machine_switch_context() (osfmk/arm64/pcb.c; approximate path: the pmap, i.e. TTBR0/ASID, is switched here as well) → Switch_context (osfmk/arm64/cswitch.s): stores the old thread’s callee-saved registers, loads the new thread’s, and updates the current-thread pointer (approximate path: on arm64 current_thread() reads TPIDR_EL1). XNU also supports continuations: a thread that blocks can give up its kernel stack and, when it wakes, restart from a specified function instead of “returning”.
  • 新创建的线程从没调用过切换函数，所以创建时伪造一份上下文：Linux 让 cpu_context.pc 指向 ret_from_fork；XNU 让它从一个线程起始的汇编桩开始（Thread_continue，大致路径）。
  • A newly created thread has never called the switch function, so a context is faked for it at creation: Linux points cpu_context.pc at ret_from_fork; XNU starts it from a thread-start assembly stub (Thread_continue, approximate path).

4. 调度：选下一个是谁

4. Scheduling: who runs next

Linux 用调度类分层（stop → deadline → rt → fair → idle），普通任务都在 fair 类（kernel/sched/fair.c）。优先级数值 0–139：0–99 实时，100–139 对应 nice −20…19。

Linux layers scheduling classes (stop → deadline → rt → fair → idle); ordinary tasks are all in the fair class (kernel/sched/fair.c). Priority values run 0–139: 0–99 are real-time, 100–139 correspond to nice −20…19.

  • CFS（2.6.23 – 6.5）：每个任务有 vruntime = 实际运行时间 × 1024 / 权重（nice 越低权重越大，vruntime 涨得越慢）。可运行任务按 vruntime 放在红黑树里，永远选最左（最小 vruntime）。公平，但对延迟敏感的任务没有直接表达方式。
  • CFS (2.6.23 – 6.5): each task has vruntime = actual run time × 1024 / weight (the lower the nice value, the larger the weight and the slower vruntime grows). Runnable tasks sit in a red-black tree ordered by vruntime, and the leftmost one (smallest vruntime) is always picked. Fair, but there is no direct way to express the needs of latency-sensitive tasks.
  • EEVDF（Linux 6.6 起取代 CFS）：仍然记 vruntime，另外算出队列的加权平均 V。任务的 lag = V − vruntime；lag ≥ 0 的任务才 eligible（没有多拿 CPU）。每个任务有虚拟截止时间 vd = vruntime + slice / 权重；在 eligible 任务里选 vd 最早的。较短 slice 的任务 vd 更早，因此能更快被选中——延迟需求从此可以表达（任务自定义 slice 经 sched_attr.sched_runtime，约 6.12 起）。
  • EEVDF (replaces CFS from Linux 6.6): still tracks vruntime, and also computes the queue’s weighted average V. A task’s lag = V − vruntime; only tasks with lag ≥ 0 are eligible (they have not taken more than their share of CPU). Each task has a virtual deadline vd = vruntime + slice / weight; among eligible tasks the one with the earliest vd is picked. A task with a shorter slice has an earlier vd and so is picked sooner — latency needs can now be expressed (a task sets a custom slice via sched_attr.sched_runtime, from about 6.12).

XNU 优先级 0–127，分 4 个带（osfmk/kern/sched.h）：96–127 实时、80–95 内核线程、64–79 保留（系统高优先级）、0–63 用户。用户线程的 QoS（User-Interactive、User-Initiated、Default、Utility、Background）映射到 0–63 里的基础优先级（大致：UI ≈ 46–47，Default 31，Background 4）。

XNU priorities run 0–127 in 4 bands (osfmk/kern/sched.h): 96–127 real-time, 80–95 kernel threads, 64–79 reserved (system high priority), 0–63 user. A user thread’s QoS (User-Interactive, User-Initiated, Default, Utility, Background) maps to a base priority within 0–63 (roughly: UI ≈ 46–47, Default 31, Background 4).

  • timeshare + 衰减：普通线程的有效优先级 sched_pri 从基础优先级出发，随最近 CPU 使用量下降，空闲后回升——防止 CPU 密集线程饿死别人。
  • timeshare + decay: an ordinary thread’s effective priority sched_pri starts from its base priority, falls with recent CPU usage and recovers when the thread is idle — this keeps CPU-bound threads from starving everyone else.
  • clutch（osfmk/kern/sched_clutch.c）：实时线程走单独的 RT 队列直接优先；其余线程三层选择——先在 QoS root bucket（FIXPRI、FG、IN、DF、UT、BG）之间按截止时间做 EDF（高 QoS 有 warp，可以插队，但低 QoS 不会饿死），再在 bucket 内选 thread group（同一 app / 工作负载的线程组）对应的 clutch bucket，最后选 sched_pri 最高的线程。
  • clutch (osfmk/kern/sched_clutch.c): real-time threads go through a separate RT queue and take priority directly; all other threads are selected in three levels — first EDF by deadline across the QoS root buckets (FIXPRI, FG, IN, DF, UT, BG) (higher QoS has warp and can jump the queue, but lower QoS is not starved), then within the bucket the clutch bucket of a thread group (the threads of one app / workload), and finally the thread with the highest sched_pri.
  • AMP（P/E 核）：Apple Silicon 上用 clutch 的多 cluster 扩展 Edge 调度器：每个 cluster 有自己的运行队列层级，按 QoS、thread group 的性能推荐、负载决定放 P 核还是 E 核，并在 cluster 间迁移/偷取。被绑定到某个 CPU 的线程在该 processor 自己的 run queue 里。
  • AMP (P/E cores): Apple Silicon uses Edge, the multi-cluster extension of clutch: each cluster has its own run-queue hierarchy; QoS, the thread group’s performance recommendation and load decide whether a thread goes on a P core or an E core, and threads are migrated / stolen between clusters. A thread bound to a particular CPU sits in that processor’s own run queue.

5. ps/top 看到的 vs 内核持有的

5. What ps/top show vs what the kernel holds

  • Linux 的 ps/top 只是读 /proc：/proc/<pid>/stat、status，线程在 /proc/<pid>/task/<tid>/。显示的 PID 是 tgid；ps -L 的 LWP 才是每个 task 的 ID。
  • On Linux, ps/top just read /proc: /proc/<pid>/stat, status, with threads under /proc/<pid>/task/<tid>/. The PID shown is the tgid; the LWP in ps -L is each task’s own ID.
  • 状态 R 包含「正在跑」和「在运行队列里等」（内核里都是 TASK_RUNNING）；D 是不可中断睡眠。top 的 PR 列对普通任务是 20 + nice，不是内核的 100–139 数值。
  • State R covers both “running” and “waiting in the run queue” (both are TASK_RUNNING in the kernel); D is uninterruptible sleep. For ordinary tasks the PR column of top is 20 + nice, not the kernel’s 100–139 value.
  • macOS 的 ps/top 通过 sysctl（KERN_PROC）和 proc_info（libproc）拿数据，看到的是 BSD proc 视角；Mach 线程用 ps -M 看，PRI 列是线程当前优先级。QoS、thread group、跑在 P 还是 E 核，要用 powermetrics、Instruments、spindump 这类工具才看得到。
  • On macOS, ps/top get their data through sysctl (KERN_PROC) and proc_info (libproc), so what you see is the BSD proc view; use ps -M for Mach threads, where the PRI column is the thread’s current priority. QoS, thread group and whether a thread runs on a P or an E core are visible only with tools such as powermetrics, Instruments and spindump.
  • 两边都看不到：vruntime / lag / deadline、clutch bucket 的 deadline——只有调度调试接口（Linux /sys/kernel/debug/sched/debug）或 tracing 能看。
  • Invisible on both sides: vruntime / lag / deadline and the clutch bucket deadlines — only the scheduler debug interface (Linux /sys/kernel/debug/sched/debug) or tracing shows them.

自测

Self-check

1. 在 Linux 上，pthread_create() 创建的线程在内核里是什么？

1. On Linux, what is a thread created by pthread_create() inside the kernel?

glibc/musl 用 clone(CLONE_VM | CLONE_THREAD | …) 创建它：调度单位仍是 task_struct，getpid() 返回相同的 tgid，gettid() 不同。c 描述的是 fork()。glibc/musl create it with clone(CLONE_VM | CLONE_THREAD | …): the scheduling unit is still a task_struct; getpid() returns the same tgid, while gettid() differs. c describes fork().

2. 运行队列里有 T1（vruntime 10，vd 48）、T2（vruntime 16，vd 28）、T3（vruntime 34，vd 46），加权平均 V ≈ 23。EEVDF 选谁？

2. The run queue holds T1 (vruntime 10, vd 48), T2 (vruntime 16, vd 28) and T3 (vruntime 34, vd 46), with weighted average V ≈ 23. Which one does EEVDF pick?

lag = V − vruntime：T1 = 13、T2 = 7、T3 = −11，所以 T3 不 eligible。eligible 中 vd 最小的是 T2。选 T1 是 CFS 的答案。lag = V − vruntime: T1 = 13, T2 = 7, T3 = −11, so T3 is not eligible. Among the eligible tasks, T2 has the smallest vd. Picking T1 is the CFS answer.

3. XNU 中 Mach task、Mach thread 和 BSD proc 的关系是？

3. In XNU, how are the Mach task, the Mach thread and the BSD proc related?

task 是资源容器（vm_map + ipc_space），thread 是执行和调度单位；BSD 层的 PID、凭证、fd 表在 proc 里，挂在对应的 task 上；每个 thread 另有 BSD 侧的 uthread。A task is a resource container (vm_map + ipc_space) and a thread is the unit of execution and scheduling; the BSD-layer PID, credentials and fd table live in the proc, which is attached to its task; each thread also has a BSD-side uthread.

4. 为什么 cpu_switch_to / Switch_context 只保存 x19–x28、fp、sp、lr，不保存 x0–x18？

4. Why do cpu_switch_to / Switch_context save only x19–x28, fp, sp and lr, and not x0–x18?

上下文切换对被切走的线程来说只是「调用了一个函数」，所以只需保存被调用者负责的寄存器。用户态的完整寄存器（含 x0–x18）早在 Phase 0 讲的异常入口就存进了 pt_regs / saved state。To the thread being switched out, a context switch is just “calling a function”, so only the registers the callee is responsible for need saving. The full set of user-mode registers (including x0–x18) was already saved into pt_regs / saved state at the exception entry covered in Phase 0.
