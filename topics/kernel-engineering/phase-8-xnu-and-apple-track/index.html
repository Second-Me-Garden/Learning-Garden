核心概念

Core concepts

1. 从源码构建 XNU

1. Building XNU from source

仓库 README 给出的构建语法是 make SDKROOT=<sdkroot> ARCH_CONFIGS=<arch> KERNEL_CONFIGS=<variant>，variant 可以是 release、development、debug、profile（makedefs/MakeInc.def 的 SUPPORTED_KERNEL_CONFIGS 里还有 KASAN 和 SPTM）。ARM64 还要选机型 MACHINE_CONFIGS，公开源码支持的列表就写在同一文件的 SUPPORTED_ARM64_MACHINE_CONFIGS 里（当前为 T6000 T6020 T6030 T6031 T6041 T8101 T8103 T8112 T8122 T8132 VMAPPLE）。产物是可引导的 kernel.[config] 和带符号的 kernel.[config].unstripped，make install_kernels DSTROOT=… 安装，安装阶段生成 DWARF 的 .dSYM。README 里的例子写的是 SDKROOT=macosx.internal——那是 Apple 内部 SDK；外部只能用 Xcode 自带的 macosx SDK，缺的部分靠 KDK 补：makefile 在设置了 KDKROOT 时会从 KDK 里找平台头文件和 libfirehose_kernel 库（makedefs/MakeInc.def）。

The build syntax given in the repository README is make SDKROOT=<sdkroot> ARCH_CONFIGS=<arch> KERNEL_CONFIGS=<variant>, where the variant can be release, development, debug or profile (SUPPORTED_KERNEL_CONFIGS in makedefs/MakeInc.def also lists KASAN and SPTM). ARM64 also needs a machine, MACHINE_CONFIGS; the list the public source supports is in SUPPORTED_ARM64_MACHINE_CONFIGS in the same file (currently T6000 T6020 T6030 T6031 T6041 T8101 T8103 T8112 T8122 T8132 VMAPPLE). The outputs are a bootable kernel.[config] and a kernel.[config].unstripped with symbols; make install_kernels DSTROOT=… installs them, and the install step generates the DWARF .dSYM. The README example uses SDKROOT=macosx.internal — that is Apple’s internal SDK; outside Apple you can only use the macosx SDK that ships with Xcode, and the missing pieces come from the KDK: when KDKROOT is set, the makefile looks in the KDK for platform headers and the libfirehose_kernel library (makedefs/MakeInc.def).

KDK（Kernel Debug Kit）在 developer.apple.com 的下载页搜索「Kernel Debug Kit」获取，必须与目标机器的 macOS build 号完全一致，安装到 /Library/Developer/KDKs/。里面有各 SoC 的 release / development（有时还有 kasan）内核、对应的 dSYM（带 lldbmacros）和说明文档。即使你不自己编译 XNU，KDK 也是 Phase 6 两机调试和符号化的前提。

You get the KDK (Kernel Debug Kit) by searching for “Kernel Debug Kit” on the developer.apple.com downloads page; it must match the target machine’s macOS build number exactly, and it installs into /Library/Developer/KDKs/. It contains release / development (sometimes also kasan) kernels for each SoC, the matching dSYMs (with lldbmacros) and documentation. Even if you never build XNU yourself, the KDK is a prerequisite for the two-machine debugging and symbolication of Phase 6.

两个必须提前知道的现实（在一台 macOS 27.2 的 Mac 上于 2026-10-30 实测）：① 源码发布滞后——本机 uname -v 显示运行的是 xnu-13432.41.4，而公开仓库最新的 tag 是 xnu-12377.121.6；② 机型可能不在列表里——同一台机器的 RELEASE_ARM64_T8142 不在公开的 MACHINE_CONFIGS 中。所以最稳妥的练习路径是：选一个公开 tag，在跑对应 macOS 版本的虚拟机里使用 VMAPPLE 配置。最后一步「引导自己编译的内核」：README 里的 kextcache + com.apple.Boot.plist 方法是 Intel 时代的；Apple Silicon 上要用 kmutil 生成 kernel collection，并在 recoveryOS 里降为 Reduced Security 后配置启动——具体步骤随版本变化，以 KDK 自带说明为准（大致路径）。

Two realities you need to know in advance (measured on a Mac running macOS 27.2 on 2026-10-30): ① source releases lag — on that machine uname -v shows it running xnu-13432.41.4, while the newest tag in the public repository is xnu-12377.121.6; ② your machine may not be on the list — the same machine’s RELEASE_ARM64_T8142 is not among the public MACHINE_CONFIGS. So the safest practice path is: pick a public tag and use the VMAPPLE configuration in a virtual machine running the matching macOS version. For the last step, “booting the kernel you built”: the README’s kextcache + com.apple.Boot.plist method dates from the Intel era; on Apple Silicon you use kmutil to generate a kernel collection and configure booting after lowering to Reduced Security in recoveryOS — the exact steps change between versions, so follow the documentation that ships with the KDK (approximate path).

2. Darwin 内部阅读计划

2. A Darwin internals reading plan

按「一个请求从进来到出去」的顺序读，每个文件只追一条主线，读完画一张自己的图。下面的文件都在当前公开 tag 中存在；遇到改名或移动，用 grep -rn "^函数名(" osfmk bsd iokit 重新定位，不要凭记忆补。

Read in the order “a request comes in and goes back out”, follow only one main thread through each file, and draw your own diagram when you finish. All of the files below exist in the current public tag; if something has been renamed or moved, find it again with grep -rn "^function_name(" osfmk bsd iokit rather than filling the gap from memory.

  1. osfmk/arm64/start.s → osfmk/arm/arm_init.c：第一条指令到 arm_init（对照 Phase 1）。
  2. osfmk/arm64/start.s → osfmk/arm/arm_init.c: from the first instruction to arm_init (compare with Phase 1).
  3. osfmk/kern/startup.c + doc/lifecycle/startup.md：kernel_bootstrap 与 STARTUP 分阶段初始化机制。
  4. osfmk/kern/startup.c + doc/lifecycle/startup.md: kernel_bootstrap and the phased STARTUP initialisation mechanism.
  5. bsd/kern/bsd_init.c：bsd_init 到 exec launchd。
  6. bsd/kern/bsd_init.c: from bsd_init to the exec of launchd.
  7. osfmk/arm64/sleh.c：sleh_synchronous、handle_svc（x16 非负走 unix_syscall，负数走 mach_syscall）、sleh_irq/sleh_fiq（对照 Phase 0、Phase 2）。
  8. osfmk/arm64/sleh.c: sleh_synchronous, handle_svc (a non-negative x16 goes to unix_syscall, a negative one to mach_syscall), sleh_irq/sleh_fiq (compare with Phase 0 and Phase 2).
  9. bsd/dev/arm/systemcalls.c + bsd/kern/syscalls.master：BSD 系统调用分发与编号表。
  10. bsd/dev/arm/systemcalls.c + bsd/kern/syscalls.master: BSD system call dispatch and the number table.
  11. osfmk/kern/task.c、osfmk/kern/thread.c：task / thread 的创建与生命周期。
  12. osfmk/kern/task.c, osfmk/kern/thread.c: creation and life cycle of tasks / threads.
  13. osfmk/kern/sched_prim.c、osfmk/kern/sched_clutch.c + doc/scheduler/sched_clutch_edge.md：thread_block、thread_invoke、clutch / Edge（对照 Phase 1）。
  14. osfmk/kern/sched_prim.c, osfmk/kern/sched_clutch.c + doc/scheduler/sched_clutch_edge.md: thread_block, thread_invoke, clutch / Edge (compare with Phase 1).
  15. osfmk/ipc/mach_msg.c → osfmk/ipc/ipc_kmsg.c → osfmk/ipc/ipc_port.c、ipc_right.c + doc/mach_ipc/：一条消息的拷入、权限转移、排队与拷出（对照 Phase 3）。
  16. osfmk/ipc/mach_msg.c → osfmk/ipc/ipc_kmsg.c → osfmk/ipc/ipc_port.c, ipc_right.c + doc/mach_ipc/: copy-in, rights transfer, queuing and copy-out of one message (compare with Phase 3).
  17. osfmk/vm/vm_fault.c、osfmk/vm/vm_map.c、osfmk/kern/zalloc.c、osfmk/kern/kalloc.c + doc/allocators/（对照 Phase 2、Phase 7）。
  18. osfmk/vm/vm_fault.c, osfmk/vm/vm_map.c, osfmk/kern/zalloc.c, osfmk/kern/kalloc.c + doc/allocators/ (compare with Phase 2 and Phase 7).
  19. bsd/kern/kern_exec.c：posix_spawn / execve、Mach-O 装载、代码签名相关钩子。
  20. bsd/kern/kern_exec.c: posix_spawn / execve, Mach-O loading, the code-signing hooks.
  21. bsd/vfs/vfs_lookup.c → vfs_syscalls.c → vfs_vnops.c（vn_read）→ vfs_cluster.c（cluster_read）（对照 Phase 4）。
  22. bsd/vfs/vfs_lookup.c → vfs_syscalls.c → vfs_vnops.c (vn_read) → vfs_cluster.c (cluster_read) (compare with Phase 4).
  23. iokit/Kernel/IOService.cpp → IOUserClient.cpp（is_io_connect_method → externalMethod）→ IOUserServer.cpp（DriverKit 的内核一侧）；libkern/c++/OSObject.cpp、OSKext.cpp（对照 Phase 5）。
  24. iokit/Kernel/IOService.cpp → IOUserClient.cpp (is_io_connect_method → externalMethod) → IOUserServer.cpp (the kernel side of DriverKit); libkern/c++/OSObject.cpp, OSKext.cpp (compare with Phase 5).
  25. security/mac_base.c、security/mac_vfs.c、bsd/kern/kern_csr.c：MACF 与 SIP 检查点（对照 Phase 7）。
  26. security/mac_base.c, security/mac_vfs.c, bsd/kern/kern_csr.c: the MACF and SIP check points (compare with Phase 7).
  27. osfmk/kern/debug.c + tools/lldbmacros/：panic log 怎样生成、宏怎样读内核数据结构（对照 Phase 6）。
  28. osfmk/kern/debug.c + tools/lldbmacros/: how the panic log is generated and how the macros read kernel data structures (compare with Phase 6).

节奏建议：每天 1–2 个文件；每个文件留下「入口函数、关键数据结构、加了什么锁、和 Linux 哪里对应」四行笔记。读完 14 项，你就拥有面试里讲 XNU 的全部素材。延伸阅读：《*OS Internals》Vol. II 可作阅读计划的总地图；《Mac OS X Internals》讲 XNU 内核的相关章节交代了 Mach / BSD / IOKit 分层的来历。

Suggested pace: 1–2 files a day; for each file, leave a four-line note — “entry function, key data structures, which locks are taken, where it corresponds to Linux”. Once you have read all 14 items, you have all the material you need to talk about XNU in an interview. Further reading: *OS Internals Vol. II works as the overall map for the reading plan; the XNU kernel chapters of Mac OS X Internals explain where the Mach / BSD / IOKit layering came from.

3. 作品集项目

3. Portfolio projects

作品的目的不是炫技，而是给面试官一个可以深挖的具体东西。规格：

The point of the work is not to show off, but to give the interviewer something concrete to dig into. Specification:

  • A · Linux 内核模块（必做）：一个 misc 字符设备 /dev/kstat，统计打开与读取次数（Lab A 给了可编译的骨架），再扩展成真正有内容的东西——例如一个带 ioctl 的环形缓冲区，或者用 kprobe / tracepoint 统计某个系统调用的调用者。验收标准：copy_to_user/copy_from_user 的返回值全部检查；所有错误路径正确回滚；在开了 CONFIG_KASAN 和 CONFIG_PROVE_LOCKING（lockdep）的 QEMU 内核里压力测试零告警；附一个测试脚本和 README。
  • A · Linux kernel module (required): a misc character device /dev/kstat that counts opens and reads (Lab A gives a skeleton that compiles), then extended into something with real content — for example a ring buffer with an ioctl, or using a kprobe / tracepoint to count the callers of a system call. Acceptance criteria: every return value of copy_to_user/copy_from_user is checked; every error path rolls back correctly; stress tests produce zero warnings in a QEMU kernel built with CONFIG_KASAN and CONFIG_PROVE_LOCKING (lockdep); a test script and a README are included.
  • B1 · DriverKit 驱动（二选一）：一个最小 dext：IOService 子类在 Start 里打日志，并提供一个 IOUserClient 子类和一个外部方法，由宿主 App 通过 SystemExtensions 框架激活、用 IOServiceOpen + IOConnectCallScalarMethod 调用。门槛是签名与 entitlement：DriverKit entitlement 需要向 Apple 申请，本地开发的加载方式（如 systemextensionsctl developer on）随系统版本有不同要求——先读 Apple 的「Requesting Entitlements for DriverKit Development」。
  • B1 · DriverKit driver (choose B1 or B2): a minimal dext: an IOService subclass that logs in Start and provides an IOUserClient subclass with one external method; a host app activates it through the SystemExtensions framework and calls it with IOServiceOpen + IOConnectCallScalarMethod. The hurdle is signing and entitlements: the DriverKit entitlements have to be requested from Apple, and the requirements for loading during local development (such as systemextensionsctl developer on) differ between OS versions — read Apple’s “Requesting Entitlements for DriverKit Development” first.
  • B2 · Mach IPC 工具（二选一，不需要特殊 entitlement）：一对 client/server，server 用 bootstrap_check_in 注册服务（由 launchd plist 提供名字），client 用 bootstrap_look_up 找到它；消息里传一个端口权限（让 server 回复到 client 的 send-once 端口）和一段 OOL 内存；最后对比 mach_msg、pipe、Unix socket 的往返延迟。Lab B 给了最小的单进程 mach_msg 起点。
  • B2 · Mach IPC tool (choose B1 or B2; no special entitlement needed): a client/server pair; the server registers a service with bootstrap_check_in (the name comes from a launchd plist), and the client finds it with bootstrap_look_up; a message carries a port right (so that the server replies to the client’s send-once port) and a piece of OOL memory; finally, compare the round-trip latency of mach_msg, a pipe and a Unix socket. Lab B gives a minimal single-process mach_msg starting point.

每个项目都要有一份一页的设计说明：解决什么问题、接口长什么样、并发与锁的选择、失败路径、测了什么、一个你遇到并用 Phase 6 工具定位的 bug。

Each project needs a one-page design note: what problem it solves, what the interface looks like, the choice of concurrency and locking, the failure paths, what was tested, and one bug you hit and tracked down with the Phase 6 tools.

4. 跟踪 XNU 的版本变化

4. Tracking XNU version changes

Linux 的变化有完整记录：每个提交有说明，kernelnewbies 的 LinuxChanges 与 LWN 的合并窗口总结按版本汇总。XNU 只有按发布的快照：opensource.apple.com/releases 列出每个 macOS 版本对应的 xnu 版本号，GitHub 仓库里对应同名 tag（如 xnu-12377.101.15、xnu-12377.121.6），一个 tag 大致就是一个提交。读法是做 diff：

Linux changes are fully recorded: every commit has a message, and kernelnewbies’ LinuxChanges and LWN’s merge-window summaries collect them by version. XNU has only per-release snapshots: opensource.apple.com/releases lists the xnu version for each macOS version, and the GitHub repository has a tag of the same name (such as xnu-12377.101.15, xnu-12377.121.6); one tag is roughly one commit. The way to read them is to diff:

  • git diff --stat 旧tag 新tag -- osfmk/ipc/ 先看哪些文件变了、变了多少；
  • git diff --stat OLD_TAG NEW_TAG -- osfmk/ipc/ first, to see which files changed and by how much;
  • 新增的文件、doc/ 下新增的设计说明、新出现的宏（例如本阶段在 Phase 7 里看到的 CONFIG_SPTM、KALLOC_TYPE_DEFINE）往往标志一项新机制；
  • new files, new design notes under doc/ and newly appearing macros (for example CONFIG_SPTM and KALLOC_TYPE_DEFINE, which you saw in Phase 7) often signal a new mechanism;
  • 把 diff 和同期 Apple 安全研究博客、Platform Security Guide 的修订记录对照——机制的「为什么」通常写在那里。
  • compare the diff with the Apple Security Research blog and the revision history of the Platform Security Guide from the same period — the “why” of a mechanism is usually written there.

5. Apple 面试流程

5. The Apple interview process

下面是公开面经里常见的形状（推断：Apple 按团队招聘，环节、顺序和题目因团队而异，以招聘方的实际安排为准）。每一环都写上「考什么」和「带哪件作品」：

Below is the shape commonly described in public interview reports (inference: Apple hires by team, and the stages, their order and the questions vary by team; the recruiter’s actual schedule takes precedence). For each stage, note “what it tests” and “which piece of work to bring”:

  • 招聘方 / 经理初筛：为什么是这个团队、你做过什么。带：两分钟版的作品介绍。
  • Recruiter / manager screen: why this team, and what you have done. Bring: the two-minute version of your project pitch.
  • 技术电话面：一道 C 编码题 + 操作系统问题。带：Phase 0–2 的基本功（异常、页表、上下文切换能讲清）。
  • Technical phone screen: one C coding question + operating-systems questions. Bring: the fundamentals from Phases 0–2 (being able to explain exceptions, page tables and context switches clearly).
  • 编码（C / C++）：链表、位运算、环形缓冲区、简单分配器、带锁的数据结构，重在边界条件、错误处理和并发正确性。带：作品 A 的代码，准备好被问「这里如果并发会怎样」。
  • Coding (C / C++): linked lists, bit manipulation, ring buffers, simple allocators, data structures with locks — the emphasis is on boundary conditions, error handling and concurrency correctness. Bring: the code of project A, and be ready to be asked “what happens here under concurrency?”
  • 操作系统基础：虚拟内存、缺页、调度、系统调用、中断、同步原语、IPC。带：阅读计划的笔记与 Phase 1–4 的动画——能在白板上画出来。
  • OS fundamentals: virtual memory, page faults, scheduling, system calls, interrupts, synchronisation primitives, IPC. Bring: your reading-plan notes and the diagrams from Phases 1–4 — be able to draw them on a whiteboard.
  • 调试：给一份 panic log / crash / 一段有 bug 的代码，说出你的排查顺序。带：Phase 6 的符号化流程和你在作品里定位过的真实 bug。
  • Debugging: given a panic log / a crash / a piece of buggy code, describe the order in which you would investigate. Bring: the Phase 6 symbolication workflow and the real bug you tracked down in your project.
  • 系统设计：设计一个内核子系统或驱动接口（例如一个高频日志缓冲区、一个省电的定时器合并机制），讲清取舍。带：作品的设计说明，Phase 7 的安全考量。
  • System design: design a kernel subsystem or driver interface (for example a high-frequency logging buffer, or a power-saving timer-coalescing mechanism) and explain the trade-offs. Bring: your project design notes and the security considerations from Phase 7.

延伸阅读：《Cracking the Coding Interview》面试流程与编码题相关章节（通用软件岗视角，内核题要自己补）。

Further reading: the chapters of Cracking the Coding Interview on the interview process and coding questions (a general software-engineering perspective; you have to supply the kernel questions yourself).

6. 讲述你的工作

6. Talking about your work

每件作品准备一个「问题 → 做法 → 取舍 → 结果」的故事，有两分钟和十分钟两个版本。问题要具体（「我想知道一次 mach_msg 往返比 pipe 慢多少、慢在哪」比「我学习了 Mach IPC」好得多）；做法讲你用了哪些内核接口和工具；取舍是面试官最想听的部分（为什么用 mutex 而不是 spinlock、为什么选 B2 而不是 B1）；结果给数字和你学到的、能迁移到 Apple 工作里的东西。

For each piece of work, prepare a “problem → approach → trade-offs → result” story in two versions, two minutes and ten minutes. The problem should be specific (“I wanted to know how much slower a mach_msg round trip is than a pipe, and where the time goes” is much better than “I studied Mach IPC”); the approach covers which kernel interfaces and tools you used; the trade-offs are the part the interviewer most wants to hear (why a mutex rather than a spinlock, why B2 rather than B1); the result gives numbers and what you learned that carries over to work at Apple.

两条纪律：对 XNU 内部的每个说法，都能指出源码文件（「这在 osfmk/ipc/ipc_kmsg.c 里」），说不准的就直说「我读到的版本是这样，新版本可能变了」；不要声称理解你没读过的东西——面试官多半就是写那段代码的人。延伸阅读：《Cracking the Coding Interview》行为面试相关章节。

Two disciplines: for every claim about XNU internals, be able to point to the source file (“this is in osfmk/ipc/ipc_kmsg.c”), and when you are not sure, say so plainly: “this is how it was in the version I read; newer versions may have changed”; do not claim to understand things you have not read — the interviewer is quite likely the person who wrote that code. Further reading: the behavioural-interview chapters of Cracking the Coding Interview.

Lab A · QEMU Linux：作品项目 A 的骨架

Lab A · QEMU Linux: the skeleton of project A

  1. 把下面存为 kstat/kstat.c（在 Linux 6.6 头文件上编译通过；你的 Phase 0 树更新，接口可能有变，以编译器报错为准）：Save the following as kstat/kstat.c (it compiles against Linux 6.6 headers; your Phase 0 tree is newer and the interfaces may have changed, so go by the compiler errors):
    // SPDX-License-Identifier: GPL-2.0
#include <linux/module.h>
#include <linux/miscdevice.h>
#include <linux/fs.h>
#include <linux/mutex.h>
#include <linux/uaccess.h>

static DEFINE_MUTEX(kstat_lock);
static unsigned long opens, reads;

static int kstat_open(struct inode *inode, struct file *f)
{
	mutex_lock(&kstat_lock);
	opens++;
	mutex_unlock(&kstat_lock);
	return 0;
}

static ssize_t kstat_read(struct file *f, char __user *buf, size_t len, loff_t *pos)
{
	char tmp[64];
	int n;

	mutex_lock(&kstat_lock);
	if (*pos == 0)
		reads++;
	n = scnprintf(tmp, sizeof(tmp), "opens=%lu reads=%lu\n", opens, reads);
	mutex_unlock(&kstat_lock);
	return simple_read_from_buffer(buf, len, pos, tmp, n);
}

static const struct file_operations kstat_fops = {
	.owner = THIS_MODULE,
	.open  = kstat_open,
	.read  = kstat_read,
};

static struct miscdevice kstat_dev = {
	.minor = MISC_DYNAMIC_MINOR,
	.name  = "kstat",
	.fops  = &kstat_fops,
};
module_misc_device(kstat_dev);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Phase 8 portfolio skeleton: /dev/kstat");
    同目录放一个只有一行的 Makefile：obj-m += kstat.o。Put a one-line Makefile in the same directory: obj-m += kstat.o.

    #include <stdio.h>
#include <mach/mach.h>

typedef struct { mach_msg_header_t h; int value; } ping_t;
typedef struct { mach_msg_header_t h; int value; mach_msg_trailer_t t; } ping_rcv_t;

int main(void) {
  mach_port_t port;
  kern_return_t kr = mach_port_allocate(mach_task_self(), MACH_PORT_RIGHT_RECEIVE, &port);
  if (kr != KERN_SUCCESS) { fprintf(stderr, "allocate: %s\n", mach_error_string(kr)); return 1; }
  kr = mach_port_insert_right(mach_task_self(), port, port, MACH_MSG_TYPE_MAKE_SEND);
  if (kr != KERN_SUCCESS) { fprintf(stderr, "insert_right: %s\n", mach_error_string(kr)); return 1; }

  ping_t msg = {0};
  msg.h.msgh_bits = MACH_MSGH_BITS(MACH_MSG_TYPE_COPY_SEND, 0);
  msg.h.msgh_size = sizeof msg;
  msg.h.msgh_remote_port = port;
  msg.h.msgh_id = 4242;
  msg.value = 7;
  kr = mach_msg(&msg.h, MACH_SEND_MSG, sizeof msg, 0, MACH_PORT_NULL, MACH_MSG_TIMEOUT_NONE, MACH_PORT_NULL);
  if (kr != MACH_MSG_SUCCESS) { fprintf(stderr, "send: %s\n", mach_error_string(kr)); return 1; }

  ping_rcv_t rcv = {0};
  kr = mach_msg(&rcv.h, MACH_RCV_MSG, 0, sizeof rcv, port, MACH_MSG_TIMEOUT_NONE, MACH_PORT_NULL);
  if (kr != MACH_MSG_SUCCESS) { fprintf(stderr, "receive: %s\n", mach_error_string(kr)); return 1; }
  printf("port=0x%x msgh_id=%d value=%d size=%u\n", port, rcv.h.msgh_id, rcv.value, rcv.h.msgh_size);
  return 0;
}

自测

Self-check

1. XNU 由哪三大部分组成？

1. What are the three main parts of XNU?

XNU = Mach（osfmk/：任务、线程、IPC、VM、调度）+ BSD（bsd/：POSIX、VFS、网络）+ IOKit（iokit/：C++ 驱动框架），另有 libkern（C++ 运行时、kext 支持）和 pexpert（平台相关）。DriverKit 是用户态的驱动框架，不在内核中。XNU = Mach (osfmk/: tasks, threads, IPC, VM, scheduling) + BSD (bsd/: POSIX, VFS, networking) + IOKit (iokit/: the C++ driver framework), plus libkern (the C++ runtime, kext support) and pexpert (platform-specific code). DriverKit is a user-space driver framework and is not in the kernel.

2. 在 xnu 源码树中，Mach IPC 的核心实现位于哪个目录？

2. In the xnu source tree, which directory holds the core implementation of Mach IPC?

Mach 部分都在 osfmk/ 下：IPC 在 osfmk/ipc/，消息收发入口在 osfmk/ipc/mach_msg.c，消息本体的处理在 ipc_kmsg.c。The whole Mach part lives under osfmk/: IPC is in osfmk/ipc/, the entry point for sending and receiving messages is osfmk/ipc/mach_msg.c, and the message body itself is handled in ipc_kmsg.c.

3. arm64 上的 macOS 用户程序调用 read() 时，内核怎么知道该走 BSD 系统调用还是 Mach trap？

3. When a macOS user program on arm64 calls read(), how does the kernel know whether to take the BSD system call path or a Mach trap?

libsyscall 的桩把调用号放进 x16 再执行 svc #0x80；osfmk/arm64/sleh.c 的 handle_svc 按 x16 的符号分发（另有一个特殊的平台调用号）。read 的编号是 3，见 bsd/kern/syscalls.master。The libsyscall stub puts the call number in x16 and then executes svc #0x80; handle_svc in osfmk/arm64/sleh.c dispatches on the sign of x16 (there is also one special platform call number). read is number 3; see bsd/kern/syscalls.master.

4. 你的 Mac 运行的 xnu 版本比 GitHub 上最新的公开 tag 还新，芯片型号也不在 SUPPORTED_ARM64_MACHINE_CONFIGS 里。最稳妥的练习方式是？

4. Your Mac runs an xnu version newer than the latest public tag on GitHub, and its chip is not in SUPPORTED_ARM64_MACHINE_CONFIGS either. What is the safest way to practise?

公开源码发布滞后且只支持列出的机型；VMAPPLE 配置加上与 tag 对应的 macOS 虚拟机，可以在不降低主力机安全级别的前提下练习构建、引导和 lldb 调试。读源码当然要做，但构建与调试是面试中能讲出细节的经历。Public source releases lag and support only the listed machines; the VMAPPLE configuration plus a macOS virtual machine that matches the tag lets you practise building, booting and lldb debugging without lowering the security level of your main machine. Reading the source is of course necessary, but building and debugging are the experiences you can describe in detail in an interview.
