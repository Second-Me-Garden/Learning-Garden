实验环境 Lab environment: VMs, containers, snapshots

内核实验的常态是「把机器弄崩」：空指针、死锁、改坏页表、加载自己写的模块。这些都应该发生在一台随时可以扔掉、可以一键回滚的机器里，而不是你每天用的 Mac。本页搭三层环境：宿主 macOS 只负责编辑、编译和当调试器；QEMU 里的 Linux arm64 虚拟机做 Linux 内核实验；容器做构建；一台 macOS 客体虚拟机做 XNU、kext、关 SIP 之类的实验。

目标

读完并做完实验后，你应该能：
  • 说清每类实验应该在哪一层做，以及为什么宿主机永远不关 SIP、不装自写 kext。
  • 用一条脚本 run-vm.sh 启动带磁盘、共享目录、gdbstub 的 QEMU Linux arm64 虚拟机，并用 qemu-img snapshot 回滚一次。
  • 用同一个编译器在容器里编内核和模块，把产物放回共享目录给虚拟机用。
  • 在 UTM（Apple Virtualization 后端）里装一台 macOS 客体机，在它的 Recovery 里关 SIP，并确认宿主机的 SIP 仍然开着。

为什么要隔离

  • 内核崩溃是整机崩溃。用户态程序崩了只死一个进程；内核里一个空指针就是 panic，正在写的文件、没保存的编辑器缓冲区一起丢。在虚拟机里，崩溃只是一个窗口里的一段 log，重启只要几秒。
  • root 和内核权限没有「撤销」。实验里经常要 sudo、写 /dev/mem、改内核参数、跑 Phase 7 的漏洞复现程序。这些在一台带快照的客体机里做，做坏了回滚即可。
  • 关 SIP 是降低整台机器的安全级别。SIP（System Integrity Protection）保护系统文件、限制调试系统进程、限制加载内核扩展；关掉它意味着恶意软件也获得同样的自由。macOS 上需要关 SIP 的实验（dtruss、内核级 dtrace、加载自写 kext、改 boot-args、引导 KDK 的 development 内核）只在 macOS 客体机里做。
  • 自写模块 / kext 就是在内核里运行你的代码。写错一行就可能破坏文件系统缓存或内存。Linux 模块只在 QEMU 客体机里 insmod；macOS kext 只在 macOS 客体机里加载。
一条硬规则：宿主 Mac 永远不动 SIP、不改 boot-args、不降低启动安全级别、不装自写 kext 或 dext。宿主机上可以做的是：读源码、编译、跑 QEMU、当 lldb 调试器的「host」端、安装 KDK（它只是放在 /Library/Developer/KDKs/ 下的文件，不改变正在运行的内核）。

核心概念

1. 三层环境

宿主是你的 Apple Silicon Mac（macOS，arm64）。上面跑三类客体：

  • QEMU Linux arm64 VM：所有 Linux 内核实验——启动自编内核、insmod 自写模块、gdbstub 单步、故意制造 panic。Phase 0 的 qemu-system-aarch64 -M virt 命令就是它的雏形。
  • arm64 Linux 容器（Docker Desktop、OrbStack 或 Lima 任选其一）：只做构建——编内核、编模块、做 busybox initramfs、生成磁盘镜像。容器不是内核实验场：它和其他容器共用 Docker Desktop / OrbStack / Lima 那台 Linux 虚拟机的内核，在 --privileged 容器里 insmod 会把模块装进那台共享 VM 的内核里——不要这样做。
  • macOS 客体 VM（UTM 的 Apple Virtualization 后端，或 Tart）：所有 XNU 侧需要权限的实验——关 SIP、改 boot-args、加载 kext、DriverKit 开发者模式、作为两机内核调试的「target」。

三者和宿主之间的连接只有四种：共享目录（传代码和产物）、gdbstub（宿主 lldb 调 QEMU 里的 Linux 内核）、KDP（宿主 lldb 调 macOS 客体的 XNU）、快照 / 克隆（回滚）。下面的动画逐层走一遍。

2. QEMU Linux VM 详解

以 Phase 0 Lab A 的命令为基线，逐项加上实验需要的东西：

选项作用说明
-M virt -cpu cortex-a72QEMU 的通用 arm64 虚拟板 + 纯软件模拟（TCG）的 CPU慢但行为稳定，gdbstub 断点最可靠。想要接近原生速度可换成 -accel hvf -cpu host（用 macOS 的 Hypervisor.framework）；hvf 下的调试支持不如 TCG 完整，调试时建议切回 TCG（推断，随 QEMU 版本变化）。
-smp 2虚拟 CPU 个数并发、锁、per-CPU 变量（Phase 3）至少要 2 个；单步调试时 1 个更好跟。
-m 2G客体内存busybox 环境 1G 足够；开 KASAN 或跑较大的测试再加。
-drive … -device virtio-blk-pci一块 virtio 磁盘镜像用 qemu-img 生成 qcow2 格式，客体里显示为 /dev/vda。qcow2 支持内部快照和写时复制。
-virtfs local,path=…,mount_tag=share,security_model=none9p 共享目录宿主目录直接出现在客体里，客体 mount -t 9p -o trans=virtio,version=9p2000.L share /mnt/share # throwaway 模式下没有共享设备，失败即跳过。QEMU 从 7.0 起支持 macOS 宿主上的 9p。virtiofs 更快，但它依赖宿主上运行的 virtiofsd 守护进程，后者面向 Linux 宿主，macOS 宿主上用 9p。
-s -Sgdbstub-s = -gdb tcp::1234；-S 让 CPU 停在第一条指令前，等调试器 continue。内核命令行加 nokaslr，符号地址才对得上。
-snapshot一次性运行所有磁盘写入进临时文件，退出即丢弃——跑可疑代码时用。
qemu-img snapshot磁盘快照（VM 关机时操作）-c 名字 创建、-l 列出、-a 名字 回滚、-d 名字 删除。

内核要带上这些驱动（arm64 defconfig 一般已经包含，编完先检查一次，见 Lab A）：CONFIG_VIRTIO_PCI、CONFIG_VIRTIO_BLK、CONFIG_EXT4_FS、CONFIG_NET_9P、CONFIG_NET_9P_VIRTIO、CONFIG_9P_FS、CONFIG_DEVTMPFS。把全部选项收进一个脚本，以后每个 Phase 都只敲 ./run-vm.sh：

#!/bin/sh
# run-vm.sh: start the kernel-lab VM.  Usage: ./run-vm.sh [debug|throwaway|fast]
set -eu
cd "$(dirname "$0")"
KERNEL=${KERNEL:-./Image}
INITRD=${INITRD:-./initramfs.cpio.gz}
DISK=${DISK:-./disk.qcow2}
CPU="-cpu cortex-a72"
EXTRA=""
SHARE="-virtfs local,path=$PWD/share,mount_tag=share,security_model=none"
case "${1:-}" in
  debug)     EXTRA="-s -S" ;;               # gdbstub on tcp::1234, wait for debugger
  throwaway) EXTRA="-snapshot"; SHARE="" ;; # discard all disk writes on exit AND attach no host share
  fast)      CPU="-accel hvf -cpu host" ;;  # Hypervisor.framework, near-native speed
esac
mkdir -p share
# shellcheck disable=SC2086
exec qemu-system-aarch64 -M virt $CPU -smp 2 -m 2G -nographic \
  -kernel "$KERNEL" -initrd "$INITRD" \
  -append "console=ttyAMA0 rdinit=/init nokaslr" \
  -drive file="$DISK",if=none,format=qcow2,id=hd0 \
  -device virtio-blk-pci,drive=hd0 \
  $SHARE $EXTRA

调试时另开一个终端：lldb vmlinux，然后 gdb-remote 1234（或 GNU gdb 的 target remote :1234）。退出 QEMU：Ctrl-a x。

3. 构建容器

原则：内核和模块用同一个编译器、同一份配置编。模块的 vermagic 和导出符号版本（CONFIG_MODVERSIONS 打开时）要和运行中的内核一致，编译器不同也可能让内核拒绝加载或行为异常。Phase 0 在 macOS 上用 Homebrew LLVM 编内核也能跑，但到了要编模块（Phase 5）、要装工具链里 macOS 没有的东西时，在 arm64 Linux 容器里一次性编齐更省事。

  • 源码放哪里：macOS 默认文件系统大小写不敏感，绑定挂载（-v）进容器后仍然不敏感，内核树会出问题。两种做法：源码放在 Phase 0 建的大小写敏感 APFS 卷里再挂进去；或者放在容器自己的命名卷（docker volume create linux-src）里，构建也更快。
  • 产物放回共享目录：只把 Image、vmlinux（调试符号）、*.ko、initramfs.cpio.gz 拷到宿主的实验目录，run-vm.sh 和 9p 共享目录都从那里取。
  • 容器只编不跑：容器里不 insmod，也不需要 --privileged。
docker volume create linux-src
docker run --platform linux/arm64 --rm -it \
  -v linux-src:/src -v "$HOME/kernel-lab:/lab" alpine:3.20 sh
# inside the container (package list is approximate; add what make asks for):
apk add build-base clang lld llvm make bc bison flex perl \
        linux-headers elfutils-dev openssl-dev ncurses-dev git
cd /src && git clone --depth 1 https://github.com/torvalds/linux.git && cd linux
make LLVM=1 defconfig && make LLVM=1 -j"$(nproc)" Image modules
cp arch/arm64/boot/Image vmlinux /lab/
# out-of-tree module, same compiler and tree:
make -C /src/linux M=/lab/share/hello LLVM=1 modules

容器本身就是 arm64，所以不必写 ARCH=arm64。OrbStack 和 Lima 都提供 docker 兼容的命令行（OrbStack 自带，Lima 通过其 Docker 模板），上面的命令在三者上应当相同；Lima 也可以直接开一台完整的 Linux VM 来编译。

4. macOS 客体 VM

Apple Silicon 上能跑 arm64 macOS 客体的只有 Apple 的 Virtualization framework（UTM 的 Apple Virtualization 后端、Tart 都是它的前端）。QEMU 后端（UTM 里称为 QEMU）能跑 Linux、Windows 等客体，磁盘是 qcow2、支持快照，但它不能运行 arm64 macOS 客体（推断，以 UTM 文档为准）。

  • 安装：UTM → 新建 → Virtualize → macOS，选一个 IPSW（恢复镜像）文件或让它下载最新版。也可以用 Tart：tart create --from-ipsw=latest sip-lab，或 tart clone 一个社区预装镜像。
  • 没有快照，用克隆：Apple Virtualization 后端没有类似 qcow2 的磁盘快照。替代办法是在做危险实验前克隆整个 VM bundle（UTM 的 Clone 菜单；Tart 的 tart clone 源 新名字）。在 APFS 上克隆是写时复制，初始几乎不占额外空间。坏了就删掉坏的、从干净的再克隆一份。
  • 在客体里关 SIP：关闭客体机，从 Recovery 启动它（Tart：tart run --recovery sip-lab；UTM 的入口位置随版本变化，查 UTM 文档），打开 Recovery 里的 Terminal：csrutil disable，重启。在客体里 csrutil status 应显示 disabled。真机 Apple Silicon 上加载第三方 kext 和改 boot-args 还要把启动安全级别降到 Reduced Security（Startup Security Utility 或 bputil）；在虚拟机里是否需要同样一步、具体步骤，以你的 macOS 版本和 KDK 说明为准（不确定）。
  • boot-args：在客体里 sudo nvram boot-args="…"，重启生效；nvram boot-args 查看当前值。
  • KDK 与两机调试（大致路径）：从 developer.apple.com 下载与客体 macOS 版本完全对应的 Kernel Debug Kit，宿主和客体都装（宿主用它的符号和 lldbmacros，客体用它的 development 内核）。客体通过 boot-arg debug= 打开调试（位定义见 Phase 6），在客体上按 KDK 自带 ReadMe 的步骤让它引导 development 内核；宿主上 lldb 载入 KDK 里对应内核的 dSYM，kdp-remote 客体IP 连接。这一整条路径在虚拟机里能走通到什么程度随 macOS 版本变化，本页没有逐步验证，以 KDK ReadMe 为准。
Virtualization framework 对同时运行的 macOS 客体数量有限制（大致 2 台，与 macOS 许可协议的条款对应，以 Apple 文档为准）。一台「干净模板」关机放着，一台工作副本在跑，正好够用。

动手实验

Lab A · 搭好 QEMU Linux VM：磁盘 + 共享目录 + 一键脚本，快照回滚一次

  1. 实验目录，把上面的 run-vm.sh 存进去，并拿到内核（Phase 0 编好的，或第 3 节容器里编的）：
    mkdir -p ~/kernel-lab/share && cd ~/kernel-lab
chmod +x run-vm.sh
cp /path/to/linux/arch/arm64/boot/Image /path/to/linux/vmlinux .
  2. 确认内核带了需要的驱动（在内核源码树里跑）：
    grep -E 'CONFIG_(VIRTIO_PCI|VIRTIO_BLK|EXT4_FS|NET_9P|NET_9P_VIRTIO|9P_FS|DEVTMPFS)=y' .config   # 七项都必须是 =y（内建）；=m 的模块不在 initramfs 里，挂载会静默失败
    缺哪个就 scripts/config -e 选项名，再 make LLVM=1 ARCH=arm64 olddefconfig 并重编。
  3. 写客体的 /init，它会挂上磁盘和共享目录：
    #!/bin/sh
/bin/busybox --install -s
mount -t proc none /proc
mount -t sysfs none /sys
mount -t devtmpfs none /dev
mkdir -p /mnt/disk /mnt/share
mount -t ext4 /dev/vda /mnt/disk || echo "no disk"
mount -t 9p -o trans=virtio,version=9p2000.L share /mnt/share || echo "no 9p"
exec /bin/sh
  4. 在构建容器里做 initramfs 和一块 ext4 磁盘，再在宿主上转成 qcow2：
    docker run --platform linux/arm64 --rm -v "$PWD:/lab" alpine:3.20 sh -c '
  apk add -q busybox-static cpio e2fsprogs &&
  mkdir -p /r/bin /r/sbin /r/usr/bin /r/usr/sbin /r/proc /r/sys /r/dev /r/mnt &&
  cp /bin/busybox.static /r/bin/busybox &&
  cp /lab/init /r/init && chmod +x /r/init &&
  (cd /r && find . | cpio -o -H newc | gzip > /lab/initramfs.cpio.gz) &&
  truncate -s 2G /lab/disk.img && mkfs.ext4 -q -F /lab/disk.img'
qemu-img convert -f raw -O qcow2 disk.img disk.qcow2 && rm disk.img
qemu-img info disk.qcow2
  5. 先打一个干净快照，再启动：
    qemu-img snapshot -c clean disk.qcow2
qemu-img snapshot -l disk.qcow2
echo "hello from host" > share/hello.txt
./run-vm.sh
    客体 shell 里：
    cat /mnt/share/hello.txt
echo "dirty" > /mnt/disk/marker && sync
ls /mnt/disk
poweroff -f
  6. 回滚并验证 marker 消失：
    qemu-img snapshot -a clean disk.qcow2
./run-vm.sh
# in the guest:
ls /mnt/disk        # marker is gone
  7. 试一次调试模式：./run-vm.sh debug（QEMU 停住不动是正常的），另一个终端：
    lldb vmlinux
(lldb) gdb-remote 1234
(lldb) breakpoint set --name start_kernel
(lldb) continue
    断点命中后 bt 看调用栈。断不下来时参考 Phase 6：关 CONFIG_DEBUG_INFO_REDUCED、MMU 打开前后用硬件断点。

Lab B · 建 macOS 客体 VM，在客体里关 SIP，确认宿主没变

  1. 先在宿主上记录基线：
    csrutil status
    应为 System Integrity Protection status: enabled.
  2. 安装 UTM，新建 → Virtualize → macOS，选择 IPSW 或让 UTM 下载，给 4 核、8 GB 内存、64 GB 以上磁盘，完成 macOS 安装向导。（或 Tart：brew install cirruslabs/cli/tart，tart create --from-ipsw=latest sip-lab。）
  3. 关机，克隆一份作为干净模板（UTM 的 Clone；Tart：tart clone sip-lab sip-lab-clean）。以后实验坏了就删掉工作副本，从模板再克隆。
  4. 从 Recovery 启动工作副本（Tart：tart run --recovery sip-lab；UTM 的入口查 UTM 文档），在 实用工具 → 终端 里：
    csrutil disable
    按提示确认，重启进入正常系统。
  5. 在客体里：
    csrutil status
    应显示 disabled。
  6. 回到宿主再跑一次：
    csrutil status
    必须仍是 enabled.——这就是本页要证明的事：客体里的安全设置是客体自己的，宿主一点不变。
交付物：Lab A 回滚前后 ls /mnt/disk 的输出 + qemu-img snapshot -l 的输出；Lab B 客体与宿主两次 csrutil status 的截图。写进当天日志。

自测

1. 你要做一个需要关 SIP 的 dtruss 实验，应该在哪里关 SIP？

SIP 是每台（虚拟）机器自己的设置。只在 macOS 客体机里关，宿主永远保持开启；容器是 Linux，没有 SIP。

2. 为什么不在 --privileged 的 Docker 容器里 insmod 自写模块？

容器共享宿主（这里是后台 Linux VM）的内核。内核实验放在自己专用、可回滚的 QEMU VM 里。它不会进 XNU——macOS 不加载 Linux 模块。

3. UTM 的 Apple Virtualization 后端没有快照，做危险的 kext 实验前该怎么准备回滚？

Apple Virtualization 的磁盘不是 qcow2，qemu-img snapshot 用不上；APFS 上克隆是写时复制，快又省空间。

4. 要跑一个来路不明的内核漏洞复现程序（Phase 7），哪种方式最稳妥？

-snapshot 让所有磁盘写入在退出时丢弃，但它不管 9p；共享目录必须在 QEMU 命令行上就不附加（throwaway 模式下 SHARE 为空），客体才真的碰不到宿主的文件。
