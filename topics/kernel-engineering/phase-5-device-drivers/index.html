Device Drivers 设备驱动：Linux driver model / devicetree ↔ IOKit / DriverKit，中断与 DMA

驱动是内核与硬件之间的那一层，也是内核里代码量最大、bug 最多的部分。Apple 自己设计芯片和外设，驱动工作（IOKit、DriverKit、DART）是 Apple 内核团队的日常；这一阶段建立 Linux 驱动模型和 IOKit 的对照理解。

目标

读完并做完实验后，你应该能：
  • 解释 Linux bus/device/driver 三者如何通过 devicetree 的 compatible 匹配并调用 probe。
  • 说清中断上半部与下半部的分工，以及何时使用 request_threaded_irq。
  • 描述一次 DMA 映射的流程，以及 IOMMU（Apple Silicon 上是 DART）在其中的作用。
  • 说出 IOKit 的 matching → probe → start 生命周期，以及 DriverKit dext 与 kext 的区别。

  • Phase 2（物理地址与虚拟地址、页表——DMA 地址是第三种地址）。

核心概念

1. Linux 驱动模型

Linux 用三个对象描述「谁驱动谁」：struct bus_type（一条总线：platform、PCI、USB、I2C……，定义 match、probe、uevent）、struct device（一个设备实例，有 parent、bus、driver、of_node）、struct device_driver（一个驱动，有 name、of_match_table、probe/remove）。具体总线把它们嵌进自己的结构，如 struct platform_device、struct pci_dev。三者都基于 kobject，因此自动出现在 sysfs：/sys/bus/*/devices、/sys/bus/*/drivers、/sys/devices。

匹配是双向的：新设备注册（device_add → bus_probe_device）时遍历该总线上已有的驱动；新驱动注册（driver_register → driver_attach）时遍历已有的设备。每一对都调总线的 match，成功后进入 drivers/base/dd.c 的 really_probe → 驱动的 probe。probe 返回 0 即绑定；返回 -EPROBE_DEFER 表示依赖（时钟、GPIO、电源）还没就绪，稍后重试；返回 -ENODEV 表示「不是我的」。

devicetree：ARM SoC 上的大多数外设不能被枚举（不像 PCI 有配置空间），只能由固件「声明」。bootloader（或 QEMU）把编译好的 DTB 的物理地址放在 x0 交给内核（arm64 启动协议），内核展开成 struct device_node 树，of_platform_populate 为带 compatible 的节点创建 platform_device。platform 总线的 platform_match 先比 of_match_table 里的 compatible 字符串（列表里越靠前越具体），再退回按名字匹配。驱动用 MODULE_DEVICE_TABLE(of, ...) 导出匹配表，生成 modalias，udev/mdev 据此自动 modprobe。arm64 服务器通常用 ACPI 而不是 devicetree，但驱动模型相同。延伸阅读：《Linux Device Drivers》第 14 章「Linux 设备模型」（2.6 时代，早于 arm64 devicetree）。

2. 字符设备与 platform driver

用户态通过 /dev 下的设备节点访问驱动。字符设备由设备号 dev_t（major/minor）标识：alloc_chrdev_region 申请号、cdev_init/cdev_add 挂上 struct file_operations，再创建 class 和 device 让 devtmpfs/udev 生成节点。最省事的是 misc device：misc_register（或 module_misc_device 宏）一步完成，主设备号固定为 10、次设备号动态分配。file_operations 就是 Phase 4 VFS 分派的终点：.open、.read、.write、.unlocked_ioctl、.mmap、.poll、.llseek；在 .read/.write 里与用户缓冲区交换数据必须用 copy_to_user/copy_from_user（或 simple_read_from_buffer 这类辅助函数）。

platform driver 是 SoC 外设最常见的写法：struct platform_driver 填 .probe 和 .driver = { .name, .of_match_table }，用 module_platform_driver() 注册。probe 里的典型动作：devm_platform_ioremap_resource(pdev, 0) 把设备树里 reg 描述的寄存器区映射成内核虚拟地址（页表属性是 Device-nGnRE，Phase 2 的 MAIR），用 readl/writel 访问；platform_get_irq 拿中断号、devm_request_irq 注册处理函数。devm_* 是托管资源：设备解绑时按逆序自动释放，消灭了大量错误路径上的泄漏。

XNU 的 BSD 层也有字符设备（cdevsw_add + devfs_make_node，/dev/null、终端都是这样来的），但 IOKit 驱动通常不走 /dev：用户态通过 IOServiceOpen 打开一个 IOUserClient，再用 IOConnectCallMethod 调驱动的 externalMethod。这个连接本身是一个 Mach port（Phase 3 的 kobject），每次调用就是一条 Mach 消息——IOUserClient 的参数校验也因此是 macOS/iOS 内核漏洞最集中的地方之一。

3. 中断：上半部、下半部、threaded IRQ

ARM64 上设备中断先到中断控制器：标准 Arm 平台（QEMU virt）是 GIC，Apple Silicon 是 Apple 自己的 AIC（Linux 驱动 drivers/irqchip/irq-apple-aic.c；Apple 芯片上定时器，以及支持 fast IPI 的芯片上的核间中断，走 FIQ）。控制器向 CPU 发 IRQ，CPU 跳到 VBAR_EL1 的 IRQ 向量。Linux 里 handle_arch_irq 指向控制器驱动（如 gic_handle_irq），它读出硬件中断号，经 irq domain 翻译成 Linux irq 号，调 generic_handle_domain_irq → 流控函数（如 handle_fasteoi_irq）→ handle_irq_event → 驱动注册的 handler。/proc/interrupts 每行就是一个 irq 号在各 CPU 上的计数。

上半部（hardirq handler，request_irq(irq, handler, flags, name, dev)）运行在中断上下文：本 CPU 中断已关、不能睡眠、要尽快返回——只做确认中断、读必要状态、把数据挪出硬件 FIFO 这类事，返回 IRQ_HANDLED（或共享中断线上「不是我的」时返回 IRQ_NONE）。其余工作推给下半部：softirq（编译期固定的少数几种，网络收发、块完成、定时器、RCU 用；在中断返回时或 ksoftirqd 里运行，仍不能睡眠）；tasklet（建在 softirq 之上，正被逐步淘汰，6.9 起引入 BH workqueue 作为替代）；workqueue（schedule_work/queue_work，在 kworker 内核线程里运行，可以睡眠）。

threaded IRQ：request_threaded_irq(irq, handler, thread_fn, IRQF_ONESHOT, name, dev)。handler 是快速的上半部，返回 IRQ_WAKE_THREAD 后内核唤醒专属线程 irq/<N>-<name> 执行 thread_fn，它可以睡眠（拿 mutex、做 I2C/SPI 传输——这些总线上的设备读一个寄存器就要睡眠等待）。IRQF_ONESHOT 让该中断线在线程跑完前保持屏蔽，避免电平触发的中断反复打进来。handler 传 NULL 则使用默认上半部。何时用：处理过程需要睡眠、或希望中断处理可被调度和设定优先级时；PREEMPT_RT 内核会把几乎所有中断强制线程化。

XNU：fleh_irq → sleh_irq（osfmk/arm64/sleh.c）→ 平台中断控制器驱动（Apple Silicon 上是闭源 kext，基类 IOInterruptController）→ 分发到驱动注册的处理器。IOKit 驱动几乎从不在上半部做事：它创建 IOInterruptEventSource 并加入自己的 IOWorkLoop，中断发生时事件源在中断上下文里只记一次数并唤醒 workloop 线程，真正的 action 在线程里运行——IOKit 默认就是「threaded IRQ」。需要在中断上下文里先判断「是不是我的」时用 IOFilterInterruptEventSource，其 filter 函数在主中断上下文运行，返回 true 才调度 action。延伸阅读：《Linux Kernel Development》第 7–8 章「中断和中断处理」「下半部和推后执行的工作」；《Linux Device Drivers》第 10 章「中断处理」。

4. DMA 与 IOMMU

DMA 让设备直接读写内存，CPU 只负责告诉设备「从哪读、写到哪」。问题是设备看到的地址既不是内核虚拟地址，也未必是物理地址，而是 DMA 地址（dma_addr_t，又叫 bus address / IOVA）。Linux 的 DMA API 屏蔽了差别：先用 dma_set_mask_and_coherent(dev, DMA_BIT_MASK(n)) 声明设备能寻址多少位；一致性映射 dma_alloc_coherent(dev, size, &dma_handle, GFP_KERNEL) 分配 CPU 和设备都能随时看到一致内容的长期缓冲区（描述符环）；流式映射 dma_map_single(dev, buf, len, DMA_TO_DEVICE) 为一次传输临时映射已有缓冲区，必须用 dma_mapping_error 检查结果，传完 dma_unmap_single；多段缓冲区用 scatterlist + dma_map_sg。

cache 一致性：arm64 上很多设备不参与 CPU cache 一致性。CPU 写进 cache 的数据设备看不到，设备写进内存的数据 CPU 可能读到旧 cache。流式映射的 map/unmap（以及 dma_sync_single_for_cpu/_for_device）会按方向自动做 cache clean/invalidate；设备树里标了 dma-coherent 的设备由硬件保证一致，省掉这些操作。绕过 DMA API 自己算物理地址是经典 bug 来源。

IOMMU 位于设备和内存之间，像设备专用的 MMU：每个设备（或设备组）有自己的 I/O 页表，把 IOVA 翻译成物理地址，未映射的地址直接拒绝。好处：设备只能访问驱动明确映射给它的页（防恶意或失控设备的 DMA 攻击，Thunderbolt/PCIe 外接设备尤其需要）；物理上不连续的页可以映射成连续的 IOVA；只能寻址 32 位的设备也能用高地址内存（否则要用 swiotlb 反弹缓冲区复制）。Arm 服务器上是 SMMU（drivers/iommu/arm/arm-smmu-v3/），驱动无需改动——DMA API 背后的 dma-iommu 层自动建 I/O 页表。

XNU 用对象描述内存：IOMemoryDescriptor（任意一段内存，withAddressRange 等工厂方法）或 IOBufferMemoryDescriptor（新分配的缓冲区）；prepare() 把页钉住，IODMACommand（withSpecification 描述设备的寻址能力和段限制，setMemoryDescriptor，gen64IOVMSegments 生成设备可用的地址段，complete() 结束）负责地址翻译和 cache 同步；系统 IOMMU 抽象是 IOMapper。驱动永远不直接拿物理地址。延伸阅读：《Linux Device Drivers》第 15 章「内存映射与 DMA」。

5. XNU IOKit

IOKit 是 XNU 的面向对象驱动框架，用 C++ 的一个受限子集编写：没有异常、没有 RTTI、没有多重继承（历史上也不用模板）。libkern 用 OSMetaClass 自己实现运行时类型信息和引用计数：类用 OSDeclareDefaultStructors/OSDefineMetaClassAndStructors 宏声明，类型转换用 OSDynamicCast，对象用 retain/release（OSSafeReleaseNULL）。所有驱动都继承自 IOService（← IORegistryEntry ← OSObject）。

IORegistry 是运行时的对象树，按「平面」（plane）组织：IOService 平面表示 provider/client 关系（总线 nub → 驱动 → 驱动发布的 nub → 下一层驱动……），IODeviceTree 平面对应固件给的设备树，IOPower 平面表示电源依赖。ioreg 就是它的查看器。Matching：provider（比如 PCI 总线驱动为每个设备创建的 nub）调 registerService() 后，IOKit 在 IOCatalogue 里找 IOProviderClass 与之相符的 personality（kext 的 Info.plist 中 IOKitPersonalities 字典：IOClass、IOProviderClass、IONameMatch、IOPropertyMatch、IOPCIMatch、IOProbeScore……），先做被动匹配（比较属性），需要时按需加载 kext。

候选驱动的生命周期：init → attach(provider) → probe(provider, &score)（主动匹配：可以真的去碰硬件，调整分数或返回 NULL 放弃）→ 按分数从高到低尝试 start(provider)，第一个成功的胜出，其余 detach 并释放。start 里驱动通常：mapDeviceMemoryWithIndex 映射寄存器、建或取 IOWorkLoop（getWorkLoop）、添加 IOInterruptEventSource/IOTimerEventSource/IOCommandGate、最后自己 registerService() 让上层客户端来匹配它。关闭时 stop → detach → free。

IOWorkLoop 是 IOKit 的并发模型：一个 workloop 一个线程，挂在上面的所有事件源（中断、定时器、command gate 发来的调用）串行执行。驱动状态只在 workloop 上修改，就不需要细粒度锁；其他线程想改状态时用 IOCommandGate::runAction 「进门」排队。代价是一个慢 action 会挡住同一 workloop 上的其他事件。

6. DriverKit

DriverKit（macOS 10.15 起）把第三方驱动移到用户态：驱动打包成 dext，随宿主 App 分发，由 App 通过 SystemExtensions 框架（OSSystemExtensionRequest）请求激活、经用户批准后安装；运行时每个 dext 是一个独立的、受沙箱限制的用户态进程。崩溃只会让该进程重启，不会 kernel panic；漏洞也不直接等于内核代码执行。

编程模型刻意模仿 IOKit：类仍叫 IOService、IOBufferMemoryDescriptor、IODMACommand，方法首字母大写（Start、Stop）；接口声明写在 .iig 文件里，由 iig 工具生成跨进程调用的桩代码。中断用 IOInterruptDispatchSource 投递到 IODispatchQueue（对应 IOWorkLoop + IOInterruptEventSource）。personality 里多了 IOUserClass、IOUserServerName 键；内核里由 IOUserServer（iokit/Kernel/IOUserServer.cpp）代表 dext 参与匹配并转发调用。

限制：只支持 Apple 提供的 family（USBDriverKit、PCIDriverKit、HIDDriverKit、NetworkingDriverKit、SerialDriverKit、AudioDriverKit 等），每类访问需要 Apple 授予的 entitlement（如 com.apple.developer.driverkit 及 transport 类 entitlement）；每次与内核交互都有 IPC 开销；不能任意访问内核内存。与之相对，kext 在内核态运行，Apple 已将第三方 kext 标为废弃，Apple Silicon 上加载第三方 kext 需要在恢复模式中降低安全策略并经用户批准。Linux 的对照是 UIO/VFIO（用户态驱动框架），但 Linux 没有「第三方驱动默认在用户态」的平台政策。

7. Apple Silicon DART

DART（Device Address Resolution Table）是 Apple SoC 上的 IOMMU。公开资料主要来自 Asahi Linux 的逆向：SoC 上有很多个 DART 实例，分别位于 USB、PCIe、显示、ISP 等设备前面；每个 DART 支持若干 stream（不同的设备或功能），每个 stream 有自己的 I/O 页表，页大小为 16 KB。设备发出的每次 DMA 都经 DART 翻译，未映射的地址直接被拒绝并报错。

在 macOS 中，DART 由 Apple 的闭源驱动管理，以 IOMapper 的形式接入 IOKit：驱动通过 IODMACommand 拿到的地址就是 DART 里的 IOVA，驱动本身感知不到物理地址。这让 Thunderbolt/PCIe 外接设备只能看到为它映射的缓冲区，也是 Apple 平台防 DMA 攻击的硬件基础。

公开参考是 Linux 的 drivers/iommu/apple-dart.c（由 Asahi 项目贡献，已进入主线），它实现了标准 IOMMU API，所以上层驱动照常用 DMA API。DART 的 16 KB 粒度也影响了 Linux：页大小 4 KB 的内核与 16 KB 的 IOMMU 页配合存在困难，这是 Asahi 选择 16 KB 页内核的原因之一（Phase 2 的页大小在这里又出现了）。

  2. 两个模块。lg_echo.c：一个 misc 字符设备，write 存下最多 256 字节，read 原样读回：
    // lg_echo.c
#include <linux/module.h>
#include <linux/miscdevice.h>
#include <linux/fs.h>
#include <linux/mutex.h>
#include <linux/uaccess.h>

#define BUF_SZ 256
static char buf[BUF_SZ];
static size_t len;
static DEFINE_MUTEX(lock);                    /* read/write 可能并发，且 copy_*_user 可能睡眠：用 mutex */

static ssize_t lg_read(struct file *f, char __user *u, size_t n, loff_t *pos)
{
	ssize_t ret;

	mutex_lock(&lock);
	ret = simple_read_from_buffer(u, n, pos, buf, len);
	mutex_unlock(&lock);
	return ret;
}

static ssize_t lg_write(struct file *f, const char __user *u, size_t n, loff_t *pos)
{
	ssize_t ret;

	if (n > BUF_SZ)
		return -EINVAL;
	mutex_lock(&lock);
	if (copy_from_user(buf, u, n)) {
		len = 0;
		ret = -EFAULT;
	} else {
		len = n;
		ret = n;
	}
	mutex_unlock(&lock);
	return ret;
}

static const struct file_operations lg_fops = {
	.owner  = THIS_MODULE,
	.read   = lg_read,
	.write  = lg_write,
	.llseek = default_llseek,
};

static struct miscdevice lg_dev = {
	.minor = MISC_DYNAMIC_MINOR,
	.name  = "lg_echo",
	.fops  = &lg_fops,
	.mode  = 0666,
};
module_misc_device(lg_dev);
MODULE_LICENSE("GPL");
    lg_plat.c：自己注册一个 platform_device 和一个同名 platform_driver，看总线把它们配对并调用 probe：
    // lg_plat.c
#include <linux/module.h>
#include <linux/platform_device.h>

static int lg_probe(struct platform_device *pdev)
{
	dev_info(&pdev->dev, "probe: matched by name %s\n", pdev->name);
	return 0;
}

static struct platform_driver lg_drv = {
	.probe  = lg_probe,
	.driver = { .name = "lg_plat" },     /* 没有 of_match_table：platform_match 退回按名字匹配 */
};

static struct platform_device *lg_pdev;

static int __init lg_init(void)
{
	int ret = platform_driver_register(&lg_drv);

	if (ret)
		return ret;
	lg_pdev = platform_device_register_simple("lg_plat", -1, NULL, 0);
	if (IS_ERR(lg_pdev)) {
		platform_driver_unregister(&lg_drv);
		return PTR_ERR(lg_pdev);
	}
	return 0;
}

自测

1. 为什么中断上半部（hardirq handler）要尽量短？

上半部只做确认中断、读取必要状态等快速工作；耗时工作交给 softirq、workqueue 或 threaded IRQ（可以睡眠的内核线程）。IOKit 用 IOInterruptEventSource 把工作挪到 IOWorkLoop 线程，是同一思路。

2. DriverKit 驱动（dext）运行在哪里？

DriverKit 的设计目标就是把第三方驱动移出内核：dext 在用户态运行，内核里由 IOUserServer 代表它参与匹配并转发调用；dext 崩溃不会导致内核 panic。

3. 一个 platform 驱动的 probe 返回 -EPROBE_DEFER，意味着什么？

-EPROBE_DEFER 把这次 probe 放进延迟列表，在其他驱动成功绑定后重试；表示「不是我的」应返回 -ENODEV。IOKit 里对应的思路是：provider 自己 registerService 之后才开始为它匹配驱动。

4. 在 Apple Silicon 的 macOS 上，驱动通过 IODMACommand 拿到并写进设备寄存器的 DMA 地址是什么？

设备发出的 DMA 先经 DART 按该设备的 I/O 页表翻译；驱动看到的只有 IOVA，设备也只能访问被映射给它的页。Linux 的 DMA API 返回的 dma_addr_t 在有 IOMMU 时同样是 IOVA。
