核心概念

Core concepts

1. Linux 驱动模型

1. The Linux driver model

Linux 用三个对象描述「谁驱动谁」：struct bus_type（一条总线：platform、PCI、USB、I2C……，定义 match、probe、uevent）、struct device（一个设备实例，有 parent、bus、driver、of_node）、struct device_driver（一个驱动，有 name、of_match_table、probe/remove）。具体总线把它们嵌进自己的结构，如 struct platform_device、struct pci_dev。三者都基于 kobject，因此自动出现在 sysfs：/sys/bus/*/devices、/sys/bus/*/drivers、/sys/devices。

Linux describes “who drives whom” with three objects: struct bus_type (a bus: platform, PCI, USB, I2C…, defining match, probe, uevent), struct device (a device instance, with parent, bus, driver, of_node) and struct device_driver (a driver, with name, of_match_table, probe/remove). Concrete buses embed them in their own structures, such as struct platform_device and struct pci_dev. All three are built on kobject, so they appear in sysfs automatically: /sys/bus/*/devices, /sys/bus/*/drivers, /sys/devices.

匹配是双向的：新设备注册（device_add → bus_probe_device）时遍历该总线上已有的驱动；新驱动注册（driver_register → driver_attach）时遍历已有的设备。每一对都调总线的 match，成功后进入 drivers/base/dd.c 的 really_probe → 驱动的 probe。probe 返回 0 即绑定；返回 -EPROBE_DEFER 表示依赖（时钟、GPIO、电源）还没就绪，稍后重试；返回 -ENODEV 表示「不是我的」。

Matching works in both directions: when a new device registers (device_add → bus_probe_device), the drivers already on that bus are walked; when a new driver registers (driver_register → driver_attach), the existing devices are walked. Every pair goes through the bus’s match; on success, really_probe in drivers/base/dd.c → the driver’s probe. A probe that returns 0 binds; returning -EPROBE_DEFER means a dependency (clock, GPIO, power) is not ready yet and the probe is retried later; returning -ENODEV means “not mine”.

devicetree：ARM SoC 上的大多数外设不能被枚举（不像 PCI 有配置空间），只能由固件「声明」。bootloader（或 QEMU）把编译好的 DTB 的物理地址放在 x0 交给内核（arm64 启动协议），内核展开成 struct device_node 树，of_platform_populate 为带 compatible 的节点创建 platform_device。platform 总线的 platform_match 先比 of_match_table 里的 compatible 字符串（列表里越靠前越具体），再退回按名字匹配。驱动用 MODULE_DEVICE_TABLE(of, ...) 导出匹配表，生成 modalias，udev/mdev 据此自动 modprobe。arm64 服务器通常用 ACPI 而不是 devicetree，但驱动模型相同。延伸阅读：《Linux Device Drivers》第 14 章「Linux 设备模型」（2.6 时代，早于 arm64 devicetree）。

devicetree: most peripherals on an ARM SoC cannot be enumerated (unlike PCI, which has configuration space); they can only be “declared” by the firmware. The bootloader (or QEMU) hands the kernel the physical address of the compiled DTB in x0 (the arm64 boot protocol); the kernel unflattens it into a tree of struct device_node, and of_platform_populate creates a platform_device for each node that has a compatible. The platform bus’s platform_match first compares the compatible strings in the of_match_table (the earlier in the list, the more specific), then falls back to matching by name. A driver exports its match table with MODULE_DEVICE_TABLE(of, ...), which generates a modalias that udev/mdev use to modprobe it automatically. arm64 servers usually use ACPI rather than devicetree, but the driver model is the same. Further reading: Linux Device Drivers, Chapter 14, “The Linux Device Model” (2.6 era, predating arm64 devicetree).

2. 字符设备与 platform driver

2. Character devices and platform drivers

用户态通过 /dev 下的设备节点访问驱动。字符设备由设备号 dev_t（major/minor）标识：alloc_chrdev_region 申请号、cdev_init/cdev_add 挂上 struct file_operations，再创建 class 和 device 让 devtmpfs/udev 生成节点。最省事的是 misc device：misc_register（或 module_misc_device 宏）一步完成，主设备号固定为 10、次设备号动态分配。file_operations 就是 Phase 4 VFS 分派的终点：.open、.read、.write、.unlocked_ioctl、.mmap、.poll、.llseek；在 .read/.write 里与用户缓冲区交换数据必须用 copy_to_user/copy_from_user（或 simple_read_from_buffer 这类辅助函数）。

User space reaches a driver through a device node under /dev. A character device is identified by a device number dev_t (major/minor): alloc_chrdev_region requests a number, cdev_init/cdev_add attach a struct file_operations, and then a class and a device are created so that devtmpfs/udev create the node. The least effort is a misc device: misc_register (or the module_misc_device macro) does it in one step, with the major number fixed at 10 and the minor number allocated dynamically. file_operations is where the Phase 4 VFS dispatch ends: .open, .read, .write, .unlocked_ioctl, .mmap, .poll, .llseek; inside .read/.write, data must be exchanged with the user buffer through copy_to_user/copy_from_user (or helpers such as simple_read_from_buffer).

platform driver 是 SoC 外设最常见的写法：struct platform_driver 填 .probe 和 .driver = { .name, .of_match_table }，用 module_platform_driver() 注册。probe 里的典型动作：devm_platform_ioremap_resource(pdev, 0) 把设备树里 reg 描述的寄存器区映射成内核虚拟地址（页表属性是 Device-nGnRE，Phase 2 的 MAIR），用 readl/writel 访问；platform_get_irq 拿中断号、devm_request_irq 注册处理函数。devm_* 是托管资源：设备解绑时按逆序自动释放，消灭了大量错误路径上的泄漏。

A platform driver is the most common way to write a driver for an SoC peripheral: a struct platform_driver fills in .probe and .driver = { .name, .of_match_table } and is registered with module_platform_driver(). Typical work in probe: devm_platform_ioremap_resource(pdev, 0) maps the register region described by reg in the device tree to a kernel virtual address (page-table attribute Device-nGnRE, the MAIR from Phase 2), accessed with readl/writel; platform_get_irq gets the interrupt number and devm_request_irq registers the handler. devm_* are managed resources: they are released automatically in reverse order when the device is unbound, which eliminates a great many leaks on error paths.

XNU 的 BSD 层也有字符设备（cdevsw_add + devfs_make_node，/dev/null、终端都是这样来的），但 IOKit 驱动通常不走 /dev：用户态通过 IOServiceOpen 打开一个 IOUserClient，再用 IOConnectCallMethod 调驱动的 externalMethod。这个连接本身是一个 Mach port（Phase 3 的 kobject），每次调用就是一条 Mach 消息——IOUserClient 的参数校验也因此是 macOS/iOS 内核漏洞最集中的地方之一。

XNU’s BSD layer also has character devices (cdevsw_add + devfs_make_node; /dev/null and terminals come about this way), but IOKit drivers usually do not go through /dev: user space opens an IOUserClient with IOServiceOpen, then calls the driver’s externalMethod with IOConnectCallMethod. The connection itself is a Mach port (the kobject from Phase 3), and every call is a Mach message — which is also why IOUserClient argument validation is one of the places where macOS/iOS kernel vulnerabilities are most concentrated.

3. 中断：上半部、下半部、threaded IRQ

3. Interrupts: top half, bottom half, threaded IRQ

ARM64 上设备中断先到中断控制器：标准 Arm 平台（QEMU virt）是 GIC，Apple Silicon 是 Apple 自己的 AIC（Linux 驱动 drivers/irqchip/irq-apple-aic.c；Apple 芯片上定时器，以及支持 fast IPI 的芯片上的核间中断，走 FIQ）。控制器向 CPU 发 IRQ，CPU 跳到 VBAR_EL1 的 IRQ 向量。Linux 里 handle_arch_irq 指向控制器驱动（如 gic_handle_irq），它读出硬件中断号，经 irq domain 翻译成 Linux irq 号，调 generic_handle_domain_irq → 流控函数（如 handle_fasteoi_irq）→ handle_irq_event → 驱动注册的 handler。/proc/interrupts 每行就是一个 irq 号在各 CPU 上的计数。

On ARM64 a device interrupt first reaches the interrupt controller: on standard Arm platforms (QEMU virt) this is the GIC; on Apple Silicon it is Apple’s own AIC (Linux driver drivers/irqchip/irq-apple-aic.c; on Apple chips the timers, and the inter-processor interrupts on chips that support fast IPIs, come in as FIQs). The controller raises an IRQ at the CPU, and the CPU jumps to the IRQ vector at VBAR_EL1. In Linux, handle_arch_irq points at the controller driver (for example gic_handle_irq), which reads the hardware interrupt number, translates it into a Linux irq number through the irq domain, and calls generic_handle_domain_irq → the flow handler (for example handle_fasteoi_irq) → handle_irq_event → the handler the driver registered. Each line of /proc/interrupts is the per-CPU count for one irq number.

上半部（hardirq handler，request_irq(irq, handler, flags, name, dev)）运行在中断上下文：本 CPU 中断已关、不能睡眠、要尽快返回——只做确认中断、读必要状态、把数据挪出硬件 FIFO 这类事，返回 IRQ_HANDLED（或共享中断线上「不是我的」时返回 IRQ_NONE）。其余工作推给下半部：softirq（编译期固定的少数几种，网络收发、块完成、定时器、RCU 用；在中断返回时或 ksoftirqd 里运行，仍不能睡眠）；tasklet（建在 softirq 之上，正被逐步淘汰，6.9 起引入 BH workqueue 作为替代）；workqueue（schedule_work/queue_work，在 kworker 内核线程里运行，可以睡眠）。

The top half (the hardirq handler, request_irq(irq, handler, flags, name, dev)) runs in interrupt context: interrupts are off on this CPU, it cannot sleep, and it must return as quickly as possible — it only acknowledges the interrupt, reads the necessary status and moves data out of the hardware FIFO, then returns IRQ_HANDLED (or IRQ_NONE when it is “not mine” on a shared interrupt line). The rest of the work is pushed to the bottom half: softirq (a few kinds fixed at compile time, used for network receive/transmit, block completion, timers and RCU; runs on interrupt return or in ksoftirqd, and still cannot sleep); tasklet (built on softirq and being phased out; BH workqueues were introduced in 6.9 as the replacement); workqueue (schedule_work/queue_work, runs in kworker kernel threads and can sleep).

threaded IRQ：request_threaded_irq(irq, handler, thread_fn, IRQF_ONESHOT, name, dev)。handler 是快速的上半部，返回 IRQ_WAKE_THREAD 后内核唤醒专属线程 irq/<N>-<name> 执行 thread_fn，它可以睡眠（拿 mutex、做 I2C/SPI 传输——这些总线上的设备读一个寄存器就要睡眠等待）。IRQF_ONESHOT 让该中断线在线程跑完前保持屏蔽，避免电平触发的中断反复打进来。handler 传 NULL 则使用默认上半部。何时用：处理过程需要睡眠、或希望中断处理可被调度和设定优先级时；PREEMPT_RT 内核会把几乎所有中断强制线程化。

threaded IRQ: request_threaded_irq(irq, handler, thread_fn, IRQF_ONESHOT, name, dev). handler is the fast top half; after it returns IRQ_WAKE_THREAD, the kernel wakes the dedicated thread irq/<N>-<name> to run thread_fn, which can sleep (take a mutex, do an I2C/SPI transfer — reading a single register of a device on these buses means sleeping while you wait). IRQF_ONESHOT keeps the interrupt line masked until the thread has finished, so a level-triggered interrupt does not keep firing. Passing NULL as handler uses the default top half. When to use it: when the handling needs to sleep, or when you want interrupt handling to be schedulable and to have a settable priority; a PREEMPT_RT kernel force-threads almost all interrupts.

XNU：fleh_irq → sleh_irq（osfmk/arm64/sleh.c）→ 平台中断控制器驱动（Apple Silicon 上是闭源 kext，基类 IOInterruptController）→ 分发到驱动注册的处理器。IOKit 驱动几乎从不在上半部做事：它创建 IOInterruptEventSource 并加入自己的 IOWorkLoop，中断发生时事件源在中断上下文里只记一次数并唤醒 workloop 线程，真正的 action 在线程里运行——IOKit 默认就是「threaded IRQ」。需要在中断上下文里先判断「是不是我的」时用 IOFilterInterruptEventSource，其 filter 函数在主中断上下文运行，返回 true 才调度 action。延伸阅读：《Linux Kernel Development》第 7–8 章「中断和中断处理」「下半部和推后执行的工作」；《Linux Device Drivers》第 10 章「中断处理」。

XNU: fleh_irq → sleh_irq (osfmk/arm64/sleh.c) → the platform interrupt-controller driver (a closed-source kext on Apple Silicon, base class IOInterruptController) → dispatch to the handler the driver registered. IOKit drivers almost never do work in the top half: a driver creates an IOInterruptEventSource and adds it to its own IOWorkLoop; when the interrupt fires, the event source only records a count in interrupt context and wakes the workloop thread, and the real action runs in that thread — IOKit is a “threaded IRQ” by default. When you need to decide “is this mine?” in interrupt context first, use IOFilterInterruptEventSource: its filter function runs in primary interrupt context, and the action is scheduled only if it returns true. Further reading: Linux Kernel Development, Chapters 7–8, “Interrupts and Interrupt Handlers” and “Bottom Halves and Deferring Work”; Linux Device Drivers, Chapter 10, “Interrupt Handling”.

4. DMA 与 IOMMU

4. DMA and the IOMMU

DMA 让设备直接读写内存，CPU 只负责告诉设备「从哪读、写到哪」。问题是设备看到的地址既不是内核虚拟地址，也未必是物理地址，而是 DMA 地址（dma_addr_t，又叫 bus address / IOVA）。Linux 的 DMA API 屏蔽了差别：先用 dma_set_mask_and_coherent(dev, DMA_BIT_MASK(n)) 声明设备能寻址多少位；一致性映射 dma_alloc_coherent(dev, size, &dma_handle, GFP_KERNEL) 分配 CPU 和设备都能随时看到一致内容的长期缓冲区（描述符环）；流式映射 dma_map_single(dev, buf, len, DMA_TO_DEVICE) 为一次传输临时映射已有缓冲区，必须用 dma_mapping_error 检查结果，传完 dma_unmap_single；多段缓冲区用 scatterlist + dma_map_sg。

DMA lets a device read and write memory directly; the CPU only tells the device “where to read from and where to write to”. The catch is that the address the device sees is neither a kernel virtual address nor necessarily a physical address, but a DMA address (dma_addr_t, also called a bus address / IOVA). The Linux DMA API hides the difference: first declare how many address bits the device can use with dma_set_mask_and_coherent(dev, DMA_BIT_MASK(n)); a coherent mapping, dma_alloc_coherent(dev, size, &dma_handle, GFP_KERNEL), allocates a long-lived buffer (a descriptor ring) whose contents the CPU and the device always see consistently; a streaming mapping, dma_map_single(dev, buf, len, DMA_TO_DEVICE), temporarily maps an existing buffer for one transfer — the result must be checked with dma_mapping_error, and dma_unmap_single is called when the transfer is done; multi-segment buffers use a scatterlist + dma_map_sg.

cache 一致性：arm64 上很多设备不参与 CPU cache 一致性。CPU 写进 cache 的数据设备看不到，设备写进内存的数据 CPU 可能读到旧 cache。流式映射的 map/unmap（以及 dma_sync_single_for_cpu/_for_device）会按方向自动做 cache clean/invalidate；设备树里标了 dma-coherent 的设备由硬件保证一致，省掉这些操作。绕过 DMA API 自己算物理地址是经典 bug 来源。

Cache coherence: on arm64 many devices do not take part in CPU cache coherence. Data the CPU has written into the cache is invisible to the device, and for data the device has written to memory the CPU may read a stale cache line. The map/unmap of a streaming mapping (and dma_sync_single_for_cpu/_for_device) automatically performs cache clean/invalidate according to the direction; a device marked dma-coherent in the device tree is kept coherent by hardware, so these operations are skipped. Bypassing the DMA API and computing physical addresses yourself is a classic source of bugs.

IOMMU 位于设备和内存之间，像设备专用的 MMU：每个设备（或设备组）有自己的 I/O 页表，把 IOVA 翻译成物理地址，未映射的地址直接拒绝。好处：设备只能访问驱动明确映射给它的页（防恶意或失控设备的 DMA 攻击，Thunderbolt/PCIe 外接设备尤其需要）；物理上不连续的页可以映射成连续的 IOVA；只能寻址 32 位的设备也能用高地址内存（否则要用 swiotlb 反弹缓冲区复制）。Arm 服务器上是 SMMU（drivers/iommu/arm/arm-smmu-v3/），驱动无需改动——DMA API 背后的 dma-iommu 层自动建 I/O 页表。

The IOMMU sits between devices and memory, like an MMU dedicated to devices: each device (or device group) has its own I/O page table that translates IOVAs into physical addresses, and unmapped addresses are rejected outright. The benefits: a device can access only the pages the driver has explicitly mapped for it (protection against DMA attacks from malicious or runaway devices, which external Thunderbolt/PCIe devices especially need); physically non-contiguous pages can be mapped as a contiguous IOVA range; and a device that can address only 32 bits can still use high memory (otherwise swiotlb bounce buffers have to copy the data). On Arm servers this is the SMMU (drivers/iommu/arm/arm-smmu-v3/), and drivers need no changes — the dma-iommu layer behind the DMA API builds the I/O page tables automatically.

XNU 用对象描述内存：IOMemoryDescriptor（任意一段内存，withAddressRange 等工厂方法）或 IOBufferMemoryDescriptor（新分配的缓冲区）；prepare() 把页钉住，IODMACommand（withSpecification 描述设备的寻址能力和段限制，setMemoryDescriptor，gen64IOVMSegments 生成设备可用的地址段，complete() 结束）负责地址翻译和 cache 同步；系统 IOMMU 抽象是 IOMapper。驱动永远不直接拿物理地址。延伸阅读：《Linux Device Drivers》第 15 章「内存映射与 DMA」。

XNU describes memory with objects: IOMemoryDescriptor (any range of memory, with factory methods such as withAddressRange) or IOBufferMemoryDescriptor (a newly allocated buffer); prepare() wires the pages down, and IODMACommand (withSpecification describes the device’s addressing capability and segment limits, setMemoryDescriptor, gen64IOVMSegments generates the address segments the device can use, complete() finishes) handles address translation and cache synchronisation; the system IOMMU abstraction is IOMapper. A driver never takes a physical address directly. Further reading: Linux Device Drivers, Chapter 15, “Memory Mapping and DMA”.

5. XNU IOKit

5. XNU IOKit

IOKit 是 XNU 的面向对象驱动框架，用 C++ 的一个受限子集编写：没有异常、没有 RTTI、没有多重继承（历史上也不用模板）。libkern 用 OSMetaClass 自己实现运行时类型信息和引用计数：类用 OSDeclareDefaultStructors/OSDefineMetaClassAndStructors 宏声明，类型转换用 OSDynamicCast，对象用 retain/release（OSSafeReleaseNULL）。所有驱动都继承自 IOService（← IORegistryEntry ← OSObject）。

IOKit is XNU’s object-oriented driver framework, written in a restricted subset of C++: no exceptions, no RTTI, no multiple inheritance (and historically no templates either). libkern implements its own run-time type information and reference counting with OSMetaClass: classes are declared with the OSDeclareDefaultStructors/OSDefineMetaClassAndStructors macros, casts use OSDynamicCast, and objects use retain/release (OSSafeReleaseNULL). Every driver inherits from IOService (← IORegistryEntry ← OSObject).

IORegistry 是运行时的对象树，按「平面」（plane）组织：IOService 平面表示 provider/client 关系（总线 nub → 驱动 → 驱动发布的 nub → 下一层驱动……），IODeviceTree 平面对应固件给的设备树，IOPower 平面表示电源依赖。ioreg 就是它的查看器。Matching：provider（比如 PCI 总线驱动为每个设备创建的 nub）调 registerService() 后，IOKit 在 IOCatalogue 里找 IOProviderClass 与之相符的 personality（kext 的 Info.plist 中 IOKitPersonalities 字典：IOClass、IOProviderClass、IONameMatch、IOPropertyMatch、IOPCIMatch、IOProbeScore……），先做被动匹配（比较属性），需要时按需加载 kext。

The IORegistry is the run-time object tree, organised into “planes”: the IOService plane represents provider/client relationships (bus nub → driver → the nub that driver publishes → the next driver…), the IODeviceTree plane corresponds to the device tree supplied by the firmware, and the IOPower plane represents power dependencies. ioreg is its viewer. Matching: after a provider (for example the nub the PCI bus driver creates for each device) calls registerService(), IOKit searches the IOCatalogue for personalities whose IOProviderClass fits it (the IOKitPersonalities dictionary in a kext’s Info.plist: IOClass, IOProviderClass, IONameMatch, IOPropertyMatch, IOPCIMatch, IOProbeScore…), first doing passive matching (comparing properties), and loads the kext on demand when needed.

候选驱动的生命周期：init → attach(provider) → probe(provider, &score)（主动匹配：可以真的去碰硬件，调整分数或返回 NULL 放弃）→ 按分数从高到低尝试 start(provider)，第一个成功的胜出，其余 detach 并释放。start 里驱动通常：mapDeviceMemoryWithIndex 映射寄存器、建或取 IOWorkLoop（getWorkLoop）、添加 IOInterruptEventSource/IOTimerEventSource/IOCommandGate、最后自己 registerService() 让上层客户端来匹配它。关闭时 stop → detach → free。

The lifecycle of a candidate driver: init → attach(provider) → probe(provider, &score) (active matching: it may really touch the hardware, adjust the score, or return NULL to give up) → start(provider) is tried in descending order of score; the first to succeed wins, and the rest are detached and released. In start a driver typically maps its registers with mapDeviceMemoryWithIndex, creates or obtains an IOWorkLoop (getWorkLoop), adds IOInterruptEventSource/IOTimerEventSource/IOCommandGate, and finally calls registerService() itself so that clients in the layer above can match against it. On shutdown: stop → detach → free.

IOWorkLoop 是 IOKit 的并发模型：一个 workloop 一个线程，挂在上面的所有事件源（中断、定时器、command gate 发来的调用）串行执行。驱动状态只在 workloop 上修改，就不需要细粒度锁；其他线程想改状态时用 IOCommandGate::runAction 「进门」排队。代价是一个慢 action 会挡住同一 workloop 上的其他事件。

IOWorkLoop is IOKit’s concurrency model: one workloop, one thread, and all the event sources attached to it (interrupts, timers, calls coming in through a command gate) execute serially. If driver state is modified only on the workloop, no fine-grained locks are needed; other threads that want to change the state “enter the gate” and queue up with IOCommandGate::runAction. The cost is that one slow action holds up the other events on the same workloop.

6. DriverKit

6. DriverKit

DriverKit（macOS 10.15 起）把第三方驱动移到用户态：驱动打包成 dext，随宿主 App 分发，由 App 通过 SystemExtensions 框架（OSSystemExtensionRequest）请求激活、经用户批准后安装；运行时每个 dext 是一个独立的、受沙箱限制的用户态进程。崩溃只会让该进程重启，不会 kernel panic；漏洞也不直接等于内核代码执行。

DriverKit (from macOS 10.15) moves third-party drivers into user space: a driver is packaged as a dext and distributed with its host app; the app requests activation through the SystemExtensions framework (OSSystemExtensionRequest), and the dext is installed after the user approves; at run time each dext is a separate, sandboxed user-space process. A crash only restarts that process instead of causing a kernel panic, and a vulnerability is not directly kernel code execution.

编程模型刻意模仿 IOKit：类仍叫 IOService、IOBufferMemoryDescriptor、IODMACommand，方法首字母大写（Start、Stop）；接口声明写在 .iig 文件里，由 iig 工具生成跨进程调用的桩代码。中断用 IOInterruptDispatchSource 投递到 IODispatchQueue（对应 IOWorkLoop + IOInterruptEventSource）。personality 里多了 IOUserClass、IOUserServerName 键；内核里由 IOUserServer（iokit/Kernel/IOUserServer.cpp）代表 dext 参与匹配并转发调用。

The programming model deliberately mirrors IOKit: the classes are still called IOService, IOBufferMemoryDescriptor and IODMACommand, and method names start with a capital letter (Start, Stop); interfaces are declared in .iig files, from which the iig tool generates the stub code for cross-process calls. Interrupts are delivered by an IOInterruptDispatchSource to an IODispatchQueue (corresponding to IOWorkLoop + IOInterruptEventSource). The personality gains the IOUserClass and IOUserServerName keys; in the kernel, IOUserServer (iokit/Kernel/IOUserServer.cpp) represents the dext in matching and forwards calls.

限制：只支持 Apple 提供的 family（USBDriverKit、PCIDriverKit、HIDDriverKit、NetworkingDriverKit、SerialDriverKit、AudioDriverKit 等），每类访问需要 Apple 授予的 entitlement（如 com.apple.developer.driverkit 及 transport 类 entitlement）；每次与内核交互都有 IPC 开销；不能任意访问内核内存。与之相对，kext 在内核态运行，Apple 已将第三方 kext 标为废弃，Apple Silicon 上加载第三方 kext 需要在恢复模式中降低安全策略并经用户批准。Linux 的对照是 UIO/VFIO（用户态驱动框架），但 Linux 没有「第三方驱动默认在用户态」的平台政策。

Limitations: only the families Apple provides are supported (USBDriverKit, PCIDriverKit, HIDDriverKit, NetworkingDriverKit, SerialDriverKit, AudioDriverKit and others); each kind of access needs an entitlement granted by Apple (such as com.apple.developer.driverkit plus a transport entitlement); every interaction with the kernel carries IPC overhead; and kernel memory cannot be accessed at will. By contrast, a kext runs in kernel mode; Apple has deprecated third-party kexts, and loading a third-party kext on Apple Silicon requires lowering the security policy in recovery mode plus user approval. The Linux counterpart is UIO/VFIO (user-space driver frameworks), but Linux has no platform policy of “third-party drivers run in user space by default”.

7. Apple Silicon DART

7. Apple Silicon DART

DART（Device Address Resolution Table）是 Apple SoC 上的 IOMMU。公开资料主要来自 Asahi Linux 的逆向：SoC 上有很多个 DART 实例，分别位于 USB、PCIe、显示、ISP 等设备前面；每个 DART 支持若干 stream（不同的设备或功能），每个 stream 有自己的 I/O 页表，页大小为 16 KB。设备发出的每次 DMA 都经 DART 翻译，未映射的地址直接被拒绝并报错。

DART (Device Address Resolution Table) is the IOMMU on Apple SoCs. Public information comes mainly from Asahi Linux’s reverse engineering: an SoC has many DART instances, each sitting in front of devices such as USB, PCIe, display and the ISP; each DART supports a number of streams (different devices or functions), each stream has its own I/O page table, and the page size is 16 KB. Every DMA a device issues is translated by the DART, and unmapped addresses are rejected outright with an error.

在 macOS 中，DART 由 Apple 的闭源驱动管理，以 IOMapper 的形式接入 IOKit：驱动通过 IODMACommand 拿到的地址就是 DART 里的 IOVA，驱动本身感知不到物理地址。这让 Thunderbolt/PCIe 外接设备只能看到为它映射的缓冲区，也是 Apple 平台防 DMA 攻击的硬件基础。

In macOS the DART is managed by Apple’s closed-source driver and plugs into IOKit as an IOMapper: the address a driver gets through IODMACommand is an IOVA in the DART, and the driver itself never sees physical addresses. This lets an external Thunderbolt/PCIe device see only the buffers mapped for it, and it is the hardware foundation of DMA-attack protection on Apple platforms.

公开参考是 Linux 的 drivers/iommu/apple-dart.c（由 Asahi 项目贡献，已进入主线），它实现了标准 IOMMU API，所以上层驱动照常用 DMA API。DART 的 16 KB 粒度也影响了 Linux：页大小 4 KB 的内核与 16 KB 的 IOMMU 页配合存在困难，这是 Asahi 选择 16 KB 页内核的原因之一（Phase 2 的页大小在这里又出现了）。

The public reference is Linux’s drivers/iommu/apple-dart.c (contributed by the Asahi project and merged into mainline), which implements the standard IOMMU API, so the drivers above it use the DMA API as usual. DART’s 16 KB granularity has also affected Linux: a kernel with 4 KB pages has trouble working with 16 KB IOMMU pages, which is one of the reasons Asahi chose a 16 KB-page kernel (the page size from Phase 2 shows up again here).

	mutex_lock(&lock);
	ret = simple_read_from_buffer(u, n, pos, buf, len);
	mutex_unlock(&lock);
	return ret;
}

{

		return -EINVAL;
	mutex_lock(&lock);
	if (copy_from_user(buf, u, n)) {
		len = 0;
		ret = -EFAULT;
	} else {
		len = n;
		ret = n;
	}
	mutex_unlock(&lock);
	return ret;
}

自测

Self-check

1. 为什么中断上半部（hardirq handler）要尽量短？

1. Why should the interrupt top half (the hardirq handler) be as short as possible?

上半部只做确认中断、读取必要状态等快速工作；耗时工作交给 softirq、workqueue 或 threaded IRQ（可以睡眠的内核线程）。IOKit 用 IOInterruptEventSource 把工作挪到 IOWorkLoop 线程，是同一思路。The top half does only fast work such as acknowledging the interrupt and reading the necessary status; time-consuming work goes to softirq, a workqueue or a threaded IRQ (a kernel thread that can sleep). IOKit uses IOInterruptEventSource to move the work onto the IOWorkLoop thread — the same idea.

2. DriverKit 驱动（dext）运行在哪里？

2. Where does a DriverKit driver (dext) run?

DriverKit 的设计目标就是把第三方驱动移出内核：dext 在用户态运行，内核里由 IOUserServer 代表它参与匹配并转发调用；dext 崩溃不会导致内核 panic。Moving third-party drivers out of the kernel is exactly what DriverKit is designed for: a dext runs in user space, and in the kernel IOUserServer represents it in matching and forwards calls; a dext crash does not cause a kernel panic.

3. 一个 platform 驱动的 probe 返回 -EPROBE_DEFER，意味着什么？

3. A platform driver’s probe returns -EPROBE_DEFER. What does that mean?

-EPROBE_DEFER 把这次 probe 放进延迟列表，在其他驱动成功绑定后重试；表示「不是我的」应返回 -ENODEV。IOKit 里对应的思路是：provider 自己 registerService 之后才开始为它匹配驱动。-EPROBE_DEFER puts this probe on the deferred list, to be retried after other drivers bind successfully; to say “not mine”, return -ENODEV. The corresponding idea in IOKit: drivers are matched for a provider only after the provider itself calls registerService.

4. 在 Apple Silicon 的 macOS 上，驱动通过 IODMACommand 拿到并写进设备寄存器的 DMA 地址是什么？

4. On macOS on Apple Silicon, what is the DMA address a driver gets through IODMACommand and writes into the device registers?

设备发出的 DMA 先经 DART 按该设备的 I/O 页表翻译；驱动看到的只有 IOVA，设备也只能访问被映射给它的页。Linux 的 DMA API 返回的 dma_addr_t 在有 IOMMU 时同样是 IOVA。A DMA issued by the device is first translated by DART through that device’s I/O page table; the driver sees only the IOVA, and the device can access only the pages mapped for it. With an IOMMU present, the dma_addr_t returned by the Linux DMA API is likewise an IOVA.
