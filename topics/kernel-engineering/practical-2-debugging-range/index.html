任务

The brief

你接手了四个小驱动，每个都有一张未解决的工单。对每一张工单：You have inherited four small drivers, each with one open ticket. For every ticket:
  • 复现：用附带的压力脚本，在带调试选项的内核上让问题稳定出现。
  • Reproduce it: with the stress script that comes with the module, on a kernel built with the debugging options, until the problem shows up reliably.
  • 定位：选对工具，读懂它的报告，用一句话说出根因。
  • Locate it: pick the right tool, read its report, and state the root cause in one sentence.
  • 修复并验证：改代码，重启虚拟机，压力脚本连续三次通过，工具不再报告，模块能干净卸载。
  • Fix it and verify: change the code, reboot the VM, pass the stress script three times in a row with the tool silent, and unload the module cleanly.
  • 写下来：一个带说明的修复提交，加一页事后分析。
  • Write it down: one fix commit with a proper message, and a one-page post-mortem.

交付物与验收标准

Deliverables and acceptance

交付物：一个 git 仓库，里面是四个修复提交（每张工单一个）和四份事后分析，按本页「怎么写」一节的模板。

Deliverables: one git repository holding four fix commits (one per ticket) and four post-mortems that follow the template in “Writing it up” below.

验收标准：每张工单都要满足下面六条。每一条都能由别人照着你的事后分析重做一遍来检查。

Acceptance criteria: all six hold for every ticket. Each can be checked by someone else who repeats what your post-mortem says.

  1. 复现过。事后分析里有你用的命令，以及你自己那次运行的工具报告或错误输出的关键几行。
  2. Reproduced. The post-mortem gives the commands you used and the key lines of the tool report or wrong output from your own run.
  3. 根因是一句话。它说的是哪一段代码违反了哪一条规则，而不是症状。「机器卡死」是症状；「对象被释放时它里面的定时器还在排队」是根因。
  4. The root cause is one sentence. It names which code breaks which rule, not the symptom. “The machine hangs” is a symptom; “the object is freed while a timer inside it is still queued” is a root cause.
  5. 修复后通过。在一次新启动的虚拟机里，压力脚本连续三次打印预期结果；dmesg 里没有 BUG:、WARNING:、INFO: task；工单 4 的 kmemleak 扫描结果里没有这个模块；rmmod 成功且之后没有新消息。
  6. It passes with the fix. In a freshly booted VM the stress script prints the expected result three times in a row; dmesg has no BUG:, WARNING: or INFO: task; for ticket 4 the kmemleak scan lists nothing from the module; rmmod succeeds and nothing new is logged after it.
  7. 功能还在。修复不能靠删掉功能来过关：会话的字节数仍然汇总进总数，统计行里的计数仍然属于它旁边的表名，合法镜像仍然被接受。
  8. The feature is still there. A fix may not pass by deleting what the code does: session bytes still reach the total, the counters in a stats line still belong to the table named beside them, a valid image is still accepted.
  9. 没有让工具闭嘴。不用 data_race()、kmemleak_not_leak()、lockdep_off() 之类的标注把报告压下去，也不靠加 msleep() 让问题变得难以触发。
  10. The tool was not silenced. No annotation such as data_race(), kmemleak_not_leak() or lockdep_off() to suppress the report, and no msleep() that only makes the problem harder to hit.
  11. 提交合格。每个修复是一个提交，checkpatch.pl --strict 对它报告 0 errors、0 warnings；提交信息按实战 1 的规则写，并引用工具报告里最关键的几行。
  12. The commit is in shape. Each fix is one commit on which checkpatch.pl --strict reports 0 errors and 0 warnings; the message follows the rules of Practical 1 and quotes the lines of the tool report that matter most.

背景知识

Background

五个概念，每个只讲到够你完成任务为止。工具的行为按 v7.3.1 的内核文档和源码核对。

Five concepts, each taken only as far as the task needs. How the tools behave was checked against the kernel documentation and source at v7.3.1.

1. 先复现，再动手

1. Reproduce before you touch anything

一个不能随手触发的 bug，你没法证明自己修好了它：改完之后它不出现，可能是修好了，也可能只是这次没碰上。所以第一步永远是把「偶尔出现」变成「每次都出现」。常用的办法有三种：加压（更多并发、更多次数，四个压力脚本都是这个思路）、开检查（让调试工具在错误发生的那一刻就报告，而不是等它造成后果）、缩小范围（只加载一个模块，只跑一个脚本）。

A bug you cannot trigger at will is a bug you cannot prove fixed: when it stays away after your change, the change may have fixed it, or this run may simply have missed it. So the first step is always to turn “sometimes” into “every time”. There are three common ways: add load (more concurrency, more iterations; all four stress scripts work this way), switch on checks (so that a debugging tool reports the mistake at the moment it happens instead of when its consequences surface) and narrow the field (load one module, run one script).

还有一条这一阶段特有的规矩：每张工单用一次新启动的虚拟机。KASAN 默认每次启动只报告第一处非法访问；任何一份 KASAN 或 lockdep 报告之后，内核都会关掉锁检查（日志里是 Disabling lock debugging due to kernel taint 或 INFO: lockdep is turned off.）。在一台已经报过错的机器上「没有新报告」什么也证明不了。热身的最后一步会让你亲眼看到这一点。

One rule is specific to this stage: a freshly booted VM for every ticket. By default KASAN reports only the first invalid access of a boot, and after any KASAN or lockdep report the kernel turns lock checking off (the log says Disabling lock debugging due to kernel taint or INFO: lockdep is turned off.). “No new report” on a machine that has already reported once proves nothing. The last step of the warm-up lets you see this for yourself.

2. 每种工具看得见什么

2. What each tool can see

调试工具各管一类错误，对别的类别完全沉默。选错工具时，你会得到一份干净的日志和一个依然存在的 bug。

Each debugging tool covers one class of mistake and is completely silent about the others. Pick the wrong one and you get a clean log and a bug that is still there.

An object younger than 5 seconds is not reported (MSECS_MIN_AGE in mm/kmemleak.c), so wait a few seconds after the stress script before scanning. On arm64, KCSAN can only be selected once CONFIG_EXPERT is on.

3. 怎样读一份报告

3. How to read a report

四种工具的报告都很长，但结构相同，读的顺序也相同：

The reports of all four tools are long, but they share one structure and are read in one order:

  1. 标题行说的是错误的种类和发现它的位置，例如 BUG: KASAN: slab-use-after-free in enqueue_timer+0x9c/0x630。注意「发现它的位置」经常是内核的公共代码，不是出错的代码。
  2. The title line gives the kind of error and where it was detected, for example BUG: KASAN: slab-use-after-free in enqueue_timer+0x9c/0x630. Note that “where it was detected” is often common kernel code, not the code that is wrong.
  3. 每个调用栈里，找第一个属于你的函数。模块里的函数后面带着方括号里的模块名，例如 lg_fw_write+0x54/0x208 [lg_fw]。它上面的几行是工具自己和内核公共代码，下面是系统调用入口。
  4. In every stack, find the first function that is yours. A function in a module carries the module name in brackets, for example lg_fw_write+0x54/0x208 [lg_fw]. The lines above it are the tool itself and common kernel code; the lines below are the system-call entry.
  5. 把几个调用栈放在一起看。KASAN 的释放后使用报告有三个栈：谁访问、谁分配、谁释放。错的几乎总是「谁释放」和「谁访问」之间的关系，而不是其中某一个。lockdep 报告有两条依赖链，每条说明一种加锁顺序是在哪里出现的。
  6. Read the stacks together. A KASAN use-after-free report has three: who accessed, who allocated, who freed. What is wrong is almost always the relation between “who freed” and “who accessed”, not either one alone. A lockdep report has two dependency chains, each saying where one of the lock orders was taken.
  7. 最后才看细节：地址、对象大小、偏移量、影子内存。它们用来核对你的猜测，而不是用来产生猜测。
  8. Details come last: addresses, object sizes, offsets, shadow memory. They serve to check your hypothesis, not to produce it.

函数名+0x偏移/0x长度 可以换算成源码行号。对模块里位于 .text 段的函数，先查函数在 .ko 里的地址，加上偏移；调用栈里记的是返回地址，所以再减去一条指令的长度（arm64 上是 4）：

function+0xoffset/0xsize can be turned into a source line. For a module function in the .text section, look up the address of the function inside the .ko and add the offset; a stack trace records return addresses, so subtract the length of one instruction (4 on arm64):

llvm-nm lg_fw.ko | grep ' lg_fw_write'      # 00000000000000e8 t lg_fw_write
# 0xe8 + 0x54 - 4 = 0x138
llvm-addr2line -f -i -e lg_fw.ko 0x138
_kmalloc_noprof
/home/user/klab/linux/include/linux/slab.h:995
lg_fw_write
/home/user/klab/vm/lab-build/lg_fw.c:39

输出由内到外列出内联展开的每一层，最后一行是你的代码：lg_fw.c 第 39 行（路径是验证运行那台机器上的）。模块要带调试信息编译，arm64 的 defconfig 默认带。初始化函数在 .init.text 段，这个办法对它不适用。

The output lists each level of inlining from the inside out, and its last line is your code: line 39 of lg_fw.c (the paths are those of the machine the checking run used). The module has to be built with debug information, which the arm64 defconfig enables. Init functions live in the .init.text section, and this method does not work for them.

4. 修根因，不修症状

4. Fix the cause, not the symptom

让报告消失的改法通常不止一种，其中只有一种是修复。判断的办法是先把根因写成一条被违反的规则，再看你的改动是否让这条规则重新成立：

There is usually more than one change that makes a report go away, and only one of them is a fix. The test is to write the root cause down as a rule that was broken, and then ask whether your change makes that rule hold again:

修完之后的验证也要对准根因：重跑的必须是当初能复现问题的同一个脚本，在一次新启动里，而且要跑不止一遍。

Verification after the fix aims at the cause too: rerun the very script that reproduced the problem, in a fresh boot, and more than once.

5. 事后分析

5. The post-mortem

事后分析（post-mortem）是修完 bug 之后写给同事的一页纸。它回答五个问题：用户看到了什么，怎样复现，根因是什么，改了什么，怎样确认修好了。再加一个最有价值的问题：这个 bug 当初是怎样混进来、又为什么没有被更早发现的。它只谈代码和流程，不追究是谁写的。

A post-mortem is the page you write for your colleagues once a bug is fixed. It answers five questions: what the user saw, how to reproduce it, what the root cause was, what was changed, and how the fix was confirmed. Then comes the most valuable one: how did this bug get in, and why was it not caught earlier. It is about code and process and never about who wrote the line.

这页纸也是面试时「讲一个你查过的 bug」的底稿。面试官想听的正是这个顺序：症状，你排除了什么，决定性的证据是哪一行，修复为什么对。

This page is also your script for “tell me about a bug you tracked down” in an interview. That order is what the interviewer wants to hear: the symptom, what you ruled out, which line was the decisive evidence, and why the fix is right.

    cd linux                      # the v7.3.1 tree

工单 1 · lg_session：警告刷屏，有时机器没反应

Ticket 1 · lg_session: a flood of warnings, sometimes a dead machine

lg_session 给每次 open() 建一个会话，写入的字节数先记在会话里，由一个每 20 毫秒运行一次的工作项汇总进全局总数。

lg_session creates a session for every open(). Bytes written are first counted in the session, and a work item that runs every 20 milliseconds folds them into the global total.

insmod lg_session.ko
./stress-session.sh

修好的样子：脚本连跑三遍，每遍都打印 stress-session: this run added 3200 bytes, expected 3200，日志干净，rmmod lg_session 之后再等一秒也没有新消息。没修的模块在第一遍之后客体可能卡死，这时按 Ctrl-A 再按 X 退出 QEMU。

Fixed looks like this: three runs of the script each print stress-session: this run added 3200 bytes, expected 3200, the log is clean, and a second after rmmod lg_session there is still nothing new. With the module as handed out, the guest may hang after the first run; if it does, leave QEMU with Ctrl-A then X.

提示 1：从哪里看起Hint 1: where to start

日志很长，但 KASAN 只报告一次，而且它在最前面。用 dmesg | grep -n -m1 -A70 "BUG: KASAN" 只看第一份报告，后面的几百条 WARNING 都是它的后果。

The log is long, but KASAN reports once and its report comes first. dmesg | grep -n -m1 -A70 "BUG: KASAN" shows that first report alone; the hundreds of WARNINGs after it are its consequences.

提示 2：三个调用栈怎么读Hint 2: reading the three stacks

访问的栈顶在定时器代码里，那不是出错的地方。看 Freed by 这个栈里第一个属于模块的函数，再问：这个对象被释放的时候，内核里还有谁记着它的地址？

The top of the access stack is in the timer code, and that is not where the mistake is. Look at the first module function in the Freed by stack, and ask: at the moment this object was freed, who else in the kernel still remembered its address?

提示 3：往哪个方向修Hint 3: which way to fix it

struct lg_session 里嵌着一个会自己重新排队的 delayed_work。读 kernel/workqueue.c 里 cancel_delayed_work() 和 cancel_delayed_work_sync() 上方的注释，想清楚对一个会自己重新排队的工作项，两者的差别意味着什么。

struct lg_session embeds a delayed_work that re-queues itself. Read the comments above cancel_delayed_work() and cancel_delayed_work_sync() in kernel/workqueue.c and work out what their difference means for a work item that re-queues itself.

工单 2 · lg_route：两个命令一起卡住

Ticket 2 · lg_route: two commands hang together

lg_route 通过 debugfs 提供三个文件：写 config 切换路由表并把计数清零，写 lookup 记一次命中或未命中，读 stats 得到表名和计数。

lg_route offers three files through debugfs: writing config switches the routing table and resets the counters, writing lookup counts a hit or a miss, and reading stats returns the table name and the counters.

修好的样子：脚本连跑三遍，每遍都以 stress-route: done 结束，日志干净，rmmod lg_route 成功。脚本要放到后台跑：没修的模块会让它永远不返回，你需要 shell 来查看现场。

Fixed looks like this: three runs of the script each end with stress-route: done, the log is clean, and rmmod lg_route succeeds. Run the script in the background: with the module as handed out it never returns, and you need the shell to look at the scene.

提示 1：有两份证据Hint 1: there are two pieces of evidence

lockdep 的报告在脚本刚开始时就出现了，早于任何任务卡住。大约半分钟之后，hung task 检测再报告一次。echo w > /proc/sysrq-trigger 可以随时列出卡住的任务。先读 lockdep 那份。

The lockdep report appears right at the start of the script, before any task is stuck. About half a minute later the hung-task detector reports as well. echo w > /proc/sysrq-trigger lists the stuck tasks at any time. Read the lockdep report first.

提示 2：lockdep 报告怎么读Hint 2: reading the lockdep report

报告分三段：当前任务想拿哪把锁、已经拿着哪把锁（各带一个函数名和偏移）；然后是 -> #1 和 -> #0 两条依赖链，说明相反的顺序是在哪个函数里出现的；最后的 CPU0 / CPU1 表格把死锁的过程画了出来。把两个函数名抄下来，去源码里对照它们加锁的顺序。

The report has three parts: which lock the current task wants and which it already holds (each with a function name and an offset); then two dependency chains, -> #1 and -> #0, that say in which function the opposite order was taken; and finally a CPU0 / CPU1 table that draws the deadlock. Write the two function names down and compare the order in which each takes the locks in the source.

提示 3：往哪个方向修Hint 3: which way to fix it

验收标准 4 说统计行里的计数必须属于它旁边的表名，所以 lg_stats_show() 仍然要同时拿着两把锁，不能改成先放一把再拿另一把。剩下的自由度只有一个：顺序。

Acceptance criterion 4 says the counters in a stats line must belong to the table named beside them, so lg_stats_show() still has to hold both locks at once; dropping one before taking the other is not allowed. That leaves one degree of freedom: the order.

工单 3 · lg_stats：序号总是少一些

Ticket 3 · lg_stats: the sequence number always falls short

lg_stats 把每次 write() 当作一个包：分配下一个序号，保存包的内容，并累计包数和字节数。

lg_stats treats every write() as one packet: it hands out the next sequence number, keeps a copy of the packet and counts packets and bytes.

insmod lg_stats.ko
./stress-stats.sh

修好的样子：脚本连跑三遍，每遍都打印 stress-stats: packets 8000 bytes 128000 next_seq 8000，日志干净，rmmod lg_stats 成功。这张工单在调试内核上没有任何工具报告，只有错的数字；想让工具指出相互竞争的两处访问，需要另编一个 KCSAN 内核（提示 2）。

Fixed looks like this: three runs of the script each print stress-stats: packets 8000 bytes 128000 next_seq 8000, the log is clean, and rmmod lg_stats succeeds. 提示 1：不用工具能走多远Hint 1: how far you get without a tool

lg_stats_write() 只有十几行。对每个被读或被写的共享变量问一句：两个进程同时执行到这一行会怎样？特别注意「读出来」和「写回去」之间隔着什么。

lg_stats_write() is a dozen lines long. For every shared variable it reads or writes, ask: what happens when two processes reach this line at the same time? Pay special attention to what lies between a value being read and being written back.

提示 2：编一个 KCSAN 内核Hint 2: building a KCSAN kernel

KCSAN 也会报告内核其他地方的竞争，所以只看标题里带 lg_stats 的那些：dmesg | grep -A30 "KCSAN: data-race in lg_stats"。KCSAN 是抽样检测，跑一遍压力脚本可能一份报告都没有，这时再跑几遍。

KCSAN also reports races elsewhere in the kernel, so look only at the reports whose title names lg_stats: dmesg | grep -A30 "KCSAN: data-race in lg_stats". KCSAN samples, so one run of the stress script may produce no report at all; run it a few more times then.

提示 3：往哪个方向修Hint 3: which way to fix it

把三个计数器改成原子变量并不够：序号是先读出来、隔了一次 copy_from_user() 之后才写回去的，中间这一段也必须不被打断。另外，copy_from_user() 可能睡眠，这决定了你能用哪一种锁。

Turning the three counters into atomics is not enough: the sequence number is read, and written back only after a copy_from_user(), and that whole stretch must not be interleaved either. Also, copy_from_user() may sleep, which decides what kind of lock you can use.

工单 4 · lg_fw：可用内存越来越少

Ticket 4 · lg_fw: less and less free memory

lg_fw 是一个固件槽：一次 write() 是一个镜像，开头是 8 字节的头（魔数 LGFW 和载荷长度）。头校验通过的镜像替换槽里原有的那个。

lg_fw is a firmware slot: one write() is one image, starting with an 8-byte header (the magic LGFW and the payload length). An image whose header passes validation replaces the one in the slot.

insmod lg_fw.ko
./stress-fw.sh
sleep 6; echo scan > /sys/kernel/debug/kmemleak
sleep 2; echo scan > /sys/kernel/debug/kmemleak

Fixed looks like this: the growth of SUnreclaim that the script prints no longer keeps rising from round 2 to round 5, and the last line is stress-fw: image size 16, expected 16; after the two scans grep -c prints 0; the log is clean and rmmod lg_fw succeeds. The script starts dd five thousand times, which takes a few minutes under pure software emulation.

提示 1：为什么要看五轮Hint 1: why five rounds

第 1 轮的增量在修好之后也很大（验证运行里是 26 MB 左右），所以单看一个数字分不出好坏。要看的是趋势：没修时每一轮都再涨 8 MB 左右，修好之后第 2 轮起基本不动。

The growth in round 1 is large even with the fix (about 26 MB in the checking run), so a single number does not tell good from bad. What counts is the trend: as handed out, every round adds another 8 MB or so; with the fix, the figure hardly moves from round 2 on.

提示 2：kmemleak 的报告怎么读Hint 2: reading the kmemleak report

head -n 20 /sys/kernel/debug/kmemleak。每个条目是一个没有人再指向的对象：大小、分配它的进程、以及分配时的调用栈。栈里第一个属于模块的函数是分配点，不是 bug 所在：泄漏的 bug 是「某条路径上少了一次释放」，要你顺着分配点往下读代码去找。

head -n 20 /sys/kernel/debug/kmemleak. Every entry is an object that nothing points to any more: its size, the process that allocated it, and the stack at the allocation. The first module function in that stack is the allocation site, not the bug: a leak is “a free that is missing on some path”, and you find it by reading the code downwards from the allocation.

自测

Self-check

1. 一份 KASAN 报告的标题是 slab-use-after-free in enqueue_timer，访问的调用栈最上面几行全是定时器和工作队列的内核代码。bug 最可能在哪里？

1. A KASAN report is titled slab-use-after-free in enqueue_timer, and the top of the access stack is all kernel timer and workqueue code. Where is the bug most likely to be?

标题行给的是发现错误的位置。定时器代码只是照常遍历自己的链表，碰到了一块已经被释放的内存。要看 Freed by 栈里第一个属于你的函数，并问对象释放时还有谁记着它。The title line gives the place where the error was detected. The timer code was walking its own list as usual and ran into memory that had been freed. Look at the first function of yours in the Freed by stack, and ask who still remembered the object when it was freed.

2. lockdep 打印了 possible circular locking dependency detected，但压力脚本正常跑完，没有任何任务卡住。应该怎么处理？

2. lockdep printed possible circular locking dependency detected, yet the stress script ran to its end and no task was stuck. What do you do?

lockdep 不需要死锁真的发生，它从观察到的加锁顺序推出死锁可能发生。这正是它的价值：在工单 2 里，它的报告比 hung task 检测早了大约 30 秒，也早于任何用户能看到的症状。lockdep does not need the deadlock to happen; it infers from the lock orders it has observed that one can happen. That is its value: in ticket 2 its report came about 30 seconds before the hung-task detector, and before any symptom a user could see.

3. 你在一次已经打印过 KASAN 报告的启动里加载了修好的模块，压力脚本通过，没有新报告。这说明什么？

3. In a boot that has already printed a KASAN report, you load the fixed module; the stress script passes and there is no new report. What does that show?

KASAN 默认每次启动只报告第一处非法访问，而且第一份报告之后锁检查也被关掉了。热身的最后一步里，同一个越界写发生了两次，日志里只有一份报告。By default KASAN reports only the first invalid access of a boot, and lock checking is switched off after that first report as well. In the last step of the warm-up the same out-of-bounds write happened twice, and the log held one report.

4. kmemleak 的一个条目里，调用栈的第一个模块函数是 lg_fw_write+0x54。这个位置是什么？

4. In a kmemleak entry, the first module function in the stack is lg_fw_write+0x54. What is that place?

kmemleak 只记录分配时的调用栈。泄漏的 bug 是「某条路径上少了一次释放」，而少掉的代码不会出现在任何调用栈里，只能从分配点出发，逐个检查函数的出口。kmemleak records the stack at the allocation and nothing else. A leak is “a free that is missing on some path”, and code that is missing appears in no stack; you start from the allocation site and check every exit of the function.
