内核是攻击者的终极目标：一个内核内存破坏漏洞往往意味着整机沦陷。Apple 在硬件和内核两层叠加了大量缓解措施（PAC、PPL/SPTM、kalloc_type、代码签名），内核工程师写的每一行代码都要放在这套防御体系里考量。

The kernel is the attacker’s ultimate target: a single kernel memory-corruption bug often means the whole machine is compromised. Apple stacks a large number of mitigations across both the hardware and the kernel (PAC, PPL/SPTM, kalloc_type, code signing), and every line of code a kernel engineer writes has to be weighed against this defensive system.

核心概念

Core concepts

1. 内核威胁模型

1. The kernel threat model

威胁模型回答三个问题：攻击者从哪里开始（通常是一个低权限进程——沙箱里的 App、浏览器渲染进程——或者一段送进内核的外部数据）、能碰到哪些内核代码（攻击面）、想达到什么（提权、逃出沙箱、持久化）。Linux 的典型攻击面：几百个系统调用、设备文件上的 ioctl、netlink、网络协议栈、挂载不可信的文件系统镜像、io_uring、eBPF（非特权 eBPF 通常由 kernel.unprivileged_bpf_disabled 关闭）。XNU 多了两类：Mach trap 与发往内核对象的 Mach 消息（MIG 接口），以及 IOKit 用户客户端——用户态 IOServiceOpen 后通过 IOConnectCallMethod 进到驱动的 IOUserClient::externalMethod，每个驱动都是一块新攻击面。Sandbox 的意义正在于缩小一个进程能够到的攻击面。

A threat model answers three questions: where the attacker starts (usually a low-privilege process — a sandboxed app, a browser renderer process — or a piece of external data fed into the kernel), which kernel code it can reach (the attack surface), and what it wants to achieve (privilege escalation, sandbox escape, persistence). The typical Linux attack surface: several hundred system calls, ioctl on device files, netlink, the network stack, mounting untrusted filesystem images, io_uring, and eBPF (unprivileged eBPF is usually disabled by kernel.unprivileged_bpf_disabled). XNU adds two more kinds: Mach traps and Mach messages sent to kernel objects (MIG interfaces), and IOKit user clients — after IOServiceOpen in user space, IOConnectCallMethod reaches the driver’s IOUserClient::externalMethod, so every driver is a new piece of attack surface. The whole point of the sandbox is to shrink the attack surface a process can reach.

典型利用链：漏洞（越界读写、释放后使用 UAF、竞态、类型混淆、逻辑错误）→ 原语（信息泄露、有限的写 → 任意地址读写）→ 绕过缓解 → 达成目标（例如改掉自己进程的凭证：Linux 的 struct cred，XNU 挂在 struct proc_ro 里的 p_ucred）。缓解措施的设计思路就是在这条链的每一环上加成本：让漏洞更难出现（类型安全、隔离）、更难变成原语（堆加固）、原语更难用（KASLR、PAC、PPL/SPTM）。XNU 自己的 doc/allocators/read-only.md 写得很直白：由于 PAC 等控制流防御，今天的攻击者更倾向只改数据（data-only），所以防线也在向「保护关键数据」移动。延伸阅读：《Modern Operating Systems》第 9 章「安全」；《Operating Systems: Three Easy Pieces》第 53–55 章（安全导论、认证、访问控制）。

A typical exploit chain: bug (out-of-bounds read/write, use-after-free (UAF), race, type confusion, logic error) → primitive (information leak, limited write → arbitrary read/write) → mitigation bypass → goal (for example, overwriting your own process’s credentials: struct cred on Linux, p_ucred in struct proc_ro on XNU). Mitigations are designed to add cost at every link of this chain: make bugs less likely to exist (type safety, isolation), harder to turn into primitives (heap hardening), and primitives harder to use (KASLR, PAC, PPL/SPTM). XNU’s own doc/allocators/read-only.md says it plainly: because of control-flow defences such as PAC, today’s attackers prefer to modify only data (data-only), so the defences are moving towards “protecting critical data” as well. Further reading: Modern Operating Systems, Chapter 9, “Security”; Operating Systems: Three Easy Pieces, Chapters 53–55 (introduction to security, authentication, access control).

2. KASLR 与 W^X / PXN / PAN

2. KASLR and W^X / PXN / PAN

KASLR 让内核镜像每次启动加载到随机虚拟地址，攻击者写死的地址全部失效，从而必须先拿到一个信息泄露。Linux arm64（CONFIG_RANDOMIZE_BASE）的种子来自设备树 /chosen/kaslr-seed，没有时用 CPU 的 RNDR 指令（FEAT_RNG），都没有就打印 KASLR disabled due to lack of seed（arch/arm64/kernel/kaslr.c）；nokaslr 关闭它；panic 时打印 Kernel Offset。配套的是「不泄露地址」：kptr_restrict、%pK、默认对 %p 打印的指针做哈希、dmesg_restrict。用户态 ASLR 由 /proc/sys/kernel/randomize_va_space 控制：0 关闭，1 随机化 mmap 基址、栈和 vDSO，2 再加上 brk 堆。XNU 的内核整体滑动一个 kernel slide（vm_kernel_slide）；内核往外报地址时用 VM_KERNEL_UNSLIDE / VM_KERNEL_ADDRPERM 去滑动或置换（osfmk/mach/vm_param.h）；查询 slide 的 kas_info() 系统调用要求 root，还要再过一道 MACF 检查（bsd/vm/vm_unix.c）。

KASLR loads the kernel image at a random virtual address on every boot, so every address the attacker has hard-coded becomes invalid and they must first obtain an information leak. On Linux arm64 (CONFIG_RANDOMIZE_BASE) the seed comes from the device tree’s /chosen/kaslr-seed; without one, the CPU’s RNDR instruction (FEAT_RNG) is used, and if neither exists the kernel prints KASLR disabled due to lack of seed (arch/arm64/kernel/kaslr.c); nokaslr turns it off; a panic prints Kernel Offset. It goes together with “do not leak addresses”: kptr_restrict, %pK, hashing pointers printed with %p by default, and dmesg_restrict. User-space ASLR is controlled by /proc/sys/kernel/randomize_va_space: 0 is off, 1 randomises the mmap base, the stack and the vDSO, and 2 adds the brk heap. XNU slides the whole kernel by a kernel slide (vm_kernel_slide); when the kernel reports addresses to the outside, it unslides or permutes them with VM_KERNEL_UNSLIDE / VM_KERNEL_ADDRPERM (osfmk/mach/vm_param.h); the kas_info() system call, which queries the slide, requires root and must also pass a MACF check (bsd/vm/vm_unix.c).

W^X：任何一页要么可写、要么可执行，不能同时。Linux arm64 的内核代码和只读数据用 CONFIG_STRICT_KERNEL_RWX（arm64 上默认强制）、rodata=full 保护——但这些是内核自己设的页表权限，拿到任意写的攻击者理论上可以改回去。Apple 把这一步交给硬件：KIP（Kernel Integrity Protection，源码里的 KTRR/CTRR，如 osfmk/arm64/amcc_rorgn.h）在内核初始化完成后由内存控制器锁定内核代码区域，此后连内核自己也改不了。

W^X: any page is either writable or executable, never both. On Linux arm64, kernel code and read-only data are protected with CONFIG_STRICT_KERNEL_RWX (enforced by default on arm64) and rodata=full — but these are page-table permissions the kernel sets itself, and an attacker with arbitrary write could in theory change them back. Apple hands this step to the hardware: with KIP (Kernel Integrity Protection; KTRR/CTRR in the source, e.g. osfmk/arm64/amcc_rorgn.h) the memory controller locks the kernel code region once kernel initialisation is complete, and from then on not even the kernel itself can change it.

PXN（Phase 2 讲过的描述符第 53 位）让内核不能执行用户页——挡住「把 shellcode 放在用户内存，再让内核跳过去」的 ret2usr。PAN（Privileged Access Never，ARMv8.1，PSTATE.PAN）更进一步：内核用普通 load/store 访问用户可访问的页直接触发 permission fault，挡住「在用户内存里伪造内核对象，让内核去读」。内核只能经受控的拷贝路径访问用户内存：Linux 的 copy_from_user 一类（arm64 用 LDTR/STTR 这类「按 EL0 权限访问」的指令，或在短窗口内临时放开 PAN，大致路径）；XNU 的 copyin/copyout（osfmk/arm64/copyio.c）。Linux 相关选项：CONFIG_ARM64_PAN，老 CPU 上用切换 TTBR0 模拟的 CONFIG_ARM64_SW_TTBR0_PAN，以及让「用户只执行页」也受 PAN 约束的 CONFIG_ARM64_EPAN。

PXN (bit 53 of the descriptor, covered in Phase 2) stops the kernel from executing user pages — blocking ret2usr, “put shellcode in user memory and make the kernel jump to it”. PAN (Privileged Access Never, ARMv8.1, PSTATE.PAN) goes further: an ordinary kernel load/store to a user-accessible page raises a permission fault directly, blocking “forge a kernel object in user memory and get the kernel to read it”. The kernel can reach user memory only through controlled copy paths: Linux’s copy_from_user family (on arm64 it uses instructions such as LDTR/STTR that “access with EL0 permissions”, or lifts PAN temporarily for a short window; approximate path) and XNU’s copyin/copyout (osfmk/arm64/copyio.c). The related Linux options: CONFIG_ARM64_PAN; CONFIG_ARM64_SW_TTBR0_PAN, which emulates it on older CPUs by switching TTBR0; and CONFIG_ARM64_EPAN, which makes “user execute-only pages” subject to PAN as well.

3. stack canary 与 CFI

3. Stack canaries and CFI

Stack canary：编译器在有局部数组的函数栈帧里、返回地址之前放一个随机值，返回前检查；被连续溢出覆盖就调用 __stack_chk_fail 直接终止。Linux：CONFIG_STACKPROTECTOR / _STRONG，arm64 还有每任务不同 canary 的 CONFIG_STACKPROTECTOR_PER_TASK。XNU 同样有 __stack_chk_guard（libkern/stack_protector.c）。canary 只防连续溢出覆盖到返回地址；任意地址写、或者能先泄露 canary 时就挡不住。

Stack canary: in the stack frame of a function with local arrays, the compiler places a random value before the return address and checks it before returning; if a contiguous overflow has overwritten it, __stack_chk_fail is called and execution terminates immediately. Linux: CONFIG_STACKPROTECTOR / _STRONG; arm64 also has CONFIG_STACKPROTECTOR_PER_TASK, with a different canary per task. XNU likewise has __stack_chk_guard (libkern/stack_protector.c). A canary only defends against a contiguous overflow reaching the return address; it cannot stop an arbitrary-address write, or an attacker who can leak the canary first.

CFI（控制流完整性）把间接跳转限制在「合法目标」：后向边（返回）由 PAC（下一节）或 Linux 的 shadow call stack（CONFIG_SHADOW_CALL_STACK，返回地址另存一份在 x18 指向的隐藏栈）保护；前向边（函数指针调用）由 Clang kCFI（Linux CONFIG_CFI，旧名 CONFIG_CFI_CLANG：调用前检查目标函数前面的类型哈希）和 ARM BTI（Branch Target Identification，CONFIG_ARM64_BTI_KERNEL：间接跳转只能落在 bti 指令上，页表里的 GP 位开启检查）保护。XNU 在 arm64e 上主要靠 PAC 签名的函数指针和 vtable 指针实现前向边保护。延伸阅读：《Computer Systems: A Programmer's Perspective》第 3 章中缓冲区溢出及其对抗（栈随机化、栈保护、不可执行栈）相关小节。

CFI (control-flow integrity) restricts indirect branches to “legitimate targets”: the backward edge (returns) is protected by PAC (next section) or by Linux’s shadow call stack (CONFIG_SHADOW_CALL_STACK, which keeps a second copy of each return address on a hidden stack pointed to by x18); the forward edge (function-pointer calls) is protected by Clang kCFI (Linux CONFIG_CFI, formerly CONFIG_CFI_CLANG: before the call, it checks a type hash placed in front of the target function) and by ARM BTI (Branch Target Identification, CONFIG_ARM64_BTI_KERNEL: an indirect branch may land only on a bti instruction, with the check enabled by the GP bit in the page table). On arm64e, XNU relies mainly on PAC-signed function pointers and vtable pointers for forward-edge protection. Further reading: Computer Systems: A Programmer's Perspective, the sections of Chapter 3 on buffer overflows and how to thwart them (stack randomisation, stack protection, non-executable stacks).

4. ARM Pointer Authentication（PAC）

4. ARM Pointer Authentication (PAC)

ARMv8.3 的 FEAT_PAuth 增加了 5 把 128 位密钥（APIAKey、APIBKey、APDAKey、APDBKey、APGAKey，各分 …Lo_EL1/…Hi_EL1 两个系统寄存器；EL0 读不到）和一组指令：pacia Xd, Xn 用 IA 密钥、以 Xn 为修饰值（modifier）给 Xd 里的指针算出一个短 MAC——PAC——写进指针未用于寻址的高位；autia 用同样的密钥和修饰值重算并比较，对了就去掉 PAC 恢复原指针；xpaci/xpacd 只去掉不校验；paciasp/pacibsp 是「对 LR、以 SP 为修饰值」的简写；retaa/retab、blraa 把校验与跳转合成一条。PAC 位数取决于虚拟地址宽度和 TBI：48 位 VA 且开启 TBI 时只有 [54:48] 7 位（bit 55 用来选 TTBR），关闭 TBI 时高字节也可用；所以 PAC 是概率防护，靠的是「猜错一次就崩溃」。

FEAT_PAuth in ARMv8.3 adds five 128-bit keys (APIAKey, APIBKey, APDAKey, APDBKey, APGAKey, each split across two system registers, …Lo_EL1/…Hi_EL1; EL0 cannot read them) and a set of instructions: pacia Xd, Xn uses the IA key, with Xn as the modifier, to compute a short MAC — the PAC — over the pointer in Xd, and writes it into the pointer’s high bits that are not used for addressing; autia recomputes it with the same key and modifier and compares, and on a match removes the PAC to restore the original pointer; xpaci/xpacd only strip it, without checking; paciasp/pacibsp are shorthand for “sign LR, with SP as the modifier”; retaa/retab and blraa combine verification and branch into one instruction. The number of PAC bits depends on the virtual-address width and on TBI: with a 48-bit VA and TBI enabled there are only 7 bits, [54:48] (bit 55 selects the TTBR); with TBI disabled the top byte can be used as well. So PAC is a probabilistic defence that relies on “one wrong guess means a crash”.

校验失败时：有 FEAT_FPAC 的 CPU 让 aut* 指令立即产生异常（ESR_ELx.EC = 0x1C）——Linux 用户态收到 SIGILL（do_el0_fpac），内核态 die("Oops - FPAC")（do_el1_fpac，arch/arm64/kernel/traps.c）；XNU 走 sleh.c 里的 handle_pac_fail。没有 FPAC 时，aut* 把错误码写进高位使指针变成非规范地址（FEAT_PAuth 行为；FEAT_PAuth2 下改为把重算的 PAC 异或进高位，效果同样通常是非规范地址），等到真正用它跳转或访存时才触发 translation fault。arm64e 编译器还会在部分 aut 之后自己插入检查，失败时执行 brk（XNU 的 ptrauth_handle_brk_trap 负责把它报告成 PAC 失败）。

When verification fails: on a CPU with FEAT_FPAC, the aut* instruction raises an exception immediately (ESR_ELx.EC = 0x1C) — on Linux, user space receives SIGILL (do_el0_fpac) and kernel mode hits die("Oops - FPAC") (do_el1_fpac, arch/arm64/kernel/traps.c); XNU goes to handle_pac_fail in sleh.c. Without FPAC, aut* writes an error code into the high bits so that the pointer becomes a non-canonical address (FEAT_PAuth behaviour; under FEAT_PAuth2 it instead XORs the recomputed PAC into the high bits, which likewise usually yields a non-canonical address), and a translation fault is raised only when the pointer is actually used for a branch or a memory access. The arm64e compiler also inserts its own check after some aut instructions and executes brk on failure (XNU’s ptrauth_handle_brk_trap reports it as a PAC failure).

Linux：CONFIG_ARM64_PTR_AUTH 给用户态启用（每个进程 exec 时随机生成密钥，/proc/cpuinfo 里能看到 paca pacg），CONFIG_ARM64_PTR_AUTH_KERNEL 用 -mbranch-protection=pac-ret（与 BTI 同开时 pac-ret+bti）编译内核，保护返回地址，用 IA 密钥。Apple arm64e 是全面使用：返回地址用 IB 密钥（XNU 汇编宏 ARM64_STACK_PROLOG/EPILOG 就是 pacibsp/retab，osfmk/arm64/asm.h），C 函数指针用 IA，数据指针用 DA/DB，C++ vtable 指针、ObjC 关键指针等再混入「存放地址 + 类型常量」做修饰值（address diversity），让签名不能从一个位置挪到另一个位置复用。ptrauth.h 里 ptrauth_key_process_independent_code 就是 IA 的别名——A 类密钥跨进程共享（共享缓存里的指针才能通用），B 类按进程区分。第三方 arm64e 二进制至今仍属「预览 ABI」：能编译，但正常系统默认不让它运行（见 Lab B）。

Linux: CONFIG_ARM64_PTR_AUTH enables it for user space (keys are generated randomly for each process at exec, and paca pacg shows up in /proc/cpuinfo); CONFIG_ARM64_PTR_AUTH_KERNEL builds the kernel with -mbranch-protection=pac-ret (pac-ret+bti when BTI is enabled too) to protect return addresses, using the IA key. Apple arm64e uses it throughout: return addresses use the IB key (the XNU assembly macros ARM64_STACK_PROLOG/EPILOG are exactly pacibsp/retab, osfmk/arm64/asm.h), C function pointers use IA, data pointers use DA/DB, and C++ vtable pointers, key ObjC pointers and so on also mix “storage address + type constant” into the modifier (address diversity), so that a signature cannot be moved from one location and reused at another. In ptrauth.h, ptrauth_key_process_independent_code is simply an alias for IA — the A keys are shared across processes (which is what lets pointers in the shared cache work everywhere), while the B keys differ per process. Third-party arm64e binaries are still a “preview ABI” today: they compile, but a normal system does not let them run by default (see Lab B).

5. PPL 与 SPTM

5. PPL and SPTM

前面所有防线都有一个共同的弱点：页表在内核手里。一旦攻击者拿到内核任意读写，就可以直接改页表——把代码页改成可写、把任意物理内存映射进来、给未签名代码加上可执行权限。Apple 的回答是把「改页表」这件事从内核里拿走（以下据 Apple Platform Security Guide「Operating system integrity」）：

All of the defences above share one weakness: the page tables are in the kernel’s hands. Once an attacker has arbitrary kernel read/write, they can modify the page tables directly — make code pages writable, map in arbitrary physical memory, grant execute permission to unsigned code. Apple’s answer is to take “modifying the page tables” away from the kernel (the following is based on the “Operating system integrity” section of the Apple Platform Security Guide):

  • Fast Permission Restrictions（A11 起，也称 APRR 寄存器）：一个按线程快速收紧内存权限的 CPU 寄存器，不必改页表、刷 TLB。
  • Fast Permission Restrictions (from the A11; also called the APRR registers): a CPU register that quickly tightens memory permissions per thread, without changing the page tables or flushing the TLB.
  • PPL（Page Protection Layer）：建立在 KIP 和 Fast Permission Restrictions 之上的一小段受保护代码，只有 PPL 能修改页表和存放已签名用户代码的页。Apple 指南说明 PPL「签名校验后代码不可改」这一层保护只在 iOS、iPadOS、visionOS、watchOS 上提供，macOS 因为允许运行任意代码而不提供。XNU 源码里与之相关的是 osfmk/arm/pmap/pmap_ppl_interface.c 和 XNU_MONITOR 宏。
  • PPL (Page Protection Layer): a small piece of protected code built on KIP and Fast Permission Restrictions; only PPL can modify the page tables and the pages that hold signed user code. Apple’s guide states that PPL’s layer of protection — “code cannot be modified after signature verification” — is provided only on iOS, iPadOS, visionOS and watchOS, and not on macOS, because macOS allows arbitrary code to run. The related XNU source is osfmk/arm/pmap/pmap_ppl_interface.c and the XNU_MONITOR macro.
  • SPTM + TXM（A15 及以后、M2 及以后的芯片，替代 PPL；iOS、iPadOS、macOS、visionOS）：Secure Page Table Monitor 运行在比内核更高的特权级，管理用户与内核两边的页表；Trusted Execution Monitor 权限更低，负责实际执行「什么代码可以运行」的策略。两者分开，是为了让 TXM 被攻破也不自动等于 SPTM 被绕过。XNU 源码里能看到 CONFIG_SPTM 宏，构建配置里还有一个 SPTM 内核变体。
  • SPTM + TXM (A15 and later and M2 and later chips, replacing PPL; iOS, iPadOS, macOS, visionOS): the Secure Page Table Monitor runs at a higher privilege level than the kernel and manages the page tables of both user space and the kernel; the Trusted Execution Monitor has lower privilege and actually enforces the policy on “which code may run”. They are kept separate so that compromising TXM does not automatically mean bypassing SPTM. In the XNU source you can see the CONFIG_SPTM macro, and the build configuration also has an SPTM kernel variant.

Linux 主线没有直接对应物：内核始终可以写自己的页表。最接近的是在内核之下放一个 hypervisor 来保护页表和关键数据——一些手机厂商的方案（例如三星 RKP）就是这样做的（推断：这类方案多为厂商私有，细节不公开）；Android 的 pKVM 则是用 hypervisor 把客户虚拟机的内存与宿主内核隔离，目标不同但思路相同——更高特权级 + 更小的可信代码。

Mainline Linux has no direct counterpart: the kernel can always write its own page tables. The closest thing is to put a hypervisor below the kernel to protect the page tables and critical data — some phone vendors’ schemes (for example Samsung RKP) do exactly this (inference: such schemes are mostly vendor-proprietary and their details are not public); Android’s pKVM, by contrast, uses a hypervisor to isolate guest virtual machines’ memory from the host kernel — a different goal, but the same idea: a higher privilege level + a smaller body of trusted code.

6. kalloc_type 与堆隔离

6. kalloc_type and heap isolation

UAF 利用的经典步骤是「占位」：对象 A 被释放后，攻击者让内核在同一块内存上分配一个内容可控的对象 B，从此持有 A 悬空指针的代码会把 B 当成 A 来用（类型混淆）。通用分配器按大小分档，任何大小相近的对象都能互相占位，这正是攻击者需要的。

The classic step in exploiting a UAF is “reclaiming” the freed memory: after object A is freed, the attacker gets the kernel to allocate an object B with controlled contents in the same memory, and from then on code holding the dangling pointer to A uses B as if it were A (type confusion). A general-purpose allocator groups objects by size class, so any objects of similar size can reclaim each other’s memory — exactly what the attacker needs.

XNU kalloc_type（iOS 15 / macOS 12 起；osfmk/kern/kalloc.h 的 kalloc_type(...)、KALLOC_TYPE_DEFINE）：编译器为每个类型生成签名，分配器据此把不同类型的对象分到不同的 zone，纯数据（不含指针）的走单独的 kalloc_data；加上 zone 的虚拟地址不在不同 zone 之间复用（大致机制，详见 Apple 的 kalloc_type 博文），跨类型占位就变得非常难。更敏感的数据放进只读 zone：只能通过 zalloc_ro_mut 修改（doc/allocators/read-only.md），进程凭证就在 struct proc_ro 里。最新一层是 MIE（Memory Integrity Enforcement，A19 / M5 及以后）：在这些安全分配器之上，加上同步模式的 EMTE（增强内存标签扩展）——每块内存和指针各带一个标签，标签不符的访问当场被硬件拦下。

XNU kalloc_type (from iOS 15 / macOS 12; kalloc_type(...) and KALLOC_TYPE_DEFINE in osfmk/kern/kalloc.h): the compiler generates a signature for each type, and the allocator uses it to put objects of different types in different zones, with pure data (containing no pointers) going to a separate kalloc_data; combined with zone virtual addresses not being reused across zones (approximate mechanism; see Apple’s kalloc_type blog post for details), cross-type reclaiming becomes very hard. More sensitive data goes into read-only zones: it can be modified only through zalloc_ro_mut (doc/allocators/read-only.md), and process credentials live in struct proc_ro. The newest layer is MIE (Memory Integrity Enforcement, A19 / M5 and later): on top of these secure allocators it adds EMTE (Enhanced Memory Tagging Extension) in synchronous mode — every block of memory and every pointer carries a tag, and an access with a mismatched tag is stopped by the hardware on the spot.

Linux 的 slab 加固是一组选项：CONFIG_SLAB_FREELIST_HARDENED（混淆空闲链表指针）、CONFIG_SLAB_FREELIST_RANDOM（随机化空闲顺序）、init_on_free/init_on_alloc（释放/分配时清零）、CONFIG_SLAB_BUCKETS（6.11 起，把大小由用户控制的分配放进独立的桶）、以及 6.6 引入的 CONFIG_RANDOM_KMALLOC_CACHES（按调用点 + 每次启动的随机种子，从 16 份 kmalloc 缓存里选一份）。截至 2026-10 的主线开发树（v7.3）把后者改名为 CONFIG_KMALLOC_PARTITION_CACHES，并新增 KMALLOC_PARTITION_TYPED 模式：编译器支持 Clang allocation token 时按分配的类型选缓存——这是 Linux 目前最接近 kalloc_type 的机制。硬件标签方面对应的是 arm64 MTE 与 CONFIG_KASAN_HW_TAGS。

Linux slab hardening is a set of options: CONFIG_SLAB_FREELIST_HARDENED (obfuscates freelist pointers), CONFIG_SLAB_FREELIST_RANDOM (randomises the free order), init_on_free/init_on_alloc (zero memory on free / allocation), CONFIG_SLAB_BUCKETS (from 6.11; puts allocations whose size is controlled by user space into separate buckets), and CONFIG_RANDOM_KMALLOC_CACHES, introduced in 6.6 (picks one of 16 copies of the kmalloc caches by call site + a per-boot random seed). As of 2026-10, the mainline development tree (v7.3) renames the latter to CONFIG_KMALLOC_PARTITION_CACHES and adds a KMALLOC_PARTITION_TYPED mode: when the compiler supports Clang allocation tokens, the cache is picked by the allocated type — the closest Linux currently comes to kalloc_type. For hardware tagging, the counterparts are arm64 MTE and CONFIG_KASAN_HW_TAGS.

7. 强制访问控制与代码签名

7. Mandatory access control and code signing

Linux LSM：内核在敏感操作处调用 security_* 钩子（例如 security_file_open，钩子清单在 include/linux/lsm_hook_defs.h），由启用的安全模块决定放行与否：SELinux（基于标签的完整 MAC）、AppArmor（基于路径的配置文件）、Landlock（非特权进程给自己加限制）、Yama（限制 ptrace）、lockdown（限制连 root 也不能做的事，如写 /dev/mem、加载未签名模块）。完整性一侧有模块签名（CONFIG_MODULE_SIG）、IMA/EVM、dm-verity。

Linux LSM: at sensitive operations the kernel calls security_* hooks (for example security_file_open; the hook list is in include/linux/lsm_hook_defs.h), and the enabled security modules decide whether to allow the operation: SELinux (full label-based MAC), AppArmor (path-based profiles), Landlock (unprivileged processes restricting themselves), Yama (restricts ptrace), and lockdown (restricts things that not even root may do, such as writing /dev/mem or loading unsigned modules). On the integrity side there are module signing (CONFIG_MODULE_SIG), IMA/EVM and dm-verity.

XNU MACF（源自 TrustedBSD）：内核在同类位置调用 mac_*_check_*（如 mac_vnode_check_open，security/mac_vfs.c；IOKit 有 mac_iokit_check_open），策略模块用 mac_policy_register 注册（security/mac_base.c）。主要策略是两个内核扩展：Sandbox（Seatbelt：按配置文件限制文件、Mach 服务查找、IOKit 打开等，Lab B 能在内核日志里看到它的 deny 记录）和 AMFI（AppleMobileFileIntegrity：执行时校验代码签名与 entitlements，配合用户态 amfid；内核侧代码签名状态在 bsd/kern/kern_cs.c、ubc_subr.c）。SIP（System Integrity Protection）是「连 root 也不行」的那一层：保护系统文件、受保护进程、内核扩展加载等，检查点是 csr_check()（bsd/kern/kern_csr.c），只能在 recoveryOS 里修改。macOS 11 起的系统卷还是签名封存的只读快照（SSV），在 Apple Silicon 上 SPTM/TXM 也参与到「哪些代码可以执行」的决策中。延伸阅读：《*OS Internals》Vol. III 的 MACF、代码签名、Sandbox 相关章节；《The Design and Implementation of the FreeBSD Operating System》安全相关章节（MACF 源自 TrustedBSD）。

XNU MACF (derived from TrustedBSD): at the same kinds of places the kernel calls mac_*_check_* (such as mac_vnode_check_open, security/mac_vfs.c; IOKit has mac_iokit_check_open), and policy modules register with mac_policy_register (security/mac_base.c). The main policies are two kernel extensions: Sandbox (Seatbelt: restricts files, Mach service lookups, IOKit opens and so on according to a profile; in Lab B you can see its deny records in the kernel log) and AMFI (AppleMobileFileIntegrity: verifies code signatures and entitlements at exec time, together with the user-space amfid; the kernel-side code-signing state is in bsd/kern/kern_cs.c and ubc_subr.c). SIP (System Integrity Protection) is the “not even root” layer: it protects system files, protected processes, kernel-extension loading and so on; its check point is csr_check() (bsd/kern/kern_csr.c), and it can be changed only in recoveryOS. Since macOS 11 the system volume has also been a signed, sealed, read-only snapshot (SSV), and on Apple Silicon SPTM/TXM also take part in deciding “which code may execute”. Further reading: the MACF, code-signing and Sandbox chapters of *OS Internals Vol. III; the security chapters of The Design and Implementation of the FreeBSD Operating System (MACF derives from TrustedBSD).

8. 读 CVE 分析

8. Reading CVE analyses

读任何一篇内核漏洞分析都填同一张表：① 根因（哪一行代码、属于哪类错误：越界、UAF、竞态、未初始化、逻辑）；② 可达性（从什么权限、经哪个接口触发，沙箱里能否够到）；③ 原语（漏洞直接给了什么：读/写多少字节、能否重复）；④ 缓解（哪些措施让利用更难，作者怎样绕过——或者为什么根本不需要绕过）；⑤ 修复（补丁改了什么，是只修这一处还是消灭了一类问题）。

For any kernel vulnerability analysis you read, fill in the same table: ① Root cause (which line of code, and which class of error: out-of-bounds, UAF, race, uninitialised, logic); ② Reachability (from what privilege and through which interface it is triggered, and whether it can be reached from inside a sandbox); ③ Primitive (what the bug gives directly: how many bytes of read/write, and whether it can be repeated); ④ Mitigations (which measures make exploitation harder and how the author got around them — or why no bypass was needed at all); ⑤ Fix (what the patch changed, and whether it fixes just this one spot or eliminates a whole class of problems).

两个好练习：Dirty Pipe（CVE-2022-0847，Linux）——管道缓冲区的 flags 字段在某条路径上未初始化，残留的「可合并」标志让写入落进只读文件的页缓存；它是逻辑错误、不涉及内存破坏，KASLR、PAN、CFI 全都帮不上，修复只是把 flags 初始化——说明缓解措施不能替代正确的代码。XNU 一侧读 Project Zero 博客上 Ian Beer 等人的 iOS 内核分析：注意它们怎样因为 PAC 而走向 data-only 利用，以及 Apple 随后在 kalloc_type、只读 zone、SPTM 上的应对。

Two good exercises: Dirty Pipe (CVE-2022-0847, Linux) — the flags field of a pipe buffer was left uninitialised on one path, and a leftover “can merge” flag let writes land in the page cache of a read-only file; it is a logic error with no memory corruption involved, so KASLR, PAN and CFI are all of no help, and the fix was simply to initialise the flags — which shows that mitigations cannot replace correct code. On the XNU side, read the iOS kernel analyses by Ian Beer and others on the Project Zero blog: notice how PAC pushed them towards data-only exploitation, and how Apple then responded with kalloc_type, read-only zones and SPTM.

Linux 版直接用 PAC 指令（内联汇编），存为 pac_linux.c：

The Linux version uses the PAC instructions directly (inline assembly); save it as pac_linux.c:

#include <stdio.h>
#include <stdint.h>

static inline uint64_t pacia(uint64_t p, uint64_t mod) { __asm__ volatile("pacia %0, %1" : "+r"(p) : "r"(mod)); return p; }
static inline uint64_t autia(uint64_t p, uint64_t mod) { __asm__ volatile("autia %0, %1" : "+r"(p) : "r"(mod)); return p; }
static inline uint64_t xpaci(uint64_t p) { __asm__ volatile("xpaci %0" : "+r"(p)); return p; }

static void target(void) { puts("target()"); }

int main(void) {
  uint64_t fn = (uint64_t)&target, mod = 0x1234;
  uint64_t s = pacia(fn, mod);
  printf("raw    = %#018llx\n", (unsigned long long)fn);
  printf("signed = %#018llx\n", (unsigned long long)s);
  printf("strip  = %#018llx\n", (unsigned long long)xpaci(s));
  printf("auth   = %#018llx (== raw)\n", (unsigned long long)autia(s, mod));
  fflush(stdout);
  uint64_t r = autia(s ^ 0x10, mod);   /* 篡改后校验：有 FEAT_FPAC 时这里直接 SIGILL */
  printf("auth(tampered) = %#018llx  （无 FPAC：指针被毒化，不要调用它）\n", (unsigned long long)r);
  return 0;
}

macOS 版用编译器的 <ptrauth.h> 内建函数，存为 pac_demo.c：

#include <stdio.h>
#include <stdint.h>
#include <ptrauth.h>

static int secret = 42;

int main(void) {
  int *p = &secret;
  /* 用 DA 密钥、以 0x1234 作 discriminator 给数据指针签名 */

自测

Self-check

1. ARM PAC 的签名（PAC 值）存放在哪里？

1. Where is the ARM PAC signature (the PAC value) stored?

64 位虚拟地址并不使用全部 64 位，PAC 利用这些高位存放签名；autia 等指令校验成功会去掉签名，失败则触发异常（FEAT_FPAC）或使指针失效。专用寄存器里放的是密钥，不是签名。A 64-bit virtual address does not use all 64 bits, and PAC uses those high bits to hold the signature; instructions such as autia remove the signature when verification succeeds, and on failure raise an exception (FEAT_FPAC) or invalidate the pointer. The dedicated registers hold the keys, not the signatures.

2. PAN（Privileged Access Never）开启后阻止的是什么？

2. What does PAN (Privileged Access Never) block once it is enabled?

PAN 阻止 EL1 直接读写 EL0 可访问的页面，内核只能经由 copyin/copy_from_user 等受控路径访问；禁止内核执行用户页的是 PXN；用户态访问内核内存本来就被页表的 AP 位禁止。PAN stops EL1 from directly reading or writing pages accessible to EL0, so the kernel can reach them only through controlled paths such as copyin/copy_from_user; it is PXN that stops the kernel from executing user pages; user-mode access to kernel memory is already forbidden by the AP bits of the page table.

3. 为什么 Apple 要用 PPL / SPTM 把页表修改从内核中剥离出来？

3. Why does Apple use PPL / SPTM to take page-table modification out of the kernel?

KASLR、PXN、PAC 都假设攻击者还不能随意改页表。PPL（A12–A14、M1）在内核内部建立受保护区域；SPTM（A15、M2 及以后）运行在比内核更高的特权级，与 TXM 配合决定页表与可执行代码。Linux 主线没有对应机制。KASLR, PXN and PAC all assume the attacker cannot yet modify the page tables at will. PPL (A12–A14, M1) sets up a protected region inside the kernel; SPTM (A15, M2 and later) runs at a higher privilege level than the kernel and, together with TXM, decides on the page tables and executable code. Mainline Linux has no equivalent mechanism.

4. kalloc_type 主要让哪一种利用步骤变难？

4. Which exploitation step does kalloc_type mainly make harder?

kalloc_type 按类型签名把对象分进不同 zone，纯数据走 kalloc_data，跨类型占位因此变得很难。返回地址由 canary / PAC 保护；KASLR 侧信道是另一类问题。Linux 最接近的是 KMALLOC_PARTITION_TYPED（编译器支持时按类型选缓存）。kalloc_type uses type signatures to split objects into different zones, with pure data going to kalloc_data, so cross-type reclaiming becomes very hard. Return addresses are protected by canaries / PAC; KASLR side channels are a different class of problem. The closest Linux mechanism is KMALLOC_PARTITION_TYPED (which picks the cache by type when the compiler supports it).
