Learning Garden Kernel Engineering Phase 7

Phase 7 / 9 · 约 1–2 周

Security & Hardening 安全与加固：KASLR、PAN/PXN、PAC、PPL/SPTM、sandbox、code signing

内核是攻击者的终极目标：一个内核内存破坏漏洞往往意味着整机沦陷。Apple 在硬件和内核两层叠加了大量缓解措施（PAC、PPL/SPTM、kalloc_type、代码签名），内核工程师写的每一行代码都要放在这套防御体系里考量。

目标

读完并做完实验后，你应该能：
  • 为内核写出一个简单威胁模型：攻击面在哪里、攻击者拿到什么原语、各项缓解措施阻断哪一步。
  • 解释 KASLR、W^X、PXN、PAN、stack canary、CFI 各自防御的攻击手法。
  • 说明 ARM PAC 如何用 pacia 签名、autia 校验指针，以及 PPL/SPTM 为什么要把页表保护从内核本身剥离出来。
  • 对比 XNU 的 MACF/Sandbox/AMFI/SIP 与 Linux 的 LSM/SELinux，并能读懂一篇内核 CVE 分析文章。

前置

  • Phase 0：特权级、ARM64 系统寄存器、异常（本阶段的 PAC 失败、PAN 违例最终都是一次同步异常）。
  • Phase 2：页表描述符的 AP、PXN/UXN 位，kalloc_type 与 SLUB——W^X、PXN、PAN、堆隔离都建立在其上。
  • Phase 4（系统调用与 VFS——LSM/MACF 钩子挂在这里）；Phase 6（读 oops/panic、用 QEMU 与容器做实验）。
本阶段内容只为防御与理解：讲清每项缓解拦住了什么，所有实验只在你自己的 QEMU 虚拟机、容器和自己编译的程序上进行，不涉及利用真实漏洞。

核心概念

1. 内核威胁模型

威胁模型回答三个问题：攻击者从哪里开始（通常是一个低权限进程——沙箱里的 App、浏览器渲染进程——或者一段送进内核的外部数据）、能碰到哪些内核代码（攻击面）、想达到什么（提权、逃出沙箱、持久化）。Linux 的典型攻击面：几百个系统调用、设备文件上的 ioctl、netlink、网络协议栈、挂载不可信的文件系统镜像、io_uring、eBPF（非特权 eBPF 通常由 kernel.unprivileged_bpf_disabled 关闭）。XNU 多了两类：Mach trap 与发往内核对象的 Mach 消息（MIG 接口），以及 IOKit 用户客户端——用户态 IOServiceOpen 后通过 IOConnectCallMethod 进到驱动的 IOUserClient::externalMethod，每个驱动都是一块新攻击面。Sandbox 的意义正在于缩小一个进程能够到的攻击面。

典型利用链：漏洞（越界读写、释放后使用 UAF、竞态、类型混淆、逻辑错误）→ 原语（信息泄露、有限的写 → 任意地址读写）→ 绕过缓解 → 达成目标（例如改掉自己进程的凭证：Linux 的 struct cred，XNU 挂在 struct proc_ro 里的 p_ucred）。缓解措施的设计思路就是在这条链的每一环上加成本：让漏洞更难出现（类型安全、隔离）、更难变成原语（堆加固）、原语更难用（KASLR、PAC、PPL/SPTM）。XNU 自己的 doc/allocators/read-only.md 写得很直白：由于 PAC 等控制流防御，今天的攻击者更倾向只改数据（data-only），所以防线也在向「保护关键数据」移动。

2. KASLR 与 W^X / PXN / PAN

KASLR 让内核镜像每次启动加载到随机虚拟地址，攻击者写死的地址全部失效，从而必须先拿到一个信息泄露。Linux arm64（CONFIG_RANDOMIZE_BASE）的种子来自设备树 /chosen/kaslr-seed，没有时用 CPU 的 RNDR 指令（FEAT_RNG），都没有就打印 KASLR disabled due to lack of seed（arch/arm64/kernel/kaslr.c）；nokaslr 关闭它；panic 时打印 Kernel Offset。配套的是「不泄露地址」：kptr_restrict、%pK、默认对 %p 打印的指针做哈希、dmesg_restrict。用户态 ASLR 由 /proc/sys/kernel/randomize_va_space 控制：0 关闭，1 随机化 mmap 基址、栈和 vDSO，2 再加上 brk 堆。XNU 的内核整体滑动一个 kernel slide（vm_kernel_slide）；内核往外报地址时用 VM_KERNEL_UNSLIDE / VM_KERNEL_ADDRPERM 去滑动或置换（osfmk/mach/vm_param.h）；查询 slide 的 kas_info() 系统调用要求 root，还要再过一道 MACF 检查（bsd/vm/vm_unix.c）。

W^X：任何一页要么可写、要么可执行，不能同时。Linux arm64 的内核代码和只读数据用 CONFIG_STRICT_KERNEL_RWX（arm64 上默认强制）、rodata=full 保护——但这些是内核自己设的页表权限，拿到任意写的攻击者理论上可以改回去。Apple 把这一步交给硬件：KIP（Kernel Integrity Protection，源码里的 KTRR/CTRR，如 osfmk/arm64/amcc_rorgn.h）在内核初始化完成后由内存控制器锁定内核代码区域，此后连内核自己也改不了。

PXN（Phase 2 讲过的描述符第 53 位）让内核不能执行用户页——挡住「把 shellcode 放在用户内存，再让内核跳过去」的 ret2usr。PAN（Privileged Access Never，ARMv8.1，PSTATE.PAN）更进一步：内核用普通 load/store 访问用户可访问的页直接触发 permission fault，挡住「在用户内存里伪造内核对象，让内核去读」。内核只能经受控的拷贝路径访问用户内存：Linux 的 copy_from_user 一类（arm64 用 LDTR/STTR 这类「按 EL0 权限访问」的指令，或在短窗口内临时放开 PAN，大致路径）；XNU 的 copyin/copyout（osfmk/arm64/copyio.c）。Linux 相关选项：CONFIG_ARM64_PAN，老 CPU 上用切换 TTBR0 模拟的 CONFIG_ARM64_SW_TTBR0_PAN，以及让「用户只执行页」也受 PAN 约束的 CONFIG_ARM64_EPAN。

3. stack canary 与 CFI

Stack canary：编译器在有局部数组的函数栈帧里、返回地址之前放一个随机值，返回前检查；被连续溢出覆盖就调用 __stack_chk_fail 直接终止。Linux：CONFIG_STACKPROTECTOR / _STRONG，arm64 还有每任务不同 canary 的 CONFIG_STACKPROTECTOR_PER_TASK。XNU 同样有 __stack_chk_guard（libkern/stack_protector.c）。canary 只防连续溢出覆盖到返回地址；任意地址写、或者能先泄露 canary 时就挡不住。

CFI（控制流完整性）把间接跳转限制在「合法目标」：后向边（返回）由 PAC（下一节）或 Linux 的 shadow call stack（CONFIG_SHADOW_CALL_STACK，返回地址另存一份在 x18 指向的隐藏栈）保护；前向边（函数指针调用）由 Clang kCFI（Linux CONFIG_CFI，旧名 CONFIG_CFI_CLANG：调用前检查目标函数前面的类型哈希）和 ARM BTI（Branch Target Identification，CONFIG_ARM64_BTI_KERNEL：间接跳转只能落在 bti 指令上，页表里的 GP 位开启检查）保护。XNU 在 arm64e 上主要靠 PAC 签名的函数指针和 vtable 指针实现前向边保护。

4. ARM Pointer Authentication（PAC）

ARMv8.3 的 FEAT_PAuth 增加了 5 把 128 位密钥（APIAKey、APIBKey、APDAKey、APDBKey、APGAKey，各分 …Lo_EL1/…Hi_EL1 两个系统寄存器；EL0 读不到）和一组指令：pacia Xd, Xn 用 IA 密钥、以 Xn 为修饰值（modifier）给 Xd 里的指针算出一个短 MAC——PAC——写进指针未用于寻址的高位；autia 用同样的密钥和修饰值重算并比较，对了就去掉 PAC 恢复原指针；xpaci/xpacd 只去掉不校验；paciasp/pacibsp 是「对 LR、以 SP 为修饰值」的简写；retaa/retab、blraa 把校验与跳转合成一条。PAC 位数取决于虚拟地址宽度和 TBI：48 位 VA 且开启 TBI 时只有 [54:48] 7 位（bit 55 用来选 TTBR），关闭 TBI 时高字节也可用；所以 PAC 是概率防护，靠的是「猜错一次就崩溃」。

校验失败时：有 FEAT_FPAC 的 CPU 让 aut* 指令立即产生异常（ESR_ELx.EC = 0x1C）——Linux 用户态收到 SIGILL（do_el0_fpac），内核态 die("Oops - FPAC")（do_el1_fpac，arch/arm64/kernel/traps.c）；XNU 走 sleh.c 里的 handle_pac_fail。没有 FPAC 时，aut* 把错误码写进高位使指针变成非规范地址（FEAT_PAuth 行为；FEAT_PAuth2 下改为把重算的 PAC 异或进高位，效果同样通常是非规范地址），等到真正用它跳转或访存时才触发 translation fault。arm64e 编译器还会在部分 aut 之后自己插入检查，失败时执行 brk（XNU 的 ptrauth_handle_brk_trap 负责把它报告成 PAC 失败）。

Linux：CONFIG_ARM64_PTR_AUTH 给用户态启用（每个进程 exec 时随机生成密钥，/proc/cpuinfo 里能看到 paca pacg），CONFIG_ARM64_PTR_AUTH_KERNEL 用 -mbranch-protection=pac-ret（与 BTI 同开时 pac-ret+bti）编译内核，保护返回地址，用 IA 密钥。Apple arm64e 是全面使用：返回地址用 IB 密钥（XNU 汇编宏 ARM64_STACK_PROLOG/EPILOG 就是 pacibsp/retab，osfmk/arm64/asm.h），C 函数指针用 IA，数据指针用 DA/DB，C++ vtable 指针、ObjC 关键指针等再混入「存放地址 + 类型常量」做修饰值（address diversity），让签名不能从一个位置挪到另一个位置复用。ptrauth.h 里 ptrauth_key_process_independent_code 就是 IA 的别名——A 类密钥跨进程共享（共享缓存里的指针才能通用），B 类按进程区分。第三方 arm64e 二进制至今仍属「预览 ABI」：能编译，但正常系统默认不让它运行（见 Lab B）。

5. PPL 与 SPTM

前面所有防线都有一个共同的弱点：页表在内核手里。一旦攻击者拿到内核任意读写，就可以直接改页表——把代码页改成可写、把任意物理内存映射进来、给未签名代码加上可执行权限。Apple 的回答是把「改页表」这件事从内核里拿走（以下据 Apple Platform Security Guide「Operating system integrity」）：

  • Fast Permission Restrictions（A11 起，也称 APRR 寄存器）：一个按线程快速收紧内存权限的 CPU 寄存器，不必改页表、刷 TLB。
  • PPL（Page Protection Layer）：建立在 KIP 和 Fast Permission Restrictions 之上的一小段受保护代码，只有 PPL 能修改页表和存放已签名用户代码的页。Apple 指南说明 PPL「签名校验后代码不可改」这一层保护只在 iOS、iPadOS、visionOS、watchOS 上提供，macOS 因为允许运行任意代码而不提供。XNU 源码里与之相关的是 osfmk/arm/pmap/pmap_ppl_interface.c 和 XNU_MONITOR 宏。
  • SPTM + TXM（A15 及以后、M2 及以后的芯片，替代 PPL；iOS、iPadOS、macOS、visionOS）：Secure Page Table Monitor 运行在比内核更高的特权级，管理用户与内核两边的页表；Trusted Execution Monitor 权限更低，负责实际执行「什么代码可以运行」的策略。两者分开，是为了让 TXM 被攻破也不自动等于 SPTM 被绕过。XNU 源码里能看到 CONFIG_SPTM 宏，构建配置里还有一个 SPTM 内核变体。

Linux 主线没有直接对应物：内核始终可以写自己的页表。最接近的是在内核之下放一个 hypervisor 来保护页表和关键数据——一些手机厂商的方案（例如三星 RKP）就是这样做的（推断：这类方案多为厂商私有，细节不公开）；Android 的 pKVM 则是用 hypervisor 把客户虚拟机的内存与宿主内核隔离，目标不同但思路相同——更高特权级 + 更小的可信代码。

6. kalloc_type 与堆隔离

UAF 利用的经典步骤是「占位」：对象 A 被释放后，攻击者让内核在同一块内存上分配一个内容可控的对象 B，从此持有 A 悬空指针的代码会把 B 当成 A 来用（类型混淆）。通用分配器按大小分档，任何大小相近的对象都能互相占位，这正是攻击者需要的。

XNU kalloc_type（iOS 15 / macOS 12 起；osfmk/kern/kalloc.h 的 kalloc_type(...)、KALLOC_TYPE_DEFINE）：编译器为每个类型生成签名，分配器据此把不同类型的对象分到不同的 zone，纯数据（不含指针）的走单独的 kalloc_data；加上 zone 的虚拟地址不在不同 zone 之间复用（大致机制，详见 Apple 的 kalloc_type 博文），跨类型占位就变得非常难。更敏感的数据放进只读 zone：只能通过 zalloc_ro_mut 修改（doc/allocators/read-only.md），进程凭证就在 struct proc_ro 里。最新一层是 MIE（Memory Integrity Enforcement，A19 / M5 及以后）：在这些安全分配器之上，加上同步模式的 EMTE（增强内存标签扩展）——每块内存和指针各带一个标签，标签不符的访问当场被硬件拦下。

Linux 的 slab 加固是一组选项：CONFIG_SLAB_FREELIST_HARDENED（混淆空闲链表指针）、CONFIG_SLAB_FREELIST_RANDOM（随机化空闲顺序）、init_on_free/init_on_alloc（释放/分配时清零）、CONFIG_SLAB_BUCKETS（6.11 起，把大小由用户控制的分配放进独立的桶）、以及 6.6 引入的 CONFIG_RANDOM_KMALLOC_CACHES（按调用点 + 每次启动的随机种子，从 16 份 kmalloc 缓存里选一份）。截至 2026-10 的主线开发树（v7.3）把后者改名为 CONFIG_KMALLOC_PARTITION_CACHES，并新增 KMALLOC_PARTITION_TYPED 模式：编译器支持 Clang allocation token 时按分配的类型选缓存——这是 Linux 目前最接近 kalloc_type 的机制。硬件标签方面对应的是 arm64 MTE 与 CONFIG_KASAN_HW_TAGS。

7. 强制访问控制与代码签名

Linux LSM：内核在敏感操作处调用 security_* 钩子（例如 security_file_open，钩子清单在 include/linux/lsm_hook_defs.h），由启用的安全模块决定放行与否：SELinux（基于标签的完整 MAC）、AppArmor（基于路径的配置文件）、Landlock（非特权进程给自己加限制）、Yama（限制 ptrace）、lockdown（限制连 root 也不能做的事，如写 /dev/mem、加载未签名模块）。完整性一侧有模块签名（CONFIG_MODULE_SIG）、IMA/EVM、dm-verity。

XNU MACF（源自 TrustedBSD）：内核在同类位置调用 mac_*_check_*（如 mac_vnode_check_open，security/mac_vfs.c；IOKit 有 mac_iokit_check_open），策略模块用 mac_policy_register 注册（security/mac_base.c）。主要策略是两个内核扩展：Sandbox（Seatbelt：按配置文件限制文件、Mach 服务查找、IOKit 打开等，Lab B 能在内核日志里看到它的 deny 记录）和 AMFI（AppleMobileFileIntegrity：执行时校验代码签名与 entitlements，配合用户态 amfid；内核侧代码签名状态在 bsd/kern/kern_cs.c、ubc_subr.c）。SIP（System Integrity Protection）是「连 root 也不行」的那一层：保护系统文件、受保护进程、内核扩展加载等，检查点是 csr_check()（bsd/kern/kern_csr.c），只能在 recoveryOS 里修改。macOS 11 起的系统卷还是签名封存的只读快照（SSV），在 Apple Silicon 上 SPTM/TXM 也参与到「哪些代码可以执行」的决策中。

8. 读 CVE 分析

读任何一篇内核漏洞分析都填同一张表：① 根因（哪一行代码、属于哪类错误：越界、UAF、竞态、未初始化、逻辑）；② 可达性（从什么权限、经哪个接口触发，沙箱里能否够到）；③ 原语（漏洞直接给了什么：读/写多少字节、能否重复）；④ 缓解（哪些措施让利用更难，作者怎样绕过——或者为什么根本不需要绕过）；⑤ 修复（补丁改了什么，是只修这一处还是消灭了一类问题）。

两个好练习：Dirty Pipe（CVE-2022-0847，Linux）——管道缓冲区的 flags 字段在某条路径上未初始化，残留的「可合并」标志让写入落进只读文件的页缓存；它是逻辑错误、不涉及内存破坏，KASLR、PAN、CFI 全都帮不上，修复只是把 flags 初始化——说明缓解措施不能替代正确的代码。XNU 一侧读 Project Zero 博客上 Ian Beer 等人的 iOS 内核分析：注意它们怎样因为 PAC 而走向 data-only 利用，以及 Apple 随后在 kalloc_type、只读 zone、SPTM 上的应对。

动手实验

准备 · 一个可以在两边跑的 PAC 小程序

Linux 版直接用 PAC 指令（内联汇编），存为 pac_linux.c：

#include <stdio.h>
#include <stdint.h>

static inline uint64_t pacia(uint64_t p, uint64_t mod) { __asm__ volatile("pacia %0, %1" : "+r"(p) : "r"(mod)); return p; }
static inline uint64_t autia(uint64_t p, uint64_t mod) { __asm__ volatile("autia %0, %1" : "+r"(p) : "r"(mod)); return p; }
static inline uint64_t xpaci(uint64_t p) { __asm__ volatile("xpaci %0" : "+r"(p)); return p; }

static void target(void) { puts("target()"); }

int main(void) {
  uint64_t fn = (uint64_t)&target, mod = 0x1234;
  uint64_t s = pacia(fn, mod);
  printf("raw    = %#018llx\n", (unsigned long long)fn);
  printf("signed = %#018llx\n", (unsigned long long)s);
  printf("strip  = %#018llx\n", (unsigned long long)xpaci(s));
  printf("auth   = %#018llx (== raw)\n", (unsigned long long)autia(s, mod));
  fflush(stdout);
  uint64_t r = autia(s ^ 0x10, mod);   /* 篡改后校验：有 FEAT_FPAC 时这里直接 SIGILL */
  printf("auth(tampered) = %#018llx  （无 FPAC：指针被毒化，不要调用它）\n", (unsigned long long)r);
  return 0;
}

macOS 版用编译器的 <ptrauth.h> 内建函数，存为 pac_demo.c：

#include <stdio.h>
#include <stdint.h>
#include <ptrauth.h>

static int secret = 42;

int main(void) {
  int *p = &secret;
  /* 用 DA 密钥、以 0x1234 作 discriminator 给数据指针签名 */
  int *s = ptrauth_sign_unauthenticated(p, ptrauth_key_asda, 0x1234);
  printf("raw     = %p\n", (void *)p);
  printf("signed  = %p\n", (void *)s);
  printf("stripped= %p\n", (void *)ptrauth_strip(s, ptrauth_key_asda));
  int *ok = ptrauth_auth_data(s, ptrauth_key_asda, 0x1234);
  printf("auth ok -> %d\n", *ok);
  int *bad = (int *)((uintptr_t)s ^ 0x10);            /* 篡改，只校验、不解引用 */
  int *r = ptrauth_auth_data(bad, ptrauth_key_asda, 0x1234);
  printf("auth(tampered) = %p\n", (void *)r);
  return 0;
}

自测

1. ARM PAC 的签名（PAC 值）存放在哪里？

64 位虚拟地址并不使用全部 64 位，PAC 利用这些高位存放签名；autia 等指令校验成功会去掉签名，失败则触发异常（FEAT_FPAC）或使指针失效。专用寄存器里放的是密钥，不是签名。

2. PAN（Privileged Access Never）开启后阻止的是什么？

PAN 阻止 EL1 直接读写 EL0 可访问的页面，内核只能经由 copyin/copy_from_user 等受控路径访问；禁止内核执行用户页的是 PXN；用户态访问内核内存本来就被页表的 AP 位禁止。

3. 为什么 Apple 要用 PPL / SPTM 把页表修改从内核中剥离出来？

KASLR、PXN、PAC 都假设攻击者还不能随意改页表。PPL（A12–A14、M1）在内核内部建立受保护区域；SPTM（A15、M2 及以后）运行在比内核更高的特权级，与 TXM 配合决定页表与可执行代码。Linux 主线没有对应机制。

4. kalloc_type 主要让哪一种利用步骤变难？

kalloc_type 按类型签名把对象分进不同 zone，纯数据走 kalloc_data，跨类型占位因此变得很难。返回地址由 canary / PAC 保护；KASLR 侧信道是另一类问题。Linux 最接近的是 KMALLOC_PARTITION_TYPED（编译器支持时按类型选缓存）。
