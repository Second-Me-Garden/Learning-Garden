Learning Garden Kernel Engineering Phase 3

Phase 3 / 9 · 约 1–2 周

Concurrency & IPC 并发与 IPC：spinlock/mutex/RCU、内存序；Mach port 与消息

内核里任何共享数据都可能同时被多个 CPU 和中断处理程序访问，锁、原子操作和内存序决定了代码是否正确。XNU 又是一个以 Mach 消息为骨架的内核：launchd、XPC、IOKit 用户客户端都建立在 Mach port 之上，不懂 port 和 mach_msg 就读不懂 Darwin 的大半代码。

  • 画出一次 mach_msg 发送与接收的路径，区分 send right、receive right、send-once right。
  • 用 Linux 的 pipe、futex、signal 对照说明 Mach IPC 在设计上的不同取舍。

核心概念

1. spinlock、mutex、rw_semaphore

锁分两大类：忙等（拿不到就原地转圈）和可睡眠（拿不到就把自己挂到等待队列、让出 CPU）。选择标准只有三条：当前上下文能不能睡眠（中断处理程序、持有其他 spinlock 时都不能）；临界区有多长（比两次上下文切换还短，转圈更划算）；读多写少还是读写相当。

Linux：spinlock_t 用 spin_lock/spin_unlock，持锁期间关抢占；若同一把锁也会在中断里被拿，进程上下文必须用 spin_lock_irqsave 同时关本地中断，否则中断打进来再拿同一把锁就自锁。arm64 上的实现是 queued spinlock（qspinlock，等待者排成 MCS 队列，避免大量 CPU 抢同一条 cache line），等待时借 smp_cond_load_acquire 用 WFE 省电。struct mutex 可睡眠，但在 owner 正在别的 CPU 上运行时先「乐观自旋」一会儿再睡；struct rw_semaphore（down_read/down_write）允许多读者并发。PREEMPT_RT 内核会把大部分 spinlock_t 换成基于 rt_mutex 的可睡眠锁，真正必须忙等的地方用 raw_spinlock_t。

XNU：对应物是 lck_spin_t（lck_spin_lock，关抢占）、lck_mtx_t（lck_mtx_lock）和 lck_rw_t（lck_rw_lock_shared/lck_rw_lock_exclusive/lck_rw_done）。lck_mtx_t 是自适应锁：owner 在运行就自旋，否则阻塞；阻塞时经由 turnstile（osfmk/kern/turnstile.c）把等待者的优先级「借」给 owner，即优先级继承——Linux 的普通 struct mutex 没有这一点，只有 rt_mutex 有。注意 lck_rw_lock_shared_to_exclusive 升级失败时会放掉已持有的共享锁，调用者必须重新查找状态。

为什么持 spinlock 不能睡眠：持锁时抢占已关，睡眠意味着调度走——别的 CPU 在等这把锁会一直空转；若调度到的线程恰好也要这把锁就死锁。Linux 打开 CONFIG_DEBUG_ATOMIC_SLEEP 后 might_sleep() 会打印 BUG: sleeping function called from invalid context；XNU 在 DEVELOPMENT/DEBUG 内核里对「关抢占时阻塞」也有断言（具体报错文本随版本变化）。

2. 原子操作与内存序

ARM64 是弱内存模型：没有依赖关系的两次访存，其他 CPU 观察到的顺序可以和程序顺序不同（x86 是较强的 TSO）。经典的「消息传递」模式：

CPU0:  data = 42;               smp_store_release(&ready, 1);
CPU1:  if (smp_load_acquire(&ready))   BUG_ON(data != 42);   /* 有了 acquire/release 就不会触发 */

release 保证它之前的所有读写先于这次写对他人可见；acquire 保证它之后的读写不会跑到这次读之前。ARM64 有专门的指令：stlr（store-release）和 ldar（load-acquire），Linux arm64 的 smp_store_release/smp_load_acquire 就编成它们（arch/arm64/include/asm/barrier.h）。需要全屏障时用 dmb ish（inner shareable，覆盖所有 CPU）：smp_mb() = dmb ish，smp_rmb() = dmb ishld，smp_wmb() = dmb ishst。dsb 更强（等前面的访存真正完成，用于 TLB/cache 维护），isb 刷流水线，两者都不是普通并发代码要用的。

读改写原子操作：ARMv8.0 用 LL/SC（ldxr/stxr 循环），ARMv8.1 LSE 提供单条指令 ldadd、cas、swp（带 a/l/al 后缀表示 acquire/release）。Linux 在启动时检测 CPU 是否支持 LSE，再用 alternatives 机制把 atomic_* 的实现打补丁成 LSE 版本；Apple M 系列支持 LSE。Linux 接口：atomic_t/atomic_long_t、atomic_inc、atomic_fetch_add、cmpxchg，以及只防编译器撕裂/合并、不加硬件屏障的 READ_ONCE/WRITE_ONCE。

XNU 用 os_atomic_* 宏（libkern/os/atomic_private.h 一带），内存序作为显式参数写在调用里：os_atomic_load(&x, acquire)、os_atomic_store(&x, 1, release)、os_atomic_inc(&n, relaxed)、os_atomic_cmpxchg(&x, old, new, acq_rel)、os_atomic_thread_fence(seq_cst)。本质是 C11 <stdatomic.h> 的包装，内存序命名与 C11 一致——读 XNU 代码时，每个原子操作的语义都直接写在参数里，这一点比 Linux 的命名约定更直白。

3. RCU（Read-Copy-Update）

场景：一个被极频繁读、偶尔改的指针（路由表、配置、进程列表）。读者用任何锁都会让 cache line 在 CPU 间来回弹。RCU 的做法：读者完全不写共享内存——rcu_read_lock()，p = rcu_dereference(gp)，用完 rcu_read_unlock()；写者复制一份、在副本上修改，用 rcu_assign_pointer(gp, new)（本质是 store-release）一次性换指针。此后进来的读者看到新版本，而换指针之前就进来的读者可能还拿着旧版本——所以旧版本不能立即释放。

等待「所有已存在的读者都离开」的这段时间叫宽限期（grace period）。写者调 synchronize_rcu() 阻塞等它结束再 kfree(old)；不能阻塞时用 call_rcu(&old->rcu, cb) 或 kfree_rcu(old, rcu) 登记回调。在非抢占 RCU 里，rcu_read_lock() 只是关抢占，于是「每个 CPU 都至少发生过一次上下文切换、进入 idle 或回到用户态」（quiescent state）就足以证明旧读者都结束了——宽限期检测不需要读者做任何事。可抢占 RCU 则让读者在 task 里记一个嵌套计数，代价略高。实现见 kernel/rcu/tree.c；写者之间仍要用普通锁互斥。

XNU 传统上没有 RCU，较新版本引入了 SMR（safe memory reclamation），接口大致在 osfmk/kern/smr.h：读者 smr_enter/smr_leave，用 smr_entered_load 读指针；写者持锁用 smr_serialized_store 发布，smr_synchronize 同步等待或 smr_call 异步回收。机制是基于序号（epoch）的：全局写序号递增，每个 CPU 进入读区时记下当时的序号，回收者等所有 CPU 的读序号都越过目标值。思想与 RCU 相同，宽限期的「证据」从「上下文切换」换成了「每 CPU 读序号」。函数名以你检出的 smr.h 为准。

4. per-CPU 数据

最好的锁是不需要锁：如果数据可以按 CPU 拆开（统计计数器、每 CPU 空闲对象缓存、运行队列），每个 CPU 只碰自己那份，就没有共享。Linux 用 DEFINE_PER_CPU(type, name) 定义，this_cpu_inc(name)、this_cpu_read(name) 访问本 CPU 副本，per_cpu(name, cpu) 访问指定 CPU 的副本，动态分配用 alloc_percpu + per_cpu_ptr。arm64 上「本 CPU 偏移」放在 TPIDR_EL1（VHE 下是 TPIDR_EL2），所以 this_cpu_* 只需一次寄存器读加偏移。

为什么要关抢占：「读本 CPU 副本 → 加一 → 写回」是三步；若中间被抢占并迁移到另一个 CPU，写回就写到了错误的副本、或和原 CPU 上的新线程撞车。单条 this_cpu_inc 是抢占安全的；多步操作要包在 get_cpu_var/put_cpu_var 或 preempt_disable/preempt_enable 里。若中断处理程序也改这份数据，还需要关本地中断。

XNU 有对应的 PERCPU_DATA(name) 声明和 PERCPU_GET(name) 访问（osfmk/kern/percpu.h），以及历史更久的每 CPU 结构 cpu_data_t（getCpuDatap()）和 processor_t（current_processor()）。关抢占用 disable_preemption()/enable_preemption()。arm64 XNU 用 TPIDR_EL1 保存当前线程指针，每 CPU 数据再从线程上找到（大致路径，细节随版本变化）。

5. 锁正确性检查：lockdep 与 XNU lck_*

死锁最常见的成因是锁顺序反转：路径 1 先 A 后 B，路径 2 先 B 后 A，两条路径同时跑才会卡死——测试里可能永远碰不上。lockdep（CONFIG_PROVE_LOCKING）不等死锁真的发生：它把锁按类（同一处初始化代码产生的锁属于同一类，靠静态 lock_class_key）归并，记录每个任务当前持有的锁栈；每次加锁就在「已持有类 → 新类」之间加一条依赖边，并检查是否成环。只要两条路径分别各跑过一次，就会报 WARNING: possible circular locking dependency detected，附上两条路径的调用栈。它还检查中断安全性：同一类锁既在硬中断里被拿、又在开中断时被拿，就报 inconsistent lock state。代价是明显变慢，只用于调试内核。代码里可用 lockdep_assert_held(&lock) 写下「调用者必须持锁」的契约。

XNU 没有公开的、与 lockdep 等价的锁序证明器。它的锁接口围绕锁组：先 lck_grp_alloc_init("name", LCK_GRP_ATTR_NULL) 建组，再 lck_mtx_alloc_init(grp, LCK_ATTR_NULL) 等在组内建锁；较新代码多用静态声明宏（如 LCK_GRP_DECLARE、LCK_MTX_DECLARE）。锁组用于统计和调试归属。正确性主要靠断言：LCK_MTX_ASSERT(lck, LCK_MTX_ASSERT_OWNED) 一类宏在 DEVELOPMENT/DEBUG 内核中生效（Apple 提供的 KDK 含这些内核），以及 DTrace 的 lockstat provider 观察争用。

6. Mach port 与 mach_msg

port 是内核里的一个对象（struct ipc_port，osfmk/ipc/ipc_port.h），本质是一个带权限控制的消息队列（ipc_mqueue）。用户态永远拿不到 port 指针，只拿到一个 32 位名字（mach_port_name_t）。每个 task 有自己的 IPC 名字空间 ipc_space，内部是 ipc_entry 表：名字 → (port 指针, 持有哪些权限, 引用计数)。同一个 port 在 task A 里叫 0x1103、在 task B 里叫 0x0f03 完全正常——名字只在本 task 有意义，和文件描述符的思路一样。

收发只有一个系统调用：mach_msg(msg, option, send_size, rcv_size, rcv_name, timeout, notify)。option 含 MACH_SEND_MSG 则先发，含 MACH_RCV_MSG 则再收，两者都有就是「发请求并等回复」的一次 RPC。消息以 mach_msg_header_t 开头：msgh_bits（远端/本地端口各用什么方式传递权限）、msgh_size、msgh_remote_port（发往哪里）、msgh_local_port（回复端口）、msgh_id。MACH_MSGH_BITS_COMPLEX 置位时，正文里可以带描述符：port 描述符（传递权限）和 out-of-line（OOL）内存描述符——大块数据不复制，而是在内核里变成 vm_map_copy，接收时按 copy-on-write 映射进对方地址空间（Phase 2 的 COW 在这里派上用场）。

内核里的大致路径：arm64 上 svc #0x80、x16 为负数表示 Mach trap，mach_msg_trap 是 −31 号；进入 osfmk/ipc/mach_msg.c 后，消息被拷进内核的 ipc_kmsg，ipc_kmsg_copyin 把名字翻译成 port 指针并处理权限，ipc_kmsg_send → ipc_mqueue_send 入队（或直接交给正在等待的接收者），接收侧 ipc_mqueue_receive 出队，ipc_kmsg_copyout 把指针翻译成接收方的名字，最后拷回用户缓冲区。较新的 XNU（macOS 13 起）新增了 mach_msg2_trap，内部函数也有重命名，以源码为准。port 的消息队列有长度上限（qlimit，默认值较小），满了发送方阻塞或按超时返回。

很多 port 背后不是用户进程，而是内核对象（kobject）：task port、thread port、host port、IOKit 的 user client。对这些 port 发消息，等于调用内核服务；接口由 MIG（Mach Interface Generator）从 .defs 文件生成收发桩代码。所以 task_info、mach_vm_allocate 这些「函数」其实都是 Mach 消息。

7. port rights 与 XPC

权限有三种：receive right——一个 port 只有一个，持有者才能从队列取消息；send right——可以有很多，带引用计数；send-once right——只能发一条消息，发完即消失，用于回复（内核保证：要么收到回复，要么在 send-once right 被销毁时收到一条 send-once 通知，接收方不会永远等）。在 msgh_bits 或 port 描述符里用 MACH_MSG_TYPE_MAKE_SEND（由 receive right 造一个 send right）、MACH_MSG_TYPE_COPY_SEND（复制自己的 send right）、MACH_MSG_TYPE_MOVE_SEND（转交）、MACH_MSG_TYPE_MAKE_SEND_ONCE、MACH_MSG_TYPE_MOVE_RECEIVE 指定传递方式。receive right 被销毁后，其他 task 手里的 send right 变成 dead name；可以注册 MACH_NOTIFY_DEAD_NAME、MACH_NOTIFY_NO_SENDERS 通知来感知对端死亡或无人引用。

这是一个capability 系统：能向谁发消息，完全取决于你手里有没有它的 send right，而 right 只能通过消息传递获得。那第一个 right 从哪来？每个 task 创建时都有一个 bootstrap port（special port），指向 launchd。服务端在 launchd 的 plist 里声明 MachServices，客户端 bootstrap_look_up(bootstrap_port, "com.example.svc", &port) 拿到 send right。launchd 还能按需启动：服务进程不存在时先替它持有 receive right，第一条消息到来再拉起进程并把 receive right 交给它。

XPC（libxpc）是这一切的现代封装：xpc_connection_create_mach_service 走同一套 bootstrap 查找，消息是序列化成 Mach 消息的 XPC 字典。安全检查依赖内核附加在接收消息尾部的 trailer：接收时请求 MACH_RCV_TRAILER_AUDIT，内核会填入发送方的 audit token（pid、uid、pid 版本号等），这是内核写的、发送方无法伪造的身份——服务端据此查代码签名和 entitlement。用 pid 做检查有 pid 复用竞争，审计 token 才是正确的依据。

8. 对照：Linux IPC（pipe、futex、signal）

Linux 没有一个统一的消息原语，而是按用途组合：pipe（fs/pipe.c，pipe_inode_info 里一圈 pipe_buffer，默认 16 页，可用 F_SETPIPE_SZ 调整）传字节流；UNIX domain socket 传报文，并能用 SCM_RIGHTS 附带文件描述符——这是 Linux 里最接近「在消息中传递 port right」的东西；文件描述符本身就是 capability。服务发现不在内核，由 systemd socket activation、D-Bus 在用户态完成。Android 的 binder（drivers/android/binder.c）是 Linux 上设计最接近 Mach IPC 的机制：对象引用、RPC、发送方身份。

futex（kernel/futex/）是「用户态快速锁」：无竞争时 pthread mutex 只在用户态做一次 CAS，不进内核；有竞争才 futex(uaddr, FUTEX_WAIT, val)——内核按 uaddr 散列到等待桶，确认 *uaddr 仍等于 val 才睡，避免丢失唤醒；解锁方 FUTEX_WAKE。XNU 的对应物是私有系统调用 ulock（__ulock_wait/__ulock_wake，bsd/kern/sys_ulock.c），os_unfair_lock 建立在它之上：锁字里存的是 owner 线程的 port 名字，于是内核知道该把优先级继承给谁（又是 turnstile）。macOS 14.4 起还有公开的 os_sync_wait_on_address 系列。

signal：Linux 里硬件异常（如非法访存）直接变成 SIGSEGV 挂到线程上，返回用户态前投递。XNU 先把它变成一条 Mach 异常消息（EXC_BAD_ACCESS 等），按 thread → task → host 的顺序发往注册的异常 port（调试器、崩溃报告器在这里接管）；没人处理才由 BSD 层（bsd/uxkern/ux_exception.c 一带）转换成 UNIX 信号。这就是 Mach 设计的取舍：一个通用、带权限的消息原语承担几乎所有跨边界通信，换来统一的安全模型和可插拔的服务，代价是每次交互的固定开销和复杂得多的权限记账。

Lab A · Linux（Phase 0 的 QEMU 环境）：竞态、spinlock、atomic、RCU、lockdep

  1. 新建目录 lab3/，写三个模块。race.c：两个 kthread 各把同一个计数器加 100 万次，mode 参数选择无保护 / spinlock / atomic：
    // race.c
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/spinlock.h>
#include <linux/atomic.h>
#include <linux/completion.h>
#include <linux/ktime.h>

static int mode;                         /* 0 = 无保护, 1 = spinlock, 2 = atomic */
module_param(mode, int, 0444);
#define LOOPS 1000000

static long plain;
static atomic_long_t acnt = ATOMIC_LONG_INIT(0);
static DEFINE_SPINLOCK(lock);
static struct completion done[2];

static int worker(void *arg)
{
	int i;

	for (i = 0; i < LOOPS; i++) {
		if (mode == 1) {
			spin_lock(&lock);
			plain++;
			spin_unlock(&lock);
		} else if (mode == 2) {
			atomic_long_inc(&acnt);
		} else {
			WRITE_ONCE(plain, READ_ONCE(plain) + 1);   /* 读-加-写，三步之间可被另一 CPU 插入 */
		}
	}
	kthread_complete_and_exit(arg, 0);
}

static int __init race_init(void)
{
	ktime_t t0 = ktime_get();
	struct task_struct *t;
	int i, started = 0, ret = 0;

	for (i = 0; i < 2; i++) {
		init_completion(&done[i]);
		t = kthread_run(worker, &done[i], "race/%d", i);
		if (IS_ERR(t)) { ret = PTR_ERR(t); break; }
		started++;
	}
	for (i = 0; i < started; i++)
		wait_for_completion(&done[i]);
	if (ret)
		return ret;
	pr_info("race: mode=%d expected=%d got=%ld in %lld us\n", mode, 2 * LOOPS,
		mode == 2 ? atomic_long_read(&acnt) : plain,
		ktime_us_delta(ktime_get(), t0));
	return 0;
}

static void __exit race_exit(void) { }
module_init(race_init);
module_exit(race_exit);
MODULE_LICENSE("GPL");
    rcudemo.c：一个读者 kthread 不停 rcu_read_lock/rcu_dereference，初始化函数三次发布新版本并测量 synchronize_rcu 的耗时：
    // rcudemo.c
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/rcupdate.h>
#include <linux/slab.h>
#include <linux/ktime.h>
#include <linux/sched.h>

struct cfg { int v; };
static struct cfg __rcu *gp;
static struct task_struct *rd;

static int reader(void *unused)
{
	long sum = 0;

	while (!kthread_should_stop()) {
		struct cfg *c;

		rcu_read_lock();
		c = rcu_dereference(gp);
		if (c)
			sum += c->v;
		rcu_read_unlock();
		cond_resched();                     /* 读区外让出 CPU：这正是一个 quiescent state */
	}
	pr_info("rcudemo: reader stop, sum=%ld\n", sum);
	return 0;
}

static int __init rcudemo_init(void)
{
	struct cfg *n, *old;
	ktime_t t0;
	int i;

	rd = kthread_run(reader, NULL, "rcu_reader");
	if (IS_ERR(rd))
		return PTR_ERR(rd);
	for (i = 1; i <= 3; i++) {
		n = kmalloc(sizeof(*n), GFP_KERNEL);
		if (!n)
			break;
		n->v = i;
		old = rcu_dereference_protected(gp, 1);   /* 只有本函数在写 */
		rcu_assign_pointer(gp, n);
		t0 = ktime_get();
		synchronize_rcu();
		pr_info("rcudemo: published v=%d, grace period %lld us\n", i, ktime_us_delta(ktime_get(), t0));
		kfree(old);
	}
	return 0;
}

static void __exit rcudemo_exit(void)
{
	struct cfg *old;

	kthread_stop(rd);
	old = rcu_dereference_protected(gp, 1);
	RCU_INIT_POINTER(gp, NULL);
	synchronize_rcu();
	kfree(old);
}
module_init(rcudemo_init);
module_exit(rcudemo_exit);
MODULE_LICENSE("GPL");

自测

1. 持有 spinlock 时调用可能睡眠的函数（例如 GFP_KERNEL 的 kmalloc），主要问题是什么？

spinlock 的设计前提是临界区短且不睡眠；持锁期间抢占被关闭，睡眠会导致等锁的 CPU 空转甚至死锁。要睡眠请用 mutex（或改用 GFP_ATOMIC 分配）。

2. 一个 Mach port 的 receive right 最多可以同时被几个 task 持有？

每个 port 只有一个 receive right（单一接收者），可以用 MACH_MSG_TYPE_MOVE_RECEIVE 转交但不能复制；send right 可以有很多个，分布在不同 task 中。

3. 在 ARM64 上，Linux 的 smp_store_release(&ready, 1) 通常编译成什么？

ARM64 是弱内存模型，release 语义由专门的 stlr 指令提供，对应的 acquire 读是 ldar。isb 只刷新指令流水线，不提供数据访存的顺序保证。

4. RCU 写者 rcu_assign_pointer(gp, new) 之后调 synchronize_rcu()，它在等什么？

之后进入读区的读者只能看到新版本，不会引用旧对象，所以不必等它们；宽限期只覆盖已存在的读者。否则在读者源源不断的系统上写者会永远等下去。
