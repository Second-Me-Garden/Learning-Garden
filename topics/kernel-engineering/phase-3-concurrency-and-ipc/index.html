Concurrency & IPC 并发与 IPC：spinlock/mutex/RCU、内存序；Mach port 与消息spinlock/mutex/RCU, memory ordering; Mach ports and messages

内核里任何共享数据都可能同时被多个 CPU 和中断处理程序访问，锁、原子操作和内存序决定了代码是否正确。XNU 又是一个以 Mach 消息为骨架的内核：launchd、XPC、IOKit 用户客户端都建立在 Mach port 之上，不懂 port 和 mach_msg 就读不懂 Darwin 的大半代码。

Any shared data in the kernel may be accessed at the same time by several CPUs and interrupt handlers; locks, atomic operations and memory ordering decide whether the code is correct. XNU is also a kernel built around Mach messages: launchd, XPC and IOKit user clients are all built on Mach ports, and without understanding ports and mach_msg you cannot read most of Darwin’s code.

核心概念

Core concepts

1. spinlock、mutex、rw_semaphore

1. spinlock, mutex, rw_semaphore

锁分两大类：忙等（拿不到就原地转圈）和可睡眠（拿不到就把自己挂到等待队列、让出 CPU）。选择标准只有三条：当前上下文能不能睡眠（中断处理程序、持有其他 spinlock 时都不能）；临界区有多长（比两次上下文切换还短，转圈更划算）；读多写少还是读写相当。

Locks fall into two broad classes: busy-waiting (if you cannot get it, spin in place) and sleeping (if you cannot get it, put yourself on a wait queue and give up the CPU). There are only three criteria for choosing: whether the current context can sleep (it cannot in an interrupt handler, nor while holding another spinlock); how long the critical section is (if it is shorter than two context switches, spinning is cheaper); and whether reads far outnumber writes or the two are about equal.

Linux：spinlock_t 用 spin_lock/spin_unlock，持锁期间关抢占；若同一把锁也会在中断里被拿，进程上下文必须用 spin_lock_irqsave 同时关本地中断，否则中断打进来再拿同一把锁就自锁。arm64 上的实现是 queued spinlock（qspinlock，等待者排成 MCS 队列，避免大量 CPU 抢同一条 cache line），等待时借 smp_cond_load_acquire 用 WFE 省电。struct mutex 可睡眠，但在 owner 正在别的 CPU 上运行时先「乐观自旋」一会儿再睡；struct rw_semaphore（down_read/down_write）允许多读者并发。PREEMPT_RT 内核会把大部分 spinlock_t 换成基于 rt_mutex 的可睡眠锁，真正必须忙等的地方用 raw_spinlock_t。

Linux: spinlock_t uses spin_lock/spin_unlock and disables preemption while held; if the same lock is also taken in an interrupt, process context must use spin_lock_irqsave to disable local interrupts as well, otherwise an interrupt that arrives and takes the same lock deadlocks against itself. On arm64 the implementation is the queued spinlock (qspinlock: waiters line up in an MCS queue, which avoids many CPUs fighting over the same cache line), and while waiting it uses WFE through smp_cond_load_acquire to save power. struct mutex can sleep, but when the owner is running on another CPU it first “optimistically spins” for a while before sleeping; struct rw_semaphore (down_read/down_write) lets several readers run concurrently. PREEMPT_RT kernels turn most spinlock_t into sleeping locks based on rt_mutex, and the places that truly must busy-wait use raw_spinlock_t.

XNU：对应物是 lck_spin_t（lck_spin_lock，关抢占）、lck_mtx_t（lck_mtx_lock）和 lck_rw_t（lck_rw_lock_shared/lck_rw_lock_exclusive/lck_rw_done）。lck_mtx_t 是自适应锁：owner 在运行就自旋，否则阻塞；阻塞时经由 turnstile（osfmk/kern/turnstile.c）把等待者的优先级「借」给 owner，即优先级继承——Linux 的普通 struct mutex 没有这一点，只有 rt_mutex 有。注意 lck_rw_lock_shared_to_exclusive 升级失败时会放掉已持有的共享锁，调用者必须重新查找状态。

XNU: the counterparts are lck_spin_t (lck_spin_lock, disables preemption), lck_mtx_t (lck_mtx_lock) and lck_rw_t (lck_rw_lock_shared/lck_rw_lock_exclusive/lck_rw_done). lck_mtx_t is an adaptive lock: it spins if the owner is running and blocks otherwise; when it blocks, it goes through a turnstile (osfmk/kern/turnstile.c) to “lend” the waiter’s priority to the owner, i.e. priority inheritance — Linux’s ordinary struct mutex does not do this; only rt_mutex does. Note that when lck_rw_lock_shared_to_exclusive fails to upgrade, it drops the shared lock already held, and the caller must look up its state again.

为什么持 spinlock 不能睡眠：持锁时抢占已关，睡眠意味着调度走——别的 CPU 在等这把锁会一直空转；若调度到的线程恰好也要这把锁就死锁。Linux 打开 CONFIG_DEBUG_ATOMIC_SLEEP 后 might_sleep() 会打印 BUG: sleeping function called from invalid context；XNU 在 DEVELOPMENT/DEBUG 内核里对「关抢占时阻塞」也有断言（具体报错文本随版本变化）。延伸阅读：《Linux Kernel Development》第 9–10 章「内核同步介绍」「内核同步方法」；《Understanding the Linux Kernel》第 5 章「内核同步」。

Why you must not sleep while holding a spinlock: preemption is off while the lock is held, and sleeping means being scheduled away — other CPUs waiting for this lock keep spinning uselessly; if the thread that gets scheduled happens to want the same lock, it deadlocks. With CONFIG_DEBUG_ATOMIC_SLEEP enabled, Linux’s might_sleep() prints BUG: sleeping function called from invalid context; XNU also has assertions for “blocking with preemption disabled” in DEVELOPMENT/DEBUG kernels (the exact error text varies by version). Further reading: Linux Kernel Development, Chapters 9–10, “An Introduction to Kernel Synchronization” and “Kernel Synchronization Methods”; Understanding the Linux Kernel, Chapter 5, “Kernel Synchronization”.

2. 原子操作与内存序

2. Atomic operations and memory ordering

ARM64 是弱内存模型：没有依赖关系的两次访存，其他 CPU 观察到的顺序可以和程序顺序不同（x86 是较强的 TSO）。经典的「消息传递」模式：

ARM64 has a weak memory model: two memory accesses with no dependency between them may be observed by other CPUs in an order different from program order (x86 has the stronger TSO). The classic “message passing” pattern:

CPU0:  data = 42;               smp_store_release(&ready, 1);
CPU1:  if (smp_load_acquire(&ready))   BUG_ON(data != 42);   /* 有了 acquire/release 就不会触发 */

release 保证它之前的所有读写先于这次写对他人可见；acquire 保证它之后的读写不会跑到这次读之前。ARM64 有专门的指令：stlr（store-release）和 ldar（load-acquire），Linux arm64 的 smp_store_release/smp_load_acquire 就编成它们（arch/arm64/include/asm/barrier.h）。需要全屏障时用 dmb ish（inner shareable，覆盖所有 CPU）：smp_mb() = dmb ish，smp_rmb() = dmb ishld，smp_wmb() = dmb ishst。dsb 更强（等前面的访存真正完成，用于 TLB/cache 维护），isb 刷流水线，两者都不是普通并发代码要用的。

release guarantees that all reads and writes before it become visible to others before this write; acquire guarantees that reads and writes after it do not move ahead of this read. ARM64 has dedicated instructions, stlr (store-release) and ldar (load-acquire), and Linux arm64’s smp_store_release/smp_load_acquire compile to them (arch/arm64/include/asm/barrier.h). When you need a full barrier, use dmb ish (inner shareable, covering all CPUs): smp_mb() = dmb ish, smp_rmb() = dmb ishld, smp_wmb() = dmb ishst. dsb is stronger (it waits for earlier accesses to actually complete, and is used for TLB/cache maintenance), and isb flushes the pipeline; neither is meant for ordinary concurrent code.

读改写原子操作：ARMv8.0 用 LL/SC（ldxr/stxr 循环），ARMv8.1 LSE 提供单条指令 ldadd、cas、swp（带 a/l/al 后缀表示 acquire/release）。Linux 在启动时检测 CPU 是否支持 LSE，再用 alternatives 机制把 atomic_* 的实现打补丁成 LSE 版本；Apple M 系列支持 LSE。Linux 接口：atomic_t/atomic_long_t、atomic_inc、atomic_fetch_add、cmpxchg，以及只防编译器撕裂/合并、不加硬件屏障的 READ_ONCE/WRITE_ONCE。

Read-modify-write atomics: ARMv8.0 uses LL/SC (an ldxr/stxr loop), and ARMv8.1 LSE provides single instructions ldadd, cas, swp (the a/l/al suffixes mean acquire/release). Linux detects at boot whether the CPU supports LSE, then uses the alternatives mechanism to patch the atomic_* implementations into LSE versions; Apple M-series chips support LSE. Linux interfaces: atomic_t/atomic_long_t, atomic_inc, atomic_fetch_add, cmpxchg, and READ_ONCE/WRITE_ONCE, which only prevent the compiler from tearing/merging accesses and add no hardware barrier.

XNU 用 os_atomic_* 宏（libkern/os/atomic_private.h 一带），内存序作为显式参数写在调用里：os_atomic_load(&x, acquire)、os_atomic_store(&x, 1, release)、os_atomic_inc(&n, relaxed)、os_atomic_cmpxchg(&x, old, new, acq_rel)、os_atomic_thread_fence(seq_cst)。本质是 C11 <stdatomic.h> 的包装，内存序命名与 C11 一致——读 XNU 代码时，每个原子操作的语义都直接写在参数里，这一点比 Linux 的命名约定更直白。

XNU uses the os_atomic_* macros (around libkern/os/atomic_private.h), with the memory order written as an explicit argument in the call: os_atomic_load(&x, acquire), os_atomic_store(&x, 1, release), os_atomic_inc(&n, relaxed), os_atomic_cmpxchg(&x, old, new, acq_rel), os_atomic_thread_fence(seq_cst). They are essentially a wrapper around C11 <stdatomic.h>, and the memory-order names match C11 — when you read XNU code, the semantics of every atomic operation are written right in its arguments, which is more direct than Linux’s naming conventions.

3. RCU（Read-Copy-Update）

3. RCU (Read-Copy-Update)

场景：一个被极频繁读、偶尔改的指针（路由表、配置、进程列表）。读者用任何锁都会让 cache line 在 CPU 间来回弹。RCU 的做法：读者完全不写共享内存——rcu_read_lock()，p = rcu_dereference(gp)，用完 rcu_read_unlock()；写者复制一份、在副本上修改，用 rcu_assign_pointer(gp, new)（本质是 store-release）一次性换指针。此后进来的读者看到新版本，而换指针之前就进来的读者可能还拿着旧版本——所以旧版本不能立即释放。

The scenario: a pointer that is read extremely often and changed occasionally (routing tables, configuration, the process list). Any lock that readers take makes the cache line bounce between CPUs. RCU’s approach: readers write no shared memory at all — rcu_read_lock(), p = rcu_dereference(gp), and rcu_read_unlock() when done; the writer makes a copy, modifies the copy, and swaps the pointer in one step with rcu_assign_pointer(gp, new) (essentially a store-release). Readers that enter afterwards see the new version, but readers that entered before the swap may still hold the old one — so the old version cannot be freed immediately.

等待「所有已存在的读者都离开」的这段时间叫宽限期（grace period）。写者调 synchronize_rcu() 阻塞等它结束再 kfree(old)；不能阻塞时用 call_rcu(&old->rcu, cb) 或 kfree_rcu(old, rcu) 登记回调。在非抢占 RCU 里，rcu_read_lock() 只是关抢占，于是「每个 CPU 都至少发生过一次上下文切换、进入 idle 或回到用户态」（quiescent state）就足以证明旧读者都结束了——宽限期检测不需要读者做任何事。可抢占 RCU 则让读者在 task 里记一个嵌套计数，代价略高。实现见 kernel/rcu/tree.c；写者之间仍要用普通锁互斥。

The time spent waiting for “all existing readers to leave” is called the grace period. The writer calls synchronize_rcu() to block until it ends, then does kfree(old); when it cannot block, it registers a callback with call_rcu(&old->rcu, cb) or kfree_rcu(old, rcu). In non-preemptible RCU, rcu_read_lock() only disables preemption, so “every CPU has gone through at least one context switch, entered idle, or returned to user mode” (a quiescent state) is enough to prove that all old readers have finished — grace-period detection needs nothing from the readers. Preemptible RCU instead has readers keep a nesting count in the task, at a slightly higher cost. The implementation is in kernel/rcu/tree.c; writers still need an ordinary lock for mutual exclusion among themselves.

XNU 传统上没有 RCU，较新版本引入了 SMR（safe memory reclamation），接口大致在 osfmk/kern/smr.h：读者 smr_enter/smr_leave，用 smr_entered_load 读指针；写者持锁用 smr_serialized_store 发布，smr_synchronize 同步等待或 smr_call 异步回收。机制是基于序号（epoch）的：全局写序号递增，每个 CPU 进入读区时记下当时的序号，回收者等所有 CPU 的读序号都越过目标值。思想与 RCU 相同，宽限期的「证据」从「上下文切换」换成了「每 CPU 读序号」。函数名以你检出的 smr.h 为准。延伸阅读：《Is Parallel Programming Hard, And, If So, What Can You Do About It?》「Deferred Processing」相关章节，RCU 部分出自 RCU 作者本人。

XNU traditionally had no RCU; newer versions introduced SMR (safe memory reclamation), with the interface roughly in osfmk/kern/smr.h: readers use smr_enter/smr_leave and read the pointer with smr_entered_load; the writer holds a lock and publishes with smr_serialized_store, then waits synchronously with smr_synchronize or reclaims asynchronously with smr_call. The mechanism is sequence-number (epoch) based: a global write sequence number increases, each CPU records the current sequence number when it enters a read section, and the reclaimer waits until the read sequence numbers of all CPUs have passed the target value. The idea is the same as RCU; the “evidence” for the grace period changes from “context switches” to “per-CPU read sequence numbers”. Take the function names from the smr.h you checked out. Further reading: Is Parallel Programming Hard, And, If So, What Can You Do About It?, the chapters on “Deferred Processing”; the RCU part is written by the author of RCU himself.

4. per-CPU 数据

4. Per-CPU data

最好的锁是不需要锁：如果数据可以按 CPU 拆开（统计计数器、每 CPU 空闲对象缓存、运行队列），每个 CPU 只碰自己那份，就没有共享。Linux 用 DEFINE_PER_CPU(type, name) 定义，this_cpu_inc(name)、this_cpu_read(name) 访问本 CPU 副本，per_cpu(name, cpu) 访问指定 CPU 的副本，动态分配用 alloc_percpu + per_cpu_ptr。arm64 上「本 CPU 偏移」放在 TPIDR_EL1（VHE 下是 TPIDR_EL2），所以 this_cpu_* 只需一次寄存器读加偏移。

The best lock is no lock at all: if the data can be split by CPU (statistics counters, per-CPU free-object caches, run queues) and each CPU touches only its own copy, nothing is shared. Linux defines it with DEFINE_PER_CPU(type, name), accesses this CPU’s copy with this_cpu_inc(name) and this_cpu_read(name), and a given CPU’s copy with per_cpu(name, cpu); dynamic allocation uses alloc_percpu + per_cpu_ptr. On arm64 the “this CPU’s offset” value lives in TPIDR_EL1 (TPIDR_EL2 under VHE), so this_cpu_* needs only one register read plus an offset.

为什么要关抢占：「读本 CPU 副本 → 加一 → 写回」是三步；若中间被抢占并迁移到另一个 CPU，写回就写到了错误的副本、或和原 CPU 上的新线程撞车。单条 this_cpu_inc 是抢占安全的；多步操作要包在 get_cpu_var/put_cpu_var 或 preempt_disable/preempt_enable 里。若中断处理程序也改这份数据，还需要关本地中断。

Why preemption must be disabled: “read this CPU’s copy → add one → write back” is three steps; if the thread is preempted in the middle and migrated to another CPU, the write-back goes to the wrong copy, or collides with a new thread on the original CPU. A single this_cpu_inc is preemption-safe; multi-step operations must be wrapped in get_cpu_var/put_cpu_var or preempt_disable/preempt_enable. If an interrupt handler also modifies the data, local interrupts must be disabled as well.

XNU 有对应的 PERCPU_DATA(name) 声明和 PERCPU_GET(name) 访问（osfmk/kern/percpu.h），以及历史更久的每 CPU 结构 cpu_data_t（getCpuDatap()）和 processor_t（current_processor()）。关抢占用 disable_preemption()/enable_preemption()。arm64 XNU 用 TPIDR_EL1 保存当前线程指针，每 CPU 数据再从线程上找到（大致路径，细节随版本变化）。

XNU has the corresponding PERCPU_DATA(name) declaration and PERCPU_GET(name) access (osfmk/kern/percpu.h), plus the older per-CPU structures cpu_data_t (getCpuDatap()) and processor_t (current_processor()). Preemption is disabled with disable_preemption()/enable_preemption(). arm64 XNU keeps the current-thread pointer in TPIDR_EL1, and per-CPU data is then reached from the thread (approximate path; details vary by version).

5. 锁正确性检查：lockdep 与 XNU lck_*

5. Lock correctness checking: lockdep and XNU lck_*

死锁最常见的成因是锁顺序反转：路径 1 先 A 后 B，路径 2 先 B 后 A，两条路径同时跑才会卡死——测试里可能永远碰不上。lockdep（CONFIG_PROVE_LOCKING）不等死锁真的发生：它把锁按类（同一处初始化代码产生的锁属于同一类，靠静态 lock_class_key）归并，记录每个任务当前持有的锁栈；每次加锁就在「已持有类 → 新类」之间加一条依赖边，并检查是否成环。只要两条路径分别各跑过一次，就会报 WARNING: possible circular locking dependency detected，附上两条路径的调用栈。它还检查中断安全性：同一类锁既在硬中断里被拿、又在开中断时被拿，就报 inconsistent lock state。代价是明显变慢，只用于调试内核。代码里可用 lockdep_assert_held(&lock) 写下「调用者必须持锁」的契约。

The most common cause of deadlock is lock-order inversion: path 1 takes A then B, path 2 takes B then A, and it only hangs when both paths run at the same time — tests may never hit it. lockdep (CONFIG_PROVE_LOCKING) does not wait for a deadlock to actually happen: it groups locks into classes (locks created by the same initialisation code belong to the same class, via a static lock_class_key) and records the stack of locks each task currently holds; every time a lock is taken it adds a dependency edge “held class → new class” and checks for a cycle. As soon as each of the two paths has run once, it reports WARNING: possible circular locking dependency detected, with the call stacks of both paths. It also checks interrupt safety: if the same lock class is taken both in a hard interrupt and with interrupts enabled, it reports inconsistent lock state. The cost is a noticeable slowdown, so it is used only in debug kernels. In code, lockdep_assert_held(&lock) writes down the contract “the caller must hold the lock”.

XNU 没有公开的、与 lockdep 等价的锁序证明器。它的锁接口围绕锁组：先 lck_grp_alloc_init("name", LCK_GRP_ATTR_NULL) 建组，再 lck_mtx_alloc_init(grp, LCK_ATTR_NULL) 等在组内建锁；较新代码多用静态声明宏（如 LCK_GRP_DECLARE、LCK_MTX_DECLARE）。锁组用于统计和调试归属。正确性主要靠断言：LCK_MTX_ASSERT(lck, LCK_MTX_ASSERT_OWNED) 一类宏在 DEVELOPMENT/DEBUG 内核中生效（Apple 提供的 KDK 含这些内核），以及 DTrace 的 lockstat provider 观察争用。

XNU has no public lock-order prover equivalent to lockdep. Its lock interface is organised around lock groups: first create a group with lck_grp_alloc_init("name", LCK_GRP_ATTR_NULL), then create locks in the group with lck_mtx_alloc_init(grp, LCK_ATTR_NULL) and the like; newer code mostly uses static declaration macros (such as LCK_GRP_DECLARE, LCK_MTX_DECLARE). Lock groups serve statistics and debug attribution. Correctness relies mainly on assertions: macros such as LCK_MTX_ASSERT(lck, LCK_MTX_ASSERT_OWNED) take effect in DEVELOPMENT/DEBUG kernels (the KDKs Apple provides include these kernels), plus DTrace’s lockstat provider for observing contention.

6. Mach port 与 mach_msg

6. Mach ports and mach_msg

port 是内核里的一个对象（struct ipc_port，osfmk/ipc/ipc_port.h），本质是一个带权限控制的消息队列（ipc_mqueue）。用户态永远拿不到 port 指针，只拿到一个 32 位名字（mach_port_name_t）。每个 task 有自己的 IPC 名字空间 ipc_space，内部是 ipc_entry 表：名字 → (port 指针, 持有哪些权限, 引用计数)。同一个 port 在 task A 里叫 0x1103、在 task B 里叫 0x0f03 完全正常——名字只在本 task 有意义，和文件描述符的思路一样。

A port is an object in the kernel (struct ipc_port, osfmk/ipc/ipc_port.h), essentially a message queue (ipc_mqueue) with access control. User space never gets a port pointer, only a 32-bit name (mach_port_name_t). Each task has its own IPC name space, ipc_space, which internally is a table of ipc_entry: name → (port pointer, which rights are held, reference count). It is perfectly normal for the same port to be called 0x1103 in task A and 0x0f03 in task B — a name means something only within its own task, the same idea as file descriptors.

收发只有一个系统调用：mach_msg(msg, option, send_size, rcv_size, rcv_name, timeout, notify)。option 含 MACH_SEND_MSG 则先发，含 MACH_RCV_MSG 则再收，两者都有就是「发请求并等回复」的一次 RPC。消息以 mach_msg_header_t 开头：msgh_bits（远端/本地端口各用什么方式传递权限）、msgh_size、msgh_remote_port（发往哪里）、msgh_local_port（回复端口）、msgh_id。MACH_MSGH_BITS_COMPLEX 置位时，正文里可以带描述符：port 描述符（传递权限）和 out-of-line（OOL）内存描述符——大块数据不复制，而是在内核里变成 vm_map_copy，接收时按 copy-on-write 映射进对方地址空间（Phase 2 的 COW 在这里派上用场）。

Sending and receiving use a single system call: mach_msg(msg, option, send_size, rcv_size, rcv_name, timeout, notify). If option contains MACH_SEND_MSG it sends first, if it contains MACH_RCV_MSG it then receives, and with both it is one RPC: “send the request and wait for the reply”. A message starts with mach_msg_header_t: msgh_bits (how rights are transferred for the remote and local ports), msgh_size, msgh_remote_port (where it goes), msgh_local_port (the reply port), msgh_id. When MACH_MSGH_BITS_COMPLEX is set, the body can carry descriptors: port descriptors (which transfer rights) and out-of-line (OOL) memory descriptors — large data is not copied but becomes a vm_map_copy in the kernel, and on receipt it is mapped copy-on-write into the receiver’s address space (Phase 2’s COW pays off here).

内核里的大致路径：arm64 上 svc #0x80、x16 为负数表示 Mach trap，mach_msg_trap 是 −31 号；进入 osfmk/ipc/mach_msg.c 后，消息被拷进内核的 ipc_kmsg，ipc_kmsg_copyin 把名字翻译成 port 指针并处理权限，ipc_kmsg_send → ipc_mqueue_send 入队（或直接交给正在等待的接收者），接收侧 ipc_mqueue_receive 出队，ipc_kmsg_copyout 把指针翻译成接收方的名字，最后拷回用户缓冲区。较新的 XNU（macOS 13 起）新增了 mach_msg2_trap，内部函数也有重命名，以源码为准。port 的消息队列有长度上限（qlimit，默认值较小），满了发送方阻塞或按超时返回。

The approximate path in the kernel: on arm64, svc #0x80 with a negative x16 means a Mach trap, and mach_msg_trap is number −31; after entering osfmk/ipc/mach_msg.c, the message is copied into a kernel ipc_kmsg, ipc_kmsg_copyin translates names into port pointers and handles the rights, ipc_kmsg_send → ipc_mqueue_send enqueues it (or hands it directly to a waiting receiver), on the receiving side ipc_mqueue_receive dequeues it, ipc_kmsg_copyout translates pointers into the receiver’s names, and finally it is copied back to the user buffer. Newer XNU (from macOS 13) adds mach_msg2_trap, and internal functions have been renamed too; go by the source. A port’s message queue has a length limit (qlimit, with a small default); when it is full the sender blocks or returns on timeout.

很多 port 背后不是用户进程，而是内核对象（kobject）：task port、thread port、host port、IOKit 的 user client。对这些 port 发消息，等于调用内核服务；接口由 MIG（Mach Interface Generator）从 .defs 文件生成收发桩代码。所以 task_info、mach_vm_allocate 这些「函数」其实都是 Mach 消息。
Many ports are backed not by a user process but by a kernel object (kobject): the task port, thread port, host port, IOKit user clients. Sending a message to such a port amounts to calling a kernel service; MIG (Mach Interface Generator) generates the send/receive stub code for these interfaces from .defs files. So “functions” such as task_info and mach_vm_allocate are in fact all Mach messages.

7. port rights 与 XPC

7. Port rights and XPC

权限有三种：receive right——一个 port 只有一个，持有者才能从队列取消息；send right——可以有很多，带引用计数；send-once right——只能发一条消息，发完即消失，用于回复（内核保证：要么收到回复，要么在 send-once right 被销毁时收到一条 send-once 通知，接收方不会永远等）。在 msgh_bits 或 port 描述符里用 MACH_MSG_TYPE_MAKE_SEND（由 receive right 造一个 send right）、MACH_MSG_TYPE_COPY_SEND（复制自己的 send right）、MACH_MSG_TYPE_MOVE_SEND（转交）、MACH_MSG_TYPE_MAKE_SEND_ONCE、MACH_MSG_TYPE_MOVE_RECEIVE 指定传递方式。receive right 被销毁后，其他 task 手里的 send right 变成 dead name；可以注册 MACH_NOTIFY_DEAD_NAME、MACH_NOTIFY_NO_SENDERS 通知来感知对端死亡或无人引用。

There are three kinds of rights: the receive right — a port has only one, and only its holder can take messages off the queue; the send right — there can be many, reference-counted; the send-once right — it can send only one message and disappears once used, and is used for replies (the kernel guarantees that either the reply arrives or, when the send-once right is destroyed, a send-once notification arrives, so the receiver never waits forever). In msgh_bits or in a port descriptor, the transfer mode is given with MACH_MSG_TYPE_MAKE_SEND (make a send right from a receive right), MACH_MSG_TYPE_COPY_SEND (copy your own send right), MACH_MSG_TYPE_MOVE_SEND (hand it over), MACH_MSG_TYPE_MAKE_SEND_ONCE and MACH_MSG_TYPE_MOVE_RECEIVE. Once a receive right is destroyed, the send rights held by other tasks become dead names; you can register MACH_NOTIFY_DEAD_NAME and MACH_NOTIFY_NO_SENDERS notifications to learn that the other end has died or that nobody references the port any more.

这是一个capability 系统：能向谁发消息，完全取决于你手里有没有它的 send right，而 right 只能通过消息传递获得。那第一个 right 从哪来？每个 task 创建时都有一个 bootstrap port（special port），指向 launchd。服务端在 launchd 的 plist 里声明 MachServices，客户端 bootstrap_look_up(bootstrap_port, "com.example.svc", &port) 拿到 send right。launchd 还能按需启动：服务进程不存在时先替它持有 receive right，第一条消息到来再拉起进程并把 receive right 交给它。

This is a capability system: whom you can send messages to depends entirely on whether you hold their send right, and rights can only be obtained through messages. So where does the first right come from? Every task is created with a bootstrap port (a special port) that points to launchd. A server declares MachServices in its launchd plist, and a client gets a send right with bootstrap_look_up(bootstrap_port, "com.example.svc", &port). launchd can also launch on demand: while the service process does not exist, launchd holds the receive right on its behalf, and when the first message arrives it starts the process and hands the receive right to it.

XPC（libxpc）是这一切的现代封装：xpc_connection_create_mach_service 走同一套 bootstrap 查找，消息是序列化成 Mach 消息的 XPC 字典。安全检查依赖内核附加在接收消息尾部的 trailer：接收时请求 MACH_RCV_TRAILER_AUDIT，内核会填入发送方的 audit token（pid、uid、pid 版本号等），这是内核写的、发送方无法伪造的身份——服务端据此查代码签名和 entitlement。用 pid 做检查有 pid 复用竞争，审计 token 才是正确的依据。

XPC (libxpc) is the modern wrapper around all of this: xpc_connection_create_mach_service goes through the same bootstrap lookup, and messages are XPC dictionaries serialised into Mach messages. Security checks rely on the trailer that the kernel appends to the end of a received message: request MACH_RCV_TRAILER_AUDIT when receiving and the kernel fills in the sender’s audit token (pid, uid, pid version and so on), an identity written by the kernel that the sender cannot forge — the server uses it to check the code signature and entitlements. Checking by pid has a pid-reuse race; the audit token is the correct basis.

8. 对照：Linux IPC（pipe、futex、signal）

8. Contrast: Linux IPC (pipe, futex, signal)

Linux 没有一个统一的消息原语，而是按用途组合：pipe（fs/pipe.c，pipe_inode_info 里一圈 pipe_buffer，默认 16 页，可用 F_SETPIPE_SZ 调整）传字节流；UNIX domain socket 传报文，并能用 SCM_RIGHTS 附带文件描述符——这是 Linux 里最接近「在消息中传递 port right」的东西；文件描述符本身就是 capability。服务发现不在内核，由 systemd socket activation、D-Bus 在用户态完成。Android 的 binder（drivers/android/binder.c）是 Linux 上设计最接近 Mach IPC 的机制：对象引用、RPC、发送方身份。

Linux has no single unified message primitive; it combines mechanisms by purpose: a pipe (fs/pipe.c, a ring of pipe_buffer in pipe_inode_info, 16 pages by default, adjustable with F_SETPIPE_SZ) carries a byte stream; a UNIX domain socket carries messages and can attach file descriptors with SCM_RIGHTS — the closest thing in Linux to “passing a port right in a message”; a file descriptor is itself a capability. Service discovery is not in the kernel; systemd socket activation and D-Bus do it in user space. Android’s binder (drivers/android/binder.c) is the mechanism on Linux whose design is closest to Mach IPC: object references, RPC, sender identity.

futex（kernel/futex/）是「用户态快速锁」：无竞争时 pthread mutex 只在用户态做一次 CAS，不进内核；有竞争才 futex(uaddr, FUTEX_WAIT, val)——内核按 uaddr 散列到等待桶，确认 *uaddr 仍等于 val 才睡，避免丢失唤醒；解锁方 FUTEX_WAKE。XNU 的对应物是私有系统调用 ulock（__ulock_wait/__ulock_wake，bsd/kern/sys_ulock.c），os_unfair_lock 建立在它之上：锁字里存的是 owner 线程的 port 名字，于是内核知道该把优先级继承给谁（又是 turnstile）。macOS 14.4 起还有公开的 os_sync_wait_on_address 系列。

futex (kernel/futex/) is the “fast user-space lock”: without contention a pthread mutex does a single CAS in user space and never enters the kernel; only under contention does it call futex(uaddr, FUTEX_WAIT, val) — the kernel hashes uaddr into a wait bucket and sleeps only after confirming that *uaddr still equals val, which avoids lost wakeups; the unlocker calls FUTEX_WAKE. XNU’s counterpart is the private system call ulock (__ulock_wait/__ulock_wake, bsd/kern/sys_ulock.c), on which os_unfair_lock is built: the lock word stores the owner thread’s port name, so the kernel knows whom to pass the inherited priority to (turnstiles again). From macOS 14.4 there is also the public os_sync_wait_on_address family.

signal：Linux 里硬件异常（如非法访存）直接变成 SIGSEGV 挂到线程上，返回用户态前投递。XNU 先把它变成一条 Mach 异常消息（EXC_BAD_ACCESS 等），按 thread → task → host 的顺序发往注册的异常 port（调试器、崩溃报告器在这里接管）；没人处理才由 BSD 层（bsd/uxkern/ux_exception.c 一带）转换成 UNIX 信号。这就是 Mach 设计的取舍：一个通用、带权限的消息原语承担几乎所有跨边界通信，换来统一的安全模型和可插拔的服务，代价是每次交互的固定开销和复杂得多的权限记账。

signal: on Linux a hardware exception (such as an illegal memory access) becomes a SIGSEGV attached directly to the thread and delivered before returning to user mode. XNU first turns it into a Mach exception message (EXC_BAD_ACCESS and so on) and sends it to the registered exception ports in thread → task → host order (debuggers and crash reporters take over here); only if nobody handles it does the BSD layer (around bsd/uxkern/ux_exception.c) convert it into a UNIX signal. This is the trade-off of the Mach design: one general-purpose message primitive with rights carries almost all cross-boundary communication, which buys a uniform security model and pluggable services, at the cost of a fixed overhead on every interaction and far more complex rights bookkeeping.

    // race.c
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/spinlock.h>
#include <linux/atomic.h>
#include <linux/completion.h>
#include <linux/ktime.h>

static int mode;                         /* 0 = 无保护, 1 = spinlock, 2 = atomic */
module_param(mode, int, 0444);
#define LOOPS 1000000

static long plain;
static atomic_long_t acnt = ATOMIC_LONG_INIT(0);
static DEFINE_SPINLOCK(lock);
static struct completion done[2];

static int worker(void *arg)
{
	int i;

	for (i = 0; i < LOOPS; i++) {
		if (mode == 1) {
			spin_lock(&lock);
			plain++;
			spin_unlock(&lock);
		} else if (mode == 2) {
			atomic_long_inc(&acnt);
		} else {
			WRITE_ONCE(plain, READ_ONCE(plain) + 1);   /* 读-加-写，三步之间可被另一 CPU 插入 */
		}
	}
	kthread_complete_and_exit(arg, 0);
}

static int __init race_init(void)
{
	ktime_t t0 = ktime_get();
	struct task_struct *t;
	int i, started = 0, ret = 0;

	for (i = 0; i < 2; i++) {
		init_completion(&done[i]);
		t = kthread_run(worker, &done[i], "race/%d", i);
		if (IS_ERR(t)) { ret = PTR_ERR(t); break; }
		started++;
	}
	for (i = 0; i < started; i++)
		wait_for_completion(&done[i]);
	if (ret)
		return ret;
	pr_info("race: mode=%d expected=%d got=%ld in %lld us\n", mode, 2 * LOOPS,
		mode == 2 ? atomic_long_read(&acnt) : plain,
		ktime_us_delta(ktime_get(), t0));
	return 0;
}

static void __exit race_exit(void) { }
module_init(race_init);
module_exit(race_exit);
MODULE_LICENSE("GPL");
    rcudemo.c：一个读者 kthread 不停 rcu_read_lock/rcu_dereference，初始化函数三次发布新版本并测量 synchronize_rcu 的耗时：rcudemo.c: a reader kthread loops on rcu_read_lock/rcu_dereference, while the init function publishes a new version three times and measures how long synchronize_rcu takes:
    // rcudemo.c
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/rcupdate.h>
#include <linux/slab.h>
#include <linux/ktime.h>
#include <linux/sched.h>

struct cfg { int v; };
static struct cfg __rcu *gp;
static struct task_struct *rd;

static int reader(void *unused)
{
	long sum = 0;

	while (!kthread_should_stop()) {
		struct cfg *c;

		rcu_read_lock();
		c = rcu_dereference(gp);
		if (c)
			sum += c->v;
		rcu_read_unlock();
		cond_resched();                     /* 读区外让出 CPU：这正是一个 quiescent state */
	}
	pr_info("rcudemo: reader stop, sum=%ld\n", sum);
	return 0;
}

static int __init rcudemo_init(void)
{
	struct cfg *n, *old;
	ktime_t t0;
	int i;

	rd = kthread_run(reader, NULL, "rcu_reader");
	if (IS_ERR(rd))
		return PTR_ERR(rd);
	for (i = 1; i <= 3; i++) {
		n = kmalloc(sizeof(*n), GFP_KERNEL);
		if (!n)
			break;
		n->v = i;
		old = rcu_dereference_protected(gp, 1);   /* 只有本函数在写 */
		rcu_assign_pointer(gp, n);
		t0 = ktime_get();
		synchronize_rcu();
		pr_info("rcudemo: published v=%d, grace period %lld us\n", i, ktime_us_delta(ktime_get(), t0));
		kfree(old);
	}
	return 0;
}

static void __exit rcudemo_exit(void)
{
	struct cfg *old;

	kthread_stop(rd);
	old = rcu_dereference_protected(gp, 1);
	RCU_INIT_POINTER(gp, NULL);
	synchronize_rcu();
	kfree(old);
}
module_init(rcudemo_init);
module_exit(rcudemo_exit);
MODULE_LICENSE("GPL");

自测

Self-check

1. 持有 spinlock 时调用可能睡眠的函数（例如 GFP_KERNEL 的 kmalloc），主要问题是什么？

1. What is the main problem with calling a function that may sleep (for example kmalloc with GFP_KERNEL) while holding a spinlock?

spinlock 的设计前提是临界区短且不睡眠；持锁期间抢占被关闭，睡眠会导致等锁的 CPU 空转甚至死锁。要睡眠请用 mutex（或改用 GFP_ATOMIC 分配）。A spinlock is designed on the premise that the critical section is short and does not sleep; preemption is disabled while it is held, and sleeping makes CPUs waiting for the lock spin uselessly or even deadlock. If you need to sleep, use a mutex (or allocate with GFP_ATOMIC instead).

2. 一个 Mach port 的 receive right 最多可以同时被几个 task 持有？

2. At most how many tasks can hold the receive right of one Mach port at the same time?

每个 port 只有一个 receive right（单一接收者），可以用 MACH_MSG_TYPE_MOVE_RECEIVE 转交但不能复制；send right 可以有很多个，分布在不同 task 中。Each port has exactly one receive right (a single receiver); it can be handed over with MACH_MSG_TYPE_MOVE_RECEIVE but not copied; there can be many send rights, spread across different tasks.

3. 在 ARM64 上，Linux 的 smp_store_release(&ready, 1) 通常编译成什么？

3. On ARM64, what does Linux’s smp_store_release(&ready, 1) usually compile to?

ARM64 是弱内存模型，release 语义由专门的 stlr 指令提供，对应的 acquire 读是 ldar。isb 只刷新指令流水线，不提供数据访存的顺序保证。ARM64 is a weak memory model; release semantics are provided by the dedicated stlr instruction, and the matching acquire read is ldar. isb only flushes the instruction pipeline and gives no ordering guarantee for data accesses.

4. RCU 写者 rcu_assign_pointer(gp, new) 之后调 synchronize_rcu()，它在等什么？

4. After the RCU writer does rcu_assign_pointer(gp, new) and calls synchronize_rcu(), what is it waiting for?

之后进入读区的读者只能看到新版本，不会引用旧对象，所以不必等它们；宽限期只覆盖已存在的读者。否则在读者源源不断的系统上写者会永远等下去。Readers that enter a read section later can only see the new version and will not reference the old object, so there is no need to wait for them; the grace period covers only the readers that already exist. Otherwise, on a system with a steady stream of readers, the writer would wait forever.
