Syscalls, VFS & Filesystems 系统调用入口、VFS 层次、ext4 ↔ APFS、块 I/O

一次 open()/read() 会穿过系统调用入口、VFS 抽象层、页缓存、具体文件系统和块层，最终到达存储设备。Apple 的内核工程师经常要回答「数据到底什么时候落盘」「APFS 的 clone 和 snapshot 是怎么实现的」这类问题，这一阶段把整条 I/O 路径串起来。

目标

读完并做完实验后，你应该能：
  • 从 open() 出发，说出 Linux 的 file/dentry/inode 与 XNU 的 vnode 各自在哪一步被找到或创建。
  • 解释页缓存（Linux）与 UBC（XNU）的作用，以及一次 buffered write 何时真正写到设备。
  • 对比 ext4 与 APFS 的关键设计：日志 vs copy-on-write，snapshot、clone、原生加密。
  • 说清 macOS 上 fsync 与 fcntl(F_FULLFSYNC) 的区别，以及数据库为什么关心它。

前置

  • Phase 0（系统调用的异常进入与返回：svc、ESR_EL1、eret）；QEMU 里能启动 Linux arm64 内核，Phase 3 已经会对那棵源码树编模块。
  • Phase 2（页、缺页、vm_object 与 pager——页缓存和 UBC 就建立在它们之上）。
  • Phase 3（VFS 对象的引用计数与锁；RCU——Linux 路径查找的快路径就是 RCU-walk）。

核心概念

1. 系统调用表与 ABI（回顾）

Linux arm64：用户态把调用号放 x8、参数放 x0–x5，执行 svc #0；返回值在 x0，失败时是 -errno（−4095 到 −1），libc 把它变成 -1 并设置 errno。内核侧 el0_svc → do_el0_svc → el0_svc_common → invoke_syscall（arch/arm64/kernel/syscall.c）按号查 sys_call_table。每个调用用 SYSCALL_DEFINEn 宏定义（如 fs/open.c 里的 SYSCALL_DEFINE4(openat, ...)），宏会生成从 pt_regs 取参数的包装函数 __arm64_sys_openat。arm64 只有 openat 没有 open——新架构不再提供旧式调用。

XNU arm64：svc #0x80，调用号在 x16（正数是 BSD syscall，负数是 Mach trap，Phase 3 的 mach_msg_trap 就是 −31）。BSD 调用的错误约定不同：失败时内核置 PSTATE 的 C（进位）标志、x0 放正的 errno，libsystem 的汇编桩看到进位再跳去设置 errno。内核侧 sleh_synchronous → handle_svc → unix_syscall（bsd/dev/arm/systemcalls.c）查 sysent[]；这张表由 bsd/kern/syscalls.master 在构建时生成（init_sysent.c）。实现函数的签名统一是 int open(proc_t p, struct open_args *uap, int32_t *retval)：返回值是 errno，结果写进 retval。

参数校验是系统调用最容易出安全漏洞的地方：用户传来的指针一律不可信，不能直接解引用。Linux 用 copy_from_user/copy_to_user（返回未拷贝的字节数，非 0 就返回 -EFAULT）、strncpy_from_user（路径名经 getname() 进内核），指针参数标注 __user 供 sparse 检查；XNU 用 copyin/copyout/copyinstr（arm64 实现在 osfmk/arm64/ 下的 copyio 相关文件）。两边在 ARMv8.1+ 上都开启 PAN（Privileged Access Never）：内核普通访存碰到用户页直接 fault，只有专门的 uaccess 路径才能访问——把「忘了用 copyin」的 bug 变成立即崩溃而不是可利用漏洞。另一条铁律是 TOCTOU：只拷贝一次，之后只用内核里的副本做检查和使用。

2. VFS 对象模型

VFS 让 read() 不必知道底下是 ext4、NFS 还是 procfs：通用代码只操作抽象对象，具体行为通过操作表（函数指针结构）分派给文件系统。

Linux 有四个核心对象：struct super_block——一个已挂载的文件系统实例（s_op 指向 super_operations）；struct inode——一个文件本身（元数据、i_op、i_fop、i_mapping 指向它的页缓存）；struct dentry——一个名字到 inode 的绑定（d_parent、d_name、d_inode），硬链接就是多个 dentry 指向同一 inode；struct file——一次 open 的结果（f_pos 偏移、打开标志、f_op）。进程的 fd 表 files_struct/fdtable 是 struct file * 数组，fd 就是下标。

XNU（BSD 层）：struct mount 对应 super_block（mnt_op）；struct vnode 同时扮演 inode 的角色（v_type、v_op 操作向量、v_mount、v_data 指向文件系统私有节点、v_ubcinfo），文件系统操作统一走 VNOP_LOOKUP、VNOP_OPEN、VNOP_READ、VNOP_WRITE、VNOP_PAGEIN 等 KPI。XNU 没有独立的 dentry：名字信息由 name cache 和 vnode 上的 v_name/v_parent 承担。打开的文件分两层：struct fileglob 是真正的打开文件（偏移、标志、fg_ops、fg_data 指向 vnode 或 socket），struct fileproc 是 fd 表里的每进程条目，指向 fileglob——dup 和 fork 后多个 fileproc 共享一个 fileglob，这与 Linux 多个 fd 共享同一 struct file 是同一件事。延伸阅读：《Linux Kernel Development》第 13 章「虚拟文件系统」；《Understanding the Linux Kernel》第 12 章「虚拟文件系统」。

3. 路径查找

Linux（fs/namei.c）：do_sys_openat2 → do_filp_open → path_openat。path_init 定起点（绝对路径用 current->fs 的 root，相对路径用 cwd 或 dirfd），link_path_walk 逐个分量循环，每个分量 walk_component：先 lookup_fast 在 dcache（按「父 dentry + 名字」散列）里找，未命中才 lookup_slow 调父目录的 i_op->lookup（如 ext4_lookup）去读磁盘上的目录、分配新 dentry 和 inode。途中处理挂载点（dentry 被挂载时换到被挂载文件系统的根）、符号链接（有深度上限，防循环）和每级目录的执行权限（may_lookup → inode_permission）。

快路径是 RCU-walk：整个查找先在 rcu_read_lock 下进行，不增加任何引用计数、不拿锁，靠 seqcount 检测并发修改；一旦遇到需要睡眠的情况（未命中、要读磁盘）或检测到变化，返回 -ECHILD，退回带引用计数的 REF-walk 重来。热路径上的路径查找因此几乎没有 cache line 争用——这正是 Phase 3 RCU 的大规模应用。最后一个分量由 open_last_lookups/do_open 处理（可能创建文件），vfs_open 调 f_op->open，fd_install 把 struct file 放进 fd 表。

XNU（bsd/vfs/vfs_lookup.c）：open → openat_internal → open1 → vn_open_auth（bsd/vfs/vfs_vnops.c）→ namei()。namei 把路径 copyinstr 进 nameidata，定起点（进程根或 cwd 的 vnode），交给 lookup() 逐分量处理：先查 name cache（bsd/vfs/vfs_cache.c，cache_lookup，按「目录 vnode + 名字」散列；还有一次走多个分量的快路径 cache_lookup_path），未命中则 VNOP_LOOKUP 让文件系统返回 vnode 并 cache_enter 记入缓存。挂载点通过目录 vnode 的 v_mountedhere 跳到被挂载卷的根。权限检查走 kauth（vnode_authorize），并且每一步都可能经过 MAC Framework 钩子——macOS 沙箱（Sandbox.kext）就在这里拒绝访问。open1 先用 falloc_withinit 分配 fileproc/fileglob，再经 vn_open_auth → VNOP_OPEN，最后返回 fd。

4. 页缓存 ↔ UBC

文件数据被缓存在内存页里，read/write 只是在用户缓冲区和这些页之间拷贝；同一个文件被 mmap 时，进程页表直接映射同一批物理页——所以 write() 的结果立即在 mmap 里可见，反之亦然，不存在两份缓存的一致性问题。

Linux：每个 inode 有一个 struct address_space（inode->i_mapping），用 xarray（i_pages）按文件页偏移索引 folio，操作表 address_space_operations（read_folio、readahead、writepages、dirty_folio 等）由文件系统提供。读路径 filemap_read → filemap_get_pages：命中直接拷贝，未命中触发预读（readahead，顺序读时窗口逐步变大）。写路径 generic_perform_write：把数据拷进页缓存、标脏，然后立即返回；回写由 per-bdi 的 writeback 工作线程完成，触发条件是脏页超时（/proc/sys/vm/dirty_expire_centisecs，默认 3000 即 30 秒）、脏页比例超限（dirty_background_ratio/dirty_ratio）或显式 fsync/sync。/proc/meminfo 的 Cached、Dirty、Writeback 就是这几类页的数量。

XNU 的 UBC（Unified Buffer Cache）把文件缓存直接做成 Mach VM 对象：vnode 的 ubc_info（bsd/sys/ubc_internal.h）通过 ui_control 关联一个 vm_object，文件页就是这个 object 里的 vm_page，背后的 pager 是 vnode pager——Phase 2 讲的「vm_object + pager」在这里落地。文件系统在 VNOP_READ/VNOP_WRITE 里调用通用的 cluster 层（bsd/vfs/vfs_cluster.c：cluster_read、cluster_write、cluster_push），它负责查 UBC、预读、聚合 I/O；缺页时 VM 经 vnode pager 调 VNOP_PAGEIN，换出脏页调 VNOP_PAGEOUT。I/O 以 UPL（universal page list，一组被锁定的页）为单位在 VM 与文件系统之间传递。bsd/kern/ubc_subr.c 是 UBC 的主要实现文件。延伸阅读：《Linux Kernel Development》第 16 章「页缓存与页回写」；《Understanding the Linux Kernel》第 15 章「页缓存」。

5. ext4 vs APFS

ext4 是「原地更新 + 日志」：磁盘分成若干 block group，每组有位图和 inode 表；文件数据用 extent（起始块 + 长度，单个 extent 最多 32768 块，4 KB 块时为 128 MB）描述，比 ext2/3 的间接块表紧凑得多；目录用 htree 散列索引；新版 mkfs.ext4（e2fsprogs ≥ 1.43）默认开启元数据校验和（metadata_csum）。崩溃一致性靠 jbd2 日志：元数据修改先写进日志并提交，再写回原位；默认 data=ordered 模式保证数据块在引用它的元数据提交之前落盘（不会在崩溃后看到别的文件的旧数据），但数据本身不进日志。延迟分配让块分配推迟到回写时，有利于连续分配，但也是「应用不 fsync 就 rename」在崩溃后得到空文件的历史原因。

APFS 是「从不原地覆盖」的 copy-on-write 文件系统，为闪存设计。磁盘上一个容器（container superblock nx_superblock_t）内含多个卷（apfs_superblock_t），卷之间共享空闲空间（macOS 的系统卷、数据卷、Preboot、VM 卷都在一个容器里）。元数据是 B-tree，改一个节点就写一个新副本并向上更新到根，再通过对象映射（omap，虚拟对象 ID → 物理地址）和检查点原子地切换——没有传统日志，因为旧版本始终完好。

COW 直接带来三项能力：snapshot——保留某个事务时刻的树根，代价几乎为零（Time Machine 本地快照、系统更新都依赖它；macOS 11 起系统卷是带哈希校验的签名快照，即 SSV）；clone——clonefile(2) 或 cp -c 让新文件共享原文件的 extent（带引用计数），之后哪边写就只复制被写的块；原生加密——按卷或按文件的密钥（FileVault、iOS Data Protection 的各保护等级），加密在文件系统层而不是整盘层。APFS 的实现（apfs.kext）不开源，但 Apple 公开了磁盘格式规范 Apple File System Reference。延伸阅读：《Operating Systems: Three Easy Pieces》第 42 章「崩溃一致性：FSCK 与日志」；《Practical File System Design with the Be File System》的日志相关章节（作者后来主导了 APFS）。

6. 块层与 I/O 调度

Linux：文件系统把要读写的页组织成 struct bio（目标设备、起始扇区、一组 bio_vec 页段），submit_bio 交给块层。现代块层是 blk-mq：每 CPU 一个软件队列，合并相邻请求成 struct request，再分发到与硬件队列一一对应的 hardware dispatch queue，最后调驱动的 queue_rq（QEMU 里的 virtio-blk 是 virtio_queue_rq，NVMe 是 nvme_queue_rq）。NVMe 本身就有多个硬件队列，blk-mq 的设计正是为它们准备的。I/O 调度器可选 none、mq-deadline、bfq、kyber（/sys/block/<dev>/queue/scheduler），NVMe 上常用 none。设备完成后中断 → 驱动 → blk_mq_complete_request → bio_endio，回调解锁页并唤醒等待者。

XNU：I/O 单位是 buf_t（struct buf，bsd/sys/buf_internal.h）。cluster 层用 VNOP_BLOCKMAP 问文件系统「文件偏移对应哪个设备块」，生成 buf 后经 VNOP_STRATEGY 下发；对块设备 vnode 是 specfs 的 spec_strategy（bsd/miscfs/specfs/spec_vnops.c），这里也执行低优先级 I/O 的节流（throttling，后台任务的 I/O 让位于前台，与 taskpolicy/IOPOL 策略相关）。再往下进入 IOKit 存储栈，大致路径是 BSD 块设备入口 → IOMediaBSDClient → IOMedia → IOBlockStorageDriver → 具体控制器驱动（Apple Silicon 上是 Apple 自家的 NVMe 控制器驱动）。IOKit 驱动层在 Phase 5 展开。

7. 持久化语义：fsync 与 F_FULLFSYNC

「写完」有四个层级：数据在用户缓冲区（stdio）→ 在页缓存（write 返回时）→ 已发给设备但在设备自己的易失写缓存里 → 在持久介质上。只有最后一层能扛住断电。

Linux：fsync(fd) → vfs_fsync_range → f_op->fsync（ext4 是 ext4_sync_file）：写回该文件的脏页、提交日志，并向设备发 cache flush（块层 REQ_PREFLUSH/REQ_FUA 标志）——在默认挂载选项下，Linux 的 fsync 返回就意味着到了持久介质（前提是设备如实执行 flush）。fdatasync 省掉与读取数据无关的元数据（如 mtime）。sync_file_range 不发 flush，不保证持久。O_DIRECT 绕过页缓存，但同样不等于持久。新建文件还要 fsync 它所在的目录，目录项才算落盘。

macOS：man 2 fsync 写得很清楚——fsync 把数据交给驱动器，但不要求驱动器把自己的写缓存刷到介质；要做到这一点需要 fcntl(fd, F_FULLFSYNC)，它额外向设备发 flush 命令，开销显著更高（实验里你会测到数量级差异）。还有一个折中 F_BARRIERFSYNC：只要求顺序（屏障之前的写先于之后的写到达介质），不等全部刷完，适合日志型存储。所以 SQLite 在 macOS 上有 PRAGMA fullfsync，数据库和需要崩溃一致性的应用要显式选择用哪一种——这正是「数据到底什么时候落盘」这个问题在 Apple 平台上的标准答案。

  2. 写一个 /proc 文件模块 lgproc.c，用来观察 VFS 如何把 read 分派到你的代码：
    // lgproc.c
#include <linux/module.h>
#include <linux/proc_fs.h>
#include <linux/seq_file.h>
#include <linux/sched.h>
#include <linux/jiffies.h>

static int lg_show(struct seq_file *m, void *v)
{
	seq_printf(m, "hello from %s (pid %d), jiffies=%lu\n",
		   current->comm, task_pid_nr(current), jiffies);
	return 0;
}

static int __init lgproc_init(void)
{
	if (!proc_create_single("lg_hello", 0444, NULL, lg_show))
		return -ENOMEM;
	return 0;
}

static void __exit lgproc_exit(void)
{
	remove_proc_entry("lg_hello", NULL);
}
module_init(lgproc_init);
module_exit(lgproc_exit);
MODULE_LICENSE("GPL");
    Makefile：obj-m := lgproc.o，然后 make -C ../linux LLVM=1 ARCH=arm64 M="$PWD" modules（同 Phase 3）。

static double now(void) {
  struct timespec ts;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  return ts.tv_sec + ts.tv_nsec / 1e9;
}

int main(int argc, char **argv) {
  const char *mode = argc > 1 ? argv[1] : "fsync";   /* none | fsync | full | barrier */
  char buf[4096];
  int fd = open("synctest.dat", O_WRONLY | O_CREAT | O_TRUNC, 0644);
  if (fd < 0) { perror("open"); return 1; }
  memset(buf, 'x', sizeof buf);
  double t0 = now();
  for (int i = 0; i < 200; i++) {
    if (write(fd, buf, sizeof buf) != (ssize_t)sizeof buf) { perror("write"); return 1; }
    int r = 0;
    if (strcmp(mode, "fsync") == 0) r = fsync(fd);
#ifdef F_FULLFSYNC
    else if (strcmp(mode, "full") == 0) r = fcntl(fd, F_FULLFSYNC);
#endif
#ifdef F_BARRIERFSYNC
    else if (strcmp(mode, "barrier") == 0) r = fcntl(fd, F_BARRIERFSYNC);
#endif
    if (r == -1) { perror(mode); return 1; }
  }
  double dt = now() - t0;
  printf("%-8s 200 x 4 KB: %.3f s  (%.3f ms/op)\n", mode, dt, dt * 1000 / 200);
  close(fd);
  unlink("synctest.dat");
  return 0;
}

自测

1. 在 macOS 上，要确保写入的数据穿过设备的写缓存真正落到持久介质，应使用什么？

macOS 的 fsync 把数据交给设备，但不要求设备清空自己的写缓存；F_FULLFSYNC 额外要求设备 flush，代价更高。F_BARRIERFSYNC 只保证顺序。

2. Linux 中把「路径名分量」映射到 inode、并被缓存以加速路径查找的对象是？

dentry 表示目录项（名字 → inode），由 dcache 缓存；file 表示一次打开，super_block 表示一个已挂载的文件系统实例。XNU 没有独立的 dentry，对应功能由 name cache 承担。

3. 在 Linux 上，一次普通（非 O_DIRECT、非 O_SYNC）的 write() 成功返回时，数据通常在哪里？

buffered write 只把数据拷进页缓存并标脏就返回；回写在超时、脏页比例超限或 fsync/sync 时发生。实验里 /proc/meminfo 的 Dirty 在 sync 前后的变化就是证据。

4. 在 APFS 上 cp -c big.bin clone.bin 克隆一个 1 GB 文件，df 显示可用空间几乎不变，原因是？

clone 是两个独立的文件（inode 不同，修改互不影响），但数据块共享并带引用计数；任一方写入时只复制被修改的块。硬链接是同一个 inode，修改会互相可见。
