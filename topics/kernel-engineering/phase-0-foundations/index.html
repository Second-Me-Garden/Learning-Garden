Foundations 内核基础：特权级、C 系统编程、ARM64、工具链

在读任何一行内核代码之前，先把「内核在 CPU 上到底是怎么跑起来的」这件事搞清楚：用户态和内核态如何切换、内核代码和普通 C 程序有什么不一样、ARM64 上哪些寄存器在管这件事、以及怎么把一个 Linux 内核编出来在 QEMU 里跑。

目标

读完并做完实验后，你应该能：
  • 解释 ARM64 的 exception level（EL0–EL3）和 x86 ring 的对应关系，说清 svc → 内核 → eret 这一来一回 CPU 做了什么。
  • 说出 freestanding C（内核 C）和用户态 C 的 6 个关键区别，并知道 volatile、内存屏障、内联汇编各解决什么问题。
  • 在 macOS（Apple Silicon）上用 LLVM 工具链编译 Linux arm64 内核，并在 QEMU virt 机器上启动到 shell。
  • 在 Linux 和 XNU 源码树里找到「同一件事」各自在哪个目录。

前置

  • C：指针、结构体、函数指针、位运算；读过 CSAPP 第 1–3、7–9 章更好。
  • 知道进程、线程、虚拟内存、系统调用是什么（本阶段不展开，Phase 1–2 展开）。
  • 一台 Apple Silicon Mac + Homebrew；磁盘空余 ≥ 10 GB（Linux 源码树 + 构建产物）。
  • 先按 实验环境 建好 QEMU Linux VM 和构建容器——所有实验都在客体机里做，宿主机不动。

核心概念

1. 内核 = 运行在更高特权级上的那部分代码

CPU 硬件把执行分成若干特权级。ARM64 叫 exception level：EL0 用户程序、EL1 操作系统内核、EL2 hypervisor、EL3 secure monitor（固件）。x86 对应 ring 3 / ring 0（ring 1、2 现代 OS 不用），hypervisor 另有 VMX root mode。「内核态」就是 CPU 处于 EL1（或 ring 0）的状态，此时才能执行特权指令（改页表基址、关中断、访问设备寄存器）。

从 EL0 进入 EL1 只有一条路：触发 exception——同步的（svc 系统调用指令、缺页、非法指令）或异步的（IRQ/FIQ 中断、SError）。CPU 跳到 VBAR_EL1 指向的 exception vector table（16 个入口，每个 0x80 字节，按「来自哪个 EL × 哪类异常」排布），内核从那里接管。返回用户态也只有一条路：eret。

Apple Silicon 补充：据 Asahi Linux 的逆向文档，Apple 的 XNU 在 M 系列芯片上运行于 EL2 并启用 VHE（Virtualization Host Extensions），这样它既是内核也是 Hypervisor.framework 的宿主；用户态仍是 EL0。本阶段只区分 user / kernel 两级即可，EL2 细节放到 Phase 8。

延伸阅读：《Operating Systems: Three Easy Pieces》第 6 章「受限直接执行」；《Computer Systems: A Programmer's Perspective》第 8 章「异常控制流」。

2. 系统调用：一次受控的「越级」

用户程序调 write()，libc 把系统调用号放进约定寄存器、参数放进 x0–x5，执行 svc（Linux 用 svc #0，XNU 的 libsystem 用 svc #0x80；立即数内核不看）。CPU 自动把返回地址存入 ELR_EL1、处理器状态存入 SPSR_EL1、异常原因存入 ESR_EL1，切到 EL1，跳到向量表「来自 lower EL（AArch64）的同步异常」入口（VBAR_EL1 + 0x400）。内核入口汇编把所有通用寄存器压到内核栈，再按号查表分发到具体处理函数；返回时把结果写回 x0，恢复寄存器，eret。下面的动画一步步走这条路，Linux 和 XNU 并排。

一个细节值得记住：Linux arm64 用 x8 传系统调用号，XNU arm64 用 x16；XNU 里正数是 BSD syscall（sysent[]），负数是 Mach trap（mach_trap_table[]）——这是 XNU「两个内核叠在一起」在 ABI 上的直接痕迹。延伸阅读：《Linux Kernel Development》第 5 章「系统调用」；《Understanding the Linux Kernel》第 10 章「系统调用」（x86 视角，流程同构）。

3. 内核 C 和你写过的 C 不一样

区别用户态 C内核 C（freestanding）
标准库有 libc、malloc、printf没有 libc。内核自带 kmalloc/printk（Linux）、kalloc/printf（XNU），没有 stdio.h
栈几 MB，可随意递归每线程 16 KB（Linux arm64）/ 16 KB（XNU arm64）；大数组、深递归直接栈溢出
浮点随便用默认禁止——保存/恢复 FP/SIMD 寄存器太贵；Linux 用 kernel_neon_begin() 显式包起来
内存只有虚拟地址要分清虚拟地址、物理地址、DMA 地址；volatile 访问设备寄存器（MMIO）
并发线程由你创建中断随时打断你；任何共享数据都要考虑锁、关中断、内存屏障（dmb/dsb/isb）
错误处理崩了就崩了内核里一个空指针 = 整机 panic。返回 -errno（Linux）/ KERN_*（Mach）/ errno（BSD 层）
编译器-O2 随便大量 __attribute__（section、aligned、noreturn）、内联汇编、链接脚本决定每段代码放在哪

延伸阅读：《Linux Kernel Development》第 2 章「从内核出发」，其中专门讲内核开发与普通 C 程序的差别。

动手实验

Lab A · 在 macOS 上编译 Linux arm64 内核并在 QEMU 里启动

  1. 工具链：
    brew install qemu llvm lld make
export PATH="$(brew --prefix llvm)/bin:$(brew --prefix make)/libexec/gnubin:$PATH"
    Linux 内核支持纯 LLVM 构建（LLVM=1），不需要 GNU 交叉 gcc。macOS 自带的 make 太旧，用 Homebrew 的 gmake。
  2. 源码：
    git clone --depth 1 https://github.com/torvalds/linux.git
cd linux
make LLVM=1 ARCH=arm64 defconfig
make LLVM=1 ARCH=arm64 -j"$(sysctl -n hw.ncpu)" Image
    注意：macOS 默认文件系统大小写不敏感，内核树里有同名不同大小写的文件会冲突。保险做法：先建一个大小写敏感的 APFS 卷（磁盘工具 → 新增卷 → APFS（区分大小写）），把源码放进去。
  3. 先不带 rootfs 直接启动，看 boot log 走到哪里：
    qemu-system-aarch64 -M virt -cpu cortex-a72 -m 1G -nographic \
  -kernel arch/arm64/boot/Image -append "console=ttyAMA0 earlycon"
    你会看到内核初始化全过程，最后 panic：VFS: Unable to mount root fs——这是预期的，它证明内核本身已经跑完了 Phase 1 要讲的整条启动链。Ctrl-a x 退出 QEMU。
  4. 给它一个最小 initramfs（busybox）。在 macOS 上直接编 busybox 很麻烦，走 Linux 容器（Docker Desktop 或 OrbStack）：
    docker run --platform linux/arm64 --rm -v "$PWD/initramfs:/out" alpine:3.20 sh -c '
  apk add -q busybox-static &&
  mkdir -p /r/bin /r/proc /r/sys /r/dev &&
  cp /bin/busybox.static /r/bin/busybox &&
  for c in sh ls cat echo mount uname dmesg; do ln -s busybox /r/bin/$c; done &&
  printf "#!/bin/sh\nmount -t proc none /proc\nmount -t sysfs none /sys\nexec /bin/sh\n" > /r/init &&
  chmod +x /r/init &&
  cd /r && find . | cpio -o -H newc | gzip > /out/initramfs.cpio.gz'
    然后：
    qemu-system-aarch64 -M virt -cpu cortex-a72 -m 1G -nographic \
  -kernel arch/arm64/boot/Image -initrd initramfs/initramfs.cpio.gz \
  -append "console=ttyAMA0 rdinit=/init"
    进 shell 后试 uname -a、cat /proc/cpuinfo、dmesg | head -40。
  5. 看看你刚才动画里的东西真的存在：
    llvm-objdump -d vmlinux --disassemble-symbols=el0t_64_sync | head -40
grep -n "el0t_64_sync\|kernel_entry" arch/arm64/kernel/entry.S | head

Lab B · 在 macOS 上看 XNU 的痕迹

  1. 内核版本与构建：
    uname -a
sysctl kern.version kern.osproductversion hw.ncpu machdep.cpu.brand_string
  2. 已加载的内核扩展（现在大多数是 Apple 自己的，第三方驱动已迁到 DriverKit）：
    kmutil showloaded --list-only | head -30
  3. 内核日志（相当于 dmesg）：
    log show --last 5m --predicate 'process == "kernel"' | tail -50
  4. 看一个进程的系统调用（dtruss 需要关 SIP，先用文件系统视角的 fs_usage）：
    sudo fs_usage -w -f filesys -t 5 2>/dev/null | head -50
  5. 下载 XNU 源码，找到动画里的函数：
    git clone --depth 1 https://github.com/apple-oss-distributions/xnu.git
cd xnu
grep -n "fleh_synchronous\|sleh_synchronous" osfmk/arm64/locore.s osfmk/arm64/sleh.c | head
grep -n "^[0-9]" bsd/kern/syscalls.master | head -20   # BSD syscall 表
grep -n "MACH_TRAP" osfmk/kern/syscall_sw.c | head       # Mach trap 表
交付物：一张 QEMU 里 uname -a 的截图 + 你用自己的话写的「svc 到 eret 发生了什么」（10 行以内），放进 docs/agent/logs/ 当天的日志。

自测

1. ARM64 上，普通应用程序运行在哪个 exception level？

EL0 = user，EL1 = kernel，EL2 = hypervisor，EL3 = secure monitor。

2. 执行 svc 之后，用户态的返回地址被硬件保存在哪里？

ELR_EL1 存返回地址，SPSR_EL1 存进入前的 PSTATE，ESR_EL1 存异常原因。x30 是函数调用的 LR，异常不会碰它。

3. XNU arm64 上系统调用号放在哪个寄存器？负数的号表示什么？

XNU 用 x16（Linux 用 x8）。正数查 sysent[]（BSD），负数查 mach_trap_table[]（Mach）。

4. 为什么内核代码默认不能用浮点运算？

保存 32 个 128 位寄存器太贵，所以异常入口默认只保存通用寄存器。
