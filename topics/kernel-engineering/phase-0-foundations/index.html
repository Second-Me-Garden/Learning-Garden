Foundations 内核基础：特权级、C 系统编程、ARM64、工具链Kernel foundations: privilege levels, C systems programming, ARM64, the toolchain

核心概念

Core concepts

内核和你的程序跑在同一颗 CPU、同一套寄存器上。如果用户程序能随手改页表基址、关中断，任何一个 bug 都能拖垮整台机器；可如果它完全碰不到内核，又没法读文件、开网络。所以硬件必须同时做到两件事：平时把用户代码关在低特权级，又留一扇只能从固定位置进入、用完必须原路返回的门。

The kernel and your program run on the same CPU with the same registers. If a user program could casually change the page-table base or disable interrupts, any bug could bring down the whole machine; yet if it could never reach the kernel, it could not read a file or open a socket. So the hardware has to do two things at once: keep user code locked at a low privilege level, and leave one door that can only be entered at fixed places and must be exited the way it came.

回答它的是概念 1 的 exception level 与异常向量表，概念 2 的系统调用就是走这扇门的一次完整往返。

Concept 1, exception levels and the exception vector table, answers it; concept 2, the system call, is one complete round trip through that door.

1. 内核 = 运行在更高特权级上的那部分代码

1. The kernel = the code that runs at a higher privilege level

CPU 硬件把执行分成若干特权级。ARM64 叫 exception level：EL0 用户程序、EL1 操作系统内核、EL2 hypervisor、EL3 secure monitor（固件）。x86 对应 ring 3 / ring 0（ring 1、2 现代 OS 不用），hypervisor 另有 VMX root mode。「内核态」就是 CPU 处于 EL1（或 ring 0）的状态，此时才能执行特权指令（改页表基址、关中断、访问设备寄存器）。

CPU hardware divides execution into privilege levels. ARM64 calls them exception levels: EL0 user programs, EL1 the operating-system kernel, EL2 the hypervisor, EL3 the secure monitor (firmware). On x86 the counterparts are ring 3 / ring 0 (modern OSes do not use rings 1 and 2), with VMX root mode separately for the hypervisor. "Kernel mode" is the state in which the CPU is at EL1 (or ring 0); only then can it execute privileged instructions (changing the page-table base, disabling interrupts, accessing device registers).

从 EL0 进入 EL1 只有一条路：触发 exception——同步的（svc 系统调用指令、缺页、非法指令）或异步的（IRQ/FIQ 中断、SError）。CPU 跳到 VBAR_EL1 指向的 exception vector table（16 个入口，每个 0x80 字节，按「来自哪个 EL × 哪类异常」排布），内核从那里接管。返回用户态也只有一条路：eret。

There is only one way from EL0 into EL1: raising an exception — synchronous (the svc system-call instruction, a page fault, an illegal instruction) or asynchronous (IRQ/FIQ interrupts, SError). The CPU jumps to the exception vector table that VBAR_EL1 points to (16 entries of 0x80 bytes each, laid out by "which EL it came from × which kind of exception"), and the kernel takes over from there. There is also only one way back to user mode: eret.

CPU 怎么在 16 个入口里挑一个？入口地址 = VBAR_EL1 + 组基址 + 类型偏移。组由「从哪来」决定，类型由「哪类异常」决定，每个入口 0x80 字节（32 条指令），整张表 16 × 0x80 = 0x800 字节。下面三个例子对应下方图解 B。

How does the CPU pick one of the 16 entries? Entry address = VBAR_EL1 + group base + type offset. The group is decided by "where it came from", the type by "which kind of exception"; each entry is 0x80 bytes (32 instructions), so the whole table is 16 × 0x80 = 0x800 bytes. The three examples below match diagram B further down.

组基址 / group base             类型偏移 / type offset
0x000  current EL, SP_EL0       +0x000  Synchronous
0x200  current EL, SP_ELx       +0x080  IRQ
0x400  lower EL, AArch64        +0x100  FIQ
0x600  lower EL, AArch32        +0x180  SError

  2. 同一个用户程序运行时网卡来了 IRQ（路由到 EL1）：0x400 + 0x080 = VBAR_EL1 + 0x480。
  3. 内核自己在 EL1、用 SP_EL1 时来了 IRQ：当前 EL、SP_ELx 组 → 0x200 + 0x080 = VBAR_EL1 + 0x280（Arm 指南里正是这个例子）。
  1. User mode (EL0, AArch64) executes svc #0: a synchronous exception from a lower EL in AArch64 → 0x400 + 0x000 = VBAR_EL1 + 0x400.
  2. An IRQ from the network card arrives (routed to EL1) while the same user program runs: 0x400 + 0x080 = VBAR_EL1 + 0x480.
  3. An IRQ arrives while the kernel itself runs at EL1 on SP_EL1: the current-EL, SP_ELx group → 0x200 + 0x080 = VBAR_EL1 + 0x280 (exactly the example in the Arm guide).

Linux 的 arch/arm64/kernel/entry.S 里 vectors 表的 16 行 kernel_ventry 就按这个顺序排列（EL1t、EL1h、64-bit EL0、32-bit EL0，每组 sync/irq/fiq/error）；XNU 的 osfmk/arm64/locore.s 只填了前 12 个入口，AArch32 那一组没有处理代码。

In Linux’s arch/arm64/kernel/entry.S, the 16 kernel_ventry lines of the vectors table are laid out in exactly this order (EL1t, EL1h, 64-bit EL0, 32-bit EL0, each group sync/irq/fiq/error); XNU’s osfmk/arm64/locore.s fills in only the first 12 entries and has no handler code for the AArch32 group.

2. 系统调用：一次受控的「越级」

2. System calls: a controlled jump in privilege

用户程序调 write()，libc 把系统调用号放进约定寄存器、参数放进 x0–x5，执行 svc（Linux 用 svc #0，XNU 的 libsystem 用 svc #0x80；立即数内核不看）。CPU 自动把返回地址存入 ELR_EL1、处理器状态存入 SPSR_EL1、异常原因存入 ESR_EL1，切到 EL1，跳到向量表「来自 lower EL（AArch64）的同步异常」入口（VBAR_EL1 + 0x400）。内核入口汇编把所有通用寄存器压到内核栈，再按号查表分发到具体处理函数；返回时把结果写回 x0，恢复寄存器，eret。下面的动画一步步走这条路，Linux 和 XNU 并排。

A user program calls write(); libc puts the system call number in the agreed register and the arguments in x0–x5, then executes svc (Linux uses svc #0, XNU's libsystem uses svc #0x80; the kernel ignores the immediate). The CPU automatically saves the return address in ELR_EL1, the processor state in SPSR_EL1 and the exception cause in ESR_EL1, switches to EL1, and jumps to the vector-table entry for "synchronous exception from a lower EL (AArch64)" (VBAR_EL1 + 0x400). The kernel entry assembly pushes all general-purpose registers onto the kernel stack, then looks the number up in a table and dispatches to the specific handler; on return it writes the result back to x0, restores the registers and executes eret. 追一次真实的调用：用户程序执行 write(1, "hello\n", 6)，往标准输出写 6 个字节。

Trace one real call: a user program executes write(1, "hello\n", 6), writing 6 bytes to standard output.

  1. libc 装寄存器：x0 = 1（fd）、x1 = 缓冲区地址、x2 = 6；Linux 放 x8 = 64（scripts/syscall.tbl 里 write 是 64），XNU 放 x16 = 4（bsd/kern/syscalls.master 里 write 是 4）。
  2. 执行 svc #0（XNU 是 svc #0x80）。硬件写 ESR_EL1：EC 位于 [31:26]，SVC64 的 EC 是 0x15；IL 位 [25] = 1 表示 32 位指令；ISS 的低 16 位是 svc 的立即数。所以 Linux 得到 0x15 << 26 | 1 << 25 | 0 = 0x56000000，XNU 得到 0x56000080。
  3. PC 跳到 VBAR_EL1 + 0x400（上一个例子的第 1 行）。
  4. Linux：el0t_64_sync_handler 读出 EC = 0x15 = ESR_ELx_EC_SVC64 → el0_svc → do_el0_svc 取 regs->regs[8] = 64 → invoke_syscall → sys_call_table[64] = __arm64_sys_write。
  5. XNU：sleh_synchronous 看到 ESR_EC_SVC_64 → handle_svc，x16 = 4 不小于 0 → unix_syscall → sysent[4]。
  6. 写成功返回 6：结果写进保存的 x0，eret 回到 svc 的下一条指令，用户程序看到 write 返回 6。
  1. libc loads the registers: x0 = 1 (fd), x1 = the buffer address, x2 = 6; Linux sets x8 = 64 (write is 64 in scripts/syscall.tbl), XNU sets x16 = 4 (write is 4 in bsd/kern/syscalls.master).
  2. It executes svc #0 (svc #0x80 on XNU). The hardware writes ESR_EL1: EC sits in [31:26] and is 0x15 for SVC64; the IL bit [25] = 1 marks a 32-bit instruction; the low 16 bits of the ISS hold the svc immediate. So Linux gets 0x15 << 26 | 1 << 25 | 0 = 0x56000000, and XNU gets 0x56000080.
  3. The PC jumps to VBAR_EL1 + 0x400 (item 1 of the previous example).
  4. Linux: el0t_64_sync_handler reads EC = 0x15 = ESR_ELx_EC_SVC64 → el0_svc → do_el0_svc takes regs->regs[8] = 64 → invoke_syscall → sys_call_table[64] = __arm64_sys_write.
  5. XNU: sleh_synchronous sees ESR_EC_SVC_64 → handle_svc; x16 = 4 is not negative → unix_syscall → sysent[4].
  6. The write succeeds and returns 6: the result goes into the saved x0, eret returns to the instruction after svc, and the user program sees write return 6.

一个细节值得记住：Linux arm64 用 x8 传系统调用号，XNU arm64 用 x16；XNU 里正数是 BSD syscall（sysent[]），负数是 Mach trap（mach_trap_table[]）——这是 XNU「两个内核叠在一起」在 ABI 上的直接痕迹。延伸阅读：《Linux Kernel Development》第 5 章「系统调用」；《Understanding the Linux Kernel》第 10 章「系统调用」（x86 视角，流程同构）。

One detail worth remembering: Linux arm64 passes the system call number in x8, XNU arm64 in x16; in XNU positive numbers are BSD syscalls (sysent[]) and negative numbers are Mach traps (mach_trap_table[]) — a direct trace in the ABI of XNU being "two kernels stacked together". Further reading: Linux Kernel Development chapter 5, "System Calls"; Understanding the Linux Kernel chapter 10, "System Calls" (an x86 view; the flow has the same shape).

  • 用户程序跑在 EL0，内核跑在 EL1；只有 EL1 能执行改页表、关中断这类特权指令。
  • 从 EL0 进 EL1 只能靠异常，返回只能靠 eret；系统调用就是用 svc 主动触发的同步异常。
  • CPU 按「从哪来 × 什么类型」在 VBAR_EL1 指向的 16 个入口里挑一个，从 64 位程序发出的用户态 svc 落在 VBAR_EL1 + 0x400（AArch32 的 EL0 落在 +0x600）。
  • 硬件只保存返回地址（ELR_EL1）、PSTATE（SPSR_EL1）和原因（ESR_EL1），通用寄存器由入口汇编自己压栈。
  • Linux 用 x8 传系统调用号，XNU 用 x16，XNU 的负号是 Mach trap。
  • 内核 C 没有 libc、栈只有 16 KB、默认不用浮点，一个空指针就是整机 panic。
  • User programs run at EL0 and the kernel at EL1; only EL1 can execute privileged instructions such as changing page tables or disabling interrupts.
  • The only way from EL0 into EL1 is an exception and the only way back is eret; a system call is a synchronous exception raised on purpose with svc.
  • The CPU picks one of the 16 entries at VBAR_EL1 by "where from × which type", and a user-mode svc from a 64-bit program lands at VBAR_EL1 + 0x400 (an AArch32 EL0 lands at +0x600).
  • The hardware saves only the return address (ELR_EL1), PSTATE (SPSR_EL1) and the cause (ESR_EL1); the entry assembly pushes the general-purpose registers itself.
  • Linux passes the system call number in x8 and XNU in x16, where a negative number is a Mach trap.
  • Kernel C has no libc, a 16 KB stack and no floating point by default, and one null pointer panics the whole machine.

常见误解

Common misconceptions

  • 误解：向量表里存的是处理函数的地址。→ 实际：AArch64 向量表里存的是指令，每个入口最多 32 条，CPU 直接跳进去执行。
  • 误解：svc 的立即数就是系统调用号。→ 实际：Linux 和 XNU 都不看立即数，号在 x8 / x16 里；立即数只出现在 ESR_EL1 的 ISS 里。
  • 误解：进内核时 CPU 会自动保存所有寄存器。→ 实际：硬件只存 PC、PSTATE 和原因，x0–x30 要入口汇编自己存；在 Linux 上 FP/SIMD 寄存器进入内核时不保存、按需惰性切换，XNU 则在每次进入时把 NEON 寄存器存进异常帧。
  • Myth: the vector table holds the addresses of the handlers. → Fact: an AArch64 vector table holds instructions, up to 32 per entry, and the CPU jumps straight in and executes them.
  • Myth: the svc immediate is the system call number. → Fact: neither Linux nor XNU looks at the immediate; the number is in x8 / x16, and the immediate only shows up in the ISS of ESR_EL1.
  • Myth: the CPU saves every register automatically on kernel entry. → Fact: the hardware saves only the PC, PSTATE and the cause; x0–x30 are saved by the entry assembly; on Linux the FP/SIMD registers are not saved on kernel entry and are switched lazily, while XNU saves the NEON registers in the exception frame on every entry.

自测

Self-check

1. ARM64 上，普通应用程序运行在哪个 exception level？

1. On ARM64, which exception level do ordinary applications run at?

EL0 = user，EL1 = kernel，EL2 = hypervisor，EL3 = secure monitor。EL0 = user, EL1 = kernel, EL2 = hypervisor, EL3 = secure monitor.

2. 执行 svc 之后，用户态的返回地址被硬件保存在哪里？

2. After svc executes, where does the hardware save the user-mode return address?

ELR_EL1 存返回地址，SPSR_EL1 存进入前的 PSTATE，ESR_EL1 存异常原因。x30 是函数调用的 LR，异常不会碰它。ELR_EL1 holds the return address, SPSR_EL1 the PSTATE before entry, ESR_EL1 the exception cause. x30 is the LR for function calls; exceptions do not touch it.

3. XNU arm64 上系统调用号放在哪个寄存器？负数的号表示什么？

3. On XNU arm64, which register holds the system call number? What does a negative number mean?

XNU 用 x16（Linux 用 x8）。正数查 sysent[]（BSD），负数查 mach_trap_table[]（Mach）。XNU uses x16 (Linux uses x8). Positive numbers look up sysent[] (BSD), negative ones mach_trap_table[] (Mach).

4. 为什么内核代码默认不能用浮点运算？

4. Why can kernel code not use floating point by default?

保存 32 个 128 位寄存器太贵，所以异常入口默认只保存通用寄存器。Saving 32 128-bit registers is too expensive, so by default the exception entry saves only the general-purpose registers.
