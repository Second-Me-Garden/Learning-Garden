CUDA Graphs and the plan()/run() Split CUDA 图与 plan()/run() 拆分：为什么解码步要被捕获、图里不许做什么、按固定批大小填充，以及 FlashInfer 把 CPU 上的 plan() 和图里的 run() 分开Why decode steps are captured, what a graph may not contain, padding to fixed batch sizes, and how FlashInfer separates plan() on the CPU from run() inside the graph

解码的每一步要跑完所有层的所有内核，而小批次下每个内核都很短，CPU 一个一个地发射它们的开销可能和内核本身一样长。CUDA 图把一整步的内核连同参数录下来，之后每步只用一次调用重放。代价是图是死的：形状、指针、控制流都在捕获时定下，图里不能同步主机、不能按数据分配内存、不能换批大小。SGLang 的回答是三件事：按一组固定批大小各捕获一张图，把真实批次填充到最近的那个尺寸；把注意力后端的准备工作拆成图外和图内两半；用 FlashInfer 的 plan()/run() 拆分，在 CPU 上算好调度，写进地址固定的缓冲区，让图里的 run() 去读。这台 Apple M5 上的 Metal 对照实测：一步 512 个小内核，每个内核一个命令缓冲区时每步约 7.7–7.8 ms，编码一次、每步重放的间接命令缓冲区约 1.8–1.9 ms，而它的 CPU 编码时间不随内核数增长。

Every decode step runs every kernel of every layer, and at small batch sizes each kernel is short, so the CPU cost of launching them one at a time can be as long as the kernels themselves. A CUDA graph records a whole step’s kernels with their arguments, and each later step replays it with a single call. The price is that a graph is frozen: shapes, pointers and control flow are fixed at capture, so a graph cannot synchronize with the host, allocate memory by data, or change batch size. SGLang answers with three things: it captures one graph per size in a fixed list of batch sizes and pads the real batch up to the nearest one; it splits the attention backend’s preparation into an out-of-graph half and an in-graph half; and it uses FlashInfer’s plan()/run() split, computing the schedule on the CPU and writing it into fixed-address buffers that run() reads inside the graph. Measured with the Metal twin on this Apple M5: a step of 512 small kernels takes about 7.7–7.8 ms with one command buffer per kernel and about 1.8–1.9 ms as an indirect command buffer encoded once and replayed each step, whose CPU encoding time does not grow with the kernel count.

1. 为什么要捕获解码步：发射开销对微秒级内核

1. Why decode steps are captured: launch overhead against microsecond-class kernels

CUDA Programming Guide 的 4.2 节是这样讲的：把内核放进流时，主机驱动要为每个内核做一串准备和发射操作，这笔开销每个内核都要付一次；对执行时间很短的内核，这笔开销可能占端到端时间的相当一部分。图把整个工作流事先定义好，这些开销在实例化时付一次，之后每次发射图本身「开销很小」。PyTorch 的 CUDA 语义说明（docs/source/notes/cuda.md 的 CUDA Graphs 一节）说得更具体：重放跳过了参数设置和内核分派的所有层次，包括 Python、C++ 和 CUDA 驱动的开销，底层只用一次 cudaGraphLaunch 提交整张图；图里的内核在 GPU 上也略快一点，但主要收益是省掉 CPU 开销。

Section 4.2 of the CUDA Programming Guide puts it this way: when you place a kernel into a stream, the host driver performs a sequence of preparation and launch operations, an overhead paid for every kernel issued; for a kernel with a short execution time, this overhead can be a significant fraction of the end-to-end time. A graph defines the whole workflow in advance, so those costs are paid once at instantiation, and launching the graph afterwards has very little overhead. The PyTorch CUDA semantics notes (the CUDA Graphs section of docs/source/notes/cuda.md) are more specific: a replay skips all layers of argument setup and kernel dispatch, including Python, C++ and CUDA driver overheads, and submits the entire graph with a single cudaGraphLaunch; kernels in a replay also run slightly faster on the GPU, but eliding CPU overhead is the main benefit.

解码正落在这个区间里。一步解码对批里每个请求只算一个 token，每一层都要跑归一化、QKV 投影、RoPE、注意力、输出投影、MLP 这一串内核（Phase 0），而批小时每个 GEMM 只是一次 GEMV、每个注意力内核只读几个请求的 KV，内核很短。实验环境页选的 Qwen3-0.6B 有 28 层，一步就是 28 遍这一串。CPU 在 Python 里逐个发射它们时，GPU 可能在两个内核之间空等（推断，Lab A 第 1 步会量）。预填充则相反：一次算成百上千个 token，内核长，发射开销占比小，所以 v0.5.22 的预填充图默认用 breakable 后端，full 被标为实验性（python/sglang/srt/arg_groups/cuda_graph_hook.py 第 365–369 行的警告）。

Decode falls squarely in that range. A decode step computes one token for each request in the batch, and every layer runs the chain of normalization, QKV projection, RoPE, attention, output projection and MLP kernels (Phase 0); at a small batch each GEMM is just a GEMV and each attention kernel reads the KV of a few requests, so the kernels are short. Qwen3-0.6B, the model the lab environment page uses, has 28 layers, so one step is 28 passes of that chain. While the CPU launches them one by one from Python, the GPU may sit idle between kernels (inference; step 1 of Lab A measures it). Prefill is the opposite: hundreds or thousands of tokens at once, long kernels, and a small share for launch overhead, which is why v0.5.22 defaults the prefill graph to the breakable backend and marks full as experimental (the warning at lines 365–369 of python/sglang/srt/arg_groups/cuda_graph_hook.py).

2. 能被捕获的内核不能做什么

2. What a capturable kernel may not do

流处于捕获模式时，发给它的工作并不执行，只被记进图里；重放时图用同样的内核、同样的参数，对指针参数来说就是同样的内存地址（PyTorch 说明原话）。由此推出一张禁止清单。PyTorch 说明的 Constraints 一节把它分成两类：

While a stream is in capture mode, work issued to it does not run; it is only recorded into the graph, and every replay runs the same kernels with the same arguments, which for pointer arguments means the same memory addresses (the PyTorch notes’ own words). A list of prohibitions follows from that. The Constraints section of the PyTorch notes splits it in two:

  • 多半直接报运行时错误：同步 CPU 和 GPU 的操作（例如 .item()）；基于 CPU 或 GPU 数据的动态控制流（除非用 torch.cond()）；在默认流上捕获。CUDA 指南的 Prohibited and Unhandled Operations 一节给出底层原因：同步或查询一个正在被捕获的流是无效的，因为里面的工作并没有被调度执行。
  • Most likely a runtime error: ops that synchronize the CPU with the GPU (for example .item()); dynamic control flow based on CPU or GPU data (unless written with torch.cond()); capturing on the default stream. The Prohibited and Unhandled Operations section of the CUDA guide gives the underlying reason: synchronizing or querying a stream that is being captured is invalid, because its work has not been scheduled for execution.
  • 多半悄悄算错：捕获区里的 CPU 工作不会被录下，重放时直接没了；每次重放读写同样的虚拟地址；动态形状被禁止，图假定每个张量每次重放都是同样的大小和布局；捕获进行中，进程里不能有别的未被捕获的 CUDA 工作。
  • Most likely silent wrong results: CPU work in the captured region is not recorded and simply vanishes at replay; every replay reads and writes the same virtual addresses; dynamic shapes are prohibited, since the graph assumes every tensor has the same size and layout in every replay; and no non-captured CUDA work may run in the process while a capture is underway.

「动态分配」落在两条之间。在捕获区里新建一个张量本身是可以的：PyTorch 的分配器在捕获时从这张图私有的内存池里拿地址，重放时这块地址固定不变（CUDA 指南的 Graph Memory Nodes 一节也说，图内分配在图的整个生命周期里地址固定）。不可以的是让大小依赖数据：图只录下捕获那一次的大小，下一步数据变大了，图仍然用那块旧内存（推断，依据是上面两条规则）。SGLang 把这条写成了合同：base_attn_backend.py 第 124–127 行规定 init_forward_metadata_in_graph 的函数体不许调 .item()、.cpu()、.tolist() 和动态形状的 torch.empty()，这些都属于图外。对内核作者来说，结论是：内核的网格大小、指针和形状参数在捕获时就定了，一切每步会变的量（长度、偏移、真实批大小）都必须从地址固定的显存缓冲区里读。

Dynamic allocation sits between the two lists. Creating a tensor inside the captured region is itself allowed: PyTorch’s allocator hands out addresses from the graph’s private memory pool during capture, and those addresses stay fixed for every replay (the Graph Memory Nodes section of the CUDA guide likewise says graph allocations have fixed addresses for the life of the graph). What is not allowed is a size that depends on data: the graph records only the size seen at capture, and when a later step needs more, the graph still uses the old block (inference from the two rules above). SGLang writes this down as a contract: lines 124–127 of base_attn_backend.py say the body of init_forward_metadata_in_graph must not call .item(), .cpu(), .tolist() or a dynamic-shape torch.empty(); those belong outside the graph. For a kernel author the conclusion is this: the grid size, pointers and shape arguments of a kernel are fixed at capture, so anything that changes from step to step (lengths, offsets, the real batch size) has to be read from a GPU buffer whose address does not change.

3. 填充到固定的批大小：SGLang 的捕获尺寸

3. Padding to static batch sizes: SGLang’s capture sizes

批大小每一步都在变（请求进来、结束），而一张图只认一个形状，所以 SGLang 预先为一组批大小各捕获一张图，运行时把真实批次填充到最近的那个。这组尺寸由 cuda_graph_hook.py 第 462–494 行的 generate_decode_cuda_graph_batch_sizes 产生，普通情况（没有推测解码）是：

The batch size changes from step to step (requests arrive and finish), and a graph knows only one shape, so SGLang captures one graph for each size in a list of batch sizes ahead of time and pads the real batch up to the nearest one at run time. The list comes from generate_decode_cuda_graph_batch_sizes, lines 462–494 of cuda_graph_hook.py; in the ordinary case (no speculative decoding) it is:

    [1, 2, 4, 8, 12]
    + list(range(16, 257, 8))
    + list(range(272, 512, 16))
    + list(range(512, max_bs + 1, 32))
)
# 之后去掉大于 max_bs 的，如果 max_bs 不在表里就补上（第 489–492 行）

小批次处密、大批次处疏：批大小 13 填到 16，浪费 3 行；批大小 100 填到 104，浪费 4 行。打开 --disable-cuda-graph-padding 时表变成 1 到 max_bs 的每一个整数（第 469–470 行），但正如它的帮助文字所说，遇到需要填充的批次就不用图；推测解码另有一张更密的表（第 479–487 行）。max_bs 的默认值按显卡显存分档，在 arg_groups/memory_hook.py 第 88–180 行：小于 20 GB（注释写的是 T4、4080）为 8；小于 35 GB（A10、4090、5090）在 tp_size 小于 4 时为 48；小于 60 GB（A100 40GB、L40）为 32；小于 90 GB（H100、A100）为 256。按这个分档，24 GB 的 L4 落在第二档，max_bs 为 48，表就是 [1, 2, 4, 8, 12, 16, 24, 32, 40, 48]（推断：取决于 SGLang 读到的显存数，Lab A 第 2 步从启动日志核对）。

The list is dense at small batches and sparse at large ones: a batch of 13 pads to 16, wasting 3 rows, and a batch of 100 pads to 104, wasting 4. With --disable-cuda-graph-padding the list becomes every integer from 1 to max_bs (lines 469–470), but, as its help text says, a batch that would need padding then runs without a graph; speculative decoding has its own denser list (lines 479–487). The default max_bs depends on GPU memory, in tiers at lines 88–180 of arg_groups/memory_hook.py: below 20 GB (the comment names T4 and 4080) it is 8; below 35 GB (A10, 4090, 5090) it is 48 when tp_size is under 4; below 60 GB (A100 40GB, L40) 32; below 90 GB (H100, A100) 256. By these tiers the 24 GB L4 falls in the second, so max_bs is 48 and the list is [1, 2, 4, 8, 12, 16, 24, 32, 40, 48] (inference: it depends on the memory figure SGLang reads; step 2 of Lab A checks it in the start-up log).

Phase 1 showed that at the start of each forward step the backend’s init_forward_metadata builds kv_indptr and kv_indices and calls plan(). 5. FlashInfer 的 plan() 在 CPU 上，run() 在图里

5. FlashInfer: plan() on the CPU, run() in the graph

FlashInfer 论文（arXiv:2501.01005 v2）的 3.3 节 Dynamism-Aware Runtime 和 3.4 节 Programming Interface 讲了这个拆分。plan 函数拿到各请求的序列长度，启动负载均衡的调度器，在 CPU 上算出调度计划（每个线程块的工作队列，以及部分结果到最终输出的映射），再异步拷到 GPU 上工作区缓冲区里固定的一段；计划可以缓存，一步解码里所有层的注意力共用一份。run 函数用查询、键值和这份缓存的计划算注意力。论文原话：CUDA 图可以捕获对 run 的调用，把整步注意力编进一张图；但 plan 不会被 CUDA 图捕获，因为它在 CPU 上。论文说这个拆分受 inspector-executor 模型启发（引 Mirchandaney 等 1988 年的工作）。为了满足图的要求，注意力和合并两个阶段都用持久化内核，网格大小编译后固定，每步都以同样的网格启动；工作区各段的偏移固定，传给内核的指针每步相同。

Section 3.3, Dynamism-Aware Runtime, and section 3.4, Programming Interface, of the FlashInfer paper (arXiv:2501.01005 v2) describe the split. The plan function takes each request’s sequence length, runs the load-balanced scheduler, and computes a schedule on the CPU (the work queue of each thread block, and the mapping from partial results to final outputs), then copies it asynchronously into a fixed region of the workspace buffer on the GPU; the plan can be cached and shared by the attention of every layer in a decode step. The run function computes attention from the query, the keys and values, and the cached plan. In the paper’s words, a CUDA graph can capture calls to run and compile the whole step of attention into one graph, but plan is not captured, because it is on the CPU. The paper says the split is inspired by the inspector-executor model (citing Mirchandaney et al., 1988). To meet the graph’s requirements, both the attention stage and the merge stage use persistent kernels whose grid size is fixed once compiled, so each step launches the same grid, and each section of the workspace has a fixed offset, so the pointers passed to the kernels are the same every step.

// The ICB: all dispatches encoded once, a barrier after each so layer l + 1 waits for layer l.
func makeICB(_ S: Int) -> MTLIndirectCommandBuffer {
    let d = MTLIndirectCommandBufferDescriptor()
    d.commandTypes = .concurrentDispatch
    d.inheritBuffers = false; d.inheritPipelineState = false; d.maxKernelBufferBindCount = 4

        c.setComputePipelineState(pso)
        c.setKernelBuffer(x, offset: 0, at: 0); c.setKernelBuffer(kv, offset: 0, at: 1)
        c.setKernelBuffer(meta, offset: 0, at: 2); c.setKernelBuffer(layers, offset: l * 4, at: 3)
        c.concurrentDispatchThreadgroups(grid, threadsPerThreadgroup: tg)
        c.setBarrier()
    }
    return icb
}

enum Mode: String, CaseIterable {
    case perKernelCB = "S command buffers, 1 dispatch each"
    case encodersInOneCB = "1 command buffer, S encoders"
    case oneEncoder = "1 command buffer, 1 encoder"
    case icb = "indirect command buffer, encoded once"
}

func runStep(_ mode: Mode, _ S: Int, _ icb: MTLIndirectCommandBuffer) -> (encode: Double, wall: Double, gpu: Double) {
    let t0 = DispatchTime.now().uptimeNanoseconds
    var cbs: [MTLCommandBuffer] = []
    switch mode {
    case .perKernelCB:                                  // like eager launches: one submission per kernel
        for l in 0..<S {
            let cb = queue.makeCommandBuffer()!, enc = cb.makeComputeCommandEncoder()!
            enc.setComputePipelineState(pso); bind(enc, l)
            enc.dispatchThreadgroups(grid, threadsPerThreadgroup: tg); enc.endEncoding()
            cb.commit(); cbs.append(cb)
        }
    case .encodersInOneCB:
        let cb = queue.makeCommandBuffer()!
        for l in 0..<S {
            let enc = cb.makeComputeCommandEncoder()!
            enc.setComputePipelineState(pso); bind(enc, l)
            enc.dispatchThreadgroups(grid, threadsPerThreadgroup: tg); enc.endEncoding()
        }
        cb.commit(); cbs.append(cb)
    case .oneEncoder:                                   // default (serial) dispatch type keeps the order
        let cb = queue.makeCommandBuffer()!, enc = cb.makeComputeCommandEncoder()!
        enc.setComputePipelineState(pso)
        for l in 0..<S { bind(enc, l); enc.dispatchThreadgroups(grid, threadsPerThreadgroup: tg) }
        enc.endEncoding(); cb.commit(); cbs.append(cb)
    case .icb:                                          // the replay: one call, whatever S is
        let cb = queue.makeCommandBuffer()!, enc = cb.makeComputeCommandEncoder()!
        enc.useResource(x, usage: [.read, .write])
        enc.useResources([kv, meta, layers], usage: .read)
        enc.executeCommandsInBuffer(icb, range: 0..<S)
        enc.endEncoding(); cb.commit(); cbs.append(cb)
    }
    let t1 = DispatchTime.now().uptimeNanoseconds

    let t2 = DispatchTime.now().uptimeNanoseconds
    return (Double(t1 - t0) * 1e-9, Double(t2 - t0) * 1e-9, cbs.last!.gpuEndTime - cbs.first!.gpuStartTime)
}

自测

Self-check

1. SGLang 为什么默认给解码步用完整的 CUDA 图，而对预填充的完整图标为实验性？

1. Why does SGLang use a full CUDA graph for decode steps by default, while marking a full prefill graph experimental?

PyTorch 说明讲得很清楚：图的主要收益是省掉 CPU 开销，内核在 GPU 上只略快，读的字节数不变。分页 KV 在不用图时照样工作（Phase 1 的实验就是关着图做的），带缓存前缀的预填充也读分页的 KV。剩下的解释是内核长短：短内核时发射开销才显著。The PyTorch notes are clear: the main benefit of a graph is eliding CPU overhead, kernels run only slightly faster on the GPU, and the bytes read do not change. The paged KV cache works fine without graphs (the Phase 1 lab ran with them off), and a prefill with a cached prefix reads paged KV too. What remains is kernel length: launch overhead matters when kernels are short.

2. 在 v0.5.22 的默认捕获表下（没有推测解码，max_bs 为 48），一个 13 个请求的解码批次用哪张图？

2. With the v0.5.22 default capture list (no speculative decoding, max_bs of 48), which graph does a decode batch of 13 requests use?

默认表是 [1, 2, 4, 8, 12] 加上从 16 起步长 8 的尺寸，所以 48 以内是 1、2、4、8、12、16、24、32、40、48；_pad_to_bucket 取不小于 13 的最小值 16。每个整数都捕获只发生在 --disable-cuda-graph-padding 下；都填到 48 会白算 35 行，表之所以分得这么细正是为了避免这种浪费。The default list is [1, 2, 4, 8, 12] plus sizes from 16 in steps of 8, so up to 48 it is 1, 2, 4, 8, 12, 16, 24, 32, 40 and 48; _pad_to_bucket takes the smallest value not below 13, which is 16. Capturing every integer happens only with --disable-cuda-graph-padding; padding everything to 48 would waste 35 rows, which is exactly what the fine-grained list exists to avoid.

3. 下面哪件事属于 init_forward_metadata_out_graph，而不能放进 init_forward_metadata_in_graph？

3. Which of these belongs in init_forward_metadata_out_graph and cannot go into init_forward_metadata_in_graph?

plan() 里的 indptr.to("cpu") 是主机同步，base_attn_backend.py 的合同明文禁止在图内钩子里调 .cpu()，所以它在图外。run() 是模型前向的一部分，本来就在图里被捕获；形状固定、只碰预分配缓冲区的 GPU 操作正是图内钩子允许的内容。The indptr.to("cpu") inside plan() is a host sync, and the contract in base_attn_backend.py explicitly forbids .cpu() in the in-graph hook, so it stays outside. run() is part of the model forward and is captured in the graph anyway; a fixed-shape GPU op that touches only preallocated buffers is exactly what the in-graph hook allows.

4. 一个 use_cuda_graph=True 的 FlashInfer 解码包装器被捕获进图之后，两次重放之间可以变的是什么？

4. Once a FlashInfer decode wrapper with use_cuda_graph=True has been captured into a graph, what may change between two replays?

图记下的是内核和缓冲区的地址，所以只能改内容：plan() 用 copy_ 写进同一批缓冲区。批大小是冻结的形状，图模式下 plan() 发现批大小变了会抛 ValueError，所以 SGLang 为每个捕获尺寸各建一组包装器。新张量的地址图从没见过，重放仍然读旧的那块。The graph records kernels and buffer addresses, so only contents may change: plan() writes into the same buffers with copy_. The batch size is a frozen shape, and in graph mode plan() raises ValueError when it changes, which is why SGLang builds one set of wrappers per captured size. A new tensor has an address the graph has never seen, and the replay still reads the old block.
