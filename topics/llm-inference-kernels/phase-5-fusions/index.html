Elementwise operators such as normalization, activation and positional encoding do almost no arithmetic; their time goes into moving data, and every unfused operator reads the activation from memory once and writes it once. Merge neighbouring operators into one kernel and the intermediate results stay in registers, so there are fewer reads and writes. For this topic’s Qwen3-0.6B (hidden size 1024, intermediate size 3072, BF16), a residual add followed by RMSNorm reads and writes 10 KiB per token as two kernels and 8 KiB as one fused kernel; SiLU-and-mul drops from 30 KiB to 18 KiB. SGLang takes these fused kernels by default on CUDA, and hands sampling to FlashInfer’s rejection-sampling kernel, which never sorts. Measured with the Metal twin on this Apple M5: at 16384 tokens the fused versions are faster by exactly their byte ratio (1.25–1.26 and 1.65–1.66 times); at 16 tokens the ratio rises to about 1.5–2.3 times, because what is saved there is mostly one dispatch rather than bytes. 核心概念

Core concepts

一个解码步除了矩阵乘和注意力，还有一长串逐元素算子：残差加法、RMSNorm、SiLU-and-mul、RoPE、写 KV 缓存，最后还要从 151936 个概率里抽一个 token。每个这样的算子运算很少，时间几乎全花在搬字节上；两个算子一前一后时，前一个把结果写回显存，后一个原样读回来，再各付一次内核发射。融合要做到的是：中间结果不出寄存器，内核数变少；采样要做到的是：不为抽一个 token 把整行概率排一遍序。

Besides the matmuls and attention, a decode step runs a long chain of elementwise operators: the residual add, RMSNorm, SiLU-and-mul, RoPE, the KV-cache write, and at the end a draw of one token from 151936 probabilities. Each of these does little arithmetic and spends almost all its time moving bytes; when two of them run back to back, the first writes its result to memory, the second reads it straight back, and each pays a kernel launch. Fusion has to keep the intermediate in registers and cut the number of kernels; sampling has to draw one token without sorting the whole row of probabilities.

The fusion principle of concept 1 answers the first, and concepts 2 to 5 are four instances of it; the sorting-free rejection sampling of concept 6 answers the second.

1. 为什么融合能省显存流量

1. Why fusion cuts memory traffic

一个逐元素算子对每个元素只做几次加乘，算术强度（每字节的运算数）远低于显卡的屋脊点，所以它的时间几乎等于「读入的字节 + 写出的字节」除以显存带宽。两个这样的算子一前一后，第一个把结果写回显存，第二个再原样读回来；这一写一读纯粹是搬运。融合的意思就是把它们写进同一个内核：中间结果留在寄存器（或共享内存）里，不再经过显存，同时少发射一个内核。

An elementwise operator does a handful of adds and multiplies per element, so its arithmetic intensity (operations per byte) sits far below the GPU’s ridge point, and its time is almost exactly the bytes it reads plus the bytes it writes, divided by memory bandwidth. Put two such operators back to back and the first writes its result to memory only for the second to read it straight back; that write and that read are pure transport. Fusion means writing both into one kernel: the intermediate result stays in registers (or shared memory) and never touches device memory, and one kernel launch disappears with it.

2. Residual add + RMSNorm

预归一化的 Transformer 每层有两处「上一段的输出加回残差，再对和做 RMSNorm」：注意力之前和 MLP 之前。融合内核的合同写在 sgl_kernel 的 Python 包装里（python/sglang/kernels/aot/python/sgl_kernel/elementwise.py 第 125–162 行），两步都是原地的：

A pre-norm Transformer has two places per layer where the previous block’s output is added back into the residual and the sum goes through RMSNorm: before attention and before the MLP. The fused kernel’s contract is in the Python wrapper of sgl_kernel (lines 125–162 of python/sglang/kernels/aot/python/sgl_kernel/elementwise.py), and both steps are in place:

Step 1:
``residual[i] += input[i]``

Step 2:
``input[i] = (residual[i] / RMS(residual)) * weight[i]``

一个 token 的一行（1024 个元素）正好交给一个线程块：每个线程读几个 x 和 r，在寄存器里相加并写回残差，同时累加平方和；块内归约出整行的平方和，得到 1/RMS；每个线程再用自己寄存器里的值乘上它和权重，写出 y。行内的归约就是 PMPP 讲的归约模式，所以「先加再归一化」能留在一个内核里。Lab B 的 Metal 内核就是这样写的。

One token’s row (1024 elements) maps onto one thread block: each thread reads a few elements of x and r, adds them in registers and writes the residual back while accumulating a sum of squares; a block-wide reduction gives the row’s sum of squares and so 1/RMS; then each thread multiplies the values still in its registers by that and by the weight and writes y. The in-row reduction is the reduction pattern from PMPP, which is why the add and the norm can live in one kernel. Lab B’s Metal kernel is written exactly this way.

5. all-reduce + 残差 + RMSNorm

5. All-reduce + residual + RMSNorm

张量并行时，o_proj 和 down_proj 是按行切的线性层，每张卡只算出部分和，必须先 all-reduce 才能加回残差。紧跟其后的正是下一个残差 + RMSNorm，于是可以把 all-reduce 的收尾、残差加法和归一化放进同一个通信内核：归约出来的和不必先写回显存、再被归一化内核读回。按一行 2 KiB 数，省下的是这一写一读的 4 KiB 本地显存流量和一次发射（推断：实际节省还取决于 all-reduce 算法本身怎么搬数据）。

With tensor parallelism, o_proj and down_proj are row-split linear layers: each GPU computes only a partial sum, which must be all-reduced before it can be added to the residual. The very next thing is a residual + RMSNorm, so the tail of the all-reduce, the residual add and the norm can share one communication kernel: the reduced sum never has to be written to memory and read back by a norm kernel. At 2 KiB a row, what is saved is that write and that read, 4 KiB of local memory traffic, plus one launch (inference: the real saving also depends on how the all-reduce algorithm itself moves data).

6. 采样：不排序的 top-k / top-p

6. Sampling: top-k / top-p without a full sort

每步最后，每个请求从一整行概率里选一个 token。教科书写法是先把这一行按概率从大到小排序，再做前缀和、按 top-k 和 top-p 截断、归一化、抽样。SGLang 的 pytorch 后端就这样做（layers/sampler.py 第 779 行起，排序在第 813–815 行）。词表 151936 时，一行 FP32 概率是 593.5 KiB，排序要把它读进来、写出排好的值和 int64 的下标（每个元素 12 字节，约 1.74 MiB），后面的前缀和和两次截断又各读写一遍（推断，按这几行代码的张量数出，不含排序算法内部的多趟）。

At the end of every step, each request picks one token from a whole row of probabilities. The textbook way sorts the row from largest to smallest, takes a prefix sum, truncates by top-k and top-p, renormalizes and draws. SGLang’s pytorch backend does exactly this (from line 779 of layers/sampler.py, the sort at lines 813–815). With a vocabulary of 151936, one row of FP32 probabilities is 593.5 KiB; the sort reads it and writes the sorted values plus int64 indices (12 bytes per element, about 1.74 MiB), and the prefix sum and the two truncations each read and write it again (inference, counted from the tensors in those lines, not including the internal passes of the sort algorithm).

The FlashInfer v0.7.1 docstring says it implements GPU-based rejection sampling without explicit sorting, with the multiple rounds of rejection sampling in a single CUDA kernel (lines 1780–1786 of flashinfer/sampling.py); joint means each round checks top-k and top-p at the same time (lines 1810–1813). The kernel is TopKTopPSamplingFromProbKernel in include/flashinfer/sampling.cuh (lines 1210–1338), one thread block per request, and each round does this:

  1. 抽一个候选：取 u = uniform × q，q 是还在候选范围里的概率总和；按词表原来的顺序，只累加概率大于 low 的 token，累加和超过 u 的那个就是候选（逆变换采样，块内前缀和，超过就提前停）。
  2. Draw a candidate: take u = uniform × q, where q is the mass still in range; walk the vocabulary in its original order adding only probabilities above low, and the token at which the running sum passes u is the candidate (inverse transform sampling, with block prefix sums and an early stop).
  3. 检验：pivot_0 是候选的概率，pivot_1 = (pivot_0 + high) / 2。再读一遍整行，数出概率大于两个 pivot 的 token 个数和概率和。大于 pivot_0 的个数小于 k 且和小于 p，就接受候选、结束（第 1318–1321 行）。
  4. Test: pivot_0 is the candidate’s probability and pivot_1 = (pivot_0 + high) / 2. One more read of the whole row counts the tokens above each pivot and sums their probabilities. If fewer than k tokens lie above pivot_0 and their mass is below p, the candidate is accepted and the kernel stops (lines 1318–1321).
  5. 收窄：否则，若 pivot_1 满足条件，范围变成 (pivot_0, pivot_1]；若不满足，low 提到 pivot_1（第 1322–1331 行）。两种情况范围都至少减半。
  6. Narrow: otherwise, if pivot_1 passes the test, the range becomes (pivot_0, pivot_1]; if not, low rises to pivot_1 (lines 1322–1331). Either way the range at least halves.

FlashInfer 的博客 Sorting-Free GPU Kernels for LLM Sampling（2025-03-10）把这叫 Dual Pivot Rejection Sampling，说它从 v0.2.3 开始使用，轮数最坏是 O(log(1/ε))，并证明了输出分布正好等于「先截断、再在剩下的 token 里按概率抽」；它也说实际需要的轮数通常很少。所以每轮最多读两遍这一行，没有排序、没有中间张量。博客里的单卡 H100 评测说采样时间减少了一半以上，这是博客自己的数字，本页没有复现。v0.7.1 的默认 top_k_first 另有一条快路径：先用基数 top-k 选出 k 个，再在这 k 个上做 top-p（第 1547–1605 行）；SGLang 传的是 joint，不走它。

FlashInfer’s blog post Sorting-Free GPU Kernels for LLM Sampling (2025-03-10) calls this Dual Pivot Rejection Sampling, says it has been used since v0.2.3 with a worst case of O(log(1/ε)) rounds, and proves that the output distribution is exactly that of truncating first and then sampling among the remaining tokens by probability; it also says the number of rounds needed is usually small. So each round reads the row at most twice, with no sort and no intermediate tensors. The post’s evaluation on one H100 reports sampling time cut by more than half; that is the post’s own figure and was not reproduced here. The default top_k_first order of v0.7.1 has a separate fast path, which selects k entries with a radix top-k first and then runs top-p over those k (lines 1547–1605); SGLang passes joint and does not take it.

  • An elementwise operator’s time is roughly the bytes it reads and writes divided by memory bandwidth, and fusion keeps the intermediate in registers, saving one write, one read and one launch.
  • Fused, residual + RMSNorm drops from 10 KiB to 8 KiB per token per site and SiLU-and-mul from 30 KiB to 18 KiB, about 450 KiB per token per step for Qwen3-0.6B.

常见误解

Common misconceptions

  • 误解：融合省掉了算子本身的计算。→ 实际：运算一样多，省掉的是中间结果写回显存再读回来的字节和内核发射；融合后的 RMSNorm 仍然要写出 r′，因为下一层还要用残差。
  • 误解：CUDA 图已经省掉了发射开销，所以融合没必要。→ 实际：CUDA 图省掉的是 CPU 那一份，GPU 上内核之间的那一份和中间结果的显存流量都还在；融合减少的是内核数本身。
  • 误解：不排序的采样只是近似。→ 实际：FlashInfer 的博客证明了输出分布正好等于先按 top-k 和 top-p 截断、再在剩下的 token 里按概率抽。
  • Myth: fusion saves the operators’ own arithmetic. → Fact: the arithmetic is the same; what goes is the bytes of writing the intermediate to memory and reading it back, plus the launch, and the fused RMSNorm still writes r′ because the next layer needs the residual.
  • Myth: CUDA graphs already removed the launch cost, so fusion is unnecessary. → Fact: CUDA graphs remove the CPU share; the share spent on the GPU between kernels and the memory traffic of the intermediates remain, and fusion reduces the number of kernels itself.
  • Myth: sorting-free sampling is only an approximation. → Fact: FlashInfer’s blog post proves the output distribution is exactly that of truncating by top-k and top-p first and then sampling among the remaining tokens by probability.

def torch_add_rmsnorm(x, r):                    # RMSNorm.forward_native (layernorm.py lines 821-870), op by op
    s = x.to(torch.float32) + r.to(torch.float32)
    r_new = s.to(dt)
    s = s * torch.rsqrt(s.pow(2).mean(dim=-1, keepdim=True) + EPS)

    fused_add_rmsnorm(x, r, w, EPS)
    return x, r

// Reduce one float across the threadgroup (8 SIMD groups of 32).
inline float tg_sum(float v, threadgroup float* part, uint tid) {
    v = simd_sum(v);
    if (tid % 32 == 0) part[tid / 32] = v;
    threadgroup_barrier(mem_flags::mem_threadgroup);
    float s = 0;
    for (uint i = 0; i < TG / 32; i++) s += part[i];
    return s;
}

// Unfused, kernel 1 of 2: r_out = x + r. Reads 2 rows, writes 1.
kernel void add(device const half4* x [[buffer(0)]], device const half4* r [[buffer(1)]],
                device half4* r_out [[buffer(2)]], uint i [[thread_position_in_grid]]) {
    r_out[i] = half4(float4(x[i]) + float4(r[i]));
}

// Unfused, kernel 2 of 2: y = r_out / rms(r_out) * w. One threadgroup per token; reads 1 row, writes 1.
kernel void rmsnorm(device const half4* r_out [[buffer(0)]], device const half4* w [[buffer(1)]],
                    device half4* y [[buffer(2)]], constant uint& H [[buffer(3)]],
                    uint t [[threadgroup_position_in_grid]], uint tid [[thread_position_in_threadgroup]]) {
    threadgroup float part[TG / 32];
    uint n4 = H / 4, base = t * n4;
    float4 v[4]; float ss = 0;               // H <= 4096: at most 4 half4 per thread
    for (uint k = 0, j = tid; j < n4; k++, j += TG) { v[k] = float4(r_out[base + j]); ss += dot(v[k], v[k]); }
    float inv = rsqrt(tg_sum(ss, part, tid) / float(H) + 1e-6f);
    for (uint k = 0, j = tid; j < n4; k++, j += TG) y[base + j] = half4(v[k] * inv * float4(w[j]));
}

kernel void fused_add_rmsnorm(device const half4* x [[buffer(0)]], device const half4* r [[buffer(1)]],
                              device half4* r_out [[buffer(2)]], device const half4* w [[buffer(3)]],
                              device half4* y [[buffer(4)]], constant uint& H [[buffer(5)]],

}

kernel void silu(device const half4* gu [[buffer(0)]], device half4* s [[buffer(1)]],
                 constant uint& I [[buffer(2)]], uint i [[thread_position_in_grid]]) {
    uint n4 = I / 4, t = i / n4, c = i % n4;
    float4 g = float4(gu[t * 2 * n4 + c]);
    s[i] = half4(g / (1.0f + exp(-g)));
}

}

}

Self-check

1. hidden size 1024、BF16 时，残差 + RMSNorm 从两个内核（10 KiB 每 token）融合成一个（8 KiB），省下的 2 KiB 是哪一笔？

1. With hidden size 1024 in BF16, fusing residual + RMSNorm from two kernels (10 KiB per token) into one (8 KiB) saves 2 KiB. Which transfer is it?

两个内核时，r′ 被写出一次、又被归一化内核读回一次；融合后它仍要写出，因为下一层要用残差，但不再读回，省下的就是这一读。权重本来就不计入（2 KiB，整批共用、多半在缓存里），融合内核照样从显存读它。With two kernels, r′ is written once and read back once by the norm kernel; fused, it still has to be written, because the next layer needs the residual, but it is no longer read back, and that read is the saving. The weight was never counted (2 KiB, shared by the batch and most likely cached), and the fused kernel still reads it from memory.

2. Lab B 里，16 个 token 时不融合和融合的时间比约为 1.5–2.3，比字节比（1.25 和 1.67）大；16384 个 token 时正好等于字节比。最好的解释是什么？

2. In Lab B, at 16 tokens the unfused-to-fused time ratio is about 1.5–2.3, above the byte ratios (1.25 and 1.67); at 16384 tokens it equals the byte ratio. What is the best explanation?

两种写法用的都是 FP32 算术、FP16 存储，算术也不是瓶颈；融合内核在每个尺寸下都写残差（程序里的 r_out），正确性检查也逐位对上了。剩下的解释是固定开销：16 个 token 时一个内核只要 1–4 µs，少一次派发就是少一大截；16384 个 token 时有效带宽稳定在约 130 GB/s，时间比就等于字节比。Both forms use FP32 arithmetic and FP16 storage, and arithmetic is not the bottleneck; the fused kernel writes the residual at every size (r_out in the program), and the correctness check matches bit for bit. What remains is fixed cost: at 16 tokens a kernel takes only 1–4 µs, so one dispatch fewer is a large share; at 16384 tokens the effective bandwidth holds at about 130 GB/s, so the time ratio equals the byte ratio.

3. FlashInfer 的 TopKTopPSamplingFromProbKernel（joint 顺序）一轮做了什么？

3. What does one round of FlashInfer’s TopKTopPSamplingFromProbKernel (the joint order) do?

内核里没有排序也没有堆：每轮一遍带提前停止的前缀和抽候选，一遍归约数出 pivot_0 和 pivot_1 之上的个数和概率和（sampling.cuh 第 1239–1332 行）。分段排序再归并是排序的做法，正是它要避开的；先选 k 个再做 top-p 的是 top_k_first 的快路径，用的是基数 top-k，也不是堆，而且 SGLang 不走它。There is no sort and no heap in the kernel: each round makes one prefix-sum pass with an early stop to draw a candidate and one reduction pass counting the tokens above pivot_0 and pivot_1 and summing their probabilities (lines 1239–1332 of sampling.cuh). Sorting chunks and merging is the sort it avoids; selecting k first and then applying top-p is the top_k_first fast path, which uses a radix top-k rather than heaps, and SGLang does not take it.

4. 在一张 L4 上用 v0.5.22 跑 Qwen3-0.6B，下面哪个融合肯定不会出现在 trace 里？

4. Running Qwen3-0.6B with v0.5.22 on one L4, which of these fusions is certain not to appear in the trace?

只有一张卡就没有 all-reduce，flashinfer_allreduce_residual_rmsnorm 在 world size 为 1 时直接返回空；L4 是 sm_89，也不满足 SM90 或 SM100 的条件。残差 + RMSNorm 和 SiLU-and-mul 在 CUDA 上是默认路径，单卡照样走融合内核。（RoPE + 写 KV 缓存同样不会出现，但原因不同：稠密 Qwen3 的模型代码不传那个参数。）With one GPU there is no all-reduce, and flashinfer_allreduce_residual_rmsnorm returns nothing at once when the world size is 1; the L4 is sm_89, which fails the SM90-or-SM100 condition as well. Residual + RMSNorm and SiLU-and-mul are the default paths on CUDA and take their fused kernels on a single GPU too. (RoPE + KV-cache write will not appear either, for a different reason: the dense Qwen3 model code does not pass the argument.)
