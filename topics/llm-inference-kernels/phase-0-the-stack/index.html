SGLang 从上到下分四层：前端程序、运行时调度器、模型执行器、GPU 内核。上面三层决定数据怎么排、什么时候算；只有第四层真正在 GPU 上干活。这一阶段先在 v0.5.22 的源码里找到每一层，再把一步解码拆成一串内核，算清每个内核读多少字节、做多少运算。结论很硬：一个 8B 的 BF16 模型，每生成一个 token 都要把约 15 GB 权重从显存里读一遍，而运算只有约 18 GFLOP，所以批大小为 1 的解码受内存带宽限制；一次预填充几百上千个 token，同一份权重被复用几百次，就变成受算力限制。这台 Apple M5 上实测：4096 × 4096 的 FP16 权重，单 token 的 GEMV 用 0.25–0.28 ms，256 个 token 的 GEMM 只用 2.46–2.54 ms，每个 token 便宜约 28 倍。哪些跑过、哪些没跑过：Lab B 的 Metal 程序 2026-11-01 在这台 Apple M5 上实际运行，数字原样贴出；Lab A 在 L4 上启动 SGLang 并剖析解码步，未运行，是 2026-11-01 根据 SGLang v0.5.22 的源码和文档整理的。

SGLang has four layers from top to bottom: the frontend program, the runtime scheduler, the model executor and the GPU kernels. The top three decide how data is laid out and when work happens; only the fourth actually does the work on the GPU. This phase first finds each layer in the v0.5.22 source, then breaks one decode step into a sequence of kernels and works out how many bytes each one reads and how much arithmetic it does. The conclusion is hard: for an 8B model in BF16, every generated token reads about 15 GB of weights from memory for only about 18 GFLOP of arithmetic, so decode at batch size 1 is bound by memory bandwidth; a prefill of hundreds or thousands of tokens reuses the same weights hundreds of times and becomes bound by compute. Measured on this Apple M5: with 4096 × 4096 FP16 weights, a one-token GEMV takes 0.25–0.28 ms and a 256-token GEMM only 2.46–2.54 ms, about 28 times cheaper per token. What was run and what was not: the Metal program of Lab B was actually run on this Apple M5 on 2026-11-01 and its numbers are pasted as they came; Lab A, which launches SGLang on an L4 and profiles a decode step, is not run, assembled from the SGLang v0.5.22 source and documentation on 2026-11-01.

核心概念

Core concepts

1. 四层，以及它们在 v0.5.22 源码里的位置

1. The four layers, and where they live in the v0.5.22 source

先说清一个词。本专题的「内核」（kernel）指在 GPU 上启动的一段计算程序，也就是 GPU Programming with CUDA 里写的那种；Kernel Engineering 里的「内核」是操作系统内核，管进程、内存和设备。两者没有关系，只是同名。下文的路径都按 SGLang 的 GitHub 发布 v0.5.22（2026-10-19）给出，每个文件都在 2026-11-01 从 raw.githubusercontent.com 按这个标签取回核对过。

First, one word. A “kernel” in this topic is a compute program launched on the GPU, the kind written in GPU Programming with CUDA; the “kernel” of Kernel Engineering is the operating-system kernel that manages processes, memory and devices. The two are unrelated and merely share a name. Every path below is given at SGLang’s GitHub release v0.5.22 (2026-10-19), and each file was fetched from raw.githubusercontent.com at that tag and checked on 2026-11-01.

  • 第 1 层 · 前端（python/sglang/lang/）：一个 SGLang 程序是一个 Python 函数，用 api.py 里的 gen、select 生成或选择文本，用程序状态的 fork（interpreter.py）把同一段上下文分出几条支路。几条支路天然共享前缀，这正是下面一层要利用的。
  • Layer 1 · Frontend (python/sglang/lang/): an SGLang program is a Python function that generates or chooses text with gen and select from api.py, and splits one context into several branches with the program state’s fork (interpreter.py). The branches naturally share a prefix, which is exactly what the layer below exploits.
  • 第 2 层 · 运行时（SRT）：请求经 srt/managers/tokenizer_manager.py 分词后交给 srt/managers/scheduler.py 的 Scheduler。它的事件循环（event_loop_normal，以及让 CPU 调度与 GPU 计算重叠的 event_loop_overlap）每一轮用 get_next_batch_to_run 决定这一步算哪些请求：新请求的预填充和已在运行的请求的解码可以拼进同一批，这就是连续批处理。KV 缓存由 srt/mem_cache/radix_cache.py 的 RadixCache 管理（文件开头的说明是「The radix tree data structure for managing the KV cache」）：match_prefix 找出已经缓存的前缀，只有剩下的部分需要预填充；insert 把算完的序列挂回树上，evict 在显存不够时淘汰叶子。
  • Layer 2 · Runtime (SRT): a request is tokenized by srt/managers/tokenizer_manager.py and handed to the Scheduler in srt/managers/scheduler.py. Each round of its event loop (event_loop_normal, and event_loop_overlap, which overlaps CPU scheduling with GPU compute) calls get_next_batch_to_run to decide which requests this step computes: the prefill of new requests and the decode of running ones can join the same batch, which is continuous batching. The KV cache is managed by RadixCache in srt/mem_cache/radix_cache.py (whose header reads “The radix tree data structure for managing the KV cache”): match_prefix finds the prefix already cached so only the rest needs prefill, insert hangs finished sequences back on the tree, and evict drops leaves when memory runs short.
  • 第 3 层 · 模型执行器（python/sglang/srt/model_executor/）：model_runner.py 的 ModelRunner 拿到一个 ForwardBatch（定义在 forward_batch_info.py），按它的 ForwardMode 跑一次前向：EXTEND 是预填充（源码注释：「It is also called "prefill" in common terminology」），DECODE 是解一个 token，MIXED 是分块预填充时两者混在一批。解码步如果批大小合适，就不再逐个启动内核，而是重放 runner/decode_cuda_graph_runner.py 预先捕获好的 CUDA 图（_forward_raw 里的 can_run_graph 判断）。
  • Layer 3 · Model executor (python/sglang/srt/model_executor/): ModelRunner in model_runner.py takes a ForwardBatch (defined in forward_batch_info.py) and runs one forward pass according to its ForwardMode: EXTEND is prefill (the source comment says “It is also called "prefill" in common terminology”), DECODE decodes one token, and MIXED holds both in one batch during chunked prefill. When a decode step’s batch size fits, the kernels are not launched one by one; instead a CUDA graph captured in advance by runner/decode_cuda_graph_runner.py is replayed (the can_run_graph check in _forward_raw).
  • 第 4 层 · 内核：SGLang 自己的内核库在 python/sglang/kernels/，PyPI 包名 sglang-kernel（python/pyproject.toml 钉在 0.4.9）。aot/csrc/ 是预先编译的 CUDA/C++ 算子，例如 aot/csrc/moe/moe_align_kernel.cu、aot/csrc/elementwise/fused_add_rms_norm_kernel.cu、aot/csrc/allreduce/custom_all_reduce.cu；jit/csrc/ 是即时编译的算子；ops/ 是按算子分组的 Python 入口（该目录的 README 列出 activation、attention、communication、gemm、grammar、layernorm、moe、sampling 等组）。其余内核来自上游库：同一个 pyproject 钉了 flashinfer_python[cu13]==0.7.1、sgl-deep-gemm==0.2.2、sgl-deep-ep==0.1.2.post1、xgrammar==0.2.7 和 torch==2.14.1。简报里的 sgl-kernel/ 就是搬到这里来了。
  • Layer 4 · Kernels: SGLang’s own kernel library lives at python/sglang/kernels/, PyPI package sglang-kernel (pinned at 0.4.9 in python/pyproject.toml). aot/csrc/ holds ahead-of-time CUDA/C++ ops such as aot/csrc/moe/moe_align_kernel.cu, aot/csrc/elementwise/fused_add_rms_norm_kernel.cu and aot/csrc/allreduce/custom_all_reduce.cu; jit/csrc/ holds JIT-built ops; ops/ holds the Python entry points grouped by operator (the directory’s README lists groups such as activation, attention, communication, gemm, grammar, layernorm, moe and sampling). The rest of the kernels come from upstream libraries: the same pyproject pins flashinfer_python[cu13]==0.7.1, sgl-deep-gemm==0.2.2, sgl-deep-ep==0.1.2.post1, xgrammar==0.2.7 and torch==2.14.1. This is where the brief’s sgl-kernel/ moved to.

第 3 层和第 4 层之间还有一层薄薄的接口：模型代码里的注意力层调用 srt/layers/attention/base_attn_backend.py 定义的 AttentionBackend，它的 forward_extend 和 forward_decode 由各个后端实现，例如 flashinfer_backend.py 用 FlashInfer 的 BatchDecodeWithPagedKVCacheWrapper 和 BatchPrefillWithPagedKVCacheWrapper。这个接口在 Phase 1–3 和 Phase 8 反复出现。

Between layers 3 and 4 there is a thin interface: the attention layer in the model code calls the AttentionBackend defined in srt/layers/attention/base_attn_backend.py, whose forward_extend and forward_decode are implemented by each backend; flashinfer_backend.py, for example, uses FlashInfer’s BatchDecodeWithPagedKVCacheWrapper and BatchPrefillWithPagedKVCacheWrapper. This interface returns in Phases 1–3 and Phase 8.

2. 一步解码做了什么：逐个算子

2. What one decode step does, op by op

拿一个具体的模型来数。Qwen3-8B 的 config.json（2026-11-01 从 Hugging Face 读取）：hidden 4096，MLP 中间维 12288，36 层，32 个查询头、8 个 KV 头（GQA，每 4 个查询头共用一组 KV），head_dim 128，词表 151936，权重 BF16，输入输出嵌入不共享。SGLang 的 srt/models/qwen3.py 复用 qwen2.py 的 MLP，结构与 srt/models/llama.py 相同，只多了对 q 和 k 的逐头 RMSNorm（q_norm、k_norm）。批大小为 1、上下文 4096 个 token 时，每一层依次启动下面这些内核（字节按 BF16 每元素 2 字节，1 MB = 106 字节）：

Take a concrete model and count. Qwen3-8B’s config.json (read from Hugging Face on 2026-11-01): hidden size 4096, MLP intermediate size 12288, 36 layers, 32 query heads and 8 KV heads (GQA, every 4 query heads share one KV group), head_dim 128, a vocabulary of 151936, BF16 weights, input and output embeddings not tied. SGLang’s srt/models/qwen3.py reuses the MLP of qwen2.py and has the same structure as srt/models/llama.py, adding only a per-head RMSNorm on q and k (q_norm, k_norm). At batch size 1 with a 4096-token context, each layer launches these kernels in order (bytes at 2 per BF16 element, 1 MB = 106 bytes):

  1. 残差相加 + RMSNorm（input_layernorm）：把上一层的输出加到残差上再归一化。读写的只是一个 4096 维的向量和一份 4096 的权重，几十 KB。融合版本在 aot/csrc/elementwise/fused_add_rms_norm_kernel.cu，它包含 FlashInfer 的 flashinfer/norm.cuh。
  2. Residual add + RMSNorm (input_layernorm): adds the previous layer’s output to the residual and normalizes. It reads and writes only a 4096-element vector and a 4096-element weight, tens of KB. The fused version is aot/csrc/elementwise/fused_add_rms_norm_kernel.cu, which includes FlashInfer’s flashinfer/norm.cuh.
  3. QKV 投影（QKVParallelLinear，一次 GEMM 同时算出 q、k、v）：权重 4096 × (4096 + 2 × 1024) = 25.2 M 个元素，读 50.3 MB，做 50.3 MFLOP（每个权重一次乘加，算 2 FLOP）。批大小为 1 时它其实是矩阵乘向量，也就是 GEMV。
  4. QKV projection (QKVParallelLinear, one GEMM producing q, k and v together): the weight has 4096 × (4096 + 2 × 1024) = 25.2 M elements, so it reads 50.3 MB and does 50.3 MFLOP (one multiply-add per weight, counted as 2 FLOP). At batch size 1 it is really a matrix-vector product, a GEMV.
  5. q/k 归一化、RoPE、写入 KV 缓存：对 q、k 逐头做 RMSNorm 和旋转位置编码，再把这个 token 的 k、v 写进 KV 缓存的槽位。字节和运算都很少（几十 KB），但它决定了 KV 写到哪里：槽位是运行时分配的，不一定连续（Phase 1）。
  6. q/k norm, RoPE, KV-cache write: a per-head RMSNorm and the rotary position embedding on q and k, then this token’s k and v are written into their KV-cache slots. Few bytes and little arithmetic (tens of KB), but this is where the KV lands: the slots are allocated by the runtime and need not be contiguous (Phase 1).
  7. 解码注意力：一个查询 token 对整个上下文。每层每个缓存 token 的 k、v 共 2 × 8 × 128 × 2 = 4096 字节，上下文 4096 时读 16.8 MB；运算是 32 个头各做 QK 和 PV，共 67.1 MFLOP，约 4 FLOP/字节。在 SGLang 里经 RadixAttention 调到注意力后端的 forward_decode。
  8. Decode attention: one query token against the whole context. Per layer, each cached token’s k and v take 2 × 8 × 128 × 2 = 4096 bytes, so a 4096-token context reads 16.8 MB; the arithmetic is QK and PV for each of 32 heads, 67.1 MFLOP in all, about 4 FLOP per byte. In SGLang it goes through RadixAttention to the attention backend’s forward_decode.
  9. 输出投影（o_proj，RowParallelLinear）：4096 × 4096，读 33.6 MB，33.6 MFLOP。用张量并行（TP > 1）时，每张卡只有一部分结果，这里要做一次 all-reduce（aot/csrc/allreduce/custom_all_reduce.cu）。一张 L4 上没有这一步。
  10. Output projection (o_proj, RowParallelLinear): 4096 × 4096, reading 33.6 MB for 33.6 MFLOP. With tensor parallelism (TP > 1) each GPU holds only part of the result, and an all-reduce happens here (aot/csrc/allreduce/custom_all_reduce.cu). On a single L4 this step does not exist.
  11. MLP：再一次残差相加 + RMSNorm（post_attention_layernorm）；gate_up_proj（MergedColumnParallelLinear，4096 × 24576，读 201.3 MB）；SiLU-and-mul（SiluAndMul，aot/csrc/elementwise/activation.cu，几十 KB）；down_proj（12288 × 4096，读 100.7 MB）。TP > 1 时 down_proj 之后又有一次 all-reduce。MoE 模型把这一整块换成路由与 top-k、按专家排序补齐、分组 GEMM，用专家并行时还有 all-to-all（Phase 4）。
  12. MLP: another residual add + RMSNorm (post_attention_layernorm); gate_up_proj (MergedColumnParallelLinear, 4096 × 24576, reading 201.3 MB); SiLU-and-mul (SiluAndMul, aot/csrc/elementwise/activation.cu, tens of KB); down_proj (12288 × 4096, reading 100.7 MB). With TP > 1 another all-reduce follows down_proj. A MoE model replaces this whole block with routing and top-k, sorting and padding per expert, and grouped GEMMs, plus an all-to-all under expert parallelism (Phase 4).

一层合计约 403 MB、453 MFLOP，36 层是 14.5 GB、16.3 GFLOP。最后还有一次 RMSNorm、lm_head（151936 × 4096，读 1.25 GB，由 LogitsProcessor 调用）和采样（srt/layers/sampler.py 在 FlashInfer 后端下调用 top_k_top_p_sampling_from_probs）。开头查嵌入表只读一行，可以忽略。整步约 15.7 GB、17.6 GFLOP。动画 (b) 把这串内核按字节画成条形。

One layer comes to about 403 MB and 453 MFLOP; 36 layers make 14.5 GB and 16.3 GFLOP. At the end come one more RMSNorm, the lm_head (151936 × 4096, reading 1.25 GB, called by LogitsProcessor) and sampling (srt/layers/sampler.py calls top_k_top_p_sampling_from_probs under the FlashInfer backend). 3. 算术：为什么解码受带宽限制、预填充受算力限制

3. The arithmetic: why decode is bandwidth-bound and prefill compute-bound

设模型每个 token 要用到的权重有 P 个，每个权重 b 字节（BF16、FP16 是 2）。线性层对每个权重、每个 token 做一次乘加，也就是 2 FLOP。

Let P be the number of weights each token uses, at b bytes per weight (2 for BF16 or FP16). A linear layer does one multiply-add, 2 FLOP, per weight per token.

  • 解码，批大小 B：这一步要把 P·b 字节的权重读一遍，这 B 个请求共用这一次读；运算是 2·P·B。运算强度（每字节多少 FLOP）= 2·P·B ÷ (P·b) = B（b = 2 时）。批大小为 1 时，每读 1 字节只做 1 FLOP。
  • Decode at batch size B: the step reads the P·b bytes of weights once, shared by all B requests, and does 2·P·B FLOP. The arithmetic intensity (FLOP per byte) is 2·P·B ÷ (P·b) = B for b = 2. At batch size 1, each byte read buys 1 FLOP.
  • 预填充，T 个 token：同一份权重被 T 个 token 复用，运算 2·P·T，字节仍约为 P·b 加上激活值。T 远小于 hidden 时运算强度约为 T。
  • Prefill of T tokens: the same weights are reused by T tokens, for 2·P·T FLOP, while the bytes stay at about P·b plus the activations. While T is much smaller than the hidden size, the intensity is about T.
  • 硬件的拐点：峰值算力 ÷ 内存带宽。NVIDIA L4 的产品页（2026-11-01 读取）写 FP16 Tensor Core 242 TFLOPS，并注明这是带稀疏的数字、不带稀疏时减半，即稠密 121 TFLOPS；显存带宽 300 GB/s。拐点约 121 × 1012 ÷ 300 × 109 ≈ 400 FLOP/字节。运算强度低于拐点，时间由字节数 ÷ 带宽决定；高于拐点，由运算量 ÷ 峰值算力决定。
  • The machine’s ridge point: peak compute ÷ memory bandwidth. NVIDIA’s L4 product page (read 2026-11-01) lists 242 TFLOPS of FP16 Tensor Core throughput and notes that this is shown with sparsity and is one-half lower without it, so 121 TFLOPS dense; memory bandwidth is 300 GB/s. The ridge is about 121 × 1012 ÷ 300 × 109 ≈ 400 FLOP per byte. Below the ridge, time is bytes ÷ bandwidth; above it, FLOPs ÷ peak compute.

代入 Qwen3-8B：每步解码读约 15.1 GB 权重（P ≈ 7.57 G，嵌入表只查一行，不计）。在 L4 上，光读权重就至少要 15.1 GB ÷ 300 GB/s ≈ 50 ms，所以单个请求最多每秒约 20 个 token；同样的 17.6 GFLOP 按峰值算力只要约 0.15 ms，差了三百多倍。算力几乎全在闲着。把批大小提到 B，权重还是读一遍，时间几乎不变，吞吐却乘以 B：这就是连续批处理的经济学。换成一个 2000 个 token 的提示做预填充，运算强度约 2000，高过拐点，时间下限变成 2 × 7.57 × 109 × 2000 ÷ 121 × 1012 ≈ 0.25 s，由算力决定。注意 256 个 token 在 L4 上还在拐点以下，要几百个 token 以上才真正受算力限制。以上都是由公开规格推出的下限，不是测量值。

Plug in Qwen3-8B: each decode step reads about 15.1 GB of weights (P ≈ 7.57 G; the embedding table is indexed for one row and not counted). On an L4, just reading the weights takes at least 15.1 GB ÷ 300 GB/s ≈ 50 ms, so a single request gets at most about 20 tokens a second; the same 17.6 GFLOP at peak compute would take about 0.15 ms, more than three hundred times less. The compute sits almost entirely idle. Raise the batch size to B and the weights are still read once, the time barely changes, and the throughput multiplies by B: this is the economics of continuous batching. Prefill a 2000-token prompt instead and the intensity is about 2000, above the ridge, so the lower bound becomes 2 × 7.57 × 109 × 2000 ÷ 121 × 1012 ≈ 0.25 s, set by compute. Note that 256 tokens is still below the ridge on an L4; it takes several hundred tokens or more to be truly compute-bound. All of these are lower bounds derived from published specifications, not measurements.

注意力是例外：每个请求有自己的 KV 缓存，解码注意力的字节随批大小一起增长，运算强度停在约 4 FLOP/字节（Qwen3-8B 的 GQA 每 4 个查询头共用一组 KV），批得再大也一样。所以长上下文、大批量时，解码的时间越来越多花在读 KV 上。能减少这些字节的，是让许多请求共用同一段前缀的 KV（RadixAttention 与级联注意力，Phase 1）、压缩 KV（DeepSeek 的 MLA，Phase 2）或把 KV 量化（Phase 6）。

Attention is the exception: each request has its own KV cache, so the bytes of decode attention grow with the batch and its intensity stays at about 4 FLOP per byte (Qwen3-8B’s GQA shares one KV group among 4 query heads) however large the batch. So at long contexts and large batches, more and more of decode time goes into reading KV. What reduces those bytes is letting many requests share one prefix’s KV (RadixAttention and cascade attention, Phase 1), compressing the KV (DeepSeek’s MLA, Phase 2), or quantizing it (Phase 6).

Lab B 在这台 M5 上把同样的两种形状量出来：GEMV 的强度是 1 FLOP/字节，跑在约 119–134 GB/s（D = 4096），离 Apple 给 M5 标的 153 GB/s 统一内存带宽不远（GPU 专题 Phase 0 引用的数字）；256 个 token 的 GEMM 跑在约 3.4–3.5 TFLOP/s，这只是本页这个未调优内核的速率，不是 M5 的峰值。两者相除，这对内核在 M5 上的拐点约 27 FLOP/字节，比 L4 的约 400 低得多，所以在 M5 上 256 个 token 已经远过拐点。不同机器拐点不同，但「批大小为 1 的解码强度只有 1」这件事在任何机器上都一样。

Lab B measures the same two shapes on this M5: the GEMV, at an intensity of 1 FLOP per byte, runs at about 119–134 GB/s (D = 4096), not far from the 153 GB/s of unified memory bandwidth Apple gives for the M5 (the figure cited in Phase 0 of the GPU topic); the 256-token GEMM runs at about 3.4–3.5 TFLOP/s, the rate of this page’s untuned kernel, not the M5’s peak. Dividing one by the other puts the ridge of this kernel pair on the M5 at about 27 FLOP per byte, far below the L4’s roughly 400, so on the M5 256 tokens are well past the ridge. Ridge points differ between machines, but the fact that decode at batch size 1 has an intensity of only 1 is the same on every machine.

4. 每个运行时想法落在哪个内核上

4. Where each runtime idea lands on a kernel

简报说：第 2–3 层的每一个设计选择，都会给第 4 层提出一条要求。把概念 3 的算术放进来，就能看出这些要求为什么存在。运行时的目标是让 GPU 少读字节、多复用读进来的字节、少花在启动和同步上；每一种做法都会改变数据的排列或执行的方式，内核必须接得住。

The brief says that each design choice in layers 2–3 places a requirement on layer 4. Add the arithmetic of concept 3 and you can see why those requirements exist. The runtime’s goals are for the GPU to read fewer bytes, reuse the bytes it reads more often, and spend less on launches and synchronization; each technique changes how data is laid out or how execution happens, and the kernels have to cope.

  • 少读字节：RadixAttention 让共享前缀的 KV 只存一份，代价是一个请求的 KV 散在不连续的槽位里，注意力内核必须按索引数组去收集（PagedAttention 论文 arXiv:2309.06180 先提出按页管理 KV，SGLang 论文 arXiv:2312.07104 把粒度做到 token 并用基数树共享前缀）。量化把每个权重从 2 字节降到 1 字节或半字节，但只有 GEMM 内核能直接读低精度格式时才省时间。
  • Read fewer bytes: RadixAttention stores a shared prefix’s KV only once, at the cost of scattering one request’s KV across non-contiguous slots, so the attention kernel must gather it through index arrays (the PagedAttention paper, arXiv:2309.06180, first managed KV in pages; the SGLang paper, arXiv:2312.07104, takes the granularity down to tokens and shares prefixes through a radix tree). Quantization cuts each weight from 2 bytes to 1 or half a byte, but saves time only when the GEMM kernel reads the low-precision format directly.
  • 多复用：连续批处理把很多请求拼成一批，权重读一次给所有请求用；代价是每个请求的长度不同，内核要接受变长的、不规则的批。推测解码一次验证多个草稿 token，把解码的 B 变大；代价是树状注意力掩码和验证内核。
  • Reuse more: continuous batching packs many requests into one batch so the weights are read once for all of them; the cost is that every request has a different length, so kernels must accept variable-length, ragged batches. Speculative decoding verifies several draft tokens at once, raising the effective B of decode; the cost is a tree-attention mask and a verification kernel.
  • 少花在启动和同步上：批大小为 1 时 36 层、每层七八个内核，一步就是几百次启动，小内核本身只要几微秒，启动开销会压过它们。CUDA 图把整步捕获下来重放，代价是内核不能做主机同步、不能动态分配、形状要固定或补齐。重叠调度器让 CPU 在 GPU 算这一步时准备下一步，这要求这一步里没有任何东西逼 CPU 停下来等 GPU（这是对 event_loop_overlap 的推断，Phase 3 细看）。
  • Spend less on launches and synchronization: at batch size 1, 36 layers of seven or eight kernels each make a step of several hundred launches, and small kernels that take a few microseconds each are swamped by launch overhead. A CUDA graph captures the whole step and replays it, at the cost that kernels may not synchronize with the host or allocate dynamically, and their shapes must be fixed or padded. The overlap scheduler has the CPU prepare the next step while the GPU computes this one, which requires that nothing in the step forces the CPU to stop and wait for the GPU (an inference about event_loop_overlap; Phase 3 looks closer).

// decode: y[n] = sum_k W[n][k] * x[k]. One SIMD-group (32 lanes) per output row.
kernel void gemv(device const half4* W [[buffer(0)]],
                 device const half4* x [[buffer(1)]],
                 device float*       y [[buffer(2)]],
                 constant uint&      K [[buffer(3)]],
                 uint row  [[simdgroup_index_in_threadgroup]],
                 uint lane [[thread_index_in_simdgroup]],
                 uint tg   [[threadgroup_position_in_grid]],
                 uint sgs  [[simdgroups_per_threadgroup]]) {
    uint n = tg * sgs + row;
    uint K4 = K / 4;
    device const half4* w = W + n * K4;
    float acc = 0.0f;
    for (uint k = lane; k < K4; k += 32)          // each lane reads 8 bytes, the SIMD-group 256 contiguous bytes
        acc += dot(float4(w[k]), float4(x[k]));
    acc = simd_sum(acc);

}

// each SIMD-group owns a 32 x 32 block of Y as 4 x 4 tiles of 8 x 8 (simdgroup_matrix).
kernel void gemm(device const half* X [[buffer(0)]],
                 device const half* W [[buffer(1)]],
                 device float*      Y [[buffer(2)]],
                 constant uint&     K [[buffer(3)]],
                 constant uint&     N [[buffer(4)]],
                 uint2 tg [[threadgroup_position_in_grid]],

3. 为什么加大批大小救不了解码注意力的运算强度？

3. Why does a larger batch not raise the arithmetic intensity of decode attention?

FlashInfer 的分页解码 API 正是一次启动处理一整批变长请求的，所以 a 不对。约 4 FLOP/字节远低于拐点，注意力解码受带宽限制，所以 b 不对。线性层能被批处理救，是因为权重是共享的；KV 不共享，除非几个请求共用同一段前缀，这正是 RadixAttention 和级联注意力要利用的。FlashInfer’s paged decode API exists precisely to handle a whole batch of variable-length requests in one launch, so a is wrong. About 4 FLOP per byte is far below the ridge, so decode attention is bandwidth-bound and b is wrong. Batching rescues the linear layers because their weights are shared; KV is not shared unless several requests have the same prefix, which is exactly what RadixAttention and cascade attention exploit.

4. RadixAttention 给注意力内核提出的要求是什么？

4. What requirement does RadixAttention place on the attention kernel?

a 是 MoE 的 moe_align_block_size 做的事，c 是结构化输出（xgrammar）的位掩码内核，两者都是真实的内核要求，但不是 RadixAttention 的。基数树让共享前缀的 KV 只存一份，一个请求的 KV 就散在树上不同节点对应的槽位里，内核只能按索引去收集。a is what MoE’s moe_align_block_size does and c is the bitmask kernel of structured output (xgrammar); both are real kernel requirements, but not RadixAttention’s. The radix tree stores a shared prefix’s KV once, so one request’s KV is scattered over the slots of different tree nodes, and the kernel can only gather it through indices.
