运行时（第 2 层）怎么存 KV 缓存，决定了注意力内核（第 4 层）怎么读它。SGLang 的 RadixAttention 把所有请求的 KV 放在一个按 token 分槽的池子里，用一棵 radix 树记住哪段 token 前缀已经算过、放在哪些槽位；两个请求共享前缀时，它们的槽位表里就是同一串槽位号，KV 不复制。代价是每个请求的 KV 散落在池子各处，内核不能再按「起点 + 长度」连续读，而要通过 FlashInfer 规定的两个数组 indptr 和 indices（一种 CSR 格式）逐个找到槽位。这一阶段在 v0.5.22 的源码里跟着这两个数组从 radix 树一路走到 FlashInfer 的 plan()，再看 cascade 怎样把共享前缀只读一次。这台 Apple M5 上实测：B = 64 个请求、每个 8192 个 token 的解码注意力，KV 完全打乱成单 token 页时比连续缓存只慢约 4%；一半前缀共享时反而快约三分之一，因为重复读到的槽位落在缓存里。哪些跑过、哪些没跑过：Lab B 的 Metal 程序 2026-11-01 在这台 Apple M5 上实际运行，数字原样贴出；Lab A 未运行，是 2026-11-01 根据 SGLang v0.5.22 的源码整理的。

How the runtime (layer 2) stores the KV cache decides how the attention kernel (layer 4) reads it. SGLang’s RadixAttention keeps the KV of every request in one pool of token-sized slots, and a radix tree remembers which token prefixes have already been computed and which slots hold them; when two requests share a prefix, their slot tables hold the same run of slot numbers, and no KV is copied. The price is that each request’s KV lies scattered across the pool, so the kernel can no longer read it as a start plus a length; it has to find every slot through the two arrays FlashInfer defines, indptr and indices (a CSR format). This phase follows those two arrays through the v0.5.22 source, from the radix tree to FlashInfer’s plan(), then looks at how cascade attention reads a shared prefix only once. Measured on this Apple M5: decode attention over B = 64 requests of 8192 tokens each is only about 4% slower when the KV is fully shuffled into one-token pages than over a contiguous cache; with half of the prefix shared it is about a third faster, because the repeated slots are served from the cache. What was run and what was not: the Metal program of Lab B was actually run on this Apple M5 on 2026-11-01 and its numbers are pasted as they came; Lab A is not run, assembled on 2026-11-01 from the SGLang v0.5.22 source.

1. RadixAttention：一棵以 token 为键、以槽位为值的 radix 树

1. RadixAttention: a radix tree keyed by tokens, valued by slots

SGLang 论文（arXiv:2312.07104 v2）的说法是：运行时不在请求结束后丢掉 KV，而是把所有请求的 KV 作为一个 LRU 缓存放在 radix 树里，新请求来了先找最长的已缓存前缀，只为剩下的 token 做预填充。radix 树是压缩过的前缀树（trie）：一条边上可以挂一整段 token，而不是一个 token 一层。v0.5.22 里它在 python/sglang/srt/mem_cache/radix_cache.py：

The SGLang paper (arXiv:2312.07104 v2) puts it this way: the runtime does not throw the KV away when a request ends; it keeps the KV of all requests as an LRU cache inside a radix tree, and a new request first looks up its longest cached prefix and prefills only the remaining tokens. A radix tree is a compressed prefix tree (trie): one edge can carry a whole run of tokens instead of one token per level. At v0.5.22 it lives in python/sglang/srt/mem_cache/radix_cache.py:

  • 节点（TreeNode，第 250–278 行）：key 是这段 token 的 id，value 是一个张量，放的是这些 token 在 KV 池里的槽位号，不是 K 和 V 本身；lock_ref 是引用计数，last_access_time 给驱逐策略用。value 为 None 表示已被驱逐。
  • The node (TreeNode, lines 250–278): key holds the token ids of the run, and value is a tensor holding the slot numbers of those tokens in the KV pool, not the K and V themselves; lock_ref is a reference count, and last_access_time feeds the eviction policy. A value of None means the node was evicted.
  • 匹配（match_prefix，第 364 行起；遍历在 _match_prefix_helper，第 651 行）：沿树往下走，把一路上各节点的 value 收集起来，拼起来就是已缓存前缀的槽位。如果匹配在某个节点的中间结束，就调用 _split_node（第 677 行）把它切成两段，让边界恰好落在节点之间；切的只是槽位号张量，KV 本身不动。
  • Matching (match_prefix, from line 364; the walk is in _match_prefix_helper, line 651): walk down the tree and collect the value of each node on the way; joined together they are the slots of the cached prefix. If the match ends in the middle of a node, _split_node (line 677) cuts it in two so that the boundary falls exactly between nodes; only the tensor of slot numbers is cut, and the KV itself does not move.
  • 插入（insert，第 428 行）：请求算完新 token 后，把整条 token 序列和它的槽位插回树里，已存在的部分只更新访问时间，新的部分成为新节点。
  • Insertion (insert, line 428): after a request computes new tokens, its whole token sequence and slots go back into the tree; the parts already there only get a fresh access time, and the new part becomes a new node.
  • 加锁（inc_lock_ref / dec_lock_ref，第 582–616 行）：正在运行的请求从自己的末端节点一路往上把 lock_ref 加一。论文写的是「每个节点维护一个引用计数，表示有多少个运行中的请求在用它；计数为零才可驱逐」。
  • Locking (inc_lock_ref / dec_lock_ref, lines 582–616): a running request adds one to lock_ref on every node from its last node up to the root. The paper says each node keeps a reference counter of how many running requests use it, and a node is evictable only when the counter is zero.
  • 驱逐（evict，第 552–580 行）：把可驱逐的叶子放进一个按策略排序的堆，逐个弹出，把它 value 里的槽位还给分配器（free_segment），父节点变成叶子后也进堆。策略由 --radix-eviction-policy 选，默认 lru，还有 lfu、slru、priority、tlru（python/sglang/srt/arg_groups/fields/memory.py 第 25–41 行）；--disable-radix-cache 整个关掉它（第 64 行）。
  • Eviction (evict, lines 552–580): the evictable leaves go into a heap ordered by the policy and are popped one by one; the slots in each value go back to the allocator (free_segment), and a parent that becomes a leaf joins the heap. The policy is chosen by --radix-eviction-policy, default lru, with lfu, slru, priority and tlru as the others (lines 25–41 of python/sglang/srt/arg_groups/fields/memory.py); --disable-radix-cache turns the whole thing off (line 64).

调度器那一侧，论文还给了缓存感知调度：等待队列按「最长共享前缀优先」排序，论文指出这等价于对 radix 树做深度优先遍历，能提高命中率。键里除了 token 还可以带一个 extra_key（match_prefix 的文档字符串）：不同 LoRA 适配器的请求即使 token 相同，也不会共享节点。

On the scheduler side, the paper adds cache-aware scheduling: the waiting queue is sorted longest-shared-prefix first, which the paper notes is equivalent to a depth-first walk of the radix tree and raises the hit rate. Besides tokens, a key can carry an extra_key (the docstring of match_prefix): requests for different LoRA adapters never share nodes even when their tokens are identical.

2. Token-granular pages: scattered and shared across requests

KV 存在哪里，要看两张表，都在 python/sglang/srt/mem_cache/memory_pool.py：

Where the KV lives takes two tables, both in python/sglang/srt/mem_cache/memory_pool.py:

  • KV 池（MHATokenToKVPool，第 2198 行）：默认的 NHD 布局下，每一层一个 K 张量和一个 V 张量，形状是 (size + page_size, head_num, head_dim)（_kv_buffer_shapes，第 2518–2529 行）。第一维就是槽位：一个槽位放一个 token 在这一层的全部 KV 头。多出来的那一页是填充页，CUDA 图里填充出来的假 token 写到这里（第 2538 行的注释）。
  • The KV pool (MHATokenToKVPool, line 2198): in the default NHD layout, each layer has one K tensor and one V tensor of shape (size + page_size, head_num, head_dim) (_kv_buffer_shapes, lines 2518–2529). The first dimension is the slot: one slot holds all KV heads of one token at this layer. The extra page is a padding page that absorbs the writes of dummy padded tokens in CUDA graphs (the comment at line 2538).
  • 槽位表（ReqToTokenPool，第 374 行）：一个 int32 张量 req_to_token，形状 (size + 1, max_context_len)（第 404–406 行），每个运行中的请求占一行，第 t 列是它第 t 个 token 的槽位号。第 0 行同样是给 CUDA 图填充用的。
  • The slot table (ReqToTokenPool, line 374): an int32 tensor req_to_token of shape (size + 1, max_context_len) (lines 404–406); each running request owns one row, and column t holds the slot number of its t-th token. Row 0 is again a padding row for CUDA graphs.

论文写明这些 KV 张量「以非连续的分页布局存放，每页的大小等于一个 token」。v0.5.22 的 FlashInfer 后端仍是这样交给内核的：它调 plan 时页大小那个位置参数写死为 1，kv_last_page_len 全是 1（python/sglang/srt/layers/attention/flashinfer_backend.py 第 461–463、1807、1826、2343 行）。--page-size 选项存在（fields/schedule.py 第 139 行，默认 None，启动时再解析）；页大于 1 时，radix 树的匹配长度向下取整到页的整数倍（RadixKey.page_aligned，第 147–151 行），而建索引的 Triton 内核把页号还原成 token 槽位：token = entry * ps + pos % ps（python/sglang/kernels/ops/kvcache/kv_indices.py 的文档字符串），所以 FlashInfer 看到的还是逐 token 的槽位。

The paper states that these KV tensors are stored in a non-contiguous, paged layout where the size of each page is one token. The v0.5.22 FlashInfer backend still hands them to the kernel that way: when it calls plan, the positional page-size argument is the literal 1, and kv_last_page_len is all ones (lines 461–463, 1807, 1826 and 2343 of python/sglang/srt/layers/attention/flashinfer_backend.py). A --page-size option exists (line 139 of fields/schedule.py, default None, resolved at start-up); with pages larger than one, the radix match length is rounded down to a whole number of pages (RadixKey.page_aligned, lines 147–151), and the Triton kernel that builds the indices turns page numbers back into token slots as token = entry * ps + pos % ps (the docstring of python/sglang/kernels/ops/kvcache/kv_indices.py), so FlashInfer still sees one slot per token.

两个后果。散落：分配器从空闲槽位里随便拿，请求结束、节点被驱逐后槽位又回到空闲表，服务一段时间以后，一个请求的 token 在池里基本是乱序的（推断，依据是驱逐逐节点归还槽位）。共享：请求 B 命中请求 A 留下的前缀时，B 那一行 req_to_token 的前几列直接写上 A 的槽位号，后面的列才写新分配的槽位（mem_cache/allocation.py 第 97–104 行）；两行指向同一批槽位，KV 只存一份。这和操作系统里两个进程把同一个物理页映射进各自的页表是同一个想法；PagedAttention（Kwon 等，arXiv:2309.06180）先在 vLLM 里用块（block）做了这件事，SGLang 把块缩到了一个 token。

Two consequences follow. Scattering: the allocator takes any free slot, and slots return to the free list when requests end and nodes are evicted, so after a while of serving, the tokens of one request sit in the pool in essentially random order (inference, based on eviction returning slots node by node). Sharing: when request B hits the prefix that request A left behind, the first columns of B’s row of req_to_token are simply written with A’s slot numbers, and only the later columns get newly allocated slots (lines 97–104 of mem_cache/allocation.py); the two rows point at the same slots, and the KV is stored once. It is the same idea as two processes mapping one physical page into their own page tables; PagedAttention (Kwon et al., arXiv:2309.06180) first did this in vLLM with blocks of tokens, and SGLang shrinks the block to one token.

3. CSR 合同：indptr 和 indices

3. The CSR contract: indptr and indices

FlashInfer 不管理页表。它的文档 docs/tutorials/kv_layout.rst 的 FAQ 写得很直接：分页表怎么分配、怎么回收由服务引擎决定，FlashInfer 只负责在给定的 KV 上算注意力。两边之间的合同就是几个 int32 数组（文档特别提醒用 int64 会出索引错误）：

FlashInfer does not manage the page table. The FAQ of its docs/tutorials/kv_layout.rst says it plainly: how the page table is allocated and reclaimed is up to the serving engine, and FlashInfer only computes attention over the KV it is given. The contract between the two is a handful of int32 arrays (the documentation warns that int64 causes indexing errors):

  • Ragged（不分页）：所有请求的 K/V 无填充地首尾相接放在一个 data 张量里，indptr 有 num_requests + 1 个元素，首元素为 0，请求 i 的数据是 data[indptr[i]:indptr[i+1]]。API 是 BatchPrefillWithRaggedKVCacheWrapper，用于预填充时新算出的 K/V。
  • Ragged (unpaged): the K/V of all requests are packed end to end without padding in one data tensor; indptr has num_requests + 1 elements starting at 0, and request i’s data is data[indptr[i]:indptr[i+1]]. The API is BatchPrefillWithRaggedKVCacheWrapper, used for the freshly computed K/V of a prefill.
  • Paged（分页）：文档把页表看成一个块稀疏矩阵，用 CSR 格式索引。kv_indptr（长 num_requests + 1）是每个请求页数的前缀和；kv_indices（长 kv_indptr[-1]）是所有请求页号的拼接；kv_last_page_len（长 num_requests）是每个请求最后一页里的条目数，在 1 和 page_size 之间。请求 i 的 KV 长度是 page_size × (页数 − 1) + last_page_len[i]。API 是 BatchDecodeWithPagedKVCacheWrapper 和 BatchPrefillWithPagedKVCacheWrapper。
  • Paged: the documentation treats the page table as a block-sparse matrix indexed in CSR format. kv_indptr (length num_requests + 1) is the prefix sum of each request’s page count; kv_indices (length kv_indptr[-1]) is the concatenation of all requests’ page numbers; kv_last_page_len (length num_requests) is the number of entries in each request’s last page, between 1 and page_size. Request i’s KV length is page_size × (pages − 1) + last_page_len[i]. The APIs are BatchDecodeWithPagedKVCacheWrapper and BatchPrefillWithPagedKVCacheWrapper.

用动画 (a) 的三个请求算一遍：A、B、C 各有 9、9、6 个 token，页大小 1，于是 kv_indptr = [0, 9, 18, 24]，kv_indices 是三行槽位号首尾相接的 24 个数，kv_last_page_len = [1, 1, 1]。页大小为 1 时，最后一页总是满的，kv_indices 退化成「每个 token 一个槽位号」。FlashInfer 论文（arXiv:2501.01005 v2）把这一点说成块稀疏行（BSR）格式的块大小 (Br, Bc)：Bc 由 KV 缓存管理算法决定，SGLang 的 Bc = 1 就是论文所说的 vector-sparse；内核先把这些行收集到共享内存里，再在连续的数据上用 Tensor Core。

Work it through for the three requests of diagram (a): A, B and C have 9, 9 and 6 tokens, the page size is 1, so kv_indptr = [0, 9, 18, 24], kv_indices is the 24 numbers of the three slot rows end to end, and kv_last_page_len = [1, 1, 1]. With a page size of 1 the last page is always full, and kv_indices reduces to one slot number per token. The FlashInfer paper (arXiv:2501.01005 v2) puts this as the block size (Br, Bc) of a block-sparse row (BSR) format: Bc is set by the KV-cache management algorithm, and SGLang’s Bc = 1 is what the paper calls vector-sparse; the kernel first gathers those rows into shared memory, then uses Tensor Cores on the now-contiguous data.

同一份 plan() 产生的辅助数据结构可以被所有 Transformer 层复用（flashinfer/decode.py 第 966 行起 BatchDecodeWithPagedKVCacheWrapper 的文档字符串）：数组每个批次建一次，而不是每层一次。另外，KV 张量本身的最后三维可以是 NHD（token、头、维度）或 HND，默认 NHD，和 SGLang 池子的 (槽位, 头, 维度) 一致。

The auxiliary data structures one plan() produces are reused by every Transformer layer (the docstring of BatchDecodeWithPagedKVCacheWrapper, from line 966 of flashinfer/decode.py): the arrays are built once per batch, not once per layer. Separately, the last three dimensions of the KV tensor itself can be NHD (token, head, dimension) or HND; the default is NHD, which matches the (slot, head, dimension) of SGLang’s pool.

4. Cascade：共享前缀只算一次

4. Cascade attention: computing a shared prefix once

共享前缀省下了显存，却没有省下读。普通的分页解码里，64 个请求共享同一个长系统提示，就有 64 个线程块各自把这段前缀的 KV 从显存读一遍。cascade 的根据是 FlashInfer 文档 docs/tutorials/recursive_attention.rst 里的注意力状态：一个查询对一组 KV 下标 I 的注意力，可以完整地用两样东西描述，输出 v(I) 和 log-sum-exp s(I) = log Σ exp(si)。两组不相交的下标的状态可以合并：

A shared prefix saves memory, but not reads. In plain paged decode, when 64 requests share one long system prompt, 64 thread blocks each read that prefix’s KV from memory again. Cascade attention rests on the attention state of FlashInfer’s docs/tutorials/recursive_attention.rst: one query’s attention over a set I of KV indices is fully described by two things, the output v(I) and the log-sum-exp s(I) = log Σ exp(si). The states of two disjoint index sets merge:

v(I ∪ J) = (v(I)·exp(s(I)) + v(J)·exp(s(J))) / (exp(s(I)) + exp(s(J)))
s(I ∪ J) = log(exp(s(I)) + exp(s(J)))
# 实际实现先减去最大值，保证数值稳定（文档原注）

这个合并满足交换律和结合律，所以可以把 KV 切成「共享前缀」和「各自的后缀」两段分别算，再合并。flashinfer/cascade.py 的 MultiLevelCascadeAttentionWrapper（第 226 行）就是这样：每一级有自己的 qo_indptr、kv_indptr、kv_indices、kv_last_page_len，所有级共用同一个分页 KV 张量（kv_layout.rst 的 Multi-level Cascade 一节）。它文档字符串里的例子，顶层的 qo_indptr 是 [0, batch_size]：整批查询被当成一个「请求」，一起对共享前缀做一次类似预填充的注意力，这段 KV 只读一次，并且能用上 Tensor Core；底层每个查询对自己的后缀做解码。run（第 537–571 行）先算最后一级，再用 merge_state_in_place 把其余各级合并进来。

The merge is commutative and associative, so the KV can be cut into a shared prefix and per-request suffixes, computed separately and merged. MultiLevelCascadeAttentionWrapper in flashinfer/cascade.py (line 226) does exactly this: each level has its own qo_indptr, kv_indptr, kv_indices and kv_last_page_len, and all levels share one paged KV tensor (the Multi-level Cascade section of kv_layout.rst). In the example of its docstring, the top level’s qo_indptr is [0, batch_size]: the whole batch of queries is treated as one request that attends to the shared prefix once, prefill-style, so that KV is read once and Tensor Cores can be used; the bottom level has each query decode over its own suffix. run (lines 537–571) computes the last level, then merges the other levels in with merge_state_in_place.

收益不是无条件的。文档字符串原话是层数越多不一定越好，因为合并本身有开销；recursive_attention.rst 声称在长上下文、大批次下共享前缀的批量解码可以快 30 倍，这是 FlashInfer 自己的数字，本页没有复现。v0.5.22 的 flashinfer_backend.py 里没有出现 MultiLevelCascadeAttentionWrapper（2026-11-01 在这个文件里检索）；但同样的合并在预填充里每次都在用：带已缓存前缀的 extend 批次先用 ragged 包装器算新 token 对新 token，再用分页包装器算新 token 对已缓存前缀，最后 merge_state 合并（第 1442–1463 行）。

The gain is not unconditional. The docstring itself says more levels are not always better because merging has a cost; recursive_attention.rst claims shared-prefix batch decoding can be 30 times faster with long contexts and large batches, which is FlashInfer’s own number and is not reproduced on this page. At v0.5.22, MultiLevelCascadeAttentionWrapper does not appear in flashinfer_backend.py (searched in that file on 2026-11-01); the same merge is used on every prefill, though: an extend batch with a cached prefix first runs the ragged wrapper for new tokens against new tokens, then the paged wrapper for new tokens against the cached prefix, and merges the two with merge_state (lines 1442–1463).

5. 后端怎样建这些数组

5. How the backend builds the arrays

每个前向步开始时，模型执行器调用注意力后端的 init_forward_metadata（flashinfer_backend.py 第 962 行），它按批次的模式分三路：解码、推测解码的验证、以及 extend（预填充）。解码这一路（第 969–984 行）一直走到 FlashInferIndicesUpdaterDecode.call_begin_forward（第 1726 行）：

At the start of each forward step, the model executor calls the attention backend’s init_forward_metadata (line 962 of flashinfer_backend.py), which branches three ways on the batch mode: decode, speculative verify, and extend (prefill). The decode branch (lines 969–984) runs down to FlashInferIndicesUpdaterDecode.call_begin_forward (line 1726):

  1. kv_indptr[1 : bs + 1] = torch.cumsum(paged_kernel_lens, dim=0)（第 1750 行）：每个请求的 KV 长度的前缀和，就是 CSR 的行指针。缓冲区是预先分配好的，首元素一直是 0。
  2. kv_indptr[1 : bs + 1] = torch.cumsum(paged_kernel_lens, dim=0) (line 1750): the prefix sum of each request’s KV length, which is the CSR row pointer. The buffer is preallocated, and its first element stays 0.
  3. kv_indices 是一块 int32 缓冲区（开了 CUDA 图时直接用图的输入缓冲区，第 1753–1755 行），由 kv_index_translator.pack_read_stream（mem_cache/kv_index_translator.py 第 458 行）填满。普通情况下它启动 Triton 内核 create_flashinfer_kv_indices_triton（第 507 行；定义在 kernels/ops/kvcache/kv_indices.py 第 22 行）：每个请求一个程序，按 512 一块把 req_to_token 里这个请求那一行的前 seq_len 个槽位号复制到 kv_indices[kv_indptr[b]:]。所以 indices 是在 GPU 上由一个小内核从槽位表「压平」出来的。
  4. kv_indices is an int32 buffer (the graph’s own input buffer when CUDA graphs are on, lines 1753–1755), filled by kv_index_translator.pack_read_stream (line 458 of mem_cache/kv_index_translator.py). In the ordinary case it launches the Triton kernel create_flashinfer_kv_indices_triton (line 507; defined at line 22 of kernels/ops/kvcache/kv_indices.py): one program per request copies, in blocks of 512, the first seq_len slot numbers of that request’s row of req_to_token into kv_indices[kv_indptr[b]:]. So the indices are flattened out of the slot table on the GPU by a small kernel.
  5. wrapper.begin_forward(kv_indptr, kv_indices, kv_last_page_len, num_qo_heads, num_kv_heads, head_dim, 1, …)（第 1800–1834 行）。在 FlashInfer 里 begin_forward 就是 plan（decode.py 第 2277 行）。开了 CUDA 图时 SGLang 把它换成 FlashInfer 的 fast_decode_plan（在 flashinfer_backend.py 第 76–81 行导入，第 817–821 行装上；定义在 FlashInfer decode.py 第 4395 行），这是 Phase 3 的话题。
  6. wrapper.begin_forward(kv_indptr, kv_indices, kv_last_page_len, num_qo_heads, num_kv_heads, head_dim, 1, …) (lines 1800–1834). In FlashInfer, begin_forward is plan (line 2277 of decode.py). With CUDA graphs on, SGLang swaps in FlashInfer’s fast_decode_plan (imported at lines 76–81 of flashinfer_backend.py, installed at 817–821; defined at line 4395 of FlashInfer’s decode.py), which is a Phase 3 topic.
  7. 之后每一层的 forward_decode（第 1481 行）先把新 token 的 K/V 写进池子，再调 decode_wrapper.forward(q, kv_cache, …)（第 1526 行），其中 kv_cache 就是这一层的 (K, V) 池张量。
  8. After that, each layer’s forward_decode (line 1481) first writes the new token’s K/V into the pool, then calls decode_wrapper.forward(q, kv_cache, …) (line 1526), where kv_cache is this layer’s (K, V) pool tensors.

extend 这一路多一层判断：确定性推理、分段 CUDA 图和强制分页都会关掉 ragged（第 1018–1022 行）。用 ragged 时，分页那部分的长度取前缀长度 prefix_lens（第 1915–1918 行），qo_indptr 是新 token 数的前缀和（第 2225 行），ragged 包装器的 plan 把它同时当作查询和 KV 的 indptr（第 2257–2264 行），因为新 token 只看新 token 和前缀。

The extend branch adds one decision: deterministic inference, piecewise CUDA graphs and forced paging all turn ragged off (lines 1018–1022). With ragged on, the paged part’s lengths are the prefix lengths prefix_lens (lines 1915–1918), qo_indptr is the prefix sum of new-token counts (line 2225), and the ragged wrapper’s plan takes it as both the query and the KV indptr (lines 2257–2264), because new tokens see only new tokens plus the prefix.

constant uint D = 128;   // head_dim; each of the 32 lanes owns 4 of the 128 dims

// One threadgroup per (request b, head h). PAGED: the slot of token t is indices[indptr[b] + t];
// otherwise the cache is contiguous per request (the ragged layout): slot = indptr[b] + t.
inline void attend(bool PAGED, device const float* q, device const half* k, device const half* v,
                   device const int* indptr, device const int* indices, device float* o,
                   uint H, uint h, uint b, uint lane, uint sg,
                   threadgroup float* sm, threadgroup float* sl, threadgroup float4* sacc) {
    uint begin = uint(indptr[b]), len = uint(indptr[b + 1]) - begin;
    float4 qv = ((device const float4*)(q + (b * H + h) * D))[lane];
    float scale = rsqrt(float(D)), m = -INFINITY, l = 0.0f;
    float4 acc = 0.0f;
    for (uint t = sg; t < len; t += NSG) {
        uint slot = PAGED ? uint(indices[begin + t]) : begin + t;   // the only difference
        uint base = (slot * H + h) * D;                             // KV row layout [slot, H, D]

        l = l * c + p; m = mNew;

1. In radix_cache.py at v0.5.22, what does the value of a TreeNode hold?

KV 只存在池里一份，节点只记槽位号，所以分裂节点时切的是槽位号张量，KV 不动，驱逐时把这些槽位还给分配器。比对用的是 key 里的 token id，不是 value；节点上的 hash_value 是按页算的哈希，_match_prefix_helper 匹配时并不用它。The KV exists once in the pool and the node records only slot numbers, so splitting a node cuts the tensor of slot numbers without moving KV, and eviction hands those slots back to the allocator. Matching uses the token ids in key, not value; the node’s hash_value is a per-page hash, and _match_prefix_helper does not use it to match.

2. 三个请求的 KV 长度是 9、9、6，页大小为 1。交给 FlashInfer 分页 API 的 kv_indptr 是什么？

Without the leading 0 the first request has no start; [0, 9, 9, 6] lists the lengths, not their prefix sum. SGLang fills it with exactly a cumsum at line 1750 of flashinfer_backend.py.

3. 64 个请求共享一段长前缀。两级 cascade 比普通分页解码快，主要原因是什么？

3. 64 requests share one long prefix. What mainly makes two-level cascade faster than plain paged decode?

每个请求的查询不同，前缀上的分数和 softmax 也各不相同，一个都不能跳过；cascade 省的是读，不是算。它也不改变数据类型，MultiLevelCascadeAttentionWrapper 的各级共用同一个分页 KV 张量。省下的是 63 遍重复读，代价是一次合并。Each request has its own query, so its scores and softmax over the prefix differ, and none can be skipped; cascade saves reads, not math. Nor does it change the data type: every level of MultiLevelCascadeAttentionWrapper shares one paged KV tensor. What it saves is 63 repeated reads, at the price of one merge.

缓存装不下 2 GB：共享前缀那一行说明了缓存的作用随共享部分变大而减弱。编译器看不到运行时才填的索引内容，不可能重排。剩下的解释是行的粒度：256 字节的连续块对内存来说已经足够大，额外的 4 字节索引不到 KV 字节的 1%。No cache holds 2 GB: the shared-prefix row shows the cache helping less as the shared part grows. The compiler cannot see index contents that are filled at run time, so it cannot reorder them. What remains is row granularity: a 256-byte contiguous block is already large enough for memory, and the extra 4-byte index is under 1% of the KV bytes.
