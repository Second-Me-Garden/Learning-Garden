同一个注意力算子，在预填充和解码里是两种完全不同的内核。预填充一次给几千个查询，运算量随长度平方增长，要紧的是别把 T × T 的分数矩阵写回显存，并让 tensor core 一直有活干：这是 FlashAttention 的分块与在线 softmax，到 Hopper 上再加 FA3 的 warp 专门化和 FP8。解码每个头只有一个查询，要做的只是把整段 KV 从显存里流过一遍；批大小为 1 时连 GPU 都填不满，于是要沿着 KV 的长度切开、各算一段、最后合并：这是 split-KV，也叫 flash-decoding。SGLang v0.5.22 让两个阶段各选各的内核：--prefill-attention-backend 和 --decode-attention-backend。这台 Apple M5 上实测：64K 个 token 的解码，不切分时 8 个头只用 8 个 SIMD-group，读 KV 只有约 16 GB/s；每个头切成 256 段后跑到约 125 GB/s，快约 7.9 倍，结果与 CPU 参考一致。哪些跑过、哪些没跑过：Lab B 的 Metal 程序 2026-11-01 在这台 Apple M5 上实际运行，数字原样贴出；Lab A 在 L4 上比较两个注意力后端、在 H100 上比较 FA3 与 FA2，未运行，是 2026-11-01 根据 SGLang v0.5.22 的源码和几篇论文整理的。

The same attention operator becomes two entirely different kernels in prefill and in decode. Prefill hands over thousands of queries at once and its arithmetic grows with the square of the length; what matters is never writing the T × T score matrix back to memory and keeping the tensor cores busy: FlashAttention’s tiling and online softmax, with FA3’s warp specialization and FP8 added on Hopper. Decode has one query per head, and all it has to do is stream the whole KV through from memory once; at batch size 1 it cannot even fill the GPU, so the KV is cut along its length, each piece is computed separately, and the pieces are merged at the end: split-KV, also called flash-decoding. SGLang v0.5.22 lets each phase choose its own kernels with --prefill-attention-backend and --decode-attention-backend. Measured on this Apple M5: decoding against 64K tokens without splitting puts 8 heads on only 8 SIMD-groups and reads KV at about 16 GB/s; cutting each head into 256 splits reaches about 125 GB/s, about 7.9 times as fast, and the result matches the CPU reference. What was run and what was not: the Metal program of Lab B was actually run on this Apple M5 on 2026-11-01 and its numbers are pasted as they came; Lab A, which compares two attention backends on an L4 and FA3 against FA2 on an H100, is not run, assembled from the SGLang v0.5.22 source and the papers on 2026-11-01.

核心概念

Core concepts

同一个注意力算子，预填充一次喂进几千个 token，解码一次只喂一个，坏的地方却不一样。预填充照教科书先算出整张分数矩阵 S，Qwen3-8B 在 T = 4096 时一层就是约 1.07 GB，写一次读一次就把本该受算力限制的内核拖回带宽一侧；可 softmax 偏偏要整行的最大值和整行的和。解码没有大矩阵，但查询长度是 1，线程块只有「批 × 头」那么多，批小时大部分 SM 闲着，带宽读不满。

One attention operator, fed thousands of tokens at once in prefill and a single token in decode, goes wrong in two different ways. Prefill done the textbook way first materializes the whole score matrix S, about 1.07 GB per layer for Qwen3-8B at T = 4096, and writing and re-reading it drags a kernel that should be compute-bound back to the bandwidth side; yet softmax needs the maximum and the sum of a whole row. Decode has no large matrix, but its query length is 1, so there are only batch × heads thread blocks, and at small batch most SMs sit idle and the bandwidth goes unused.

概念 2 的分块与在线 softmax 让 S 只活在片上而结果仍然精确，概念 4 的 split-KV 把一个查询的 KV 读取摊到所有 SM 上，概念 6 让两个阶段各用各的内核。

Concept 2, tiling with the online softmax, keeps S on chip while the result stays exact; concept 4, split-KV, spreads one query’s KV read over every SM; and concept 6 lets each phase use its own kernel.

1. 同一个注意力，两种界

1. One attention, two bounds

设一层有 Hq 个查询头、Hkv 个 KV 头，head_dim 为 d，BF16 每元素 2 字节。每一对（查询，键）在 QKT 里做 d 次乘加、在 PV 里再做 d 次，共 4d FLOP。

Let a layer have Hq query heads and Hkv KV heads with head_dim d, at 2 bytes per BF16 element. Each (query, key) pair does d multiply-adds in QKT and d more in PV, 4d FLOP in all.

  • 预填充 T 个 token（因果）：约 T²/2 对，运算 ≈ 2·d·T²·Hq；字节是读 Q、K、V、写 O，≈ 2·T·d·(2Hq + 2Hkv)。运算强度随 T 线性增长。代入 Phase 0 的 Qwen3-8B（Hq = 32，Hkv = 8，d = 128），T = 4096 时一层约 137.5 GFLOP、83.9 MB，约 1640 FLOP/字节，远过 L4 约 400 的拐点。
  • Prefill of T tokens (causal): about T²/2 pairs, so FLOPs ≈ 2·d·T²·Hq; the bytes are reading Q, K, V and writing O, ≈ 2·T·d·(2Hq + 2Hkv). The intensity grows linearly with T. With Phase 0’s Qwen3-8B (Hq = 32, Hkv = 8, d = 128) at T = 4096, one layer is about 137.5 GFLOP over 83.9 MB, about 1640 FLOP per byte, far past the L4’s ridge of about 400.
  • 解码，上下文 L：每个查询头一个查询，运算 4·d·L·Hq；字节是把 K、V 读一遍，4·d·L·Hkv。运算强度 = Hq ÷ Hkv，也就是 GQA 的组大小，与 L 无关。Qwen3-8B 是 4 FLOP/字节，正是 Phase 0 算出的数。
  • Decode with context L: one query per query head, 4·d·L·Hq FLOP; the bytes are one read of K and V, 4·d·L·Hkv. The intensity is Hq ÷ Hkv, the GQA group size, independent of L. For Qwen3-8B it is 4 FLOP per byte, exactly the figure Phase 0 worked out.

预填充的高强度有一个前提：分数矩阵 S = QKT 和 P = softmax(S) 不能写回显存。照教科书的写法先算出整个 S，Qwen3-8B 在 T = 4096 时一层的 S 是 4096² × 32 个 BF16，约 1.07 GB，写一次再读一次就是 2.15 GB，在 L4 的 300 GB/s 下至少 7.2 ms，而这一层的运算按峰值算力只要约 1.14 ms：本来受算力限制的内核被拖回了带宽一侧。FlashAttention 的全部意义就是让 S 和 P 只活在片上。解码这边没有大的中间矩阵，每个查询只有长度为 L 的一行分数，问题变成另一个：怎样用满带宽。以上都是由形状推出的下限，不是测量值。

Prefill’s high intensity has one precondition: the score matrix S = QKT and P = softmax(S) must never be written back to memory. Computed the textbook way, S for one Qwen3-8B layer at T = 4096 is 4096² × 32 BF16 values, about 1.07 GB; writing it once and reading it once is 2.15 GB, at least 7.2 ms at the L4’s 300 GB/s, while the layer’s arithmetic at peak compute takes only about 1.14 ms: a kernel that should be compute-bound is dragged back to the bandwidth side. The whole point of FlashAttention is to keep S and P on chip. Decode has no large intermediate matrix, only one row of L scores per query, and its problem is a different one: how to use all of the bandwidth. All of these are lower bounds derived from the shapes, not measurements.

2. FlashAttention 与 FlashAttention-2：分块与在线 softmax

2. FlashAttention and FlashAttention-2: tiling and the online softmax

FlashAttention（Dao 等，arXiv:2205.14135，读的是 v2）把注意力写成 IO 感知的算法：按块把 Q、K、V 从显存（论文称 HBM）搬进片上 SRAM，在片上算完一块的 S、P 和对 O 的贡献，不把 S 写回去，摘要说它比标准注意力需要更少的 HBM 访问。难点是 softmax 要用整行的最大值和整行的和，而一块只看到一行的一段。解法就是 GPU 专题作品项目里的在线 softmax，从一行推广到一块：

FlashAttention (Dao et al., arXiv:2205.14135, read at v2) recasts attention as an IO-aware algorithm: Q, K and V move from device memory (HBM in the paper) into on-chip SRAM tile by tile, each tile’s S, P and contribution to O are computed on chip, and S is never written back; the abstract says it needs fewer HBM accesses than standard attention. The difficulty is that softmax needs the maximum and the sum of a whole row, while one tile sees only a stretch of the row. The answer is the online softmax of the GPU topic’s capstone, generalized from one row to one tile:

  1. 一个线程块拿到一个查询块 Qi（Br 行），每一行在寄存器里维护三样东西：运行最大值 m、运行和 l、未归一化的输出 O（d 个数），初值是 −∞、0、0。
  2. One thread block takes one query block Qi (Br rows), and each row keeps three things in registers: a running maximum m, a running sum l and an unnormalized output O (d numbers), starting at −∞, 0 and 0.
  3. 依次搬进 Kj、Vj（每块 Bc 个 token），在片上算 S = QiKjT · scale，得到这一块的行最大值，m′ = max(m, rowmax(S))。
  4. Bring in Kj and Vj in turn (Bc tokens per tile), compute S = QiKjT · scale on chip, take this tile’s row maximum, and set m′ = max(m, rowmax(S)).
  5. P = exp(S − m′)；旧的 l 和 O 都是相对旧的 m 算的，先乘 exp(m − m′) 换到新的基准，再加上这一块：l ← l·exp(m − m′) + rowsum(P)，O ← O·exp(m − m′) + P·Vj。
  6. P = exp(S − m′); the old l and O were computed against the old m, so first multiply them by exp(m − m′) to move them to the new baseline, then add this tile: l ← l·exp(m − m′) + rowsum(P), O ← O·exp(m − m′) + P·Vj.
  7. 所有块走完，Oi = O ÷ l，写回显存一次。因果掩码下，越过对角线的整块直接跳过，对角线上的块按位置掩掉一半。
  8. After the last tile, Oi = O ÷ l is written back to memory once. Under the causal mask, tiles entirely past the diagonal are skipped, and the tile on the diagonal masks out half its entries by position.

  1. Tile 1: this tile’s maximum, 3, becomes m, and P is taken relative to m, so its largest entry is exp(0) = 1 and cannot overflow. l = 1.135, the first figure of step 6 of diagram (a).
  2. Tile 2: the new tile holds a 5, larger than the old m = 3. The old l and O were computed against 3, so they are first multiplied by exp(3 − 5) = 0.1353 to move them to the baseline 5, and then the new tile’s P and P·V are added. l becomes 1.203, as in the diagram.

结果是精确的，不是近似：每一步的缩放都只是把同一个和换一个基准。动画 (a) 用一行四个分数手算一遍。FlashAttention-2（arXiv:2307.08691，v1）不改这个算法，改的是分工，摘要列了三条：减少非矩阵乘的运算（例如 1/l 只在最后乘一次，而不是每块都乘），即使只有一个头也把工作分给不同线程块以提高占用率（正文说是沿序列长度分），以及在线程块内部按 Q 的行而不是按 K/V 给 warp 分工，减少经过 shared memory 的通信。摘要说这样比 FlashAttention 快约 2 倍，在 A100 上达到理论峰值的 50–73%。

The result is exact, not an approximation: each rescaling merely moves the same sum to a new baseline. Diagram (a) works one row of four scores by hand. FlashAttention-2 (arXiv:2307.08691, v1) keeps the algorithm and changes the division of work, listing three changes in its abstract: fewer non-matmul FLOPs (for example, 1/l applied once at the end instead of after every tile), parallelizing across thread blocks even for a single head to raise occupancy (along the sequence length, per the paper body), and, inside a thread block, dividing work among warps by rows of Q instead of by K/V to cut communication through shared memory. The abstract reports about 2 times the speed of FlashAttention, reaching 50–73% of the theoretical peak on an A100.

3. FA3：Hopper 上的 warp 专门化与 FP8

3. FA3: warp specialization and FP8 on Hopper

FlashAttention-3（arXiv:2407.08608，v2）的摘要开门见山：FA2 在 H100 上只用到 35% 的算力。Hopper 的 tensor core（WGMMA）和 TMA 搬运都是异步的，FA3 用三招把它们用起来：

FlashAttention-3 (arXiv:2407.08608, v2) states it in its abstract: FA2 reaches only 35% utilization on the H100. Hopper’s tensor cores (WGMMA) and its TMA copies are both asynchronous, and FA3 uses three techniques to exploit them:

  • warp 专门化：一部分 warp 只负责用 TMA 把 K、V 块搬进 shared memory（生产者），其余的 warpgroup 只做矩阵乘和 softmax（消费者），搬运与计算整体重叠。
  • Warp specialization: some warps only bring K and V tiles into shared memory with TMA (producers) while the other warpgroups only do the matmuls and the softmax (consumers), so data movement overlaps computation as a whole.
  • GEMM 与 softmax 交错：softmax 里的 exp 不走 tensor core，吞吐低得多（H100 上 exp 所用的多功能单元只有 3.9 TFLOPS，矩阵乘是 989 TFLOPS，FA3 论文第 3.2 节）；FA3 让一个 warpgroup 做 softmax 时另一个做 GEMM，并在一个 warpgroup 内部把下一块的 QKT 与这一块的 softmax 流水起来（论文正文称前者为 ping-pong 调度）。
  • Interleaved GEMM and softmax: the exp in softmax does not run on the tensor cores and has far lower throughput (the H100’s multi-function units that compute exp deliver 3.9 TFLOPS against 989 TFLOPS of matmul, §3.2 of the FA3 paper); FA3 has one warpgroup do softmax while another does a GEMM, and pipelines the next tile’s QKT with this tile’s softmax inside one warpgroup (the paper body calls the former ping-pong scheduling).
  • FP8：块量化（每块一个缩放因子）加上非相干处理（把 Q 和 K 乘以一个随机 ±1 对角矩阵再乘一个 Hadamard 矩阵来摊平离群值，FA3 论文第 3.3 节，可以在 O(d log d) 内算完），摘要说 FP8 版本的数值误差比基线 FP8 注意力低 2.6 倍。
  • FP8: block quantization (one scale per block) plus incoherent processing (multiplying Q and K by a random ±1 diagonal matrix times a Hadamard matrix to spread out outliers, §3.3 of the FA3 paper, computable in O(d log d)); the abstract says the FP8 version has 2.6 times lower numerical error than a baseline FP8 attention.

摘要给的结果：在 H100 上比 FA2 快 1.5–2.0 倍，FP16 最高 740 TFLOPs/s（75% 利用率），FP8 接近 1.2 PFLOPs/s。这些是论文作者的数字，本页没有复现。FlashAttention 仓库的 README（2026-11-01 读取）把 FA3 放在 hopper/ 目录，写明「optimized for Hopper GPUs」，要求 H100 / H800 和 CUDA 12.3 以上。

4. 解码：split-KV（flash-decoding）

4. Decode: split-KV (flash-decoding)

FlashAttention 沿批和查询块分配线程块。解码时查询长度是 1，线程块数就只剩「批大小 × 头数」这么多。Flash-Decoding 的文章（Dao、Haziza、Massa、Sizov，Stanford CRFM，2023-10-12）说得很直白：批大小小于 SM 数时（A100 有 108 个），这个算子只用到 GPU 的一小部分；批大小为 1 时 FlashAttention 用不到 GPU 的 1%。解法分三步，文章原样列出：

FlashAttention assigns thread blocks along the batch and the query blocks. In decode the query length is 1, so the number of thread blocks shrinks to batch size × heads. The Flash-Decoding post (Dao, Haziza, Massa and Sizov, Stanford CRFM, 2023-10-12) puts it plainly: when the batch size is smaller than the number of SMs (108 on an A100), the operation uses only a small part of the GPU, and at batch size 1 FlashAttention uses less than 1% of it. The fix has three steps, which the post lists as such:

  1. 把 K/V 沿长度切成 S 段。
  2. Split the K/V along its length into S chunks.
  3. 每一段由自己的线程块并行地算查询对这一段的注意力（段内就是概念 2 的在线 softmax），写出未归一化的部分输出 os，外加每行每段一个标量：这一段的 log-sum-exp（等价于这里的 ms 与 ls）。
  4. Compute the query’s attention to each chunk in parallel in its own thread block (the online softmax of concept 2 within the chunk), writing an unnormalized partial output os plus one scalar per row per split: that chunk’s log-sum-exp (equivalent to ms and ls here).
  5. 再起一个小内核合并：M = maxs ms，ws = exp(ms − M)，o = Σ ws·os ÷ Σ ws·ls。这和块内的缩放是同一个公式，所以结果同样精确。
  6. Merge in one more small kernel: M = maxs ms, ws = exp(ms − M), o = Σ ws·os ÷ Σ ws·ls. This is the same formula as the in-tile rescaling, so the result is just as exact.

把上面概念 2 的那一行当成解码：一个查询、4 个缓存 token，分数 [1, 3 | 5, 2]，V 是 [10, 20 | 30, 40]。这次不是一个线程块依次走两块，而是切成 S = 2 段，两个线程块同时各算一段（图解 (b) 用 S = 4，算法相同）。

Treat the row of concept 2 as a decode: one query, 4 cached tokens, scores [1, 3 | 5, 2] and V [10, 20 | 30, 40]. This time one thread block does not walk two tiles in turn; the KV is cut into S = 2 splits and two thread blocks compute one split each at the same time (diagram (b) uses S = 4; the algorithm is the same).

split 1 : m_1 = 3   l_1 = 0.1353 + 1      = 1.1353   o_1 = 0.1353*10 + 20      = 21.353
split 2 : m_2 = 5   l_2 = 1 + 0.0498      = 1.0498   o_2 = 30 + 0.0498*40      = 31.991
merge   : M = max(3, 5) = 5    w_1 = exp(3 - 5) = 0.1353    w_2 = exp(5 - 5) = 1
          o = (0.1353*21.353 + 1*31.991) / (0.1353*1.1353 + 1*1.0498)
            = 34.881 / 1.2034 = 28.985
  1. stage 1：两个线程块互不等待，各自在段内做在线 softmax，写出 (ms, ls, os)。这里 d = 1，每段多写 d + 2 = 3 个数。
  2. stage 2：合并内核取 M = 5，第 1 段的结果按旧基准 3 算，乘权重 exp(3 − 5) = 0.1353；第 2 段已经以 5 为基准，权重是 1。
  3. 分子 34.881、分母 1.2034，与概念 2 里一个线程块依次走两块时块 2 结束的 O 和 l 一模一样，最终仍是 28.985。合并就是块内缩放那一步，只是挪到了另一个内核里。
  4. 收益在线程块数：Lab B 在 M5 上把每头 1 段换成每头 256 段，64K 个 token 的解码从 17.01 ms 降到 2.15 ms（图解 (b) 第 7 步）。
  1. Stage 1: the two thread blocks never wait for each other; each runs the online softmax within its split and writes (ms, ls, os). With d = 1, each split writes d + 2 = 3 extra numbers.
  2. Stage 2: the merge kernel takes M = 5; split 1 was computed against the old baseline 3 and gets the weight exp(3 − 5) = 0.1353, while split 2 is already against 5 and gets the weight 1.
  3. The numerator, 34.881, and the denominator, 1.2034, are exactly the O and l at the end of tile 2 when one thread block walked both tiles in concept 2, and the answer is again 28.985. The merge is the in-tile rescaling step moved into another kernel.
  4. The gain is in the number of thread blocks: Lab B on the M5 went from 1 split per head to 256, and a decode over 64K tokens fell from 17.01 ms to 2.15 ms (step 7 of diagram (b)).

代价是每段多写 d + 2 个数、多一次启动，和整段 KV 比微不足道；收益是线程块数从「批 × 头」变成「批 × 头 × S」，带宽能用满。切多少段要权衡：太少填不满 GPU，太多则每段太短、合并变贵。v0.5.22 里三种做法：FlashInfer 的解码 wrapper 在 plan() 里决定切分（SGLang 文档 attention_backend.mdx 讲如何实现后端的部分，第 745 行说 init_forward_metadata 里调用 plan 函数做 split_kv 这类优化；Phase 3 细讲 plan/run）；Triton 后端用固定上限 --triton-attention-num-kv-splits，默认 8，帮助文字写的正是「flash decoding Triton kernel」（arg_groups/fields/exec_.py 第 359–362 行），内核在 python/sglang/kernels/ops/attention/decode_attention.py：分段的 _fwd_kernel_stage1（GQA 用 _fwd_grouped_kernel_stage1）和合并的 _fwd_kernel_stage2；FA3 后端把 num_splits 设成 0，源码注释说这是把 SplitKV 的大小交给 FA 运行时决定（flashattention_backend.py 第 338–341 行）。

The cost is d + 2 extra numbers written per split and one more launch, negligible against the whole KV; the gain is that thread blocks go from batch × heads to batch × heads × S, so the bandwidth can be used in full. The number of splits is a trade-off: too few leaves the GPU unfilled, too many makes each split short and the merge expensive. v0.5.22 does it three ways: FlashInfer’s decode wrapper decides the split in plan() (the part of SGLang’s attention_backend.mdx on implementing a backend says, on line 745, that init_forward_metadata calls the plan function for optimizations such as split_kv; Phase 3 covers plan/run); the Triton backend uses a fixed cap, --triton-attention-num-kv-splits, default 8, whose help text says exactly “flash decoding Triton kernel” (arg_groups/fields/exec_.py, lines 359–362), with the kernels in python/sglang/kernels/ops/attention/decode_attention.py: _fwd_kernel_stage1 for the splits (_fwd_grouped_kernel_stage1 under GQA) and _fwd_kernel_stage2 for the merge; the FA3 backend sets num_splits to 0, which the source comment says delegates SplitKV sizing to the FA runtime (flashattention_backend.py, lines 338–341).

同一个合并公式在 SGLang 里还出现在另一处：FlashInfer 后端做预填充时，新 token 之间的注意力用 ragged wrapper（因果）、对已缓存前缀的注意力用 paged wrapper（不因果），两边各返回输出和 LSE，再用 merge_state 合并（flashinfer_backend.py 第 1442–1463 行）。这就是概念 6 里分块预填充和 Phase 1 前缀共享背后的那一步。

The same merge formula appears in one more place in SGLang: during prefill, the FlashInfer backend computes attention among the new tokens with the ragged wrapper (causal) and attention to the cached prefix with the paged wrapper (not causal); each returns an output and an LSE, and merge_state combines them (flashinfer_backend.py, lines 1442–1463). This is the step behind chunked prefill in concept 6 and prefix sharing in Phase 1.

5. MLA：DeepSeek 式模型的 KV

5. MLA: the KV of DeepSeek-style models

多头潜在注意力（MLA）由 DeepSeek-V2（arXiv:2405.04434，v5）提出，摘要说 MLA 把 KV 缓存显著压缩成一个潜向量，并说 DeepSeek-V2 比 DeepSeek 67B 的 KV 缓存少 93.3%；DeepSeek-V3 技术报告（arXiv:2412.19437，v2）沿用了它。不缓存每个头的 k、v，而是每个 token 缓存一个共享的潜向量 cKV，外加一个单独携带 RoPE 的小键。DeepSeek-V3 的 config.json（2026-11-01 从 Hugging Face 读取）：128 个注意力头，kv_lora_rank 512，qk_rope_head_dim 64，qk_nope_head_dim 128，v_head_dim 128，61 层。于是每个 token 每层缓存 512 + 64 = 576 个数；同样的头数若用普通多头注意力，要缓存 128 × (128 + 64) 个键和 128 × 128 个值，共 40960 个，约是 MLA 的 71 倍（由 config 推出）。SGLang 内置 FlashMLA 的构建文件里有名为 phase1_k576 的稀疏预填充实例（第 120 行），与这个 576 对得上（推断）。

Multi-head latent attention (MLA) was introduced by DeepSeek-V2 (arXiv:2405.04434, v5), whose abstract says MLA significantly compresses the KV cache into a latent vector and that DeepSeek-V2 has a 93.3% smaller KV cache than DeepSeek 67B; the DeepSeek-V3 technical report (arXiv:2412.19437, v2) keeps it. Instead of caching each head’s k and v, each token caches one shared latent vector cKV plus a small separate key that carries RoPE. DeepSeek-V3’s config.json (read from Hugging Face on 2026-11-01): 128 attention heads, kv_lora_rank 512, qk_rope_head_dim 64, qk_nope_head_dim 128, v_head_dim 128, 61 layers. So each token caches 512 + 64 = 576 numbers per layer; ordinary multi-head attention with the same heads would cache 128 × (128 + 64) keys and 128 × 128 values, 40960 in all, about 71 times as much (derived from the config). The build file of SGLang’s bundled FlashMLA has a sparse-prefill instance named phase1_k576 (line 120), which matches this 576 (an inference).

对内核来说，变化在运算强度上。DeepSeek-V2 论文描述了把上投影矩阵「吸收」进查询和输出投影的算法，解码时 128 个查询头都直接对同一份 576 维的潜向量做注意力，就像一个 128 组的多查询注意力。按这个吸收形式推算：每个缓存 token 读 576 × 2 = 1152 字节，每个头做 2 × 576（打分）+ 2 × 512（对潜向量加权）= 2176 FLOP，128 个头共约 27.9 万 FLOP，约 242 FLOP/字节，比 Qwen3-8B 的 4 高六十倍。这是推断，不是测量；张量并行把头分到几张卡上时，每张卡上的强度相应降低。所以 MLA 的解码内核要像预填充那样认真对待 tensor core，FlashMLA 就是为此写的。

For the kernel, the change is in arithmetic intensity. The DeepSeek-V2 paper describes absorbing the up-projection matrices into the query and output projections, so in decode all 128 query heads attend directly to the same 576-dimensional latent, like a multi-query attention with 128 heads per group. Worked out in that absorbed form: each cached token reads 576 × 2 = 1152 bytes, and each head does 2 × 576 (scoring) + 2 × 512 (weighting the latent) = 2176 FLOP, about 279 thousand FLOP over 128 heads, about 242 FLOP per byte, sixty times Qwen3-8B’s 4. This is an inference, not a measurement; when tensor parallelism spreads the heads over several GPUs, the intensity on each GPU drops accordingly. So an MLA decode kernel has to take the tensor cores as seriously as a prefill kernel does, which is what FlashMLA was written for.

FlashMLA 现在在哪一层。上游 deepseek-ai/FlashMLA 的 README（main，2026-11-01 读取）开头的破坏性变更通知说：2026.09.30 的版本移除了对 Hopper 架构和前代模型（包括 DeepSeek V3 / V3.2 / V4.0）的支持，改了 FP8 / FP4 KV 缓存格式，需要 Hopper 时切回提交 ba89a3466e9470ad08ab39738d4e7bb66989e1e7；它的要求一节写的是 SM100 / SM103。SGLang v0.5.22 内置的不是上游，而是 sgl-project/FlashMLA 的提交 3620b63（2026-09-28，早于上游那次发布两天；python/sglang/kernels/aot/cmake/flashmla.cmake 第 1–8 行，注释写的是 DeepSeek v4.1 的内核）。这个构建文件仍然生成 sm_90a 代码（第 29–35 行），并编译 sm90 的稠密与稀疏解码（第 105–115 行），CUDA 12.8 以上再加 sm_100f，13.0 以上再加 sm_103a。也就是说，按源码，SGLang 自带的 FlashMLA 在 H100 上有内核；但一个 MLA 模型要在一张 H100 上跑起来、flashmla 后端能不能接它，本页都没有核对，所以 FlashMLA 在本页只作描述，不放进任何一层实验。--attention-backend flashmla 要求 page size 64（attention_backend.mdx 第 329 行），文档给的示例是 8 卡跑 DeepSeek-R1。

Where FlashMLA sits now. The breaking-change notice at the top of the upstream deepseek-ai/FlashMLA README (main, read 2026-11-01) says that the 2026.09.30 release removed support for the Hopper architecture and for earlier models (including DeepSeek V3 / V3.2 / V4.0) and changed the FP8 / FP4 KV-cache format, and that Hopper users should switch to commit ba89a3466e9470ad08ab39738d4e7bb66989e1e7; its requirements section says SM100 / SM103. SGLang v0.5.22 does not bundle upstream but commit 3620b63 of sgl-project/FlashMLA (2026-09-28, two days before that upstream release; python/sglang/kernels/aot/cmake/flashmla.cmake, lines 1–8, whose comment says DeepSeek v4.1 kernels). That build file still generates sm_90a code (lines 29–35) and compiles the sm90 dense and sparse decode (lines 105–115), adding sm_100f above CUDA 12.8 and sm_103a from 13.0. So by the source, SGLang’s own FlashMLA does have kernels for the H100; but whether an MLA model can run on one H100 and whether the flashmla backend accepts it were not checked here, so FlashMLA is only described on this page and placed in no lab tier. --attention-backend flashmla requires page size 64 (attention_backend.mdx, line 329), and the documentation’s example runs DeepSeek-R1 on 8 GPUs.

6. 分块预填充与按阶段选后端

6. Chunked prefill and choosing a backend per phase

分块预填充：一个很长的提示不一次预填充完，而是按 --chunked-prefill-size 个 token 一块地做，帮助文字是「The maximum number of tokens in a chunk for the chunked prefill」，设成 -1 关闭（arg_groups/fields/schedule.py 第 52–55 行）。默认值是 None，启动时按显存大小决定（arg_groups/memory_hook.py 的 handle_gpu_memory_settings，第 90–111 行；门槛按 MiB 比较，gpu_mem 来自 nvidia-smi，单位 MiB）：20 GB 以下 2048，20–35 GB 是 4096（L4 的 24 GB 落在这一档），60–90 GB 是 8192（H100 80 GB）。--enable-mixed-chunk 让预填充块和正在解码的请求拼进同一批（同一文件第 202–205 行），这就是 Phase 0 提到的 ForwardMode.MIXED。对内核而言，第 k 块的查询要看前面所有块已经写进缓存的 KV，再加自己块内的因果部分：查询长度小于 KV 长度、前缀不因果、块内因果。FlashInfer 后端用概念 4 末尾那对 ragged + paged 调用和 merge_state 处理它。这样做的好处在调度上：一个长提示不会一口气占住 GPU 几百毫秒，让正在解码的请求干等（推断：这是对调度目的的概括，源码帮助文字没有这样写）。

Chunked prefill: a very long prompt is not prefilled all at once but in chunks of --chunked-prefill-size tokens, whose help text is “The maximum number of tokens in a chunk for the chunked prefill”; -1 turns it off (arg_groups/fields/schedule.py, lines 52–55). The default is None, decided at startup by memory size (handle_gpu_memory_settings in arg_groups/memory_hook.py, lines 90–111; the thresholds are compared in MiB, and gpu_mem comes from nvidia-smi in MiB): 2048 below 20 GB, 4096 for 20–35 GB (the L4’s 24 GB falls here), 8192 for 60–90 GB (an 80 GB H100). --enable-mixed-chunk lets a prefill chunk and the requests being decoded share one batch (lines 202–205 of the same file), which is the ForwardMode.MIXED of Phase 0. For the kernel, the queries of chunk k must see the KV that all earlier chunks have already written into the cache plus the causal part inside their own chunk: a query length shorter than the KV length, a non-causal prefix and a causal chunk. The FlashInfer backend handles it with the ragged + paged pair and merge_state from the end of concept 4. The benefit is in scheduling: one long prompt does not hold the GPU for hundreds of milliseconds while running decodes wait (an inference summarizing the scheduling purpose; the source help text does not say this).

  • --prefill-attention-backend：「Choose the kernels for prefill attention layers (have priority over --attention-backend).」

All three take their values from the same list on lines 69–99 of arg_groups/choices.py: on NVIDIA there are fa3, fa4, flashinfer, flashmla, trtllm_mla, cutedsl_mla, trtllm_mha and others, and generic ones such as triton, torch_native and flex_attention. The documentation, attention_backend.mdx (lines 507–542), calls using different backends for prefill and decode hybrid attention and marks it experimental: set only one of the two and the other phase inherits --attention-backend; set both and differently, and HybridAttnBackend from hybrid_attn_backend.py is wrapped around them automatically, sending EXTEND to the prefill backend and DECODE to the decode backend. Automatic selection when nothing is given (the same document, lines 545–559): for MHA models, fa3 on Hopper, trtllm_mha on Blackwell, and flashinfer on other architectures such as Ampere and Ada, falling back to triton; for MLA models, fa3 on Hopper, flashinfer on Blackwell (with trtllm_mla picked automatically for DeepSeek V3), and triton elsewhere. Why choose separately: prefill wants a tiled kernel that keeps the tensor cores fed, decode wants a streaming kernel that gathers pages, splits and fits in a CUDA graph, and the library best at one is often not the one best at the other; in the documentation’s words, “one backend excels at prefill and another excels at decode”.

  • 预填充的运算强度随 T 线性增长（Qwen3-8B 在 T = 4096 时约 1640 FLOP/字节），解码的强度等于 GQA 组大小 Hq ÷ Hkv（Qwen3-8B 是 4），与上下文长度无关。
  • 预填充能受算力限制的前提是 S 和 P 不写回显存，FlashAttention 让它们只活在片上。
  • 在线 softmax 每行只带运行最大值 m、运行和 l 和未归一化的 O，新块的最大值更大时先乘 exp(m − m′) 再累加，结果精确。
  • FlashAttention-2 不改算法、改分工：1/l 只在最后乘一次，沿序列长度给线程块分工，块内 warp 按 Q 的行分。
  • split-KV 把 KV 切成 S 段并行算，每段写出 ms、ls、os，再用同一个缩放公式合并，线程块数从「批 × 头」变成「批 × 头 × S」。
  • SGLang 用 --prefill-attention-backend 和 --decode-attention-backend 让两个阶段各用最合适的内核。
  • Prefill’s arithmetic intensity grows linearly with T (about 1640 FLOP per byte for Qwen3-8B at T = 4096), while decode’s equals the GQA group size Hq ÷ Hkv (4 for Qwen3-8B), whatever the context length.
  • Prefill can be compute-bound only if S and P are never written back to memory, and FlashAttention keeps them on chip.
  • The online softmax carries only a running maximum m, a running sum l and an unnormalized O per row, and when a new tile has a larger maximum it multiplies by exp(m − m′) before adding, so the result is exact.
  • FlashAttention-2 keeps the algorithm and changes the division of work: 1/l is applied once at the end, thread blocks are spread along the sequence length, and warps inside a block split the rows of Q.
  • Split-KV computes S chunks of the KV in parallel, each writing ms, ls and os, and merges them with the same rescaling formula, so thread blocks go from batch × heads to batch × heads × S.
  • SGLang’s --prefill-attention-backend and --decode-attention-backend let each phase use the kernel best suited to it.

常见误解

Common misconceptions

  • 误解：FlashAttention 是对 softmax 的近似，换速度丢精度。→ 实际：它是精确的；分数 [1, 3 | 5, 2] 分块算出的和 1.2034 与整行一次算出的相同，误差只来自浮点舍入。
  • 误解：FlashAttention 快是因为少做了乘加。→ 实际：前向的 QKT 和 PV 乘加一个不少；论文摘要说它省的是 HBM 访问，S 不落显存。
  • 误解：解码的上下文越长，就越接近受算力限制。→ 实际：运算和字节都随 L 线性增长，强度固定在 Hq ÷ Hkv；能改变它的是模型结构，比如 MLA 按吸收形式推算约 242 FLOP/字节。
  • Myth: FlashAttention approximates softmax, trading accuracy for speed. → Fact: it is exact; the tiled sum over scores [1, 3 | 5, 2], 1.2034, equals the sum over the whole row at once, and the only error is floating-point rounding.
  • Myth: FlashAttention is fast because it does fewer multiply-adds. → Fact: the forward pass does every multiply-add of QKT and PV; what it saves, per the paper’s abstract, is HBM accesses, because S never reaches memory.
  • Myth: the longer the decode context, the closer it gets to compute-bound. → Fact: FLOPs and bytes both grow linearly in L, so the intensity stays at Hq ÷ Hkv; what changes it is the model architecture, for example about 242 FLOP per byte for MLA in the absorbed form (derived).

#include <metal_stdlib>
using namespace metal;
constant uint D  = 128;   // head_dim; each of the 32 lanes owns 4 output dims
constant uint BR = 16;    // query rows per threadgroup (4 SIMD-groups x 4 rows)
constant uint BC = 32;    // keys per K/V tile: one key per lane when scoring

// prefill: O = softmax(Q K^T * scale, causal) V for one head and BR query rows per threadgroup.
// Q, K, V: [H][T][D] half. O: [H][T][D] float. K/V tiles go through threadgroup memory;
// each row keeps a running max m, a running sum l and an unnormalized output o (the online softmax).
kernel void flash_prefill(device const half* Q [[buffer(0)]], device const half* K [[buffer(1)]],
                          device const half* V [[buffer(2)]], device float* O [[buffer(3)]],
                          constant uint& T [[buffer(4)]], constant float& scale [[buffer(5)]],
                          uint2 tg [[threadgroup_position_in_grid]], uint tid [[thread_index_in_threadgroup]],
                          uint lane [[thread_index_in_simdgroup]], uint sg [[simdgroup_index_in_threadgroup]]) {
    threadgroup half Qs[BR][D], Ks[BC][D], Vs[BC][D];
    uint h = tg.y, q0 = tg.x * BR;
    ulong base = ulong(h) * T * D;
    for (uint i = tid; i < BR * D / 4; i += 128)                       // load this block's Q rows once
        ((threadgroup half4*)Qs)[i] = ((device const half4*)(Q + base + ulong(q0) * D))[i];
    float m[4], l[4]; float4 o[4];
    for (uint r = 0; r < 4; r++) { m[r] = -INFINITY; l[r] = 0.0f; o[r] = float4(0.0f); }
    uint kEnd = q0 + BR;                                                // causal: keys up to the last row of the block
    for (uint k0 = 0; k0 < kEnd; k0 += BC) {
        threadgroup_barrier(mem_flags::mem_threadgroup);
        for (uint i = tid; i < BC * D / 4; i += 128) {                 // stream one K tile and one V tile in
            ((threadgroup half4*)Ks)[i] = ((device const half4*)(K + base + ulong(k0) * D))[i];
            ((threadgroup half4*)Vs)[i] = ((device const half4*)(V + base + ulong(k0) * D))[i];
        }
        threadgroup_barrier(mem_flags::mem_threadgroup);
        for (uint r = 0; r < 4; r++) {
            uint row = sg * 4 + r, qi = q0 + row, kj = k0 + lane;
            float s = 0.0f;                                             // lane j scores key k0 + j

            s = (kj <= qi) ? s * scale : -INFINITY;

            m[r] = mNew;
        }
    }
    for (uint r = 0; r < 4; r++) {

        *(device float4*)(O + base + ulong(qi) * D + lane * 4) = o[r] / l[r];   // normalize once, at the end
    }
}

// decode, step 1: one SIMD-group per (split, head) walks `chunk` keys of one head's KV and writes a partial
// (m, l, o) for its split. With one split per head this is the unsplit kernel: H SIMD-groups for the whole GPU.
kernel void decode_partial(device const half* q [[buffer(0)]], device const half* K [[buffer(1)]],
                           device const half* V [[buffer(2)]], device float* pm [[buffer(3)]],
                           device float* pl [[buffer(4)]], device float* po [[buffer(5)]],
                           constant uint& L [[buffer(6)]], constant uint& chunk [[buffer(7)]],
                           constant float& scale [[buffer(8)]],
                           uint2 tg [[threadgroup_position_in_grid]], uint lane [[thread_index_in_simdgroup]],
                           uint2 ntg [[threadgroups_per_grid]]) {
    uint split = tg.x, h = tg.y, S = ntg.x;
    ulong base = ulong(h) * L * D;
    float4 qv = float4(*(device const half4*)(q + h * D + lane * 4));
    float m = -INFINITY, l = 0.0f; float4 o = float4(0.0f);
    for (uint k = split * chunk; k < (split + 1) * chunk; k++) {       // the SIMD-group reads each K and V row together
        float s = simd_sum(dot(qv, float4(*(device const half4*)(K + base + ulong(k) * D + lane * 4)))) * scale;
        float mNew = max(m, s), corr = exp(m - mNew), p = exp(s - mNew);
        l = l * corr + p;
        o = o * corr + p * float4(*(device const half4*)(V + base + ulong(k) * D + lane * 4));
        m = mNew;
    }
    uint idx = h * S + split;
    if (lane == 0) { pm[idx] = m; pl[idx] = l; }
    *(device float4*)(po + ulong(idx) * D + lane * 4) = o;
}

// decode, step 2: combine the S partials of each head. Rescale each by exp(m_s - M), add, divide by the total sum.
kernel void decode_combine(device const float* pm [[buffer(0)]], device const float* pl [[buffer(1)]],
                           device const float* po [[buffer(2)]], device float* out [[buffer(3)]],
                           constant uint& S [[buffer(4)]],
                           uint h [[threadgroup_position_in_grid]], uint d [[thread_index_in_threadgroup]]) {
    float M = -INFINITY;
    for (uint s = 0; s < S; s++) M = max(M, pm[h * S + s]);
    float lsum = 0.0f, acc = 0.0f;
    for (uint s = 0; s < S; s++) {
        float w = exp(pm[h * S + s] - M);
        lsum += w * pl[h * S + s];
        acc  += w * po[ulong(h * S + s) * D + d];
    }
    out[h * D + d] = acc / lsum;
}

自测

Self-check

1. FlashAttention 处理到第 2 块 K/V 时，某一行的最大值从 m 变成了更大的 m′。它怎样处理已经累加好的 l 和 O？

1. When FlashAttention reaches the second K/V tile, the maximum of one row grows from m to a larger m′. What does it do with the l and O it has already accumulated?

l 和 O 里的每一项都是相对旧的 m 算的，乘 exp(m − m′) 正好把它们换成相对 m′ 的值，所以 b 精确且不用回头。a 也能得到对的结果，但每次最大值变大都要重读前面的块，失去了分块的意义。c 不对：不同的块是相对不同的 m 累加的，最后一次除法无法知道每一项当初用的是哪个 m。Every term in l and O was computed against the old m, and multiplying by exp(m − m′) turns each into its value against m′, so b is exact and never looks back. a also gives the right answer, but it rereads earlier tiles every time the maximum grows, defeating the tiling. c is wrong: different tiles were accumulated against different values of m, and one final division cannot know which m each term used.

2. 批大小 1、8 个 KV 头、上下文 64K 的解码，在一块有几十个 SM 的 GPU 上。不做 split-KV 时为什么慢？

2. Decode at batch size 1 with 8 KV heads and a 64K context runs on a GPU with dozens of SMs. Why is it slow without split-KV?

解码注意力的强度是 GQA 组大小，与上下文长度无关，远低于拐点，所以 a 不对。FlashAttention 本来就不需要整段 KV 放进 shared memory，它按块流过，所以 c 不对。问题出在并行度：线程块按批和查询块分配，解码时只剩批 × 头个。Lab B 在 M5 上量到，同样 64K 的 KV，8 个 SIMD-group 只读到约 16 GB/s，切成 2048 个之后约 125 GB/s。Decode attention’s intensity is the GQA group size, independent of the context length and far below the ridge, so a is wrong. FlashAttention never needed the whole KV in shared memory; it streams through in tiles, so c is wrong. The problem is parallelism: thread blocks are assigned by batch and query block, which in decode leaves only batch × heads of them. Lab B measured on the M5 that the same 64K of KV reads at about 16 GB/s with 8 SIMD-groups and about 125 GB/s once split into 2048.

3. 在 SGLang v0.5.22 上，想让预填充用 FlashInfer、解码用 Triton，应该怎样启动？

3. On SGLang v0.5.22, how do you launch with FlashInfer for prefill and Triton for decode?

--attention-backend 只接受 choices.py 那张表里的单个值，flashinfer,triton 不在表里，所以 a 会被拒绝。c 只设了 Triton 解码内核的切分上限，而两个阶段用的都是 FlashInfer，这个参数不起作用。b 的两个参数都优先于 --attention-backend，两者不同时自动套上 HybridAttnBackend，文档把它标为实验性功能。--attention-backend takes a single value from the list in choices.py, and flashinfer,triton is not on it, so a is refused. c only sets the split cap of the Triton decode kernel, while both phases run on FlashInfer, so the flag has no effect. Both flags in b take priority over --attention-backend, and when they differ HybridAttnBackend is wrapped around them automatically, a feature the documentation marks experimental.

4. DeepSeek-V3 用 MLA，每个 token 每层只缓存 576 个数。为什么它的解码注意力比 Qwen3-8B 的 GQA 更接近受算力限制？

4. DeepSeek-V3 uses MLA and caches only 576 numbers per token per layer. Why is its decode attention much closer to compute-bound than Qwen3-8B’s GQA?

MLA 仍然要对潜向量做 softmax，所以 b 不对。c 把方向弄反了：读的字节变多只会降低强度，而且 576 个数是所有头共用的，不是每个头一份。强度高是因为共享：Qwen3-8B 每 4 个查询头共用一组 KV，强度约 4；DeepSeek-V3 的 128 个头共用同一份 576 维潜向量，按吸收形式推算约 242（单卡，未计张量并行）。MLA still applies a softmax over the latent, so b is wrong. c has it backwards: more bytes read can only lower the intensity, and the 576 numbers are shared by all heads, not one copy per head. The intensity is high because of sharing: in Qwen3-8B every 4 query heads share one KV group, for an intensity of about 4; DeepSeek-V3’s 128 heads share one 576-dimensional latent, about 242 in the absorbed form (one GPU, before tensor parallelism).
