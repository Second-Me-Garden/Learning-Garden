MoE 层里每个 token 只走 E 个专家中的 k 个，于是一层 FFN 变成了 E 个形状相同、行数各不相同的小 GEMM。内核要解决三件事：先把（token，槽位）按专家排好、每个专家的行数补到块大小 BM 的整数倍，这是 moe_align_block_size；再用一次启动算完所有专家，每个 M 块只属于一个专家、只读一份权重，这是分组 GEMM（Triton 的 fused_moe_kernel，Hopper 上 FP8 块量化权重用 DeepGEMM）；专家分在多块 GPU 上时，还要把 token 发过去、把结果收回来，这是 DeepEP 的 dispatch 和 combine。补齐的行要白算，BM 越大白算越多，但每块权重被复用的行也越多。这台 Apple M5 上实测：4096 个 token、64 个专家、每 token 4 个专家时，BM = 64 浪费 9.9% 的行却比浪费 2.4% 的 BM = 16 快约 1.8 倍（12.2 对 21.9 ms）；只有 64 个 token 时每个专家平均 4 行，BM = 32 浪费 87% 仍然最快，因为这时内核在读权重，算力本来就闲着。哪些跑过、哪些没跑过：Lab B 的 Metal 程序 2026-11-01 在这台 Apple M5 上实际运行，数字原样贴出；Lab A 在 L4 上量 moe_align_block_size 的补齐浪费、在 H100 上跑 DeepGEMM 的分组 GEMM，未运行，是 2026-11-01 根据 SGLang v0.5.22 的源码和 DeepGEMM、DeepEP 的文档整理的；DeepEP 要多块 GPU，只作描述。

In a MoE layer each token goes through only k of E experts, so one FFN layer turns into E small GEMMs of the same shape but different row counts. The kernels have three jobs: first sort the (token, slot) entries by expert and pad each expert’s rows to a multiple of the block size BM, which is moe_align_block_size; then compute every expert in one launch, with each M block belonging to exactly one expert and reading one set of weights, which is the grouped GEMM (Triton’s fused_moe_kernel, and DeepGEMM for FP8 block-quantized weights on Hopper); and when the experts are spread over several GPUs, send the tokens there and bring the results back, which is DeepEP’s dispatch and combine. Padding rows are computed for nothing, and a larger BM pads more, but it also lets more rows reuse each weight tile. Measured on this Apple M5 with 4096 tokens, 64 experts and 4 experts per token: BM = 64 wastes 9.9% of its rows and is still about 1.8 times as fast as BM = 16, which wastes 2.4% (12.2 against 21.9 ms); with only 64 tokens, each expert gets 4 rows on average, and BM = 32 wastes 87% yet is the fastest, because the kernel is then reading weights and its arithmetic sits idle anyway. What was run and what was not: the Metal program of Lab B was actually run on this Apple M5 on 2026-11-01 and its numbers are pasted as they came; Lab A, which measures the padding waste of moe_align_block_size on an L4 and runs DeepGEMM’s grouped GEMM on an H100, is not run, assembled on 2026-11-01 from the SGLang v0.5.22 source and the DeepGEMM and DeepEP documentation; DeepEP needs several GPUs and is only described.

Core concepts

1. 路由与 top-k

1. Routing and top-k

稀疏门控的 MoE 层由 Shazeer 等（arXiv:1701.06538，读的是 v1）提出，摘要的说法是：一个可训练的门控网络为每个样本决定用哪些专家的稀疏组合。今天的 LLM 里，每一层 MoE 对每个 token 做同样的几步：

The sparsely gated MoE layer comes from Shazeer et al. (arXiv:1701.06538, read at v1), whose abstract puts it this way: a trainable gating network determines a sparse combination of experts to use for each example. In today’s LLMs, every MoE layer does the same few steps for every token:

  1. 路由器是一个小线性层：T 个 token 的隐状态乘 E × K 的门控权重，得到 T × E 的 logits。
  2. The router is a small linear layer: the hidden states of T tokens times an E × K gate weight give T × E logits.
  3. 每行打分（softmax，或 DeepSeek-V3 的 sigmoid），取最大的 k 个，得到 topk_ids（T × k 个专家号）和 topk_weights（T × k 个权重，通常在选中的 k 个里重新归一化）。
  4. Score each row (softmax, or sigmoid in DeepSeek-V3), keep the largest k, and get topk_ids (T × k expert numbers) and topk_weights (T × k weights, usually renormalized over the k chosen).
  5. 把 T × k 展平成 T·k 项，第 i 项属于 token i // k。每个专家拿到属于它的那些项，做门与上投影的 GEMM、SiLU-and-mul、下投影的 GEMM。
  6. Flatten T × k into T·k entries; entry i belongs to token i // k. Each expert takes its own entries and runs the gate-and-up GEMM, SiLU-and-mul and the down GEMM.
  7. 合并：每个 token 把自己 k 个专家的输出按权重加起来。
  8. Combine: each token adds up the outputs of its k experts, weighted.

两个真实形状（Hugging Face 上的 config.json，2026-11-01 读取）。Qwen3-30B-A3B：128 个专家，每 token 8 个，隐藏维 2048，专家中间维 768，48 层。DeepSeek-V3：256 个路由专家加 1 个共享专家，每 token 8 个，隐藏维 7168，专家中间维 2048，scoring_func 是 sigmoid，n_group 8、topk_group 4，topk_method 是 noaux_tc，routed_scaling_factor 2.5。DeepSeek-V3 技术报告（arXiv:2412.19437，v2）讲 DeepSeekMoE 的一节说明了这些字段：亲和度用 sigmoid 算，在选中的分数之间归一化得到门控值；为了负载均衡，给每个专家加一个偏置项，只用于决定 top-k，乘到输出上的门控值仍来自原始分数；每个 token 最多发往 4 个节点。对内核来说，这些都只是改变 topk_ids 和 topk_weights 怎么算，后面的排序、GEMM 和合并完全一样。

Two real shapes (the config.json files on Hugging Face, read 2026-11-01). Qwen3-30B-A3B: 128 experts, 8 per token, hidden size 2048, expert intermediate size 768, 48 layers. DeepSeek-V3: 256 routed experts plus 1 shared expert, 8 per token, hidden size 7168, expert intermediate size 2048, scoring_func sigmoid, n_group 8 and topk_group 4, topk_method noaux_tc, routed_scaling_factor 2.5. The DeepSeekMoE section of the DeepSeek-V3 technical report (arXiv:2412.19437, v2) explains these fields: affinities are computed with a sigmoid and normalized among the selected scores to give the gating values; for load balancing, each expert gets a bias term that is used only to decide the top-k, while the gating value multiplied into the output still comes from the original score; and each token is sent to at most 4 nodes. For the kernels, all of this only changes how topk_ids and topk_weights are computed; the sorting, the GEMMs and the combine that follow are exactly the same.

2. moe_align_block_size：按专家排序并补齐

2. moe_align_block_size: sort and pad per expert

分组 GEMM 要的输入是：同一个专家的项挨在一起，而且每个专家占的行数是 GEMM 的 M 块大小 BM 的整数倍，这样每个 M 块只属于一个专家。moe_align_block_size 产生三样东西（Python 包装 srt/layers/moe/moe_runner/triton_utils/moe_align_block_size.py 的文档字符串，第 38–74 行）：

A grouped GEMM wants its input arranged so that the entries of one expert sit together and each expert occupies a multiple of the GEMM’s M block size BM, so that every M block belongs to exactly one expert. moe_align_block_size produces three things (the docstring of the Python wrapper, srt/layers/moe/moe_runner/triton_utils/moe_align_block_size.py, lines 38–74):

  • sorted_token_ids：按专家排好的项号 i（0 到 T·k − 1），每个专家的段尾用 T·k 这个值补齐，后面的 GEMM 把它当作不存在的行。
  • sorted_token_ids: entry numbers i (0 to T·k − 1) sorted by expert, each expert’s segment padded at its end with the value T·k, which the GEMM afterwards treats as a row that does not exist.
  • expert_ids：每个 BM 大小的块属于哪个专家。
  • expert_ids: which expert each BM-sized block belongs to.
  • num_tokens_post_padded：补齐之后的总行数。
  • num_tokens_post_padded: the total row count after padding.

The CUDA implementation is python/sglang/kernels/aot/csrc/moe/moe_align_kernel.cu (v0.5.22, fetched with curl on 2026-11-01). The host function (lines 328–398) picks a path by size: fewer than 1024 entries and at most 64 experts take a single-block small-batch kernel (line 346); otherwise two kernels are launched:

  1. moe_align_block_size_kernel，2 个线程块、每块 1024 个线程（第 370 行）。第 1 号块只负责把整个 sorted_token_ids 填成补齐值（第 72–87 行）。第 0 号块在 shared memory 里用 atomicAdd 数出每个专家的项数（第 104–108 行），把每个计数向上取整到 BM 的倍数（第 115 行），做一次 warp 级的两层前缀和（第 172–221 行），写出总数和每个专家的起点 cumsum，再用二分查找给每个块定专家号（第 226–240 行）。
  2. moe_align_block_size_kernel, 2 thread blocks of 1024 threads (line 370). Block 1 only fills the whole of sorted_token_ids with the padding value (lines 72–87). Block 0 counts each expert’s entries with atomicAdd in shared memory (lines 104–108), rounds each count up to a multiple of BM (line 115), runs a two-level warp prefix sum (lines 172–221), writes the total and each expert’s start cumsum, and gives each block its expert with a binary search (lines 226–240).
  3. count_and_sort_expert_tokens_kernel，每块 256 个线程、最多 65535 块（第 384–395 行）：每个线程拿一项，对它所属专家的游标做一次 atomicAdd，得到的位置就是它在 sorted_token_ids 里的下标（第 27–43 行）。所以同一个专家段内的顺序取决于原子操作的先后，不是固定的。
  4. count_and_sort_expert_tokens_kernel, 256 threads per block and at most 65535 blocks (lines 384–395): each thread takes one entry and does one atomicAdd on its expert’s cursor; the position it gets is its index in sorted_token_ids (lines 27–43). The order inside one expert’s segment therefore depends on the order of the atomics and is not fixed.

这就是一个直方图、一次扫描和一次分散写，没有真正的排序。有两个细节。第一，专家号进内核前都加了 1（第 39、106 行），包装函数相应地传入 num_experts + 1（第 153–163 行），注释说专家并行时被过滤掉的专家号是 −1，一共有 num_experts + 1 个号（第 103 行）：−1 落进第 0 个桶，GEMM 看到 −1 就跳过这一块。第二，缓冲区按最坏情况分配：每个桶最多补 BM − 1 行，所以上界是 T·k + (E + 1)(BM − 1)，再向上取整到 4 的倍数，因为补齐时用 int4 一次写 4 个（第 87–92 行）。这个上界在 CPU 上就能算出来，不必等 GPU 数完，CUDA 图（Phase 3）要的正是这样固定大小的缓冲区。

This is a histogram, one scan and one scatter, with no real sort. Two details. First, every expert number is incremented by 1 on the way in (lines 39 and 106), and the wrapper accordingly passes num_experts + 1 (lines 153–163); its comment says that under expert parallelism filtered experts have the number −1, giving num_experts + 1 numbers in all (line 103): −1 lands in bucket 0, and the GEMM skips any block marked −1. Second, the buffers are sized for the worst case: each bucket pads at most BM − 1 rows, so the bound is T·k + (E + 1)(BM − 1), rounded up to a multiple of 4 because the padding is written four at a time with int4 stores (lines 87–92). The bound can be computed on the CPU without waiting for the GPU to count, and fixed-size buffers like this are exactly what CUDA graphs (Phase 3) need.

v0.5.22 has two more paths. With at most 64 entries and more than 63 experts, the wrapper switches to a single-launch Triton kernel, moe_align_small_numel (lines 108–128; the limit SMALL_NUMEL_LIMIT = 64 is on line 19 of kernels/ops/moe/moe_align_small_numel.py), which is exactly where decode at batch size 1 lands. kernels/ops/moe/moe_align.py is a JIT version of the same op, compiling kernels/jit/csrc/moe/moe_align_kernel.cu; the default path does not use it, and it is taken only when an experimental LoRA optimization switch is on (wrapper lines 130–151). The default path calls the AOT kernel in the sgl_kernel wheel through the registry in kernels/ops/moe/__init__.py (lines 32–43 and 85–97).

3. 分组 GEMM：Triton 的 fused_moe 与 DeepGEMM

3. Grouped GEMMs: Triton’s fused_moe and DeepGEMM

E 个专家的 GEMM 形状相同（N、K 固定），只有 M（行数）各不相同。一个一个启动，就是 E 次启动，而且解码时每次只有几行。分组 GEMM 只启动一次：网格按（M 块，N 块）展开，每个程序从 expert_ids 查出自己的专家，从 sorted_token_ids 查出自己的行。

The GEMMs of the E experts have the same shape (N and K fixed) and differ only in M, the row count. Launching them one by one means E launches, each with only a few rows in decode. A grouped GEMM launches once: the grid spans (M block, N block), and each program looks up its expert in expert_ids and its rows in sorted_token_ids.

Triton 的 fused_moe_kernel（python/sglang/kernels/ops/moe/fused_moe_triton_kernels.py 第 325 行；调用它的 srt/layers/moe/moe_runner/triton_utils/fused_moe.py 第 3 行注明改编自 vLLM）。按源码，一个程序做这些事：

Triton’s fused_moe_kernel (line 325 of python/sglang/kernels/ops/moe/fused_moe_triton_kernels.py; the caller, srt/layers/moe/moe_runner/triton_utils/fused_moe.py, notes on line 3 that it is adapted from vLLM). By the source, one program does the following:

  • 如果 pid_m × BLOCK_SIZE_M 已经超过 num_tokens_post_padded，直接返回（第 442–444 行）：网格是按上界开的，多出来的块什么也不做。
  • If pid_m × BLOCK_SIZE_M is already past num_tokens_post_padded, return at once (lines 442–444): the grid is launched for the upper bound, and the extra blocks do nothing.
  • 读这一块的 BM 个项号，token_mask = offs_token < num_valid_tokens 标出哪些是真行（第 446–448 行）；读这一块的专家号（第 450 行），−1 就写零或返回（第 453 行）。
  • Read this block’s BM entry numbers, with token_mask = offs_token < num_valid_tokens marking the real rows (lines 446–448); read this block’s expert (line 450), and on −1 write zeros or return (line 453).

  • The address of a row of A is offs_token // top_k (line 484): dividing the entry number by k gives the token’s row, so the hidden state need not be copied k times for k experts. B is this expert’s weight (line 492).
  • 沿 K 循环时，A 用 mask=token_mask、other=0.0 加载（第 548–559 行）：补齐行不读显存，但它们照样占着矩阵乘的那几行，这就是补齐浪费的算力。FP8 块量化时，每走一个 K 块乘一次两边的缩放：accumulator += tl.dot(a, b) * a_scale[:, None] * b_scale[None, :]（第 587 行）。
  • Along the K loop, A is loaded with mask=token_mask and other=0.0 (lines 548–559): padding rows read no memory, but they still occupy their rows of the matrix product, which is the compute that padding wastes. With FP8 block quantization, both scales are applied once per K block: accumulator += tl.dot(a, b) * a_scale[:, None] * b_scale[None, :] (line 587).

One MoE layer is two such calls around one activation: the gate-and-up GEMM (fused_moe.py, line 656), SiLU-and-mul, the down GEMM (line 893), and finally moe_sum_reduce, which adds up each token’s k rows with their weights (around lines 958–1003). FP8 块量化。DeepSeek-V3 技术报告（第 3.3.2 节）的细粒度量化：激活按 1 × 128 的小片缩放（每个 token 每 128 个通道一个缩放因子），权重按 128 × 128 的块缩放（每 128 个输入通道乘 128 个输出通道一个）；报告说这样缩放能随更小的分组适应离群值，并且每个 1 × 128 激活片和 128 × 128 权重块的最大绝对值都是在线算的。发布的 config.json 与此一致：fmt 是 e4m3，weight_block_size 是 [128, 128]，activation_scheme 是 dynamic。

FP8 block quantization. The fine-grained quantization of the DeepSeek-V3 technical report (section 3.3.2): activations are scaled in 1 × 128 tiles (one scale per token per 128 channels) and weights in 128 × 128 blocks (one per 128 input channels by 128 output channels); the report says that scaling over these smaller groups adapts to outliers, and that the maximum absolute value of each 1 × 128 activation tile and 128 × 128 weight block is computed online. The released config.json agrees: fmt is e4m3, weight_block_size is [128, 128], and activation_scheme is dynamic.

4. 专家并行：DeepEP 的 dispatch 与 combine

4. Expert parallelism: DeepEP’s dispatch and combine

专家太多、一块 GPU 放不下时，把专家分到多块 GPU 上（专家并行，EP）。这时每个 token 的隐状态要先发到持有它那 k 个专家的 GPU 上（dispatch，一次 all-to-all），在那里做分组 GEMM，再把结果发回来、按权重加起来（combine，又一次 all-to-all）。DeepSeek-V3 技术报告给的部署：预填充时 MoE 部分用 EP32；解码时最小部署单元是 40 个节点、320 块 GPU，MoE 部分 EP320，每块 GPU 只放一个专家，dispatch 和 combine 走 InfiniBand 上的点对点传输。

When there are too many experts for one GPU, the experts are spread over several GPUs (expert parallelism, EP). Each token’s hidden state must then first be sent to the GPUs holding its k experts (dispatch, one all-to-all), go through the grouped GEMM there, and come back to be added up with its weights (combine, another all-to-all). The deployment in the DeepSeek-V3 technical report: EP32 for the MoE part in prefill; in decode, a minimum deployment unit of 40 nodes with 320 GPUs, EP320 for the MoE part, one expert per GPU, with dispatch and combine done as point-to-point transfers over InfiniBand.

DeepEP（README，标签 v1.2.1，2026-11-01 读取）就是这两次 all-to-all 的 GPU 内核库，分两套：

DeepEP (README at the v1.2.1 tag, read 2026-11-01) is the GPU kernel library for these two all-to-alls, in two sets:

  • normal：高吞吐，可以把数据从 NVLink 域转发到 RDMA 域，用于训练和推理预填充，可以限定占用的 SM 数（README 的例子是 Buffer.set_num_sms(24)）。先用 get_dispatch_layout 算出每个 rank、每个专家收多少，再 dispatch、combine。README 的注释说 dispatch 时 CPU 要等 GPU 发来的接收计数，所以与 CUDA 图不兼容。README 在 H800（NVLink 约 160 GB/s）上测得机内 EP8 的 dispatch 瓶颈带宽 153 GB/s。
  • normal: high throughput, able to forward data from the NVLink domain to the RDMA domain, for training and inference prefill, with control over the number of SMs used (the README’s example is Buffer.set_num_sms(24)). get_dispatch_layout first works out how much each rank and each expert receives, then come dispatch and combine. The README’s comment says the CPU waits for the received count signalled by the GPU during dispatch, so it is not compatible with CUDA graphs. The README measured a dispatch bottleneck bandwidth of 153 GB/s for intranode EP8 on H800s (about 160 GB/s NVLink).
  • low-latency：为解码写的，最初只走 RDMA，README 2025.06.05 的更新说现在尽量用 NVLink；low_latency_dispatch 和 low_latency_combine 与 CUDA 图兼容，并提供一种基于 hook 的通信与计算重叠，不占 SM。README 在 H800 加 400 Gb/s InfiniBand 上、每批 128 个 token、隐藏维 7168、top-8 时，EP8 的 dispatch 77 µs、combine 114 µs。它的输出格式正好喂给 DeepGEMM 的 masked 分组 GEMM。
  • low-latency: written for decode, originally pure RDMA, and per the README’s 2025.06.05 update now using NVLink as much as possible; low_latency_dispatch and low_latency_combine are compatible with CUDA graphs and offer hook-based overlap of communication and computation that occupies no SMs. The README measured, on H800s with 400 Gb/s InfiniBand, 128 tokens per batch, hidden size 7168 and top-8, 77 µs for dispatch and 114 µs for combine at EP8. Its output format feeds DeepGEMM’s masked grouped GEMM directly.

5. 补齐浪费与块大小的取舍

5. Padding waste and the block-size trade

设专家 e 拿到 ne 行，补齐后是 ⌈ne / BM⌉ × BM 行。浪费的比例是补齐行占补齐后总行数的比例。两个极端：

Let expert e receive ne rows; after padding it has ⌈ne / BM⌉ × BM rows. The waste is the share of padding rows in the padded total. Two extremes:

  • 解码，ne 远小于 BM。Qwen3-30B-A3B 解码一个 token：8 项分给 8 个不同的专家，各 1 行，BM = 16 时补到 128 行，浪费 120 / 128 ≈ 94%。但这一步本来就受带宽限制：每个专家的三块权重是 3 × 768 × 2048 ≈ 472 万个参数，BF16 约 9.4 MB，8 个专家约 75.5 MB，而有用的运算只有 2 × 472 万 × 8 ≈ 7550 万 FLOP，强度约 1 FLOP/字节，远低于任何 GPU 的拐点。白算的行用的是本来闲着的算力，时间几乎全花在读权重上（这是由 config 推出的，不是测量值）。这时 BM 小一点的好处是线程块更多、更快把权重读完，Lab B 在 T = 64 时看到的正是这个。
  • Decode, ne far below BM. Decoding one token of Qwen3-30B-A3B: 8 entries go to 8 different experts with 1 row each; at BM = 16 they pad to 128 rows, a waste of 120 / 128 ≈ 94%. But this step is bandwidth-bound anyway: each expert’s three weight matrices hold 3 × 768 × 2048 ≈ 4.72 million parameters, about 9.4 MB in BF16, about 75.5 MB for 8 experts, while the useful arithmetic is only 2 × 4.72 million × 8 ≈ 75.5 million FLOP, an intensity of about 1 FLOP per byte, far below the ridge of any GPU. The wasted rows use compute that would sit idle anyway, and the time goes almost entirely into reading the weights (derived from the config, not measured). What a smaller BM buys here is more thread blocks that finish reading the weights sooner, which is what Lab B sees at T = 64.
  • 预填充，ne 远大于 BM。每个专家最多补 BM − 1 行，如果余数大致均匀，平均补约 (BM − 1) / 2 行。8192 个 token、k = 8、128 个专家，平均每个专家 512 行，BM = 64 时平均补约 31.5 行，浪费约 5.8%（推断：假设余数均匀）。这时 GEMM 受算力限制，浪费的行是真金白银；但 BM 越大，每块权重被越多的行复用、每个线程块里矩阵乘的活越整，GEMM 本身跑得越快。
  • Prefill, ne far above BM. Each expert pads at most BM − 1 rows, and about (BM − 1) / 2 on average if the remainders are roughly uniform. With 8192 tokens, k = 8 and 128 experts, each expert averages 512 rows; at BM = 64 it pads about 31.5 rows on average, a waste of about 5.8% (an inference assuming uniform remainders). Here the GEMM is compute-bound and wasted rows cost real time; but a larger BM lets each weight tile be reused by more rows and gives each thread block a fuller matrix product, so the GEMM itself runs faster.

所以 BM 的取舍是：小 BM 浪费少、线程块多；大 BM 复用多、每块效率高，但补齐多。最快的 BM 由行数决定，这就是 SGLang 的配置要按 M 分档、并按 GPU 型号调表的原因（概念 3）。还有第三条路：MegaBlocks（Gale 等，arXiv:2211.15841，v1）的摘要说，现有框架逼用户在丢弃 token 和在补齐上浪费算力与内存之间二选一，它把 MoE 改写成块稀疏运算，从不丢 token。Lab B 在 M5 上把这个取舍量了出来：4096 个 token 时 BM = 64 最快，64 个 token 时 BM = 32 最快。

So the BM trade is this: a small BM wastes less and gives more thread blocks; a large BM reuses more and makes each block more efficient, but pads more. The fastest BM depends on the row count, which is why SGLang’s configs are bucketed by M and tuned per GPU model (concept 3). There is a third way: the abstract of MegaBlocks (Gale et al., arXiv:2211.15841, v1) says existing frameworks force users to choose between dropping tokens and wasting computation and memory on padding, and it recasts MoE as block-sparse operations that never drop tokens. Lab B measures this trade on the M5: BM = 64 is fastest at 4096 tokens, and BM = 32 at 64 tokens.

        uint e = simd_min(cand);                                   // lowest expert index holding the max
        sel[j] = m; ids[j] = int(e);
        if (e == lane) v0 = -INFINITY; else if (e == lane + 32) v1 = -INFINITY;
    }
    if (lane == 0) {
        float s = 0.0f;
        for (uint j = 0; j < TOPK; j++) s += exp(sel[j] - sel[0]);
        for (uint j = 0; j < TOPK; j++) { topk_ids[t * TOPK + j] = ids[j]; topk_w[t * TOPK + j] = exp(sel[j] - sel[0]) / s; }
    }
}

// 2a. align, one threadgroup: count entries per expert, round each count up to a multiple of BM, exclusive scan,
// write the padded total, the owning expert of every block, each expert's write cursor, and fill sorted_ids
// with the padding sentinel numel (the CUDA kernel's pad_sorted_token_ids).
kernel void align_count(device const int* topk_ids [[buffer(0)]], device int* sorted_ids [[buffer(1)]],
                        device int* expert_of_block [[buffer(2)]], device int* total_post_pad [[buffer(3)]],
                        device atomic_int* cursor [[buffer(4)]], constant uint& numel [[buffer(5)]],
                        constant uint& BM [[buffer(6)]], constant uint& max_padded [[buffer(7)]],
                        uint tid [[thread_index_in_threadgroup]], uint ntid [[threads_per_threadgroup]]) {
    threadgroup atomic_int counts[E];
    threadgroup int start[E + 1];
    if (tid < E) atomic_store_explicit(&counts[tid], 0, memory_order_relaxed);
    for (uint i = tid; i < max_padded; i += ntid) sorted_ids[i] = int(numel);
    threadgroup_barrier(mem_flags::mem_threadgroup);
    for (uint i = tid; i < numel; i += ntid) atomic_fetch_add_explicit(&counts[topk_ids[i]], 1, memory_order_relaxed);
    threadgroup_barrier(mem_flags::mem_threadgroup);
    if (tid == 0) {                                                // E = 64: a serial scan is enough
        int acc = 0;
        for (uint e = 0; e < E; e++) {
            start[e] = acc;
            int c = atomic_load_explicit(&counts[e], memory_order_relaxed);
            acc += (c + int(BM) - 1) / int(BM) * int(BM);
        }
        start[E] = acc; *total_post_pad = acc;
    }
    threadgroup_barrier(mem_flags::mem_threadgroup);
    if (tid < E) {
        atomic_store_explicit(&cursor[tid], start[tid], memory_order_relaxed);
        for (int b = start[tid] / int(BM); b < start[tid + 1] / int(BM); b++) expert_of_block[b] = int(tid);
    }
}

// 2b. scatter: one thread per (token, slot) entry takes the next position in its expert's segment
// (count_and_sort_expert_tokens_kernel in the CUDA source). Order inside a segment is whatever the atomics give.
kernel void align_scatter(device const int* topk_ids [[buffer(0)]], device int* sorted_ids [[buffer(1)]],
                          device atomic_int* cursor [[buffer(2)]], constant uint& numel [[buffer(3)]],
                          uint i [[thread_position_in_grid]]) {
    if (i >= numel) return;
    int pos = atomic_fetch_add_explicit(&cursor[topk_ids[i]], 1, memory_order_relaxed);
    sorted_ids[pos] = int(i);
}

// 3. grouped GEMM: threadgroup (n-tile, m-block) computes BM sorted rows x BN columns of C = X[token] . W[e]^T,
// where e = expert_of_block[m-block]. Rows are gathered through sorted_ids; padding rows (id == numel) load zeros,
// are multiplied like any other row, and are not stored. BM / 8 SIMD-groups, each an 8-row strip of 8x8 tiles.
kernel void grouped_gemm(device const half* X [[buffer(0)]], device const half* W [[buffer(1)]],
                         device const int* sorted_ids [[buffer(2)]], device const int* expert_of_block [[buffer(3)]],
                         device const int* total_post_pad [[buffer(4)]], device float* C [[buffer(5)]],
                         constant uint& numel [[buffer(6)]], constant uint& BM [[buffer(7)]],
                         uint2 tg [[threadgroup_position_in_grid]], uint tid [[thread_index_in_threadgroup]],
                         uint sg [[simdgroup_index_in_threadgroup]]) {
    uint mb = tg.y, n0 = tg.x * BN, ntid = BM * 4;                 // BM / 8 SIMD-groups of 32 threads
    if (mb * BM >= uint(*total_post_pad)) return;                 // the grid is sized for the worst case
    uint e = uint(expert_of_block[mb]);
    threadgroup half As[64][BK];
    threadgroup half Ws[BN][BK];
    threadgroup float Cs[64][BN];
    threadgroup int rowId[64];
    if (tid < BM) rowId[tid] = sorted_ids[mb * BM + tid];
    simdgroup_float8x8 acc[4];
    for (uint j = 0; j < 4; j++) acc[j] = make_filled_simdgroup_matrix<float, 8, 8>(0.0f);
    for (uint k0 = 0; k0 < K; k0 += BK) {
        threadgroup_barrier(mem_flags::mem_threadgroup);
        for (uint i = tid; i < BM * BK / 4; i += ntid) {          // gather BM token rows of X
            uint r = i / (BK / 4), c = (i % (BK / 4)) * 4;
            int id = rowId[r];
            half4 v = (uint(id) < numel) ? *(device const half4*)(X + ulong(uint(id) / TOPK) * K + k0 + c) : half4(0.0h);
            *(threadgroup half4*)&As[r][c] = v;
        }
        for (uint i = tid; i < BN * BK / 4; i += ntid) {          // BN rows of this expert's weight
            uint r = i / (BK / 4), c = (i % (BK / 4)) * 4;
            *(threadgroup half4*)&Ws[r][c] = *(device const half4*)(W + (ulong(e) * N + n0 + r) * K + k0 + c);
        }
        threadgroup_barrier(mem_flags::mem_threadgroup);
        for (uint kk = 0; kk < BK; kk += 8) {
            simdgroup_half8x8 a;
            simdgroup_load(a, &As[sg * 8][kk], BK);
            for (uint j = 0; j < 4; j++) {
                simdgroup_half8x8 b;
                simdgroup_load(b, &Ws[j * 8][kk], BK, ulong2(0, 0), true);   // transposed: b[k][n] = W[n][k]
                simdgroup_multiply_accumulate(acc[j], a, b, acc[j]);
            }
        }
    }
    for (uint j = 0; j < 4; j++) simdgroup_store(acc[j], &Cs[sg * 8][j * 8], BN);
    threadgroup_barrier(mem_flags::mem_threadgroup);
    for (uint i = tid; i < BM * BN; i += ntid) {                   // scatter real rows back to C[(token, slot)]
        uint r = i / BN, c = i % BN;
        int id = rowId[r];
        if (uint(id) < numel) C[ulong(id) * N + n0 + c] = Cs[r][c];
    }
}

// 4. combine: out[t] = sum over the token's k slots of weight * C[(t, slot)] (moe_sum in the CUDA source).
kernel void combine(device const float* C [[buffer(0)]], device const float* topk_w [[buffer(1)]],
                    device float* out [[buffer(2)]], uint2 gid [[thread_position_in_grid]]) {
    uint n = gid.x, t = gid.y;
    float s = 0.0f;
    for (uint j = 0; j < TOPK; j++) s += topk_w[t * TOPK + j] * C[(ulong(t) * TOPK + j) * N + n];
    out[ulong(t) * N + n] = s;
}

自测

Self-check

1. moe_align_block_size 为什么要把每个专家的行数补到 BLOCK_SIZE_M 的整数倍？

1. Why does moe_align_block_size pad each expert’s row count to a multiple of BLOCK_SIZE_M?

补齐只把每个专家的行数向上取整到 BM 的倍数，热门专家仍然比冷门的多好几块，所以 b 不对，负载均衡是路由偏置和冗余专家的事。c 不对：BM 在 SGLang 的默认配置里是 16 或 64，BF16 也一样要补齐，与 FP8 无关。a 正确：Triton 内核每个程序读一次 expert_ids[pid_m]，整块都乘同一个专家的权重，所以一块里不能混两个专家。Padding only rounds each expert’s row count up to a multiple of BM, and a popular expert still gets several more blocks than an unpopular one, so b is wrong; load balancing is the job of routing biases and redundant experts. c is wrong: BM is 16 or 64 in SGLang’s default configs, and BF16 pads just the same, so it has nothing to do with FP8. a is right: each program of the Triton kernel reads expert_ids[pid_m] once and multiplies the whole block by that one expert’s weights, so a block cannot mix two experts.

2. Qwen3-30B-A3B（128 个专家，每 token 8 个）解码一个 token，BM = 16。补齐浪费大约是多少，这一步主要花时间在哪里？

2. Qwen3-30B-A3B (128 experts, 8 per token) decodes one token with BM = 16. About how much is the padding waste, and where does this step mainly spend its time?

8 项分给 8 个不同的专家，各 1 行，每个补到 16 行，共 128 行，其中 120 行是补齐，约 94%，所以 a 和 c 都不对；c 还忽略了补齐是按专家做的，一个专家只有一行也要补满一块。浪费虽高，这一步的强度只有约 1 FLOP/字节，8 个专家约 75.5 MB 的权重要从显存读一遍，白算的行用的是本来闲着的算力。The 8 entries go to 8 different experts with 1 row each, each padded to 16 rows, 128 rows in all, of which 120 are padding, about 94%, so a and c are both wrong; c also forgets that padding is per expert, and an expert with a single row still fills a whole block. High as the waste is, this step’s intensity is only about 1 FLOP per byte: about 75.5 MB of weights for the 8 experts must be read from memory once, and the wasted rows use compute that would sit idle anyway.

3. Lab B 在 4096 个 token 时，BM = 64 浪费 9.9%，BM = 16 浪费 2.4%，但 BM = 64 快约 1.8 倍。主要原因是什么？

3. In Lab B at 4096 tokens, BM = 64 wastes 9.9% and BM = 16 wastes 2.4%, yet BM = 64 is about 1.8 times as fast. What is the main reason?

对齐内核在三种 BM 下都是约 0.015 ms，比 GEMM 小三个数量级，所以 a 不对。补齐行在 Lab B 的内核里和 Triton 内核里一样，读成 0 之后照样参与矩阵乘，所以 b 不对，那正是浪费的定义。c 正确：多算约 8% 的行（18176 对 16784），换来执行速率接近翻倍。The align kernel takes about 0.015 ms at all three BM values, three orders of magnitude below the GEMM, so a is wrong. Padding rows, in Lab B’s kernel as in the Triton kernel, are loaded as 0 and still take part in the matrix product, so b is wrong; that is the very definition of the waste. c is right: computing about 8% more rows (18176 against 16784) buys nearly twice the executed rate.

4. 专家并行的解码阶段，SGLang 的 --deepep-mode auto 选 DeepEP 的哪种内核，为什么？

4. In the decode phase under expert parallelism, which DeepEP kernels does SGLang’s --deepep-mode auto choose, and why?

exec_.py 的帮助文字说 auto 对解码批用 low_latency、对预填充批用 normal。normal 内核在 dispatch 时 CPU 要等 GPU 的接收计数，DeepEP 的 README 说这与 CUDA 图不兼容，而解码步要进 CUDA 图，所以 b 不对。c 不对：专家分在多块 GPU 上时，一个 token 的 8 个专家多半不在本卡，每一步都要发出去再收回来。The help text in exec_.py says auto means low_latency for decode batches and normal for prefill batches. During dispatch the normal kernels make the CPU wait for the GPU’s received count, which the DeepEP README says is incompatible with CUDA graphs, and decode steps run in CUDA graphs, so b is wrong. c is wrong: with the experts spread over several GPUs, most of one token’s 8 experts are not on the local GPU, so every step sends the token out and brings the results back.
