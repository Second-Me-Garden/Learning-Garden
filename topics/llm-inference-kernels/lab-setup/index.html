为什么这样分层

Why these tiers

  • 这台 Mac 跑不了本专题研究的那条路径。SGLang v0.5.22 的安装文档写明它需要 CUDA 13，而 CUDA 只跑在 NVIDIA GPU 上。SGLang 也有一个 Apple 芯片后端（文档页 Apple Silicon with Metal），但它用的是 MLX，要先 pip install，跑的也不是本专题要读的 CUDA 内核，所以不用。
  • This Mac cannot run the path this topic studies. The SGLang v0.5.22 install documentation states that it requires CUDA 13, and CUDA runs only on NVIDIA GPUs. SGLang does have an Apple-silicon backend (the documentation page Apple Silicon with Metal), but it uses MLX, needs a pip install first, and does not run the CUDA kernels this topic reads, so it is not used.
  • 免费的 Colab T4 不够。Triton v3.9.0 的 README 要求 compute capability 8.0 或更高，T4 是 7.5（sm_75），本专题的 Triton 内核在上面都跑不了。L4 是 Ada（sm_89），有 FP8，24 GB 显存，SGLang 的安装文档把它列在 FlashInfer 支持的卡里。所以 L4 是最便宜的一层。
  • The free Colab T4 is not enough. The Triton v3.9.0 README requires compute capability 8.0 or higher, and the T4 is 7.5 (sm_75), so none of this topic’s Triton kernels run on it. The L4 is Ada (sm_89), has FP8 and 24 GB of memory, and the SGLang install documentation lists it among the cards FlashInfer supports. So the L4 is the cheapest tier.
  • 有几个内核要 Hopper。上游 FA3 和 DeepGEMM 都不支持 Ada；SGLang 自带的 FlashMLA 编译的是 sm_90a；DeepEP 要 Hopper，还要多块 GPU（概念 3 给出各自的出处）。H100 每小时的价格是 L4 的好几倍，所以只有 FA3 和 DeepGEMM 那几步实验才开 H100；FlashMLA 和 DeepEP 只讲解，不在任何一层上运行。
  • A few kernels need Hopper. Upstream FA3 and DeepGEMM do not support Ada; the FlashMLA that SGLang bundles is built for sm_90a; DeepEP needs Hopper and several GPUs (concept 3 gives each source). An H100 costs several times as much per hour as an L4, so the H100 is started only for the few FA3 and DeepGEMM lab steps; FlashMLA and DeepEP are described and run on no tier.
  • 每个内核想法都在本机再跑一遍。Metal 的 grid、threadgroup、SIMD-group 和 CUDA 的 grid、block、warp 一一对应。Mac 上的 Metal 孪生实验不花钱、不排队，而且是真跑出来的数字，用它检验你对 CUDA 那一侧的理解。
  • Every kernel idea runs a second time here. Metal’s grid, threadgroup and SIMD-group map one to one onto CUDA’s grid, block and warp. The Metal twin on the Mac costs nothing, never queues, and gives numbers that were really measured; use it to test what you understood on the CUDA side.

核心概念

Core concepts

本专题读的是 SGLang 在 NVIDIA GPU 上跑的 CUDA 内核，可这台 Mac 没有 NVIDIA GPU；免费的 Colab T4 计算能力只有 7.5，跑不了要求 8.0 的 Triton；FA3 和 DeepGEMM 至少要 Hopper，而同一档云里 H100 每小时是 L4 的 4.5 到 6.8 倍。另一头，推理服务器是一个网络服务，租来的机器又直接连在公网上，照抄文档示例就会把它开给整个互联网。所以问题是：怎样花尽量少的钱，让每一课的实验都有一台跑得动它的机器，同时不把服务暴露出去？

This topic reads the CUDA kernels SGLang runs on NVIDIA GPUs, but this Mac has no NVIDIA GPU; the free Colab T4 has compute capability 7.5 and cannot run Triton, which needs 8.0; FA3 and DeepGEMM need at least Hopper, and within the same cloud tier an H100 hour costs 4.5 to 6.8 times an L4 hour. On the other side, an inference server is a network service, the rented machine sits directly on the internet, and copying the documentation examples opens it to everyone. So the question is: how do you give every lesson’s labs a machine that can run them, for as little money as possible, without exposing the server?

Follow that one request from the second terminal to the server and back, and see along the way why nothing from outside can reach it. The path is worked out from the commands and the v0.5.22 source; it is not run.

  1. docker exec -it sglang-lab bash 按名字进入 docker run --name sglang-lab 起的那个容器，和服务器在同一个网络命名空间里。
  2. curl 连 127.0.0.1:30000。这是容器自己的回环地址，服务器正在上面听：--host 127.0.0.1 --port 30000，和 serving.py 第 65–66 行的默认值相同。
  3. 请求体按 OpenAI 兼容的 /v1/chat/completions 格式发给 Qwen/Qwen3-0.6B，服务器做一次预填充和若干解码步，答案文本在返回 JSON 的 choices[0].message.content 里。
  4. 从外面看：docker run 没有 -p，主机上没有任何端口转到 30000；服务器又只听容器内的回环地址，所以主机的公网地址上 30000 端口什么也没有；按 GPU 专题环境页的安全表，对外只开 SSH 的 22 端口。
  1. docker exec -it sglang-lab bash enters, by name, the container started with docker run --name sglang-lab, in the same network namespace as the server.
  2. curl connects to 127.0.0.1:30000. That is the container’s own loopback address, where the server is listening: --host 127.0.0.1 --port 30000, the same as the defaults at lines 65–66 of serving.py.
  3. The body goes to Qwen/Qwen3-0.6B in the OpenAI-compatible /v1/chat/completions format; the server runs one prefill and a number of decode steps, and the answer text comes back in choices[0].message.content of the returned JSON.
  4. From the outside: docker run had no -p, so no host port forwards to 30000; and the server listens only on the loopback address inside the container, so there is nothing on port 30000 at the host’s public address; under the safety table of the GPU topic’s lab page, the only port open to the world is SSH’s 22.

三个测量工具，都来自 v0.5.22 的 docs/docs/developer_guide/benchmark_and_profiling.mdx：

Three measuring tools, all from docs/docs/developer_guide/benchmark_and_profiling.mdx at v0.5.22:

  • bench_one_batch 是最底层的工具：不起服务器，直接建一个 ModelRunner，对一个固定的静态批次调用 extend() 和 decode()，绕过调度器。文档说它最适合剖析单个内核的性能。v0.5.22 里它的模块是 sglang.benchmark.one_batch（源码 python/sglang/benchmark/one_batch.py）。它自己加载模型，跑之前先停掉服务器，免得两份模型抢同一块显存（推断）。
  • bench_one_batch is the lowest-level tool: it starts no server, builds a ModelRunner directly and calls extend() and decode() on one fixed static batch, bypassing the scheduler. The documentation says it suits profiling individual kernels best. At v0.5.22 its module is sglang.benchmark.one_batch (source python/sglang/benchmark/one_batch.py). It loads the model itself, so stop the server first, or two copies of the model compete for the same GPU memory (inference).
  • torch profiler：服务器上用 /start_profile 接口开始剖析，trace 写进 SGLANG_TORCH_PROFILER_DIR；one_batch 上加 --profile，用 --profile-stage decode 只剖析解码。trace 在 ui.perfetto.dev 或 Chrome 的 chrome://tracing 里打开。
  • The torch profiler: on the server, the /start_profile endpoint starts profiling and the trace goes to SGLANG_TORCH_PROFILER_DIR; on one_batch, add --profile, and --profile-stage decode profiles only the decode. Open the trace in ui.perfetto.dev or in Chrome’s chrome://tracing.
  • Nsight Systems（nsys）：文档给的单批次命令带 --trace-fork-before-exec=true --cuda-graph-trace=node，后一个选项让 CUDA 图里的每个节点都单独出现在时间线上。
  • Nsight Systems (nsys): the single-batch command in the documentation carries --trace-fork-before-exec=true --cuda-graph-trace=node; the second option makes every node of a CUDA graph appear on its own in the timeline.
# 未运行 · not run; assembled from the SGLang documentation at v0.5.22 on 2026-11-01

所以本专题每一页都用运行时编译，和 GPU 专题一样：MSL 源码作为字符串放在 Swift 程序里，程序运行时调用 MTLDevice.makeLibrary(source:options:) 编译成库，再建成计算管线状态后派发。计时只看 GPU 自己报的执行时间（gpuStartTime 到 gpuEndTime），不看整个进程的运行时间，因为每次运行都要先编译一次 kernel。SGLang 的 Apple 文档页也写明：要编译它可选的原生 Metal 内核，需要完整 Xcode 里的 Metal 编译器，单独的 Command Line Tools 不够。这是不走那条路的又一个原因。

So every page of this topic uses runtime compilation, as the GPU topic does: the MSL source sits as a string inside the Swift program, which calls MTLDevice.makeLibrary(source:options:) at run time to compile it into a library, builds a compute pipeline state and dispatches it. Timing looks only at the execution time the GPU reports itself (gpuStartTime to gpuEndTime), never at the whole process run time, because every run compiles the kernel first. SGLang’s Apple documentation page also states that building its optional native Metal kernels needs the Metal compiler from the full Xcode application, and the standalone Command Line Tools are not enough. That is one more reason not to take that route.

    // metal_add.swift: Metal 向量加法，kernel 在运行时从源码编译（不需要 xcrun metal）
import Metal

let src = """
#include <metal_stdlib>
using namespace metal;
kernel void add(device const float* a [[buffer(0)]],
                device const float* b [[buffer(1)]],
                device float*       c [[buffer(2)]],
                uint i [[thread_position_in_grid]]) {
    c[i] = a[i] + b[i];
}
"""

guard let dev = MTLCreateSystemDefaultDevice() else { print("no device"); exit(1) }
let lib = try dev.makeLibrary(source: src, options: nil)  // 运行时编译 MSL
let fn  = lib.makeFunction(name: "add")!
let pso = try dev.makeComputePipelineState(function: fn)

let n = 1 << 20
// 默认是共享存储：CPU 和 GPU 读写同一块内存
let a = dev.makeBuffer(length: n * 4)!
let b = dev.makeBuffer(length: n * 4)!
let c = dev.makeBuffer(length: n * 4)!
let pa = a.contents().bindMemory(to: Float.self, capacity: n)
let pb = b.contents().bindMemory(to: Float.self, capacity: n)
for i in 0..<n { pa[i] = Float(i); pb[i] = 2 }

let q = dev.makeCommandQueue()!
let cb = q.makeCommandBuffer()!
let enc = cb.makeComputeCommandEncoder()!
enc.setComputePipelineState(pso)
enc.setBuffer(a, offset: 0, index: 0)
enc.setBuffer(b, offset: 0, index: 1)
enc.setBuffer(c, offset: 0, index: 2)
let w = pso.threadExecutionWidth               // SIMD-group 宽度，对应 CUDA 的 warp
let maxT = pso.maxTotalThreadsPerThreadgroup   // 对应 CUDA 每 block 的线程上限
enc.dispatchThreads(MTLSize(width: n, height: 1, depth: 1),
                    threadsPerThreadgroup: MTLSize(width: w, height: 1, depth: 1))
enc.endEncoding()
cb.commit()
cb.waitUntilCompleted()

let pc = c.contents().bindMemory(to: Float.self, capacity: n)
print("device=\(dev.name) simdWidth=\(w) maxThreadsPerThreadgroup=\(maxT) "
    + "c[12345]=\(pc[12345]) gpuTime_ms=\((cb.gpuEndTime - cb.gpuStartTime) * 1000)")
