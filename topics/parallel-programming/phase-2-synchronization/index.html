1. 数据竞争：标准的定义，以及为什么是未定义行为

1. Data races: the standard’s definition, and why they are undefined behaviour

C++ 标准（[intro.races]）的原话是：如果一次程序执行包含两个可能并发的冲突操作，其中至少一个不是原子操作，并且两者之间没有 happens-before 关系，这次执行就含有数据竞争；任何数据竞争都导致未定义行为。三个词逐个拆开：

The C++ standard ([intro.races]) says: the execution of a program contains a data race if it contains two potentially concurrent conflicting actions, at least one of which is not atomic, and neither happens before the other; any such data race results in undefined behaviour. Take the terms one at a time:

  • 冲突：两个操作访问同一个内存位置，并且至少一个是写。两个线程同时只读同一个变量不冲突，没有竞争。
  • Conflicting: two actions access the same memory location and at least one of them is a write. Two threads only reading the same variable at once do not conflict, so there is no race.
  • 不是原子操作：对 std::atomic 的读写互相之间永远不构成数据竞争，哪怕用的是 memory_order_relaxed。
  • Not atomic: reads and writes of a std::atomic never form a data race with each other, even with memory_order_relaxed.
  • 没有 happens-before：同一个线程里的先后、对同一把锁的解锁与随后的加锁、线程创建与 join，都会建立 happens-before。持有同一把锁的两段代码因此不会竞争。Phase 3 会把这个关系讲完整。
  • No happens-before: program order within one thread, an unlock of a mutex followed by a later lock of the same mutex, and thread creation and join all establish happens-before. Two pieces of code holding the same lock therefore cannot race. Phase 3 covers this relation in full.

为什么是未定义行为，而不只是「结果不对」：标准允许编译器假设没有数据竞争，于是它可以把一个普通变量留在寄存器里不写回、把两次读合并成一次、把一个循环里的读提到循环外。while (!done) {} 里的普通 bool done 可能被读一次就永远不再读，循环永远不退出。在硬件一侧，一个没有对齐的或者比一个字更宽的写可能被另一个线程看到一半（撕裂）。Lab A 的汇编显示，-O2 下 ++counter 是 ldr、add、str 三条指令：两个线程都读到 5、都写回 6，一次加法就丢了。丢加法只是这一次编译恰好产生的症状，标准对结果什么都不保证。

Why undefined behaviour, not merely “a wrong result”: the standard lets the compiler assume there are no data races, so it may keep a plain variable in a register without writing it back, merge two reads into one, or hoist a read out of a loop. With a plain bool done, while (!done) {} may read it once and never again, and the loop never exits. On the hardware side, a write that is misaligned or wider than a word may be seen half-done by another thread (tearing). Lab A’s assembly shows that at -O2 ++counter is three instructions, ldr, add and str: both threads read 5, both write back 6, and one increment is lost. The lost increment is only the symptom this particular build happens to produce; the standard guarantees nothing about the result.

  1. T1 的 ldr 读到 5，还没 str，T2 的 ldr 也读到 5。两次写之间没有 happens-before，又都不是原子操作，这就是概念 1 定义里的数据竞争。
  2. 两个线程各自算出 6、写回 6，一次加法消失。400 万次里这样的重叠多到丢掉约 61%，而且每次丢的数不同，取决于线程怎样交错。
  3. 加上 std::mutex：T2 拿不到锁就睡在内核里，T1 的解锁与 T2 随后的加锁建立 happens-before，所以 T2 一定读到 6、写回 7。四个线程最后得到 4000000。
  4. 正确的代价是时间：每次加法都要争同一条缓存行，mutex 中位数 72.85 ms、atomic 55.57 ms，而错误的 race 只要 2.95 ms。每个线程只加自己的局部和、最后合并的 local 是 8.31 ms，因为它什么都不共享。
  1. T1’s ldr reads 5 and, before its str, T2’s ldr reads 5 too. Nothing makes one write happen before the other and neither is atomic: this is a data race by the definition of concept 1.
  2. Each thread computes 6 and writes back 6, and one addition vanishes. Over four million additions such overlaps are common enough to lose about 61 %, and a different amount each run, depending on how the threads interleave.
  3. Add a std::mutex: T2 cannot get the lock and sleeps in the kernel, and T1’s unlock followed by T2’s lock establishes happens-before, so T2 must read 6 and write back 7. The four threads end at 4000000.
  4. Being correct costs time: every addition fights over the same cache line, so the median is 72.85 ms for mutex and 55.57 ms for atomic, against 2.95 ms for the wrong race. local, where each thread adds only to its own partial sum and they are combined at the end, takes 8.31 ms because it shares nothing.

数据竞争与竞态条件（race condition）不是一回事：竞态条件是指结果依赖线程执行的先后，比如「先检查余额、再扣款」两步各自加了锁，但两步之间被别的线程插进来。它可以完全没有数据竞争，TSan 也查不出来，要靠把两步放进同一个临界区来修。

A data race is not the same as a race condition: a race condition means the result depends on the order in which threads run, for example “check the balance, then debit” where each step takes the lock on its own but another thread slips in between them. It can have no data race at all, TSan cannot find it, and the fix is to put both steps in one critical section.

TSan 怎样找到竞争：-fsanitize=thread 在每次内存访问处插桩，给每个线程维护一个向量时钟，记录锁、原子操作、线程创建和 join 建立的先后关系；它发现两次访问同一地址、至少一次是写、而且两者之间没有先后关系时就报告，报告里给出两处访问的源码行。它只报告这次运行里真的发生过的访问，所以要让测试跑到有竞争的代码路径。

How TSan finds races: -fsanitize=thread instruments every memory access and keeps a vector clock per thread, recording the ordering that locks, atomics, thread creation and join establish; when it sees two accesses to one address, at least one a write, with no ordering between them, it reports them with both source lines. It reports only accesses that actually happened in this run, so the test has to reach the racy code path.

2. 互斥锁：无争用时做什么，有争用时做什么

2. Mutexes: what they do uncontended and what they do contended

一把互斥锁（mutex）保证同一时刻只有一个线程在临界区里。它的设计分两条路：

A mutex guarantees that only one thread at a time is inside the critical section. Its design has two paths:

  • 快速路径（无争用）：锁字里写着「空闲」，加锁就是一条带 acquire 语义的原子比较交换，解锁是一条 release 写，全程不进内核。Lab B 实测：只有一个线程时，std::mutex 一次加锁加解锁约 3.7 ns，os_unfair_lock 约 2.2 ns。
  • The fast path (uncontended): the lock word says “free”, locking is one atomic compare-and-swap with acquire semantics and unlocking is one release store, and the kernel is never entered. Measured in Lab B: with a single thread, one lock-plus-unlock of std::mutex costs about 3.7 ns and of os_unfair_lock about 2.2 ns.
  • 慢速路径（有争用）：拿不到锁的线程不该原地空转烧掉一个核，而是请内核让自己睡眠，直到持有者解锁时把它叫醒。Linux 上 glibc 的 pthread mutex 用 futex(FUTEX_WAIT) 睡、FUTEX_WAKE 唤醒，内核只在锁字仍是「被占用」时才让它睡，避免丢失唤醒。
  • The slow path (contended): a thread that cannot get the lock should not burn a core spinning; it asks the kernel to put it to sleep until the holder unlocks and wakes it. On Linux, glibc’s pthread mutex sleeps with futex(FUTEX_WAIT) and wakes with FUTEX_WAKE, and the kernel lets it sleep only if the lock word still says “taken”, which avoids lost wakeups.

macOS 上的慢速路径（用 sample 在本机抓到的调用栈，2026-10-31）：std::mutex 底下是 pthread mutex，争用时走 _pthread_mutex_firstfit_lock_slow → __psynch_mutexwait，解锁走 __psynch_mutexdrop；os_unfair_lock 争用时走 _os_unfair_lock_lock_slow → __ulock_wait2，解锁走 __ulock_wake。函数名里的 firstfit 说明本机默认的 mutex 策略是「先到先得」：刚解锁的线程可以立刻再拿到锁，而不是交给排队最久的人（pthread.h 里有 PTHREAD_MUTEX_POLICY_FIRSTFIT_NP 和 PTHREAD_MUTEX_POLICY_FAIRSHARE_NP 两种）。psynch 和 ulock 在内核里怎样排队、怎样借用 turnstile 做优先级继承，本页只给大致图景：内核按锁地址找到等待队列，把线程挂上去并让出 CPU；细节见 Kernel Phase 3 概念 1 和概念 8。

The slow path on macOS (call stacks captured with sample on this Mac, 2026-10-31): std::mutex sits on a pthread mutex, which under contention goes through _pthread_mutex_firstfit_lock_slow → __psynch_mutexwait and unlocks through __psynch_mutexdrop; os_unfair_lock under contention goes through _os_unfair_lock_lock_slow → __ulock_wait2 and unlocks through __ulock_wake. The firstfit in the function names shows that this Mac’s default mutex policy is “first fit”: a thread that has just unlocked may take the lock straight back instead of handing it to whoever has waited longest (pthread.h defines both PTHREAD_MUTEX_POLICY_FIRSTFIT_NP and PTHREAD_MUTEX_POLICY_FAIRSHARE_NP). How psynch and ulock queue waiters in the kernel and borrow turnstiles for priority inheritance is given here only as a rough picture (approximate): the kernel finds a wait queue by the lock’s address, puts the thread on it and gives up the CPU; the details are in Kernel Phase 3, concepts 1 and 8.

条件变量：锁只管「互斥」，不管「等某件事发生」。std::condition_variable 的 wait(lock, pred) 原子地放锁并睡眠，被唤醒后重新拿锁再检查条件。必须带谓词或写成循环：标准允许虚假唤醒（spurious wakeup），而且 notify 发生在 wait 之前时通知会丢，只有被锁保护的状态变量记得住它。Lab B 用条件变量做一道起跑门，让所有线程同时开跑。信号量是带计数的版本：C++20 的 std::counting_semaphore 在本机可以编译运行（2026-10-31 实测），GCD 里对应 dispatch_semaphore。

Condition variables: a lock only provides mutual exclusion, not “wait until something happens”. std::condition_variable’s wait(lock, pred) atomically releases the lock and sleeps, and after waking it retakes the lock and checks the condition again. It must have a predicate or sit in a loop: the standard allows spurious wakeups, and a notify that happens before the wait is lost; only the state variable protected by the lock remembers it. Lab B uses a condition variable as a starting gate so that every thread starts at the same moment. A semaphore is the counting version: C++20’s std::counting_semaphore compiles and runs on this Mac (tested 2026-10-31), and in GCD the counterpart is dispatch_semaphore.

3. 自旋锁：为什么不争用时不吃亏，超额订阅时崩溃

3. Spinlocks: why they cost nothing extra uncontended and collapse when oversubscribed

自旋锁拿不到锁时不睡，原地反复检查。Lab B 的实现是 test-and-test-and-set：先用一次原子交换（std::atomic_flag::test_and_set，本机编译成 swpab）抢锁，失败后只读这一位（test），等它变回空闲再抢，这样等待者大部分时间在读自己 L1 里的一份副本，不会不停地写那条缓存行。解锁是一条 release 写（stlrb）。

A spinlock does not sleep when the lock is taken; it keeps checking in place. Lab B implements test-and-test-and-set: it grabs the lock with one atomic exchange (std::atomic_flag::test_and_set, compiled to swpab on this Mac), and on failure it only reads the flag (test) until it looks free before trying again, so waiters spend most of their time reading a copy in their own L1 instead of writing the cache line over and over. Unlocking is one release store (stlrb).

  • 教科书的说法：自旋锁没有睡眠和唤醒的簿记，临界区很短、每个等待者都独占一个核时，转几圈比进一次内核便宜。本机实测：只有一个线程时，手写自旋锁 3.6–4.2 ns，与 std::mutex 的 3.7 ns 相当，比 os_unfair_lock 的 2.2 ns 还慢。原因是三者的无争用路径都只是一两条原子指令，没有谁进内核。所以「自旋锁无争用时最快」的前提，是对手锁的快速路径更重；在 macOS 用户态这个前提不成立。
  • The textbook argument: a spinlock has no sleep-and-wake bookkeeping, so when the critical section is very short and every waiter has a core to itself, spinning a few times is cheaper than one trip into the kernel. Measured on this Mac: with a single thread, the hand-written spinlock costs 3.6–4.2 ns, the same as std::mutex at 3.7 ns and slower than os_unfair_lock at 2.2 ns. The reason is that all three uncontended paths are one or two atomic instructions and none of them enters the kernel. So “a spinlock is fastest uncontended” assumes the rival lock has a heavier fast path, and in macOS user space that assumption does not hold.
  • 有争用时：一把共享锁、10 个线程，自旋锁每次加解锁 108.9 ns，std::mutex 13.5 ns，os_unfair_lock 10.3 ns。每次解锁，所有在读这一行的等待者的副本都作废，随后一起来抢，这一行在核之间来回搬运（Phase 0 的伪共享，只是这次是真共享）。睡眠的锁让等待者离场，只剩持有者在跑；加上 firstfit 和 unfair 允许刚解锁的线程立刻再拿锁，大多数加解锁都发生在同一个核的缓存里。这一解释是从测量推断的。
  • Under contention: with one shared lock and 10 threads, one lock-plus-unlock costs 108.9 ns with the spinlock, 13.5 ns with std::mutex and 10.3 ns with os_unfair_lock. Each unlock invalidates the copies of every waiter reading the line, and they all rush in, so the line travels between cores (Phase 0’s false sharing, except that this time the sharing is real). A sleeping lock takes the waiters off the cores and leaves the holder running alone; and because firstfit and unfair let the thread that just unlocked take the lock straight back, most lock-unlock pairs happen in one core’s cache. This explanation is inferred from the measurements.
  • 超额订阅时：20 个线程跑在 10 个核上，自旋锁涨到 181.6 ns，两把睡眠锁仍在 13–15 ns。持锁线程被调度器换下时，其他线程会在它回来之前把整个时间片都花在空转上，而它们占着的核恰恰是持有者回来需要的。sample 也印证了这一点：自旋锁的运行里，内核等待调用一次都没有出现，等待者一直在用户态转。
  • When oversubscribed: with 20 threads on 10 cores, the spinlock rises to 181.6 ns while both sleeping locks stay at 13–15 ns. When the scheduler takes the holder off its core, the other threads spend their whole time slices spinning until it comes back, and the cores they occupy are exactly what the holder needs to return. sample confirms it: in the spinlock run not a single kernel wait call appears, and the waiters keep spinning in user space.

为什么内核里的自旋锁没有这个问题：Linux 的 spin_lock 和 XNU 的 lck_spin_lock 持锁时关抢占，持有者不会被换下，所以等待者最多等完一个很短的临界区；代价是持锁时不许睡眠。用户态做不到关抢占，这正是 macOS 弃用 OSSpinLock 的原因：SDK 的 libkern/OSSpinLockDeprecated.h 写明这些接口不应再使用，尤其当不同优先级的线程可能争用同一把锁时，并让人改用 <os/lock.h>。内核一侧的细节见 Kernel Engineering Phase 3 · Concurrency & IPC 概念 1。

Why spinlocks in the kernel do not have this problem: Linux’s spin_lock and XNU’s lck_spin_lock disable preemption while the lock is held, so the holder cannot be taken off its core and a waiter waits at most for one short critical section; the price is that the holder may not sleep. User space cannot disable preemption, which is exactly why macOS deprecated OSSpinLock: the SDK header libkern/OSSpinLockDeprecated.h says these interfaces should no longer be used, particularly where threads of differing priorities may contend on the same lock, and points to <os/lock.h> instead. The kernel side is in Kernel Engineering Phase 3 · Concurrency & IPC, concept 1.

4. 读写锁、锁粒度与护航效应

4. Reader-writer locks, lock granularity and convoying

读写锁允许多个读者同时进入，写者独占。C++17 的 std::shared_mutex 用 std::shared_lock 读、std::unique_lock 或 std::lock_guard 写。它并不免费：本机 libc++ 的头文件 <shared_mutex> 里，__shared_mutex_base 由一把 mutex、两个 condition_variable 和一个状态字组成，所以每次 lock_shared 都要先拿那把内部 mutex 改读者计数。Lab B 的只读测试（2026-10-31）：

A reader-writer lock lets several readers in at once and gives a writer exclusive access. C++17’s std::shared_mutex reads with std::shared_lock and writes with std::unique_lock or std::lock_guard. It is not free: in this Mac’s libc++ header <shared_mutex>, __shared_mutex_base consists of one mutex, two condition_variables and a state word, so every lock_shared first takes that internal mutex to change the reader count. Lab B’s read-only test (2026-10-31):

  • 临界区只读 1 个 long：shared_mutex 在每种线程数下都比 std::mutex 慢，10 线程时 11.0 ms 对 5.4 ms。
  • A critical section that reads 1 long: shared_mutex is slower than std::mutex at every thread count, 11.0 ms against 5.4 ms at 10 threads.
  • 读 512 个 long（4 KiB）：两者差不多，读者计数那条缓存行上的争用抵消了并发读的收益。
  • Reading 512 longs (4 KiB): the two are about equal, because contention on the cache line holding the reader count cancels the gain from reading concurrently.
  • 读 16384 个 long（128 KiB）：shared_mutex 在 4 线程时 10.8 ms，std::mutex 76.7 ms，快 7 倍。临界区足够长，读者真的同时在读，读写锁才划算。
  • Reading 16384 longs (128 KiB): at 4 threads shared_mutex takes 10.8 ms and std::mutex 76.7 ms, 7 times faster. Only when the critical section is long enough for readers really to read at the same time does a reader-writer lock pay off.

锁粒度：一把大锁保护所有数据（粗粒度）简单、不会死锁，但所有线程排成一队；每个桶、每个对象一把锁（细粒度）能并行，但锁多了要操心顺序（概念 5），而且每把锁本身都要付概念 2 的那几纳秒。最好的锁是不需要的锁：Lab A 的第三种修法让每个线程只加自己的局部和，最后再合并，完全没有共享，因而也没有同步的代价。McKenney 把这种做法叫作分区（partitioning）。

Lock granularity: one big lock over all the data (coarse-grained) is simple and cannot deadlock, but every thread queues behind it; one lock per bucket or per object (fine-grained) allows parallelism, but more locks mean worrying about order (concept 5), and every lock still costs the few nanoseconds of concept 2. The best lock is the one you do not need: Lab A’s third fix has each thread add only to its own partial sum and combines them at the end, so nothing is shared and there is no synchronization cost. McKenney calls this partitioning.

护航效应（lock convoy）：若一把锁严格先来先得地交给排队最久的线程，而那个线程还在睡眠、要等内核唤醒，那么每次交接都要付一次唤醒的延迟，期间锁空着，所有线程排成一列慢慢挪，就像车队跟着最慢的车。firstfit 和 unfair 的设计正是为了避开它：让正在运行的线程直接拿走锁。代价是公平性：<os/lock.h> 的注释写明，名字里的 unfair 指不保证获取顺序，刚解锁的线程可能在被唤醒的等待者之前再次拿到锁，这对性能常常有利，但等待者可能饿死。

Lock convoys: if a lock is handed strictly first-come-first-served to the thread that has waited longest, and that thread is asleep and must wait for the kernel to wake it, then every hand-off pays one wake-up latency while the lock sits idle, and all the threads crawl along in a column like cars behind the slowest one. The firstfit and unfair designs exist to avoid this: the thread that is already running takes the lock. The price is fairness: the comment in <os/lock.h> says that “unfair” means no attempt at fair acquisition order, so a thread that has just unlocked may take the lock again before a woken waiter gets the chance; this is often good for performance, but waiters may starve.

5. 死锁与加锁顺序

5. Deadlock and lock ordering

死锁需要四个条件同时成立（Coffman 条件）：互斥（资源一次只能给一个线程）、持有并等待（拿着一把锁去等另一把）、不可抢占（锁不能被强行收回）、循环等待（T1 等 T2 手里的锁，T2 又等 T1 手里的锁）。前三条是锁的本性，能打破的通常是第四条。

Deadlock needs four conditions at once (the Coffman conditions): mutual exclusion (a resource goes to one thread at a time), hold and wait (holding one lock while waiting for another), no preemption (a lock cannot be taken away by force) and circular wait (T1 waits for a lock T2 holds while T2 waits for a lock T1 holds). The first three are the nature of locks; the one you can usually break is the fourth.

  • 全局加锁顺序：给所有锁规定一个顺序（按层级、按地址、按 ID），每个线程都按这个顺序拿。这样等待关系永远只朝一个方向，不可能成环。动画 (b) 就是这个对比。
  • A global lock order: give all locks one order (by level, by address, by ID) and have every thread take them in that order. The waits then always point one way and can never form a cycle. Diagram (b) shows this contrast.
  • std::scoped_lock（C++17）一次拿多把锁，用一个避免死锁的算法，所以参数顺序写反了也不会死锁。本机实测：两个线程分别以 (a, b) 和 (b, a) 的顺序用它，每次都正常结束；换成两个按相反顺序的 std::lock_guard 并在中间停 10 ms，每次都卡死。
  • std::scoped_lock (C++17) takes several locks at once with a deadlock-avoidance algorithm, so even arguments written in the opposite order do not deadlock. Measured on this Mac: two threads using it with (a, b) and (b, a) finish every time; with two std::lock_guards in opposite order and a 10 ms pause in between, it hangs every time.
  • 持锁时别调用你不了解的代码：回调、虚函数、别人的库都可能在里面拿另一把锁，顺序就不在你手里了。
  • Do not call code you do not know while holding a lock: a callback, a virtual function or someone else’s library may take another lock inside, and the order is no longer in your hands.

怎样认出死锁：程序卡住但 CPU 占用为零。本机对卡死的程序做 sample，两个线程都停在 __psynch_mutexwait，ps 报告的 CPU 时间是 0:00.00（2026-10-31）。TSan 在 Linux 上有锁顺序反转（lock-order-inversion）的检测，但本机实测没有报：同样倒序加锁、未卡死的程序，带 -fsanitize=thread 运行，即使设 TSAN_OPTIONS=detect_deadlocks=1 也没有任何输出、退出码 0。在 Mac 上不要指望 TSan 帮你找死锁。Linux 内核里对应的工具是 lockdep，见 Kernel Phase 3。

How to recognise a deadlock: the program hangs at zero CPU use. Running sample on the hung program on this Mac shows both threads in __psynch_mutexwait, and ps reports a CPU time of 0:00.00 (2026-10-31). TSan has lock-order-inversion detection on Linux, but on this Mac it reported nothing: a program with the same inverted order that did not hang, run under -fsanitize=thread, printed nothing and exited 0, even with TSAN_OPTIONS=detect_deadlocks=1. On a Mac, do not count on TSan to find deadlocks. The Linux kernel’s counterpart tool is lockdep; see Kernel Phase 3.

6. 优先级反转与优先级继承

6. Priority inversion and priority inheritance

三个线程，优先级高 H、中 M、低 L。L 拿着锁；H 想要这把锁，只好等 L；这时 M 就绪，它比 L 优先级高，于是抢走 L 的核一直跑。结果 H 实际上在等 M，一个和锁毫不相干的中优先级线程。最著名的例子是 1997 年火星探路者号（Mars Pathfinder）反复重启，修法是在 VxWorks 里打开那把互斥锁的优先级继承。在 macOS 上，「优先级」主要就是 QoS 类：一个 QOS_CLASS_USER_INTERACTIVE 的界面线程等一个 QOS_CLASS_BACKGROUND 线程手里的锁，正是这种局面。

Three threads with high, medium and low priority: H, M and L. L holds the lock; H wants it and has to wait for L; then M becomes runnable, it outranks L, and it takes L’s core and keeps running. H is now in effect waiting for M, a medium-priority thread that has nothing to do with the lock. The best-known case is the Mars Pathfinder rover resetting repeatedly in 1997, fixed by turning on priority inheritance for that mutex in VxWorks. On macOS, “priority” is mostly the QoS class: a QOS_CLASS_USER_INTERACTIVE UI thread waiting for a lock held by a QOS_CLASS_BACKGROUND thread is exactly this situation.

  • 优先级继承：H 开始等锁时，系统把 L 的优先级临时提到 H 的水平，M 就抢不走 L 的核；L 放锁时恢复原优先级，H 拿到锁。做到这一点的前提是系统知道谁持有这把锁。
  • Priority inheritance: when H starts waiting for the lock, the system temporarily raises L to H’s level, so M cannot take L’s core; when L releases the lock, it drops back and H gets the lock. The precondition is that the system knows who holds the lock.
  • os_unfair_lock 满足这个前提：<os/lock.h> 的注释写明，锁里的值包含线程所有权信息，系统可以用它尝试解决优先级反转。内核一侧借 turnstile 把等待者的优先级借给持有者，见 Kernel Phase 3 概念 1、概念 8。
  • os_unfair_lock meets the precondition: the comment in <os/lock.h> says the value stored in the lock contains thread ownership information that the system may use to attempt to resolve priority inversions. On the kernel side, a turnstile lends the waiter’s priority to the holder; see Kernel Phase 3, concepts 1 and 8.
  • 自旋锁不满足：锁字里只有「占用 / 空闲」一位，内核不知道该提谁；而且高优先级的等待者在空转，反而占着低优先级持有者需要的核。这是 OSSpinLock 被弃用的直接原因。
  • A spinlock does not: its lock word holds only one bit, taken or free, so the kernel does not know whom to boost; and the high-priority waiter is spinning, occupying the very core the low-priority holder needs. That is the direct reason OSSpinLock was deprecated.
  • POSIX 的做法是互斥锁属性 PTHREAD_PRIO_INHERIT（本机 pthread.h 里有这个宏）；Linux 上它落到 PI futex（FUTEX_LOCK_PI，见 futex(2)）和内核的 rt_mutex。本机的默认 pthread mutex 是否做继承，以下是读源码的结论，没有实测：默认属性是 PTHREAD_PRIO_NONE（libpthread 的 types_internal.h），但 XNU 的 psynch 把普通 mutex 的等待者挂在一个以持有者为 inheritor 的 turnstile 上（kern_synch.c），所以有争用时等待者很可能把优先级推给持有者。
  • The POSIX route is the mutex attribute PTHREAD_PRIO_INHERIT (the macro exists in this Mac’s pthread.h); on Linux it maps to PI futexes (FUTEX_LOCK_PI, see futex(2)) and the kernel’s rt_mutex. Whether this Mac’s default pthread mutex does inheritance comes from reading the source, not from measurement: the default attribute is PTHREAD_PRIO_NONE (libpthread’s types_internal.h), yet XNU’s psynch parks plain-mutex waiters on a turnstile with the owner as inheritor (kern_synch.c), so contended waiters likely push their priority onto the holder.

  • 数据竞争是两个可能并发的冲突访问、至少一个不是原子的、彼此没有 happens-before；它是未定义行为，不只是结果不对。
  • 数据竞争和竞态条件不是一回事，TSan 只能找到这次运行里真的发生过的数据竞争。

  • A data race is two potentially concurrent conflicting accesses, at least one not atomic, with no happens-before between them; it is undefined behaviour, not just a wrong result.
  • A data race is not the same as a race condition, and TSan finds only the data races that actually happened in the run.
  • An uncontended mutex is one atomic compare-and-swap plus one release store and never enters the kernel; only under contention does it sleep in the kernel (futex on Linux, psynch or ulock on this Mac).
  • A user-space spinlock cannot disable preemption and its lock word records no owner, so it collapses under contention and oversubscription and cannot do priority inheritance.
  • The best lock is the one you do not need: partitioning by thread and combining at the end beats every lock and atomic, and a reader-writer lock pays off only when the critical section is long.
  • Deadlock needs all four Coffman conditions, and the one you can usually break is circular wait: a global lock order, or std::scoped_lock taking several locks at once.

template <class L> struct alignas(128) Slot { L lock; long count = 0; };  // one line each

constexpr long OPS = 2'000'000;                   // total lock/unlock pairs per run

template <class L> double run_once(int T, bool shared) {
  std::vector<Slot<L>> slots(T);
  std::mutex gm; std::condition_variable cv; bool go = false; int ready = 0;
  std::chrono::steady_clock::time_point t0;
  {
    std::vector<std::jthread> pool;
    for (int t = 0; t < T; ++t)
      pool.emplace_back([&, t] {
        Slot<L>& s = slots[shared ? 0 : t];
        { std::unique_lock g(gm); ++ready; cv.notify_all(); cv.wait(g, [&] { return go; }); }
        for (long i = 0; i < OPS / T; ++i) { s.lock.lock(); ++s.count; s.lock.unlock(); }
      });
    std::unique_lock g(gm);
    cv.wait(g, [&] { return ready == T; });       // every thread is parked at the gate
    t0 = std::chrono::steady_clock::now();
    go = true;
    cv.notify_all();
  }                                               // jthreads join here
  double ns = std::chrono::duration<double, std::nano>(std::chrono::steady_clock::now() - t0).count();
  long sum = 0; for (auto& s : slots) sum += s.count;
  if (sum != OPS / T * T) std::puts("count mismatch");
  return ns / (OPS / T * T);                      // wall ns per lock/unlock pair, all threads together
}

3. T1 先锁 a 再锁 b，T2 先锁 b 再锁 a，程序偶尔卡死，CPU 占用为零。哪个修法是对的？

3. T1 locks a then b, T2 locks b then a, and the program sometimes hangs at zero CPU use. Which fix is right?

死锁来自循环等待；统一顺序让等待只朝一个方向，std::scoped_lock 用避免死锁的算法一次拿多把，两者都打破了环。换成自旋锁不打破环，只是把「睡着等」变成「转着等」，CPU 还会被烧满；加 sleep 只改变时机，概念 5 里描述的死锁测试正是在两次加锁之间停了 10 ms 才每次必卡。Deadlock comes from circular wait; one lock order makes the waits point one way, and std::scoped_lock takes several locks at once with a deadlock-avoidance algorithm, and both break the cycle. Spinlocks do not break the cycle; they only turn “waiting asleep” into “waiting while spinning” and burn the CPU as well. A sleep only changes the timing; the deadlock test described in concept 5 hung every time precisely because it paused 10 ms between the two locks.

4. 一个高 QoS 的界面线程在等一个 background QoS 线程手里的锁，同时几个中等 QoS 的线程在忙。为什么 os_unfair_lock 能缓解这种情况，而自旋锁不能？

4. A high-QoS UI thread waits for a lock held by a background-QoS thread while several medium-QoS threads are busy. Why can os_unfair_lock ease this and a spinlock cannot?

优先级继承的前提是知道持有者：<os/lock.h> 写明锁值包含线程所有权信息，系统可用它尝试解决优先级反转；自旋锁只有一位「占用」，内核不知道该提谁。a 错在相反：名字里的 unfair 正是说它不保证顺序。c 是真的测量结果（2.2 对 4.2 ns），但无争用速度与优先级反转无关。Priority inheritance requires knowing the holder: <os/lock.h> says the lock value contains thread ownership information that the system may use to attempt to resolve priority inversions, whereas a spinlock has only a “taken” bit, so the kernel does not know whom to boost. a is the opposite of the truth: “unfair” in the name means it does not guarantee order. c is a real measurement (2.2 against 4.2 ns), but uncontended speed has nothing to do with priority inversion.
