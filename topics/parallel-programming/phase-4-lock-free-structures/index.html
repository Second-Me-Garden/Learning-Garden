Core concepts

一把锁的持有者被调度器换下，等这把锁的每个线程都跟着停。能不能写出一种结构，任何一个线程停在任何位置都挡不住别人？Phase 3 的 compare-exchange 看起来就是答案，可一个只用 CAS 的栈在 Lab A 里 100 次试验坏了 100 次，TSan 却一声不吭；节点 pop 出来以后什么时候能释放，也没人说得清。不用锁时，「别人还能前进」到底指什么，靠什么保证结构不坏、内存能回收，又在什么时候值得这样做？

1. 进度保证：阻塞、无阻碍、无锁、无等待

1. Progress guarantees: blocking, obstruction-free, lock-free, wait-free

「无锁」不是「代码里没有 mutex」，而是一个关于进度的承诺：当某些线程被调度器换下、停住甚至死掉时，其余线程还能不能完成操作。Herlihy 等人的书把它们定义为对方法调用的保证（定义来自 Herlihy 1991、1993 和 Herlihy、Luchangco、Moir 2003；McKenney 第 14.2 节逐条列出并引用了这些出处）：

“Lock-free” does not mean “no mutex in the code”; it is a promise about progress: when some threads are descheduled, stalled or even dead, can the remaining threads still complete their operations? Herlihy et al. define these as guarantees on method calls (the definitions come from Herlihy 1991 and 1993 and from Herlihy, Luchangco and Moir 2003; McKenney’s section 14.2 lists them one by one with these citations):

  • 无等待（wait-free）：每一个线程都在有限步内完成自己的调用，不管别的线程在干什么。没有饥饿。
  • Wait-free: every thread completes its call in a finite number of its own steps, whatever the other threads do. There is no starvation.
  • 无锁（lock-free）：在任何时刻，至少有一个线程在有限步内完成调用，所以整个系统一直在前进；但某个具体线程可能一直输掉 CAS、永远做不完（饥饿）。
  • Lock-free: at any moment at least one thread completes a call in a finite number of steps, so the system as a whole always moves forward; but one particular thread may keep losing its CAS and never finish (starvation).
  • 无阻碍（obstruction-free）：一个线程只要单独运行（其他线程都暂停）足够久，就会在有限步内完成。有争用时可能大家互相打断、谁都做不完（活锁）。
  • Obstruction-free: a thread that runs in isolation (all others paused) for long enough completes in a finite number of steps. Under contention they may keep interrupting each other so that nobody finishes (livelock).
  • 阻塞（blocking）：无死锁（deadlock-free）和无饥饿（starvation-free）都属于这一类，它们的保证依赖调度器公平：持锁线程停住，所有等它的线程都停住。Herlihy 把它们叫作依赖型（dependent）进度条件。
  • Blocking: deadlock-freedom and starvation-freedom belong here, and their guarantees depend on a fair scheduler: if the lock holder stalls, everyone waiting for it stalls. Herlihy calls these dependent progress conditions.

McKenney 第 14.2 节原文给出的表述（v2026.06.21a，本页逐字核对过）：wait-free 是「Every thread will make progress in finite time」，lock-free 是「At least one thread will make progress in finite time」，obstruction-free 是「Every thread will make progress in finite time in the absence of contention」；他还列出了 bounded wait-free、clash-free 等更细的等级。

McKenney’s section 14.2 states them as follows (v2026.06.21a, checked word for word for this page): wait-free is “Every thread will make progress in finite time”, lock-free is “At least one thread will make progress in finite time”, and obstruction-free is “Every thread will make progress in finite time in the absence of contention”; he also lists finer levels such as bounded wait-free and clash-free.

怎样判断一段代码：Lab A 的 push 是「读 top，CAS，失败就重来」。一次 CAS 失败，说明别的线程的 CAS 刚刚成功，系统整体前进了，所以它是 lock-free；但同一个线程可能无限次失败，所以它不是 wait-free。fetch_add 在本机编译成一条 LSE 指令 ldadd，程序里没有重试循环，通常把它算作 wait-free；硬件仲裁能否在争用下给每个核有界的完成时间，本页没有查到 Arm 的明确说法。另外注意 std::atomic<T>::is_lock_free() 只回答「这个原子对象的操作是不是用锁模拟的」，它说的是单个对象，不是你的算法。

How to classify code: Lab A’s push is “read top, CAS, retry on failure”. A failed CAS means that another thread’s CAS has just succeeded, so the system as a whole made progress and the loop is lock-free; but the same thread may fail without bound, so it is not wait-free. fetch_add compiles to one LSE instruction, ldadd, on this Mac, with no retry loop in the program, and is usually counted as wait-free; whether hardware arbitration gives every core a bounded completion time under contention is something this page found no explicit Arm statement on. Note too that std::atomic<T>::is_lock_free() only answers “are this atomic object’s operations emulated with a lock?”; it describes one object, not your algorithm.

为什么要关心进度：持锁的线程被换下、被信号打断、或者在优先级反转里被饿住时，阻塞结构上的每个线程都会跟着停；无锁结构没有「持有者」，一个线程停在任何位置都挡不住别人。这才是无锁的主要收益，概念 6 会说明它不等于「更快」。正确性的标准是可线性化（linearizability）：每次调用看起来都在调用开始和返回之间的某个瞬间原子地生效，Treiber 栈的这个瞬间就是那次成功的 CAS。

Why progress matters: when a lock holder is descheduled, interrupted by a signal or starved by priority inversion, every thread on a blocking structure stops with it; a lock-free structure has no “holder”, so one thread stopping anywhere cannot hold up the rest. That is the main benefit of lock-freedom, and concept 6 shows it is not the same as “faster”. The correctness standard is linearizability: each call appears to take effect atomically at some instant between its invocation and its return, and for the Treiber stack that instant is the successful CAS.

2. Treiber 栈、CAS 与 ABA

2. The Treiber stack, CAS and ABA

Treiber 栈（R. Kent Treiber，IBM 1986 年的研究报告）是最简单的无锁结构：一个原子指针 top 指向链表头。

The Treiber stack (R. Kent Treiber, an IBM research report from 1986) is the simplest lock-free structure: one atomic pointer, top, points to the head of a linked list.

  • push(n)：读 top 得到 old，令 n->next = old，再 CAS(top, old → n)。CAS 失败时 compare_exchange_weak 会把 old 改成当前值，循环重来。成功的 CAS 用 release：n 的内容必须先于「top 指向 n」被别人看见。
  • push(n): read top into old, set n->next = old, then CAS(top, old → n). On failure compare_exchange_weak updates old to the current value and the loop retries. The successful CAS uses release: n’s contents must become visible before “top points to n” does.
  • pop()：读 top 得到 old（acquire，这样读 old->next 才能看到 push 时写下的值），再 CAS(top, old → old->next)。
  • pop(): read top into old (acquire, so that reading old->next sees the value written at push time), then CAS(top, old → old->next).

在 arm64 上：ARMv8.0 只有 load-exclusive / store-exclusive（ldaxr、stlxr）这对 LL/SC 指令，CAS 要写成循环，被打断就会失败，这正是 compare_exchange_weak 允许「伪失败」的原因。ARMv8.1 的 LSE 加了单条的 cas 系列。本机 sysctl hw.optional.arm.FEAT_LSE 为 1，Apple clang 21 在 -O2 下把 pop 的读编译成 ldapr、把 CAS 编译成 casa（带 acquire 的 CAS），所以这里 weak 和 strong 生成的是同一条指令（2026-10-31，Lab A 第 4 步）。

On arm64: ARMv8.0 has only the load-exclusive / store-exclusive LL/SC pair (ldaxr, stlxr), so a CAS is a loop that fails if it is interrupted, which is exactly why compare_exchange_weak may fail spuriously. ARMv8.1’s LSE adds the single-instruction cas family. On this Mac sysctl hw.optional.arm.FEAT_LSE is 1, and Apple clang 21 at -O2 compiles pop’s load to ldapr and its CAS to casa (CAS with acquire), so weak and strong produce the same instruction here (2026-10-31, Lab A step 4).

ABA：CAS 只问「top 现在还等于 old 吗」，不问「这期间有没有变过」。T1 读到 top = A、A->next = B，在 CAS 前被换下；T2 弹出 A、弹出 B、再把 A 压回去，此时 A->next 已经是 C；T1 醒来执行 CAS(top, A → B)，top 确实等于 A，于是成功，栈顶变成了 T2 手里的 B，C 丢了。动画 (a) 逐步演示这个过程。节点地址被重复使用（内存池、空闲链表、或者 malloc 把刚释放的块再分出去）时就会发生。Lab A 实测：不带计数的版本 100 次试验 100 次损坏，每次最后都在链表里留下一个环。

ABA: a CAS asks only “is top still equal to old?”, not “has it changed in the meantime?”. T1 reads top = A and A->next = B, then is descheduled before its CAS; T2 pops A, pops B and pushes A back, and now A->next is C; T1 wakes and runs CAS(top, A → B), top really is A, so it succeeds, the top becomes the B that T2 is holding, and C is lost. Diagram (a) steps through this. It happens whenever node addresses are reused (a pool, a free list, or malloc handing a just-freed block out again). Measured in Lab A: the untagged version corrupted in 100 of 100 trials, each one ending with a cycle in the list.

Fixes:

  • 带计数的指针（tagged pointer）：把 top 换成「指针 + 64 位计数」的 16 字节结构，每次成功的 CAS 让计数加 1。T1 手里是 {A, 5}，现在的值是 {A, 8}，CAS 失败、重读。本机 std::atomic<Tagged> 的 is_lock_free() 为 1，CAS 编译成 caspa / caspl（一对 64 位寄存器的 CAS），acquire 读编译成 ldp 加 dmb ishld（FEAT_LSE2 让对齐的 16 字节 ldp 成为单次原子访问）。x86-64 上对应的是 cmpxchg16b，GCC 和 clang 要加 -mcx16 才会内联它，这个选项只对 x86 有意义。
  • A tagged pointer: replace top with a 16-byte “pointer plus 64-bit counter” and have every successful CAS add 1 to the counter. T1 holds {A, 5}, the current value is {A, 8}, so the CAS fails and T1 rereads. On this Mac std::atomic<Tagged> reports is_lock_free() as 1; the CAS compiles to caspa / caspl (a CAS on a pair of 64-bit registers), and the acquire load to ldp plus dmb ishld (FEAT_LSE2 makes an aligned 16-byte ldp a single atomic access). On x86-64 the counterpart is cmpxchg16b, which GCC and clang inline only with -mcx16, an option that means something only on x86.
  • 不让地址在被引用时复用：如果还有线程可能拿着 A，就不释放、不复用 A。这正是概念 4 的回收机制做的事，所以 hazard pointer 和 epoch 同时解决了 ABA。
  • Never reuse an address while it may be referenced: if any thread may still hold A, do not free or reuse A. That is exactly what the reclamation schemes of concept 4 do, so hazard pointers and epochs solve ABA as well.

3. Michael–Scott 队列：帮助别人完成操作

3. The Michael–Scott queue: helping other operations finish

队列比栈难，因为两端各有一个指针：head 和 tail。Michael 和 Scott 1996 年的论文「Simple, Fast, and Practical Non-Blocking and Blocking Concurrent Queue Algorithms」给出的无锁队列至今仍是标准答案：

A queue is harder than a stack because it has a pointer at each end: head and tail. The lock-free queue in Michael and Scott’s 1996 paper, “Simple, Fast, and Practical Non-Blocking and Blocking Concurrent Queue Algorithms”, is still the standard answer:

  • 哑节点：队列里永远至少有一个节点，head 指向它，真正的第一个元素是 head->next。这样空队列和非空队列不用分开处理，入队和出队也不会碰同一个指针。
  • A dummy node: the queue always holds at least one node, head points to it, and the real first element is head->next. Empty and non-empty queues then need no separate cases, and enqueue and dequeue never touch the same pointer.
  • 入队分两步：先 CAS(tail->next, null → n) 把新节点挂上（这一步是线性化点），再 CAS(tail, 旧 tail → n) 把尾指针挪过去。两步之间 tail 落后一个节点。
  • Enqueue takes two steps: first CAS(tail->next, null → n) links the new node (this is the linearization point), then CAS(tail, old tail → n) swings the tail pointer. Between the two steps tail lags one node behind.
  • 帮助（helping）：任何线程看到 tail->next 不为空，就先替别人做完第二步，再做自己的事。所以入队者在两步之间停住也挡不住任何人，这就是它 lock-free 而不只是 obstruction-free 的原因。
  • Helping: any thread that sees a non-null tail->next first completes the other thread’s second step, then does its own work. An enqueuer that stalls between its two steps therefore blocks nobody, which is why the queue is lock-free and not merely obstruction-free.

原论文用带修改计数的指针（counted pointer）防 ABA，与 Lab A 的修法相同；同一篇论文还给出了一个双锁的阻塞队列（头尾各一把锁），在没有合适原子指令的机器上更实用。本页不为它单独做实验：它的 ABA 和回收问题与 Treiber 栈完全一样，只是多了一个指针。

The original paper prevents ABA with counted pointers, the same fix as Lab A; the same paper also gives a blocking two-lock queue (one lock at each end), which is more practical on machines without suitable atomic instructions. 4. 内存回收：hazard pointer、epoch，以及内核的 RCU

4. Memory reclamation: hazard pointers, epochs, and the kernel’s RCU

Lab A 用一个固定的节点池，从不释放节点，所以才能放心读 old->next。真实的栈会在 pop 之后 delete 节点，而另一个线程可能刚读到 top == old、正要读 old->next：那就是释放后使用（use-after-free）。锁天然没有这个问题，持锁期间没有别人在看；无锁结构必须回答「什么时候没有任何线程还可能拿着这个指针」。三种回答：

Lab A uses a fixed pool and never frees a node, which is the only reason reading old->next is safe. A real stack would delete the node after pop, while another thread may have just read top == old and be about to read old->next: a use-after-free. Locks avoid this by nature, because nobody else is looking while the lock is held; a lock-free structure must answer “when can no thread still be holding this pointer?”. Three answers:

  • Hazard pointer（Maged Michael，2004）：每个线程有几个公开的槽。读 top 之后，先把这个指针写进自己的槽，然后用 seq_cst 顺序重读 top，确认它没变，才可以解引用。要释放的节点先放进本线程的「待退休」列表；列表够长时扫描所有线程的槽，不在任何槽里的节点才真正释放。读者每次访问都要付一次写和一次全序栅栏；好处是垃圾有上界：一个停住的线程最多钉住它槽里的那几个节点。动画 (c) 把登记、重读、退休、扫描和释放逐步画出来。
  • Hazard pointers (Maged Michael, 2004): each thread owns a few public slots. After reading top it writes that pointer into its slot, rereads top with seq_cst ordering to confirm it is unchanged, and only then dereferences it. A node to be freed goes onto the thread’s own retire list; when the list is long enough, the thread scans every thread’s slots and frees only the nodes that appear in none. Readers pay one store and one full fence per access; in return garbage is bounded: a stalled thread pins at most the few nodes in its slots. Diagram (c) steps through publishing, rereading, retiring, scanning and freeing.
  • Epoch 回收（Keir Fraser，2004 年剑桥技术报告「Practical lock-freedom」）：有一个全局 epoch 计数。线程进入操作时记下当前 epoch，离开时清掉；退休的节点按它退休时的 epoch 分组。当所有正在操作中的线程都已经看到更新的 epoch，更早那组节点就不可能再被任何人拿着，可以整批释放。读者只在进出时各写一次自己的那一格，比 hazard pointer 便宜；代价是一个停在操作中间的线程会让 epoch 无法前进，垃圾无限堆积。
  • Epoch-based reclamation (Keir Fraser, the 2004 Cambridge technical report “Practical lock-freedom”): there is a global epoch counter. A thread records the current epoch when it enters an operation and clears it on leaving; retired nodes are grouped by the epoch in which they were retired. Once every thread still inside an operation has seen a newer epoch, no one can hold a node from the older group, and the whole group is freed at once. Readers write only their own slot, once on entry and once on exit, which is cheaper than hazard pointers; the price is that one thread stalled in the middle of an operation stops the epoch from advancing, and garbage piles up without bound.
  • RCU，内核的答案：把 epoch 的思路推到读者「什么也不写」。Linux 内核里 rcu_read_lock() 在非抢占内核中只是关抢占，读区里不会发生上下文切换，所以每个 CPU 只要经历过一次上下文切换、进入 idle 或回到用户态（quiescent state），就证明它在宽限期开始前进入的读区都结束了。写者用 rcu_assign_pointer（本质是 store-release）发布新版本，synchronize_rcu() 等宽限期结束再释放旧版本。动画 (b) 演示这个时间线；内核里的 API、kernel/rcu/tree.c 和 XNU 基于序号的 SMR 见 Kernel Engineering Phase 3 概念 3。
  • RCU, the kernel’s answer: push the epoch idea to readers that “write nothing at all”. In the Linux kernel, rcu_read_lock() in a non-preemptible kernel only disables preemption, so no context switch happens inside a read section, and one context switch, idle entry or return to user mode per CPU (a quiescent state) proves that every read section begun before the grace period has ended. The writer publishes a new version with rcu_assign_pointer (essentially a store-release), and synchronize_rcu() waits for the grace period to end before the old version is freed. Diagram (b) shows this timeline; the kernel API, kernel/rcu/tree.c and XNU’s sequence-number-based SMR are in Kernel Engineering Phase 3, concept 3.

用户态为什么不能照搬：用户态线程关不了抢占，内核也不会把「这个线程发生过上下文切换」告诉你。所以用户态 RCU 要读者自己报告：liburcu 的 QSBR 版本要求每个读者线程定期调用 rcu_quiescent_state()（liburcu.org 写明这是读端最快、对应用侵入最大的版本）；默认版本在内核支持 sys_membarrier() 时用它让写者一侧付出栅栏的代价，否则退回读端更慢的 urcu-mb。用户态 RCU 因此和 epoch 回收很像，区别在于读区的标记有多便宜。C++26 把两者都标准化了：<hazard_pointer>（P2530，Maged Michael 等）和 <rcu>（P2545，Paul McKenney 等）。本机 Apple clang 21 的 libc++ 还没有这两个头文件（2026-10-31，#include <rcu> 报 file not found）。

Why user space cannot copy it directly: a user-space thread cannot disable preemption, and the kernel does not tell you that “this thread has context-switched”. User-space RCU therefore has readers report for themselves: liburcu’s QSBR flavour requires every reader thread to call rcu_quiescent_state() periodically (liburcu.org says it has the fastest read side at the expense of more intrusiveness in the application); the default flavour uses sys_membarrier() when the kernel supports it, so that the writer side pays for the fences, and otherwise falls back to urcu-mb with a slower read side. User-space RCU thus looks much like epoch reclamation; the difference is how cheap the read-side marker is. C++26 standardizes both: <hazard_pointer> (P2530, Maged Michael et al.) and <rcu> (P2545, Paul McKenney et al.). The libc++ in this Mac’s Apple clang 21 does not have either header yet (2026-10-31: #include <rcu> fails with file not found).

5. Seqlock：读者不写任何东西，写错了就重读

5. Seqlocks: readers write nothing and retry when they lose

RCU 需要「复制再换指针」，适合指针指向的大对象。一条小记录（这里是 64 字节）有更轻的办法：seqlock。它带一个序号 seq，偶数表示稳定，奇数表示正在写。

RCU needs “copy, then swap the pointer”, which suits large objects reached through a pointer. A small record (64 bytes here) has a lighter option: the seqlock. It carries a sequence number seq; even means stable, odd means a write is in progress.

  • 写者：seq 加 1 变成奇数，release 栅栏，写数据，再以 release 写把 seq 加到下一个偶数。写者从不等读者；多个写者之间仍要一把普通锁。
  • Writer: add 1 to seq to make it odd, issue a release fence, write the data, then store the next even value to seq with release. The writer never waits for readers; several writers still need an ordinary lock among themselves.
  • 读者：以 acquire 读 seq 得到 s1，是奇数就重来；复制数据；acquire 栅栏；再读 seq，等于 s1 才算读到一份完整的副本，否则扔掉重读。读者不写任何共享内存，所以那条缓存行可以同时在所有读者的 L1 里，读者数增加不会互相拖慢。
  • Reader: load seq with acquire into s1, and start over if it is odd; copy the data; issue an acquire fence; read seq again, and only if it still equals s1 is the copy whole, otherwise throw it away and reread. Readers write no shared memory, so the cache line can sit in every reader’s L1 at once and adding readers does not slow them down.

一个读者撞上一次写，再看 Lab B 怎样把这件事数出来。序号 4 和 6 是示意用的值，后两行是 Lab B 的实测：

One reader runs into one write, and then Lab B counts how often that happens. The sequence numbers 4 and 6 are values chosen for illustration; the last two lines are Lab B measurements:

  2. 读者复制完，过 acquire 栅栏重读序号得到 6，和开头的 4 不等，说明复制期间有写，手里的副本可能是半新半旧，整份扔掉。
  3. 重来一次时没有写插进来，前后两次都读到 6，这份副本完整。读者全程没有写任何共享内存。
  4. Lab B 里写者每微秒写一次、4 个读者时，平均每次成功的读只扔掉 0.577 次尝试；去掉检查的 nocheck 有 5.29 % 的副本是撕裂的。写者不停地写时，1 个读者每成功一次要扔掉约 4040 次，每秒只读到 0.3 百万次，同样条件下 mutex 读者是 14.6 百万次。
  1. The reader sees the even value 4 and starts copying. Halfway through, the writer makes the sequence number odd, 5, writes the 8 words, and sets it to 6.
  2. The reader finishes the copy, passes the acquire fence and rereads the sequence number: 6, not the 4 it started with, so a write happened during the copy and the copy may be half old, half new. The whole copy is thrown away.
  3. On the retry no write gets in, both reads see 6, and the copy is whole. At no point did the reader write any shared memory.
  4. In Lab B, with one write per microsecond and 4 readers, each successful read throws away only 0.577 attempts on average, and nocheck, which skips the check, has 5.29 % torn copies. With the writer writing non-stop, 1 reader throws away about 4040 attempts per success and manages only 0.3 million reads per second, against 14.6 million for a mutex reader under the same conditions.

在 C++ 内存模型里怎样写对：读者在写者写的同时读数据，如果数据是普通变量，那就是数据竞争、是未定义行为，哪怕读到的副本随后会被丢掉。所以 Lab B 把 8 个数据字都声明为 std::atomic<uint64_t>，用 relaxed 读写，再用两个栅栏建立顺序。这是 Hans Boehm 在 2012 年的论文「Can Seqlocks Get Along with Programming Language Memory Models?」里分析过的写法。本机编译结果（Lab B 第 3 步）：relaxed 原子读写就是普通的 ldr、str，写者只多一条 dmb ish 和一条 stlr，读者只多一条 ldapr 和一条 dmb ishld。

Getting it right under the C++ memory model: readers read the data while the writer is writing it; if the data were plain variables that would be a data race and undefined behaviour, even though the copy is thrown away afterwards. So Lab B declares all eight data words as std::atomic<uint64_t>, reads and writes them relaxed, and orders them with two fences. This is the approach Hans Boehm analysed in his 2012 paper “Can Seqlocks Get Along with Programming Language Memory Models?”. What this Mac’s compiler emits (Lab B step 3): relaxed atomic loads and stores are plain ldr and str; the writer adds only one dmb ish and one stlr, and the reader only one ldapr and one dmb ishld.

限制：读者在重查 seq 之前看到的可能是写到一半的数据，所以不能拿它去解引用指针、做除数或当数组下标。Linux 内核文档（docs.kernel.org 的 Sequence counters and sequential locks）写明 seqlock 不能用于含指针的数据，因为写者可能让读者正在跟随的指针失效。内核用 seqcount_t / seqlock_t，读者写成 read_seqbegin … read_seqretry 循环。另一个限制是读者可能饿死：写得太频繁时读者永远对不上序号，内核为此提供 read_seqbegin_or_lock，先无锁试一次，失败后改为加锁读。Lab B 量出了这个饿死。

Limits: before it rechecks seq, a reader may see half-written data, so it must not dereference it as a pointer, divide by it or use it as an array index. The Linux kernel documentation (docs.kernel.org, Sequence counters and sequential locks) says a seqlock cannot be used if the protected data contains pointers, because the writer can invalidate a pointer that the reader is following. The kernel uses seqcount_t / seqlock_t, with readers written as a read_seqbegin … read_seqretry loop. The other limit is reader starvation: if writes come too often, readers never get a matching sequence number, and for that the kernel offers read_seqbegin_or_lock, which tries once without the lock and then reads under it. Lab B measures this starvation.

6. 什么时候锁更快

6. When a lock is faster

无锁不等于更快。它保证的是进度，代价有三笔：

Lock-free does not mean faster. What it guarantees is progress, and it costs three things:

  • 争用下同样是一条缓存行：Treiber 栈的每次操作都要 CAS 同一个 top，和一把锁争的是同一条线。CAS 失败还要重读、重算、重试，做了的工作被扔掉。Phase 2 实测，10 个线程抢一把 os_unfair_lock 每次只要 10.3 ns：睡眠锁让等待者离场，持有者在自己的缓存里连续完成多次操作。一个高争用的 CAS 循环未必能赢它；本页没有为此单独做基准测试。
  • Under contention it is still one cache line: every Treiber stack operation CASes the same top, the same line a lock would fight over. A failed CAS must reread, recompute and retry, throwing work away. Phase 2 measured 10.3 ns per operation for 10 threads on one os_unfair_lock: a sleeping lock takes the waiters off the cores, and the holder completes several operations in a row in its own cache. A heavily contended CAS loop need not beat that; this page ran no separate benchmark for it.
  • 写多时乐观方案会输：Lab B 让写者不停地写时，1 个 seqlock 读者每秒只完成 0.1–0.3 百万次读，同样条件下 std::mutex 读者是 14.6–16.4 百万次。锁让读者和写者轮流，seqlock 让读者永远对不上序号。
  • Optimism loses when writes dominate: with Lab B’s writer writing non-stop, one seqlock reader completes only 0.1–0.3 million reads per second, against 14.6–16.4 million for a std::mutex reader under the same conditions. The lock makes reader and writer take turns; the seqlock leaves the reader never matching the sequence number.
  • 复杂度和验证：ABA、回收、内存序，每一项都是一类新错误，而 TSan 对 ABA 一声不吭（Lab A）。McKenney 9.6 节给出的建议也是先用最简单能满足需求的方案。
  • Complexity and verification: ABA, reclamation and memory ordering each add a new class of bug, and TSan says nothing about ABA (Lab A). McKenney’s section 9.6 likewise advises starting from the simplest scheme that meets the need.

无锁真正划算的地方：读远多于写（seqlock、RCU：Lab B 里每微秒写一次时，10 个 seqlock 读者比 mutex 快 40 到 90 倍）；不允许阻塞的上下文（信号处理函数、实时音频线程、中断处理，那里拿不到锁就是灾难）；以及线程可能被长时间换下、而其他线程不能等它的场合。其余情况，先用一把锁，用数据证明它是瓶颈再换。

Where lock-free really pays: when reads far outnumber writes (seqlocks and RCU: in Lab B, with one write per microsecond, 10 seqlock readers are 40 to 90 times faster than a mutex); in contexts that must not block (signal handlers, real-time audio threads, interrupt handlers, where failing to get a lock is a disaster); and where a thread may be descheduled for a long time while the others must not wait for it. Everywhere else, start with a lock and replace it only once data proves it is the bottleneck.

Further reading: McKenney, Chapter 9, section 9.6, “Which to Choose?” (the Overview, Details and Production Use subsections), and 14.2.2, “Applicability of NBS Benefits”; the “Impact on Performance” section of Bos, Chapter 7, “Understanding the Processor”.

  • 无锁是一个进度承诺：任何时刻至少一个线程在有限步内完成；无等待要求每个线程都如此，「读、算、CAS、失败重试」的循环只是无锁。
  • Treiber 栈的 push 用 release 的 CAS 发布新节点，pop 用 acquire 读栈顶，那次成功的 CAS 就是操作的线性化点。
  • CAS 只比较值，节点地址被复用时就会 ABA：Lab A 不带计数 100 次坏 100 次，带计数的 16 字节指针 0 次，TSan 两次都不报告。
  • 无锁结构必须回答节点什么时候能释放：hazard pointer 给垃圾设上界，epoch 读端更便宜但怕停住的线程，RCU 的读者什么都不写。
  • seqlock 的读者不写共享内存、对不上序号就重读，读多写少时比 mutex 快 40 到 90 倍，写者不停时却会饿死。
  • 无锁不等于更快：默认先用一把锁，用数据证明它是瓶颈再换。
  • Lock-free is a progress promise: at every moment at least one thread completes in a finite number of steps; wait-free demands that of every thread, and a read, compute, CAS, retry loop is only lock-free.
  • A Treiber push publishes the new node with a release CAS, a pop reads the top with acquire, and the successful CAS is the operation’s linearization point.
  • CAS compares only values, so reused node addresses give ABA: in Lab A the untagged stack broke in 100 of 100 trials, the 16-byte tagged pointer in 0, and TSan reported neither.
  • A lock-free structure must answer when a node may be freed: hazard pointers bound the garbage, epochs have a cheaper read side but fear a stalled thread, and RCU readers write nothing at all.
  • Seqlock readers write no shared memory and reread when the sequence number does not match, which makes them 40 to 90 times faster than a mutex when reads dominate, but they starve under a non-stop writer.
  • Lock-free does not mean faster: start with a lock, and replace it only once data proves it is the bottleneck.

常见误解

Common misconceptions

  • 误解：无锁就是代码里没有 mutex，所以一定比锁快。→ 实际：它承诺的是进度，不是速度；写者不停时 1 个 mutex 读者比 1 个 seqlock 读者快 50 到 160 倍（Lab B）。
  • 误解：TSan 跑干净，无锁代码就是对的。→ 实际：Lab A 所有共享访问都是原子的，没有数据竞争，栈照样每次都坏；ABA 是算法错误，TSan 看不见。
  • 误解：is_lock_free() 返回 true，我的算法就是无锁的。→ 实际：它只说这一个原子对象的操作不是用锁模拟的，算法的进度要按概念 1 的定义自己判断。
  • Myth: lock-free means no mutex in the code, so it must beat a lock. → Fact: it promises progress, not speed; with a non-stop writer one mutex reader beats one seqlock reader by 50 to 160 times (Lab B).
  • Myth: if TSan runs clean, the lock-free code is correct. → Fact: in Lab A every shared access is atomic and there is no data race, yet the stack breaks every time; ABA is an algorithm bug that TSan cannot see.
  • Myth: if is_lock_free() returns true, my algorithm is lock-free. → Fact: it says only that one atomic object’s operations are not emulated with a lock; the algorithm’s progress must be judged against the definitions of concept 1.

Lab A · A Treiber stack, the ABA failure, and a tagged pointer

  1. 把下面的程序存成 treiber.cpp。8 个节点组成一个固定的池，从不释放，所以这里只会出现 ABA，不会出现释放后使用。4 个线程各做 20 万轮「pop 两个，再按原顺序 push 回去」：先放回的 A 会压在一个不同的 next 上，正好制造动画 (a) 第 4 步的局面。每个节点有一个 held 标志，两个线程同时拿到同一个节点就记一次 double pop。每次试验结束时数一数从 top 能走到几个节点：应该是 8；走到第 9 个说明链表成环。Save the program below as treiber.cpp. Eight nodes form a fixed pool that is never freed, so only ABA can happen here, not use-after-free. Four threads each do 200,000 rounds of “pop two, then push them back in the same order”: A, going back first, lands on a different next, which recreates step 4 of diagram (a). Each node has a held flag, and two threads holding the same node at once counts as a double pop. At the end of each trial the program counts how many nodes can be reached from top: it should be 8, and reaching a ninth means the list has a cycle.
    // treiber.cpp: a Treiber stack over a fixed pool of nodes, untagged versus tagged top
// usage: ./treiber plain | tagged   [trials]
#include <atomic>
#include <cstdint>
#include <cstdio>
#include <cstring>
#include <string>
#include <thread>
#include <vector>

constexpr int NODES = 8;           // small stack: the same addresses come back often
constexpr int THREADS = 4;
constexpr long OPS = 200'000;      // pop-pop-push-push rounds per thread per trial

struct Node {
  std::atomic<Node*> next{nullptr};      // atomic: another thread may relink it while we read
  std::atomic<int> held{0};              // 1 while some thread has popped it
};
Node pool[NODES];

// ---- untagged: top is one pointer, CAS compares only the address ----
std::atomic<Node*> top_plain{nullptr};
void push_plain(Node* n) {
  Node* old = top_plain.load(std::memory_order_relaxed);
  do n->next.store(old, std::memory_order_relaxed);
  while (!top_plain.compare_exchange_weak(old, n, std::memory_order_release, std::memory_order_relaxed));
}
Node* pop_plain() {
  Node* old = top_plain.load(std::memory_order_acquire);
  while (old && !top_plain.compare_exchange_weak(old, old->next.load(std::memory_order_relaxed),
                                                 std::memory_order_acquire, std::memory_order_acquire)) {}
  return old;                            // ABA: old->next may be stale when the CAS succeeds
}

// ---- tagged: pointer plus a counter in one 16-byte word, every successful CAS bumps the tag ----
struct alignas(16) Tagged { Node* p; std::uint64_t tag; };
std::atomic<Tagged> top_tagged{Tagged{nullptr, 0}};
void push_tagged(Node* n) {
  Tagged old = top_tagged.load(std::memory_order_relaxed);
  do n->next.store(old.p, std::memory_order_relaxed);
  while (!top_tagged.compare_exchange_weak(old, Tagged{n, old.tag + 1}, std::memory_order_release, std::memory_order_relaxed));
}
Node* pop_tagged() {
  Tagged old = top_tagged.load(std::memory_order_acquire);
  while (old.p && !top_tagged.compare_exchange_weak(old, Tagged{old.p->next.load(std::memory_order_relaxed), old.tag + 1},
                                                    std::memory_order_acquire, std::memory_order_acquire)) {}
  return old.p;
}

template <bool T> Node* pop() { return T ? pop_tagged() : pop_plain(); }
template <bool T> void push(Node* n) { T ? push_tagged(n) : push_plain(n); }
template <bool T> Node* head() { return T ? top_tagged.load().p : top_plain.load(); }

std::atomic<long> double_pops{0};        // a node handed to two threads at once

template <bool T> int trial() {          // returns the number of nodes reachable at the end, NODES + 1 means a cycle
  top_plain.store(nullptr); top_tagged.store(Tagged{nullptr, 0});
  for (auto& n : pool) { n.held.store(0); push<T>(&n); }
  long before = double_pops.load();
  {
    std::vector<std::jthread> ts;
    for (int t = 0; t < THREADS; ++t)
      ts.emplace_back([] {
        for (long i = 0; i < OPS; ++i) {
          Node* a = pop<T>(); Node* b = pop<T>();          // take two, give them back in the same order
          for (Node* n : {a, b}) if (n && n->held.exchange(1)) double_pops.fetch_add(1);
          for (Node* n : {a, b}) if (n) { n->held.store(0); push<T>(n); }  // a goes back first, so a sits on top of a different next
        }
      });
  }
  int count = 0;                                            // walk at most NODES + 1 links
  for (Node* n = head<T>(); n && count <= NODES; n = n->next.load()) ++count;
  if (count == NODES && double_pops.load() != before) count = -1;  // right length, but a node was shared
  return count;
}

int main(int argc, char** argv) {
  bool tagged = argc > 1 && !std::strcmp(argv[1], "tagged");
  int trials = argc > 2 ? std::atoi(argv[2]) : 20;
  std::printf("%s top: lock-free %d, sizeof %zu\n", tagged ? "tagged" : "plain",
              tagged ? (int)top_tagged.is_lock_free() : (int)top_plain.is_lock_free(),
              tagged ? sizeof(Tagged) : sizeof(Node*));
  int bad = 0, seen[NODES + 3] = {};       // seen[k + 1]: trials that ended with k reachable nodes
  for (int i = 0; i < trials; ++i) {
    int c = tagged ? trial<true>() : trial<false>();
    ++seen[c + 1]; bad += c != NODES;
  }
  std::printf("corrupted trials: %d / %d, double pops: %ld\nreachable nodes at the end (want %d):", bad, trials, double_pops.load(), NODES);
  for (int k = -1; k <= NODES + 1; ++k) if (seen[k + 1]) std::printf("  %s:%d", k < 0 ? "shared" : k > NODES ? "cycle" : std::to_string(k).c_str(), seen[k + 1]);
  std::puts("");
}

Lab B · 用 seqlock 保护一条 64 字节的记录，与 mutex 对比

Lab B · A seqlock protecting a 64-byte record, measured against a mutex

  1. 把下面的程序存成 seqlock.cpp。记录是 8 个 64 位字，共 64 字节，写者每次把 8 个字都写成同一个新值，所以读者只要看到两个字不相等，就是读到了撕裂的副本（torn）。seqlock 和 mutex 两种做法各测 1、4、10 个读者加 1 个写者；第三种 nocheck 用同一个 seqlock 写者，但读者不看序号，用来证明序号检查在起作用。命令行参数是写者每次写之间的间隔（纳秒），0 表示写者不停。每个格子是 5 次 0.5 秒运行的中位数。10 个读者加 1 个写者是 11 个线程，比本机的 10 个核多一个：Save the program below as seqlock.cpp. The record is eight 64-bit words, 64 bytes, and the writer sets all eight to the same new value each time, so a reader that sees two unequal words has read a torn copy. The seqlock and mutex methods are each measured with 1, 4 and 10 readers plus 1 writer; a third mode, nocheck, uses the same seqlock writer but readers that ignore the sequence number, to prove that the check is doing its job.     // seqlock.cpp: one writer updates a 64-byte record; R readers copy it. seqlock versus std::mutex
// usage: ./seqlock [period_ns]   one write every period_ns (0: the writer never pauses)
//        R = 1, 4, 10 readers; 5 runs of 0.5 s each, median
#include <algorithm>
#include <atomic>
#include <chrono>
#include <cstdint>
#include <cstdio>
#include <cstdlib>
#include <mutex>
#include <thread>
#include <vector>

using clk = std::chrono::steady_clock;
constexpr int WORDS = 8;                                   // 8 x 8 bytes = one 64-byte record

// ---- seqlock: even sequence = stable, odd = a write is in progress ----
struct alignas(128) SeqRecord {
  std::atomic<std::uint64_t> seq{0};
  std::atomic<std::uint64_t> w[WORDS] = {};                // relaxed atomics: racing reads are not UB
};
void seq_write(SeqRecord& r, std::uint64_t v) {
  std::uint64_t s = r.seq.load(std::memory_order_relaxed);
  r.seq.store(s + 1, std::memory_order_relaxed);           // odd: readers will retry
  std::atomic_thread_fence(std::memory_order_release);     // the odd seq is visible before any data
  for (auto& x : r.w) x.store(v, std::memory_order_relaxed);
  r.seq.store(s + 2, std::memory_order_release);           // even again; the data is visible before it
}
bool seq_read(SeqRecord& r, std::uint64_t out[WORDS], long& retries) {
  for (;;) {
    std::uint64_t s1 = r.seq.load(std::memory_order_acquire);
    if (s1 & 1) { ++retries; continue; }                   // writer inside
    for (int i = 0; i < WORDS; ++i) out[i] = r.w[i].load(std::memory_order_relaxed);
    std::atomic_thread_fence(std::memory_order_acquire);   // the data loads complete before the re-check
    if (r.seq.load(std::memory_order_relaxed) == s1) return true;
    ++retries;                                             // a write overlapped: throw the copy away
  }
}

// ---- mutex baseline: the same record as plain words under std::mutex ----
struct alignas(128) MutexRecord { std::mutex m; std::uint64_t w[WORDS] = {}; };
void mtx_write(MutexRecord& r, std::uint64_t v) { std::lock_guard g(r.m); for (auto& x : r.w) x = v; }
void mtx_read(MutexRecord& r, std::uint64_t out[WORDS]) { std::lock_guard g(r.m); for (int i = 0; i < WORDS; ++i) out[i] = r.w[i]; }

void nocheck_read(SeqRecord& r, std::uint64_t out[WORDS]) {   // the bug: copy without looking at seq
  for (int i = 0; i < WORDS; ++i) out[i] = r.w[i].load(std::memory_order_relaxed);
}

struct Result { double reads_per_s, writes_per_s, retries_per_read; long torn; };

long period_ns = 0;

enum Mode { MUTEX, SEQ, NOCHECK };

template <Mode M> Result run_once(int R, double seconds) {
  SeqRecord sr; MutexRecord mr;
  std::atomic<bool> stop{false};
  struct alignas(128) Count { long reads = 0, retries = 0, torn = 0; };
  std::vector<Count> cnt(R);
  long writes = 0;
  {
    std::vector<std::jthread> ts;
    ts.emplace_back([&] {                                  // the one writer
      std::uint64_t v = 0;
      auto next = clk::now();
      while (!stop.load(std::memory_order_relaxed)) {
        ++v; M == MUTEX ? mtx_write(mr, v) : seq_write(sr, v);
        next += std::chrono::nanoseconds(period_ns);       // pace by spinning on the clock, not by sleeping
        while (period_ns && clk::now() < next && !stop.load(std::memory_order_relaxed)) {}
      }
      writes = (long)v;
    });
    for (int t = 0; t < R; ++t)
      ts.emplace_back([&, t] {
        std::uint64_t out[WORDS]; Count c;
        while (!stop.load(std::memory_order_relaxed)) {
          if constexpr (M == SEQ) seq_read(sr, out, c.retries);
          else if constexpr (M == NOCHECK) nocheck_read(sr, out);
          else mtx_read(mr, out);
          ++c.reads;
          for (int i = 1; i < WORDS; ++i) if (out[i] != out[0]) { ++c.torn; break; }   // a mixed record
        }
        cnt[t] = c;
      });
    std::this_thread::sleep_for(std::chrono::duration<double>(seconds));
    stop = true;
  }
  long reads = 0, retries = 0, torn = 0;
  for (auto& c : cnt) { reads += c.reads; retries += c.retries; torn += c.torn; }
  return {reads / seconds, writes / seconds, reads ? double(retries) / reads : 0, torn};
}

template <Mode M> void bench(const char* name, int R) {
  run_once<M>(R, 0.1);                                   // warm-up
  std::vector<Result> v;
  for (int i = 0; i < 5; ++i) v.push_back(run_once<M>(R, 0.5));
  std::sort(v.begin(), v.end(), [](auto& a, auto& b) { return a.reads_per_s < b.reads_per_s; });
  const Result& m = v[2];
  double torn_pct = 100.0 * m.torn / (m.reads_per_s * 0.5);
  std::printf("%-8s %2d %11.1f %11.2f %10.3f %7.2f\n", name, R, m.reads_per_s / 1e6, m.writes_per_s / 1e6, m.retries_per_read, torn_pct);
}

自测

Self-check

1. Treiber 栈的 push 是「读 top、设 next、CAS，失败就重来」。它属于哪一类进度保证？

1. The Treiber stack’s push is “read top, set next, CAS, retry on failure”. Which progress guarantee does it give?

CAS 失败只可能是因为别的线程的 CAS 刚刚成功，所以系统整体一直前进，这是 lock-free；但没有任何东西保证某一个线程最终会赢，所以不是 wait-free。a 错在把单条指令的有界和整个循环的有界混为一谈：指令有界，重试次数无界。c 错在失败的线程并不等待谁，它立刻重读重试，任何线程停住都挡不住它。A CAS can fail only because another thread’s CAS has just succeeded, so the system as a whole keeps moving: that is lock-free. Nothing guarantees that a particular thread eventually wins, so it is not wait-free. a confuses a bounded instruction with a bounded loop: the instruction is bounded, the number of retries is not. c is wrong because the failing thread waits for nobody; it rereads and retries at once, and no stalled thread can hold it up.

2. Lab A 里不带计数的栈 100 次试验 100 次损坏，换成 16 字节的「指针 + 计数」后 0 次。真正起作用的是什么？

2. In Lab A the untagged stack corrupted in 100 of 100 trials and the 16-byte “pointer plus counter” version in 0. What actually made the difference?

ABA 的根源是 CAS 只比较地址；加上计数后，「这期间被改过」变成了值的一部分。a 错：两者都带 acquire（casa 的 a 和 caspa 的 a 意思相同），内存序没有变化，p 只表示一对寄存器。b 错：变慢可能让窗口更难碰到，但不可能把 100 次降到 0 次；而且只要窗口存在，正确性就不能靠运气。The root of ABA is that a CAS compares only the address; with a counter, “it changed in the meantime” becomes part of the value. a is wrong: both carry acquire (the a in casa and in caspa means the same thing), the ordering is unchanged, and the p only means a pair of registers. b is wrong: being slower might make the window harder to hit, but cannot take 100 failures to 0, and as long as the window exists correctness cannot rest on luck.

3. 一个真实的 Treiber 栈在 pop 成功后马上 delete 节点。为什么不安全？

3. A real Treiber stack calls delete on the node as soon as pop succeeds. Why is that unsafe?

pop 只保证这个节点已经不在栈里，不保证别的线程手里没有它的地址。延迟回收的三种机制回答的都是「什么时候没有人还可能拿着它」，而且不复用地址也顺带消除了 ABA。b 错：macOS 和 glibc 的 malloc 都是线程安全的。c 错：含原子成员的对象可以正常销毁，前提是没有人还在访问它，而这正是问题所在。Pop guarantees only that the node is no longer on the stack, not that no other thread holds its address. The three deferred-reclamation mechanisms all answer “when can nobody still hold it?”, and not reusing addresses removes ABA as a side effect. b is wrong: both macOS’s and glibc’s malloc are thread-safe. c is wrong: an object with atomic members can be destroyed normally, provided nobody is still accessing it, which is exactly the problem.

4. Lab B 里写者不停地写时，1 个 seqlock 读者每秒只完成 0.1–0.3 百万次读，1 个 mutex 读者是 14.6–16.4 百万次。主要原因是什么？

4. In Lab B, with the writer writing non-stop, one seqlock reader completes only 0.1–0.3 million reads per second and one mutex reader 14.6–16.4 million. What is the main reason?

输出里的 retry/read 是几千：每成功一次要扔掉几千次尝试。写者每微秒写一次时，同一个栅栏下读者每秒完成 5.2 亿到 8.5 亿次读，所以 a 不成立。c 正好说反了：seqlock 读者不拿任何锁、不写任何共享内存，这是它在读多时快的原因，也是写多时没人替它挡住写者的原因。The output shows a retry/read in the thousands: thousands of attempts thrown away per success. With one write per microsecond, the same fence lets a reader complete 500 to 850 million reads per second, so a does not hold. c is the reverse of the truth: a seqlock reader takes no lock and writes no shared memory, which is why it is fast when reads dominate, and also why nothing holds the writer back for it when writes dominate.
