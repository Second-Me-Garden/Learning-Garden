Phase 2 removed data races with locks and atomics, but left a lower-level question open: when, and in what order, does one thread see the values another thread wrote? The answer is not “at once, in program order”. This M5 is ARM64, whose memory ordering is weak, and the compiler reorders too. This phase first catches reordering in the act on the lab machine: two threads each write one variable and then read the other’s, and under relaxed order both read 0 in 2683 of 100 million trials. Then it covers how the C++20 memory model gives exact guarantees through happens-before and synchronizes-with, which instruction each memory order compiles to on the M5, and how that differs from x86 TSO. 核心概念

Core concepts

先别往下读，猜一猜：x、y 初始为 0，线程 A 执行 x = 1; r1 = y;，线程 B 执行 y = 1; r2 = x;。最后 (r1, r2) 可能是哪几种：(0, 1)、(1, 0)、(1, 1)、(0, 0)？把两个线程的语句交错起来，(0, 0) 不可能出现，可这台 M5 上它确实会出现。那么程序员到底能依赖什么：一个线程写下的值，另一个线程什么时候、以什么顺序看见，又要写什么才能把顺序要回来？

Before reading on, make a guess: x and y start at 0, thread A runs x = 1; r1 = y; and thread B runs y = 1; r2 = x;. Which values can (r1, r2) end up with: (0, 1), (1, 0), (1, 1), (0, 0)? Interleave the two threads’ statements and (0, 0) cannot happen, yet on this M5 it does. So what can a programmer actually rely on: when, and in what order, does one thread see the values another wrote, and what do you have to write to get the order back?

1. 顺序一致性，以及硬件为什么不给你

1. Sequential consistency, and why hardware does not give it to you

顺序一致性（sequential consistency，Lamport 1979）的意思是：所有线程的所有内存操作，可以排成一个全局的先后顺序，这个顺序里每个线程自己的操作保持程序顺序，每次读都读到这个顺序里它之前最后一次写。这是人脑默认的模型：把两个线程的语句交错起来，任何一种交错都可能，交错之外的结果都不可能。

Sequential consistency (Lamport, 1979) means that all memory operations of all threads can be arranged in one global order in which each thread’s own operations keep their program order and every read returns the last write before it in that order. It is the model the human mind assumes: interleave the two threads’ statements, any interleaving is possible, and no result outside the interleavings is.

看最小的反例，store buffering（SB），也是 Dekker 互斥算法的核心。x、y 初始为 0；线程 A 执行 x = 1; r1 = y;，线程 B 执行 y = 1; r2 = x;。按顺序一致性，无论怎么交错，总有一个写先发生，所以 r1 == 0 && r2 == 0 不可能。Lab A 在这台 M5 上数到了它：relaxed 原子操作下，1 亿次试验里出现 2683 次。

Take the smallest counterexample, store buffering (SB), which is also the heart of Dekker’s mutual-exclusion algorithm. x and y start at 0; thread A runs x = 1; r1 = y; and thread B runs y = 1; r2 = x;. Under sequential consistency one of the writes always comes first, whatever the interleaving, so r1 == 0 && r2 == 0 is impossible. Lab A counts it on this M5: with relaxed atomics it happened 2683 times in 100 million trials.

  • 原因是 store buffer。一次写如果要等 cache line 被拿到独占状态才能继续，核就会停很多个周期。所以每个核把写先放进自己的 store buffer，接着执行后面的读；本核的读能从自己的 buffer 里拿到刚写的值（store forwarding），别的核却要等 buffer 排空到 cache 才看得见。于是 A 的读 y 可以在 A 的写 x 对 B 可见之前完成，B 也一样，两边都读到 0。这是解释用的模型；M5 的微架构细节 Apple 没有公开。
  • The cause is the store buffer. If a write had to wait until its cache line was held exclusively, the core would stall for many cycles. So each core puts writes into its own store buffer and goes on executing the reads that follow; the core’s own reads can pick up the value it just wrote from its buffer (store forwarding), but other cores see it only once the buffer drains into the cache. So A’s read of y can complete before A’s write of x is visible to B, and the same holds for B, and both read 0. This is an explanatory model; Apple has not published the M5 microarchitecture.
  • cache 本身是一致的。重排不是因为「cache 不一致」：同一个地址上，所有核对写的先后看法一致（coherence）。重排说的是不同地址之间的先后：A 写 x、读 y，两个地址，两件事的顺序被别的核看反了。
  • The caches themselves are coherent. Reordering does not mean the caches disagree: for any single address, all cores agree on the order of its writes (coherence). Reordering is about order between different addresses: A writes x and reads y, two addresses, and another core sees those two events in the opposite order.
  • x86 是 TSO。x86-64 的内存序叫 Total Store Order：读不和读重排，写不和写重排，写不和更早的读重排；唯一允许的是「较晚的读越过较早的、写到不同地址的写」，也就是 store buffer 造成的那一种（Intel SDM 第 3 卷 Memory Ordering 一节；Sewell 等人的 x86-TSO 论文）。所以 SB 在 x86 上也会失败，但下面的 message passing 不会。
  • x86 is TSO. The x86-64 memory order is called Total Store Order: reads are not reordered with reads, writes are not reordered with writes, and writes are not reordered with earlier reads; the one reordering allowed is a later read passing an earlier write to a different address, exactly the store-buffer case (the Memory Ordering section of Intel SDM volume 3; the x86-TSO paper by Sewell et al.). So SB fails on x86 too, but the message passing below does not.
  • ARM64 是弱序的。对不同地址的普通读写，在没有依赖、没有屏障的情况下，读读、读写、写读、写写四种重排都允许（Arm ARM 的 AArch64 内存模型一章）。Lab A 的 message passing 实验在 M5 上抓到了写写或读读重排：读者看见了旗子，却读到了旧数据，2000 万次里 10 到 58 次。ARMv8 自 2017 年前后的一次架构修订起（Pulte 等，POPL 2018）是 other-multi-copy-atomic 的：一个写一旦被另一个核看见，就被所有其他核看见。
  • ARM64 is weakly ordered. For plain reads and writes to different addresses, with no dependency and no barrier, all four reorderings are allowed: read-read, read-write, write-read and write-write (the AArch64 memory model chapter of the Arm ARM). The message-passing experiment in Lab A catches a write-write or read-read reordering on the M5: the reader saw the flag but read stale data, 10 to 58 times in 20 million trials. Since a revision of the architecture around 2017 (Pulte et al., POPL 2018), ARMv8 is other-multi-copy atomic: once one other core sees a write, all other cores see it.

To answer the opening question, first enumerate under sequential consistency, then walk the store buffer (the same scene as diagram (a) below). Call the four operations a1 x = 1, a2 r1 = y, b1 y = 1 and b2 r2 = x; with 1 before 2 inside each thread there are 4! / (2! × 2!) = 6 interleavings:

a1 a2 b1 b2   → r1 = 0, r2 = 1
a1 b1 a2 b2   → r1 = 1, r2 = 1
a1 b1 b2 a2   → r1 = 1, r2 = 1
b1 a1 a2 b2   → r1 = 1, r2 = 1
b1 a1 b2 a2   → r1 = 1, r2 = 1
b1 b2 a1 a2   → r1 = 1, r2 = 0
(0, 0): none of the 6

  1. 顺序一致性下，第一个执行的操作必是某个写（a1 或 b1），排在它后面的另一线程的读就一定看见 1，所以 6 种交错里没有 (0, 0)：(1, 1) 4 种，(0, 1) 和 (1, 0) 各 1 种。
  2. 在 M5 上，a1 编成 str，x = 1 进了 A 的 store buffer，A 不等它对外可见，接着执行 a2；b1 同样停在 B 的 buffer 里。
  3. a2 的 ldr 从内存读到 y = 0，b2 读到 x = 0。两个 buffer 随后排空，内存是 x = y = 1，但两次读已经返回了 0。
  4. 汇编里 str 在 ldr 之前，编译器没有改顺序，所以那 2683 次来自硬件。换成 seq_cst（stlr + ldar）或在中间加 dmb ish 后，1 亿次里是 0 次；acquire/release 仍有 354 次，原因见概念 4。
  1. Under sequential consistency the first operation executed must be a write (a1 or b1), and the other thread’s read, which comes after it, then sees 1, so none of the 6 interleavings gives (0, 0): 4 give (1, 1), and (0, 1) and (1, 0) one each.
  2. On the M5, a1 compiles to str: x = 1 goes into A’s store buffer, and A goes on to a2 without waiting for it to become visible; b1 likewise sits in B’s buffer.
  3. The ldr of a2 reads y = 0 from memory and b2 reads x = 0. Both buffers then drain and memory holds x = y = 1, but both reads have already returned 0.
  4. In the assembly str comes before ldr; the compiler kept the order, so the 2683 come from the hardware. With seq_cst (stlr + ldar) or a dmb ish in between it is 0 in 100 million; acquire/release still gives 354, for the reason in concept 4.

2. 编译器也会重排

2. The compiler reorders too

硬件之前还有一层。C++ 编译器只承诺单线程下「看起来一样」（as-if 规则），而且假定程序没有数据竞争：两个线程不加同步地访问同一个普通变量、其中一个是写，就是未定义行为。在这个前提下，编译器可以把普通变量的读写重排、合并、提到循环外，或者干脆删掉。经典的例子是 while (!done) {}：done 是普通 bool 时，编译器可以只读一次，循环永不结束。

There is one more layer before the hardware. A C++ compiler promises only that a single thread behaves “as if” it ran as written (the as-if rule), and it assumes the program has no data race: two threads accessing the same ordinary variable without synchronization, at least one of them writing, is undefined behaviour. Under that assumption the compiler may reorder, merge, hoist out of a loop or simply delete reads and writes of ordinary variables. The classic example is while (!done) {}: with done an ordinary bool, the compiler may read it once and loop forever.

  • 原子变量的访问不会被删掉或合并成「只读一次」，内存序还约束了它周围的普通访问能往哪边移：acquire 之后的访问不能移到它前面，release 之前的访问不能移到它后面。relaxed 只保证原子性，不约束周围。
  • Accesses to atomics are not deleted or merged into a single read, and the memory order also limits which way the ordinary accesses around them may move: accesses after an acquire may not move before it, and accesses before a release may not move after it. Relaxed guarantees only atomicity and constrains nothing around it.
  • 同一条 C++ 语句，在不同机器上要的指令不同，但对编译器的约束一样。Lab B 里 atomic_thread_fence(acquire) 和 (release) 在 x86-64 上不生成任何指令（TSO 已经给了这两种顺序），可它们仍然禁止编译器跨过它们重排。只想约束编译器、不要硬件屏障时，标准写法是 std::atomic_signal_fence；GCC 和 clang 的老写法是 asm volatile("" ::: "memory")，Linux 内核的 barrier() 就是它。
  • One C++ statement needs different instructions on different machines but constrains the compiler identically. In Lab B, atomic_thread_fence(acquire) and (release) generate no instruction at all on x86-64 (TSO already gives those orders), yet they still forbid the compiler from reordering across them. To constrain only the compiler, without a hardware barrier, the standard way is std::atomic_signal_fence; the older GCC and clang way is asm volatile("" ::: "memory"), which is what the Linux kernel’s barrier() is.
  • 怎样分清是编译器还是硬件。看汇编。Lab A 里 relaxed 版本编出来是 str 在前、ldr 在后，程序顺序原样保留，所以那 2683 次失败只能是硬件重排的。
  • How to tell the compiler from the hardware. Read the assembly. In Lab A the relaxed version compiles to str first and ldr second, program order intact, so the 2683 failures can only be the hardware reordering.

3. C++20 内存模型：happens-before 与 synchronizes-with

3. The C++20 memory model: happens-before and synchronizes-with

C++11 起，标准不再说「哪条指令先执行」，而是定义几种关系，再用它们规定每次读可以读到哪些写。下面的说法照标准的 [intro.races] 和 [atomics.order] 两节（C++20；2026-10-31 对照了 eel.is 上的当前草案，下列条文与 C++20 一致；草案已把 memory_order::consume 移到附录 D 并弃用，语义与 acquire 相同（[depr.atomics.order]））：

Since C++11 the standard no longer says which instruction executes first; it defines a few relations and uses them to state which writes each read may see. What follows follows the standard’s sections [intro.races] and [atomics.order] (C++20; checked on 2026-10-31 against the current draft at eel.is, where the clauses below match C++20 and memory_order::consume has moved to Annex D as deprecated, with the same meaning as acquire ([depr.atomics.order])):

  • sequenced-before：同一个线程里，按语言的求值顺序规则，一个求值在另一个之前。粗略地说就是程序顺序。
  • sequenced-before: within one thread, one evaluation comes before another by the language’s evaluation-order rules. Roughly, program order.
  • modification order：每个原子对象上所有的修改排成一个全序，所有线程都同意这个顺序。四条 coherence 规则（读读、读写、写读、写写）保证一个线程不会在同一个对象上先看见新值、再看见旧值。这是 relaxed 也有的保证。
  • Modification order: all modifications of each atomic object form one total order that every thread agrees on. Four coherence rules (read-read, read-write, write-read, write-write) make sure a thread never sees a newer value of one object and then an older one. Relaxed has this guarantee too.
  • release sequence（C++20 的定义）：以原子对象 M 上的一次 release 操作 A 为首，在 M 的 modification order 里紧接着 A 的、最长的一段连续修改，其中 A 之后的每一个都是原子的读-改-写（RMW）操作。C++20 去掉了 C++11 里「同一线程的后续普通写也算」的那一条（P0982R1）。
  • Release sequence (the C++20 definition): headed by a release operation A on atomic object M, it is the maximal contiguous run of modifications in M’s modification order that starts with A and in which every modification after A is an atomic read-modify-write (RMW) operation. C++20 dropped the C++11 clause that also counted later plain stores by the same thread (P0982R1).
  • synchronizes-with：对 M 做 release 操作的原子操作 A，与对 M 做 acquire 操作、并且读到「以 A 为首的 release sequence 中任一修改」所写的值的原子操作 B 同步。要点是 B 必须读到那个值；acquire 读到更早的值，就什么也不同步。
  • synchronizes-with: an atomic operation A that performs a release on M synchronizes with an atomic operation B that performs an acquire on M and takes its value from any modification in the release sequence headed by A. The point is that B must read that value; an acquire that reads an earlier value synchronizes with nothing.
  • happens-before：A 在 B 之前发生，当且仅当 A sequenced-before B，或 A synchronizes-with B，或存在 X 使 A happens-before X 且 X happens-before B。也就是这两种关系的传递闭包（不用 consume 时，C++20 的定义化简到这里；当前草案就是这样写的）。另外 std::thread 的创建、join，mutex 的 unlock 和下一次 lock，标准都规定为 synchronizes-with。
  • happens-before: A happens before B if and only if A is sequenced before B, or A synchronizes with B, or there is an X such that A happens before X and X happens before B. In other words, the transitive closure of those two relations (with no consume operations, C++20’s definition reduces to this, and the current draft states it this way). The standard also makes thread creation, join, and a mutex unlock followed by the next lock synchronizes-with edges.
  • 数据竞争：两个线程里的两个冲突访问（同一位置，至少一个是写），至少一个不是原子的，并且谁也不 happens-before 谁。有数据竞争的程序是未定义行为。反过来，没有数据竞争时，普通变量的读一定读到 happens-before 它的最后一次写。
  • Data race: two conflicting accesses (same location, at least one a write) in different threads, at least one not atomic, and neither happens before the other. A program with a data race has undefined behaviour. Conversely, without data races, a read of an ordinary variable always sees the last write that happens before it.

用这些关系推一遍 message passing（与下方图解 (b) 相同的数字）：data 是普通 int，ready 是 std::atomic<int>，都从 0 开始。写者执行 W1、W2，读者执行 R1、R2：

Derive message passing from these relations (the same numbers as diagram (b) below): data is a plain int, ready is a std::atomic<int>, and both start at 0. The writer runs W1 and W2, the reader R1 and R2:

// writer                                   // reader
data = 42;                          // W1   while (ready.load(std::memory_order_acquire) != 1) {}  // R1
ready.store(1, std::memory_order_release);  // W2   int r = data;                               // R2

W1 sequenced-before W2      (program order, writer)
W2 synchronizes-with R1     (R1 is acquire and reads the 1 that the release W2 wrote)
R1 sequenced-before R2      (program order, reader)
W1 happens-before R2        (transitive closure)  → R2 must read 42, and there is no data race on data
  1. W1 sequenced-before W2，R1 sequenced-before R2：这两条只是各自线程的程序顺序。
  2. R1 是 acquire 读，并且读到了 release 写 W2 写下的 1，所以 W2 synchronizes-with R1。循环里前几次读到 0 的那些 R1 什么也不同步，只有读到 1 的那一次算数。
  3. 传递得到 W1 happens-before R2。对 data 的两次访问有了先后，不构成数据竞争，R2 读到的是 happens-before 它的最后一次写，也就是 42。
  4. 两边都改成 relaxed，第 2 条边就消失了：R2 和 W1 之间没有 happens-before，data 上有数据竞争。Lab A 的 mp.cpp 为了能数这种结果，把 data 也写成 relaxed 原子变量（写入值是 1 而不是 42）：M5 上每次 2000 万轮的运行里出现 10 到 58 次 ready = 1 却读到 data = 0，release/acquire 下 0 次。
  1. W1 is sequenced before W2 and R1 before R2: these two are just each thread’s program order.
  2. R1 is an acquire load and reads the 1 that the release store W2 wrote, so W2 synchronizes with R1. The earlier passes of the loop, whose R1 read 0, synchronize with nothing; only the one that reads 1 counts.
  3. By transitivity W1 happens before R2. The two accesses to data are now ordered, there is no data race, and R2 reads the last write that happens before it, which is 42.
  4. Make both sides relaxed and the second edge disappears: nothing orders W1 before R2, and data has a data race. To count this outcome, Lab A’s mp.cpp makes data a relaxed atomic as well (and writes 1 instead of 42): on the M5, in each run of 20 million trials, 10 to 58 times the reader sees ready = 1 and still reads data = 0, and 0 times under release and acquire.

release sequence 的实际用处是引用计数。线程 T1 用 release 写入 count = 2，之后 T2、T3 各做一次 fetch_sub（RMW）。T3 的 acquire 读到的是 T2 写的值，但因为 T2 的 RMW 在以 T1 的写为首的 release sequence 里，T3 仍然与 T1 同步，T1 在写之前做的初始化对 T3 可见。

The practical use of the release sequence is reference counting. Thread T1 writes count = 2 with release, after which T2 and T3 each do one fetch_sub (an RMW). T3’s acquire reads the value T2 wrote, but since T2’s RMW lies in the release sequence headed by T1’s write, T3 still synchronizes with T1, and the initialization T1 did before its write is visible to T3.

4. 五种内存序：relaxed、acquire、release、acq_rel、seq_cst

4. The five memory orders: relaxed, acquire, release, acq_rel, seq_cst

  • relaxed：只有原子性和每个对象自己的 modification order，不建立任何 synchronizes-with。适合只关心最终值的计数器（Lab B 的 fetch_add）和统计量。
  • relaxed: atomicity and each object’s own modification order, nothing more; it creates no synchronizes-with. Right for counters where only the final value matters (the fetch_add of Lab B) and for statistics.
  • release（用于写）：本线程在它之前的所有读写，不会被挪到它之后。配对的 acquire 读到它写的值时，这些读写对读者可见。
  • release (for stores): none of this thread’s reads and writes before it are moved after it. When a paired acquire reads the value it wrote, those reads and writes become visible to the reader.
  • acquire（用于读）：本线程在它之后的所有读写，不会被挪到它之前。和 release 配成 message passing：写者先写数据再 release 写旗子，读者 acquire 读到旗子后，一定能读到数据（图解 (b)）。
  • acquire (for loads): none of this thread’s reads and writes after it are moved before it. Paired with release it gives message passing: the writer writes the data and then the flag with release, and once the reader’s acquire reads the flag it is guaranteed to read the data (diagram (b)).
  • acq_rel（用于 RMW）：同时是 acquire 和 release。一次 fetch_add 或 compare-exchange 既接收前一个 release 发布的内容，又把自己之前的写发布出去。
  • acq_rel (for RMWs): both acquire and release. One fetch_add or compare-exchange both receives what the previous release published and publishes its own earlier writes.
  • seq_cst（默认）：在 acquire/release 之上，所有 seq_cst 操作（包括 seq_cst 栅栏）还处在一个单一全序 S 里，S 与 strongly happens-before 一致、与每个对象的 modification order 一致（[atomics.order]）。正是这个 S 禁止了 SB 的结果：A 的写和 B 的写在 S 里总有先后，排在后面的那个线程的读一定看见前一个写。标准的推论是：只用 mutex 和 seq_cst 原子、没有数据竞争的程序，行为就像顺序一致的交错。
  • seq_cst (the default): on top of acquire and release, all seq_cst operations (seq_cst fences included) also lie in one single total order S that is consistent with strongly happens-before and with each object’s modification order ([atomics.order]). That S is exactly what forbids the SB outcome: A’s write and B’s write always come in some order in S, and the read of whichever thread comes later must see the earlier write. The standard’s corollary: a program free of data races that uses only mutexes and seq_cst atomics behaves like a sequentially consistent interleaving.

为什么 acquire/release 修不好 SB 和 Dekker？release 只管「我之前的不往后挪」，acquire 只管「我之后的不往前挪」，两者都不禁止「一次 release 写之后的一次 acquire 读」被提到写前面，因为它们是不同的变量，谁也没读到谁写的值，没有 synchronizes-with。Lab A 实测：acquire/release 的 SB 在 1 亿次里失败 354 次，Dekker 在 5 次运行里有 2 次丢了计数。memory_order_consume 原本想用数据依赖代替 acquire，没有编译器按设计实现它（clang 把它当 acquire），C++17 起不鼓励使用，本页不讲。

Why can acquire and release not fix SB and Dekker? Release only says nothing before me moves after me, and acquire only says nothing after me moves before me; neither forbids an acquire load that follows a release store from being hoisted above it, because they are different variables, neither read the other’s value, and there is no synchronizes-with. Measured in Lab A: acquire/release SB failed 354 times in 100 million trials, and Dekker lost counts in 2 of 5 runs. memory_order_consume was meant to replace acquire with data dependencies; no compiler implemented it as designed (clang treats it as acquire), its use has been discouraged since C++17, and this page leaves it out.

5. 栅栏

5. Fences

std::atomic_thread_fence(order) 不是对某个变量的操作，而是把内存序挂在一个程序点上，和它前后的 relaxed 操作配合（[atomics.fences]）：

std::atomic_thread_fence(order) is not an operation on any variable; it attaches a memory order to a point in the program and works together with the relaxed operations around it ([atomics.fences]):

  • release 栅栏 F，后接一次原子写 X：如果某个 acquire 操作读到了 X（或 X 所在 release sequence 里的值），F 就与那个 acquire 同步。效果像把 X 换成 release 写，但一个栅栏可以覆盖之后的多次写。
  • A release fence F followed by an atomic store X: if some acquire operation reads X (or a value in the release sequence X heads), F synchronizes with that acquire. The effect is like making X a release store, but one fence can cover several later stores.
  • 一次原子读 Y，后接 acquire 栅栏 F：如果 Y 读到了某个 release 写的值，那个 release 就与 F 同步。常见写法是循环里用 relaxed 读旗子，跳出循环后放一个 acquire 栅栏，只在最后付一次代价。
  • An atomic load Y followed by an acquire fence F: if Y reads the value of some release store, that release synchronizes with F. The common pattern is to read a flag with relaxed inside a loop and put one acquire fence after the loop, paying the cost only once.
  • seq_cst 栅栏加入全序 S。Lab A 的 SB 和 Dekker 在写和读之间各放一个 atomic_thread_fence(seq_cst)，变量仍用 relaxed（Dekker 用 acquire/release），失败都归零。在 M5 上它编成一条 dmb ish，在 x86-64 上是 lock orl $0, -64(%rsp)（Apple clang 21 的选择，不是 mfence）。
  • A seq_cst fence joins the total order S. The SB and Dekker experiments of Lab A place one atomic_thread_fence(seq_cst) between the write and the read while keeping the variables relaxed (acquire/release for Dekker), and the failures drop to zero. On the M5 it compiles to one dmb ish; on x86-64 it is lock orl $0, -64(%rsp) (Apple clang 21’s choice, not mfence).

Lab B compiles each memory order into a function of its own and generates assembly with Apple clang 21 for this machine (the default target), for ARMv8.0 (-mcpu=cyclone, the Apple A7, no LSE) and for x86-64 (-arch x86_64). The pattern that comes out:

  • ARM64 的 acquire/release 是指令本身的属性，不是额外的屏障。stlr（store-release）和 ldar（load-acquire）自带顺序。ldar 是 RCsc 的：它不会越过程序顺序更早的 stlr，所以 seq_cst 的读和写只要 ldar + stlr，不需要 dmb。
  • On ARM64, acquire and release are properties of the instructions themselves, not extra barriers. stlr (store-release) and ldar (load-acquire) carry their ordering. ldar is RCsc: it does not pass an earlier stlr in program order, so seq_cst loads and stores need only ldar + stlr, with no dmb.
  • 本机的 acquire 读是 ldapr，不是 ldar。ldapr（ARMv8.3 的 RCpc load-acquire）去掉了「不越过更早的 stlr」这一条，更便宜，而 C++ 的 acquire 本来也不要求这一条。这正是 Lab A 里 acquire/release 的 SB 能失败的硬件原因：stlr x 之后的 ldapr y 可以先完成。为 ARMv8.0 编译时没有 ldapr，acquire 也用 ldar。
  • An acquire load on this machine is ldapr, not ldar. ldapr (the RCpc load-acquire of ARMv8.3) drops the do-not-pass-an-earlier-stlr rule, which makes it cheaper, and C++ acquire never required that rule. That is the hardware reason the acquire/release SB can fail in Lab A: an ldapr y after an stlr x may complete first. When compiling for ARMv8.0 there is no ldapr, and acquire uses ldar too.
  • RMW：本机用 LSE 单条指令，ARMv8.0 用 LL/SC 循环。本机 fetch_add 是 ldadd（relaxed）或 ldaddal（acq_rel、seq_cst），compare-exchange 是 casal，atomic_flag::test_and_set 是 swpab。-mcpu=cyclone 时同样的代码变成 ldaxr … stlxr 加 cbnz 重试的循环：独占地读，再条件地写，期间别人碰过这条 cache line 就重来。
  • RMWs: single LSE instructions here, LL/SC loops on ARMv8.0. Here fetch_add is ldadd (relaxed) or ldaddal (acq_rel and seq_cst), compare-exchange is casal, and atomic_flag::test_and_set is swpab. With -mcpu=cyclone the same code becomes an ldaxr … stlxr loop with a cbnz retry: load exclusively, store conditionally, and start over if anyone touched the cache line in between.
  • x86-64 上几乎都是 mov。relaxed、acquire、seq_cst 的读，relaxed 和 release 的写，全是一条普通 movl：TSO 已经给了这些顺序。只有 seq_cst 写要 xchgl（隐含 lock，是全屏障，堵住 TSO 唯一允许的 store→load 重排），所有 RMW 都是带 lock 前缀的指令。所以「x86 上 relaxed 和 seq_cst 一样快」的直觉只对读成立。
  • On x86-64 nearly everything is a mov. Relaxed, acquire and seq_cst loads, and relaxed and release stores, are all one plain movl: TSO already provides those orders. Only a seq_cst store needs xchgl (implicitly locked, a full barrier that closes the one store-to-load reordering TSO allows), and every RMW is a lock-prefixed instruction. So the intuition that relaxed and seq_cst are equally fast on x86 holds only for loads.
  • 内核里是同一套指令。Linux arm64 的 smp_load_acquire/smp_store_release 编成 ldar/stlr，smp_mb() 是 dmb ish，并在启动时检测 LSE 后把 atomic_* 打补丁成 LSE 版本（内核专题 Phase 3 的「原子操作与内存序」）。
  • The kernel uses the same instructions. Linux arm64’s smp_load_acquire/smp_store_release compile to ldar/stlr, smp_mb() is dmb ish, and at boot the kernel detects LSE and patches atomic_* into the LSE versions (the concept atomic operations and memory ordering in kernel topic Phase 3).

7. compare-exchange 与 ABA 问题

7. Compare-exchange and the ABA problem

compare_exchange_strong(expected, desired) 原子地做一件事：如果当前值等于 expected，就写入 desired 并返回 true；否则把当前值写回 expected 并返回 false。几乎所有无锁算法都是一个「读旧值、算新值、CAS 提交、失败就重试」的循环。compare_exchange_weak 允许在值相等时也失败（spurious failure），因为在 LL/SC 机器上 stlxr 可能因为别的原因失败；它本来就放在重试循环里时，用 weak 可以省掉内层循环。本机有 casal，strong 版本就是一条指令加比较。

compare_exchange_strong(expected, desired) does one thing atomically: if the current value equals expected, it writes desired and returns true; otherwise it writes the current value back into expected and returns false. Almost every lock-free algorithm is a loop of read the old value, compute the new one, commit with CAS, retry on failure. compare_exchange_weak may fail even when the values are equal (a spurious failure), because on an LL/SC machine stlxr can fail for other reasons; when the call already sits in a retry loop, weak saves an inner loop. This machine has casal, so the strong version is one instruction plus a compare.

ABA：CAS 只比较值，不知道值在中间变过。无锁栈的 pop 读到栈顶 A 和 A 的 next 为 B，准备 CAS(top, A → B)；这时另一个线程 pop 了 A、pop 了 B、又把 A push 回去（同一个地址被重用）。top 又是 A，CAS 成功，top 被设成已经不在栈里的 B。修法是让「值」包含版本：带计数的指针（tagged pointer，用 128 位的 CAS 或指针的空闲高位），或者保证 A 在还有人可能持有它时不被重用（hazard pointer、epoch、RCU）。这些是 Phase 4 的内容，Lab A 会在那里让 ABA 真的发生：100 次试验里 100 次损坏。

ABA: CAS compares only the value and cannot tell that it changed in between. A lock-free stack’s pop reads the top A and A’s next, B, and prepares CAS(top, A → B); meanwhile another thread pops A, pops B and pushes A back (the same address reused). top is A again, the CAS succeeds, and top is set to B, which is no longer on the stack. The fixes give the value a version: a tagged pointer (with a 128-bit CAS or the spare high bits of a pointer), or a guarantee that A is not reused while anyone might still hold it (hazard pointers, epochs, RCU). Those are Phase 4, whose Lab A makes ABA actually happen: it corrupted the stack in 100 of 100 trials.

常见误解

Common misconceptions

  • 误解：更强的内存序让写「更快」被别的线程看见。→ 实际：内存序只约束先后，不约束快慢；它规定的是读到某个值之后还能推出什么（Bos 第 3 章 Common Misconceptions 的第一条）。
  • 误解：x86 不怎么重排，在 x86 上就不用管内存序。→ 实际：TSO 仍允许 store→load 重排，SB 在 x86 上照样失败，而且编译器的重排与机器无关。
  • 误解：两个线程互相通知时 acquire/release 总是够的。→ 实际：SB 和 Dekker 里没有哪次 acquire 读到对方 release 写的值，Lab A 中 acquire/release 的 SB 在 1 亿次里失败 354 次，要用 seq_cst 或 seq_cst 栅栏。
  • Myth: a stronger memory order makes a write visible to other threads “sooner”. → Fact: memory order constrains order, not speed; it says what else you may conclude once a read has seen a value (the first item of Common Misconceptions in chapter 3 of Bos).
  • Myth: x86 hardly reorders, so on x86 memory order does not matter. → Fact: TSO still allows store-to-load reordering, SB fails on x86 too, and compiler reordering does not depend on the machine at all.
  • Myth: acquire and release are always enough when two threads signal each other. → Fact: in SB and Dekker no acquire reads the value the other side’s release wrote, so in Lab A the acquire/release SB failed 354 times in 100 million; you need seq_cst or a seq_cst fence.

The first version used a two-thread barrier per round and saw 0 in a million trials under relaxed: the barrier releases the two threads a cache miss apart, and the first one’s write has long drained by then.     // sb.cpp: store buffering（Dekker 算法的核心）。线程 A：x = 1; r1 = y。线程 B：y = 1; r2 = x。
// 主线程当裁判：放行一轮，等两边都做完，检查 r1、r2，清零，再放行下一轮。
#include <atomic>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <thread>

struct alignas(128) Slot { std::atomic<int> v{0}; };   // 每个变量独占一条 128 字节 cache line
Slot x, y, go, done;
int r1, r2;

enum Mode { RELAXED, ACQ_REL, SEQ_CST, FENCE };

template <Mode M>
static int side(std::atomic<int> &mine, std::atomic<int> &other) {
    if constexpr (M == RELAXED) {
        mine.store(1, std::memory_order_relaxed);
        return other.load(std::memory_order_relaxed);
    } else if constexpr (M == ACQ_REL) {
        mine.store(1, std::memory_order_release);
        return other.load(std::memory_order_acquire);
    } else if constexpr (M == SEQ_CST) {
        mine.store(1, std::memory_order_seq_cst);
        return other.load(std::memory_order_seq_cst);
    } else {
        mine.store(1, std::memory_order_relaxed);
        std::atomic_thread_fence(std::memory_order_seq_cst);
        return other.load(std::memory_order_relaxed);
    }
}

template <Mode M>
static long run(long n) {
    auto worker = [n](std::atomic<int> &mine, std::atomic<int> &other, int &r) {
        for (int i = 1; i <= n; ++i) {
            while (go.v.load(std::memory_order_acquire) != i) { }   // 两个线程等同一个旗子，几乎同时出发
            r = side<M>(mine, other);
            done.v.fetch_add(1, std::memory_order_release);
        }
    };
    long both_zero = 0;
    std::jthread a(worker, std::ref(x.v), std::ref(y.v), std::ref(r1));
    std::jthread b(worker, std::ref(y.v), std::ref(x.v), std::ref(r2));
    for (int i = 1; i <= n; ++i) {
        go.v.store(i, std::memory_order_release);                  // 放行第 i 轮
        while (done.v.load(std::memory_order_acquire) != 2) { }    // 等两边都做完
        if (r1 == 0 && r2 == 0) ++both_zero;                       // 顺序一致性下不可能
        done.v.store(0, std::memory_order_relaxed);
        x.v.store(0, std::memory_order_relaxed);
        y.v.store(0, std::memory_order_relaxed);
    }
    return both_zero;
}

    const char *m = argc > 1 ? argv[1] : "relaxed";

           : !strcmp(m, "acq_rel") ? run<ACQ_REL>(n)
           : !strcmp(m, "seq_cst") ? run<SEQ_CST>(n)
           :                         run<FENCE>(n);

}

  5. Dekker 互斥算法。它靠「先立自己的旗、再看对方的旗」保证两个线程不同时进临界区，正是 SB 的形状。临界区里故意用 relaxed 的读、加一、写，而不用 fetch_add，这样互斥一旦失效就会丢计数：Dekker’s mutual-exclusion algorithm. It keeps two threads out of the critical section together by raising one’s own flag and then checking the other’s, exactly the SB shape. The critical section deliberately does a relaxed read, add one and write instead of fetch_add, so any failure of mutual exclusion loses counts:
    // dekker.cpp: Dekker 互斥算法保护一个计数器。两个线程各进临界区 N 次，每次把计数器读出、加 1、写回。
// 互斥成立时结果是 2N；少了多少，就是两个线程同时进过临界区多少次（至少）。
#include <atomic>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <thread>

struct alignas(128) Slot { std::atomic<int> v{0}; };
Slot flag[2], turn, counter;

enum Mode { RELAXED, ACQ_REL, ACQ_REL_FENCE, SEQ_CST };

template <Mode M> constexpr std::memory_order LD =
    M == RELAXED ? std::memory_order_relaxed : M == SEQ_CST ? std::memory_order_seq_cst : std::memory_order_acquire;
template <Mode M> constexpr std::memory_order ST =
    M == RELAXED ? std::memory_order_relaxed : M == SEQ_CST ? std::memory_order_seq_cst : std::memory_order_release;

template <Mode M>
static void lock(int i) {
    int j = 1 - i;
    flag[i].v.store(1, ST<M>);                          // 我想进
    if constexpr (M == ACQ_REL_FENCE) std::atomic_thread_fence(std::memory_order_seq_cst);
    while (flag[j].v.load(LD<M>)) {                     // 对方也想进？
        if (turn.v.load(LD<M>) != i) {                  // 不该我：先退让
            flag[i].v.store(0, ST<M>);
            while (turn.v.load(LD<M>) != i) { }
            flag[i].v.store(1, ST<M>);
            if constexpr (M == ACQ_REL_FENCE) std::atomic_thread_fence(std::memory_order_seq_cst);
        }
    }
}

template <Mode M>
static void unlock(int i) {
    turn.v.store(1 - i, ST<M>);
    flag[i].v.store(0, ST<M>);
}

template <Mode M>
static long run(int n) {
    auto body = [n](int i) {
        for (int k = 0; k < n; ++k) {
            lock<M>(i);
            int c = counter.v.load(std::memory_order_relaxed);   // 临界区：故意不用 fetch_add
            counter.v.store(c + 1, std::memory_order_relaxed);
            unlock<M>(i);
        }
    };
    { std::jthread a(body, 0), b(body, 1); }
    return 2L * n - counter.v.load();
}

            while (go.v.load(std::memory_order_acquire) != i) { }
            data.v.store(1, std::memory_order_relaxed);

// 每个配置先预热 2 次，再测 7 次，报每次加 1 的中位数耗时。
#include <algorithm>
#include <atomic>
#include <chrono>
#include <cstdio>
#include <cstring>
#include <thread>
#include <vector>

constexpr long N = 1'000'000;
struct alignas(128) { std::atomic<long> v{0}; } counter;
struct alignas(128) { long v = 0; } plain;          // 只在自旋锁里面读写
struct alignas(128) { std::atomic_flag f; } spin;

void lock_tas()  { while (spin.f.test_and_set(std::memory_order_acquire)) { } }
void lock_ttas() {
    while (spin.f.test_and_set(std::memory_order_acquire))
        while (spin.f.test(std::memory_order_relaxed)) { }   // 先只读地等，锁放开了再抢
}
void unlock()    { spin.f.clear(std::memory_order_release); }

template <class F>
double ns_per_op(int T, F body) {
    auto t0 = std::chrono::steady_clock::now();
    { std::vector<std::jthread> ts; for (int t = 0; t < T; ++t) ts.emplace_back(body); }
    double ns = std::chrono::duration<double, std::nano>(std::chrono::steady_clock::now() - t0).count();
    return ns / (double(T) * N);
}

int main(int argc, char **argv) {
    const char *m = argc > 1 ? argv[1] : "relaxed";
    for (int T : {1, 4, 10}) {
        std::vector<double> r;
        long expect = 0, got = 0;
        for (int rep = 0; rep < 9; ++rep) {
            counter.v.store(0); plain.v = 0;
            double ns;
            if (!strcmp(m, "relaxed"))
                ns = ns_per_op(T, [] { for (long i = 0; i < N; ++i) counter.v.fetch_add(1, std::memory_order_relaxed); });
            else if (!strcmp(m, "seq_cst"))
                ns = ns_per_op(T, [] { for (long i = 0; i < N; ++i) counter.v.fetch_add(1); });
            else if (!strcmp(m, "tas"))
                ns = ns_per_op(T, [] { for (long i = 0; i < N; ++i) { lock_tas(); ++plain.v; unlock(); } });
            else
                ns = ns_per_op(T, [] { for (long i = 0; i < N; ++i) { lock_ttas(); ++plain.v; unlock(); } });
            got = counter.v.load() + plain.v; expect = T * N;
            if (rep >= 2) r.push_back(ns);                    // 前 2 次是预热
        }
        std::sort(r.begin(), r.end());
        std::printf("%-7s T=%2d  ns per increment: median %6.2f  min %6.2f  max %6.2f  total %ld/%ld\n",
                    m, T, r[3], r[0], r[6], got, expect);
    }
}

1. Lab A 的 relaxed SB 在 M5 上出现了 r1 = r2 = 0。最准确的解释是什么？

1. Lab A’s relaxed SB produced r1 = r2 = 0 on the M5. What is the most accurate explanation?

汇编里 relaxed 版本是 str 在前、ldr 在后，编译器没有重排。cache 一致性只保证同一地址上写的顺序一致，它一直成立；SB 是两个不同地址之间的先后被看反了，原因是 store buffer 让后面的读先于前面的写完成。In the assembly the relaxed version is str first and ldr second, so the compiler did not reorder. Cache coherence only guarantees an agreed order of writes to one address, and it held throughout; SB is the order between two different addresses being seen reversed, because the store buffer lets the later load complete before the earlier store.

2. Dekker 用 acquire 读、release 写，5 次运行里仍有 2 次丢计数。为什么？

2. Dekker with acquire loads and release stores still lost counts in 2 of 5 runs. Why?

任何内存序的原子访问都不会撕裂。seq_cst 写用的是同一条 stlr，变的是读：ldar 不越过更早的 stlr，ldapr 可以，这正是 C++ 允许 acquire 做的事。立旗和看对方旗是不同变量，谁也没读到谁的值，没有 synchronizes-with。Atomic accesses never tear, whatever the order. A seq_cst store uses the same stlr; what changes is the load: ldar does not pass an earlier stlr, while ldapr may, which is exactly what C++ allows acquire to do. Raising one’s flag and checking the other’s are different variables, neither reads the other’s value, and there is no synchronizes-with.

3. Apple clang 21 为一次 seq_cst 原子写分别在本机 M5 和 x86-64 上生成什么？

3. What does Apple clang 21 generate for one seq_cst atomic store on this M5 and on x86-64?

Lab B 的 store_seq_cst 在本机是 stlr，配合 seq_cst 读的 ldar 就够，不需要 dmb。x86 上普通 movl 只够 release；seq_cst 要堵住 store→load 重排，clang 用隐含 lock 的 xchgl，不是 mov 加 mfence。Lab B’s store_seq_cst is stlr here, which together with the ldar of seq_cst loads is enough, with no dmb. On x86 a plain movl is only enough for release; seq_cst must close the store-to-load reordering, and clang uses the implicitly locked xchgl, not mov plus mfence.

4. 10 个线程时 TTAS 自旋锁比 TAS 快两到四倍。主要原因是什么？

4. At 10 threads the TTAS spin lock is two to four times faster than TAS. What is the main reason?

汇编里 TTAS 不争用时和 TAS 一样是一条 swpab，指令数不是原因（1 个线程时两者都是 6.1 ns）。ARM64 的 acquire 是 swpab 自带的属性，不是单独的屏障，两种锁的成功加锁都同样带 acquire。差别在争用时 cache line 的状态：TAS 每次 swpab 都要独占，TTAS 的 ldrb 只要共享。In the assembly, uncontended TTAS is one swpab just like TAS, so instruction count is not the reason (both take 6.1 ns with 1 thread). On ARM64 acquire is a property of swpab itself, not a separate barrier, and the successful lock in both carries acquire. The difference is the cache line’s state under contention: every TAS swpab needs it exclusive, while TTAS’s ldrb needs it only shared.
