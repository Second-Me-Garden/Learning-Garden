1. fork-join：结构化的并行

1. Fork-join: parallelism with structure

fork-join 只有一条规则：在一个作用域里分出去（fork）的工作，必须在同一个作用域结束前全部汇合（join）。于是并行的那一段只有一个入口、一个出口，像结构化编程里的循环和函数一样可以嵌套、可以推理。Phase 1 的 detach 和「放进队列就不管」的 dispatch_async 不是结构化的；std::jthread 在作用域结束时 join、dispatch_apply 返回前等所有迭代做完、OpenMP 并行区结尾的隐式屏障（implicit barrier），都是结构化的。

Fork-join has one rule: work that is forked inside a scope must all be joined before that scope ends. The parallel part then has one entry and one exit, and can be nested and reasoned about like loops and functions in structured programming. Phase 1’s detach and fire-and-forget dispatch_async are not structured; std::jthread joining at the end of its scope, dispatch_apply waiting for every iteration before it returns, and the implicit barrier at the end of an OpenMP parallel region all are.

估计一段 fork-join 程序能并行到什么程度，用两个量：work（T1，一个核做完全部工作的时间）和 span（T∞，无限多个核时最长那条依赖链的时间）。两者之比 T1/T∞ 叫并行度（parallelism），核再多也快不过它。贪心调度器（任何时刻只要有活就不让核闲着）在 P 个核上的时间满足 TP ≤ T1/P + T∞。两个例子：

To estimate how parallel a fork-join program can get, use two quantities: work (T1, the time for one core to do everything) and span (T∞, the time of the longest dependency chain with unlimited cores). Their ratio T1/T∞ is the parallelism, and no number of cores beats it. A greedy scheduler (one that never leaves a core idle while there is work) on P cores satisfies TP ≤ T1/P + T∞. Two examples:

  • 矩阵乘法按行并行。1024 行互不依赖，span 就是最贵的那一行。并行度约等于行数，远大于 10 个核，所以瓶颈不在 span，而在怎么把行分给核（概念 2、7）。
  • Matrix multiply, parallel by rows. The 1024 rows are independent, so the span is the single most expensive row. The parallelism is roughly the row count, far more than 10 cores, so the bottleneck is not the span but how the rows are handed to cores (concepts 2 and 7).
  • 递归 fib。work 随 n 指数增长，span 只随 n 线性增长（沿着 fib(n-1) 一路下去），并行度巨大。问题变成任务太多、太小，要靠 cutoff 把底下的小任务改回串行（概念 4、7）。
  • Recursive fib. The work grows exponentially in n while the span grows only linearly (straight down through fib(n-1)), so the parallelism is enormous. The problem becomes too many, too small tasks, fixed with a cutoff that turns the small tasks at the bottom back into serial code (concepts 4 and 7).

2. OpenMP 的 parallel for 和 schedule

2. OpenMP parallel for and its schedules

OpenMP 是一组编译器指令（pragma）加一个运行时库。#pragma omp parallel 在进入时 fork 出一组线程（team），在区域结尾的隐式屏障处 join；#pragma omp for 把紧跟着的循环的迭代分给这组线程；两者常合写成 #pragma omp parallel for。循环变量自动是每个线程私有的。线程数由 OMP_NUM_THREADS 环境变量或 num_threads(n) 子句决定；在并行区里 omp_get_num_threads() 返回这组线程的个数，在并行区外它返回 1，想在外面知道「将会有几个」用 omp_get_max_threads()。迭代怎么分，由 schedule 子句决定（OpenMP 5.2 规范的 schedule Clause 一节）：

OpenMP is a set of compiler directives (pragmas) plus a runtime library. #pragma omp parallel forks a team of threads on entry and joins them at the implicit barrier at the end of the region; #pragma omp for hands the iterations of the loop that follows to that team; the two are often written together as #pragma omp parallel for. The loop variable is automatically private to each thread. The thread count comes from the OMP_NUM_THREADS environment variable or a num_threads(n) clause; inside a parallel region omp_get_num_threads() returns the team size, outside it returns 1, and to learn outside how many there will be use omp_get_max_threads(). How the iterations are split is set by the schedule clause (the schedule Clause section of the OpenMP 5.2 specification):

  • schedule(static)：把迭代切成大致相等的连续几段，每个线程最多一段，进入循环时就算好，之后不再协调。schedule(static,c) 则切成每段 c 次，按线程编号轮流发。开销最小，前提是每次迭代一样贵、每个核一样快。
  • schedule(static): cut the iterations into roughly equal contiguous pieces, at most one per thread, computed on entry with no coordination afterwards. schedule(static,c) instead cuts pieces of c iterations and deals them out round-robin by thread number. The lowest overhead, provided every iteration costs the same and every core is equally fast.
  • schedule(dynamic,c)：每段 c 次（不写 c 就是 1），线程做完一段再去领下一段。能吸收迭代代价不均和核速度不均，代价是每段一次去运行时领活。
  • schedule(dynamic,c): pieces of c iterations (1 when c is omitted); a thread that finishes a piece goes back for the next. It absorbs uneven iteration costs and uneven core speeds, at the price of one trip to the runtime per piece.
  • schedule(guided,c)：也是做完再领，但每次领的段大小和「剩下的迭代数除以线程数」成正比，越往后越小，最小到 c（默认 1）。开头用大块省开销，结尾用小块收尾。
  • schedule(guided,c): also take-when-done, but each piece is proportional to the remaining iterations divided by the thread count, so pieces shrink as the loop goes on, down to c (1 by default). Big pieces early save overhead, small pieces at the end even out the finish.
  • schedule(runtime)：到运行时再读 OMP_SCHEDULE 环境变量，例如 OMP_SCHEDULE="dynamic,16"。Lab A 用它，一个二进制比较所有调度方式。
  • schedule(runtime): read the OMP_SCHEDULE environment variable at run time, for example OMP_SCHEDULE="dynamic,16". Lab A uses this to compare every schedule with one binary.

3. reduction：每个线程一份，最后再加

3. Reductions: one copy per thread, added at the end

reduction(+:sum) 让每个线程拿到一份私有的 sum，初值是这个运算的单位元（加法是 0），循环里只改自己那份，循环结束时运行时把各份合起来再加回原变量。这正是 Phase 2 修数据竞争的第三种方法「每线程一份私有累加」，只是由编译器替你写。上面 nm 里的 __kmpc_reduce_nowait 就是合并那一步。可用的运算还有 *、max、min、&、|、^、&&、||，也可以用 declare reduction 自定义。图解 (c) 把私有副本、合并那一步和共享原子放在一起逐步对照。

reduction(+:sum) gives each thread a private sum initialised to the operator’s identity (0 for addition); the loop updates only its own copy, and at the end the runtime combines the copies and adds them back into the original variable. This is exactly Phase 2’s third fix for a data race, a private per-thread sum, written by the compiler for you. The __kmpc_reduce_nowait in the nm output above is that combining step. Other operators are *, max, min, &, |, ^, && and ||, and declare reduction defines your own. Diagram (c) steps through the private copies and the combining step side by side with a shared atomic.

  • 为什么不用一个共享原子。每次加法都去抢同一条 cache line，Phase 2 已经量过它有多慢。reduction 让共享写只发生 T 次（T 是线程数），而不是每次加法一次（Lab A 里是 N × N 次）。
  • Why not one shared atomic. Every addition would fight over the same cache line, and Phase 2 measured how slow that is. A reduction makes the shared write happen T times (T threads), rather than once per addition (N × N in Lab A).
  • 浮点数的结果可能和串行差最后几位。浮点加法不满足结合律，reduction 改变了相加的顺序，线程数或调度一变结果就可能变。要逐位一样，就得固定分块并按固定顺序合并。
  • A floating-point result may differ from the serial one in the last bits. Floating-point addition is not associative, a reduction changes the order of additions, and a different thread count or schedule may change the result. Bit-for-bit equality needs fixed chunks combined in a fixed order.
  • GCD 没有 reduction 子句。做法是给每个块一格私有的部分和数组，dispatch_apply 返回后在调用线程里串行加起来。数组的每一格最好各占一条 128 字节的 cache line，否则就是 Phase 0 的 false sharing。
  • GCD has no reduction clause. Give each chunk its own slot in an array of partial sums and add them serially on the calling thread after dispatch_apply returns. Each slot should sit on its own 128-byte cache line, or it is the false sharing of Phase 0.

4. task：不规则的并行

4. Tasks: irregular parallelism

循环适合「事先知道有多少份活」的情况。递归、树、图的遍历事先不知道，就用任务（task）：#pragma omp task 把紧跟着的语句打包成一个任务交给运行时，可能由别的线程执行；#pragma omp taskwait 等当前任务直接生成的子任务全部完成（不等孙任务；要等全部后代用 taskgroup）。标准写法是先 parallel 建一组线程，再用 single 让其中一个线程生成根任务，其余线程一开始就去任务池里找活：

Loops suit cases where you know up front how many pieces of work there are. Recursion and tree or graph traversal do not, so use tasks: #pragma omp task packages the statement that follows into a task for the runtime, possibly run by another thread; #pragma omp taskwait waits for the child tasks the current task created directly (not grandchildren; to wait for all descendants, use taskgroup). The standard form is parallel to create a team, then single so one thread generates the root task, while the others go to the task pool for work from the start:

// fib_omp.c: 递归 fib，用 OpenMP task 拆开，小于 CUTOFF 时改串行
#include <omp.h>
#include <stdio.h>
#include <stdlib.h>

static int cutoff;

static long fib_serial(int n) { return n < 2 ? n : fib_serial(n - 1) + fib_serial(n - 2); }

static long fib(int n) {
    if (n < cutoff) return fib_serial(n);           // 太小就不再拆
    long a, b;
    #pragma omp task shared(a)
    a = fib(n - 1);
    b = fib(n - 2);                                 // 另一半由当前线程自己做
    #pragma omp taskwait
    return a + b;
}

int main(int argc, char **argv) {
    int n = argc > 1 ? atoi(argv[1]) : 42;
    cutoff = argc > 2 ? atoi(argv[2]) : 25;
    long r = 0;
    double t0 = omp_get_wtime();
    #pragma omp parallel
    {
        #pragma omp single                          // 一个线程生成根任务，其余线程从任务池里取
        r = fib(n);
    }
    printf("fib(%d) = %ld  cutoff %d  threads %d  %.0f ms\n",
           n, r, cutoff, omp_get_max_threads(), (omp_get_wtime() - t0) * 1e3);
    return 0;
}
  • shared(a) 不能省。任务里用到的、在外面不是 shared 的变量，默认是 firstprivate：任务拿到一份拷贝。a 是函数的局部变量，不写 shared(a)，子任务就把结果写进自己的拷贝，父任务读到的是未初始化的 a。taskwait 保证父任务读 a 之前子任务已经写完。
  • shared(a) cannot be left out. A variable used in a task that is not shared in the enclosing context is firstprivate by default: the task gets a copy. a is a local of the function, so without shared(a) the child writes its result into its own copy and the parent reads an uninitialised a. taskwait guarantees the child has finished writing before the parent reads a.
  • cutoff 写成普通的 if。OpenMP 也有 if(n > CUTOFF) 子句，但条件为假时仍然生成一个立即执行的任务，任务的簿记开销还在；直接分支到串行函数最省。
  • Write the cutoff as a plain if. OpenMP also has an if(n > CUTOFF) clause, but when the condition is false it still creates a task that runs immediately, so the bookkeeping cost remains; branching straight to a serial function is cheapest.
  • 任务之间有先后时用 depend。#pragma omp task depend(out: x) 和后面的 depend(in: x) 让运行时按数据依赖排好兄弟任务的顺序，不用 taskwait 把所有人都停下来。
  • Use depend when tasks have an order. #pragma omp task depend(out: x) followed by depend(in: x) lets the runtime order sibling tasks by their data dependencies, without a taskwait that stops everyone.

5. GCD：dispatch_apply 和 group

5. GCD: dispatch_apply and groups

dispatch_apply(n, queue, block) 调用 block n 次，参数是 0 到 n-1，全部做完才返回，所以它本身就是一次 fork-join，调用线程也参与干活。queue 传 DISPATCH_APPLY_AUTO，SDK 头文件 dispatch/queue.h 的说明是让系统使用和当前线程配置尽量相符的工作线程。libdispatch 的源码（src/apply.c，2026-10-31 读的 main 分支）说明了它怎么分活：

dispatch_apply(n, queue, block) calls the block n times with arguments 0 to n-1 and returns only when all are done, so it is itself one fork-join, and the calling thread joins in the work. For queue, pass DISPATCH_APPLY_AUTO; the SDK header dispatch/queue.h describes it as asking the system to use worker threads that match the current thread’s configuration as closely as possible. libdispatch’s source (src/apply.c, the main branch read on 2026-10-31) shows how it hands out the work:

  • 一次领一个编号。每个参与的线程循环执行 idx = os_atomic_inc_orig(&da->da_index, relaxed)，领到的编号小于 n 就调用一次 block。也就是说，dispatch_apply 就是 chunk 为 1 次迭代的动态调度。你能控制的是「一次迭代」有多大：传 n = 10，每次迭代做 102 行；传 n = 1024，每次迭代做 1 行。
  • One index at a time. Every participating thread loops on idx = os_atomic_inc_orig(&da->da_index, relaxed) and calls the block once whenever the index is below n. So dispatch_apply is a dynamic schedule with a chunk of one iteration. What you control is how big one iteration is: with n = 10 each iteration does 102 rows; with n = 1024 each does 1 row.
  • 线程数有上限。线程数取这个 QoS 下的最大并行度，绝不超过迭代数；嵌套在另一个 dispatch_apply 里时，内层的线程数要除以外层的迭代数，避免乘出超订来（_dispatch_apply_calc_thread_count）。
  • The thread count is capped. It is the maximum parallelism for the QoS and never more than the iteration count; when nested inside another dispatch_apply, the inner thread count is divided by the outer iteration count so the two do not multiply into oversubscription (_dispatch_apply_calc_thread_count).
  • 不规则的工作用 group。几件不同的工作用 dispatch_group_async 放进同一个 group，再 dispatch_group_wait，也是 fork-join。但别拿它写递归任务树：在工作线程里调 dispatch_group_wait 会让这个池线程睡着，按 Phase 1 讲的 workqueue 行为，系统会补线程，递归一深就成了超订。递归树要的是「等的时候顺便干活」，那就是 work stealing。
  • Use a group for irregular work. Put several different jobs in one group with dispatch_group_async, then dispatch_group_wait; that is fork-join too. But do not use it for a recursive task tree: calling dispatch_group_wait on a worker thread puts that pool thread to sleep, and by the workqueue behaviour described in Phase 1 the system adds threads, so a deep recursion becomes oversubscription. A recursive tree needs waiting that works while it waits, and that is work stealing.

Lab B 的实测（N = 1024 的 double 矩阵乘法）：只切 1 块时和串行一样慢（约 113 ms），因为只有一个线程在做；切 10 块约 26 ms；切 100 块约 23 ms。

Measured in Lab B (a 1024 × 1024 double matrix multiply): with 1 chunk it is as slow as serial (about 113 ms), because one thread does everything; with 10 chunks about 26 ms; with 100 chunks about 23 ms.

6. work stealing：每个线程一个 deque

6. Work stealing: one deque per thread

Phase 1 的线程池只有一个共享队列，所有人抢一把锁。work stealing 给每个线程一个自己的双端队列（deque）：

Phase 1’s thread pool had one shared queue and everyone fought over one lock. Work stealing gives each thread its own double-ended queue (deque):

  • 自己的活从尾部放、从尾部取（LIFO）。刚生成的子任务最先被做，它要的数据还在这个核的 cache 里；递归也因此按深度优先展开，同时存在的任务数和递归深度成正比，而不是和任务总数成正比。
  • The owner pushes and pops at the tail (LIFO). The newest child runs first while its data is still in this core’s cache, and the recursion unfolds depth-first, so the number of live tasks is proportional to the recursion depth, not to the total task count.
  • 闲下来的线程从别人的头部偷（FIFO）。头部是最老的任务，在递归树里就是离根最近、最大的那棵子树。偷一次就够这个小偷忙很久，所以偷的次数很少。
  • An idle thread steals from someone else’s head (FIFO). The head holds the oldest task, which in a recursion tree is the subtree nearest the root and the biggest. One steal keeps the thief busy for a long time, so steals are rare.
  • 主人和小偷在两头，平时不冲突。主人只在自己的尾部操作，只有 deque 快空了才可能和小偷碰到同一个元素。
  • Owner and thief work at opposite ends and rarely collide. The owner touches only its own tail; only when the deque is nearly empty can it meet a thief on the same element.
  • 等待时不睡，而是继续干活。父任务在 taskwait 处如果子任务被偷走了，它就去做自己 deque 里的或者偷来的任务，直到子任务完成。这解决了概念 5 里 group 等待把池线程睡掉的问题。
  • Waiting does not sleep; it keeps working. A parent at a taskwait whose child was stolen runs tasks from its own deque or steals until the child is done. That solves the problem in concept 5 of a group wait putting a pool thread to sleep.

LLVM 的 libomp 就是这么做 OpenMP 任务的（openmp/runtime/src/kmp_tasking.cpp，2026-10-31 读的 main 分支）：每个线程一个带锁的 deque，__kmp_remove_my_task 从自己的尾部取，__kmp_steal_task 加锁后从对方的头部偷。Lab B 的 ws_fib.cpp 是同一个设计，每个 deque 一把 std::mutex，简单而且 TSan 检查干净。去掉锁的版本（Chase–Lev deque）要用到 Phase 3 的内存序和 Phase 4 那类无锁技巧，本页不展开。

LLVM’s libomp runs OpenMP tasks exactly this way (openmp/runtime/src/kmp_tasking.cpp, the main branch read on 2026-10-31): one locked deque per thread, __kmp_remove_my_task takes from the thread’s own tail, and __kmp_steal_task takes the victim’s lock and steals from its head. Lab B’s ws_fib.cpp uses the same design with one std::mutex per deque, which is simple and comes out clean under TSan. The lock-free version (the Chase–Lev deque) needs Phase 3’s memory orders and Phase 4-style lock-free techniques, and this page does not cover it.

fib(42)、10 个线程、cutoff 25 时，每次运行生成 6764 个任务（算出），只发生 146–179 次偷（实测），用时约 59–60 ms，串行约 360 ms。

With fib(42), 10 threads and cutoff 25, each run creates 6764 tasks (computed) and 146–179 steals happen (measured), taking about 59–60 ms against about 360 ms serial.

6764 这个数可以事先算出来。按 fib_omp.c 和 Lab B 的 ws_fib.cpp 的写法，n 小于 cutoff c 时直接串行，n ≥ c 的每次调用生成 1 个任务（交出 fib(n-1)），再递归 n-1 和 n-2。记 K(n) 为 fib(n) 生成的任务数：

The 6764 can be worked out in advance. In fib_omp.c and Lab B’s ws_fib.cpp, a call with n below the cutoff c runs serially, and each call with n ≥ c creates 1 task (handing off fib(n-1)) and recurses on n-1 and n-2. Let K(n) be the number of tasks fib(n) creates:

K(n) = 0 for n < c;   K(n) = 1 + K(n-1) + K(n-2) for n ≥ c
c = 25:  K(25) = 1, K(26) = 2, K(27) = 4, K(28) = 7, …  K(n) = F(n - c + 3) - 1
fib(42), c = 25:  F(20) - 1 = 6765 - 1    = 6764      steals 146-179 (2.2-2.6 %)   59-60 ms

  2. fib(42)、cutoff 25 时是 F(20) − 1 = 6764，和概念 6 引用的任务数一致（Lab B 的任务数就是按这个递归式算出的，程序只计偷的次数）。
  3. 6764 个任务里只有 146 到 179 个被偷，约 2.2–2.6 %：其余的都由生成它的线程从自己 deque 的尾部取回来做。每次偷拿的是对方头部最老、最大的子树，所以偷一次就够忙很久。
  4. cutoff 降到 10 时是 F(35) − 1 = 9227464 个任务，多了约 1364 倍，计算量却一样：时间从 59–60 ms 涨到 165–175 ms，多出来的都是生成、入队和取任务的开销。
  1. K follows the same recurrence as the Fibonacci numbers plus 1, so K(n) + 1 is a Fibonacci number: K(25) + 1 = 2 = F(3), and each level up moves one index along.
  2. For fib(42) with cutoff 25 that gives F(20) − 1 = 6764, the task count concept 6 cites (Lab B computes its task counts from this recursion; the program counts only steals).
  3. Only 146 to 179 of the 6764 tasks are stolen, about 2.2–2.6 %: the rest are taken back by the thread that created them, from the tail of its own deque. Each steal takes the oldest, biggest subtree at the victim’s head, so one steal keeps the thief busy for a long time.
  4. With the cutoff lowered to 10 it is F(35) − 1 = 9227464 tasks, about 1364 times as many for the same computation: the time rises from 59–60 ms to 165–175 ms, and all of the extra is the cost of creating, queuing and taking tasks.

7. 粒度和负载均衡

7. Granularity and load balance

每一块活都有固定开销：领活、入队、可能的一次偷。块太大，最后几块拖尾，别的核干等（负载不均）；块太小，开销吃掉收益。本页的三组实测从两头看这件事（数字都是 2026-10-31 两次运行的范围）：

Every piece of work has a fixed overhead: taking it, queuing it, perhaps a steal. Pieces that are too big leave a tail where the last few run while other cores wait (load imbalance); pieces that are too small let the overhead eat the gain. This page’s three sets of measurements look at it from both ends (ranges from two runs on 2026-10-31):

  • 迭代代价不均。下三角版本的矩阵乘法第 i 行只做 i+1 次内循环，越往后越贵。手写线程的静态平分 15.5–16.3 ms，动态每次领 8 行 11.5–11.7 ms；GCD 切 10 块 16.4–17.7 ms，切 100 块 11.3–11.6 ms。最后那段最重的行落在一个线程上，静态调度就输了 40 % 左右。
  • Uneven iteration costs. In the lower-triangular version of the matrix multiply, row i runs the inner loop only i+1 times, so later rows cost more. Hand-written threads with a static even split take 15.5–16.3 ms, dynamic with 8 rows per take 11.5–11.7 ms; GCD with 10 chunks takes 16.4–17.7 ms, with 100 chunks 11.3–11.6 ms. The heaviest rows at the end land on one thread, and the static schedule loses by about 40 %.
  • 核的速度不均。完整的矩阵乘法每行一样贵，静态平分照理最好，可实测静态 27.0–27.1 ms，动态每次 8 行 22.5–22.6 ms。原因最可能是 P 核和 E 核：10 等份里 6 份落在慢约 1.6 倍的 E 核上，P 核早早做完在等（推断，和 Phase 1 测的速度差一致；本页没有逐核计时）。所以在这台机器上，即使每次迭代一样贵，静态平分也不平衡。
  • Uneven core speeds. In the full matrix multiply every row costs the same, so a static even split should be best, yet static measures 27.0–27.1 ms and dynamic with 8 rows per take 22.5–22.6 ms. The most likely cause is the P and E cores: 6 of the 10 equal shares land on E cores that are about 1.6 times slower, and the P cores finish early and wait (inference, consistent with the speed gap measured in Phase 1; this page did not time each core). So on this machine, even when every iteration costs the same, a static even split is unbalanced.
  • 块太小。fib(42) 的 cutoff 从 25 降到 10，任务数从 6764 涨到 9227464，时间从 59–60 ms 涨到 165–175 ms。cutoff 在 20 到 30 之间几乎一样快，说明只要每个任务的计算远大于它的开销，具体取多少不敏感。
  • Pieces too small. Lowering fib(42)’s cutoff from 25 to 10 raises the task count from 6764 to 9227464 and the time from 59–60 ms to 165–175 ms. Cutoffs between 20 and 30 are almost equally fast: as long as each task’s computation is far larger than its overhead, the exact value hardly matters.

经验法则（不是规范，是常见做法）：块数取线程数的十倍上下，每块的计算至少是几十微秒，让领活的开销在 1 % 以下；迭代代价或核速度不均时用动态或 guided。

A rule of thumb (common practice, not a specification): about ten times as many chunks as threads, each chunk at least tens of microseconds of computation, so that the cost of taking work stays under 1 %; use dynamic or guided when iteration costs or core speeds are uneven.

9. 实践中的 Amdahl，和下面的内核

9. Amdahl in practice, and the kernel underneath

10 个核，本页最好的加速比是：fib 约 6.1 倍（360 ms 到 59 ms），完整矩阵乘法约 5.0 倍（112.5 ms 到 22.6 ms），下三角约 5.3 倍。为什么不是 10 倍：

With 10 cores, this page’s best speedups are about 6.1 times for fib (360 ms to 59 ms), about 5.0 times for the full matrix multiply (112.5 ms to 22.6 ms), and about 5.3 times for the triangular one. Why not 10:

  • 10 个核不是 10 份算力。按 Phase 1 测的 E 核慢约 1.6 倍，4 个 P 核加 6 个 E 核大约相当于 4 + 6 / 1.6 ≈ 7.75 个 P 核（推断）。fib 只在寄存器里算，6.1 倍离这个上限不远。
  • 10 cores are not 10 units of compute. With E cores about 1.6 times slower, as Phase 1 measured, 4 P cores plus 6 E cores are worth roughly 4 + 6 / 1.6 ≈ 7.75 P cores (inference). fib computes only in registers, and 6.1 times is not far from that ceiling.
  • 矩阵乘法还要搬数据。每一行都要从头到尾读一遍 8 MB 的 B，十个核同时读，内存层次的带宽可能成了限制（推断；Phase 6 的 roofline 和 Phase 7 的测量会把它量出来）。
  • The matrix multiply also moves data. Every row reads all 8 MB of B from start to end, ten cores at once, and the memory hierarchy’s bandwidth may become the limit (inference; the roofline of Phase 6 and the measurements of Phase 7 will quantify it).
  • 串行部分。初始化矩阵、建线程、最后的 join 和 reduction 合并都是串行的；本页的计时只包住计算本身，真实程序里它们就是 Amdahl 公式里的 s。
  • The serial part. Initialising the matrices, creating threads, the final join and combining the reduction are all serial; this page’s timers wrap only the computation, but in a real program those are the s in Amdahl’s formula.

运行时的线程仍是内核调度的普通线程（内核专题 Phase 1 的「调度」），所以 Phase 1 的超订规则照样适用，而且更容易踩到：一个进程里 OpenMP 的一组线程和 GCD 的线程池互相不知道对方。在 #pragma omp parallel for 的每次迭代里调用一个内部用 dispatch_apply 的库，可运行的线程数就可能是 10 乘 10。OpenMP 线程等活时可能先自旋再睡：libomp 用 KMP_BLOCKTIME 控制时长，标准的 OMP_WAIT_POLICY=active 要求自旋。在 Apple 芯片的 macOS 上 libomp 默认 blocktime 是 0，空闲线程直接睡；其他平台默认 200 ms（openmp/runtime/src/kmp.h）。一旦设了 OMP_WAIT_POLICY=active 或很大的 KMP_BLOCKTIME，旁边的 GCD 线程就分不到核。规则：一个进程里只让一个运行时负责并行，或者明确给内层设成串行。

A runtime’s threads are still ordinary threads scheduled by the kernel (the scheduling concept in kernel topic Phase 1), so Phase 1’s oversubscription rule still applies, and it is easier to trip over: inside one process, OpenMP’s team and GCD’s pool know nothing of each other. Call a library that uses dispatch_apply internally from each iteration of a #pragma omp parallel for, and the runnable thread count may be 10 times 10. OpenMP threads may also spin before they sleep. libomp’s KMP_BLOCKTIME sets how long, and the standard OMP_WAIT_POLICY=active asks for spinning. On macOS on Apple silicon, libomp’s default blocktime is 0, so idle threads sleep at once; elsewhere the default is 200 ms (openmp/runtime/src/kmp.h). If you set OMP_WAIT_POLICY=active or a large KMP_BLOCKTIME, GCD threads next to the team get no core. The rule: let one runtime own the parallelism in a process, or explicitly make the inner level serial.

  • reduction 给每个线程一份私有副本，共享写只发生 T 次而不是每次加法一次（Lab A 里是 N × N 次），浮点结果可能和串行差最后几位。
  • 事先不知道有多少活时用 task，cutoff 把底下的小任务改回串行。
  • work stealing 让主人从自己 deque 的尾部取、小偷从别人的头部偷，fib(42) 的 6764 个任务只偷了 146 到 179 次。
  • 块数取线程数的十倍上下、每块至少几十微秒；libc++ 的 std::execution::par 每 256 个元素才切一块，元素很贵时要自己选块数。
  • Fork-join requires everything forked in a scope to join before the scope ends, and work T1 and span T∞ give the bound TP ≤ T1/P + T∞.
  • schedule(static) divides the loop once on entry at the lowest overhead, while dynamic and guided take more when done and absorb uneven iteration costs and core speeds.
  • reduction gives each thread a private copy so that shared writes happen T times rather than once per addition (N × N in Lab A), and a floating-point result may differ from the serial one in the last bits.
  • Use tasks when the amount of work is not known in advance, with a cutoff that turns the small tasks at the bottom back into serial code.
  • Work stealing has the owner take from the tail of its own deque and thieves steal from the head of others, and fib(42)’s 6764 tasks needed only 146 to 179 steals.
  • Aim for about ten times as many chunks as threads, each at least tens of microseconds; libc++’s std::execution::par cuts only one chunk per 256 elements, so choose the chunk count yourself when elements are expensive.

常见误解

Common misconceptions

  • 误解：每次迭代一样贵，静态平分就是最好的。→ 实际：本机 6 个 E 核比 P 核慢约 1.6 倍，完整矩阵乘法静态 27.0–27.1 ms，动态每次 8 行 22.5–22.6 ms。
  • 误解：任务越多，并行度越高，就越快。→ 实际：fib(42) 的 cutoff 从 25 降到 10，任务从 6764 个变成 9227464 个，时间从 59–60 ms 涨到 165–175 ms。
  • 误解：std::execution::par 会自动用满所有核。→ 实际：本机 libc++ 默认根本编不过，加 -fexperimental-library 后 1024 行只切 4 块，34.0–34.5 ms，比 dispatch_apply 切 100 块的 23 ms 慢。
  • Myth: when every iteration costs the same, an even static split is best. → Fact: the 6 E cores here are about 1.6 times slower than the P cores, and the full matrix multiply takes 27.0–27.1 ms static against 22.5–22.6 ms dynamic with 8 rows per take.
  • Myth: more tasks mean more parallelism and so more speed. → Fact: lowering fib(42)’s cutoff from 25 to 10 takes the task count from 6764 to 9227464 and the time from 59–60 ms to 165–175 ms.
  • Myth: std::execution::par uses all the cores automatically. → Fact: the libc++ here does not even compile it by default, and with -fexperimental-library 1024 rows are cut into only 4 chunks, 34.0–34.5 ms, slower than the 23 ms of dispatch_apply with 100 chunks.

    // matmul_omp.c: 同一个矩阵乘法，OpenMP parallel for；schedule(runtime) 让 OMP_SCHEDULE 环境变量选调度方式
#include <omp.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

enum { N = 1024 };
static double A[N][N], B[N][N], C[N][N];

static void row(int i, int tri) {
    memset(C[i], 0, sizeof C[i]);
    int kend = tri ? i + 1 : N;                     // tri = 1：下三角，第 i 行的工作量和 i 成正比
    for (int k = 0; k < kend; ++k) {
        double a = A[i][k];
        for (int j = 0; j < N; ++j) C[i][j] += a * B[k][j];
    }
}

static double run(int tri) {
    double t0 = omp_get_wtime();
    #pragma omp parallel for schedule(runtime)
    for (int i = 0; i < N; ++i) row(i, tri);
    return omp_get_wtime() - t0;
}

static int cmp(const void *a, const void *b) {
    double x = *(const double *)a, y = *(const double *)b;
    return (x > y) - (x < y);
}

int main(int argc, char **argv) {
    int tri = argc > 1 && argv[1][0] == 't';
    for (int i = 0; i < N; ++i)
        for (int j = 0; j < N; ++j) { A[i][j] = (i + j) % 7 - 3; B[i][j] = (i * j) % 5 - 2; }
    double t[7];
    run(tri);                                       // 预热
    for (int r = 0; r < 7; ++r) t[r] = run(tri);
    qsort(t, 7, sizeof t[0], cmp);

    double sum = 0;                                 // reduction：每个线程一份私有的 sum，结束时相加
    #pragma omp parallel for reduction(+:sum)
    for (int i = 0; i < N; ++i)
        for (int j = 0; j < N; ++j) sum += C[i][j];

    int nt = 0;
    #pragma omp parallel
    {
        #pragma omp single
        nt = omp_get_num_threads();
    }
    const char *s = getenv("OMP_SCHEDULE");
    printf("%-10s OMP_SCHEDULE=%-10s threads=%2d  median %7.1f ms  min %7.1f  max %7.1f  checksum %.0f\n",
           tri ? "triangular" : "full", s ? s : "(unset)", nt, t[3] * 1e3, t[0] * 1e3, t[6] * 1e3, sum);
    return 0;
}

    // matmul_threads.cpp: 手写的 parallel for：静态（每线程一段连续的行）对比动态（原子计数器每次领 chunk 行）
#include <algorithm>
#include <atomic>
#include <chrono>
#include <cstdio>
#include <cstring>
#include <thread>
#include <vector>

constexpr int N = 1024;
static double A[N][N], B[N][N], C[N][N];

static void row(int i, bool tri) {
    std::memset(C[i], 0, sizeof C[i]);
    int kend = tri ? i + 1 : N;
    for (int k = 0; k < kend; ++k) {
        double a = A[i][k];
        for (int j = 0; j < N; ++j) C[i][j] += a * B[k][j];
    }
}

static void run_static(unsigned T, bool tri) {
    std::vector<std::jthread> ts;
    for (unsigned t = 0; t < T; ++t)
        ts.emplace_back([=] { for (int i = t * N / T; i < (int)((t + 1) * N / T); ++i) row(i, tri); });
}   // 析构时 join

static void run_dynamic(unsigned T, int chunk, bool tri) {
    std::atomic<int> next{0};
    std::vector<std::jthread> ts;
    for (unsigned t = 0; t < T; ++t)
        ts.emplace_back([&] {
            for (;;) {
                int i0 = next.fetch_add(chunk, std::memory_order_relaxed);   // 领下一块
                if (i0 >= N) return;
                for (int i = i0; i < std::min(i0 + chunk, N); ++i) row(i, tri);
            }
        });
}

template <class F> static double median_ms(F f) {
    std::vector<double> t;
    f();
    for (int r = 0; r < 7; ++r) {
        auto t0 = std::chrono::steady_clock::now();
        f();
        t.push_back(std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count());
    }
    std::sort(t.begin(), t.end());
    return t[3];
}

int main() {
    for (int i = 0; i < N; ++i)
        for (int j = 0; j < N; ++j) { A[i][j] = (i + j) % 7 - 3; B[i][j] = (i * j) % 5 - 2; }
    unsigned T = std::thread::hardware_concurrency();
    for (bool tri : {false, true}) {
        const char *name = tri ? "triangular" : "full";
        std::printf("%-10s static, %u threads:          median %6.1f ms\n", name, T, median_ms([&] { run_static(T, tri); }));
        for (int chunk : {1, 8, 64})
            std::printf("%-10s dynamic chunk %2d, %u threads: median %6.1f ms\n", name, chunk, T,
                        median_ms([&] { run_dynamic(T, chunk, tri); }));
    }
}

    // matmul_gcd.c: C = A * B（N × N double），dispatch_apply 按行分成 K 块；另测一个下三角版本（第 i 行只做 i+1 个 k）
#include <dispatch/dispatch.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

enum { N = 1024 };
static double A[N][N], B[N][N], C[N][N];

static double now_s(void) {
    struct timespec ts; clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

// 第 r0 到 r1-1 行；tri 为 1 时只用 A 的下三角，第 i 行的工作量和 i 成正比
static void rows(int r0, int r1, int tri) {
    for (int i = r0; i < r1; ++i) {
        memset(C[i], 0, sizeof C[i]);
        int kend = tri ? i + 1 : N;
        for (int k = 0; k < kend; ++k) {
            double a = A[i][k];
            for (int j = 0; j < N; ++j) C[i][j] += a * B[k][j];   // i-k-j 顺序，内层连续访问
        }
    }
}

static double run(int chunks, int tri) {           // chunks = 0 表示串行
    double t0 = now_s();
    if (chunks == 0) rows(0, N, tri);
    else dispatch_apply(chunks, DISPATCH_APPLY_AUTO, ^(size_t c) {
        rows((int)(c * N / chunks), (int)((c + 1) * N / chunks), tri);
    });
    return now_s() - t0;
}

static int cmp(const void *a, const void *b) {
    double x = *(const double *)a, y = *(const double *)b;
    return (x > y) - (x < y);
}

int main(void) {
    for (int i = 0; i < N; ++i)
        for (int j = 0; j < N; ++j) { A[i][j] = (i + j) % 7 - 3; B[i][j] = (i * j) % 5 - 2; }
    int ks[] = {0, 1, 10, 100, 1024};
    for (int tri = 0; tri <= 1; ++tri)
        for (int x = 0; x < 5; ++x) {
            double t[7];
            run(ks[x], tri);                                   // 预热
            for (int r = 0; r < 7; ++r) t[r] = run(ks[x], tri);
            qsort(t, 7, sizeof t[0], cmp);
            double sum = 0;
            for (int i = 0; i < N; ++i) for (int j = 0; j < N; ++j) sum += C[i][j];

                   tri ? "triangular" : "full", ks[x] ? "gcd" : "serial", ks[x],
                   t[3] * 1e3, t[0] * 1e3, t[6] * 1e3, sum);
        }
    return 0;
}

One locked deque per thread; the owner takes from its tail and steals from others’ heads, and a waiting thread keeps working while it waits. fib(42), with the cutoff lowered from 35 to 10:
    // ws_fib.cpp: 每个线程一个双端队列（deque）的 work stealing，跑递归 fib，带 cutoff
// 自己的队列从尾部取（LIFO），偷别人的从头部取（FIFO）；每个 deque 用一把锁，简单而正确（无锁的 Chase–Lev deque 本页不展开）
#include <algorithm>
#include <atomic>
#include <chrono>
#include <cstdio>
#include <cstdlib>
#include <deque>
#include <functional>
#include <mutex>
#include <thread>
#include <vector>

class StealPool {
    struct Worker { std::mutex m; std::deque<std::function<void()>> dq; };
    std::vector<Worker> ws;
    std::vector<std::jthread> threads;
    std::atomic<long> steals{0};
    static thread_local int me;                       // 当前线程在 ws 里的编号

    bool pop_local(std::function<void()> &t) {
        Worker &w = ws[me];
        std::lock_guard lk(w.m);
        if (w.dq.empty()) return false;
        t = std::move(w.dq.back()); w.dq.pop_back();  // 自己：从尾部取，最新、最小的任务
        return true;
    }
    bool steal(std::function<void()> &t) {
        for (size_t k = 1; k < ws.size(); ++k) {
            Worker &v = ws[(me + k) % ws.size()];
            std::lock_guard lk(v.m);
            if (v.dq.empty()) continue;
            t = std::move(v.dq.front()); v.dq.pop_front();  // 小偷：从头部取，最老、最大的任务
            steals.fetch_add(1, std::memory_order_relaxed);
            return true;
        }
        return false;
    }
    bool run_one() {
        std::function<void()> t;
        if (pop_local(t) || steal(t)) { t(); return true; }
        return false;
    }
public:
    explicit StealPool(unsigned n) : ws(n) {
        me = 0;                                       // 调用者（主线程）就是 0 号 worker
        for (unsigned i = 1; i < n; ++i)
            threads.emplace_back([this, i](std::stop_token st) {
                me = (int)i;
                while (!st.stop_requested())
                    if (!run_one()) std::this_thread::yield();
            });
    }
    void spawn(std::function<void()> f) {
        Worker &w = ws[me];
        std::lock_guard lk(w.m);
        w.dq.push_back(std::move(f));
    }
    // 等待时不睡：一边等一边做别的任务（自己的或偷来的）
    void wait(std::atomic<int> &pending) {
        while (pending.load(std::memory_order_acquire) > 0)
            if (!run_one()) std::this_thread::yield();
    }
    long steal_count() const { return steals.load(); }
};
thread_local int StealPool::me = 0;

static long fib_serial(int n) { return n < 2 ? n : fib_serial(n - 1) + fib_serial(n - 2); }

static StealPool *pool;
static int cutoff;

static long fib_ws(int n) {
    if (n < cutoff) return fib_serial(n);             // 太小就不拆：任务的开销比计算还大
    long a = 0;
    std::atomic<int> pending{1};
    pool->spawn([&] { a = fib_ws(n - 1); pending.fetch_sub(1, std::memory_order_release); });
    long b = fib_ws(n - 2);                           // 另一半自己做
    pool->wait(pending);
    return a + b;
}

template <class F> static double median_ms(F f) {
    std::vector<double> t;
    f();                                              // 预热
    for (int r = 0; r < 5; ++r) {
        auto t0 = std::chrono::steady_clock::now();
        f();
        t.push_back(std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count());
    }
    std::sort(t.begin(), t.end());
    return t[2];
}

int main(int argc, char **argv) {
    int n = argc > 1 ? std::atoi(argv[1]) : 42;
    volatile long sink;
    std::printf("serial fib(%d) = %ld: median %.0f ms\n", n, fib_serial(n),
                median_ms([&] { int m = n; asm volatile("" : "+r"(m)); sink = fib_serial(m); }));
    // asm volatile 让编译器不知道 m 的值，否则它会把纯函数调用提到计时循环外面
    StealPool p(std::thread::hardware_concurrency());
    pool = &p;
    for (int c : {35, 30, 25, 20, 15, 10}) {
        cutoff = c;
        long before = p.steal_count();
        long r = fib_ws(n);
        double ms = median_ms([&] { sink = fib_ws(n); });
        std::printf("work stealing, cutoff %2d: fib = %ld, median %5.0f ms, steals per run %ld\n",
                    c, r, ms, (p.steal_count() - before) / 7);
    }
    (void)sink;
}

Self-check

1. 下三角矩阵乘法里第 i 行的代价和 i 成正比。Lab A 用 std::jthread 手写的静态调度（每线程一段连续的行，即 schedule(static) 的做法）在 10 个线程上实测比动态调度（每次领 8 行，即 schedule(dynamic,8)）慢约 35 %（15.5 对 11.5 ms）；OpenMP 本页没有运行，预期同理。主要原因是什么？

1. In the triangular matrix multiply, row i costs in proportion to i. In Lab A the static schedule written by hand with std::jthread (one contiguous range of rows per thread, as schedule(static) does) measured about 35 % slower on 10 threads than the dynamic one (8 rows per take, as schedule(dynamic,8) does): 15.5 against 11.5 ms. OpenMP was not run on this page; it is expected to behave the same. What is the main reason?

静态调度的开销反而最小：每个线程进循环时只问一次范围（__kmpc_for_static_init_4），之后不再协调。它也不会少开线程，线程数由 OMP_NUM_THREADS 决定。慢的原因是负载不均：工作量不均的行被连续地切给了固定的线程，再加上 6 个 E 核每份做得更慢。动态调度让先做完的线程继续领活，拖尾就消失了。The static schedule actually has the lowest overhead: each thread asks for its range once on entry (__kmpc_for_static_init_4) and never coordinates again. Nor does it start fewer threads; OMP_NUM_THREADS sets the count. The slowdown is load imbalance: rows of uneven cost are cut contiguously onto fixed threads, and the 6 E cores do their shares more slowly as well. A dynamic schedule lets threads that finish first keep taking work, and the tail disappears.

2. 在 work stealing 里，线程从自己 deque 的尾部取任务，却从别人 deque 的头部偷。为什么偷头部？

2. In work stealing, a thread takes tasks from the tail of its own deque but steals from the head of someone else’s. Why steal from the head?

锁和哪一端无关：本页的 ws_fib.cpp 和 libomp 两端都加锁，无锁的 Chase–Lev deque 也是主人那一端最便宜。头部的任务恰恰最大而不是最小：主人先放进去的是 fib(41)，后放的是越来越小的子问题。偷最大的那块，本页实测 6764 个任务只偷了 146–179 次。Locking has nothing to do with which end: this page’s ws_fib.cpp and libomp lock both ends, and in the lock-free Chase–Lev deque it is the owner’s end that is cheapest. The head holds the largest tasks, not the smallest: the owner pushed fib(41) first and ever smaller subproblems after it. Stealing the biggest piece is why this page measured only 146–179 steals for 6764 tasks.

3. 用 -fexperimental-library 编译的 std::for_each(std::execution::par, …) 按 1024 行做矩阵乘法要 34 ms，而 dispatch_apply 切 100 块只要 23 ms。为什么？

3. std::for_each(std::execution::par, …) built with -fexperimental-library takes 34 ms for the matrix multiply over 1024 rows, while dispatch_apply with 100 chunks takes only 23 ms. Why?

它不是串行的：程序导入了 _dispatch_apply_f，34 ms 也远快于串行的 113 ms。执行策略不会给元素加锁，par 只是允许并行，同步是你的函数自己的事。插桩显示 1024 个元素对应 4 次迭代，和上游源码的 element_count / 256 一致；元素很贵时这个切法太粗。It is not serial: the program imports _dispatch_apply_f, and 34 ms is far faster than the serial 113 ms. An execution policy does not lock elements; par only permits parallel execution, and synchronization is your function’s business. The interposer shows 4 iterations for 1024 elements, matching element_count / 256 in the upstream source; with expensive elements that split is too coarse.

4. ws_fib 的 cutoff 从 25 降到 10，时间从约 60 ms 变成约 170 ms。最主要的原因是什么？

4. Lowering the cutoff of ws_fib from 25 to 10 changes the time from about 60 ms to about 170 ms. What is the main reason?

偷的次数只从一两百次涨到四五百次，和九百多万个任务相比可以忽略。栈的深度只和 n 成正比（42 层左右），远用不完 512 KB；真溢出会碰到保护页直接崩溃，不会变慢。真正的原因是粒度：每个任务都有固定的簿记开销，任务小到一定程度，开销就压过了计算。Steals rise only from one or two hundred to four or five hundred, negligible beside more than nine million tasks. The stack depth is proportional to n (around 42 levels), nowhere near 512 KB; a real overflow would hit the guard page and crash, not slow down. The real cause is granularity: every task has a fixed bookkeeping cost, and once tasks are small enough, the overhead outweighs the computation.
