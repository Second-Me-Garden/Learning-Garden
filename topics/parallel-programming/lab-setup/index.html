The labs in this topic measure the hardware itself: how many cores there are, how wide a cache line is, how much slower two threads get when they fight over one line. So the lab machine is the Mac in front of you, with no VM. This page first reads out this machine’s real parameters, then checks the compiler, the thread libraries, OpenMP, the observation tools and the sanitizers one by one. Every "expected output" on this page was actually produced on this Apple M5 on 2026-10-31; three things were not run: OpenMP, because it has to be installed first, and spindump and dtrace with sudo; for those two the page ran only the step without sudo and records the errors it gave. The page marks all three.

为什么在本机做

Why on this Mac

  • 我们测的就是硬件。虚拟机给客体的是虚拟 CPU：客体看不到 P 核和 E 核的区别，宿主调度器还会在背后把虚拟 CPU 挪来挪去，计时里混进了别人的噪声。加速比、false sharing、内存带宽这些数字只有在真机上才有意义。
  • What we measure is the hardware. A VM gives its guest virtual CPUs: the guest cannot see the difference between P and E cores, and the host scheduler moves the virtual CPUs around behind its back, so other people’s noise gets into the timings. Numbers such as speedup, false sharing and memory bandwidth only mean something on the real machine.
  • 这里没有任何东西进内核。内核专题要隔离，是因为自写模块和关 SIP 会危及整台机器。本专题全是普通用户态程序：最坏的结果是一个进程卡死，Ctrl-c 或 kill 就结束。
  • Nothing here goes into the kernel. The kernel topic isolates because self-written modules and turning SIP off endanger the whole machine. This topic is all ordinary user-space programs: the worst case is a hung process, ended with Ctrl-c or kill.
  • 唯一的例外是 Linux perf。macOS 上没有 perf。需要 perf stat、perf record 时（Phase 7），用内核专题的 QEMU Linux VM。那时测的是虚拟机里的程序，数字只拿来和本机的墙钟时间对照，不当作本机的硬件计数。
  • The one exception is Linux perf. There is no perf on macOS. When you need perf stat or perf record (Phase 7), use the kernel topic’s QEMU Linux VM. What it measures then is a program inside a VM; use those numbers only as a comparison against this Mac’s wall times, not as this Mac’s hardware counts.
本机规则仍然成立：SIP 一直开着，不为任何实验关掉它。dtrace 在 SIP 下只有部分探针可用，这是本专题接受的限制；需要完整 dtrace 的实验属于内核专题的 macOS 客体机。
The host rule still holds: SIP stays on and is never turned off for any lab. Under SIP only some dtrace probes are available; this topic accepts that limit, and any lab that needs full dtrace belongs to the kernel topic’s macOS guest.

3. 怎么测时间

3. How to measure time

并行程序的一次运行时间不可信：第一次要把代码和数据拉进 cache，调度器可能把线程放到 E 核，后台进程会插进来。每个实验都按同一套做法：

A single run time of a parallel program cannot be trusted: the first run has to pull code and data into the cache, the scheduler may put threads on E cores, and background processes get in the way. Every lab follows the same method:

  • 单调时钟：C 用 clock_gettime(CLOCK_UPTIME_RAW 或 CLOCK_MONOTONIC_RAW, …)（macOS 上 CLOCK_MONOTONIC 只有 1 µs 分辨率，见 Phase 1 Lab A 第 5 步），C++ 用 std::chrono::steady_clock。不要用会被 NTP 调整的墙上时间（gettimeofday、system_clock）。
  • A monotonic clock: in C, clock_gettime(CLOCK_UPTIME_RAW or CLOCK_MONOTONIC_RAW, …), because macOS gives CLOCK_MONOTONIC only 1 µs resolution (Phase 1, Lab A step 5); in C++, std::chrono::steady_clock. Do not use calendar time that NTP can adjust (gettimeofday, system_clock).
  • 预热、重复、取中位数：先空跑几次，再跑奇数次，报中位数，同时报最小值和最大值，让人看到波动。
  • Warm up, repeat, take the median: run a few times untimed, then an odd number of timed runs; report the median, together with the minimum and maximum so the spread is visible.
  • 墙钟时间和 CPU 时间分开报：std::clock() 统计进程所有线程用掉的 CPU 时间。并行版本的墙钟时间下降而 CPU 时间不变，说明工作被分摊了；CPU 时间暴涨，说明线程在空转或抢锁。
  • Report wall time and CPU time separately: std::clock() counts the CPU time used by all threads of the process. If a parallel version’s wall time falls while its CPU time stays flat, the work was shared out; if CPU time shoots up, threads are spinning or fighting over a lock.
// bench.cpp: 预热 + 重复 + 取中位数；同时报墙钟时间和 CPU 时间
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <ctime>
#include <vector>

static volatile double sink;

static void work() {                       // 被测的代码
    double s = 0;
    for (int i = 1; i <= 20'000'000; ++i) s += 1.0 / i;
    sink = s;
}

int main() {
    using clk = std::chrono::steady_clock;
    for (int i = 0; i < 3; ++i) work();    // 预热 warm-up
    std::vector<double> ms;
    std::clock_t c0 = std::clock();
    for (int i = 0; i < 11; ++i) {         // 重复 11 次
        auto t0 = clk::now();
        work();
        ms.push_back(std::chrono::duration<double, std::milli>(clk::now() - t0).count());
    }
    double cpu = 1000.0 * (std::clock() - c0) / CLOCKS_PER_SEC;
    std::sort(ms.begin(), ms.end());
    std::printf("wall median %.2f ms  min %.2f  max %.2f\n", ms[5], ms[0], ms[10]);
    std::printf("cpu total %.1f ms for 11 runs\n", cpu);
}
$ clang++ -std=c++20 -O2 -Wall bench.cpp -o bench && ./bench && ./bench
wall median 9.78 ms  min 9.77  max 11.28
cpu total 110.0 ms for 11 runs
wall median 9.81 ms  min 9.79  max 10.15
cpu total 108.3 ms for 11 runs
# 2026-10-31 实验机输出；你的数字会不同，但中位数应当比最大值稳定得多

这个程序是单线程的，所以 11 次的 CPU 时间约等于 11 次墙钟时间之和。两次运行的最大值差了 1 ms，中位数只差 0.03 ms：这就是只报中位数的理由。

This program is single-threaded, so the CPU time for 11 runs is about the sum of the 11 wall times. The maximum differs by 1 ms between the two runs while the median differs by only 0.03 ms: that is why the median is what gets reported.

4. 不能绑核：用 QoS 表达意图

4. No CPU pinning: express intent with QoS

Linux 上可以用 taskset 或 sched_setaffinity 把线程钉在某个核上。macOS 没有对应的办法。Mach 的 affinity 策略在这台机器上直接返回不支持：

On Linux you can pin a thread to a core with taskset or sched_setaffinity. macOS has no equivalent. The Mach affinity policy simply returns not supported on this machine:

$ ./aff      # 调用 thread_policy_set(..., THREAD_AFFINITY_POLICY, ...)
thread_policy_set(THREAD_AFFINITY_POLICY) = 46 ((os/kern) service not supported)
# 2026-10-31 实验机输出

macOS 给的是 QoS（quality of service）类别：你告诉调度器这件工作有多急，由它决定放 P 核还是 E 核。线程用 pthread_set_qos_class_self_np，GCD 队列在创建时带上 QoS：

What macOS offers instead is QoS (quality of service) classes: you tell the scheduler how urgent the work is, and it decides between P and E cores. A thread uses pthread_set_qos_class_self_np; a GCD queue carries a QoS when it is created:

#include <pthread.h>
#include <pthread/qos.h>
#include <stdio.h>

int main(void) {
    int r = pthread_set_qos_class_self_np(QOS_CLASS_USER_INTERACTIVE, 0);
    qos_class_t q; int rel;
    pthread_get_qos_class_np(pthread_self(), &q, &rel);
    printf("set=%d qos=0x%x\n", r, q);
    return 0;
}
$ clang qos.c -o qos && ./qos
set=0 qos=0x21
# 2026-10-31 实验机输出；0x21 就是 QOS_CLASS_USER_INTERACTIVE
QoS 是提示，不是保证。实验里要测「全部在 P 核上」时，线程数不超过 4，QoS 设为 USER_INTERACTIVE 或 USER_INITIATED，并接受偶尔被放到 E 核上的那几次落在最大值里。这正是要报中位数的另一个理由。
QoS is a hint, not a guarantee. When a lab needs to measure "all on P cores", keep the thread count at 4 or fewer, set the QoS to USER_INTERACTIVE or USER_INITIATED, and accept that the occasional run placed on E cores ends up in the maximum. That is one more reason to report the median.

6. Sanitizer：让编译器帮你抓错

6. Sanitizers: let the compiler catch the bugs

-fsanitize=thread（TSan）在每次内存访问处插入检查，记录哪个线程在什么同步关系下读写了哪个地址，发现两个没有先后关系的访问且其中一个是写，就报数据竞争。-fsanitize=address（ASan）抓越界和释放后使用。两者不能同时打开，各编一份。TSan 让程序慢很多倍，只用来找错，不用来计时。

-fsanitize=thread (TSan) inserts a check at every memory access and records which thread read or wrote which address under which synchronization; when it sees two accesses with no ordering between them, at least one a write, it reports a data race. -fsanitize=address (ASan) catches out-of-bounds accesses and use after free. The two cannot be enabled together, so build one binary for each. TSan makes the program many times slower; use it to find bugs, never to time anything.

本机上有一个要知道的行为：TSan 报完竞争后，在进程退出时调用 abort()，退出码是 134，系统还会在 ~/Library/Logs/DiagnosticReports/ 下留一份崩溃报告。只想要普通的非零退出码时，设 TSAN_OPTIONS=abort_on_error=0，退出码变成 66：

One behaviour to know on this machine: after TSan reports a race, it calls abort() when the process exits, the exit status is 134, and the system also leaves a crash report under ~/Library/Logs/DiagnosticReports/. When you only want an ordinary non-zero exit status, set TSAN_OPTIONS=abort_on_error=0 and the status becomes 66:

$ ./race >/dev/null 2>&1; echo $?
134
$ TSAN_OPTIONS=abort_on_error=0 ./race >/dev/null 2>&1; echo $?
66

    // jthread_smoke.cpp: 每个线程把自己的编号加进一个原子计数器
#include <atomic>
#include <cstdio>
#include <thread>
#include <vector>

int main() {
    unsigned n = std::thread::hardware_concurrency();
    std::atomic<long> sum{0};
    {
        std::vector<std::jthread> ts;
        for (unsigned i = 0; i < n; ++i)
            ts.emplace_back([&sum, i] { sum.fetch_add(i + 1, std::memory_order_relaxed); });
    }   // jthread 在析构时自动 join
    std::printf("hardware_concurrency = %u\n", n);
    std::printf("sum = %ld (expected %u)\n", sum.load(), n * (n + 1) / 2);
}

    // gcd_smoke.c: dispatch_apply 把 1000 次迭代分给系统线程池
#include <dispatch/dispatch.h>
#include <stdatomic.h>
#include <stdio.h>

int main(void) {
    __block atomic_long sum = 0;   // block 要修改的变量必须带 __block
    dispatch_queue_t q = dispatch_get_global_queue(QOS_CLASS_USER_INITIATED, 0);
    dispatch_apply(1000, q, ^(size_t i) {
        atomic_fetch_add_explicit(&sum, (long)i, memory_order_relaxed);
    });
    printf("sum = %ld (expected 499500)\n", atomic_load(&sum));
    return 0;
}
    $ clang -O2 -Wall gcd_smoke.c -o gcd_smoke && ./gcd_smoke

  5. 用 TSan 抓一个故意写的数据竞争。两个线程不加锁地 ++ 同一个 int：Catch a deliberate data race with TSan. Two threads ++ the same int with no lock:
    // race.cpp: 两个线程不加锁地 ++ 同一个 int，这是数据竞争（data race）
#include <cstdio>
#include <thread>

int counter = 0;

int main() {
    auto work = [] { for (int i = 0; i < 100000; ++i) ++counter; };
    std::jthread a(work), b(work);
    a.join(); b.join();
    std::printf("counter = %d (expected 200000)\n", counter);
}

自测

Self-check

1. 你想让一个计算线程尽量跑在 P 核上。在这台 Mac 上应该怎么做？

1. You want a compute thread to run on a P core as much as possible. What should you do on this Mac?

macOS 只接受 QoS 这种提示。affinity 策略在本机返回 46（service not supported）；taskset 是 Linux 的命令，macOS 上没有。macOS only accepts a hint such as QoS. The affinity policy returns 46 (service not supported) on this machine; taskset is a Linux command and does not exist on macOS.

2. 为什么本专题的实验不放进虚拟机里做？

2. Why are this topic’s labs not done inside a VM?

虚拟机里当然能编 C++20；本专题的实验也完全不碰内核，正因为不碰内核才可以在本机做。真正的理由是测量必须在真硬件上。A VM can of course compile C++20; and this topic’s labs never touch the kernel, which is exactly why they can run on the host. The real reason is that the measurements must be made on real hardware.

3. 为了避免 false sharing，要把两个计数器隔开。在这台 Mac 上至少隔多少字节？

3. To avoid false sharing you separate two counters. On this Mac, by at least how many bytes?

hw.cachelinesize 在本机是 128。64 字节是 x86 的 cache line，在这里两个计数器仍会落进同一行。16 KB 是本机的内存页大小，与 cache line 无关，隔这么远只是浪费。hw.cachelinesize is 128 on this machine. 64 bytes is the x86 cache line, and here two counters would still land in one line. 16 KB is this machine’s page size, unrelated to the cache line; separating that far only wastes memory.

4. race.cpp 在 TSan 下打印了正确的 200000，但 TSan 报了数据竞争，进程以 134 退出。这说明什么？

4. Under TSan, race.cpp prints the correct 200000, but TSan reports a data race and the process exits with 134. What does this mean?

TSan 判断的是两次写之间有没有同步，与结果无关；不带 TSan 的版本丢了将近一半的加法。程序本身没有崩：设 TSAN_OPTIONS=abort_on_error=0 后退出码变成 66，abort 来自 TSan 的退出处理。TSan judges whether there is synchronization between the two writes, regardless of the result; the build without TSan lost almost half of the increments. The program itself did not crash: with TSAN_OPTIONS=abort_on_error=0 the exit status becomes 66, and the abort comes from TSan’s exit handling.
