核心概念

Core concepts

你改了一处代码，计时从 22.6 ms 变成 20.9 ms（举例用的数字）。这是变快了，还是这台同时跑着别的任务的机器恰好安静了一会儿？就算真快了，时间到底花在哪一行，离这台机器能给的上限还有多远，是该继续改计算、少搬字节，还是该停手？没有方法，这几个问题只能靠猜，而猜错的代价是在不是瓶颈的地方花上几天。

You change one line and the timing goes from 22.6 ms to 20.9 ms (numbers for illustration). Did it get faster, or did this machine, which runs other jobs at the same time, just happen to be quiet for a moment? And if it really is faster, which line does the time go to, how far is it from what this machine can give, and should you keep changing the computation, move fewer bytes, or stop? Without a method these questions are guesswork, and a wrong guess costs days spent on something that is not the bottleneck.

概念 1 和 2 的测量循环与基准方法回答「数字可不可信」，概念 3 到 5 的剖析工具回答「时间在哪」，概念 7 和 8 的 roofline 回答「离上限多远、还该不该改」。

The measurement loop and benchmark method of concepts 1 and 2 answer whether a number can be trusted, the profilers of concepts 3 to 5 answer where the time goes, and the roofline of concepts 7 and 8 answers how far from the limit you are and whether to keep going.

1. 测量循环：每次只回答一个问题

1. The measurement loop: one question per round

性能工作最常见的失败不是不会优化，而是改了五处、快了 30 %，却不知道是哪一处起的作用，甚至不知道这 30 % 是不是噪声。办法是把它做成一个循环，每一圈只回答一个问题（图解 (a)）：

The most common failure in performance work is not a lack of optimisation skill but changing five things, getting 30 % faster, and not knowing which change did it, or even whether the 30 % is noise. The cure is to make it a loop in which each round answers exactly one question (diagram (a)):

  • 假设。写成一句能被测量推翻的话，例如「内循环每做两次浮点运算就要搬 24 字节，卡在访存上」。
  • Hypothesis. Write one sentence that a measurement could refute, for example: the inner loop moves 24 bytes for every two floating-point operations and is stuck on memory operations.
  • 基准。用概念 2 的方法量出现在的数字和它的波动范围。没有范围的数字不能和下一个数字比较。
  • Benchmark. Measure where you are now, with its spread, by the method of concept 2. A number without a range cannot be compared with the next number.
  • 剖析。用 sample（或 VM 里的 perf）确认时间确实花在假设说的地方。很多假设在这一步就被推翻了。
  • Profile. Use sample (or perf in the VM) to confirm the time really goes where the hypothesis says. Many hypotheses die at this step.
  • 只改一处。并且先确认结果没变：本页的 NEON 版本和原版本逐位相同才算数。
  • Change one thing. And first confirm the result did not change: this page’s NEON version only counts because it is bit-for-bit identical to the original.
  • 复测。同样的方法、同样的机器状态，两组范围不重叠才说「变快了」。
  • Re-measure. Same method, same machine state; say it got faster only when the two ranges do not overlap.

什么时候停：当概念 7 的 roofline 说剩下的差距已经很小，或者剩下的差距要靠你不愿付的代价（可读性、可移植性）去换。

When to stop: when the roofline of concept 7 says the remaining gap is small, or when closing it would cost something you are not willing to pay (readability, portability).

  • 预热。第一次调用 25.8 ms，之后稳定在 22 ms 左右：第一次要建 GCD 的工作线程、第一次写 C 的 8 MB 要缺页。冷进程里的第一次中位数 23.85 ms、平均 25.16 ms，最慢 34.6 ms。缺页的代价在大缓冲区上更明显：Lab A 第 6 步第一次写 1 GiB 的缓冲区用了 20 到 187 ms（随线程数和运行而变），之后读一遍只要 8 到 14 ms。
  • Warm-up. The first call takes 25.8 ms and later ones settle around 22 ms: the first call creates GCD’s worker threads and takes page faults on its first write to the 8 MB of C. Across cold processes the first call has a median of 23.85 ms, a mean of 25.16 ms and a worst case of 34.6 ms. Page faults cost more on big buffers: in step 6 of Lab A the first write to a 1 GiB buffer took 20 to 187 ms (varying with the thread count and the run), while each later read of it takes only 8 to 14 ms.
  • 中位数，不是平均数。干扰只会让程序变慢，不会让它变快，所以误差是单边的：几个特别慢的样本把平均数往上拉，中位数不动。冷进程那组里平均数比中位数高 1.3 ms，主要来自前几个慢样本。最小值是「最好情况」，适合比较代码本身，但不代表用户看到的时间；所以中位数和范围一起报。
  • The median, not the mean. Interference only ever makes a program slower, never faster, so the error is one-sided: a few very slow samples pull the mean up while the median stays put. In the cold-process set the mean is 1.3 ms above the median, mostly from the first few slow samples. The minimum is the best case, useful for comparing the code itself but not what a user sees; so report the median together with the range.
  • 负载是真的。这台机器上同时跑着别的会话和构建任务。4 个忙进程让中位数从 22.0 ms 涨到 32.7 ms，10 个忙进程涨到 40.9 ms，标准差从 0.5 涨到 5.6。写作期间有一次 1 分钟负载平均到了 17.76，那一轮测出的带宽是 126.5 GB/s，安静时是 131.7 到 132.4 GB/s。所以每次计时前后都记下 uptime，范围突然变宽时先看负载，不要先怀疑代码。
  • Load is real. This machine runs other sessions and build jobs at the same time. Four busy processes raise the median from 22.0 ms to 32.7 ms, ten raise it to 40.9 ms, and the standard deviation grows from 0.5 to 5.6. Once during writing the 1-minute load average reached 17.76, and the bandwidth measured in that round was 126.5 GB/s against 131.7 to 132.4 GB/s when quiet. So record uptime before and after each timing, and when the range suddenly widens, look at the load before suspecting the code.
  • 能固定的固定下来。macOS 没有 CPU 亲和性（affinity），线程落在哪个核上由内核决定；能做的是固定 QoS（GCD 队列的 QoS 或 pthread_set_qos_class_self_np）、固定线程数、接着电源、关掉重的程序，并在报告里写下这些条件。x86 Linux 服务器上还要固定 CPU 频率和 NUMA 节点，这里没有 NUMA。
  • Pin what can be pinned. macOS has no CPU affinity, and the kernel decides which core a thread lands on; what you can do is fix the QoS (a GCD queue’s QoS or pthread_set_qos_class_self_np), fix the thread count, stay on mains power, close heavy programs, and write those conditions into the report. On x86 Linux servers you would also fix the CPU frequency and the NUMA node; there is no NUMA here.
  • 检查结果，而不只是时间。每个程序都打印一个校验和。Phase 5 的串行基线量出 0 ms，就是因为编译器发现结果没被用到、把调用提出了循环；打印或比较结果能防住这一类「快得离谱」。
  • Check the result, not only the time. Every program prints a checksum. Phase 5’s serial baseline measured 0 ms precisely because the compiler saw the call could be hoisted out of the loop; printing or comparing the result guards against this kind of absurdly fast number.

  • 先看最后的 Sort by top of stack。它按「栈顶是哪个函数」汇总所有线程。rows 占 18450 次，约为全部栈顶样本的 92 %：时间几乎全在自己的代码里。
  • Read Sort by top of stack at the end first. It totals all threads by which function is on top of the stack. rows has 18450, about 92 % of all top-of-stack samples: nearly all the time is in your own code.
  • 再看行号。用 -g 编译后，每一帧带着 文件:行。matmul_prof.c:21 就是最内层的 C[i][j] += a * B[k][j]。逗号分开的几个偏移（+ 148,140,...）是这一帧里被采到的不同指令地址，可以拿去和 otool -tvV 的反汇编对照。
  • Then the line numbers. Built with -g, every frame carries file:line. matmul_prof.c:21 is the innermost C[i][j] += a * B[k][j]. The comma-separated offsets (+ 148,140,...) are the different instruction addresses sampled in that frame, and can be matched against the disassembly from otool -tvV.
  • 主线程也在干活。调用 dispatch_apply 的主线程自己也跑 rows（Phase 5 的概念 5）；它偶尔停在 __ulock_wait，是在等最后几块被别的线程做完。
  • The main thread works too. The main thread that called dispatch_apply runs rows itself (concept 5 of Phase 5); its occasional __ulock_wait is waiting for other threads to finish the last chunks.
  • 停在 __workq_kernreturn 的是空闲的池线程。这次采样里有 21 个线程，其中约 10 个大部分时间在 rows，其余的大多停在 __workq_kernreturn：那是 GCD 线程池里没活、在内核里等活的线程，不是你的程序在等锁。
  • Threads parked in __workq_kernreturn are idle pool threads. This sample has 21 threads; about 10 spend most of their samples in rows, and most of the rest sit in __workq_kernreturn: GCD pool threads with no work, waiting in the kernel for some, not your program waiting on a lock.
  • 内联会把热帧藏起来。对 NEON 版本采样，栈顶第一名变成了 __run_block_invoke（12616 次），行号是 mm.c:62，也就是调用 tile_neon 的那一行：编译器把 tile_neon 内联进了 block。剖析时要么接受这一点、看地址，要么给想看的函数加 __attribute__((noinline))，像 matmul_prof.c 那样。
  • Inlining hides the hot frame. Sampling the NEON version, the top entry becomes __run_block_invoke (12616 samples) at mm.c:62, the line that calls tile_neon: the compiler inlined tile_neon into the block. When profiling, either accept that and read the addresses, or put __attribute__((noinline)) on the function you want to see, as matmul_prof.c does.

5. 内核 VM 里的 Linux perf

5. Linux perf in the kernel VM

macOS 上没有 perf。Linux 的 perf 有两种用法，本页的 Lab B 两种都用：

There is no perf on macOS. Linux perf has two modes, and this page’s Lab B uses both:

  • perf stat 数事件。程序从头跑到尾，结束时打印每个事件的总数：软件事件（task-clock、context-switches、cpu-migrations、page-faults）由内核自己数，总能用；硬件事件（cycles、instructions、branch-misses、cache-misses、L1-dcache-load-misses）要 CPU 的性能监控单元（PMU）。加 -r 5 跑 5 次，每个数字后面会带 ( +- x% ) 的波动。
  • perf stat counts events. The program runs start to finish, and at the end the total of each event is printed: software events (task-clock, context-switches, cpu-migrations, page-faults) are counted by the kernel itself and always work; hardware events (cycles, instructions, branch-misses, cache-misses, L1-dcache-load-misses) need the CPU’s performance monitoring unit (PMU). With -r 5 it runs 5 times and each number carries a ( +- x% ) spread.
  • perf record 采样。按事件或频率打断程序、记下指令地址（加 -g 记调用栈），perf report 按函数汇总，perf annotate 按指令汇总。它回答的问题和 sample 一样，但能精确到指令，能按硬件事件（例如 cache miss）采样。
  • perf record samples. It interrupts the program on an event or at a frequency and records the instruction address (with -g, the call stack); perf report totals by function and perf annotate by instruction. It answers the same question as sample, down to the instruction, and can sample on hardware events such as cache misses.

在 VM 里用它有三点要先想清楚：

Three things to think through before using it in a VM:

  • 硬件计数器可能不在。VM 里的硬件事件要靠 QEMU 把 PMU 交给客体。内核专题的 VM 默认用纯软件模拟的 TCG，可以换成 -accel hvf -cpu host。这两种方式下客体能不能看到 PMU、看到的数字是模拟的还是来自真实硬件，本页没有验证。没有 PMU 时 perf stat 把硬件事件标成 <not supported>（内核专题 Phase 6 记录），这时只用软件事件。
  • Hardware counters may be missing. Hardware events in a VM depend on QEMU handing a PMU to the guest. The kernel topic’s VM defaults to TCG, pure software emulation, and can switch to -accel hvf -cpu host. Whether the guest sees a PMU under either, and whether its numbers are emulated or come from the real hardware, is unverified on this page. Without a PMU, perf stat marks hardware events as <not supported> (recorded in the kernel topic’s Phase 6); use only software events then.
  • VM 的数字不是 Mac 的数字。VM 默认只有 2 个虚拟 CPU（-smp 2），TCG 下每条 NEON 指令都是软件模拟的。拿到的计数只用来回答「两个版本之间谁多谁少」，比如 NEON 分块版本的 load 指令是否少得多；绝对时间以 Mac 上的为准。
  • VM numbers are not Mac numbers. The VM has only 2 virtual CPUs by default (-smp 2), and under TCG every NEON instruction is emulated in software. Use the counts only to answer which of two versions has more or fewer of something, for example whether the NEON blocked version issues far fewer loads; the Mac’s wall times are the authority on absolute time.
  • busybox 里没有 perf。内核专题 Phase 6 指出 perf 需要完整的用户态，busybox initramfs 里没有；要在一个 arm64 Debian 客体里装 linux-perf。这个客体用同一个 QEMU 启动，怎样准备 Debian 镜像本页不展开（查 Debian 和 QEMU 的文档）。

6. 诊断 false sharing 和带宽上限

6. Diagnosing false sharing and bandwidth limits

两种最常见的「加线程不变快」，在没有硬件计数器的 Mac 上也能凭特征认出来，再用一个对照实验确认：

The two most common cases of adding threads without getting faster can be recognised by their signatures even on a Mac without hardware counters, then confirmed with one controlled experiment:

  • false sharing 的特征。每个线程写的是自己的数据，逻辑上不共享，可线程越多越慢，甚至比单线程还慢；sample 显示时间全在那几条简单的写指令上。确认的办法是只改布局：每个线程的数据各自对齐、填充到 hw.cachelinesize（这台机器是 128 字节），时间骤降就是它。Phase 0 Lab B 的实测：两个计数器挤在一行比各占 128 字节慢 7 倍多。Linux 上专门查它的工具是 perf c2c，但它的手册页说在 Arm64 上要靠 SPE（Statistical Profiling Extension），VM 里大概率没有（未验证）。
  • The signature of false sharing. Each thread writes its own data, nothing is logically shared, yet more threads make it slower, even slower than one thread; sample shows the time all on a few simple store instructions. Confirm it by changing only the layout: align and pad each thread’s data to hw.cachelinesize (128 bytes on this machine); if the time collapses, that was it. Measured in Phase 0 Lab B: two counters in one line are more than 7 times slower than 128 bytes each. The Linux tool made for it is perf c2c, but its manual page says that on Arm64 it relies on SPE (the Statistical Profiling Extension), which the VM very likely lacks (unverified).
  • 带宽上限的特征。每字节数据只做很少的计算，算出的 GB/s 接近你实测的流式读带宽，再加线程不变快。Phase 0 的求和从 2 个线程到 4 个线程都停在约 83 GB/s（P 簇封顶），加上 E 簇才到 131 GB/s。确认的办法是算它的字节数和时间，和概念 7 的带宽线比；如果已经贴着线，改代码的计算部分没有用，只能少搬字节（融合两遍循环、用更小的数据类型、分块让数据留在 cache 里）。
  • The signature of a bandwidth limit. Very little computation per byte of data, the computed GB/s close to your measured streaming-read bandwidth, and no gain from more threads. Phase 0’s sum stayed at about 83 GB/s from 2 threads to 4 (the P cluster’s ceiling) and reached 131 GB/s only with the E cluster added. Confirm it by computing its bytes and time and comparing with the bandwidth line of concept 7; if it already sits on the line, changing the computation does nothing and the only way forward is to move fewer bytes (fuse two passes, use a smaller data type, block so the data stays in cache).
  • 两者以外。如果既不是 false sharing、也没贴着带宽线，还要考虑 P 核和 E 核的速度差（Phase 5 的静态平分）、锁竞争（Phase 2）和串行部分（Phase 0 的 Amdahl）。
  • Beyond these two. If it is neither false sharing nor against the bandwidth line, consider the P versus E core speed gap (Phase 5’s static split), lock contention (Phase 2) and the serial part (Phase 0’s Amdahl).

7. 这台 M5 的 roofline，用实测的数字

7. This M5’s roofline, in measured numbers

roofline 模型（Williams、Waterman、Patterson，2009）用两个数给一个内核定上限。算术强度 I 是它每从内存搬 1 字节做多少次浮点运算（flop/byte）。可达到的性能 P = min(峰值算力, I × 内存带宽)。在对数坐标上，带宽那一项是一条斜线，峰值算力是一条水平线，两条线的交点叫脊点（ridge point）：强度在脊点左边的内核受内存限制，右边的受计算限制。两条线都要在你的机器上量，不抄规格表。Lab A 第 6 步的实测（2026-10-31，中位数，20 次；峰值是 7 次的中位数）：

The roofline model (Williams, Waterman and Patterson, 2009) bounds a kernel with two numbers. Its arithmetic intensity I is how many floating-point operations it performs per byte moved from memory (flops per byte). Attainable performance is P = min(peak compute, I × memory bandwidth). On log axes the bandwidth term is a sloped line and peak compute a horizontal one, and where they meet is the ridge point: kernels with an intensity left of the ridge are memory-bound, those to the right compute-bound.   • 作品项目的模糊内核（FP32，预测）。可分离的 5 点高斯模糊，每个像素每一遍 5 次乘加（10 flop），每一遍读 4 字节、写 4 字节。分两遍做：I = 20 / 16 = 1.25 flop/byte，上限约 165 GFLOP/s；把两遍融合成一遍、中间结果留在 cache 里：I = 20 / 8 = 2.5，上限约 330 GFLOP/s。两者都在 FP32 脊点 4.9 的左边，所以模糊是受内存限制的，融合比任何 NEON 技巧都重要。这两个数是按模型算的预测（没算写分配带来的额外读），作品项目要你实测。

8. 从剖析到修改：已经向量化了，还能怎么快

8. From profile to fix: already vectorized, so how else to go faster

Lab A 的剖析说时间全在第 21 行。按 Phase 6 的第一反应是「用 NEON 改写它」，但先看编译器做了什么：-Rpass=loop-vectorize 报 matmul_prof.c:21:13: remark: vectorized loop (vectorization width: 2, interleaved count: 4)，反汇编里内循环就是 4 条 fmla.2d。它已经是 NEON 了，照着同样的循环手写 intrinsics 只会得到同样的指令。

Lab A’s profile says the time is all on line 21. The first instinct from Phase 6 is to rewrite it with NEON, but look first at what the compiler did: -Rpass=loop-vectorize reports matmul_prof.c:21:13: remark: vectorized loop (vectorization width: 2, interleaved count: 4), and in the disassembly the inner loop is four fmla.2d instructions. It is NEON already, and hand-written intrinsics for the same loop would only produce the same instructions.

真正的问题在每条 fmla 周围的访存：每处理 8 个 double，循环要 ldp 读 64 字节的 B、ldp 读 64 字节的 C、stp 写回 64 字节的 C，换来 16 flop。对 L1 的强度是 16 / 192 ≈ 0.083 flop/byte：C 的那一行每个 k 都要读一遍、写一遍。修改是寄存器分块（register blocking）：一次算 C 的 4 行 × 8 列，这 32 个 double 放在 16 个 NEON 寄存器里，k 从头走到尾都不写回；每个 k 只读 B 的 8 个数（64 字节）和 A 的 4 个数（32 字节），做 16 条 fmla（64 flop）。对 L1 的强度变成 64 / 96 ≈ 0.67，是原来的 8 倍。

The real problem is the memory traffic around each fmla: for every 8 doubles the loop does an ldp of 64 bytes of B, an ldp of 64 bytes of C and an stp of 64 bytes of C back, in exchange for 16 flops. Its intensity against L1 is 16 / 192 ≈ 0.083 flops per byte: the row of C is read and written once for every k. The fix is register blocking: compute 4 rows × 8 columns of C at a time, keeping those 32 doubles in 16 NEON registers with no write-back for the whole k loop; each k then reads only 8 numbers of B (64 bytes) and 4 of A (32 bytes) and issues 16 fmlas (64 flops). The intensity against L1 becomes 64 / 96 ≈ 0.67, 8 times the original.

结果：中位数从 22.0–22.8 ms 降到 14.0–15.5 ms（多次运行的范围，两组不重叠），和原版本逐位相同。没变快到 8 倍，说明访存不是唯一的限制；剩下的差距到 317 GFLOP/s 的屋顶约 2 倍，可能来自 B 按列块读时跨行的访问、E 核更慢以及 E 簇只有 6 MB 的 L2 装不下 8 MB 的 B（推断，本页没有逐项拆开测）。这正是 Lab B 想用计数器去看的东西。

The result: the median falls from 22.0–22.8 ms to 14.0–15.5 ms (ranges across several runs that do not overlap), bit-for-bit identical to the original. It did not get 8 times faster, so memory traffic is not the only limit; the remaining gap of about 2 times to the 317 GFLOP/s roof may come from reading B by column blocks across rows, from the slower E cores, and from the E cluster’s 6 MB L2 being unable to hold the 8 MB of B (inference; this page did not separate them). That is exactly what Lab B wants to look at with counters.

常见误解

Common misconceptions

  • 误解：剖析说热点在一个循环里，就该用 NEON 手写它。→ 实际：Lab A 的热循环已经被自动向量化成 4 条 fmla.2d，手写同样的循环只会得到同样的指令；要改的是访存模式。
  • 误解：多跑几次取平均就够了。→ 实际：误差是单边的，平均数会被几次慢样本拉高；报中位数和范围，并记下负载（4 个忙进程就让中位数从 22.0 ms 涨到 32.7 ms）。
  • 误解：受内存限制的内核，换更快的计算代码总能快一点。→ 实际：点积已经以 32.4 GFLOP/s 贴着 33 GFLOP/s 的屋顶，只有少搬字节（融合、分块、更小的类型）才有用。
  • Myth: if the profile puts the hot spot in a loop, rewrite it by hand in NEON. → Fact: Lab A’s hot loop was already auto-vectorized into four fmla.2d instructions, so hand-writing the same loop yields the same instructions; what has to change is the memory access pattern.
  • Myth: running it a few times and taking the mean is enough. → Fact: the error is one-sided and a few slow samples pull the mean up; report the median with the range and record the load (four busy processes raised the median from 22.0 ms to 32.7 ms).
  • Myth: a memory-bound kernel always gains a little from faster computation code. → Fact: the dot product already sits at 32.4 GFLOP/s against a 33 GFLOP/s roof, and only moving fewer bytes (fusion, blocking, smaller types) helps.

#include <dispatch/dispatch.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

enum { N = 1024, CHUNKS = 100 };
static double A[N][N], B[N][N], C[N][N];

static double now_s(void) {
    struct timespec ts; clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

__attribute__((noinline)) static void rows(int r0, int r1) {
    for (int i = r0; i < r1; ++i) {
        memset(C[i], 0, sizeof C[i]);
        for (int k = 0; k < N; ++k) {
            double a = A[i][k];
            for (int j = 0; j < N; ++j) C[i][j] += a * B[k][j];   // 热循环
        }
    }
}

static void matmul(void) {
    dispatch_apply(CHUNKS, DISPATCH_APPLY_AUTO, ^(size_t c) {
        rows((int)(c * N / CHUNKS), (int)((c + 1) * N / CHUNKS));
    });
}

int main(int argc, char **argv) {
    int reps = argc > 1 ? atoi(argv[1]) : 200;
    for (int i = 0; i < N; ++i)
        for (int j = 0; j < N; ++j) { A[i][j] = (i + j) % 7 - 3; B[i][j] = (i * j) % 5 - 2; }
    double t0 = now_s();
    for (int r = 0; r < reps; ++r) matmul();
    double sum = 0;
    for (int i = 0; i < N; ++i) for (int j = 0; j < N; ++j) sum += C[i][j];
    printf("%d reps, %.1f ms per multiply, checksum %.0f\n", reps, (now_s() - t0) / reps * 1e3, sum);
    return 0;
}

#include <arm_neon.h>
#include <dispatch/dispatch.h>
#include <math.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

enum { N = 1024 };
static double A[N][N], B[N][N], C[N][N];

static double now_s(void) {
    struct timespec ts; clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static void rows_scalar(int r0, int r1) {
    for (int i = r0; i < r1; ++i) {
        memset(C[i], 0, sizeof C[i]);
        for (int k = 0; k < N; ++k) {
            double a = A[i][k];
            #pragma clang loop vectorize(disable) interleave(disable)
            for (int j = 0; j < N; ++j) C[i][j] += a * B[k][j];
        }
    }
}

static void rows_auto(int r0, int r1) {
    for (int i = r0; i < r1; ++i) {
        memset(C[i], 0, sizeof C[i]);
        for (int k = 0; k < N; ++k) {
            double a = A[i][k];
            for (int j = 0; j < N; ++j) C[i][j] += a * B[k][j];
        }
    }
}

static void tile_neon(int i0, int j0) {
    float64x2_t c[4][4];
    for (int r = 0; r < 4; ++r) for (int q = 0; q < 4; ++q) c[r][q] = vdupq_n_f64(0);
    for (int k = 0; k < N; ++k) {
        float64x2_t b0 = vld1q_f64(&B[k][j0]), b1 = vld1q_f64(&B[k][j0 + 2]);
        float64x2_t b2 = vld1q_f64(&B[k][j0 + 4]), b3 = vld1q_f64(&B[k][j0 + 6]);
        for (int r = 0; r < 4; ++r) {
            double a = A[i0 + r][k];
            c[r][0] = vfmaq_n_f64(c[r][0], b0, a); c[r][1] = vfmaq_n_f64(c[r][1], b1, a);
            c[r][2] = vfmaq_n_f64(c[r][2], b2, a); c[r][3] = vfmaq_n_f64(c[r][3], b3, a);
        }
    }
    for (int r = 0; r < 4; ++r) for (int q = 0; q < 4; ++q) vst1q_f64(&C[i0 + r][j0 + 2 * q], c[r][q]);
}

using clk = std::chrono::steady_clock;
static double ms_since(clk::time_point t0) { return std::chrono::duration<double, std::milli>(clk::now() - t0).count(); }

static float sum_range(const float *p, size_t n) {          // 8 个累加器，每次读 128 字节
    float32x4_t a[8];
    for (auto &x : a) x = vdupq_n_f32(0);
    for (size_t i = 0; i < n; i += 32)
        for (int q = 0; q < 8; ++q) a[q] = vaddq_f32(a[q], vld1q_f32(p + i + 4 * q));
    for (int q = 1; q < 8; ++q) a[0] = vaddq_f32(a[0], a[q]);
    return vaddvq_f32(a[0]);
}
static float dot_range(const float *x, const float *y, size_t n) {
    float32x4_t a[8];
    for (auto &v : a) v = vdupq_n_f32(0);
    for (size_t i = 0; i < n; i += 32)
        for (int q = 0; q < 8; ++q) a[q] = vfmaq_f32(a[q], vld1q_f32(x + i + 4 * q), vld1q_f32(y + i + 4 * q));
    for (int q = 1; q < 8; ++q) a[0] = vaddq_f32(a[0], a[q]);
    return vaddvq_f32(a[0]);
}
template <class V, class S> static double fma_chain(long iters) {   // 16 条独立链，不受 fma 延迟限制
    V a[16], b = S::dup(1.0000001), c = S::dup(0.9999999);
    for (int q = 0; q < 16; ++q) a[q] = S::dup(q);
    for (long i = 0; i < iters; ++i)
        for (int q = 0; q < 16; ++q) a[q] = S::fma(a[q], b, c);
    double s = 0; for (int q = 0; q < 16; ++q) s += S::lane0(a[q]);
    return s;
}

constexpr int N = 1024;
static double A[N][N], B[N][N], C[N][N];

__attribute__((noinline)) static void rows_auto(int r0, int r1) {
    for (int i = r0; i < r1; ++i) {
        std::memset(C[i], 0, sizeof C[i]);
        for (int k = 0; k < N; ++k) {

            for (int j = 0; j < N; ++j) C[i][j] += a * B[k][j];

__attribute__((noinline)) static void tile_neon(int i0, int j0) {

    for (auto &r : c) for (auto &q : r) q = vdupq_n_f64(0);
    for (int k = 0; k < N; ++k) {
        float64x2_t b[4] = {vld1q_f64(&B[k][j0]), vld1q_f64(&B[k][j0 + 2]), vld1q_f64(&B[k][j0 + 4]), vld1q_f64(&B[k][j0 + 6])};

}

static void run(bool neon, unsigned T) {
    std::atomic<int> next{0};
    int tasks = neon ? N / 8 : 128;                  // neon：每个任务一个 8 列面板；auto：每个任务 8 行
    std::vector<std::jthread> ts;
    for (unsigned t = 0; t < T; ++t)
        ts.emplace_back([&] {
            for (int x; (x = next.fetch_add(1, std::memory_order_relaxed)) < tasks;)
                if (neon) for (int i0 = 0; i0 < N; i0 += 4) tile_neon(i0, x * 8);
                else rows_auto(x * 8, x * 8 + 8);
        });
}

perf record -g -o auto.data ./mm_portable auto
perf report -i auto.data --stdio --sort symbol | head -30
perf annotate -i auto.data --stdio -s rows_auto | head -60
perf record -g -o neon.data ./mm_portable neon
perf report -i neon.data --stdio --sort symbol | head -30
    预期：rows_auto 或 tile_neon 占绝大部分样本，perf annotate 里百分比最高的指令落在 fmla 和它前后的 ldp、stp 上（g++ 生成的指令可能和 clang 不同）。没有 PMU 时 perf record 会退回到基于时钟的软件事件，仍然能给出函数级的热点。Expected: rows_auto or tile_neon holds the great majority of samples, and in perf annotate the highest percentages fall on the fmla instructions and the ldps and stps around them (g++ may generate different instructions from clang). Without a PMU, perf record falls back to a clock-based software event and still gives function-level hot spots.
  6. 和 Mac 对照：把客体里两个版本的时间比（auto ÷ neon）和 Mac 上的比（23.2 ÷ 16.8 ≈ 1.4，mm.c 是约 1.5）放在一起。hvf 下比值应当相近；TCG 下 NEON 指令是模拟的，比值没有意义。计数器回答「为什么」，Mac 的墙钟回答「多快」。Compare with the Mac: put the guest’s ratio of the two versions (auto ÷ neon) beside the Mac’s (23.2 ÷ 16.8 ≈ 1.4; about 1.5 for mm.c). Under hvf the ratios should be similar; under TCG the NEON instructions are emulated and the ratio means nothing. The counters answer why; the Mac’s wall clock answers how fast.
交付物：客体的启动方式（hvf 还是 TCG）、nproc 和 perf_event_paranoid；两个版本的 perf stat 软件事件和硬件事件输出原文（包括 <not supported>）；perf report 的前几行和 rows_auto 的 perf annotate 节选；第 6 步的对照。写进当天日志，并回答：在这个客体里，哪些数字能拿来解释 Mac 上的 1.5 倍，哪些不能？
Deliverables: how the guest was booted (hvf or TCG), nproc and perf_event_paranoid; the raw perf stat output for software and hardware events for both versions (including any <not supported>); the first lines of perf report and an excerpt of perf annotate for rows_auto; the comparison from step 6. Write them into that day’s log and answer: in this guest, which numbers can explain the Mac’s 1.5 times, and which cannot?

自测

Self-check

1. 旁边有 10 个忙进程时，./mm auto 20 次的结果是中位数 40.9 ms、平均 41.1 ms、最小 32.9 ms、最大 50.3 ms。你想拿它和明天改过的版本比较。该怎么报这个数？

1. With 10 busy processes alongside, 20 runs of ./mm auto give a median of 40.9 ms, a mean of 41.1 ms, a minimum of 32.9 ms and a maximum of 50.3 ms. You want to compare it with tomorrow’s modified version. How should you report this number?

干扰只会让程序变慢，误差是单边的，平均数会被慢样本拉高，在负载下尤其如此。最小值适合比较代码本身，但单报它会藏起用户实际看到的时间，而且在负载下连最小值（32.9 ms）也比安静时的中位数（22.0 ms）慢得多。真正的问题是负载本身：在 10 个忙进程旁边量出的数，不能和另一种负载下量出的数比较，所以先重测，再报中位数加范围和负载。Interference only slows a program down, so the error is one-sided and the mean gets pulled up by slow samples, especially under load. The minimum is useful for comparing the code itself, but reporting it alone hides the time a user actually sees, and under this load even the minimum (32.9 ms) is far slower than the quiet median (22.0 ms). The real problem is the load itself: a number measured beside 10 busy processes cannot be compared with one measured under different load, so re-measure first, then report the median with its range and the load.

2. sample 说 92 % 的时间在第 21 行的内循环，-Rpass=loop-vectorize 说这一行 vectorized loop (vectorization width: 2, interleaved count: 4)。下一步最可能让它变快的是哪一个？

2. sample says 92 % of the time is in the inner loop on line 21, and -Rpass=loop-vectorize says that line is a vectorized loop (vectorization width: 2, interleaved count: 4). Which next step is most likely to make it faster?

循环已经是 fmla.2d 了，照原样手写 intrinsics 得到的还是同样的指令和同样的访存。线程数也不是瓶颈：只有 10 个核，dispatch_apply 的线程数不超过这个 QoS 的并行度，多开只是超订（Phase 1）。瓶颈在每 16 flop 要读写 192 字节；寄存器分块把对 L1 的强度从 0.083 提到 0.67，本页实测 22.4 ms 降到 14.0 ms。The loop is already fmla.2d; hand-writing intrinsics for the same loop yields the same instructions and the same memory traffic. Nor is the thread count the bottleneck: there are only 10 cores, dispatch_apply does not exceed the QoS’s parallelism, and more threads would only oversubscribe (Phase 1). The bottleneck is 192 bytes read and written per 16 flops; register blocking raises the intensity against L1 from 0.083 to 0.67, and this page measured 22.4 ms falling to 14.0 ms.

3. FP32 点积的强度是 0.25 flop/byte，屋顶给 33 GFLOP/s，实测 32.4 GFLOP/s。程序里这一步还是太慢，怎样才能让它整体变快？

3. The FP32 dot product has an intensity of 0.25 flops per byte, the roof allows 33 GFLOP/s, and it measures 32.4 GFLOP/s. This step of the program is still too slow. What can make it faster overall?

它已经贴着带宽那条斜线，时间由搬的字节数决定，不由计算决定。更多累加器只能让计算更快，而计算本来就不是限制；vDSP_dotpr 再好也要读同样多的字节，上限还是 33 GFLOP/s。唯一的办法是减少从内存搬的字节，也就是提高强度。It already sits on the bandwidth slope, so its time is set by the bytes moved, not by computation. More accumulators can only speed up the computation, which is not the limit; however good vDSP_dotpr is, it reads the same bytes and its ceiling is still 33 GFLOP/s. The only way is to move fewer bytes from memory, which means raising the intensity.

4. 在 VM 里运行 perf stat -e cycles,instructions,task-clock,page-faults ./mm_portable auto，cycles 和 instructions 显示 <not supported>，task-clock 和 page-faults 有数字。最可能的原因是什么？

4. In the VM, perf stat -e cycles,instructions,task-clock,page-faults ./mm_portable auto shows <not supported> for cycles and instructions, while task-clock and page-faults have numbers. What is the most likely cause?

权限不够时 perf 报的是权限错误并提示 perf_event_paranoid，不是 <not supported>；而且同一条命令里的软件事件有数字，说明能计数。运行时间长短只影响数字大小，不会让事件变成不支持。<not supported> 是 VM 没有把 PMU 交给客体的典型表现（内核专题 Phase 6 记录），这时只用软件事件。With insufficient permission perf reports a permission error that mentions perf_event_paranoid, not <not supported>; and the software events in the same command have numbers, so counting works. Run time affects only the size of the numbers and never makes an event unsupported. <not supported> is the typical sign that the VM did not hand a PMU to the guest (recorded in the kernel topic’s Phase 6); use only software events then.

作品项目：并行图像模糊流水线

Capstone: a parallel image-blur pipeline

作品项目把整个专题放进一个程序：线程或 GCD 做并行（Phase 1、5），没有数据竞争（Phase 2、3，用 TSan 证明），OpenMP 作为另一种写法（Phase 5，装了 libomp 才做），NEON 做数据并行（Phase 6），最后交一份按本页方法写的测量报告。下面是规格和验收标准，不是写好的代码；本页没有实现它，概念 7 里它的两个数是预测。

The capstone puts the whole topic into one program: threads or GCD for parallelism (Phases 1 and 5), no data races (Phases 2 and 3, proven with TSan), OpenMP as an alternative form (Phase 5, only where libomp is installed), NEON for data parallelism (Phase 6), and a measurement report written by this page’s method. Below are the specification and the acceptance criteria, not finished code; this page did not implement it, and its two numbers in concept 7 are predictions.

规格

Specification

  • 输入。一张 8192 × 8192 的单通道 float32 图像（256 MiB，远大于任何 cache），用固定公式生成（例如 ((x * 7 + y * 13) % 256) / 255.0f），这样任何人都能复现。
  • Input. An 8192 × 8192 single-channel float32 image (256 MiB, far larger than any cache), generated by a fixed formula (for example ((x * 7 + y * 13) % 256) / 255.0f) so anyone can reproduce it.
  • 运算。可分离的 5 点高斯模糊，权重 1、4、6、4、1 除以 16：先横向一遍，再纵向一遍；边界按最近的像素取（clamp）。
  • Operation. A separable 5-tap Gaussian blur with weights 1, 4, 6, 4, 1 divided by 16: one horizontal pass, then one vertical pass; borders take the nearest pixel (clamp).
  • V0 参考版本。串行、标量、关掉自动向量化（#pragma clang loop vectorize(disable)），只用来定义正确结果和基线时间。
  • V0, the reference. Serial, scalar, with auto-vectorization disabled (#pragma clang loop vectorize(disable)); it only defines the correct result and the baseline time.
  • V1 并行版本。std::jthread 或 dispatch_apply 按行分块，块数和调度方式由你按 Phase 5 的结论选，在报告里说明理由。
  • V1, parallel. std::jthread or dispatch_apply over blocks of rows, with the chunk count and schedule chosen by you from Phase 5’s conclusions and justified in the report.
  • V2 OpenMP 版本。同样的循环写成 #pragma omp parallel for。没装 libomp 就在报告里写「未做」和原因，不算失败。
  • V2, OpenMP. The same loops as #pragma omp parallel for. Without libomp installed, write not done and why in the report; that is not a failure.
  • V3 NEON 版本。在 V1 的基础上，横向一遍用 float32x4_t 一次处理 4 个像素（intrinsics），纵向一遍同样处理；先看 -Rpass 的 remark，说明哪一遍原本没有被自动向量化、为什么。
  • V3, NEON. On top of V1, the horizontal pass handles 4 pixels at a time with float32x4_t intrinsics, and the vertical pass likewise; read the -Rpass remarks first and say which pass was not auto-vectorized to begin with, and why.
  • V4 融合版本。按条带（例如每次 64 行加上下各 2 行的边）做完横向一遍马上做纵向一遍，让中间结果留在 cache 里，不写回整张中间图像。这是概念 7 预测的强度从 1.25 到 2.5 的那一步。
  • V4, fused. Work in strips (for example 64 rows plus a 2-row border above and below), running the vertical pass right after the horizontal one so the intermediate stays in cache and the full intermediate image is never written back. This is the step concept 7 predicts takes the intensity from 1.25 to 2.5.
  • 另一条路：n-body。如果你更想做 n-body：N = 16384 个物体、float32、所有对之间直接求引力、每一步更新速度和位置，V0 到 V4 的结构不变（V4 换成按块复用位置数据）。它的强度远在脊点右边，屋顶换成 FP32 峰值；每次相互作用算多少 flop 要在报告里自己数清楚。
  • The alternative: n-body. If you would rather build n-body: N = 16384 bodies, float32, direct all-pairs gravity, updating velocities and positions each step, with the same V0 to V4 structure (V4 becomes blocking for reuse of the position data). Its intensity is far right of the ridge, so its roof is the FP32 peak; count the flops per interaction yourself and state the count in the report.

测量报告（必交）

The measurement report (required)

  • 环境。日期，sysctl 的核数和 cache 大小，clang --version，完整的编译命令，是否接着电源，计时前后的 uptime。
  • Environment. The date, the core counts and cache sizes from sysctl, clang --version, the full build commands, whether on mains power, and uptime before and after timing.
  • 方法。预热次数、计时次数、报中位数和最小到最大的范围；时钟用什么；怎样防止编译器把计算优化掉。
  • Method. The number of warm-ups and timed runs, the median with min-to-max range, which clock, and how you stop the compiler from optimising the computation away.
  • 结果表。每个版本一行：中位数、范围、相对 V0 的加速比、按字节模型算的 GB/s、GFLOP/s，以及和 V0 的最大误差。
  • Results table. One row per version: median, range, speedup over V0, GB/s from your byte model, GFLOP/s, and the maximum error against V0.
  • 扩展曲线。最好的版本在 1、2、4、6、8、10 个线程上的时间，用 P 核和 E 核、带宽上限和串行部分解释曲线的形状。
  • Scaling curve. The best version’s time at 1, 2, 4, 6, 8 and 10 threads, with the shape of the curve explained by P and E cores, the bandwidth ceiling and the serial part.
  • roofline。用你自己量的带宽和峰值画图，放上 V1、V3、V4，标出各自的强度。
  • Roofline. A plot from your own measured bandwidth and peaks, with V1, V3 and V4 placed and their intensities marked.
  • 剖析证据。最好的版本的 sample 节选，指出热帧和热行；有 Linux VM 的，附上 V1 和 V4 的 perf stat（包括 <not supported>）。
  • Profile evidence. A sample excerpt of the best version naming the hot frame and line; with the Linux VM, add perf stat for V1 and V4 (including any <not supported>).
  • 剩下的差距。一段话：最好的版本离屋顶还有多远，你认为原因是什么，哪些是测出来的、哪些是推断。
  • The remaining gap. One paragraph: how far the best version is below its roof, what you think the cause is, and which parts are measured and which inferred.

验收标准

Acceptance criteria

  1. 每个版本和 V0 的最大绝对误差不超过 1e-5（像素值在 0 到 1 之间），报告里有这个检查的输出。
  2. Every version’s maximum absolute error against V0 is at most 1e-5 (pixel values lie between 0 and 1), and the report contains the output of that check.
  3. V1 和 V2 在 1024 × 1024 的小图上用 -fsanitize=thread 运行，没有 ThreadSanitizer 警告。
  4. V1 and V2 run on a small 1024 × 1024 image under -fsanitize=thread with no ThreadSanitizer warnings.
  5. 每个时间都是至少 3 次预热之后至少 20 次的中位数，带最小值、最大值和负载平均。
  6. Every time is the median of at least 20 runs after at least 3 warm-ups, with its minimum, maximum and load average.
  7. 报告里有字节模型：每个版本每像素从内存读写多少字节，以及由此算出的 GB/s；V4 搬的字节比 V3 少，并且实测更快，或者报告解释了为什么没有更快。
  8. The report has a byte model: how many bytes each version reads and writes from memory per pixel, and the GB/s that follows; V4 moves fewer bytes than V3 and measures faster, or the report explains why it does not.
  9. 最好的版本达到它的屋顶（你的带宽乘以它的强度）的一半以上，或者报告用剖析证据说明为什么达不到。这是一个目标值，本页没有实现作品项目来验证它可以达到。
  10. The best version reaches more than half of its roof (your bandwidth times its intensity), or the report uses profile evidence to explain why not. This is a target; this page did not implement the capstone to verify that it is reachable.
  11. 一个脚本从源码编译所有版本、跑完全部测量、打印报告里的数字；另一个人在同型号的 Mac 上运行，中位数落在你报告的范围附近。
  12. One script builds every version from source, runs every measurement and prints the numbers in the report; someone else running it on the same Mac model gets medians near the ranges you reported.
