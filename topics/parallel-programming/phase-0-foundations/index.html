写任何一把锁、任何一个原子操作之前，先回答两个问题：多加几个核，程序最多能快多少？是什么让它快不到那么多？这一阶段用 Amdahl 定律和 Gustafson 定律给出上限，再在你面前这台 Apple M5（4 个 P 核 + 6 个 E 核，128 字节缓存行）上实测两件事：一个数组求和随线程数怎样变快、又在哪里停住；两个毫不相干的计数器怎样因为挤在同一条缓存行里而慢上七倍。

Before writing a single lock or atomic operation, answer two questions: how much faster can a program get with more cores, and what stops it from getting there? This phase gives the upper bounds with Amdahl’s law and Gustafson’s law, then measures two things on the Apple M5 in front of you (4 P cores + 6 E cores, 128-byte cache lines): how an array sum speeds up with more threads and where it stops, and how two unrelated counters become seven times slower because they share one cache line.

核心概念

Core concepts

这台 Mac 有 10 个核。把一个 512 MiB 的求和平均分给 10 个线程，它能快 10 倍吗？Lab A 实测只快 5.84 倍；换成四个累加器，单线程快了 3 倍，10 线程却只比单线程快 2.46 倍。再让两个线程各加各的计数器，什么都不共享，却比隔开以后慢 7 倍。那么，是什么决定了多加一个核能换回多少速度，又是什么在悄悄吃掉它？

This Mac has 10 cores. Split a 512 MiB sum evenly across 10 threads: does it get 10 times faster? Lab A measures only 5.84 times; with four accumulators one thread gets 3 times faster, yet 10 threads beat one thread by only 2.46 times. Then two threads each add to their own counter, sharing nothing, and run 7 times slower than when the counters are moved apart. So what decides how much speed one more core buys, and what quietly eats it?

概念 2 的 Amdahl 与 Gustafson 定律给出上限，概念 3 的核心、缓存和缓存行说明实测为什么够不着它。

The laws of Amdahl and Gustafson in concept 2 give the upper bound, and the cores, caches and cache lines of concept 3 explain why the measurements fall short of it.

1. 为什么要并行，以及并行有几种

1. Why parallel, and what kinds of parallel there are

动态功耗大致与 C·V²·f 成正比（电容、电压的平方、频率）。晶体管缩小时电压也跟着降的那段时期（Dennard scaling）在 2000 年代中期结束，此后再提频率就要付出不成比例的功耗和发热，于是单核频率停在几 GHz，多出来的晶体管变成了更多的核。结果是：一个单线程程序在新机器上不会自动变快很多，想用上全部核，程序必须自己把工作分出去。

Dynamic power is roughly proportional to C·V²·f (capacitance, voltage squared, frequency). The period in which voltage fell as transistors shrank (Dennard scaling) ended in the mid-2000s; after that, raising the clock cost disproportionate power and heat, so single-core frequency stalled at a few GHz and the extra transistors became more cores. The consequence: a single-threaded program no longer gets much faster on a new machine by itself; to use all the cores, the program has to split its own work.

Concurrency（并发）与 parallelism（并行）：并发是程序结构上有多个独立推进的任务，一个核轮流跑也算；并行是这些任务真的在同一时刻跑在不同的核上。本主题关心后者，但正确性问题（Phase 2–4）在两者下都存在。

Concurrency and parallelism: concurrency means the program is structured as several independently progressing tasks, even if one core takes turns running them; parallelism means those tasks really run at the same moment on different cores. This topic is about the latter, but the correctness problems (Phases 2–4) exist under both.

Flynn 分类法（Michael Flynn，1966）按指令流和数据流的数目把计算机分成四类：SISD（单指令流单数据流，经典单核）、SIMD（一条指令同时作用于多个数据，比如每个核里的 NEON 128 位向量，Phase 6）、MISD（多指令流作用于同一数据，实际很少见）、MIMD（多个核各跑各的指令流、各读各的数据）。多核 CPU 是 MIMD，而每个核内部又有 SIMD：本主题前五个阶段讲 MIMD，Phase 6 讲核内的 SIMD。

Flynn’s taxonomy (Michael Flynn, 1966) classifies computers by the number of instruction streams and data streams: SISD (single instruction, single data: the classic single core), SIMD (one instruction acting on several data items at once, such as the 128-bit NEON vectors inside each core, Phase 6), MISD (several instruction streams on the same data, rare in practice) and MIMD (several cores, each running its own instruction stream on its own data). A multicore CPU is MIMD, and each core contains SIMD: the first five phases of this topic cover MIMD, and Phase 6 covers SIMD inside a core.

延伸阅读：McKenney《Is Parallel Programming Hard…》第 2 章「Introduction」（并行编程的三个目标：性能、生产率、通用性，以及「不并行」的替代方案）；Herlihy 等《The Art of Multiprocessor Programming》的引言章。

Further reading: McKenney, Is Parallel Programming Hard…, Chapter 2, “Introduction” (the three goals of parallel programming: performance, productivity, generality, and the alternatives to going parallel); the introductory chapter of Herlihy et al., The Art of Multiprocessor Programming.

2. Amdahl 定律与 Gustafson 定律

2. Amdahl’s law and Gustafson’s law

设 T(N) 是用 N 个核的运行时间，加速比 S(N) = T(1) / T(N)，效率 E(N) = S(N) / N。

Let T(N) be the run time on N cores; the speedup is S(N) = T(1) / T(N), and the efficiency is E(N) = S(N) / N.

Amdahl 定律（Gene Amdahl，1967）：问题规模固定。把单核运行时间分成无法并行的串行部分，占比 s，和可以完美并行的部分，占比 1 − s（0 ≤ s ≤ 1）。用 N 个核时串行部分不变，并行部分缩成 1/N：

Amdahl’s law (Gene Amdahl, 1967): the problem size is fixed. Split the single-core run time into a serial part that cannot be parallelised, with share s, and a perfectly parallel part, with share 1 − s (0 ≤ s ≤ 1). On N cores the serial part stays the same and the parallel part shrinks to 1/N:

S(N) = 1 / ( s + (1 − s) / N )        # N → ∞ : S → 1 / s

s = 0.1 时：N = 10 得 S ≈ 5.26，效率只有 53 %；核再多也不会超过 10。串行部分哪怕只占 10 %，也决定了上限。

With s = 0.1: N = 10 gives S ≈ 5.26, an efficiency of only 53 %; no number of cores takes it past 10. A serial part of only 10 % sets the ceiling.

Gustafson 定律（John Gustafson，1988）：换一个问法。核多了，人们通常会解更大的问题，而不是把同一个问题解得更快。设 s′ 是在 N 核上运行时串行部分所占的时间比例，同样这段工作若放到单核上要花 s′ + (1 − s′)·N 倍的时间，所以按比例放大后的加速比是：

Gustafson’s law (John Gustafson, 1988): ask a different question. With more cores, people usually solve a bigger problem rather than the same problem faster. Let s′ be the share of time spent in the serial part on the N-core run; the same work would take s′ + (1 − s′)·N times as long on one core, so the scaled speedup is:

S(N) = s′ + (1 − s′) · N = N − s′ · (N − 1)

s′ = 0.1、N = 10 时 S = 9.1。两条定律并不矛盾：Amdahl 的 s 是在单核运行上量的，Gustafson 的 s′ 是在 N 核运行上量的，并行部分随 N 变大时，s′ 对应的单核 s 会越来越小。

With s′ = 0.1 and N = 10, S = 9.1. The two laws do not contradict each other: Amdahl’s s is measured on the single-core run, Gustafson’s s′ on the N-core run, and as the parallel part grows with N, the single-core s that corresponds to a given s′ keeps shrinking.

Strong scaling 与 weak scaling：总问题规模固定、看时间随核数怎样下降，叫强扩展，上限由 Amdahl 给出；每个核分到的问题规模固定、总规模随核数一起涨，看时间能否保持不变，叫弱扩展，由 Gustafson 描述。下面的对照表把两者并排列出。两条定律都假设并行部分「完美」并行，而 Lab A 会显示，真实机器上还有别的东西在限制加速比：核不一样快，内存带宽有上限，创建线程也要时间。

Strong and weak scaling: keeping the total problem size fixed and watching how the time falls with more cores is strong scaling, bounded by Amdahl; keeping the problem size per core fixed, so the total grows with the core count, and checking whether the time stays flat is weak scaling, described by Gustafson. The comparison table below puts the two side by side. Both laws assume the parallel part is “perfectly” parallel, and Lab A shows that a real machine has other limits on speedup: the cores are not equally fast, memory bandwidth has a ceiling, and creating threads takes time.

  2. 同样的 s = 0.1 放进 Gustafson，问题随 N 放大，S = 9.1。两者差在 s 是在哪次运行上量的，不是谁对谁错。
  3. 反过来用 Amdahl 拟合实测的 5.84，解出 s ≈ 0.08。可程序真正的串行部分只有建 10 个线程和最后的几次加法，约 0.12–0.15 ms（概念 4），只占单线程 31.20 ms 的约 0.5 %，按 Amdahl 应该到约 9.6 倍。

  3. Run Amdahl backwards on the measured 5.84 and you get s ≈ 0.08. Yet the program’s real serial part is only creating 10 threads and the last few additions, about 0.12–0.15 ms (concept 4), about 0.5 % of the 31.20 ms single-thread run, for which Amdahl predicts about 9.6 times.
  4. The missing part comes from the cores (Lab A step 4: about 1.4 G against 2.15 G adds per second). The slowest piece sits on an E core, and the P cores finish and wait. The fitted s describes the shape of the curve, not its cause.

3. This machine: cores, caches, cache lines

Read first, then reason. This is the raw sysctl output on the lab Mac (2026-10-31):

$ sysctl machdep.cpu.brand_string hw.perflevel0.physicalcpu hw.perflevel1.physicalcpu \

machdep.cpu.brand_string: Apple M5
hw.perflevel0.physicalcpu: 4          # perflevel0 = P 核（performance）
hw.perflevel1.physicalcpu: 6          # perflevel1 = E 核（efficiency）
hw.logicalcpu: 10                     # 逻辑核 = 物理核：没有 SMT

hw.perflevel0.l1dcachesize: 131072    # 128 KB，每个 P 核

hw.perflevel1.l2cachesize: 6291456    # 6 MB，E 簇共享
hw.memsize: 34359738368               # 32 GB 统一内存
  • 两种核：4 个 P 核和 6 个 E 核执行同样的 ARM64 指令，但 E 核更慢、更省电。把工作平均切成 N 份时，最后完成的那份决定总时间，所以落在 E 核上的那份会拖慢全体（Lab A 能看到）。
  • Two kinds of core: the 4 P cores and the 6 E cores run the same ARM64 instructions, but the E cores are slower and use less power. When work is split into N equal pieces, the last piece to finish sets the total time, so a piece that lands on an E core holds everyone back (Lab A shows this).
  • 缓存层级：每个核有自己的 L1D，每个簇共享一个 L2，两个簇共享同一块 DRAM。离核越远越大、越慢。一个 512 MiB 的数组远大于任何一级缓存，扫描它时数据几乎全从 DRAM 来，速度由内存带宽决定，而不是由核的算力决定。
  • The cache hierarchy: each core has its own L1D, each cluster shares one L2, and both clusters share the same DRAM. The further from the core, the bigger and slower. A 512 MiB array is far larger than any cache level, so a scan over it gets almost all its data from DRAM, and its speed is set by memory bandwidth, not by the cores’ compute.
  • 缓存行：缓存与内存之间、缓存与缓存之间搬运的最小单位是一整行，本机报告 128 字节（典型 x86 是 64 字节）。多核之间靠缓存一致性协议（MESI 一族；Apple 的具体协议没有公开）保持各核看到的数据一致：一个核要写某一行，必须先让其他核里这一行的副本作废。
  • Cache lines: the smallest unit moved between cache and memory, and between caches, is a whole line; this Mac reports 128 bytes (typical x86 uses 64). The cores keep their views of memory consistent with a cache-coherence protocol (the MESI family; Apple’s exact protocol is not published): before a core can write a line, the copies of that line in other cores must be invalidated.
  • False sharing（伪共享）：两个线程各写各的变量，但两个变量恰好在同一条缓存行里。逻辑上毫无共享，硬件上这一行却在两个核之间来回搬运。办法是把它们隔开到不同的行：本机按 128 字节对齐。
  • False sharing: two threads each write their own variable, but the two variables happen to sit in the same cache line. Logically nothing is shared, yet in hardware the line travels back and forth between the two cores. The fix is to separate them into different lines: on this Mac, align to 128 bytes.
  • 本机没有的东西：没有 SMT（x86 上一个物理核常跑 2 个硬件线程，共享执行单元和 L1）；没有 NUMA（多路 x86 服务器每个插槽有自己的内存，访问别的插槽的内存更慢，线程和数据放在哪个节点要一起考虑）。在这些机器上，本页的数字和曲线形状都会不同。
  • What this Mac does not have: no SMT (on x86 one physical core often runs 2 hardware threads that share execution units and L1); no NUMA (on multi-socket x86 servers each socket has its own memory, memory on another socket is slower, and where threads and data live has to be planned together). On those machines both the numbers and the shapes of the curves on this page will differ.

  2. padded：b 在下一条行里，各核独占自己的行，写入不必通知对方，每次加法约 1.56 ns，快约 7.3 倍。
  3. half：b 偏移 64 字节，按 hw.cachelinesize 仍在同一条 128 字节行里。默认 QoS 下它和 padded 一样快，两个线程都在 E 核上时却慢约 2.9 倍。所以在这台 Mac 上，隔开一整条 128 字节行才在两种核上都安全。
  1. packed: b sits only 8 bytes after a, in the same line. Every write of a by P0 must first take the line exclusively and invalidate P1’s copy, and P1’s write of b takes the whole line back: about 11.4 ns per add, most of it spent moving that one line back and forth.
  2. padded: b is in the next line, each core owns its own line, and a write needs no message to the other core: about 1.56 ns per add, about 7.3 times faster.
  3. half: b is 64 bytes in, which by hw.cachelinesize is still the same 128-byte line. At the default QoS it is as fast as padded, but with both threads on E cores it is about 2.9 times slower. So on this Mac only a full 128-byte line between them is safe on both kinds of core.

4. 内核怎样对待你的线程

4. What the kernel does with your threads

在 macOS 上，std::jthread 底下是 pthread_create，再往下是一个 Mach thread：对内核来说，一个线程就是一个可调度实体，它跑在哪个核上、什么时候跑，由调度器决定，而不是由你的程序决定。Linux 上同样如此，线程就是共享 mm 的 task_struct。这部分的内核细节见 Kernel Engineering Phase 1 · Boot & Processes（线程模型、上下文切换、Edge 调度器怎样在 P 核和 E 核之间放线程）。

On macOS, std::jthread sits on pthread_create, and below that is a Mach thread: to the kernel a thread is a schedulable entity, and which core it runs on and when is decided by the scheduler, not by your program. It is the same on Linux, where a thread is a task_struct that shares mm. The kernel details are in Kernel Engineering Phase 1 · Boot & Processes (the thread model, the context switch, and how the Edge scheduler places threads on P and E cores).

  • macOS 不提供把线程钉在某个核上的接口；你能做的是设 QoS 类（pthread_set_qos_class_self_np），影响调度器把线程往 P 核还是 E 核放。Lab B 的第二次运行就把两个线程设成 QOS_CLASS_BACKGROUND。Linux 则有 sched_setaffinity 可以直接绑核。
  • macOS offers no interface to pin a thread to a core; what you can do is set a QoS class (pthread_set_qos_class_self_np), which influences whether the scheduler places the thread on P or E cores. The second run of Lab B sets both threads to QOS_CLASS_BACKGROUND. Linux, by contrast, has sched_setaffinity to bind a thread to cores directly.
  • std::jthread（C++20）与 std::thread 的区别：析构时自动 join（忘了 join 不会 std::terminate），并自带一个 std::stop_token 用于请求停止。实验里「出了花括号就等所有线程结束」正是靠这一点。
  • How std::jthread (C++20) differs from std::thread: it joins automatically in its destructor (forgetting to join does not call std::terminate), and it carries a std::stop_token for requesting a stop. The labs rely on this to “wait for every thread at the closing brace”.
  • 创建线程不是免费的：在实验 Mac 上，创建并 join 10 个空的 std::jthread 的中位数约 0.12–0.15 ms（2026-10-31，21 次取中位数）。对 Lab A 里 4 ms 级的运行来说，这就是约 3 % 的串行部分。Phase 1 会系统地测它。
  • Creating threads is not free: on the lab Mac, creating and joining 10 empty std::jthreads takes a median of about 0.12–0.15 ms (2026-10-31, median of 21 runs). For the 4 ms runs in Lab A, that is a serial part of about 3 %. Phase 1 measures it properly.

5. 测量的基本功

5. Measurement basics

  • 墙钟时间与 CPU 时间：std::chrono::steady_clock 量的是墙钟时间，也就是你等了多久；CPU 时间是所有线程在核上跑的时间之和。两个线程忙满时 CPU 时间约是墙钟的两倍：在 Lab B 上 /usr/bin/time -p 报告 real 11.98、user 23.77。加速比只看墙钟时间。
  • Wall time and CPU time: std::chrono::steady_clock measures wall time, how long you waited; CPU time is the sum of the time all threads spent on cores. With two busy threads, CPU time is about twice the wall time: on Lab B, /usr/bin/time -p reports real 11.98 and user 23.77. Speedup uses wall time only.
  • 预热：第一次运行要付页错误、冷缓存、频率爬升的代价。两个实验都先跑一次不计入的预热，Lab A 还在构造 std::vector 时就把 512 MiB 每一页都写过一遍。
  • Warm-up: the first run pays for page faults, cold caches and the clock ramping up. Both labs do one uncounted warm-up run first, and Lab A also writes every page of its 512 MiB when it constructs the std::vector.
  • 方差与中位数：同一程序每次的时间都不同，其他进程、调度器的放置和温度都会插一脚。取多次运行的中位数而不是平均值，一两个离群值就拉不动它；同时报告最小值和最大值，看分布有多宽。Lab B 里有伪共享的版本 7 次运行在 1047–1277 ms 之间摆动，对齐后的版本只在 155.6–157.6 ms 之间：争用本身就会制造方差。
  • Variance and the median: the same program takes a different time on every run; other processes, the scheduler’s placement and temperature all play a part. Take the median of several runs rather than the mean, so one or two outliers cannot drag it, and report the minimum and maximum to show how wide the spread is. In Lab B the falsely shared version swings between 1047 and 1277 ms over 7 runs, while the aligned version stays between 155.6 and 157.6 ms: contention itself creates variance.
  • 别让编译器删掉你的工作：用 -O2 编译，并把结果打印出来（Lab A 打印 sum=），否则编译器可以证明结果没人用，把整个循环删掉，你量到的就只剩空循环。
  • Do not let the compiler delete your work: build with -O2 and print the result (Lab A prints sum=); otherwise the compiler can prove nobody uses the result and delete the whole loop, and you end up timing nothing.

延伸阅读：Williams《C++ Concurrency in Action》中讲设计并发代码的一章（影响并发代码性能的因素：处理器数量、数据争用、cache ping-pong、伪共享）；McKenney 第 3 章「Hardware and its Habits」中各类操作代价的对比。

Further reading: the chapter on designing concurrent code in Williams, C++ Concurrency in Action (the factors that affect the performance of concurrent code: the number of processors, data contention, cache ping-pong, false sharing); the comparison of operation costs in McKenney, Chapter 3, “Hardware and its Habits”.

  • Amdahl 定律 S = 1 / (s + (1 − s)/N) 固定问题规模，串行比例 s 定下 1/s 的天花板：s = 0.1 时 10 核只有 5.26 倍。
  • Gustafson 定律 S = s′ + (1 − s′)·N 让问题随核数变大，s′ 在 N 核运行上量，同样的 0.1 得到 9.1 倍。
  • 这台 M5 是 4 个 P 核加 6 个 E 核，平均切分时最慢的那份落在 E 核上，所以 Lab A 一个累加器到 10 线程只有 5.84 倍。
  • 扫描一个远大于缓存的数组，瓶颈会从加法延迟移到内存带宽：P 簇约 83 GB/s 封顶，两个簇一起约 131 GB/s。
  • 两个线程写同一条 128 字节缓存行里的不同变量就是 false sharing，按 hw.cachelinesize 对齐后快 7 倍多。
  • 测量要预热、取多次运行的中位数、只用墙钟时间算加速比，并把结果打印出来，免得编译器删掉整个循环。
  • Amdahl’s law S = 1 / (s + (1 − s)/N) fixes the problem size, and the serial fraction s sets a ceiling of 1/s: with s = 0.1, 10 cores give only 5.26 times.
  • Gustafson’s law S = s′ + (1 − s′)·N lets the problem grow with the core count, s′ is measured on the N-core run, and the same 0.1 gives 9.1 times.
  • This M5 has 4 P cores plus 6 E cores, an even split leaves the slowest piece on an E core, and so Lab A with one accumulator reaches only 5.84 times at 10 threads.
  • Scanning an array far larger than the caches moves the bottleneck from add latency to memory bandwidth: the P cluster tops out at about 83 GB/s, both clusters together at about 131 GB/s.
  • Two threads writing different variables in the same 128-byte cache line is false sharing, and aligning to hw.cachelinesize makes it more than 7 times faster.
  • A measurement needs a warm-up, the median of repeated runs, wall time only for speedup, and a printed result so the compiler cannot delete the loop.

常见误解

Common misconceptions

  • 误解：N 个核就能快 N 倍，达不到说明代码写得不好。→ 实际：Amdahl 的串行部分、不一样快的核和共享的内存带宽都在限制加速比，同一个正确的求和在本机只有 5.84 倍或 2.46 倍。
  • 误解：用 Amdahl 拟合出 s ≈ 0.08，就说明程序有 8 % 的串行代码。→ 实际：Lab A 真正的串行部分约 0.5 %，曲线变缓来自 E 核和带宽；拟合只给形状，原因要靠测量找。
  • 误解：线程之间没有共享变量，就不会互相拖慢。→ 实际：缓存一致性按整行工作，两个无关的计数器落在同一条 128 字节行里，Lab B 就慢了 7 倍多。
  • Myth: N cores should make it N times faster, and falling short means bad code. → Fact: Amdahl’s serial part, cores of unequal speed and shared memory bandwidth all limit speedup; the same correct sum reaches only 5.84 or 2.46 times on this Mac.
  • Myth: fitting Amdahl and getting s ≈ 0.08 means the program has 8 % serial code. → Fact: Lab A’s real serial part is about 0.5 %, and the curve flattens because of the E cores and bandwidth; a fit gives the shape, and only measurement finds the cause.
  • Myth: threads that share no variable cannot slow each other down. → Fact: cache coherence works on whole lines, and two unrelated counters in one 128-byte line make Lab B more than 7 times slower.

  2. 把下面的程序存成 sum.cpp。它把 64 Mi 个 double（512 MiB，远大于 L2）平均切成 T 份，每份交给一个 std::jthread；每种线程数先预热一次，再跑 11 次取中位数。参数 1 用一个累加器，参数 4 用四个独立的累加器：Save the program below as sum.cpp. It splits 64 Mi doubles (512 MiB, far larger than L2) into T equal pieces, one per std::jthread; for each thread count it warms up once, then takes the median of 11 runs. Argument 1 uses one accumulator, argument 4 uses four independent accumulators:
    // sum.cpp: sum a 512 MiB array with 1, 2, 4, 8, 10 threads; median of 11 runs
// usage: ./sum 1   (one accumulator)   ./sum 4   (four accumulators)
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <cstdlib>
#include <thread>
#include <vector>

static double chunk_sum(const double* p, std::size_t n, int acc) {
  if (acc == 1) { double s = 0; for (std::size_t i = 0; i < n; ++i) s += p[i]; return s; }
  double s0 = 0, s1 = 0, s2 = 0, s3 = 0;
  std::size_t i = 0;
  for (; i + 4 <= n; i += 4) { s0 += p[i]; s1 += p[i + 1]; s2 += p[i + 2]; s3 += p[i + 3]; }
  for (; i < n; ++i) s0 += p[i];
  return (s0 + s1) + (s2 + s3);
}

int main(int argc, char** argv) {
  const int acc = argc > 1 ? std::atoi(argv[1]) : 1;
  const std::size_t N = std::size_t{1} << 26;          // 64 Mi doubles = 512 MiB, far beyond L2
  std::vector<double> a(N, 1.0);
  double t1 = 0;
  for (int T : {1, 2, 4, 8, 10}) {
    std::vector<double> ms;
    double total = 0;
    for (int rep = 0; rep < 12; ++rep) {                // rep 0 is the warm-up, not kept
      std::vector<double> part(T * 16, 0.0);            // results 128 bytes apart
      auto t0 = std::chrono::steady_clock::now();
      {
        std::vector<std::jthread> pool;
        for (int t = 0; t < T; ++t)
          pool.emplace_back([&, t] {
            std::size_t lo = N * t / T, hi = N * (t + 1) / T;
            part[t * 16] = chunk_sum(a.data() + lo, hi - lo, acc);
          });
      }                                                 // every jthread joins here
      double dt = std::chrono::duration<double, std::milli>(
                      std::chrono::steady_clock::now() - t0).count();
      total = 0;
      for (int t = 0; t < T; ++t) total += part[t * 16];
      if (rep > 0) ms.push_back(dt);
    }
    std::sort(ms.begin(), ms.end());
    double med = ms[ms.size() / 2];
    if (T == 1) t1 = med;
    std::printf("threads=%2d  median=%6.2f ms  speedup=%4.2f  %5.1f GB/s  sum=%.0f\n",
                T, med, t1 / med, N * sizeof(double) / med / 1e6, total);
  }
}

Up to 4 threads the threads most likely all sit on P cores, and the speedup is almost linear (3.68). At 8 and 10 threads the extra threads land on E cores, while every piece of work is the same size: the P cores finish early and wait for the slowest E core. Now 2 threads and 4 threads are equally fast, both about 83 GB/s: more P cores cannot pull in more bytes, because the P cluster’s bandwidth to memory is full. At 8 and 10 threads, with the E cluster added, it rises to 131 GB/s, which shows the E cluster has its own share of bandwidth. The speedup is only 2.46, yet it processes more data per nanosecond than the 10-thread run of the first set. This is what bandwidth-bound means: more cores just queue for memory.

Lab B · False sharing：同一条缓存行里的两个计数器

Lab B · False sharing: two counters in one cache line

  1. 把下面的程序存成 false_sharing.cpp。两个线程各自对自己的 std::atomic<long> 做 1 亿次 fetch_add（memory_order_relaxed，Phase 3 会讲），没有任何逻辑上的共享。三种布局：packed 两个计数器相邻（相差 8 字节）；half 相隔 64 字节但在同一条 128 字节对齐的行里；padded 各自对齐到 128 字节：Save the program below as false_sharing.cpp. Two threads each do 100 million fetch_adds on their own std::atomic<long> (memory_order_relaxed, covered in Phase 3), with nothing logically shared. Three layouts: packed puts the counters next to each other (8 bytes apart); half puts them 64 bytes apart but inside one 128-byte-aligned line; padded aligns each to 128 bytes:
    // false_sharing.cpp: two threads, each adds 1e8 times to its own counter
// usage: ./false_sharing      (default QoS)   ./false_sharing bg   (both threads at background QoS)
#include <pthread/qos.h>
#include <algorithm>
#include <atomic>
#include <chrono>
#include <cstddef>
#include <cstdio>
#include <cstring>
#include <thread>
#include <vector>

struct Packed  { std::atomic<long> a{0}; std::atomic<long> b{0}; };            // 8 bytes apart
struct alignas(128) Half { alignas(64) std::atomic<long> a{0};                 // 64 apart,
                           alignas(64) std::atomic<long> b{0}; };               // one 128-byte line
struct Padded  { alignas(128) std::atomic<long> a{0}; alignas(128) std::atomic<long> b{0}; };

constexpr long ITERS = 100'000'000;
static bool bg = false;

template <class S> double run_once() {
  S s;
  auto work = [&](std::atomic<long>& c) {
    if (bg) pthread_set_qos_class_self_np(QOS_CLASS_BACKGROUND, 0);
    for (long i = 0; i < ITERS; ++i) c.fetch_add(1, std::memory_order_relaxed);
  };
  auto t0 = std::chrono::steady_clock::now();
  { std::jthread x(work, std::ref(s.a)); std::jthread y(work, std::ref(s.b)); }
  if (s.a.load() != ITERS || s.b.load() != ITERS) std::puts("count mismatch");
  return std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count();
}

template <class S> void bench(const char* name) {
  std::vector<double> ms;
  run_once<S>();                                       // warm-up
  for (int r = 0; r < 7; ++r) ms.push_back(run_once<S>());
  std::sort(ms.begin(), ms.end());
  std::printf("%-7s offset(b)=%3zu  median=%7.1f ms  min=%7.1f  max=%7.1f\n",
              name, offsetof(S, b), ms[3], ms.front(), ms.back());
}

int main(int argc, char** argv) {
  bg = argc > 1 && std::strcmp(argv[1], "bg") == 0;
  bench<Packed>("packed");
  bench<Half>("half");
  bench<Padded>("padded");
}

自测

Self-check

1. 一个程序在单核上运行时有 10 % 的时间无法并行。问题规模不变，用 10 个核，Amdahl 定律给出的加速比上限是多少？

1. A program spends 10 % of its single-core run time in code that cannot be parallelised. With the problem size unchanged and 10 cores, what speedup bound does Amdahl’s law give?

S = 1 / (0.1 + 0.9 / 10) = 1 / 0.19 ≈ 5.26。10 是没有串行部分时的理想值；9.1 是 Gustafson 定律在 s′ = 0.1 时的结果，那里问题规模随 N 变大，而且 s′ 是在 10 核运行上量的。S = 1 / (0.1 + 0.9 / 10) = 1 / 0.19 ≈ 5.26. 10 is the ideal value with no serial part; 9.1 is Gustafson’s law with s′ = 0.1, where the problem grows with N and s′ is measured on the 10-core run.

2. Lab A 的四累加器版本里，2 线程和 4 线程都约 83 GB/s。最合理的解释是？

2. In the four-accumulator version of Lab A, 2 threads and 4 threads both reach about 83 GB/s. What is the most reasonable explanation?

创建 10 个线程只要约 0.12–0.15 ms，远小于 6.5 ms 的运行时间；如果四个线程挤在一个核上，时间会比单线程还长，而实测 6.5 ms 比单线程的 10 ms 短。加入 E 簇后带宽升到 131 GB/s，正说明限制在 P 簇的内存通路上。Creating 10 threads takes only about 0.12–0.15 ms, far less than the 6.5 ms run; if four threads shared one core, the run would take longer than one thread, but the measured 6.5 ms is shorter than the 10 ms of one thread. Adding the E cluster raises bandwidth to 131 GB/s, which shows the limit is the P cluster’s path to memory.

3. 两个线程各自只对自己的 std::atomic<long> 做 fetch_add，两个计数器地址相差 8 字节，比相隔 128 字节时慢 7 倍。慢在哪里？

3. Two threads each do fetch_add only on their own std::atomic<long>; with the counters 8 bytes apart, it is 7 times slower than with them 128 bytes apart. Where does the time go?

同样的原子加法在 padded 布局下只要 155.8 ms，所以不是指令本身慢；本机上 std::atomic<long>::is_always_lock_free 为真（编译时 static_assert 通过），没有锁。差别只在两个计数器是否共用一条行。The same atomic adds take only 155.8 ms in the padded layout, so the instruction itself is not slow; on this Mac std::atomic<long>::is_always_lock_free is true (a compile-time static_assert passes), so there is no lock. The only difference is whether the two counters share a line.

4. 你把核数翻倍，同时把总问题规模也翻倍，运行时间保持不变。这说明什么？

4. You double the core count and double the total problem size at the same time, and the run time stays the same. What does this show?

每个核的工作量不变、总量随核数增长，时间不变，正是弱扩展的理想结果。强扩展要求总问题规模固定，这里不是；Amdahl 定律只约束固定规模的问题，所以也谈不上违反。The work per core is unchanged, the total grows with the core count, and the time is unchanged: exactly the ideal result of weak scaling. Strong scaling requires a fixed total problem size, which is not the case here; Amdahl’s law constrains only fixed-size problems, so nothing violates it.
