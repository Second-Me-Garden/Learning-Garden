核心概念

Core concepts

1. 线程是什么

1. What a thread is

一个线程是一条独立的执行流：它有自己的寄存器（包括程序计数器和栈指针）、自己的栈和自己的线程局部存储（TLS），而地址空间、打开的文件、全局变量和堆是同一进程里所有线程共享的。共享地址空间正是线程比进程便宜、也比进程危险的原因：两个线程不用拷贝就能读写同一块内存，也不加同步就能把它写坏（Phase 2）。

A thread is an independent flow of execution: it has its own registers (including the program counter and the stack pointer), its own stack and its own thread-local storage (TLS), while the address space, open files, globals and the heap are shared by every thread in the process. The shared address space is exactly why threads are cheaper than processes and also more dangerous: two threads can read and write the same memory without copying it, and can also corrupt it without synchronization (Phase 2).

内核里线程长什么样，两个系统不同。Linux 上线程就是一个和别人共享 mm 的 task_struct，pthread_create 最后变成带 CLONE_VM | CLONE_THREAD | … 的 clone。XNU 上线程是 Mach thread，挂在 Mach task 下面，另有一个 BSD 侧的 uthread。两边的完整结构见内核专题 Phase 1 的「进程与线程模型」。

What a thread looks like inside the kernel differs between the two systems. On Linux a thread is simply a task_struct that shares its mm with others, and pthread_create ends up as a clone with CLONE_VM | CLONE_THREAD | …. On XNU a thread is a Mach thread under a Mach task, with a BSD-side uthread as well. The full structures on both sides are in the process and thread model concept of kernel topic Phase 1.

2. pthread_create 向内核要了什么

2. What pthread_create asks the kernel for

在 macOS 上，一次 pthread_create 分成用户态和内核态两半。下面每一步都对照了 Apple 开源的 libpthread 和 XNU 源码（2026-10-31 读的 GitHub main 分支，链接在资料里）：

On macOS one pthread_create splits into a user-space half and a kernel half. Each step below was checked against Apple’s open-source libpthread and XNU (the GitHub main branch, read on 2026-10-31; links under Resources):

  1. 用户态先自己分配栈。_pthread_allocate（libpthread/src/pthread.c）用一次 mach_vm_map 映射一整块区域，打上 VM_MEMORY_STACK 标签：最低处是保护页（guard page，默认一页，本机 16 KB），用 mach_vm_protect 设成不可访问，栈溢出时立刻段错误；中间是栈，默认 DEFAULT_STACK_SIZE = 512 KB；最上面放这个线程的 pthread_t 结构。栈向下长，所以起始栈指针就是 pthread_t 的地址。
  2. User space allocates the stack itself first. _pthread_allocate (libpthread/src/pthread.c) maps one whole region with a single mach_vm_map tagged VM_MEMORY_STACK: at the lowest address is the guard page (one page by default, 16 KB on this machine), made inaccessible with mach_vm_protect so that a stack overflow faults at once; in the middle is the stack, DEFAULT_STACK_SIZE = 512 KB by default; at the top sits this thread’s pthread_t structure. The stack grows down, so the initial stack pointer is the address of the pthread_t.
  3. 一次系统调用进内核。libpthread 调 __bsdthread_create(start_routine, arg, stack, t, flags)，flags 里带着 attr 指定的 QoS 或调度参数。
  4. One system call into the kernel. libpthread calls __bsdthread_create(start_routine, arg, stack, t, flags); the flags carry the QoS or scheduling parameters from the attr.
  5. 内核建一个 Mach thread，并伪造它的第一组寄存器。_bsdthread_create（libpthread/kern/kern_support.c）在当前 task 里 thread_create_immovable，给它一个线程 port，设好 TSD 基址（线程指针），再写入初始寄存器：pc = 进程注册过的 thread_start，sp = 刚才的栈顶，x0 = pthread_t，x2、x3 = 你的函数和参数。有 QoS 就用 THREAD_QOS_POLICY 设上。
  6. The kernel builds a Mach thread and fakes its first set of registers. _bsdthread_create (libpthread/kern/kern_support.c) calls thread_create_immovable in the current task, gives the thread a thread port, sets its TSD base (the thread pointer), then writes the initial registers: pc = the thread_start the process registered, sp = the stack top from step 1, x0 = the pthread_t, x2 and x3 = your function and its argument. If there is a QoS, it is applied with THREAD_QOS_POLICY.
  7. 交给调度器。thread_resume 让线程变成可运行，进入运行队列；调度器某次选中它时，按内核专题 Phase 1 讲的上下文切换把它放上某个核，eret 回到用户态，从 thread_start 跑到 _pthread_start，再调用你的函数。Lab B 的 sample 输出里每个工作线程的栈底都是 thread_start → _pthread_start，就是这一步留下的。
  8. Hand it to the scheduler. thread_resume makes the thread runnable and puts it on a run queue; when the scheduler picks it, the context switch described in kernel topic Phase 1 puts it on a core, eret returns to user space, and it runs from thread_start to _pthread_start and then calls your function. In the sample output of Lab B, every worker thread’s stack bottoms out in thread_start → _pthread_start; that is this step’s trace.
  9. 结束和 join。你的函数返回后，线程唤醒等着 join 它的线程，再调 __bsdthread_terminate(freeaddr, freesize, …)：线程自己还站在这块栈上，没法在用户态释放它，所以交给内核在销毁线程时一起释放。join 的一方在 __ulock_wait 里睡着等（Lab B 的 sample 里主线程就停在这里），醒来后取返回值、回收 pthread_t。
  10. Exit and join. After your function returns, the thread wakes whoever is waiting to join it and calls __bsdthread_terminate(freeaddr, freesize, …): the thread is still standing on that stack and cannot free it in user space, so it asks the kernel to free it while destroying the thread. The joining side sleeps in __ulock_wait (in the sample output of Lab B the main thread sits exactly there), and on waking it collects the return value and reclaims the pthread_t.

Linux 上同样的形状（据 glibc 和 man 手册，本页未在 Linux 上执行）：glibc 用 mmap 分配栈和保护页，把 struct pthread 和静态 TLS 放在栈顶，然后调 clone3（较老的 glibc 用 clone），flags 包括 CLONE_VM、CLONE_THREAD、CLONE_SETTLS、CLONE_CHILD_CLEARTID。最后这个 flag 让内核在线程退出时把 TID 清零并做一次 futex 唤醒，join 就是等在这个 futex 上。默认栈大小来自 RLIMIT_STACK（常见 8 MB），设成 unlimited 时多数架构用 2 MB（pthread_create(3)）。

The same shape on Linux (from glibc and the man pages; not run on Linux for this page): glibc allocates the stack and guard page with mmap, places struct pthread and the static TLS at the top of the stack, then calls clone3 (older glibc uses clone) with flags including CLONE_VM, CLONE_THREAD, CLONE_SETTLS and CLONE_CHILD_CLEARTID. That last flag makes the kernel clear the TID and do a futex wake when the thread exits, and join simply waits on that futex. The default stack size comes from RLIMIT_STACK (commonly 8 MB); when it is unlimited, most architectures use 2 MB (pthread_create(3)).

下面这个程序把栈和 TLS 摆到眼前。两个工作线程用一把锁和一个条件变量互相等，保证它们同时活着：

The program below puts the stack and the TLS in front of you. The two worker threads wait for each other with a lock and a condition variable, so that both are alive at the same time:

// stack_tls.c: 栈从哪来、多大；每个线程的 _Thread_local 变量在哪
#include <pthread.h>
#include <stdio.h>

static _Thread_local int tls_counter;
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  c = PTHREAD_COND_INITIALIZER;
static int arrived;

static void *worker(void *arg) {
    int local;
    tls_counter = (int)(long)arg;
    printf("thread %ld: stack size %zu KB, &local %p, &tls_counter %p\n",
           (long)arg, pthread_get_stacksize_np(pthread_self()) / 1024,
           (void *)&local, (void *)&tls_counter);
    pthread_mutex_lock(&m);                 // 等两个线程都到齐再退出，保证它们同时活着
    if (++arrived >= 2) pthread_cond_broadcast(&c);
    while (arrived < 2) pthread_cond_wait(&c, &m);
    pthread_mutex_unlock(&m);
    return NULL;
}

int main(void) {
    pthread_attr_t a;
    size_t def;
    pthread_attr_init(&a);
    pthread_attr_getstacksize(&a, &def);
    printf("default pthread stack: %zu KB\n", def / 1024);
    printf("main thread stack:     %zu KB\n", pthread_get_stacksize_np(pthread_self()) / 1024);

    pthread_t t[2];
    for (long i = 0; i < 2; ++i) pthread_create(&t[i], NULL, worker, (void *)(i + 1));
    for (int i = 0; i < 2; ++i) pthread_join(t[i], NULL);

    pthread_attr_setstacksize(&a, 8u << 20);          // 要 8 MB 的栈
    pthread_create(&t[0], &a, worker, (void *)3);
    pthread_join(t[0], NULL);
    return 0;
}

  • 默认 512 KB，主线程 8 MB。新线程的 512 KB 就是 libpthread 的 DEFAULT_STACK_SIZE；主线程的栈由内核在 exec 时按 ulimit -s（8176 KB）建好，不经过 _pthread_allocate。在主线程里能跑的深递归，挪到工作线程里可能就溢出了，这时用 pthread_attr_setstacksize 要大一点的栈，像 thread 3 那样。
  • 512 KB by default, 8 MB for the main thread. A new thread’s 512 KB is libpthread’s DEFAULT_STACK_SIZE; the main thread’s stack is set up by the kernel at exec time from ulimit -s (8176 KB) and never goes through _pthread_allocate. A deep recursion that works on the main thread may overflow on a worker thread; then ask for a bigger stack with pthread_attr_setstacksize, as thread 3 does.
  • 报告值比请求值多一点。pthread_get_stacksize_np 报 524 KB 而不是 512 KB，因为 libpthread 在请求的大小上加了 PTHREAD_T_OFFSET 并按页取整（源码可见，具体多出的字节数本页没有逐项核对）。
  • The reported size is a little larger than the request. pthread_get_stacksize_np reports 524 KB rather than 512 KB because libpthread adds PTHREAD_T_OFFSET to the requested size and rounds to pages (visible in the source; this page did not account for every extra byte).
  • 每个线程一份 TLS。两个同时活着的线程里，&tls_counter 相差 16 字节，是两份不同的变量。thread 3 拿到的地址和 thread 1 一样，因为 thread 1 已经退出，它那份存储被回收后又分给了新线程。所以「地址相同」不能证明「是同一个变量」，要看两个线程是否同时活着。
  • One TLS copy per thread. In the two threads that are alive together, &tls_counter differs by 16 bytes: they are two different variables. Thread 3 gets the same address as thread 1 because thread 1 has already exited and its storage was reclaimed and handed to the new thread. So the same address does not prove the same variable; what matters is whether the two threads are alive at the same time.

3. 三种写法：pthreads、std::thread / std::jthread、GCD

3. Three ways to write it: pthreads, std::thread / std::jthread, GCD

  • pthreads 是 C 接口，也是另外两种在这台机器上的底座：pthread_create 返回一个 pthread_t，之后必须二选一，pthread_join 等它结束并拿返回值，或者 pthread_detach 让它结束时自己回收。两样都不做，线程结束后它的 pthread_t 和栈就一直占着，跟僵尸进程一样。
  • pthreads is the C interface and also what the other two stand on here: pthread_create returns a pthread_t, after which you must choose one of two, pthread_join to wait for it and take its return value, or pthread_detach so that it cleans up after itself when it ends. Do neither and, once the thread ends, its pthread_t and stack stay allocated, like a zombie process.
  • std::thread 是 C++11 的包装。本机 libc++ 的实现直接调 pthread_create（nm -u 看 Lab A 的程序能看到 _pthread_create）。它的规则更严：析构时如果还是 joinable，就调用 std::terminate，程序直接结束。std::jthread（C++20）修掉了这一点：析构时先 request_stop()，再 join()，并且把一个 std::stop_token 交给线程函数，让它能礼貌地退出。本专题默认用 jthread。
  • std::thread is the C++11 wrapper. This machine’s libc++ implements it by calling pthread_create directly (nm -u on the Lab A program shows _pthread_create). Its rule is stricter: if it is still joinable when destroyed, it calls std::terminate and the program ends. std::jthread (C++20) fixes this: its destructor first calls request_stop(), then join(), and it hands the thread function a std::stop_token so the thread can exit politely. This topic uses jthread by default.
  • GCD（Grand Central Dispatch）换了一个思路：你不创建线程，只把工作（block）放进队列。dispatch_async 放进去马上返回；dispatch_group_async 是「放进去并记在一个 group 里」，之后 dispatch_group_wait 等这个 group 里的全部 block 做完；dispatch_apply 把一个循环的 N 次迭代分给多个线程，自己等全部完成（Phase 5 详讲）。执行这些 block 的线程属于一个系统管理的线程池，由内核的 workqueue 机制（xnu/bsd/pthread/pthread_workqueue.c）按核心数和线程阻塞情况增减。本机 sysctl kern.wq_max_threads 是 512，kern.wq_max_constrained_threads 是 64（2026-10-31 读出）。
  • GCD (Grand Central Dispatch) takes a different approach: you do not create threads, you put work (blocks) on queues. dispatch_async enqueues and returns at once; dispatch_group_async enqueues and records the block in a group, and dispatch_group_wait later waits for every block in that group to finish; dispatch_apply splits the N iterations of a loop across threads and waits for all of them itself (Phase 5 covers it in depth). The threads that run these blocks belong to a system-managed pool that the kernel’s workqueue mechanism (xnu/bsd/pthread/pthread_workqueue.c) grows and shrinks by core count and by how many threads are blocked. On this machine sysctl kern.wq_max_threads is 512 and kern.wq_max_constrained_threads is 64 (read on 2026-10-31).

Lab A 的结果先放在这里：同一台机器上，创建并 join 一个空线程，在 100 个一批时每个约 6 µs；把一个空 block 交给 GCD 并等它做完，100 个一批时每个约 0.1 µs，便宜四十倍以上。差距不在于 GCD 有什么魔法，而在于它的线程早就存在：每个 block 省掉了映射栈、几次进出内核、建和销毁一个 Mach thread。

The Lab A result up front: on the same machine, creating and joining an empty thread costs about 6 µs each in batches of 100; handing an empty block to GCD and waiting for it costs about 0.1 µs each in batches of 100, more than forty times cheaper. The gap is not GCD magic; its threads already exist, so each block skips mapping a stack, several trips into the kernel, and building and destroying a Mach thread.

4. 上下文切换和调度器

4. The context switch and the scheduler

线程比核多时，内核轮流让它们上核。每次轮换就是一次上下文切换：保存旧线程的寄存器、换内核栈，必要时换页表，再恢复新线程的寄存器。同一进程的两个线程共享地址空间，所以线程之间切换不用换页表，比进程之间切换少一步。寄存器层面的细节（cpu_switch_to 和 Switch_context）在内核专题 Phase 1 的「上下文切换」。

When there are more threads than cores, the kernel takes turns putting them on cores. Each turn is a context switch: save the old thread’s registers, switch the kernel stack, switch the page tables if needed, and restore the new thread’s registers. Two threads of one process share the address space, so switching between them needs no page-table switch, one step fewer than switching between processes. The register-level details (cpu_switch_to and Switch_context) are in the context switch concept of kernel topic Phase 1.

  • 自愿和非自愿。线程自己等锁、等 I/O、等 join 而让出核，是自愿切换（voluntary）；时间片用完或被更高优先级的线程抢走，是非自愿切换（involuntary）。getrusage 的 ru_nvcsw 和 ru_nivcsw 分别数这两种，Lab B 用后者。
  • Voluntary and involuntary. A thread that gives up its core to wait for a lock, for I/O or for a join makes a voluntary switch; one whose time slice runs out or that is preempted by a higher-priority thread makes an involuntary switch. getrusage counts them in ru_nvcsw and ru_nivcsw; Lab B uses the latter.
  • 代价有直接和间接两份。直接的是切换本身的指令；间接的往往更大：新线程上核时 cache 和 TLB 里装的是别人的数据，要重新热起来。本页不单独测切换本身（那需要精确的乒乓测量，Phase 7 再做），只在 Lab B 看它在整体上造成的结果。
  • The cost comes in a direct part and an indirect part. The direct part is the switch instructions themselves; the indirect part is often larger: when the new thread comes on, the cache and the TLB hold someone else’s data and must warm up again. This page does not measure the switch alone (that needs a careful ping-pong benchmark, done in Phase 7); Lab B only looks at its overall effect.
  • 吃 CPU 的线程优先级会往下掉。XNU 的普通线程是 timeshare 的：有效优先级从基础优先级出发，用得越多掉得越多。Lab B 里 100 个忙等的线程用 ps -M 看，PRI 从默认的 31 掉到了 1 到 19 之间（两次运行），就是这个衰减（内核专题 Phase 1 的「调度」）。
  • CPU-hungry threads drop in priority. Ordinary XNU threads are timeshare: the effective priority starts at the base priority and falls the more CPU the thread uses. Look at the 100 busy-waiting threads of Lab B with ps -M and PRI has fallen from the default 31 to between 1 and 19 (two runs); that is the decay (the scheduling concept of kernel Phase 1).

5. QoS：macOS 的说法，和 Linux 的优先级与亲和性

5. QoS: the macOS way, versus Linux priorities and affinity

Linux 给你直接的旋钮：nice / setpriority 调普通任务的权重，SCHED_FIFO、SCHED_RR 给实时优先级，sched_setaffinity（或 taskset）把线程限制在指定的核上。macOS 不给亲和性（实验环境页实测 THREAD_AFFINITY_POLICY 返回 46，不支持），Apple 也建议不要再用 setpriority、pthread_setschedparam 这类直接设优先级的接口，改用 QoS 类别。QoS 说的是「这件工作有多急」，由调度器决定怎么办：

Linux gives you direct knobs: nice / setpriority adjust an ordinary task’s weight, SCHED_FIFO and SCHED_RR give real-time priority, and sched_setaffinity (or taskset) restricts a thread to chosen cores. macOS gives no affinity (the lab environment page measured THREAD_AFFINITY_POLICY returning 46, not supported), and Apple advises moving away from interfaces that set priority directly, such as setpriority and pthread_setschedparam, to QoS classes. A QoS class says how urgent the work is, and the scheduler decides what to do about it:

  • 基础优先级。每个 QoS 对应 XNU 用户带 0–63 里的一个基础优先级（内核专题 Phase 1：大致 User-Interactive ≈ 46–47，Default 31，Background 4）。
  • Base priority. Each QoS maps to a base priority in XNU’s user band 0–63 (kernel topic Phase 1: roughly User-Interactive ≈ 46–47, Default 31, Background 4).
  • 放 P 核还是 E 核。Apple 的文档原话是：在 Apple silicon 上，QoS 影响系统在哪类核上运行任务，系统「更可能」把 background 任务放在低性能核上。社区的普遍说法更强，认为 Background 线程只在 E 核上跑。下面的实测说明「更可能」才是准确的说法。
  • P core or E core. Apple’s documentation says that on Apple silicon QoS influences which kind of core the system runs a task on, and that the system is “more likely” to run background tasks on lower-performance cores. The common community claim is stronger: that Background threads run only on E cores. The measurement below shows that “more likely” is the accurate wording.
  • 其他节能手段。对低 QoS 的工作，系统还会合并定时器、限制 I/O（Apple 的能效指南，归档文档）。本页没有测这两项。
  • Other energy measures. For low-QoS work the system also coalesces timers and throttles I/O (Apple’s energy efficiency guide, an archived document). This page did not measure either.

macOS 不让你选核，但会告诉你线程此刻在哪个核上：pthread_cpu_number_np（SDK 头文件 pthread/pthread.h 里有说明，返回值在 0 到 hw.ncpu 之间，而且线程随时可能被挪走）。下面的程序让每个线程做 2000 小块计算，每块前后各读一次 CPU 编号，两次相同才计入，最后按 CPU 编号平均每块的耗时：

macOS does not let you choose a core, but it does tell you which core a thread is on right now: pthread_cpu_number_np (documented in the SDK header pthread/pthread.h; the result lies between 0 and hw.ncpu, and the thread may be moved at any moment). In the program below each thread does 2000 small chunks of work, reads the CPU number before and after each chunk, counts the chunk only when both readings agree, and finally averages the time per chunk by CPU number:

// speedmap.c: 每个小块计算前后各读一次 CPU 编号，两次相同才计入；按 CPU 编号平均每块耗时
#include <pthread.h>
#include <pthread/qos.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

static volatile double sink;
static double sum_us[10]; static long cnt[10];
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static qos_class_t qos;

static double now_us(void) {
    struct timespec ts; clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return ts.tv_sec * 1e6 + ts.tv_nsec / 1e3;
}

static void *run(void *arg) {
    (void)arg;
    pthread_set_qos_class_self_np(qos, 0);
    double s = 0, my_sum[10] = {0}; long my_cnt[10] = {0};
    for (int chunk = 0; chunk < 2000; ++chunk) {
        size_t a, b;
        pthread_cpu_number_np(&a);
        double t0 = now_us();
        for (int i = 1; i <= 100000; ++i) s += 1.0 / (i + chunk);
        double dt = now_us() - t0;
        pthread_cpu_number_np(&b);
        if (a == b && a < 10) { my_sum[a] += dt; my_cnt[a]++; }
    }
    sink = s;
    pthread_mutex_lock(&m);
    for (int c = 0; c < 10; ++c) { sum_us[c] += my_sum[c]; cnt[c] += my_cnt[c]; }
    pthread_mutex_unlock(&m);
    return NULL;
}

int main(int argc, char **argv) {
    int n = argc > 1 ? atoi(argv[1]) : 10;
    qos = (argc > 2 && argv[2][0] == 'b') ? QOS_CLASS_BACKGROUND : QOS_CLASS_USER_INTERACTIVE;
    pthread_t t[64];
    for (long i = 0; i < n; ++i) pthread_create(&t[i], NULL, run, NULL);
    for (int i = 0; i < n; ++i) pthread_join(t[i], NULL);
    for (int c = 0; c < 10; ++c)
        if (cnt[c]) printf("cpu %d: %6.1f us per chunk (%ld chunks)\n", c, sum_us[c] / cnt[c], cnt[c]);
    return 0;
}

6. 线程池：把创建成本摊掉

6. Thread pools: amortising the creation cost

线程池先建好固定数量的工作线程（通常等于核心数），之后的每件工作只是往一个共享队列里放一个任务。工作线程在队列空时睡在条件变量上，不占 CPU；有任务时被叫醒一个，取出任务，在锁外执行，再回去取下一个。线程只建一次，每个任务的代价变成「加锁、入队、唤醒、出队」。下面是一个完整的最小线程池，用 std::jthread 的 stop token 处理退出：

A thread pool creates a fixed number of worker threads up front (usually the core count), and after that each piece of work is just a task put on a shared queue. Workers sleep on a condition variable while the queue is empty, using no CPU; when a task arrives one is woken, takes the task, runs it outside the lock, and goes back for the next. Threads are created once, and each task costs a lock, an enqueue, a wake-up and a dequeue. Here is a complete minimal pool that uses the stop token of std::jthread to shut down:

// pool.cpp: 最小线程池：固定数量的 worker 从一个共享队列里取任务
#include <atomic>
#include <chrono>
#include <condition_variable>
#include <cstdio>
#include <deque>
#include <functional>
#include <mutex>
#include <thread>
#include <vector>

class Pool {
    std::mutex m;
    std::condition_variable_any cv;
    std::deque<std::function<void()>> q;          // 工作队列
    std::vector<std::jthread> workers;            // 最后声明：析构时最先销毁
public:
    explicit Pool(unsigned n) {
        for (unsigned i = 0; i < n; ++i)
            workers.emplace_back([this](std::stop_token st) {
                for (;;) {
                    std::function<void()> job;
                    {
                        std::unique_lock lk(m);
                        // 队列空就睡；收到停止请求且队列空就退出
                        if (!cv.wait(lk, st, [this] { return !q.empty(); })) return;
                        job = std::move(q.front());
                        q.pop_front();
                    }
                    job();                        // 在锁外执行任务
                }
            });
    }
    void submit(std::function<void()> f) {
        { std::lock_guard lk(m); q.push_back(std::move(f)); }
        cv.notify_one();                          // 叫醒一个睡着的 worker
    }
    // 不写析构函数：每个 jthread 析构时先 request_stop() 再 join()；
    // wait 只有在「已请求停止且队列为空」时才返回 false，所以队列里剩下的任务会先做完
};

int main() {
    std::atomic<long> sum{0};
    auto t0 = std::chrono::steady_clock::now();
    {
        Pool pool(std::thread::hardware_concurrency());
        for (long i = 1; i <= 100000; ++i)
            pool.submit([&sum, i] { sum.fetch_add(i, std::memory_order_relaxed); });
    }
    double ms = std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count();
    std::printf("sum = %ld (expected 5000050000)\n", sum.load());
    std::printf("100000 tasks on 10 workers: %.1f ms, %.2f us per task\n", ms, ms * 1000 / 100000);
}

7. 超订：线程比核多时，什么变慢了

7. Oversubscription: what gets slower when threads outnumber cores

超订（oversubscription）就是可运行的线程比核多。它的代价取决于线程之间是否互相等待。Lab B 用同一个程序测两种情况，本机 10 个核：

Oversubscription means more runnable threads than cores. Its cost depends on whether the threads wait for each other. Lab B measures both cases with one program on this machine’s 10 cores:

  • 互不等待的计算：几乎免费。10 个线程 0.44–0.49 s，100 个线程 0.44–0.45 s。调度器给每个线程整段的时间片，切换的直接代价分摊到几毫秒的计算里，看不出来。代价换了个地方：每个线程的完成时间被拉长到接近整个程序的时间，单个结果来得更晚。
  • Independent computation: nearly free. 10 threads take 0.44–0.49 s and 100 threads 0.44–0.45 s. The scheduler gives each thread a whole time slice, and the direct cost of switching is spread over milliseconds of computation and disappears. The cost moves elsewhere: each thread’s completion is stretched to nearly the whole program’s run time, so any single result arrives later.
  • 抢同一把自旋锁：慢几十倍。4 个线程 0.15 s，10 个线程 0.70 s，100 个线程 4.2–5.7 s。原因是持锁者被抢占（lock-holder preemption）：持锁的线程时间片到了被换下核，锁还攥在它手里；这时上核的其他线程只能空转，把各自的时间片烧完，直到持锁者重新被调度。线程越多，持锁者等回来的时间越长。CPU 时间约等于墙钟时间的 10 倍，说明 10 个核一直满载，几乎全在空转。
  • Contending for one spin lock: dozens of times slower. 4 threads take 0.15 s, 10 threads 0.70 s, and 100 threads 4.2–5.7 s. The cause is lock-holder preemption: the thread holding the lock runs out of time slice and is switched off its core while still holding the lock; the threads that come on can only spin and burn their own time slices until the holder is scheduled again. The more threads, the longer the holder waits to come back. CPU time is about 10 times the wall time, so all 10 cores were fully busy, almost all of it spinning.
  • 还有内存。每个线程至少占 512 KB 的栈地址空间、一页保护页，以及内核里的 Mach thread 和内核栈。100 个线程不算多；一万个线程在 64 位地址空间里也放得下，但每个线程碰过的栈页都是真实内存。
  • There is memory too. Each thread takes at least 512 KB of stack address space, a guard page, and a Mach thread and kernel stack inside the kernel. 100 threads is not many; ten thousand would still fit in a 64-bit address space, but every stack page a thread has touched is real memory.

规则：CPU 密集的工作，线程数等于核心数（本机 10，或者只要 P 核时 4）；线程会阻塞在 I/O 上时才多开；拿不准就交给 GCD 或线程池，让它们按核心数控制并发。忙等的锁只能用在临界区极短、而且线程数不超过核心数的地方；Phase 2 会换成会睡眠的锁。

The rule: for CPU-bound work, use as many threads as cores (10 here, or 4 when you want P cores only); use more only when threads block on I/O; when in doubt, hand the work to GCD or a thread pool and let them bound concurrency by the core count. A busy-waiting lock belongs only where the critical section is tiny and there are no more threads than cores; Phase 2 replaces it with locks that sleep.

  4. GCD。dispatch_group_async 就是「dispatch_async 进一个 group」：把 N 个空 block 放进全局并发队列，再 dispatch_group_wait 等它们全部做完：GCD. dispatch_group_async is dispatch_async into a group: put N empty blocks on the global concurrent queue, then dispatch_group_wait for all of them to finish:
    // spawn_gcd.c: 把 N 个空 block 用 dispatch_async 放进一个 group，再等它们全部完成
#include <dispatch/dispatch.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

static double now_us(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return ts.tv_sec * 1e6 + ts.tv_nsec / 1e3;
}

static double once(dispatch_queue_t q, int n) {
    dispatch_group_t g = dispatch_group_create();
    double t0 = now_us();
    for (int i = 0; i < n; ++i) dispatch_group_async(g, q, ^{});
    dispatch_group_wait(g, DISPATCH_TIME_FOREVER);
    double per = (now_us() - t0) / n;
    dispatch_release(g);
    return per;
}

static int cmp(const void *a, const void *b) {
    double x = *(const double *)a, y = *(const double *)b;
    return (x > y) - (x < y);
}

    // oversub.c: 总工作量固定，分给 T 个线程，报墙钟时间、CPU 时间和上下文切换次数。
//   ./oversub T compute   各线程独立计算，互不等待
//   ./oversub T spin      各线程反复抢同一把自旋锁（atomic_flag），锁里只做一次加法
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/resource.h>
#include <time.h>

#define COMPUTE_TOTAL (5000L * 1000 * 1000)    // compute 模式：总共 50 亿次加法
#define SPIN_TOTAL    (2L * 1000 * 1000)       // spin 模式：总共 200 万次加锁

static int nthreads;
static atomic_flag lock = ATOMIC_FLAG_INIT;
static long shared_counter;
static volatile long sink;

static double now_s(void) {
    struct timespec ts; clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static void *compute(void *arg) {
    (void)arg;
    long n = COMPUTE_TOTAL / nthreads, s = 0;
    for (long i = 0; i < n; ++i) { s += i ^ (s >> 3); }   // 有依赖链，编译器无法向量化
    sink = s;
    return NULL;
}

static void *spin(void *arg) {
    (void)arg;
    long n = SPIN_TOTAL / nthreads;
    for (long i = 0; i < n; ++i) {
        while (atomic_flag_test_and_set_explicit(&lock, memory_order_acquire)) { }  // 忙等
        shared_counter++;
        atomic_flag_clear_explicit(&lock, memory_order_release);
    }
    return NULL;
}

static double secs(struct timeval a, struct timeval b) {
    return (b.tv_sec - a.tv_sec) + (b.tv_usec - a.tv_usec) / 1e6;
}

int main(int argc, char **argv) {
    nthreads = argc > 1 ? atoi(argv[1]) : 10;
    int use_spin = argc > 2 && strcmp(argv[2], "spin") == 0;
    pthread_t *t = malloc(sizeof *t * nthreads);
    struct rusage r0, r1;
    getrusage(RUSAGE_SELF, &r0);
    double t0 = now_s();
    for (int i = 0; i < nthreads; ++i) pthread_create(&t[i], NULL, use_spin ? spin : compute, NULL);
    for (int i = 0; i < nthreads; ++i) pthread_join(t[i], NULL);
    double wall = now_s() - t0;
    getrusage(RUSAGE_SELF, &r1);
    double cpu = secs(r0.ru_utime, r1.ru_utime) + secs(r0.ru_stime, r1.ru_stime);
    printf("%-7s T=%3d  wall %6.2f s  cpu %6.2f s  involuntary switches %6ld\n",
           use_spin ? "spin" : "compute", nthreads, wall, cpu, r1.ru_nivcsw - r0.ru_nivcsw);
    free(t);
    return 0;
}

    • 样本数不等于 CPU 时间。每个线程都是 1302 个样本，因为 sample 每次把所有线程的栈都记一遍，不管线程当时在不在核上。100 个线程只有 10 个核，任一时刻至少 90 个在排队。要看谁真的在核上，用下一步的 spindump，它会标出线程是在运行还是被挂起。
    • Sample counts are not CPU time. Every thread has 1302 samples because sample records every thread’s stack each time, whether or not the thread is on a core. With 100 threads on 10 cores, at least 90 are queued at any moment. To see who is really on a core, use spindump in the next step, which marks whether a thread was running or suspended.

自测

Self-check

1. 在 macOS 上，一个新 pthread 的栈是谁、在什么时候分配的？

1. On macOS, who allocates a new pthread’s stack, and when?

_pthread_allocate 在调用 __bsdthread_create 之前就把栈映射好，再把栈顶地址传给内核。8 MB 和 ulimit -s 是主线程的栈，由内核在 exec 时建；新线程默认 512 KB。线程开始运行时就需要栈指针指向一块已有的栈，所以不可能等到第一次运行再分配。_pthread_allocate maps the stack before calling __bsdthread_create, then passes the stack top to the kernel. 8 MB and ulimit -s describe the main thread’s stack, built by the kernel at exec; a new thread defaults to 512 KB. A thread needs its stack pointer to point at an existing stack the moment it starts running, so the stack cannot be allocated at its first run.

2. Lab A 里 GCD 每个 block 约 0.1 µs，新建并 join 一个线程约 6 µs。主要原因是什么？

2. In Lab A, GCD costs about 0.1 µs per block while creating and joining a thread costs about 6 µs. What is the main reason?

差距来自复用：GCD 池子里的线程早就建好了。block 和普通线程一样在用户态执行，只是线程由系统的 workqueue 管理。核类型也不是原因：空 block 和空线程几乎不做计算，P 核和 E 核的速度差在这里无关紧要，而且两者都会用到两类核。The gap comes from reuse: the threads in GCD’s pool were built long before. Blocks run in user space like any thread; only the threads are managed by the system workqueue. Core type is not the reason either: empty blocks and empty threads do almost no computation, so the P versus E speed difference hardly matters here, and both use both kinds of core.

3. 你把一个计算线程设成 QOS_CLASS_BACKGROUND。根据 Apple 的文档和本页的实测，下面哪个说法对？

3. You set a compute thread to QOS_CLASS_BACKGROUND. According to Apple’s documentation and this page’s measurements, which statement is right?

Apple 的原话是「更可能」放到低性能核上。本页实测一个空闲机器上的 BACKGROUND 线程全程在 cpu 6–9（P 核），10 个时 P 核也分到近四分之一的工作。QoS 对 pthread 有效：pthread_set_qos_class_self_np 返回 0，查询也确认生效，E 核在 BACKGROUND 下每块计算明显更慢。Apple’s wording is “more likely” to run on lower-performance cores. Here a single BACKGROUND thread on an idle machine stayed on cpu 6–9 (P cores) throughout, and with 10 of them the P cores still took nearly a quarter of the work. QoS does apply to pthreads: pthread_set_qos_class_self_np returns 0, a query confirms it took effect, and E cores ran each chunk clearly slower under BACKGROUND.

4. Lab B 里 100 个线程的 compute 和 10 个一样快，而 100 个线程的 spin 比 10 个慢了约 7 倍。为什么？

4. In Lab B, compute with 100 threads is as fast as with 10, while spin with 100 threads is about 7 times slower than with 10. Why?

如果切换本身太贵，compute 也会变慢，可它在 100 个线程时和 10 个一样是 0.44 s 左右。spin 只共享一个计数器和一把锁，总数据量很小，与 cache 容量无关。真正的原因是持锁者被抢占：线程比核多，持锁的线程迟早被换下去，等它的线程越多，浪费越大。If switching itself were too expensive, compute would slow down too, yet at 100 threads it takes about 0.44 s, the same as at 10. spin shares just one counter and one lock; its total data is tiny and unrelated to cache capacity. The real cause is lock-holder preemption: with more threads than cores the holder is eventually switched out, and the more threads wait for it, the more is wasted.
