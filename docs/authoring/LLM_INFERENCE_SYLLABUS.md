# LLM Inference Kernels (SGLang) topic syllabus (authoring spec)

Topic id `llm-inference-kernels`, folder `topics/llm-inference-kernels/`, progress key `llm`, hub card title "推理引擎与 GPU 内核（SGLang）· LLM Inference Kernels (SGLang)". Written against `docs/authoring/PAGE_CONTRACT.md`. Goal for the learner: read, profile and write the GPU kernels under an LLM inference engine, taking SGLang as the engine: see how each runtime design choice (RadixAttention, continuous batching, CUDA graphs, MoE, quantization, speculative decoding, structured output) places a requirement on a kernel, meet that requirement in code, and measure the end-to-end effect. "Kernel" here means a GPU compute kernel, not the OS kernel of the Kernel Engineering topic; the two link to each other. Reader: has done GPU Programming with CUDA (warps, memory hierarchy, occupancy, streams and graphs, profiling) and Parallel Programming. The overview page is the Founder's brief verbatim (`topics/llm-inference-kernels/BRIEF.md`, the text after the rule), with a dated note beside it on what moved since (the kernel library's path and package name).

## Pinned facts (verified 2026-10-31 unless noted; `llm-pins.md` has the sources)

- **SGLang:** PyPI `sglang` 0.5.23 (2026-10-30); GitHub release v0.5.22 (2026-10-19), the tag the pages cite for source paths. Its `python/pyproject.toml` pins `torch==2.14.1`, `flashinfer_python[cu13]==0.7.1`, `cuda-python>=13.0`, `xgrammar==0.2.7`, `sglang-kernel==0.4.9`, `sgl-deep-ep==0.1.2.post1`, `sgl-deep-gemm==0.2.2`, `humming-kernels[cu13]==0.1.12`, `quack-kernels==0.6.5`. The writer of each page re-reads the file at the tag before quoting a version.
- **The kernel library:** the brief's `sgl-kernel/` moved; at v0.5.22 it is `python/sglang/kernels/` with `aot/csrc/` (ahead-of-time CUDA/C++ ops, e.g. `aot/csrc/moe/moe_align_kernel.cu`), `jit/csrc/` (JIT-built ops) and `ops/` (the Python wrappers, e.g. `ops/moe/moe_align.py`); PyPI package `sglang-kernel`. The old PyPI `sgl-kernel` stopped at 0.3.21 (2026-01-15). Every page that names a source file gives the path under the v0.5.22 tag and the date.
- **AttentionBackend (v0.5.22, `python/sglang/srt/layers/attention/base_attn_backend.py`):** `init_forward_metadata`, `init_forward_metadata_out_graph`, `init_forward_metadata_in_graph`, `init_cuda_graph_state`, `forward`, `forward_decode`, `forward_extend`, `forward_mixed`, `support_triton`, `verify_mask`, plus the breakable-graph and shared-read hooks. The brief's shorter list still holds in substance.
- **Upstream libraries (GitHub releases API, 2026-10-31):** FlashInfer v0.7.2.post1 (2026-10-23; SGLang pins 0.7.1); FlashAttention v2.8.3.post2 (2026-10-13; FA3 is the `hopper/` tree, Hopper only); FlashMLA (no releases; cite by commit date; **its README on `main`, read 2026-11-01, says the 2026-09-30 release removed Hopper support and the earlier DeepSeek models and now requires SM100 / SM103, i.e. Blackwell, with the Hopper-capable code kept at commit `ba89a3466e9470ad08ab39738d4e7bb66989e1e7`** — but SGLang v0.5.22 does not bundle upstream main: it bundles the fork `sgl-project/FlashMLA` at commit 3620b63 (2026-09-28), whose `python/sglang/kernels/aot/cmake/flashmla.cmake` still emits sm_90a and builds the sm90 dense and sparse decode kernels (Phase 2 writer, 2026-11-01); so FlashMLA is described on the pages and stays off the H100 tier until an MLA model with the flashmla backend has been checked on one H100); DeepGEMM v2.1.1.post3 (2025-10-15); DeepEP v1.2.1 (2025-09-16; its dispatch and combine need several GPUs over NVLink or RDMA, so the DeepEP lab is described, not run, even on one rented H100); CUTLASS v4.8.1 (2026-10-21) and the CuTe DSL `nvidia-cutlass-dsl` 4.8.1 on PyPI (SGLang v0.5.22 pins `nvidia-cutlass-dsl[cu13]==4.8.0`, pyproject line 55 — Phase 6 writer, 2026-11-01; labs clone the v4.8.0 tag); Triton v3.9.0 (2026-10-27); TileLang v0.1.15 (2026-09-30); xgrammar v0.2.8 (2026-09-24); vLLM v0.32.0 (2026-10-18) for comparison only; PyTorch 2.15.0 (2026-10-28; SGLang pins 2.14.1).
- **Install and hardware (SGLang `docs/docs/get-started/install.mdx` at v0.5.22, read 2026-10-31):** SGLang requires CUDA 13 (the CUDA 12 lane ended with 0.5.19 when PyTorch 2.14 dropped CUDA 12.9 builds), Python 3.11 or higher; Docker images `lmsysorg/sglang:<tag>` ship a CUDA 13 environment and need a CUDA 13-compatible driver plus the NVIDIA Container Toolkit; wheels install with `uv pip install --prerelease=allow sglang` (the `cu130` extra index when needed). Triton v3.9.0's README lists NVIDIA GPUs of compute capability 8.0 or higher, so Colab's T4 (sm_75) is out for every Triton kernel.
- **GPU tiers (carried from the GPU topic, CUDA 13.4 Update 2):** Colab's T4 (sm_75) is below Triton's floor and most of these kernels; the labs that run SGLang itself use a rented L4 (sm_89: FP8 GEMMs, FlashInfer decode, CUDA graphs, xgrammar) and the Hopper-only labs (FA3, DeepGEMM) a rented H100 (sm_90), each marked with its tier and cost; FlashMLA (Blackwell-only since 2026-09-30), DeepEP (multi-GPU) and the Blackwell-only formats (NVFP4/MXFP4) are described, never run. Verified at v0.5.22 by the lab-page writer on 2026-11-01: the server binds to 127.0.0.1:30000 by default (`python/sglang/srt/arg_groups/fields/serving.py`); the CUDA-graph switch is `--cuda-graph-backend-decode disabled` (`arg_groups/fields/exec_.py` line 551; the deprecated `--disable-cuda-graph` is handled in `server_args.py` lines 407–414 and maps to disabling both the decode and the prefill graph backends — Phase 3 writer, 2026-11-01); the benchmark entry point is `python -m sglang.benchmark.one_batch` (`--profile-stage decode`); the full `lmsysorg/sglang` image installs `nsight-systems-cli` (`docker/Dockerfile` line 463); Docker Hub carries `lmsysorg/sglang:v0.5.23` (2026-10-30, about 16 GB). Renting is the Founder's spend (R-AP-9(a)); until an account exists every cloud lab is marked "未运行 · not run; assembled from the documentation and the source at v0.5.22 on <date>" exactly as the GPU topic does.
- **Local counterpart (no install on the Founder's Mac):** Metal kernels in Swift compiled at runtime, the GPU topic's route (Apple M5, SIMD width 32, 1024 threads per threadgroup, unified memory). Each phase's Lab B is the Metal twin of that phase's kernel idea, run and measured on the Mac. MLX would be the richer twin but needs `pip install`; not used unless the Founder says so.
- **Primary sources (every arXiv id below verified against the arXiv API on 2026-10-31; titles match):** the SGLang paper (Zheng et al., NeurIPS 2024, arXiv:2312.07104); PagedAttention / vLLM (Kwon et al., SOSP 2023, arXiv:2309.06180); FlashAttention (Dao et al., arXiv:2205.14135), FlashAttention-2 (arXiv:2307.08691), FlashAttention-3 (arXiv:2407.08608); FlashInfer (Ye et al., MLSys 2025, arXiv:2501.01005); DeepSeek-V3 technical report (MLA, FP8 training and inference kernels, arXiv:2412.19437); speculative decoding (Leviathan et al., ICML 2023, arXiv:2211.17192) and EAGLE (arXiv:2401.15077); XGrammar (arXiv:2411.15100). Book: PMPP 5th ed. (the GPU topic's citation) for the kernel patterns. Writers cite the arXiv id and the version they read.
- Anything beyond these pins is marked 大致 / "check the docs".

## Lab environment (`topics/llm-inference-kernels/lab-setup/index.html`)

Why this shape: the engine needs an NVIDIA GPU of at least Ada class for most of its kernels and Hopper for several; the Mac has none, so the cloud tiers of the GPU topic carry over (the lab page links the GPU topic's lab page for the account, keys, container and bill rules rather than repeating them) and the Metal twins run here. Three parts: 1. the rented L4 running the `lmsysorg/sglang:v0.5.23` image (CUDA 13 inside; the writer confirms the tag exists on Docker Hub) or `uv pip install --prerelease=allow sglang==0.5.23` in the GPU topic's `nvidia/cuda:13.4.3-devel-ubuntu24.04` container with Python 3.11 or higher, a small model that fits (the writer picks one the docs name for an L4 and states its size), `python -m sglang.launch_server`, `bench_one_batch`, the torch profiler and Nsight Systems; 2. the H100 tier only for the Hopper-only labs, with a cost note; 3. the Mac for Metal twins with the GPU topic's probe. Safety: a serving process is a network service — bind to localhost, never expose it, never put keys in notebooks. One diagram: the four layers of the brief (frontend, runtime, model executor, kernel layer) with the three machines beside them. Lab: launch the server on the L4 against the small model, send one request, read the decode step in the torch profiler (not run); the Metal probe on the Mac (run).

## Phases (nine, 0–8; each with two diagrams, Lab A (SGLang/CUDA on the cloud tier, not run) and Lab B (the Metal twin on the Mac, run), a four-question quiz, resources, bibliography; meta "Phase N / 9")

### Phase 0 · 自顶向下的栈 · The Stack, Top to Bottom (`phase-0-the-stack`)
The four layers of the brief with the v0.5.22 paths for each (frontend `python/sglang/lang/`, runtime `python/sglang/srt/managers/` scheduler and the radix cache, model executor `python/sglang/srt/model_executor/`, kernels `python/sglang/kernels/` and the upstream libraries); what a decode step does op by op (attention, GEMMs, MoE, RMSNorm, RoPE, activation, sampling, all-reduce); why decode is bandwidth-bound and prefill compute-bound, with the arithmetic (bytes of weights per token against FLOPs); where each runtime idea lands on a kernel (the brief's "each design choice in layers 2–3 places a requirement on layer 4"). Table: runtime idea ↔ kernel requirement ↔ library that meets it. Diagram (a): the four layers with one request flowing down. Diagram (b): one decode step as a sequence of kernels with their byte and FLOP budgets. Lab A: launch SGLang on the L4, profile one decode step with the torch profiler, list the ten longest kernels (not run). Lab B: a decode-shaped GEMV (4096 × 4096 FP16 weights, one token) against a prefill-shaped GEMM (256 tokens) in Metal, run, bandwidth and FLOP rates printed.

### Phase 1 · 注意力与 KV 缓存布局 · Attention and KV-Cache Layouts (`phase-1-attention-and-kv-layouts`)
RadixAttention and the radix-tree cache (`python/sglang/srt/mem_cache/`), token-granular pages scattered and shared across requests; the CSR contract (indptr/indices) FlashInfer's paged and ragged APIs take; cascade (shared-prefix) attention computing the common prefix once; how the backend's `init_forward_metadata` builds those arrays. Table: layout (contiguous ↔ paged ↔ ragged ↔ cascade) ↔ index arrays ↔ who builds them ↔ kernel cost. Diagram (a): a radix tree over three prompts and the pages each request's indices point at. Diagram (b): a decode attention kernel gathering KV through indptr/indices. Lab A: read the FlashInfer paged decode call in the SGLang backend, dump a batch's indptr/indices, run FlashInfer's decode on it with and without cascade (not run). Lab B: paged-KV decode attention in Metal: a page table with scattered pages gathered through indptr/indices against a contiguous cache, run, bandwidth compared.

### Phase 2 · 预填充与解码 · Prefill and Decode (`phase-2-prefill-and-decode`)
Prefill as a compute-bound tiled attention (FlashAttention's tiling and online softmax, FA3's warp specialization and FP8 on Hopper), decode as a bandwidth-bound stream over KV (split-KV / flash-decoding), MLA for DeepSeek-style models (FlashMLA), chunked prefill and the per-phase backend choice in SGLang (`--attention-backend`, `--decode-attention-backend` or the equivalent flags at v0.5.22, writer verifies). Table: phase ↔ bound ↔ kernel family ↔ backend flag. Diagram (a): FA2 tiling with the online-softmax running max and sum. Diagram (b): split-KV decode: partial results per split and the combine step. Lab A: time prefill and decode of one request on the L4 with two attention backends; on the H100 tier FA3 against FA2 (not run). Lab B: the GPU topic's fused softmax extended to a flash-style attention tile for prefill and a split-KV decode in Metal, run.

### Phase 3 · CUDA 图与 plan()/run() 拆分 · CUDA Graphs and the plan()/run() Split (`phase-3-cuda-graphs-plan-run`)
Why decode steps are captured (launch overhead against a 1 µs-class kernel), what a capturable kernel may not do (host syncs, dynamic allocation, dynamic shapes), padding to static batch sizes, SGLang's capture sizes and `init_cuda_graph_state` / `init_forward_metadata_in_graph`, FlashInfer's CPU-side `plan()` and graph-safe `run()`. Table: forbidden in a graph ↔ why ↔ the workaround. Diagram (a): a decode step captured and replayed with a padded batch. Diagram (b): plan() on the CPU writing metadata buffers that run() reads inside the graph. Lab A: measure decode with and without `--disable-cuda-graph` (flag name verified at the tag), then capture a toy decode step by hand with stream capture (not run). Lab B: one command buffer with N encoders replayed against N command buffers, and an indirect command buffer as the closest Metal analogue, run, per-step overhead printed.

### Phase 4 · MoE 内核 · MoE Kernels (`phase-4-moe-kernels`)
Routing and top-k, `moe_align_block_size` (sort and pad tokens per expert; `python/sglang/kernels/aot/csrc/moe/moe_align_kernel.cu`), fused or grouped GEMMs (Triton `fused_moe`, DeepGEMM for FP8 block-quantized weights), expert parallelism with DeepEP's dispatch and combine; the padding waste and how block size trades it against occupancy. Table: MoE stage ↔ kernel ↔ library ↔ hardware tier. Diagram (a): tokens routed to experts, sorted and padded into blocks. Diagram (b): grouped GEMM over the padded blocks and the combine. Lab A: run `moe_align_block_size` on a synthetic routing and measure padding waste against block size; on the H100 tier a DeepGEMM grouped GEMM (not run). Lab B: top-k routing, align-and-pad and a grouped GEMM in Metal, run, waste and throughput printed.

### Phase 5 · 融合 · Fusions (`phase-5-fusions`)
Why fusion cuts memory traffic (every unfused op reads and writes the activation once); the common fusions: residual-add + RMSNorm, SiLU-and-mul, RoPE + KV-cache write, all-reduce + norm, sampling (FlashInfer's top-k/top-p without a full sort); where each lives at v0.5.22 (the writer lists the files under `python/sglang/kernels/` and the FlashInfer calls). Table: fusion ↔ bytes saved per token ↔ where it lives. Diagram (a): unfused against fused residual + RMSNorm with the byte counts. Diagram (b): top-k/top-p sampling without a full sort. Lab A: time the fused and unfused norm paths in SGLang (flags or a small script against the ops) and read them in the profiler (not run). Lab B: fused against unfused residual + RMSNorm and SiLU-and-mul in Metal, run, bytes and time compared.

### Phase 6 · 量化内核 · Quantization Kernels (`phase-6-quantization-kernels`)
FP8 (E4M3/E5M2) weight and activation quantization with per-block scales, NVFP4/MXFP4 on Blackwell, int4 AWQ/GPTQ weight-only kernels; why quantizing saves memory but not time without a matching GEMM kernel; CUTLASS and the CuTe DSL as the way those GEMMs are built; what DeepGEMM does for FP8 block-quantized weights. Table: format ↔ what is quantized ↔ kernel ↔ minimum hardware. Diagram (a): a weight-only int4 GEMV dequantizing on the fly. Diagram (b): an FP8 block-scaled GEMM tile. Lab A: serve an FP8 and an int4 checkpoint on the L4 and compare decode speed; a CuTe DSL GEMM on the L4 (not run). Lab B: int8 and int4 weight-only GEMV with scales in Metal against FP16, run, bandwidth gain printed.

### Phase 7 · 推测解码与结构化输出内核 · Speculative Decoding and Structured-Output Kernels (`phase-7-speculative-and-structured-output`)
Draft-then-verify, EAGLE's draft tree, tree-attention masks and the verification kernel, acceptance; structured output with xgrammar: the token bitmask applied to logits every step as a small kernel on the hot path. Table: feature ↔ extra kernel ↔ cost per step. Diagram (a): a draft tree, its attention mask and the accepted path. Diagram (b): the logits bitmask applied before sampling. Lab A: run SGLang with and without EAGLE and with a JSON schema, measure accepted tokens per step and the bitmask kernel's time in the profiler (not run). Lab B: a tree-attention mask apply and a logits bitmask kernel in Metal, run.

### Phase 8 · 接入点与作品项目 · Plugging In and the Capstone (`phase-8-plugging-in`)
Where a kernel engineer plugs in: an op in `python/sglang/kernels/` exposed through torch ops, an `AttentionBackend` around a kernel, upstream contributions (FlashInfer, DeepGEMM, FlashMLA, CUTLASS), the tooling (`bench_one_batch`, the torch profiler, Nsight Systems and Compute), the languages (CUDA, CuTe/CuTe DSL, Triton, TileLang); the brief's "good way in" as the capstone: read the attention backend beside FlashInfer's paged API, profile a decode step on a MoE model, write or optimize one small fused op. Diagram (a): the plug-in points over the four layers. Diagram (b): the capstone loop: a runtime constraint → a kernel → an end-to-end measurement. Lab A: build the capstone op as a sgl-kernel-style CUDA op registered through torch ops and measured with `bench_one_batch` (not run). Lab B: the same op in Metal on the Mac, run, the two results in one table whose CUDA column is marked not run. Closing sections per the contract: 作品项目 / Capstone (specification and acceptance criteria) and 接下来 / What comes next (GPU Programming with CUDA for the kernel craft, Kernel Engineering for the OS beneath, Parallel Programming for the CPU side).
