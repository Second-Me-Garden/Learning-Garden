# ROS 2 topic syllabus (authoring spec)

Topic id `ros2`, folder `topics/ros2/`, progress key `ros2`, hub card title "ROS 2". Written against `docs/authoring/PAGE_CONTRACT.md`. Goal for the learner: understand robot middleware well enough to build, simulate and ship a small robot stack, and to see how it rests on the OS kernel (threads, scheduling, sockets, drivers). Reader: knows Python, some C++ and the Linux command line; has done or is doing the Kernel Engineering topic.

## Pinned versions (verified 2026-10-31)

- **ROS 2 Jazzy Jalisco**, LTS, released 2024-05-23, EOL May 2029, on **Ubuntu 24.04 arm64**. All commands and package names use `jazzy`.
- Newest LTS is **Lyrical Luth** (released 2026-05-22, EOL May 2031, Ubuntu 26.04, Gazebo Jetty); Kilted Kaiju (2025-05-23) is not LTS and ends December 2026. Say once, in Phase 0 and lab-setup, that swapping the distro name in every command moves the course to Lyrical. Source: the official Releases page (ros2_documentation, Releases.rst) and the Gazebo ROS installation page.
- **Gazebo Harmonic** is the recommended simulator for Jazzy; `sudo apt install ros-jazzy-ros-gz` installs it through the ROS vendor packages (Gazebo page: vendor packages start with Jazzy). Kilted pairs with Ionic, Lyrical with Jetty.
- Client libraries rclcpp (C++17) and rclpy (Python 3.12 on 24.04). Build with colcon, ament_cmake and ament_python. Default middleware on Jazzy is `rmw_fastrtps_cpp`; `rmw_cyclonedds_cpp` and `rmw_zenoh_cpp` are alternatives (mark Zenoh's support tier as "check the docs for your distro").
- Anything beyond these pins that a writer is not certain of is marked 大致 / approximate or "check the docs", never invented.

## Lab environment (`topics/ros2/lab-setup/index.html`)

Why isolate: a ROS 2 install adds an apt repository and hundreds of packages, discovery traffic is UDP multicast on the LAN (every ROS 2 machine on the network with the same `ROS_DOMAIN_ID` sees you), and native macOS is not a supported tier for Jazzy. So the labs run in a Linux guest on the Apple Silicon Mac; the host only edits files and opens a browser.

Three options, in order of recommendation:

1. **Docker container, arm64** (recommended). Base image `ros:jazzy-ros-base` (the Official Library `ros` images are published for arm64v8; the `osrf/ros` desktop images are listed amd64-only, so the desktop packages are installed on top). The Dockerfile installs `ros-jazzy-desktop`, `ros-jazzy-ros-gz`, `ros-jazzy-navigation2 ros-jazzy-nav2-bringup`, `ros-jazzy-slam-toolbox`, `ros-jazzy-ros2-control ros-jazzy-ros2-controllers ros-jazzy-gz-ros2-control`, `ros-jazzy-rqt ros-jazzy-rqt-common-plugins`, `ros-jazzy-ros2trace ros-jazzy-tracetools-launch` (optional; there is no `ros-jazzy-ros2-tracing` package, checked against the noble arm64 index 2026-10-31), plus a lightweight desktop reached from the Mac's browser (XFCE + TigerVNC + noVNC on port 6080). Compose file with `shm_size: 4g`, `LIBGL_ALWAYS_SOFTWARE=1` (Gazebo renders with Mesa llvmpipe; no GPU passthrough on macOS Docker), `QT_X11_NO_MITSHM=1`, a named volume for the workspace, and `cap_add: [SYS_NICE]` with `ulimits: rtprio: 99` for the Phase 2 real-time lab. A `lab.sh` script with `build | up | shell | down | snapshot` (snapshot = `docker commit`). Mark the whole recipe "assembled from the official docs on 2026-10-31; not executed on this Mac" so the reader expects to adjust package names. Discovery stays on the machine by default with `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` (Jazzy); `ROS_LOCALHOST_ONLY=1` is deprecated since Iron and only mentioned as the old name.
2. **UTM virtual machine**, Ubuntu 24.04 arm64 desktop, with the native ROS 2 apt install. Full desktop, but Gazebo's GUI is known to fail on UTM's partial OpenGL; use it for everything except Gazebo, or run Gazebo headless (`gz sim -s`) with RViz2 for viewing.
3. **A cloud or x86 Linux machine with a GPU** for heavy simulation, reached with SSH and a remote desktop. Optional.

Kernel crossover note for this page: a container shares the kernel of Docker Desktop's Linux VM, which is fine because ROS 2 is user space; `SCHED_FIFO` needs `CAP_SYS_NICE` and an rtprio ulimit, and `PREEMPT_RT` would need the VM's kernel, which the reader cannot change here. One diagram: host Mac ↔ container (ROS graph, Gazebo, VNC desktop) ↔ browser, plus the volume and the network namespace. Lab: build the image, run talker and listener, open noVNC, start `rviz2` and `gz sim shapes.sdf`.

## Phases

Each phase: two diagrams (a) and (b), Lab A and Lab B, a four-question quiz, resources, bibliography. Phase length 1–2 weeks at 1–2 hours a day. Total 8 phases, 0–7.

### Phase 0 · 基础 · Foundations (`phase-0-foundations`)
Concepts: what ROS 2 is (middleware + tools + ecosystem, not an OS); ROS 1 → ROS 2 (no master, DDS, security, real-time intent, Python 3); distributions and LTS; the layer stack: user node → rclcpp / rclpy → rcl → rmw → DDS or Zenoh → OS (UDP sockets, multicast, shared memory, threads, the scheduler); workspaces, overlay and underlay sourcing, colcon, ament, `package.xml`; the `ros2` CLI; `ROS_DOMAIN_ID`. Comparison table: ROS 1 ↔ ROS 2. Diagram (a): the layer stack from a node down to the kernel, one layer per step. Diagram (b): workspace build and sourcing: underlay `/opt/ros/jazzy` → overlay `~/ws/install`, colcon build graph. Lab A: in the container run `ros2 run demo_nodes_cpp talker` and `listener`, `ros2 node list`, `ros2 node info`, `ros2 topic echo`, `ros2 doctor --report`; create a workspace and build an empty package with colcon. Lab B (kernel crossover): see what the middleware does at the OS level: `ss -ulpn` for the DDS UDP ports, the discovery multicast address, threads per node with `ps -T`, the effect of `ROS_DOMAIN_ID` on port numbers.

### Phase 1 · 节点、话题、服务、动作 · Nodes, Topics, Services, Actions (`phase-1-nodes-topics-services-actions`)
Concepts: nodes and the graph; publishers and subscriptions; interfaces (`.msg`, `.srv`, `.action`, built on IDL) and building a custom interface package; services; actions (goal, feedback, result, cancel; built on topics and services); parameters (declare, get, set, callbacks, YAML, `ros2 param`); rclcpp and rclpy idioms side by side. Comparison table: rclcpp ↔ rclpy for the same node. Diagram (a): the graph: two nodes, one topic, one service, one action and the direction of each message. Diagram (b): an action from goal acceptance through feedback to result, with cancel. Lab A: a publisher and subscriber pair in Python and C++, a custom message package, `ros2 interface show`. Lab B: a service server and client, then the Fibonacci action from the official tutorial, parameters from a YAML file.

### Phase 2 · 执行器、回调与时序 · Executors, Callbacks, Timing (`phase-2-executors-and-timing`)
Concepts: `spin`, the executor loop and wait sets; SingleThreaded, MultiThreaded and the events executor (mark availability per distro); callback groups (mutually exclusive versus reentrant); timers; the deadlock of calling a service from inside a callback; callback latency and jitter; real-time basics for ROS 2: avoid allocation in the hot path, `SCHED_FIFO` with `chrt`, `PREEMPT_RT`, memory locking, the rclcpp real-time guidelines; `ros2_tracing`. Kernel crossover: a ROS 2 callback thread is a Linux task; who runs next is the kernel scheduler from Kernel Engineering Phase 1. Comparison table: executor types. Diagram (a): the executor loop: wait set → ready entities → callbacks in order. Diagram (b): two callback groups on a multithreaded executor, a timeline showing reentrant and mutually exclusive behaviour. Lab A: a 100 Hz timer node, measure jitter with `ros2 topic hz` and timestamps, then MultiThreadedExecutor with callback groups. Lab B: run the node under `chrt -f 80` in the container (needs `CAP_SYS_NICE`), compare jitter, look at `/proc/<pid>/sched` and `ps -T`.

### Phase 3 · 中间件与 QoS · Middleware and QoS (`phase-3-middleware-and-qos`)
Concepts: DDS and RTPS (participant, topic, DataWriter, DataReader); the rmw layer and the three middlewares; discovery (simple discovery over multicast, the discovery server, `ROS_LOCALHOST_ONLY`, `ROS_AUTOMATIC_DISCOVERY_RANGE` on Jazzy); QoS policies: reliability, durability, history and depth, deadline, lifespan, liveliness; compatibility rules and `ros2 topic info -v`; the sensor-data profile; large messages, shared-memory transport and loaned messages; SROS2 security (keystore, enclaves, `ROS_SECURITY_ENABLE`). Comparison table: QoS policy ↔ default profile ↔ sensor-data profile. Diagram (a): discovery and QoS matching between a reliable publisher and a best-effort subscriber, with the incompatible case. Diagram (b): the rmw layer: one API, three middlewares, where serialization and the wire sit. Lab A: QoS mismatch experiments with `ros2 topic pub` and `echo` options, `ros2 topic info -v`; switch the middleware with `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`. Lab B: an SROS2 keystore and enclave for talker and listener; watch the UDP ports and multicast with `ss` and `tcpdump`.

### Phase 4 · Launch、参数、生命周期与组合 · Launch, Parameters, Lifecycle, Composition (`phase-4-launch-lifecycle-composition`)
Concepts: Python launch files (LaunchDescription, Node, substitutions, launch arguments, events, including other launch files); parameter YAML and namespaces and remapping; managed (lifecycle) nodes and their state machine (unconfigured, inactive, active, finalized; configure, activate, deactivate, cleanup, shutdown); `ros2 lifecycle`; composition: components, `rclcpp_components`, the component container, intra-process communication and zero-copy. Comparison table: one process per node ↔ composed nodes. Diagram (a): the lifecycle state machine with every transition. Diagram (b): three nodes composed in one process with intra-process delivery versus three processes over DDS. Lab A: a launch file that starts talker and listener with remaps and a YAML parameter file; convert a node to a lifecycle node and drive it with `ros2 lifecycle set`. Lab B: load two components into a container with `ros2 component load`, enable `use_intra_process_comms`, measure the latency difference.

### Phase 5 · TF2、机器人描述与仿真 · TF2, Robot Description, Simulation (`phase-5-tf2-urdf-simulation`)
Concepts: coordinate frames and the conventions of REP 103 and REP 105 (x forward, z up; map, odom, base_link); the tf2 tree, static and dynamic transforms, broadcasters and listeners, time and `use_sim_time`; URDF and xacro (links, joints, inertia), `robot_state_publisher`, `joint_state_publisher`; RViz2; Gazebo Harmonic basics (SDF worlds, plugins, `gz sim`), the `ros_gz_bridge`, simulated sensors (lidar, camera, IMU), the differential-drive plugin. Comparison table: URDF ↔ SDF. Diagram (a): the tf tree map → odom → base_link → lidar with one transform lookup at a given time. Diagram (b): the simulation loop: Gazebo physics and sensors → bridge → ROS topics → controller → `/cmd_vel` → back. Lab A: a URDF for a two-wheel robot, view it in RViz2 with `robot_state_publisher`, write a tf2 listener. Lab B: spawn it in Gazebo Harmonic with the diff-drive and lidar plugins, bridge `/cmd_vel` and `/scan`, drive it with `teleop_twist_keyboard`.

### Phase 6 · 控制与导航 · Control and Navigation (`phase-6-control-and-navigation`)
Concepts: ros2_control architecture (controller_manager, hardware interfaces, state and command interfaces, the real-time update loop), `diff_drive_controller` and `joint_trajectory_controller`, `gz_ros2_control`; Nav2 architecture (the BT navigator and behavior trees, planner, controller, smoother and behavior servers, global and local costmaps with layers, AMCL, the map server, lifecycle managers); SLAM with `slam_toolbox`. Comparison table: Nav2 server ↔ what it answers. Diagram (a): the ros2_control loop: read → update controllers → write at a fixed rate on a real-time thread. Diagram (b): Nav2 from a goal pose through the behavior tree, planner and controller to `/cmd_vel`, with the costmaps. Lab A: ros2_control for the Phase 5 robot through `gz_ros2_control` with `diff_drive_controller`. Lab B: build a map with `slam_toolbox` in Gazebo, then Nav2 with that map, send a NavigateToPose goal from RViz2 and from a Python action client.

### Phase 7 · 工具链、测试与部署 · Tooling, Testing, Deployment (`phase-7-tooling-testing-deployment`)
Concepts: rqt (graph, console, plot), `ros2 bag` record and play (storage format MCAP; mark "default on Jazzy, check"), `ros2 doctor`, logging and its configuration, tracing with `ros2_tracing` and LTTng, testing (gtest and pytest through ament, `launch_testing`, `colcon test`), linters, `rosdep`, CI with GitHub Actions, Docker deployment with multi-stage builds, arm64 targets, micro-ROS for microcontrollers (concept only), DDS tuning (`net.core.rmem_max`, buffer sizes), a capstone: one deployable package with tests and a bag-based regression. Comparison table: the tool for each question. Diagram (a): the test pyramid for a ROS 2 package: unit → integration with launch_testing → system with bag replay. Diagram (b): record → replay with `--clock` and `use_sim_time` → analysis. Lab A: a pytest and a launch_test for the Phase 1 nodes, `colcon test`, record and replay a bag. Lab B: a multi-stage Dockerfile for the workspace, run it, trace callback latency with `ros2_tracing` (note if LTTng is unavailable in the container).
