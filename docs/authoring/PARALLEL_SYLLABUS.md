# Parallel Programming (CPU) topic syllabus (authoring spec)

Topic id `parallel-programming`, folder `topics/parallel-programming/`, progress key `par`, hub card title "并行编程 · Parallel Programming". Written against `docs/authoring/PAGE_CONTRACT.md`. Goal for the learner: write correct, measurably faster shared-memory parallel programs on a multicore machine, understand the memory model that makes them correct, and read what the hardware and the kernel do underneath. The labs run on the Mac itself (Founder direction 2026-10-30); the kernel topic's Linux VM is used only where a Linux-only tool is needed. Reader: knows C and some C++, has done or is doing Kernel Engineering; Python is used only for plotting results.

## Pinned facts (verified on the lab Mac 2026-10-31 unless noted)

- **Machine:** Apple M5, 10 cores (4 performance + 6 efficiency, `sysctl hw.perflevel0.physicalcpu` / `hw.perflevel1.physicalcpu`), cache line 128 bytes (`hw.cachelinesize`), L2 16 MB on the P cluster and 6 MB on the E cluster, no SMT, no NUMA. Say that x86 servers differ (64-byte lines, SMT, NUMA) wherever it matters.
- **OS and toolchain:** macOS 27.2 with the Command Line Tools only (`xcode-select -p` → `/Library/Developer/CommandLineTools`); Apple clang 21 (`clang --version`). Instruments and `xctrace` need the full Xcode and are optional on this topic; `sample`, `spindump`, `dtrace` (SIP limits some probes) and `leaks` are present. There is no `perf` on macOS; Linux `perf` runs in the kernel topic's QEMU VM (link `../../kernel-engineering/lab-setup/index.html`).
- **OpenMP:** Apple clang ships no OpenMP runtime. The lab installs it with `brew install libomp` and builds with `clang -Xclang -fopenmp -I$(brew --prefix libomp)/include -L$(brew --prefix libomp)/lib -lomp`; the alternative is `brew install llvm` and `$(brew --prefix llvm)/bin/clang -fopenmp`. Neither was installed on the lab Mac when this was written, so the lab page must include a smoke test (`omp_get_max_threads()` printed) and mark the exact flags as "verify with the smoke test" (sources: Homebrew formula pages, community guides; no 2026 Apple documentation found).
- **Works out of the box (compiled and run on the lab Mac):** C++20 `std::jthread` and `std::atomic` (`clang++ -std=c++20`; `hardware_concurrency()` reports 10); C11 `<stdatomic.h>` with Grand Central Dispatch (`dispatch_apply`, `__block` for captured atomics); NEON intrinsics via `<arm_neon.h>` (`vld1q_f32`, `vaddq_f32`, `vst1q_f32`); `-fsanitize=thread` is available in Apple clang (state as fact only after the writer compiles a race under it).
- **Not present:** Rust toolchain (the Rust book is reading, not a lab), Python with free threading (the system Python is 3.9).
- **Books (verified 2026-10-31):** 1. Anthony Williams, *C++ Concurrency in Action*, 2nd ed., Manning, 2019, ISBN 9781617294693. 2. Maurice Herlihy, Nir Shavit, Victor Luchangco, Michael Spear, *The Art of Multiprocessor Programming*, 2nd ed., Morgan Kaufmann, 2020, ISBN 9780124159501. 3. Paul E. McKenney, *Is Parallel Programming Hard, And, If So, What Can You Do About It?*, free (CC BY-SA), latest release at kernel.org/pub/linux/kernel/people/paulmck/perfbook/ (the writer names the release it read). 4. Mara Bos, *Rust Atomics and Locks*, O'Reilly, 2023, ISBN 9781098119447, free online at marabos.nl/atomics. Cite only these, by chapter subject; no chapter numbers unless the writer has the table of contents in front of it (McKenney's and Bos's are online).
- Anything beyond these pins is marked 大致 / "check the docs".

## Lab environment (`topics/parallel-programming/lab-setup/index.html`)

The Mac is the lab. Why no VM: these labs measure the hardware, so they must run on it; nothing here loads code into the kernel. What to install: Homebrew `libomp` (and optionally `llvm`); nothing else. How to measure: `clock_gettime(CLOCK_MONOTONIC)` or `std::chrono::steady_clock`, pinned by repetition, warm-up and the median; CPU time versus wall time; `sysctl` for the core layout; QoS classes instead of affinity (macOS offers no CPU pinning; `pthread_set_qos_class_self_np`, GCD queue QoS). Profilers on this Mac: `sample <pid>` and `spindump` for call stacks, `dtrace` where SIP allows, `leaks`; Instruments only with Xcode (optional path); the kernel VM for `perf stat` and `perf record` when a hardware-counter view is needed. Sanitizers: `-fsanitize=thread` for races, `-fsanitize=address` for memory. One diagram: the lab Mac's cores (4 P, 6 E), the two L2 clusters, the shared memory, and where each tool observes. Lab: install `libomp`, run the OpenMP smoke test, run a `sample` on a spinning program, read the core layout.

## Phases (eight, 0–7; each with two diagrams, Lab A and Lab B, a four-question quiz, resources, bibliography)

### Phase 0 · 基础 · Foundations (`phase-0-foundations`)
Why parallel (frequency wall, Amdahl's and Gustafson's laws, strong and weak scaling); Flynn's taxonomy in one paragraph; the machine: cores, P and E clusters, caches, cache lines and false sharing, memory bandwidth, no SMT or NUMA here versus x86 servers; what the kernel does with threads (link kernel Phase 1: a thread is a task, the scheduler picks cores). Measurement basics: wall versus CPU time, variance, warm-up, median of N. Table: strong ↔ weak scaling. Diagram (a): speedup against cores for serial fractions 0, 10 %, 50 %. Diagram (b): the memory hierarchy with a 128-byte line shared by two cores. Lab A: time a sum over a large array with 1, 2, 4, 8, 10 threads (std::jthread), plot speedup. Lab B: false sharing: two counters in one cache line versus padded to 128 bytes.

### Phase 1 · 线程与操作系统 · Threads and the OS (`phase-1-threads-and-the-os`)
pthreads, `std::thread` and `std::jthread`, GCD (`dispatch_async`, `dispatch_apply`, groups), thread creation cost, join and detach, stack size, thread-local storage, the context switch (link kernel Phase 1), QoS classes on macOS versus priorities and affinity on Linux, thread pools, oversubscription. Table: pthreads ↔ std::thread ↔ GCD. Diagram (a): a thread's life from `pthread_create` to the scheduler and back. Diagram (b): a thread pool with a work queue. Lab A: measure spawn and join cost per thread; compare with a GCD queue. Lab B: watch the threads with `sample` and `spindump`; oversubscribe to 100 threads and measure.

### Phase 2 · 共享内存与同步 · Shared Memory and Synchronization (`phase-2-synchronization`)
Data races and their definition; mutexes, condition variables, semaphores, reader-writer locks, spinlocks, `os_unfair_lock`; lock granularity, lock ordering and deadlock, priority inversion and inheritance (link kernel Phase 3), convoying; TSan. Table: mutex ↔ spinlock ↔ RW lock ↔ atomic. Diagram (a): two threads racing on a counter, then under a lock. Diagram (b): a deadlock from inverted lock order, then the ordered version. Lab A: a race found by `-fsanitize=thread`, fixed three ways (mutex, atomic, per-thread sum). Lab B: lock contention versus thread count, measured.

### Phase 3 · 内存模型与原子 · Memory Models and Atomics (`phase-3-memory-model-and-atomics`)
Sequential consistency and why hardware does not give it; the C11/C++20 memory model: relaxed, acquire, release, acq_rel, seq_cst; happens-before and synchronizes-with; fences; compare-exchange and the ABA problem; ARM64's weak ordering (`ldar`, `stlr`, `dmb`) versus x86 TSO; what the compiler may reorder. Table: the memory orders ↔ what they promise ↔ the ARM64 instruction. Diagram (a): store buffering: both threads read 0 under relaxed order on ARM64, not under seq_cst. Diagram (b): message passing with release and acquire. Lab A: Dekker's algorithm with relaxed atomics fails on the M5; fix with seq_cst; count the failures. Lab B: a lock-free counter and a spin lock from `atomic_flag`, with the disassembly read (`clang -O2 -S`).

### Phase 4 · 无锁结构 · Lock-free and Wait-free Structures (`phase-4-lock-free-structures`)
Progress guarantees (blocking, lock-free, wait-free); the Treiber stack; the Michael–Scott queue; memory reclamation: hazard pointers, epochs, RCU (link kernel Phase 3); seqlocks; when a lock is faster. Table: lock-free ↔ wait-free ↔ blocking. Diagram (a): a Treiber push and pop with the ABA case. Diagram (b): RCU readers and a writer across a grace period. Lab A: a Treiber stack and the ABA failure, then a tagged pointer. Lab B: a seqlock protecting a 64-byte record, measured against a mutex.

### Phase 5 · 结构化并行 · Structured Parallelism (`phase-5-structured-parallelism`)
Fork-join, `#pragma omp parallel for`, schedules (static, dynamic, guided), reductions, tasks and dependencies; GCD `dispatch_apply` and groups; work stealing; load balancing; granularity; C++17 parallel algorithms (`std::execution::par`: say whether Apple's libc++ implements them, "check the docs"); Amdahl met in practice. Table: OpenMP ↔ GCD ↔ hand-rolled threads. Diagram (a): a parallel-for split into chunks under static versus dynamic schedule. Diagram (b): work stealing between two deques. Lab A: matrix multiply with OpenMP, schedules compared. Lab B: the same with `dispatch_apply`; a recursive task tree (Fibonacci or quicksort) with OpenMP tasks.

### Phase 6 · SIMD 与数据并行 · SIMD and Data Parallelism (`phase-6-simd`)
Data parallelism inside one core: NEON (128-bit lanes), intrinsics, auto-vectorization and the remark flags (`-Rpass=loop-vectorize`, `-Rpass-missed=loop-vectorize`), alignment, AoS versus SoA, horizontal reductions, the Accelerate framework (`vDSP`), memory bandwidth and the roofline model. Table: scalar ↔ auto-vectorized ↔ intrinsics ↔ Accelerate. Diagram (a): four lanes adding in one instruction. Diagram (b): AoS versus SoA under a vector load. Lab A: a dot product scalar versus NEON intrinsics versus `vDSP_dotpr`, measured. Lab B: make a loop vectorize by reading the missed-vectorization remarks.

### Phase 7 · 性能测量与作品项目 · Measuring Performance and the Capstone (`phase-7-measurement-and-capstone`)
Benchmarking method (warm-up, repetition, median, variance, pinning what can be pinned), `sample` and `spindump` reading, `dtrace` one-liners that work under SIP, Instruments when Xcode is present (optional), Linux `perf stat` and `perf record` in the kernel VM for cache misses and branch misses, diagnosing false sharing and bandwidth limits, the roofline in numbers for the M5 (bandwidth measured in the lab, not quoted). Capstone: a parallel image or n-body pipeline that combines threads, OpenMP and NEON, with a measurement report. What comes next: GPU Programming with CUDA (planned), Kernel Engineering Phase 3 for the kernel side. Diagram (a): a measurement loop from hypothesis to profile to fix. Diagram (b): the roofline with three kernels placed on it. Lab A: profile the Phase 5 matrix multiply with `sample`, find the hot loop, apply Phase 6, measure. Lab B: run `perf stat` on the same program in the kernel VM; compare the counters with the Mac's wall times.
