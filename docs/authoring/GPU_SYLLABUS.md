# GPU Programming with CUDA topic syllabus (authoring spec)

Topic id `gpu-cuda`, folder `topics/gpu-cuda/`, progress key `gpu`, hub card title "GPU 编程与 CUDA · GPU Programming with CUDA". Written against `docs/authoring/PAGE_CONTRACT.md`. Goal for the learner: write, measure and profile CUDA kernels on a real NVIDIA GPU, understand the GPU's execution and memory model from the warp up to the driver, and carry the same ideas to Metal on the Mac. The Mac has no NVIDIA GPU (Founder direction 2026-10-30: cloud GPU labs, Metal as the local counterpart), so every CUDA lab runs on a cloud GPU and every page offers a Metal twin that runs here. Reader: has done Parallel Programming (threads, memory model, SIMD, roofline) and Kernel Engineering (drivers, DMA, page faults).

## Pinned facts (verified 2026-10-31/11-01 unless noted)

- **CUDA Toolkit:** the 13.2 line (13.2 Update 1 release notes dated 2026-04-12; an Update 2 exists). docs.nvidia.com refuses scripted fetches from this seat; the writer of the lab page reads the release-notes page itself and names the exact version, the minimum Linux driver, and the supported Ubuntu versions. Target `sm_75` or newer for every lab so a free Colab T4 works; say when a feature needs newer (tensor cores on T4 are FP16 only; `cudaMallocAsync` from 11.2; CUDA graphs from 10; cooperative groups' grid sync needs supported hardware).
- **Book:** Wen-mei W. Hwu, David B. Kirk, Izzat El Hajj, *Programming Massively Parallel Processors: A Hands-on Approach*, 4th ed., Morgan Kaufmann, August 2022, ISBN 9780323912310 (580 pp.). Primary text; cite by chapter subject unless the writer has the table of contents (the publisher's page lists it). Two older books may be cited only after the writer verifies them: Jason Sanders and Edward Kandrot, *CUDA by Example*, Addison-Wesley, 2010; John Cheng, Max Grossman, Ty McKercher, *Professional CUDA C Programming*, Wrox, 2014. Official documents are primary sources: the CUDA C++ Programming Guide, the CUDA C++ Best Practices Guide, the Nsight Compute and Nsight Systems user guides, the PTX ISA, the `compute-sanitizer` and `cuda-gdb` guides.
- **Local counterpart:** Metal 4 (announced WWDC 2025; Metal Shading Language Specification version 4 dated 2025-10-23; macOS 26 or later on M1 or later). The lab Mac runs macOS 27.2 on an M5. **Verified on the lab Mac 2026-11-01:** with the Command Line Tools alone, a Swift program compiles a Metal compute kernel from source at runtime (`MTLDevice.makeLibrary(source:)`), builds a pipeline state, dispatches it and reads the result; the writer of the lab page pastes that program and its output (device name, `threadExecutionWidth`, `maxTotalThreadsPerThreadgroup`, GPU time). The offline Metal compiler (`xcrun metal`) is not part of the Command Line Tools; say so and use runtime compilation on every page. Metal terms map as: kernel function ↔ `kernel` function; grid/block/thread ↔ grid/threadgroup/thread; warp ↔ SIMD-group (`threadExecutionWidth`, 32 on Apple GPUs, writer confirms from the printed value); shared memory ↔ threadgroup memory; `__syncthreads` ↔ `threadgroup_barrier`; stream ↔ command queue and command buffer; unified memory ↔ Apple's unified memory (`MTLStorageModeShared`).
- **Cloud GPU (prices move; the lab page says "check the provider page today" and gives one budget estimate):** Google Colab's free tier gives a T4 (Turing, `sm_75`, 16 GB) with timeouts and queues, enough for Phases 0–3; from Phase 4 (Nsight Compute) a rented machine with SSH is needed: RunPod lists the L4 (Ada, `sm_89`, 24 GB) from about $0.39 per GPU-hour (tracker dated 2026-08-04), Vast.ai is a marketplace with lower but interruptible prices, Lambda Cloud from about $1.10/hr with CUDA preinstalled, GCP G2 L4 from about $0.71/hr. Renting is the Founder's spend (R-AP-9(a)); the pages describe the path and the writer runs nothing in the cloud unless the Founder has opened an account and said so. Until then every CUDA lab is marked "not run; assembled from the CUDA documentation on <date>", exactly as the ROS 2 pages do, and the Metal twins are run on the Mac and pasted with numbers.
- **Container:** NVIDIA's `nvidia/cuda:<version>-devel-ubuntu24.04` images (writer verifies the exact 13.2 tag on Docker Hub) for the rented machine; on Colab the toolkit is preinstalled (`!nvcc --version`, `!nvidia-smi`).
- Anything beyond these pins is marked 大致 / "check the docs".

## Lab environment (`topics/gpu-cuda/lab-setup/index.html`)

Why this shape: no NVIDIA GPU on the Mac, no CUDA on macOS since 10.13. Three tiers: 1. Colab free T4 for Phases 0–3 (a notebook with `%%writefile kernel.cu` and `!nvcc -arch=sm_75 kernel.cu -o kernel && ./kernel`; session limits; save files to Drive). 2. A rented GPU box with SSH for Phases 4–7 (`nvidia-smi`, the NGC container, `ncu` and `nsys` need a real shell; one budget estimate for the whole topic at an L4 rate). 3. The Mac for the Metal twins (Swift + runtime-compiled MSL; `xcrun swiftc`; no Xcode needed). Lab: `nvidia-smi` and `nvcc --version` on Colab with a vector add; the Metal vector add on the Mac with its printed output.

## Phases (eight, 0–7; each with two diagrams, Lab A (CUDA, on the cloud tier) and Lab B (the Metal twin on the Mac, run), a four-question quiz, resources, bibliography)

### Phase 0 · 基础 · Foundations (`phase-0-foundations`)
Why GPUs: throughput over latency, thousands of threads, the SIMT model against the SIMD of Parallel Phase 6 (link `../../parallel-programming/phase-6-simd/index.html`); the CUDA programming model: host and device, kernels, grid, block, thread, warps of 32, `threadIdx`/`blockIdx`/`blockDim`; memory spaces at a glance; the toolchain (`nvcc`, `nvidia-smi`, `-arch=sm_75`); a first kernel (vector add) with error checking (`cudaGetLastError`, a check macro); timing with events. Table: CPU thread ↔ GPU thread ↔ Metal thread terms. Diagram (a): grid → blocks → warps → SMs mapping. Diagram (b): host-device flow: `cudaMalloc`, `cudaMemcpy`, launch, `cudaDeviceSynchronize`. Lab A: vector add on Colab, timed with events, size sweep. Lab B: the same in Metal on the Mac, run, with `threadExecutionWidth` and GPU time printed.

### Phase 1 · 内存层次 · The Memory Hierarchy (`phase-1-memory-hierarchy`)
Global, shared, registers, local, constant, L1/L2, texture; coalescing (a warp's 32 accesses into cache lines), bank conflicts, tiled matrix multiply with shared memory, `__syncthreads`, unified memory and pinned host memory, page faults on unified memory (link `../../kernel-engineering/phase-2-memory/index.html`). Table: memory space ↔ scope ↔ latency class ↔ Metal twin. Diagram (a): coalesced versus strided warp access to global memory. Diagram (b): tiled matmul: the tiles each block loads into shared memory. Lab A: naive versus tiled matmul, bandwidth of coalesced versus strided copies. Lab B: tiled matmul in Metal with threadgroup memory, run.

### Phase 2 · 执行与调度 · Execution and Scheduling (`phase-2-execution-and-scheduling`)
The SM: warp schedulers, latency hiding by warp switching, occupancy (registers and shared memory per block, `--ptxas-options=-v`, the occupancy API), branch divergence inside a warp, independent thread scheduling (Volta+), `__syncwarp`, block scheduling across SMs; what the driver does on launch (link `../../kernel-engineering/phase-5-device-drivers/index.html`: the driver, MMIO and DMA under `cudaLaunchKernel`). Table: occupancy limiters ↔ fix. Diagram (a): a warp scheduler with ready and stalled warps across cycles. Diagram (b): divergence: a warp splitting on `if`, both paths serialized. Lab A: occupancy sweep with register pressure and block size, divergence cost measured. Lab B: Metal SIMD-group width and divergence in a Metal kernel, run.

### Phase 3 · 并行模式 · Parallel Patterns (`phase-3-parallel-patterns`)
Reduction (tree in shared memory → warp shuffles `__shfl_down_sync`), scan (Hillis–Steele versus Blelloch), histogram with atomics and privatization, stencil, radix sort in outline, the library forms: Thrust, CUB, cuBLAS, cuDNN as examples. Table: pattern ↔ work and span ↔ CUDA building block. Diagram (a): tree reduction with warp shuffles. Diagram (b): the work-efficient scan's up-sweep and down-sweep. Lab A: reduction from naive to shuffle, measured; scan. Lab B: reduction with `simd_sum` and threadgroup memory in Metal, run.

### Phase 4 · 性能剖析与优化 · Profiling and Optimization (`phase-4-profiling-and-optimization`)
Nsight Systems (timeline, launch overhead, copies) and Nsight Compute (`ncu`: achieved occupancy, memory throughput, the roofline section, warp stall reasons), the GPU roofline against Parallel Phase 7's (link `../../parallel-programming/phase-7-measurement-and-capstone/index.html`), memory-bound versus compute-bound, tensor cores (`wmma`, FP16 on T4, TF32/BF16 on newer), cuBLAS as the ceiling. Table: ncu metric ↔ what it tells you. Diagram (a): the roofline with naive, tiled and cuBLAS matmul. Diagram (b): the SM's tensor-core path and its data types. Lab A: profile the Phase 1 matmul in ncu, fix the top stall, compare with cuBLAS. Lab B: Metal's GPU counters through `MTLCounterSampleBuffer` where available, else timing only, run.

### Phase 5 · 流、图与并发 · Streams, Graphs and Concurrency (`phase-5-streams-and-graphs`)
Asynchronous copies, streams and events, overlapping transfer and compute, pinned memory, CUDA graphs (capture, instantiate, replay; launch overhead), multi-GPU basics (peer access, NCCL in outline), MPS in one paragraph. This is what the SGLang topic will build on (CUDA graphs for decode). Table: stream ↔ command queue; event ↔ shared event; graph ↔ indirect command buffer (approximate). Diagram (a): a timeline with copies overlapping kernels on four streams. Diagram (b): graph capture and replay. Lab A: pipeline a workload over four streams; capture a graph and measure launch overhead. Lab B: Metal command buffers and encoders with overlapping work, run.

### Phase 6 · 内存管理与宿主集成 · Memory Management and Host Integration (`phase-6-memory-management`)
Unified memory with prefetch and advice, zero-copy, `cudaMallocAsync` and memory pools, caching allocators (PyTorch's in outline), pinned memory and DMA (link kernel Phase 5), device-side asserts, `compute-sanitizer` (memcheck, racecheck, initcheck), `cuda-gdb`. Table: allocation API ↔ where memory lives ↔ when to use. Diagram (a): unified memory page migration on first touch. Diagram (b): a memory pool serving allocations across streams. Lab A: unified memory with and without prefetch, measured; `compute-sanitizer` on a kernel with a race. Lab B: Metal shared versus private storage modes on Apple's unified memory, run.

### Phase 7 · 软件栈、可移植性与作品项目 · The Stack, Portability and the Capstone (`phase-7-stack-and-capstone`)
Runtime API versus driver API, PTX and SASS, JIT and fatbins, `-arch` and `-gencode`, forward compatibility, the NGC container, portability (HIP, SYCL, Kokkos in outline; Metal on Apple), kernels for PyTorch (custom ops; Triton in outline, pointing at the LLM Inference Kernels topic), the capstone: a fused softmax or layer-norm kernel measured against cuBLAS or PyTorch, or an n-body with shared-memory tiling, with a profiling report, plus its Metal twin. Diagram (a): nvcc → PTX → SASS → JIT at load. Diagram (b): the capstone kernel's data flow. Lab A: build the capstone and profile it. Lab B: its Metal twin on the Mac, run, with the two results compared in a table. What comes next: LLM Inference Kernels (SGLang) (planned), Parallel Programming for the CPU side.
